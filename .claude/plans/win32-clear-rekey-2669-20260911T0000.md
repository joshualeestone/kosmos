# win32-clear-rekey-2669 -- a Windows agent stays on the board after /clear (#2669)

Addresses #2669 (and #570). Design by Renet Tilley on the issue (2026-09-10),
implemented here at his recommendation, because it changes code this lane owns
(`win32streamstate`, `win32supervisor`) and only this box can verify it live.

## The defect

`/clear` rotates a streaming session's id: the pid stays the same and the
`session_id` is new. Three holders of the old id did not follow it:

1. **Ownership** (`win32sessions`). `win32live.byName` joins the live list to it
   BY session id, so the agent dropped off the board.
2. **The 7c-5 state file.** `stateFor` requires the session id to match, so it
   read UNKNOWN.
3. **`handle.sessionId`.** A crash relaunch `--resume`d the conversation from
   BEFORE the clear.

## Measured

- **On the box (review of 7c-5):** same pid 7812, the id changed, and the new id
  was listed in `claude agents --json` afterwards.
- **By Renet, on the protocol:** the new id appears on `conversation_reset`, on
  config-dependent hook events, then on the reset turn's `system`/`init`, in a
  top-level `session_id`.

- **On the box, the protocol (2026-09-11, `probe-clear-turns`).** A fresh session
  and a `--resume`d one behave the same: `/clear` gives `conversation_reset` (old
  id), then `system`/`init` with the NEW id, then a `result`, all within 0.1s. The
  live list shows the new id at once.
- **On the box, the defect through the real board (control, main 61594aa0).** The
  Memory "Clear" control (`POST /api/agent/<name>/clear`, #214) delivers a bare
  `/clear`. On winstream-1 the id rotated on the same pid (1ad73eff to a57c3084),
  the ownership record did not follow, the card read `stopped`, and a message sent
  afterwards could not be delivered.
- **What does NOT trigger it.** A thread message reading `/clear` arrives wrapped in
  the operator line (`engine/messages.js`), so the agent gets a prompt, not a
  command. Measured: no rotation, and one ordinary turn.

## Design (Renet's, unchanged)

- **`followSessionId(e)` in `superviseStreaming`.** It is gated on
  `system`/`init` only. For a new id, it records the new id FIRST, then moves
  `handle.sessionId`, calls `stream.rekey(id)`, forgets the old id LAST, and emits
  `rekeyed`. A failed record changes nothing and emits `rekey-failed`.
  - The stdout reader parses each event once and follows the id before handing
    the event to the state sink.
  - Only the current child can move the id.
- **`publisher.rekey(id)`** re-stamps the state file. It bumps `generation` so an
  old retry cannot act, and forces the write.
- **`win32sessions.js` is unchanged.**
- `sessions` is injectable in `superviseStreaming` so a test can make a record
  fail.

## Tests

- **`win32streamstate.test.js`:**
  - `rekey` re-stamps the id and forces the write;
  - it does nothing before a start, after a stop, or for a non-id;
  - an old retry cannot act after it;
  - on the real file, `stateFor` matches the new id and not the old one.
- **`win32supervisor.test.js`:**
  - a new-id init moves ownership, the resume id and the state file;
  - the same id, a hook event, or a replaced child's line changes nothing;
  - a failed record leaves everything on the old id and says so.
- **Live on the box:** deliver `/clear` through the board to a real agent and
  check that its card stays on the board, reads working then idle, and its
  ownership row now carries the new id.

## Order with the other open branch

`win32-resume-token-570` also edits `attach()` in `win32supervisor.js`. It merges
first; this branch is then rebased onto it (a small, known conflict at the stdout
reader and the death handler).

## Weakest part

- **The init gate.** It assumes every rotation is announced on an `init`. Renet's
  measurement shows `/clear` does this. Whether `/compact` rotates the id is
  unmeasured; if it does, the same gate follows it.
- **The create window.** `win32create.awaitSession` accepts any new row with a
  matching name during a create. A `/clear` inside the first seconds of a create
  could be taken as the create's own row. That window is seconds long and needs a
  message to arrive before the agent is even on the board.
