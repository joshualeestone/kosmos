## Why

look for, that's the most basic generic set of app features that have to exist."*

Every native complaint he raised today is one gap. `buildMenu()` in

## What finished looks like

A person who has used a Mac before presses Cmd-H, Cmd-M, Cmd-Z, Cmd-W or Cmd-comma in
Kosmos and each does the conventional thing, without knowing anything about Kosmos.
Stated as a test rather than a feeling: every item in the table below exists in the
menu bar with the listed shortcut, and the release gate proves it rather than a person
remembering to check.

## Scope

**A. The menu bar** (`native-app/main.swift`, `buildMenu()`):

| Menu | Items |
|---|---|
| Kosmos | About Kosmos, Settings… (⌘,), Services, Hide (⌘H), Hide Others (⌥⌘H), Show All, Quit (⌘Q) |
| Edit | Undo (⌘Z), Redo (⇧⌘Z), Cut, Copy, Paste, Select All |
| View | Reload (⌘R) |
| Window | Minimize (⌘M), Zoom, Close (⌘W), Bring All to Front |

Notes that decide the implementation:
- Hide / Hide Others / Show All / Services / Minimize / Zoom / Bring All to Front are
  AppKit-supplied actions. The item is what carries the key equivalent, so these are
  item declarations, not new behaviour.
- **Undo/Redo are NOT free.** `NSText.undo:` does not exist; undo in a WKWebView comes
  from the web content's own undo manager. The item must target the responder chain
  with `undo:`/`redo:` and WKWebView must honour it. ⚠️ VERIFY BY PRESSING, not by
  reading: this is the one row on the table that can compile, appear in the menu, and
  still do nothing. If it does not work, say so and card the real fix rather than
  shipping a menu item that lies.
- **Settings… (⌘,)** must open Kosmos's own Settings screen, which lives in the web
  app. So it is not an AppKit action: it needs a message into the page (the same
  mechanism `reloadBoard` uses to reach the webView), and the page needs to accept
  "open settings". If that seam does not exist yet, this row is a real piece of work
  and not a one-liner.
- **About Kosmos** should carry the version, because #(reload-button card) exists
  precisely because nobody can find the version. Feed it the same version string the
  footer reads rather than a second source. ⚠️ Two sources for one version is the
  drift pair this codebase keeps finding; use one.
- **Close (⌘W)** interacts with the existing quit-vs-close seam
  (`windowShouldClose`, `QuitBehavior.closingWindowQuits`). Do not add ⌘W without
  reading that: the app deliberately distinguishes closing the window from quitting,
  and a naive `performClose:` can route into the quit dialog.

**B. Reload means one thing** -- ⛔ **NOT ON THIS BRANCH.** It is #995 and it lives in

## What was actually built (2026-08-26 14:3x CT)

**The menu bar went from 6 shortcuts to 19.** `buildMenu()` was split into a pure
`makeMainMenu(reloadTarget:settingsTarget:)` that CONSTRUCTS the bar and a `buildMenu()`
that assigns it, so the structure can be inspected without a window server.

**The gate exists and it is proven to fail.** `--kosmos-app-menu-selftest` follows the
three hatches already in `main.swift` (`--kosmos-app-selftest`, the port one, the reload
decision table): it walks the constructed menu, prints every menu/item/shortcut/action,
and exits before `NSApplication`. `tools/build-kosmos-bundle.sh` diffs it against the
expected table, timeboxed with the same `perl -e 'alarm 15'` the reload table uses, so a
drifted hatch flag falls through to `app.run()` and fails rather than hangs.
⭐ **Verified by breaking it:** removing `Hide Kosmos`, recompiling and re-running the
hatch changes the dump by exactly that line, so the gate catches a vanished item. A gate
that has never been seen to fail is not a gate.

**Settings (⌘,) does not discard a draft.** The obvious implementation, navigating to
`/?tab=settings`, would throw away anything typed into an instructions or description
field, and this app is full of them. It asks the page to switch tabs in place (the same
`showTab` the tabs themselves call) and only navigates if that function is absent, which
would mean the page is an older build than the binary.

**⌘W routes through `performClose:`**, which fires `windowShouldClose` -- the same path
the red button takes -- so the keyboard and the button keep one meaning and the existing
quit-vs-close seam is untouched.

## ⚠️ What is NOT proven, stated plainly

The gate is **structural**: it proves an item exists carrying that key equivalent. It
cannot prove the action does anything. **Undo/Redo and Settings are the two rows that can
be present and inert**, and neither has been pressed by a person yet:

- Undo/Redo are nil-targeted and travel the responder chain to the WKWebView, whose own
  undo manager has to honour them. If nothing in the chain implements `undo:`, AppKit's
  automatic menu validation greys the item out, so the failure is VISIBLE rather than
  silent. ✅ **Checked, not assumed:** `autoenablesItems` is set nowhere in `main.swift`,
  so the AppKit default (`true`, automatic validation) applies. Had some line turned it
  off, an unimplemented action would have stayed enabled and silently done nothing, which
  is the failure mode this row is most at risk of.
- Settings depends on `showTab` being a global on the page.

Both need one headed press. Recorded as owed rather than quietly assumed.
