# #4458: test-cut-load-guard passes inside a parallel cut

## Why
Found by the 0.7.07 staging cut (Baron, 20:36 CDT): `KOSMOS_CUT_PARALLEL=1 release.sh` failed its own step 3, because
step 3 runs the suite inside the cut's environment and this test's "default is serial" arm inherited the flag. It
blocks the #2760 parallel measurement; 0.7.07 was cut serial meanwhile.

## Measured before the fix
Every variable the guard reads breaks an arm when inherited, not only the one the card names:
KOSMOS_CUT_PARALLEL (default is serial), KOSMOS_CUT_PARALLEL_MIN_CORES (min-cores default),
KOSMOS_CUT_PARALLEL_MAX_LOAD (max-load default), KOSMOS_FAKE_LOAD (field-index guard), KOSMOS_LOADAVG_RAW (live
parse), KOSMOS_CUT_MAX_LOAD (default threshold). The sibling test-cut-parallel-region.sh passes with all of them
set hostile: it already controls its environment.

## Change (tools/test-cut-load-guard.sh)
- After sourcing the guard, unset every KOSMOS_ variable the guard reads, listed FROM tools/lib/cut-load-guard.sh,
  so a variable it gains later is cleared too. An empty list fails loudly instead of clearing nothing.
- A regression arm reruns the whole file once with every one of those variables set to a value that would break
  an arm if it leaked. Removing the unset makes the file fail even in a clean shell.

## Decided
- Rejected: a hand-written unset list (the card's suggestion): a copied list goes stale when the guard gains a
  variable, and nothing would say so.
- Rejected: `env -u` per `parok` case: it covers the parok arms only, not the default and parse arms that also
  broke.
- Weakest premise: the grep reads `$KOSMOS_X` / `${KOSMOS_X` in the guard. A variable read another way (for
  example through `printenv` or an indirect name) would not be listed. None is today.
