## Next: coordinator APNs (kosmos-relay, Kano)
Storage: its **own table**, not a kind column. `push_subscriptions` has web push
columns as NOT NULL (p256dh, auth), and SQLite cannot relax those without a table
rebuild; a sibling table keeps the web push path untouched.

    apns_tokens (
      token        TEXT PRIMARY KEY,     -- hex device token
      account_id   TEXT NOT NULL,        -- from the session, never the body
      device_id    TEXT NOT NULL,        -- from the session, never the body
      bundle_id    TEXT NOT NULL,        -- must be on the coordinator's allow list
      environment  TEXT NOT NULL,        -- 'production' | 'sandbox'
      created_at   INTEGER NOT NULL
    )

Sender: `fan_out` keeps one set of device gates (not denied; acked on THIS Mac,
#1221) and then delivers to both the web subscriptions and the APNs tokens of each
admitted device. An `ApnsSender` (HTTP/2 to api.push.apple.com or the sandbox host,
ES256 provider JWT from the .p8, Key ID and Team ID, reused under its 60 minute limit)
sits beside `VapidSender`. A 410 `Unregistered` or 400 `BadDeviceToken` prunes the
token, as 404/410 do for web push. Built and tested against a mock APNs until the real
key arrives; the key is filed by Liu Kang with /add-secret and read by lookup target
only, never pasted.

### Route contract (for Johnny, iOS)
- `POST /v1/push/apns/register`
  - Header `Authorization: Bearer <session KST>`: the same session the phone signed
    in with (the coordinator derives account and device from it, and refuses a
    device the account denied, exactly as `/v1/push/subscribe` does).
  - Body `{"token": "<hex APNs device token>", "bundle_id": "<app bundle id>",
    "environment": "production" | "sandbox"}`.
  - 200 `{"ok": true}`; 400 on a malformed token, unknown bundle id or environment;
    401 on a missing or bad session; 403 for a refused device. Idempotent: the same
    token again updates the row.
- `POST /v1/push/apns/unregister`, same auth, body `{"token": "..."}`, 200 either way.
- What arrives on the phone: `aps.alert.title` "<agent> needs you" or "<agent>
  replied", `aps.alert.body` "on <project>" or "in Kosmos", `aps.sound` "default",
  plus top-level `address` (the Mac's host; a tap opens `https://<address>/`), `id`
  and `kind`. Never message text. No notification category yet: the Mac does not
  say whether a needs_you is a permission prompt, so Approve/Deny waits for that.
- **Session to the app: the WebView bridge (Liu Kang, decided 2026-09-24).** The
  coordinator sign-in page, after admission, posts the session token to
  `window.webkit.messageHandlers.kosmosSession` if it exists (a no-op in a normal
  browser). The app uses it only for `/v1/push/apns/register` and `/unregister`. Johnny
  builds in: accept only from the main frame when its `securityOrigin` is the
  coordinator's origin; keep the token in memory or the Keychain, never UserDefaults,
  never logged. Why: one sign-in, no second auth surface, and the native surface Apple
  Review 4.2 expects. Would change if Apple review or the #2854 origin decision rules out
  the coordinator page inside the app. The page change is in kosmos-relay
  `.claude/plans/apns-718.md`.

## Android (Sonya, after #3610)
The TWA can show web push under the app's own identity (notification delegation), so
the coordinator side already exists: `GET /v1/push/vapid-key` and
`POST /v1/push/subscribe` with a Bearer session. What decides the rest is the TWA's
origin (#2854, with Splinter): a subscription must be made on the origin the app is
verified for. If that origin is the coordinator's, today's subscribe works inside the
app unchanged. If it is a separate front door, that origin needs an in-origin
subscribe that carries the session to the coordinator (CORS on these two routes, or a
front-door proxy), which is where #3520's retired client flow is the starting point.
fan_out already delivers to every endpoint an account holds, so the app's subscription
sits beside any other with no coordinator change.

# webpush-718: phone push notifications, v1 (UNPARKED 2026-09-24)

Josh ruled YES on push (2026-09-24 13:41 CDT): "100% the main reason we want mobile
apps is for push notifications." Kano leads. Liu Kang's design calls, checked against
the code below. Where the code disagrees, that is said and a call is made.

## Finished means
1. With phone notifications OFF (the default), nothing about agents leaves the Mac.
   Proven by a test with a counting sender, not by reading the code.
2. A person turns them on from Settings, subscribes a phone on the coordinator's page,
   and when an agent reports needs_you a real notification lands on that phone.
3. Tapping it opens that Mac's board.
4. Turning it off stops all sending at once.

## Decisions
- **Subscribe path: option C.** (Superseded 2026-09-24 14:33 by the apps-only re-plan at the top: Settings now points to the Kosmos phone app.) The phone subscribes on the coordinator's own page
  ("Notify me on this phone", coordinator/src/signin.html). The board's Settings links
  there. No new security surface. Under C nothing calls the board's own `/v1/push/*`
  routes, so the vapid-key proxy, the subscribe 501 and the board-origin subscribe
  flow in the Settings client (#3520) are removed rather than left looking live.
  Option A would bring them back from history.
- **The gate is a switch on the Mac, off by default. That differs from "send only when a
  phone has opted in"**, because the Mac cannot see phone subscriptions: they live on
  the coordinator, and no Mac route reports them. Turning the switch on is part of the
  same Settings step that sends the person to subscribe a phone. Follow-up if wanted: a
  Mac-signed coordinator route that reports whether the account has any subscriptions,
  so a Mac with the switch on but no phone also stops sending.
- **needs_you pushes on the change INTO needs_you**, not on every repeat report (the
  deleted notify.js pushed on every one). The project name is sent when the report
  names a project.
- **Events: needs_you and replied.** needs_you is the reason push exists. replied is an
  agent answering the person in their own thread, so it is addressed to them. Not
  posted (room chatter would buzz constantly) and not check_in (heartbeat). All three of
  needs_you, replied and posted are in the coordinator's KINDS, so this is a board
  choice and one line to change.
- **Payload is the coordinator's EventReq and nothing more:** agent name, session name,
  project name (needs_you, when the report names one; null for replied), event id,
  time, kind, plus a notify install id the credential is bound to. No message text. The coordinator adds the Mac address
  itself.
- **The notify install id is NOT ping.installId().** #2631 kept installId() on the
  promise that it "never leaves the Mac". Push mints its own random id, used only to bind
  the notify credential.
- **Credential:** the coordinator mints a notify-only token at
  `POST /v1/mac/notify-credential`, which needs the Mac's signature. Only the
  kosmos-tunnel binary signs (the board keeps "NO CRYPTO HERE"), and it has no verb for
  this. So: **a new tunnel verb in kosmos-relay** that mints and prints the token on
  stdout. The board stores it owner-only in the remote state dir and never logs it.
- **Sender:** fire and forget, never throws, never sends under node --test without an
  injected sender, and sends only when switch ON + enrolled + credential present.

## Heads-up for Josh (not a blocker)
The coordinator emails the account about a needs_you nobody has acknowledged after 30
minutes (#3540, when its needs_you_email flag is on), whether or not a phone is
subscribed. So turning phone notifications on can also produce those emails. The
Settings copy says so.

3. Live: local coordinator + real Chrome (kosmos-relay docs/live-push-check.sh) to prove

Related, found while scoping: #3626 (board Mac-route calls send no signature).

## Review-driven changes (challenge loop)
- Caps are counted in UTF-8 bytes (the coordinator's `String::len`), never cutting a
  character.
- Turning on always mints a fresh token (the coordinator keeps the latest, so a token it
  no longer knows is never reused), and only one turn-on runs at a time.
- A tunnel too old for `mac-request` says this computer needs an update, rather than
  blaming Kosmos+.
- At most one needs_you buzz per agent per 5 minutes: permission prompts file a
  needs_you each, so a busy session would otherwise buzz on every one. Replies are not
  limited.
- needs_you carries the agent's current project (carried forward when the report
  names none), by name.
