## Finished means
1. With phone notifications OFF (the default), nothing about agents leaves the Mac.
   Proven by a test with a counting sender, not by reading the code.
2. A person turns them on from Settings, subscribes a phone on the coordinator's page,
   and when an agent reports needs_you a real notification lands on that phone.
3. Tapping it opens that Mac's board.
4. Turning it off stops all sending at once.

## Decisions
- **Subscribe path: option C.** The phone subscribes on the coordinator's own page
  ("Notify me on this phone", coordinator/src/signin.html). The board's Settings links
  there. No new security surface. #3510's `POST /v1/push/subscribe` 501 stays.
- **The gate is a switch on the Mac, off by default. That differs from "send only when a
  phone has opted in"**, because the Mac cannot see phone subscriptions: they live on
  the coordinator, and no Mac route reports them. Turning the switch on is part of the
  same Settings step that sends the person to subscribe a phone. Follow-up if wanted: a
  Mac-signed coordinator route that reports whether the account has any subscriptions,
  so a Mac with the switch on but no phone also stops sending.
- **Events: needs_you and replied.** needs_you is the reason push exists. replied is an
  agent answering the person in their own thread, so it is addressed to them. Not
  posted (room chatter would buzz constantly) and not check_in (heartbeat). All three of
  needs_you, replied and posted are in the coordinator's KINDS, so this is a board
  choice and one line to change.
- **Payload is the coordinator's EventReq and nothing more:** agent name, session name,
  project name (null for these two kinds), event id, time, kind, plus a notify install
  id the credential is bound to. No message text. The coordinator adds the Mac address
  itself.
- **The notify install id is NOT ping.installId().** #2631 kept installId() on the
  promise that it "never leaves the Mac". Push mints its own random id, used only to bind
  the notify credential.
- **Credential:** the coordinator mints a notify-only token at
  `POST /v1/mac/notify-credential`, which needs the Mac's signature. Only the
  kosmos-tunnel binary signs (the board keeps "NO CRYPTO HERE"), and it has no verb for
  this. So: **a new tunnel verb in kosmos-relay** that mints and prints the token on
  stdout. The board stores it owner-only in the remote state dir and never logs it.
- **Sender:** fire and forget, never throws, never sends under node --test without an
  injected sender, and sends only when switch ON + enrolled + credential present.

## Heads-up for Josh (not a blocker)
The coordinator emails the account about a needs_you nobody has acknowledged after 30
minutes (#3540, when its needs_you_email flag is on), whether or not a phone is
subscribed. So turning phone notifications on can also produce those emails. The
Settings copy says so.

# Web Push Implementation Plan (#718)

**Branch**: `webpush-718`  
**Pair**: Kano (client) + Raiden (Mac relay)  
**Date**: 2026-09-22

## Goal
Wire the outbound web-push SEND path from the Mac using existing VAPID keys in the coordinator. A push sent from the Mac reaches an installed PWA.

## Definition of Done
- Mac-side subscription storage: subscriptions persisted locally
- `/v1/push/subscribe` endpoint: receives and stores client subscriptions
- `/v1/push/vapid-key` endpoint: exposes public VAPID key for client
- Push delivery: events fan out to stored subscriptions
- End-to-end test: push from Mac → arrives in client PWA
- PR with code comments, passes `/challenge-loop`

When an event fires on the Mac (agent started, message received, etc.):
- Retrieve stored subscriptions
- Call coordinator's `fan_out()` logic to send to each subscription
- Coordinator handles encryption, VAPID JWT, and push service delivery

## Coordinator Contract
From `coordinator/src/push.rs`:

**POST /v1/push/subscribe**
- Request: `{ endpoint: "https://...", keys: { p256dh: "...", auth: "..." } }`
- Headers: `Authorization: Bearer <session-token>`
- Response: `{ ok: true }`
- Role: Stores subscription for authenticated device

**GET /v1/push/vapid-key**
- Response: `{ key: "<base64url-uncompressed-P256-point>" }`
- No auth required
- Role: Public key for `PushManager.subscribe()`

**Unsubscribe**: `/v1/push/unsubscribe` (DELETE)

## Risks & Tradeoffs
- **Subscription scope**: Per-account (all devices of one account). Kano confirms shape.
- **VAPID key caching**: Fetch once on startup, cache for app lifetime. Coordinator key rotation is rare; operator restart re-fetches.
- **Push service failures**: Coordinator handles 404/410 (dead subscriptions), logs others.

## Notes
- Coordinator already handles encryption (RFC 8291) and VAPID JWT (RFC 8292).
- Mac is outbound-only; subscriptions are POSTed TO the coordinator, not hosted on Mac.
- No inbound push service connection needed; coordinator reaches push services directly.

## Status 2026-09-24 (Kano): PARKED on two rulings, do not merge

Rebased onto main. `GET /v1/push/vapid-key` is wired for real (`engine/pushvapid.js`,
coordinator key, cached on success only, plain 502 on failure, tested in
`server.push-proxy-718.test.js`). `POST /v1/push/subscribe` is a deliberate 501.

Why subscribe is not wired: the contract above assumed the board holds the phone's
coordinator session token. It does not. The tunnel gate forgets the KST once the
phone is admitted and forwards no device identity to the board
(kosmos-relay `crates/tunnel/src/gate.html`, `proxy.rs`), and the coordinator's
subscribe requires `Bearer <phone session KST>`. Options sent to Liu Kang/Splinter:
A) tunnel injects a verified device header + new Mac-cert-authenticated coordinator
route; B) keep the KST in the tab (rejected, reverses the gate's deliberate forget);
C) drop board-origin subscribe and use the coordinator sign-in page's existing
"Notify me on this phone" (a tap opens `https://<mac>.<domain>/`, per
coordinator `sw.js` + `notify.rs:193`, reasoned from source, not measured on a phone).

Bigger blocker: no Mac sends events any more. `engine/notify.js`, the only caller of
the coordinator's `POST /v1/mac/notify`, was deleted on 2026-09-09 as a privacy call
(#2623, PR #2631, 7d0ff983). Until Josh rules on bringing it back (opt-in, off by
default) or shelving push, nothing reaches any phone whichever option is chosen.
