# fsyncwrite6-5434: trust.js's saves flush before they rename (#5434 slice 6)

Addresses #5434. Slices 1 to 5 moved the other stores onto `securewrite.writeSecret`, which flushes the temp before
the rename and the folder after it, so a crash cannot leave a file at full length but zero-filled (#5431). This
slice does the same for the last inline writers of a Claude Code account's files, all in `engine/trust.js`:

- `trustFolder`: the folder-trust line in `.claude.json`
- `forgetFolder`: its undo
- `preacceptBypass`: `skipDangerousModePermissionPrompt` in `settings.json`
- `preacceptOnboarding`: the first-run marker in `.claude.json`
- `writeRecordFile`: Kosmos's own `trust-writes.json` record

## Changes
- `engine/trust.js`: one helper, `saveConfig(target, data, prevMode)`, for the four Claude Code writers:
  `writeSecret(target, JSON + '\n', prevMode, { atomicOnly: true, ownTempsOnly: true })`, false on any failure.
  Each caller turns false into the same refusal sentence as before. The old `tempPath` (and its SEQ/STARTED) is
  gone. `writeRecordFile` saves with `{ atomicOnly: true, umaskDefault: true }`, carrying an existing record's
  mode (not on Windows), and still throws on failure. `securewrite` is required at the top: trust.js already
  requires `./filelock` and `./store`, so it never loads alone, and securewrite needs only node built-ins.
- `engine/trust.test.js`: the four tests that observed temps on `fs.writeFileSync` now observe them on
  `fs.openSync(tmp, 'wx', ...)`, where securewrite creates them.
  - The planted-symlink test now asserts that nothing is written through the link, the link is not removed, the
    config is not made a link, and the save lands on a fresh name.
  - The rename-failure test expects three temps (three attempts), all cleaned up.
- `engine/create.test.js`: the undo-failure count is 3 (one save, three temp names).
- New `engine/trust.fsync-5434.test.js` (16 tests), added to `tools/windows-tests.js` mid-list.

## Decided
- **Every guard the inline writers had is kept, inside securewrite.** That covers:
  - a unique temp name created `wx`, so a symlink planted at it is refused, never followed;
  - born at the preserved mode, then set on the fd for umask exactness;
  - a planted temp is never unlinked;
  - an atomic rename only.
- **One behaviour change, deliberate.** A file planted at the temp name used to fail that one save. Now securewrite
  moves on to a fresh name (three tries), so the save succeeds and the plant is left alone. Rejected: keeping the
  old refusal, which only turned a hostile or stray file into a failed trust write and a prompt that parks the agent.
- **Modes are unchanged.** A new Claude Code file is born 0600 and an existing one keeps `mode & 0o7777` on every
  platform, as before. Two small changes, both no looser than before:
  - the mode set on the temp is now best effort inside securewrite, where the old chmod's failure refused the save
    (a temp it misses was still created at the preserved mode less the umask);
  - the record now keeps an existing record's mode (the store.js rule: `& 0o777`, none on Windows), where the old
    unmoded temp reset it to the umask default on every save. A new record still takes the umask default.
- **Not tested here: the folder flush after the rename** (`syncDir`). It is securewrite's own, best effort, and is
  unasserted in every slice so far.
- **`ownTempsOnly` for the Claude Code folder** (the person's own), and a folder-wide reap for the record (Kosmos's
  own data folder, as store.js). This also retires the old note that a crash's stray temp is never removed:
  securewrite reaps a dead writer's temp of the same file on the next save. Stray temps from the OLD naming
  (`.kosmos-<pid>-<start>-<seq>.new`) are not reaped. That is accepted: there are few of them, and they are inert.
- **Cost:** one flush of the file and one of the folder per save, about 8 ms on this Mac's SSD (measured on
  slice 4). These saves run when an agent is created or relaunched (create.js, ensure-launch-trust.js,
  win32launch.js) and only when the file changes. They are not on a hot path. `ownTempsOnly` also reads the
  target's folder on every save (`reapDeadTempsOf`), which for the default account is the person's home folder
  (`~/.claude.json`): one directory read per save, under the file lock, once per agent in a relaunch storm. Accepted.
- **Windows: a held file is now tried three times.** A rename refused because Claude Code holds the file
  (EPERM/EBUSY) is attempted on three fresh names back to back before the save is refused, where the old writer
  refused at once. Each failed attempt removes its own temp, so nothing is left; the retry cannot help against a held
  handle and costs three writes. Unmeasured on a Windows box; the Windows CI job covers the successful path.
- **Old-named temps are not reaped:** neither the config's `.kosmos-<pid>-<start>-<seq>.new` nor the record's
  `trust-writes.json.<pid>.<ms>.<seq>.tmp` match securewrite's name pattern. They are inert and few.

## Tests
- `trust.fsync-5434.test.js`, for each of the four writers:
  - the temp renamed into the file was flushed first;
  - a new file is born 0600 and an existing one keeps its mode;
  - with all three atomic attempts refused, the save is refused and the file is unchanged.
- The same file also covers:
  - a dead temp of the same file is reaped, while another file's temp in the same folder survives (both planted
    in a fresh folder before the first write);
  - the record is flushed, keeps its mode, and its bytes are unchanged (two-space JSON, no trailing newline);
  - a failed record save returns false and leaves the record unchanged.
- Mutation checks, run on a scratch copy:
  - the old unflushed inline write fails 9 tests;
  - dropping `ownTempsOnly` fails the reap test;
  - the old unflushed record write fails both record tests;
  - dropping `atomicOnly` fails all four failure tests.
- Related set: every test that requires trust, plus slice 5's list (57 files): 1920 tests, 0 failures.

## Weakest premise
That securewrite's three-name retry is safe for a hostile plant. It cannot write through a link (`wx`) and never
unlinks what it did not create, but it does make the save succeed where it used to fail. Anyone relying on a
plant to block a trust write was relying on a side effect, not a guard. What would change my mind: a case where a
failed trust write was the intended protection.
