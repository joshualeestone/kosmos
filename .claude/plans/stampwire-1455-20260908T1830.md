## The design, and why it is additive rather than a redesign

🛑 **The tool's docblock fixes WHERE it goes:** *"IT STAMPS NOW, AND THAT IS ONLY CORRECT
IMMEDIATELY BEFORE THE DEPLOY."* Step 7, never step 1.

🔑 **The detail that makes wiring safe: the tool is IDEMPOTENT and exits 0** when the id is already
on the page ("nothing written"). So calling it on today's flow, where the entry is hand-written onto
the page before step 1, is a verified no-op.

**Therefore, additive and backward compatible:**

1. **New, optional:** the operator may leave the entry as a FILE carrying `TIMESTAMP` instead of
   hand-stamping it onto the page.
2. **Step 1** accepts either: the entry already on the page (today, gate unchanged), OR a
   well-formed pending entry file. A pending file is well-formed when it carries an
   `id="v..."` matching this version AND a `TIMESTAMP` placeholder.
3. **Step 7, before the existing gate:** if a pending file is present, run the tool. It inserts and
   stamps with the real publish minute. The existing gate then runs unchanged and passes, because
   the stamp is now zero minutes old.
4. **The gate stays as the backstop.** If the insert fails for any reason, step 7 refuses exactly as
   it does today. Nothing is weakened.

**What I rejected:** adding a re-stamp function to `versions-entry.sh` that rewrites the stamp in
place. It would be a SECOND stamper beside the tool's, which is the "two spellings of one value"
defect this repo keeps finding, and the tool's header already argues the insert-never-edit rule.

**What I am NOT doing:** changing either gate's windows, changing the ruled copy, or making the
pending-file path the only path. The hand-stamped flow keeps working untouched.
