# sinkmode-5536: the restore sink reads the root's mode back after making it private (#5536)

## Why
E0.7's restore sink (engine/restoresink.js, PR #5603) makes the restore root 0700 before writing into it, so a
shared group (macOS staff) cannot write there. Its review round 19 left one NIT worth doing, carried to #5536: the
mode is never read back. A mount that reports success but ignores modes (a CIFS dynperm mount, some FUSE mounts)
would leave a group-writable root accepted, and the group could then swap folders under a restore in progress.

## Change
- After the chmod, lstat the root again and refuse unless (mode & 0o077) is 0 (read AND write for group and others:
  a restore is someone's work, so a fixed dir_mode=0755 share is refused too; review round 1), with a message that names the cause
  and suggests a folder on this computer's own disk.
- Test: a chmodSync stub that silently no-ops on the root (the drive "ignores" it): refused. Red-checked with the read-back
  removed: the suite fails that test.

## Weakest premise
That lstat reports the mode the drive enforces. A FUSE mount could report 0700 and still enforce something else;
nothing the Mac can read would show that, so this check catches the honest-but-ignored case only.

## Review round 1 (opus): fixed
- The mask's intent written down (0o077, read as well as write; not to be loosened to 0o022), in the code and here.
- The summary comment names the read-back; the test asserts nothing was written into the refused root (pins that
  the check runs before the temp folder); the message uses a double-quoted string.

## Review round 2 (sonnet): fixed
- A second case starts at 0755 with the chmod ignored: refused, so the read arm of the 0o077 mask is tested (a mask
  loosened to 0o022 fails it; red-checked).
- The read-back compares dev/ino with the first look, like the earlier root check; the history citation left the
  code (it is here).

## Review round 3 (opus): fixed
- **macOS "Ignore ownership on this volume" (mount flag noowners), the default for many external drives:** there
  every account is reported as the owner of every file, so 0700 and the owner check keep nobody out while the mode
  reads back truthfully. The sink now reads /sbin/mount on macOS, finds the mount holding the root (longest mount-point
  prefix: SUPERSEDED in round 4 by df -P and an exact mount line), and refuses a noowners volume BEFORE the chmod. Tested with /sbin/mount stubbed (refused, nothing written,
  the mode untouched; control: the boot volume accepted) and on a real noowners volume when one is mounted. Measured
  on this Mac: the real volume was ALREADY refused by the ancestor walk (its root lets others replace folders), so the
  new check matters for a noowners volume whose root is 0755. Red-checked with the stubbed mount.
- The read-back's dev/ino arm is tested (an lstat stub that changes the inode on the read-back); red-checked. The 0755
  case asserts nothing was written; the header's wording fixed.
- Weakest premise, widened: lstat and mount report what the system says. A volume that reports ownership and modes but
  does not enforce them (some FUSE file systems) is not caught by anything the Mac can read.

## Review round 4 (sonnet): fixed
- The read-back's dev/ino failure has its own message, and its test changes the inode only on lstats AFTER the chmod,
  so the earlier root check cannot satisfy it on any platform (on Linux /tmp is already real); red-checked.
- The volume check fails CLOSED: df -P names the root's mount point (no case or Unicode matching of paths), its flags
  come from that exact mount's line, and an unreadable df, a missing mount line or a command error refuses (tested,
  red-checked). Both commands have a 10 s timeout and the error names the cause.
- The real-volume test is renamed a SMOKE test (on the volume measured, the ancestor walk refuses first); the stubbed
  test is the coverage. Comments trimmed, and the history citation dropped from the test.

## Review round 5 (opus): fixed
- The mount line must be EXACTLY the root's mount point: the " (" after it must be the line's last, so a volume at
  "/Volumes/foo (bar)" listed first can no longer lend its flags to "/Volumes/foo" (the reviewer reproduced that fail
  open). The last matching line is used (stacked mounts list the visible one last). Tested with that pair; red-checked.
- The fails-closed table asserts each arm's own message, and covers a spawn error (timeout) and a df with no mount
  point.
