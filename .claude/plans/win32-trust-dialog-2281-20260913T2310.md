# win32-trust-dialog-2281 — the trust-dialog hang, and the missing diagnostic

Issue: joshualeestone/kosmos#2281
Branch off origin/main @ `1bfd8ad2`.

## What the card is, in one sentence

A freshly spawned Windows agent whose working folder is not trusted by Claude Code
hangs at Claude Code's workspace-trust dialog, never registers in
`claude agents --json`, and — because `win32roster` is fail-closed — the board
shows an empty fleet with **no diagnostic**. The card has two halves:

1. **The trust half** — stop the dialog appearing at all by pre-seeding Claude
   Code's own workspace-trust state before the interactive spawn, id still pinned.
2. **The diagnostic half** — when trust is *genuinely* absent (so the dialog
   still fires), turn the invisible hang into a legible signal.

## Finding 1: the trust (pre-seed) half is ALREADY fixed on main

The REAL fix the card asks for is already shipped, in two merged pieces this
branch builds on:

- **`engine/trust.js` `trustFolder()`** writes
  `projects[<path>].hasTrustDialogAccepted: true` into the account's
  `.claude.json`. The key is `fs.realpathSync.native(dir)` **normalised to
  forward slashes** — `key = key.split(path.sep).join('/')` (trust.js:244,
  kosmos#2394). This is the spelling Claude Code actually reads on Windows;
  the pre-#2394 backslashed key was written, returned `ok`, and never read
  (measured on the box 2026-09-07: forward-slash key ⇒ no dialog; backslash
  key ⇒ the dialog with "No, exit" preselected).
- **`engine/win32launch.js`** — both `launch()` (the older detached
  `cmd /c start` path) and `launchStreaming()` (the production `-p` streaming
  path) call `trust.trustFolder(cwd, { configDir, createIfAbsent:true,
  agentDefaultAccount:!configDir })` **first, and gate the launch on it**
  (`trust -> prepare -> spawn`). The session id stays pinned: `prepareSession`
  mints the UUID and returns `launchArgs:['--session-id', <id>]`, spliced
  verbatim; the spawn is interactive/streaming, never `--bg`.

So on the common path — a folder Kosmos created moments earlier, pre-accepted in
the config the agent will read — the dialog no longer appears and the id stays
pinned. **There is nothing to implement for the pre-seed; it is done.** What this
branch does for that half is *prove* it (measurement below + the live-check
runbook), not re-write it.

Belt-and-suspenders: `engine/create.js` also calls `trustFolder` at create time
(`createIfAbsent`), so trust is seeded both at create and at every (re)launch.

### Why pre-seeding is not a *complete* answer (why the diagnostic still matters)

`trustFolder`'s own header (trust.js:369-374) documents the one hazard it cannot
design away: it is a read-modify-write on a file a live Claude Code also writes,
so a concurrent whole-file save by Claude Code can **drop the entry we just
added** — "the write succeeded, the agent asks the prompt anyway." Plus two
cases where trust is legitimately absent:

- a folder the **user** pointed an agent at (not one Kosmos created), and
- a **config flip** (#1629) that re-arms every trust decision for that config dir.

In all three the dialog fires, the session never registers, and today the board
is silent. That is the diagnostic half, and it is the genuinely-open work here.

## Finding 2: the mechanism the diagnostic keys on (measured on-box, read-only)

Claude Code, when a session starts, writes an early
`<config-dir>/sessions/<pid>.<hash>.key` and only later a `<pid>.json` once the
session registers. Confirmed 2026-09-13 by a **read-only** listing of this box's
`~/.claude/sessions`: every registered session had **both** a `.key` (113 bytes)
and a `<pid>.json`; the issue's measurement is that a session stuck at the trust
dialog writes the `.key` and never the `.json`. So:

> a `<pid>.<hash>.key` with **no** sibling `<pid>.json`, older than a threshold,
> is a session that started and did **not** register — the detectable "waiting at
> a prompt" state.

Sessions dir resolution mirrors `trust.js`'s `SETTINGS()` base (the config
**dir**, not the `~/.claude.json` **file**): `<configDir>/sessions`, else
`$CLAUDE_CONFIG_DIR/sessions`, else `~/.claude/sessions`. (The `configDir`
branch and the `CLAUDE_CONFIG_DIR` branch are what a Windows agent uses; the
`~/.claude/sessions` branch is what an unset-env default-account agent uses and
is the one confirmed above. The other two are confirmed by the live-check
runbook.)

## What this branch builds

### A. `engine/win32trustwait.js` — the detector (pure, testable, cross-platform)

- `sessionsDir(configDir)` — the resolution above.
- `stuckSessions({ dir, list, now, olderThanMs })` — over an injected directory
  listing (`list` returns `[{ name, mtimeMs }]`), returns
  `[{ pid, keyFile, ageMs }]` for pids with a `.key` and no `.json`, older than
  `olderThanMs`. Pure over the seam, so it runs on macOS CI unchanged.
- `pidWaiting(pid, opts)` — the one the supervisor calls: is *this* child's pid
  stuck (has a `.key`, no `.json`, past the threshold)? Uses the real
  `fs.readdirSync`/`statSync` by default (the only real-dir read; injectable).

The default real-dir read is guarded so it never throws into a caller and
returns "not stuck / cannot tell" on any fault (fail-soft, like the rest of the
win32 family).

### B. `engine/win32supervisor.js` — a bounded post-start registration diagnostic

Additive, low-risk, task-log only (no board UI, no scope-guarded files):

- After a successful `startOnce()` launch (fresh or resume), arm **one** shot
  timer at `REGISTRATION_GRACE_MS` (default 45s — the header measures healthy
  registration at ~5s, so 45s is far past any healthy delay).
- When it fires: if this child is still the current child and still alive, and
  the launched session id is **not** in `readLive()`, emit
  `onEvent({ action: 'unregistered', because: ... })`. `main()`'s existing
  `onEvent` handler already writes every action to the task log, so the sentence
  reaches the log for free.
- The `because` is **classified** by `win32trustwait.pidWaiting(child.pid, {
  configDir })`: if the pid has a stuck `.key`, it names "waiting at a
  workspace-trust prompt no one can see"; otherwise "started but has not
  registered yet" (could be a slow box or a different prompt). All seams
  (`readLive`, `timer`, and a `trustWait` injectable) are already the shape the
  loop uses, so the arm is driven from any host.

This converts the invisible hang into a task-log sentence — the "NO diagnostic"
half of the card title — without touching `server.js` or `web/index.html`.

### C. Follow-up filed for the board-card surfacing (OUT OF SCOPE here)

The board card cannot show a *not-registered* agent today: `win32roster` and
`win32live` only emit sessions present in `claude agents --json`, and
`win32streamstate.stateFor` gates on the live row (pid+sessionId). Surfacing
"waiting at a trust prompt" **on the card** needs `server.js` (a new source
beside the roster) and `web/index.html` (the rendered state) — both owned by the
updater-S4 builder this cycle. Filed as a follow-up that names
`win32trustwait` as the ready detector to wire.

- `engine/win32trustwait.test.js` — pure arms over injected listings: a stuck
  key detected; a `.key` with a `.json` sibling is NOT stuck; a young `.key`

- `engine/win32supervisor.test.js` — a new arm: a started session that never

  seams (no real spawn, no real dir), so green off-win32.

## Measurement (the on-box proof of the pre-seed WRITE)

In a **sandbox** `CLAUDE_CONFIG_DIR` (a scratch dir — never the real one):
`trustFolder` writes exactly `projects["C:/.../work"]` (forward slashes, no
backslash), returns `ok`, and the returned key equals the written key. This is
the write side of the fix; it is what the existing
`engine/trust.win32-key-2281.test.js` pins and what this branch re-confirms in a
fresh sandbox. The READ side (dialog actually suppressed) needs a real
interactive Claude and is in the runbook.

## Live-check runbook (needs a real interactive window; Josh at the keyboard for any dialog)

All steps use a **sandbox** `CLAUDE_CONFIG_DIR` pointed at a scratch dir; none
touch the real fleet, the live board (16180), or any `\Kosmos\*` task.

1. **Pre-seed suppresses the dialog (the fix).** In a scratch dir
   `$S`, `mkdir $S\cfg $S\work`; write `{ "projects": {
   "<forward-slash spelling of $S\work>": { "hasTrustDialogAccepted": true } } }`
   to `$S\cfg\.claude.json`; then
   `CLAUDE_CONFIG_DIR=$S\cfg claude` **interactively in `$S\work`**. Expected:
   no trust dialog, straight to the prompt. (This is the forward-slash control
   #2394 measured; re-run to confirm on the current Claude build.)
2. **Confirm the sessions-dir location under a set `CLAUDE_CONFIG_DIR`.** With
   the same env, after the session registers, check that
   `$S\cfg\sessions\<pid>.json` exists (not `~/.claude/sessions`). This confirms
   `win32trustwait.sessionsDir`'s `configDir`/`CLAUDE_CONFIG_DIR` branches.
   Read-only; Ctrl-C to exit — **no dialog to accept**.
3. **The diagnostic fires when trust is genuinely absent.** Repeat step 1 but
   with `hasTrustDialogAccepted` **removed** (or a fresh `$S\work2` never
   trusted). Drive one Windows agent at `$S\work2` through the supervisor with
   the sandbox env. Expected: the agent does not register within the grace, and
   the task log shows `unregistered -- ... waiting at a workspace-trust prompt
   no one can see`. **This is the step that may surface a real dialog** — if it
   does, Josh accepts/declines at the keyboard; the code does not.
4. Optional: confirm `sessions/<pid>.<hash>.key` exists while `<pid>.json` does
   not, for that stuck pid, so the detector's premise is verified live.

Steps 1-2 need only a real interactive window (no dialog to accept — trusted).
Step 3 is the one that needs Josh present in case a real dialog appears.

## Revert controls

Each behavioural change carries a test that goes red if the change is reverted:
the detector arms pin `stuckSessions`/`pidWaiting`; the supervisor arm pins the
`unregistered` event fires exactly once on a never-registering start and never on
a registering one. Reverting either the detector or the supervisor block reds the
matching arm.
