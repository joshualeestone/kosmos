# import-agent-1652 - the import direction of the portable agent file

Kosmos #1652. Josh: *"add a fourth option on the create an agent for 'import my
existing agent' then give them instructions or let them locate the file, they
could also upload or share agents that way."*

The EXPORT half shipped (`engine/agentfile.js` `exportAgent`, landed 08-31): an
agent becomes one portable markdown file with `---` frontmatter (`kosmos: agent`,
`name:`, optional `provider:`) plus the instructions body verbatim. It is wired
to nothing but its own test - the export half is an engine function only, and the
format is the load-bearing decision. `IMPORT_CONTRACT`, `MARK`, `KIND` are already
exported beside the writer. `importAgent` does not exist.

## What this builds: importAgent(text, deps) - the parse + validate half

The true inverse of `exportAgent` at the FORMAT level. exportAgent BUILDS the
file from the machine; importAgent READS and VALIDATES the file into the material
a creator needs. It does NOT create the agent itself.

**Why not create here.** `engine/create.js` is 3114 lines - dir, profile, token,
launchd, tmux, dry-run seams - and it is the one canonical creation path all
three existing create-an-agent options use. importAgent must not duplicate or
partially reimplement it: a half-creation (config without a supervisor, a pane
without a token) is exactly the "half-applied" hazard `IMPORT_CONTRACT` warns
against. So the fourth create-an-agent option calls importAgent(text) to parse +
validate, then hands `{name, body, provider}` to the SAME `createAgent` path the
other three use. Import reuses all of create's correctness.

### The contract importAgent enforces (from IMPORT_CONTRACT, stated beside the writer)

A file is a Kosmos agent file ONLY if: (1) it opens with a `---` frontmatter
block, (2) that block carries `kosmos: agent`, (3) `name:` is present and usable
(no newline, non-empty, per `safeValue`), and (4) the body names somebody
(`status.identityFromText` finds a display name - the same call adoption uses).
ANY OTHER FILE IS REFUSED WHOLE, not half-applied - this surface takes input from
outside the machine.

### Signature and return

`importAgent(text, deps)` where `deps.identityFromText` is injected (keeps
`agentfile.js` dependency-free, its current design, and avoids a require cycle
with status.js). Returns:
- `{ok: true, name, displayName, provider, body}` - validated create-material.
- `{ok: false, because}` - a whole refusal with a reason the UI can show.

`provider` is a HINT (may be null): the receiver may not have it connected, so
import states what the file wants and lets the create flow choose, exactly as the
export comment says.

### What does NOT come in (already guaranteed by the format)

The file carries no `id`/`idInstall`/`dir`/bookkeeping/credentials (exportAgent
never wrote them, and the export test proves their absence). So importAgent has
nothing to strip - and when the create flow runs, `store.writeProfile` MINTS A
FRESH id, so two people importing one file become two separate agents. The tests
assert importAgent returns no id/dir field, as an absence-with-a-control.

## Tests (engine/agentfile.import.test.js, mirroring the export test's discipline)

- a valid exported file round-trips: exportAgent -> importAgent returns ok with
  the same name, the display name from the body, and the provider hint. (The
  strongest arm: the two halves are one loop.)
- REFUSALS, each whole, each with a control that could have passed: no
  frontmatter; frontmatter without `kosmos: agent`; a `kosmos:` value that is not
  `agent`; no `name:`; a name with a newline; a body that names nobody.
- provider present -> carried; absent -> null.
- the identity anchor does NOT leak: a file that (maliciously) contains an `id:`
  line does not put it in the returned material - import returns only
  name/displayName/provider/body, never an id or dir.
- missing `deps.identityFromText` is refused, not thrown (mirrors export's
  missing-deps arm).
- NOT A NEW PARSER: the frontmatter is read with the same `---` shape
  `skills.readMeta` uses; a control (a plain markdown file) is refused.

## Decisions I am making and documenting (the card says these are mine)

- **Parse-and-validate, not create** - reasoned above. The wiring (a fourth
  create option + an endpoint that calls createAgent with the parsed material) is
  the follow-up, and the UI half needs Playwright.
- **A name that already exists on this machine is the CREATE flow's call, not
  importAgent's.** importAgent validates the FILE; whether the resulting name
  collides with a running agent is a machine-state question the create path
  already answers (`nameUsable`/`hasJob`). Putting it in importAgent would make
  the pure parser depend on machine state and duplicate create's check.
- **provider is a hint, never a gate** - matches exportAgent's own comment.
