# s7b-6587: the board says when its pinned coordinator key is not on the signed service key set (S-7a slice 2a)

Card: kosmos#6587 (detail private). Stacked on s7a-6587 (PR #6672, the verifier). Slice plan: `.claude/plans/s7a-6587.md`.

## Finished looks like (this slice)
With a recovery key pinned and a signed set shipped, a person whose computer pinned a coordinator key that is not on the set sees one fixed warning sentence in Settings, Kosmos+. Every other case shows nothing. As shipped today (no recovery key pinned, no set shipped) the answer is `off` and nothing changes for anyone. No key, kid or reason leaves the engine; the coordinator is never told.

## Decided
- **Where the set ships:** `app/engine/service-keys.json` and `.sig`, beside the verifier. The build stages an explicit list (engine/*.js only), so this slice adds the two files to it, both or neither (a lone one fails the build), and bundle.contents.test.js pins the copy. Everything under app/ is in the signed release manifest, so the set is covered by the release signature once staged. (Iteration 1 corrected the first version of this line, which said no build change was needed: false.) The Windows zip (tools/build-kosmos-windows.sh) and a deployed board (deploy/install-board.sh) stage the same way and copy it too (review 2).
- **States:** off, refused, none, elsewhere, unknown, listed, mismatch (engine/servicekeys-check.js header). Only `mismatch` is said.
- **A shipped set that does not verify (`refused`) says nothing to the person.** The manifest covers the file, so it is a broken build for the release gate to catch, not news. Weakest premise: a build with a bad set then gives no mismatch alarm at all. That fails toward silence, which is today's behaviour.
- **A pin that is not UTF-8 is `unknown`, not `mismatch`** (the NIT slice 1 left for this slice). The tunnel reads the pin with read_to_string, which fails the same way, so it cannot sign in with that pin either.
- **No held seq in this slice.** The set arrives inside the signed release, so rolling it back means rolling back the release, which the release path guards.
- **A board set to another coordinator (self-host, staging, tests) is `elsewhere` and says nothing.** Its pin is that coordinator's own key, never on Kosmos+'s set. Production means COORDINATOR() equals DEFAULT_COORDINATOR exactly. Weakest premise: the setting can change after setup, and only the tunnel knows which coordinator a pin came from; recording that is for slice 3 (kosmos-relay). A spelling of the production address with a trailing slash reads as elsewhere, which fails toward silence.
- **Rotation, and when this may be turned on.** The pin is first-use and never refreshed, so once a rotation drops the old key from the set every computer still pinned to it would read `mismatch`, a false alarm on an ordinary install (review 2). The key rotation design already requires the tunnel trust store and compare-not-overwrite (its steps 6 and 7, S-7a slice 3) to ship before any `key-promote`. Rule: no recovery key is pinned in manifest-verify for this check until slice 3 has shipped. Stated in the servicekeys-check.js header where the switch is. Rejected: suppressing `mismatch` when the pin was a retired key, which would also hide the attack this exists to catch.
- **The pin is written by rename** (kosmos-relay crates/tunnel/src/setup.rs write_file, tested by write_file_replaces_by_rename_and_leaves_no_temp_file), so a half-written pin is never read (review 2 asked).
- **Shipping the set:** whoever first commits engine/service-keys.json must flip the CONTROL "no set ships in this tree yet" in engine/servicekeys-check-6587.test.js; it is there to fail on that day.
- **Not in remote.status().because**, which the coordinator also receives; the field is only on GET /api/remote for the local page.
- **Split:** this slice is the engine, the field and the Settings line. The floating notice outside Settings (the #6613 pattern) is slice 2b, so this can merge alone.
- The shipped set is verified once per distinct content (a sha256 tag over set, sig and recovery keys), since the page polls.
