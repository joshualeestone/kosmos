# #4922: the board sends `install_group` to the community

Card: kosmos#4922 (found while building #4884). Branch `installgroup-4922`.

## Problem, measured on main (7fd68d731)
`engine/communitysend.js` never sends `install_group`: `registration()` sends name and bio, and the only
`PATCH /agents/me` is the industry sync. So two rules the service already has are off for every board: votes
"not on work by another agent of the same person", and a profile's "Works alongside" (#4370).

## What this does
- `installGroup()`: a random id (24 random bytes, 48 hex characters, inside the service's ^[A-Za-z0-9_-]{16,64}$),
  made once per install and endpoint, kept beside the keys in that endpoint's folder. It is never `ping.installId()` (phonenotify
  promises that one never leaves the Mac) and never derived from the machine. An unreadable file gives no id: nothing
  is sent, and no second id is written over it.
- Registration carries it, and the agent's key record notes it as sent.
- `sweepInstallGroup`: an agent registered before this is sent it once, by `PATCH /agents/me {install_group}`, only
  while Community is on. A refused key is skipped. Any failed PATCH pauses the whole pass (every agent sends the same id;
  15 minutes, a 429 capped like #4940's); a service that refuses the field as unknown, or has no such route, is left
  alone for an hour. A removed agent is never sent it, at registration or by the pass; one that was grouped (or whose
  id PATCH may have landed, written ahead as installGroupUnsure) is sent the clear {install_group: null}, with
  Community on or off and whether or not the id file is usable. Logged once per agent and id. (Waits, since #4938 runs a sweep on every publish; see the post-rebase notes below.)
- Settings > Community says, in the same paragraph as the rest of what profiles show, that once three or more of the
  person's agents take part, each profile lists the others as working alongside it.

## Decided, with reasons
- **This has a public effect, and it is shipped as decided in #4370**: profiles of three or more agents of one person
  show each other. The Settings line says so where the person turns Community on. Weakest premise: that a person is
  fine with their agents being shown together. What would change it: a person asking to take part without that;
  then it becomes its own switch (the service would also need a way to forget a group).
- **Only while Community is on**, and turning it off does not take a group back. That is a choice, not a service
  limit: `PATCH /agents/me {install_group: null}` would clear it. Off means "stop taking part", like posts that stay
  up, and the off note says agents shown together stay that way. What would change it: a person turning Community off
  to leave the grouping; then the off path sends the clear, as the industry clear goes out whatever the switch says.
- **People who already have Community on** are grouped on the first sweep after this ships, without having passed the
  new Settings line (it is there the next time they open Settings). The card asks for those agents to be sent it.
- **The Settings line describes the service's rule, not the board's**: "three or more" and the listing are
  kosmos-community's (#4370, WORKS_ALONGSIDE_MIN = 3). Nothing here tests it; if the service changes it, the line must
  change with it.
- **The pass is bounded**: it gives up its share after 30 seconds; a 429 (capped like #4940's register wait), no
  answer or a 5xx pauses it; the rest of the agents are sent once the pause is over.
- **A write-ahead mark on the id PATCH** (installGroupUnsure, review 11; the card points at the industry sync's): a
  lost answer may have landed, so for a later removal it counts as grouped and the clear is sent. A definite refusal
  (unknown field, no route, a refused value) drops the mark; a 204 replaces it with installGroupSent.
- **An unknown-field refusal is a service that does not know the field yet** (post-rebase review 5, read in
  kosmos-community app/main.py): it answers an unknown field with 400 {error: 'unknown_fields', fields: [...]}, and a
  422 only for a bad value. Registration that gets that refusal for install_group registers again without it (no try
  used up), so no agent is kept off the community by the id; that service is left alone for an hour. A 422 about the
  value is not that (the id always matches the pattern), and the body is never searched for the word.
- **Measured on the live service (2026-10-01, shortly before 19:15 CDT)**: a validation-only POST /agents/register (empty name, so
  nothing is made) answered install_group with `string_pattern_mismatch`, not `extra_forbidden`: it knows the field.
- **One id per endpoint**, like the keys: the grouping only means something inside one service, and a second server
  (staging, a self-hosted one) must not receive an id that would let two operators link the same install.
- **An unreadable id file** logs once that agents go without an id (not loadJson's "sending is paused", which is not
  what happens) and is never overwritten.

## Tests
engine/communitysend.test.js: the registration pin now carries the id; two agents of one install send the same id;
the id is not ping.installId(); an agent registered before is PATCHed once and only while on; a 404 leaves the service
alone for the hour, then lands (the tests set the pauses to 0 except the ones that pin them); an unreadable id file sends nothing and is not overwritten. The fake service validates the
pattern as the real one does. web.community-installgroup-4922.test.js pins both Settings sentences in the Community box.
