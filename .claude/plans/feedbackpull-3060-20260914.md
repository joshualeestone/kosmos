# #3060 -- feedbackpull writes 0: the bug is a MISSING ENTRYPOINT, not the fetch path

**Branch:** `feedbackpull-3060`
**Card:** kosmos#3060 (the collect side #97 of the 0.6.66 feedback loop)

## The card's premise, and why it is wrong (measured)

The card (Baron's diagnosis) says: `node engine/feedbackpull.js <dir>` writes 0 reports, so
"the bug is in feedbackpull's own REST-fetch path (defaultList/fetchBounded)" -- it throws or
returns empty where a direct curl of the same URL+token succeeds.

Measured on this box (I have the filed token + FDA), the fetch path is FINE:
- The EXACT node fetch defaultList uses (`GET https://blob.vercel-storage.com/?prefix=feedback/&limit=1000`,
  `authorization: Bearer <tok>`) returns **200 OK with 5 blobs** -- I ran it standalone.
- `feedbackpull.pull()` called directly returns `{ok:true, written:5, skipped:0, total:5}` and
  writes 5 real .md files. The existing real-transport test (spins a local server, pages, writes)
  passes.

So why did Baron's repro write 0? **`engine/feedbackpull.js` has no `require.main === module`
CLI block.** `node engine/feedbackpull.js <dir>` LOADS the module (defining + exporting
functions) and invokes NOTHING -- 0 files, exit 0. The 0 was never a fetch failure; the fetch
was never run by that command.

Compounding it: the feedback CLI verbs (write/list/triage/**pull**) live ONLY in the Windows
AGENT's command, `tools/windows/kosmos-cli.js` (confirmed the Windows agent CLI via
engine/boardrestart.js, engine/win32launch.js `AGENT_CLI_SHIM`). The macOS `kosmos` launcher
(`install/kosmos`, bash) exposes none of them. So on the Mac fleet -- where triage runs -- there
was **no way at all to invoke pull**, which is why triage saw an empty corpus.

## The fix

1. **Add a `require.main === module` CLI block to `engine/feedbackpull.js`** (via an exported,
   testable `runCli(argv, opts)` thin-wrapper -- the same pattern 12 sibling engine modules use,
   e.g. outbox.js). `node engine/feedbackpull.js [--dir <path>]` now calls `pull()` and prints
   the same summary shape as the Windows CLI's `pull` verb. Accepts both `--dir <path>` and a
   bare positional path (the exact #3060 repro form). `opts` is the test seam only; the real main
   block passes none, so `pull` resolves the token via the secrets map exactly as before.
2. **Surface the swallowed list error** in `pull()`: the token-present list-failure catch now
   reports the underlying error and states it is a store/network/API fault, not a missing token
   -- so a genuine fetch failure is diagnosable instead of fail-softing to a generic "0" that
   reads like an empty store (this is precisely what made #3060 look like a fetch bug).

## What finished looks like

- `node engine/feedbackpull.js --dir <dir>` prints `pulled 5 report(s) to <dir>` and writes 5
  triage-readable .md files (VERIFIED end-to-end against the live store).
- A filed token + a non-empty store yields >0 (new test, via the injected transport).
- A list failure with the token filed surfaces the real error (new test).

## Weakest premise / disclosures

- **That a direct `node engine/feedbackpull.js` is an acceptable Mac entrypoint** (vs. wiring
  `feedbackpull` into the `install/kosmos` bash launcher). I judge yes: 12 siblings use exactly
  this pattern, it is platform-neutral and testable, and it avoids touching the voice-sensitive
  bash launcher. If the team wants the full feedback CLI under `kosmos` on macOS, that is a
  larger, separate piece.
- **feedback-triage.js ALSO has no main block** and is likewise only reachable via the Windows
  CLI. So the triage HALF of the Mac flow has the same entrypoint gap -- that belongs to #2246
  (receive+triage), the next card in this chain, and is called out there rather than expanded
  into #3060.
- This does NOT change `pull`'s logic, the transport, the token path, or the Windows CLI (its
  `ctx.engine('feedbackpull').pull(...)` call is untouched; consumer tests 44/44 green).

## NOT in scope

- Wiring the full feedback CLI into the macOS launcher (product-shaped; flagged for Splinter).
- Any change to the collect route (#97) or the blob store.
