# dailylog-full-5855: the daily-log compiler must not destroy day files after a conversation rolls over

Card: #5855 (follow-up to #5841 piece 2). This is step 1 of two; step 2 is on the card.

## What is wrong

A conversation that reaches its message cap will roll over (#5841 piece 2, branch `dmroll-5841`, not on main yet): the
full file is set aside as `<thread file>.<stamp>.<pid>.<ms>[.<n>].full` and a fresh file carries a copy of its
newest rows. `engine/dailylog.js` recognises conversation files by `.json` at the end of the name, so it does not see
`.full` files. A compile after a rollover would then, from the current file alone:

- **rewrite** a day that straddles the rollover with only the rows the fresh file carried (the card does not name
  this one; the control test shows it), and
- **prune** every day whose rows now live only in a `.full` file.

Both remove compiled history that is still true. Nothing calls the compiler today; it has a working command line.

## The change (step 1)

`readConversations` looks for two signs of a rollover:

- **a `.full` file in the folder** (`rolledOver`): any thread file's name, a dot, and `.full` at the end. That is a
  superset of the rule the rollover follows one by, on purpose: counting too much refuses a run, counting too little
  prunes history. So a stray file a person named that way refuses the run too. A folder with such a name does not.
- **a current file that names an earlier file** (`continued`, the `continues` field). It is the same fact from the
  other side, and it still shows when the `.full` file is not in the listing: moved away by a person, or created by a
  rollover that landed after the folder was listed. It is read even from a fresh file that is otherwise damaged.

On either, `compileAll` refuses the run: nothing written, nothing pruned, `refused: 'rolled-over'` in the summary,
with the file names behind the two counts in `rolledOverFiles` and `continuedFiles`. The command prints to stderr
and exits 3: what happened, where, which files (the two kinds listed apart, up to ten each, the folder and every name
quoted and escaped to printable ASCII), and a last line that holds whatever the files are: the tool does not compile
when it finds either kind, changes none of them, and they can be Kosmos's own, so do not move or delete one unless
you know it is not. It does not say why a file is there or what to do with it; the tool cannot tell. An `onlyDay` run is refused too, since that day may be the straddling one.
The originals in `chats/` are not touched.

It needs only the file name and one field, not the rollover's helpers, so it can merge before or after the rollover.

## Why, kept here and not in the code

- The rollover is kosmos#5841's (branch `dmroll-5841`). A tree without it never produces a `.full` file; the code
  describes what such a file is, not who makes it.
- The originals in `chats/` are never touched, refused or not: the compiler only reads them.
- `.full` files stay on disk, so the refusal lasts until the compiler reads the chain (step 2).
- `.superseded` and `.damaged` set-aside files carry the same hazard and are not covered: #5866.
- The pin test has two arms: one for a tree with the rollover, one for a tree without. Step 2 lands after the
  rollover and removes the second arm.

## Rejected

- **Refuse only the prune**, which is what the card offers as the minimum. The rewrite of the straddling day loses
  rows too, and a day file holds every conversation's rows for that day, so the write cannot be skipped per
  conversation.
- **Read the `.full` files now, by hand.** The fresh file repeats the carried rows; reading both needs the rollover's
  own `continues` and `carried` rules. Those live in `chat.asideChain` and `chat.chainRows` on an unmerged branch.
  Copying them here would be a second derivation of rules still in review. That is step 2, with the real helpers.

## Done looks like

- With either sign present: the summary says refused, every existing day file is byte for byte as it was, and no
  new one appears. Without one: the compiler writes and prunes exactly as today (the existing 32 tests); its summary
  gains six keys.
- A control shows the damage the refusal prevents: the same rollover with the full file invisible prunes two days and
  shrinks a third.

## Weakest part

**The refusal turns the daily log off for anyone with a rolled-over conversation, until step 2.** Today that is
nobody: the rollover is not merged and the compiler has no caller. If the rollover ships and someone wires the
compiler before step 2, they get a clear refusal instead of a daily log.

**The refusal lasts until step 2 in practice.** The rollover keeps its `.full` files (it removes one only when its
own write fails and it undoes itself), so after one rollover the compiler keeps refusing.

**The signs are the rollover branch's, read before it merged.** A test holds them equal to `engine/chat.js`: where an
aside is put and how it is named (true on main already, asserted either way), and, once the rollover is in the tree,
its suffix, its rule for following a file and how it reads `continues`. Until then the test checks chat.js still
refuses at the cap, so it cannot go blind silently. They are text pins: a rewrite of those lines that keeps the
behaviour would fail the test and ask for a look, which is the safe way round.

**A rollover that lands in the middle of a run** is caught by the second sign only if the fresh file is read after it
was written. One that lands after this run has read that conversation's file is not seen until the next run, and
that run refuses. A third case is not caught at all, and was there before this change: where the rollover has to
rename the file, there is a moment with no current file, and a read that fails in that moment counts as a read
error. A read error stops the prune but not the write, so that day is rewritten without the conversation's rows.
That is the compiler's handling of any unreadable file, noted on #5866. The same goes for a fresh file that cannot be
read at all while its `.full` file has been moved away: neither sign can be seen.

**Two other set-aside kinds have the same hazard on main today and are not covered here:** `.superseded` and
`.damaged`. Filed as #5866. They share no rows with the current file, so the fix there is different (read them, or
decide what a damaged one means), and neither comes from the rollover this card is about.
