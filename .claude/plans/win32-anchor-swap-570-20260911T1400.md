# Plan: win32-anchor-swap-570 -- a zip that changes Node can replace the running anchored interpreter

## The defect

`engine/win32anchor.js` `ensureAnchored` copies the zip's `runtime\node.exe` over
the anchored `%LOCALAPPDATA%\Kosmos\runtime\node.exe` when the sizes differ. That
anchored file is the running interpreter of the task board and every agent
supervisor, and Windows refuses to overwrite a running executable. So an update
whose zip changes the Node version fails `ensureAnchored`, which causes two
failures:
- the launcher's `ensureInstalled` returns `failed`, and the #2752 hand-off is
  skipped, so the person gets "port in use" until the next logon;
- creating an agent fails with "we could not set up the files an agent needs to
  start at login".

The win32-launch-handoff-570 plan's "Weakest part" (review round 7) recorded this,
and the handoff listed it as the last follow-up.

## Measured first (Windows box, 2026-09-11, a copy of the Kosmos node.exe)

- Overwriting the running copy (`[IO.File]::Copy(..., overwrite)`) fails: "being
  used by another process".
- Renaming the running copy succeeds.
- Putting a new file at the original name then succeeds, and the process keeps
  running.
- Deleting the renamed file while the process runs fails with access denied, and
  succeeds after the process exits.
- Control: overwriting an idle copy succeeds.

## The change

`ensureAnchored` still copies only when the size differs, and never onto itself.
When it does copy, it goes through `replaceInterpreter`:
1. copy the source to `node.exe.staged-<time>-<pid>` beside the anchor (a failed
   copy never touches the running file);
2. rename the current `node.exe` to `node.exe.retired-<time>-<pid>`;
3. rename the staged file to `node.exe`.

On any failure it moves the retired file back if `node.exe` is missing, removes
the staged file, and rethrows. `ensureAnchored` turns that into its existing
sentence.

Every anchoring then runs `retireLeftoverInterpreters`, which deletes
`node.exe.retired-*`. A file that is still in use survives until its process
exits, and the next anchoring retries.

Not swept: `node.exe.staged-*`. One may be a concurrent swap in flight, and a
leftover only exists if a process died mid-copy.

## Weakest part

- **The gap between steps 2 and 3.** `node.exe` is absent for two renames. A task
  starting in that instant fails once and runs at the next logon or restart. It
  happens only when the Node version changes.
- **Size stays the discriminator** (unchanged): an equal-size different build is
  not detected.

## Tests (`engine/win32anchor.test.js`)

- **A RUNNING anchored interpreter is replaced.** This spawns a real copy of
  `process.execPath` from the anchor and keeps it running.
  - On win32, a control proves the direct overwrite is refused.
  - `ensureAnchored` with a different-size source returns ok, `node.exe` holds
    the new bytes, and the process is still alive.
  - On win32 a retired file remains while the process runs; after it exits, the
    next anchoring removes it.
- **A first anchoring leaves no side files.**
- **An old retired file is swept** even when no copy is needed.
- The existing arms are unchanged: never onto itself, an unchanged interpreter is
  not recopied, and the shim tests.

## Live check

On the box, with a real anchor at a different size (a stand-in larger `node.exe`
is not possible, because it has to run), the real case is simulated:
1. Copy the anchored node.exe aside.
2. Run `ensureAnchored` from the worktree with a source of a different size while
   the fleet runs on the anchor.
3. Confirm ok, and that the fleet is alive and still answers.
4. Restore the real interpreter the same way.

## Review log

- **Round 1 (opus).** The normal path had no correctness bug. Findings, all fixed:
  - [BUG] If the move-back also failed, its error was swallowed, and `node.exe`
    was left missing without a word. The thrown message now says "could not be
    put back from <retired>". Tested.
  - [BUG] Each rename was tried once, and antivirus or the indexer routinely
    holds a new .exe for a moment. The renames are now retried 10 x 100 ms on
    EPERM, EBUSY or EACCES (`RENAME_ATTEMPTS`, `RENAME_RETRY_DELAY_MS`). Tested
    with two simulated EBUSY.
  - [BUG, low] One anchoring's sweep could delete another's just-retired file
    mid-swap. The sweep now skips retired files younger than
    `RETIRED_SWEEP_MIN_AGE_MS` (5s), read from the time in the name, because a
    rename keeps the old mtime. `now` is injectable for tests. Tested.
  - [TEST-GAP] The failure and move-back arms were untested. There are now
    tests for a failed final rename (the old file is back, no side files), for a
    failed move-back (the sentence says so), and for a failed copy (the running
    file is untouched).
  - [TEST-GAP] A failing run leaked the 92 MB copy. Every sandbox is now removed
    in `test.after`. The leaked `%TEMP%\kosmos-anchor-EQvrWQ` was from this
    session's control run against the old code, and was deleted.
  - [NIT] The header now lists the transient side files. The "delete the
    anchor" remedy now says to do it once the fleet is stopped.
- **Round 2 (sonnet)** confirmed all round-1 fixes hold. It also measured that
  the sandbox count is unchanged across runs (the ~1100 old `kosmos-anchor-*`
  dirs come from `win32job.test.js` and earlier runs). Findings:
  - [CONVENTION] The sweep margin's comment said a swap "takes milliseconds",
    and it went stale when the retry budget was added. The margin is now
    derived from it: `2 * SWAP_RENAMES_AT_WORST * RENAME_ATTEMPTS *
    RENAME_RETRY_DELAY_MS`, which is 6s.
  - [NIT] The retry pause is synchronous, so the whole board waits. That
    trade-off is now stated at the constants.
- **Round 3 (opus)** confirmed every earlier fix goes red when removed.
  Findings:
  - [TEST-GAP] No test pinned that only transient codes are retried. The EIO
    test now asserts the final rename was tried exactly once.
  - [CONVENTION] The staged unlink's comment claimed a case that cannot happen,
    and hid the real one: antivirus holding the file leaves a 92 MB staged copy
    that nothing ever swept. A non-ENOENT unlink failure is now in the sentence,
    and staged copies older than `STAGED_SWEEP_MIN_AGE_MS` (10 min) are swept.
    Both are tested.
  - [NIT] The retired name was stamped before the 92 MB copy, so a slow copy ate
    into the margin. It is now stamped when the file moves aside. The clock is
    `o.now` plus real elapsed time.
  - [NIT, predates this branch] The never-onto-itself arm built its path under
    `AgentWorkforce`, not `store.APP`, so it checked nothing. The path is now
    derived by `anchorDir`, and the comment says the size check also blocks a
    self-copy.
- **Round 4 (sonnet): NO NEW FINDINGS** beyond one [NIT]: an unused
  destructured `newSrc` and a `void newSrc;` line in the staged-sweep test. Both
  were removed. Round 4 verified that each round-3 fix goes red when removed,
  checked the clock closure with and without `o.now`, and confirmed macOS
  portability. It ran 18/18 on the box. Converged.
