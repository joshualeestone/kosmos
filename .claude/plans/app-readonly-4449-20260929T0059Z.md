# #4449: agents can edit the installed Kosmos app folder (Sonya Blade, 2026-09-29)

Claimed with Liu Kang's conditions (m2737): measure what legitimately writes under the app folder before making
anything read-only, and post the list on the card first; the instruction line goes through the doctrine path;
setup.sh and the updater are Baron's release lane, so his read is part of the review.

## Finished means
Agents are told, through the doctrine, that the installed Kosmos is not theirs to edit (existing agents are offered
it too). The installer CAN leave the app folder read-only (`KOSMOS_READONLY_APP=1`), and the updater and uninstall
lift that for their own writes. **Read-only is OFF by default in what merges** (review iteration 1, below): this
release ships the lifting, and #4455 turns read-only on one release later. Tested with it on (test-install) and
with it off (the default is asserted).

## Measurement (posted on the card, comment 5881579550)
Live 0.7.06 install on Mortals, about 10.5 hours with 8 agents, a board start and an agent create: 0 files written
under app/, runtime/ or bin/ (control: the same search finds board.pid, logs, runners, tmux). Code read: the
engine reads and runs app/bin but never writes there; no chmod under app/. The updater (install_kosmos) is the one
writer: rm -rf then mv for `bin app runtime`. The update itself is measured on this box when 0.7.07 lands
(snapshot taken 00:56Z).

## Decision
1. Doctrine (DONE here): a NEW section `### Kosmos itself is not yours to edit`, DOCTRINE_VERSION 27 since the 2026-10-11 rebase (it was 19 after, and 16 before, the 2026-09-29 rebase onto main, which had taken 16 to 18 for #4467, #4475 and #4420), so existing
   agents are offered it. It names the Mac folder and says why and what to do instead.
2. Installer (Baron reviews): install_kosmos makes an old part writable again before its rm -rf (always), and the
   swapped-in `app` read-only after the swap (chmod -R a-w) when KOSMOS_READONLY_APP=1 (off by default this release,
   #4455 turns it on); uninstall lifts it before deleting. Rejected: read-only
   `runtime` and `bin` too (nothing reported editing them; each part added is another way to break an update);
   detection and restore only (#4408 already names the edited file, and it does not prevent the break).
3. Windows: a different tree and updater; left out of the read-only half, said on the PR.

## Measured while building (card comment)
- Claude Code's Edit tool writes a temp file beside the target and renames it over: it edits a read-only FILE in a
  writable folder (content changed, mode kept). Only a read-only FOLDER refuses it (EACCES on the temp file). So
  `chmod -R a-w app` (folders and files) is the form that stops the incident; files alone would not.
- Removing Kosmos: Finder's Move to Trash (a rename in the writable parent) works; the uninstall line (`setup.sh --uninstall`) works (lifts
  first); a plain Terminal `rm -rf` of the install is refused inside app and leaves app behind (needs chmod first).
- test-install's first run on this branch: the three #4449 checks passed, then the harness STOPPED in the #918
  section, whose direct `rm -rf` of an install home hit the read-only app under set -e (no tally). Fixed: that
  delete lifts the permission first, as the person it models would have to. Rerun waits for the 0.7.07 hold.

## Weakest part
A same-user agent can still `chmod` its way past a read-only folder; the doctrine line is what covers that, and it
only works if agents read and follow it. And a person deleting the install by hand in Terminal gets a partial delete
(measured); Trash and the uninstall line (`setup.sh --uninstall`) are unaffected.

### Review after the rebase (2026-10-11)

- **Round 1, a blocker that only the new base could show:** main gained a test-install block (#4382, a connect
  computer updating with no board) whose fixture edits `app/package.json` in the sandbox install. With this
  harness's `KOSMOS_READONLY_APP=1` that redirect is refused and `set -e` ends the run with no tally. The
  fixture now lifts the permission for its own edit. This is why the suites are checked against the total
  diff and not the range-diff.
- **Comments said "is read-only" where the code says "may be"** (off by default). Reworded in setup.sh,
  test-install.sh and the version log.
- A failed `chmod -R a-w` now prints a note; it used to be silent.
- **engine/doctrine-past.js is edited by hand on purpose** (see above). Do not regenerate it on a branch.

- **Round 2:** test-install now pins that only `app/` is locked (`bin/` and `runtime/` stay writable).
  Deferred, with reasons: (a) the pre-swap lift tolerates a failed chmod, after which `rm -rf` can fail part
  way through the swap. With the switch off the tree was never locked by us, so the swap behaves exactly as
  on main; it becomes reachable only when #4455 turns the switch on, and is item 3 below. (b) "the `[ ! -w ]`
  checks pass trivially as root": they do not, `-w` is true for root so `! -w` is false and the check reds.
  (c) the proof file is committed by convention.
