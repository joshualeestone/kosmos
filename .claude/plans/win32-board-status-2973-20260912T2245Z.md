# win32-board-status-2973

Addresses #2973. Built on origin/main 3b0e86bd, which contains #2978 (`win32-agent-job-read`,
`win32job.taskEnabled`).

## The defect, verified

`engine/win32board.js` `status()` (line 369 on 3b0e86bd) reads the board task's state from
the localized `schtasks /Query /TN Kosmos\board /FO LIST` text:

    return { registered: true, enabled: !/disabled/i.test(out), running: /\brunning\b/i.test(out) };

The LIST output also prints `HostName:` and `TaskName:`, and its status words are translated.
Any failed query counted as "not registered".

Decision sites, re-found on 3b0e86bd:

| Site | Decision | Wrong read does |
|---|---|---|
| `engine/win32board.js:462` `ensureInstalled` | `st.enabled === false` leaves a switched-off task alone | German: a switched-off task reads on and is re-registered with `<Enabled>true</Enabled>` (hardcoded in `taskXml`), so it is switched back on. Host `DISABLED-LAB`: an enabled task reads off, so a moved install is never re-registered. |
| `engine/win32board.js:509` `restart` | `st.enabled === false` refuses | German: ends a board its disabled task cannot bring back. Host name: refuses a good restart. |
| `engine/boardrestart.js:240` `win32CanRestart` | same | same |
| `engine/win32board.js:597` `restartHelperMain` | `st.running` confirms the board came back | German: never sees "Running", so it runs the task three times and logs THE BOARD DID NOT COME BACK over a board that is serving. |
| `engine/win32handoff.js:242` `attemptHandOff` | `board.status().running` decides whether the board on the port is the task's and can be ended | German: a task board is never replaced. A host name containing "running": a board that is not the task's is "ended" (a no-op) and the launch waits for a port that never frees. |
| `engine/win32board.js:620` `describe` | display facts for `machine.js`'s Settings row | the row says the wrong thing |

## Measured on this box (en-US, Windows 11 26100), scratch tasks under `\ClaudeBuilder2973`, deleted after

- `/Query /XML`: the output is 8-bit with no BOM and no NULs, whatever `encoding="UTF-16"` says.
  An ENABLED task has NO `<Enabled>` under `<Settings>` even though the registered XML said
  `<Enabled>true</Enabled>`. After `/Change /DISABLE`: `<Enabled>false</Enabled>` under
  `<Settings>`. After `/ENABLE` the element is gone again. The LogonTrigger's own `<Enabled>`
  is dropped too. So #2978's reader (Settings-scoped, absent means true) is right for the board
  task as-is.
- `/Query /FO CSV /NH`: `"\ClaudeBuilder2973\probe","N/A","Ready"`, then `"Running"`, then
  `"Disabled"`. The third column is a translated word: `C:\Windows\System32\de-DE\schtasks.exe.mui`
  on this box carries `Bereit` / `Deaktiviert` / `In Warteschlange` where en-US carries
  `Ready` / `Disabled` / `Queued`, and fr-FR `Prêt` / `Désactivé`. **The status column is NOT
  language-independent, so option (b) as written is rejected.**
- `/Query /FO CSV /V /NH`, column 7 (index 6, "Last Result") is the task's last result as a
  decimal number:
  - never run: `267011` (0x41303, SCHED_S_TASK_HAS_NOT_RUN)
  - running: `267009` (0x41301, SCHED_S_TASK_RUNNING)
  - running and then switched off while still running: still `267009`, and column 4 says Running
  - after `/End`: `267014` (0x41306, SCHED_S_TASK_TERMINATED)
  - exited on its own (`cmd /c exit 0`): `0`
  This is a result code, not a resource string. The column labels ("Last Result") and status
  words are in the MUI; the code is formatted as a number. Not measured on a non-English Windows,
  which is stated as a residual.
- Not found: exit 1, `ERROR: The system cannot find the file specified.` (English, so
  `win32job`'s `NO_SUCH_TASK` matches here and will not on a German Windows).
- `/Query /FO CSV /NH` with no `/TN` lists every task, exit 0, 259 rows, all quoted, column one
  the rooted task path, about 0.7 s.

## The fix

1. **Enabled: one derivation, #2978's.** `win32job` gains `taskEnabledFromQuery(r)`, the classify
   + decode + `<Settings><Enabled>` parse it already does for `taskEnabled`, taking a
   `/Query /XML` result from whichever runner made it. `taskEnabled(name, worldId)` becomes that
   function over `win32job`'s own query, so the agent and board reads cannot drift. The board
   calls it over its own runner seam (`Kosmos\board` is not an agent task name, and the board's
   tests stub the board runner).
2. **Three states from `win32board.status()`:** `{known, registered, enabled, running, because}`.
   - XML reads: known.
   - Not found: `registered: false`.
   - Any other failure or unparseable XML: `known: false`, EXCEPT when the full CSV listing (step 1
     above, exit 0) proves `\Kosmos\board` is absent. Without that, a German Windows (whose
     not-found sentence `NO_SUCH_TASK` does not match) would read a never-registered board as
     unknown on every boot and never register it: a regression for exactly the users this issue
     is about. Column one of the listing is parsed through a CSV field reader shared with
     `win32job.list`.
3. **Every caller treats unknown safely:**
   - `ensureInstalled`: `action: 'unknown'`, `ok: false`, no `/Create`, no claim, a sentence
     naming the cause. server.js prints "could not check" for it rather than "will not start".
   - `restart`: refuses, spawns nothing.
   - `boardrestart.win32CanRestart`: refuses on `known === false`, and requires
     `enabled === true` rather than `!== false`.
   - `describe`: returns null for a bundle whose task could not be read, which `machine.js`
     already renders as its UNKNOWN row.
4. **Running:**
   - `restartHelperMain` really asks "is a board serving again", so it uses option (a): the
     board's identity probe (`win32handoff.probeBoard`, the `x-kosmos-board` header), exported
     and reused rather than copied. The brief says the restart helper already uses it; it does
     not (the hand-off does), so this branch wires it in. The helper needs the port: the board
     passes its own `PORT` down (server.js -> `boardrestart.selfRestart(platform, {port})` ->
     `win32board.restart({port})` -> helper argv). A restart with no valid port refuses before
     anything is ended. Success needs the old pid gone AND a board answering with the header.
     If the old board never stopped, the log says so instead of "did not come back".
   - `attemptHandOff` asks "was the board on this port started by the task", which a probe
     cannot answer, so it reads the task's Last Result code (index 6 of the verbose CSV row whose
     column two is `\Kosmos\board`, equal to 267009). Unreadable is `running: null`, and the
     hand-off serves in the window with a sentence (the safe side: it never ends a board it
     could not identify).
   - `describe.running` uses the same read (display only).
5. **Board `taskXml` carries the switch:** `<Enabled>` comes from `spec.enabled` (only an explicit
   `false` writes false, as in `win32job.taskXml`). `ensureInstalled` passes the enabled state it
   read. Today it re-registers only a known-enabled or absent task, so the literal `true` was
   never wrong on that path, but the definition should be derived from the read rather than
   asserted. Then a future caller of `install` that re-registers a switched-off task cannot
   silently switch it back on, which is the #2978 rule for agent tasks. Unknown never reaches
   `install`, so this fails closed.
6. Convention 3: no new live act. `end`/`runNow`/`install` are unchanged and still reached only
   from the same gated paths. Convention 5: one XML reader, one CSV field reader, one probe.

### Review round 1 (opus), on 22dbf1ea

Rebased first onto origin/main c05c662d (#2972). It went in cleanly: #2972 touches no line this branch

**BUG (medium): Last Result 267009 stops meaning "running" after any ignored `/Run`.**
- **Measured by the reviewer** on a board-shaped IgnoreNew scratch task: running read 267009; a
  second `/Run` changed it to -2147020576 (0x800710E0), and it stayed there while the one instance
  kept running (ITaskService State 4). When the instance ended it became 0, 1 or 267014, never a
  stale running code.
- **Reachable** through the restart helper's `/Run` attempts 2 and 3, a double-click during boot,
  or a busy board.
- **Effect:** a new-zip launch read `running: false`, served here, and died on the port. That is a
  regression against main's English "Running".

**Fix: the board says it, and Task Scheduler is only the fallback.**
1. **The header.**
   - `win32handoff.BOARD_STARTED_BY_TASK_HEADER` (`x-kosmos-board-started-by-task`) sits beside
     `BOARD_IDENTITY_HEADER`.
   - One writer, `boardStartedByTaskHeaderValue()` (`'1'`/`'0'` from `win32board.startedByTask()`),
     and one reader, `startedByTaskFromHeader()`: true, false, or null when absent or unrecognized.
   - `server.js`'s GET / sends it on the same response as the identity. The marker is read per
     request, so a test can flip it.
   - `probeBoard` returns `startedByTask`.
2. **The hand-off** decides "the answering board is the task's" from the header when present, with
   no schtasks and no locale. Only a board without the header (it predates this branch) falls back
   to `status().running`.
3. **The fallback code read.**
   - `TASK_RESULT_RUNNING` (267009) and `TASK_RESULT_RUN_IGNORED_WHILE_RUNNING` (-2147020576) are
     named constants citing the measurements, and together they are `TASK_RESULTS_WHILE_RUNNING`.
   - Any other code, or a non-number, is null. Running is now `true | null`, never `false`: a code
     outside the set does not prove a task stopped, because one such code turned out to belong to a
     running task.
   - Only the hand-off reads it, and it treats null as "leave that board alone": the same act as
     false, with a different sentence.
4. **`describe.running`** (the Settings row, which runs inside the board) is now
   `startedByTask(launch env)`. Its meaning is "this board is the task's running board". A
   hand-started board reads false, correctly: the task is not what serves it. `machine.js` does not
   read `running` today.

**TEST-GAP, closed:**
- running with 0x800710E0 is still running, in English and German; 0, 1, 267011, 267014 and another
  negative HRESULT read null;
- the hand-off with the header set to true replaces the board without asking schtasks, even when
