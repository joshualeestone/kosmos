# planscreen-7404: choose a backup plan, then pay

Card: #7404 (the plan screen slice). Owner: Baron Draxum.
Design settled on the card (comments 6587891362 and 6587921033): Mona Lisa m2544, Ice Cream Kitty m2543.

## What the coordinator does (read on relay main)
- `POST /v1/mac/personal-backup` (the board's preview) answers `plans: [{ gb, price }]`, sorted, empty when any price
  cannot be read. Once backup is on for the account it is safe to call again: "the same answer, nothing new made".
  Before that it MAKES an (unbound) membership, so it is never called just to read prices.
- `POST /v1/mac/personal-backup/checkout { gb }` answers `{ url }`, a hosted Stripe page. Refusals by code:
  personal_backup_off, backup_plan_unknown, personal_backup_not_on, not_subscribed, backup_plan_exists, and a
  plain conflict while an earlier page is being opened.
- The current plan: `backupWeeklyGb` in `/v1/mac/org/status` (engine `planOf`), GB or null. The only read (Kitty).
- A paid checkout grants the plan in the same webhook; Stripe may retry a late one for hours (Kitty).

## Engine (engine/personalbackup.js)
1. `cleanPlans(d.plans)`: each { gb: safe integer > 0, price: PRICE_SHAPE }, sorted by gb; [] when empty; null when
   malformed (then the preview refuses as an answer it cannot read).
2. `preview`: the #7681 binding becomes "the screen's 'from' price (this board's KOSMOS_PERSONAL_BACKUP_PRICE) is the
   smallest plan's price"; else price_unconfirmed. The ticket and the answer carry the plans (server KEEP adds 'plans').
3. `plansNow()`: only when this board's record says on; reads the plan first (`planOf`, the status read, which also
   confirms the membership is this backup's own), then re-POSTs the preview route for cleanPlans. A plan it cannot
   read is a refusal, never "no plan".
4. `checkout(gb)`: gb a positive whole number (Kosmos+ refuses a size it does not sell: backup_plan_unknown); POST checkout; the url is used only if it is https on
   checkout.stripe.com (the board never opens a page the coordinator names elsewhere). Refusal codes to plain words.

## Server
- `POST /api/personal-backup/plans` -> { ok, plans, planGb }: screen-only, no step-up (a read).
- `POST /api/personal-backup/checkout { gb }` -> { ok, url }: step-up gated (REMOTE_STEP_UP_EXACT), like on/off.

## Page (Mona Lisa's words)
- Off view: "Personal backup is from $5/month, billed to your Kosmos+ account." Hidden while there is no price.
- On view with no plan: "Personal backup is on, but nothing is backed up until you choose a plan." then rows
  "25 GB, $5 a month" and Choose.
- After Choose: a link the person presses ("Open the payment page"; a tab opened by script after the answer is blocked),
  "Finish the 25 GB plan on the payment page. This updates when it arrives."; read the plan every minute while it is
  open; after a few minutes "Your payment is being confirmed."
- The hourly run with no plan stops with noPlan; that stop keeps the plan screen open instead of hiding it.
- A refusal, or a read that gives up: the coordinator's reason plainly; the rows stay. Never an endless spinner.

## Weakest premise
That the preview route stays safe to repeat once on (relay org.rs mac_personal_backup says so today). If it ever made
a second membership, plansNow would; the answer's org id is compared with this board's record and refused otherwise.
