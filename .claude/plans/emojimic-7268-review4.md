## Findings

- [WARNING] ios/Kosmos/ComposerExtras.swift:117-125 (toggle) with :218-230 (finish). A press during the up-to-2 s finishing window starts a brand new dictation without ending the one that is finishing. In finish(), `state` is `.ready`, `starting` is false and `live` is still true, so the button shows a grey mic and toggle falls through to a fresh start. Scenario: the person double-taps the red stop button (or taps stop, then taps the mic again to keep going). The first tap finishes, the second starts again: the microphone is back on (the opposite of what a double-tap on stop means), the generation bump makes the old session's final result be discarded, so the last half-second of words spoken before stop never reach the box, and the old `task` is never cancelled (start() overwrites `task` and `request` without cancelling). Worse edge: if that second start is then refused (recognizer unavailable, permission revoked), nothing ever releases the first session: the old callback and the fallback both fail their generation check, `live` stays true, and the audio session stays in `.record` with `.duckOthers` and active until the person happens to change the box, send or leave, so a video played meanwhile is silent or ducked. Fix: in toggle, treat `live && state == .ready` (finishing) as either a no-op or `stop()` first; and in start(), cancel any existing `task`/`request` before installing new ones. Also move start()'s `lastWritten = base; heard = false` after a `guard mine == generation` so a stale start can never touch session fields.

- [WARNING] ios/Kosmos/ComposerExtras.swift:200-204 (error with nothing heard). The "not available" refusal also fires for the ordinary "nothing was said" outcome. Scenario: the person presses the mic, changes their mind and presses stop without speaking (or stays silent until the recognizer gives up). finish() calls `endAudio()`, Speech returns an error for no speech (kAFAssistantErrorDomain 1110 style), `heard` is false, so the code calls `refuse(.unavailable)`: VoiceOver says "Stopped dictating" and then "Dictation is not available right now. Try again in a moment.", and that line stays under the box. Dictation is available; the person just did not speak. Fix: only treat an error as a refusal while `state == .listening` and before any audio was delivered, never after a stop by hand (in finish's window `state` is already `.ready`, so `if failed && !heard && state == .listening` is a one-line gate); better, ignore the no-speech error code specifically and stop quietly.

- [WARNING] ios/Kosmos/ChatView.swift:1122 and ios/Kosmos/RoomView.swift:1116 (Send stops at once). The finish path exists so the last words, about half a second behind the speech, still land; Send defeats it. Scenario: the person says "meet me at five", presses stop, then Send within the 2 s window (the natural rhythm), or presses Send straight from listening. Send calls `dictation.stop()`, which bumps the generation and cancels the task, so the final result is dropped and the message goes as "meet me at". The words are lost silently, in a message that has already been sent. This follows the stated rule ("Send stops it at once"), so it is the rule that needs a decision, not the code. Fix options: while `live`, have Send end the audio and wait for the final result (bounded by the same 2 s) before taking `draftText`/`postWords`, or disable Send while finishing (`dictation.finishing`) so the person cannot send the half-landed text.

- [NIT] ios/Kosmos/ComposerExtras.swift:167-169. `addsPunctuation` (iOS 16+) is not set, and on-device recognition then returns unpunctuated text, so dictated messages arrive as one run-on sentence. Fix: `req.addsPunctuation = true`.

- [NIT] ios/Kosmos/ComposerExtras.swift:310-316 (CursorField18 caret capture). Correctness depends on SwiftUI delivering the unfocus selection change after the FocusState flips to false. If the field reports `selection = nil` while `focus.wrappedValue` is still true (the Button action sets focus false, then UIKit ends editing), the else branch records `caret = nil` with `caretText = text`, and every pick goes at the end. Harmless fallback, but the iOS 18 cursor feature would be silently off; not verifiable without a device run. Fix: in the else branch, keep the last good `caret` rather than clearing it (only clear when text changed), and confirm on a device that a pick lands mid-text.

- [NIT] ios/LogicTests/run-composer.sh:6-11 and ios/LogicTests/composer/main.swift:63-67. The script says a directory argument compiles "a broken copy, to prove it can fail", but the wiring tests read sources from `KOSMOS_REPO` (the repo), not from that directory, so a broken copy only exercises ComposerLogic.swift. Also unpinned: the composers' `onDisappear { dictation.reset() }`, the chatEpoch reset, and ChatView's `dictation.stop()` before the draft save in onDisappear. Fix: read the view sources from `$src` too, and add one source check per reset site.

- [NIT] ios/Kosmos/RoomView.swift:1019. Toggling `.toolbar(emojiOpen ? .hidden : .automatic, for: .tabBar)` at runtime is known to be unreliable on iOS 16 (the deployment target): the tab bar may not reappear until the view is re-shown, or may not hide, leaving the panel's last row under it. Worth a check on an iOS 16 simulator; fallback is reserving the tab bar height below the panel.

- [NIT] ios/Kosmos/ComposerExtras.swift:99-110. The comment claims "headphones in or out" stop dictation, but there is no `routeChangeNotification` observer; it relies on `AVAudioEngineConfigurationChange`, which fires only when the engine's I/O format actually changes. Either observe route changes (old device unavailable) or correct the comment.
