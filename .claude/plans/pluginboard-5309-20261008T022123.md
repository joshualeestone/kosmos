# pluginboard-5309: per-agent plugin REACH signal (#5309 part 2, slice 1)

**Card:** #5309 (day-one bug: a connected plugin says ready but its tools never reach agent sessions;
false-ready, no repair path). Part 1 (agent-side wording) shipped as PR #5371 (in prod 0.7.27). This is
Part 2, slice 1.

## What #5309 part 2 asks
The board surfaces, per agent, that a plugin the person connected in their own provider app does not
reach that agent's session, so the user sees the honest state instead of a false "ready" with no repair.

## The signal this slice builds (engine only)
`engine/pluginreach.js` computes, per agent, whether the person's own provider-app plugins/connectors
REACH that agent, and if not, why. Derived entirely from the measured provider-home logic (engine/
status.js `claudeAccountDirOf`, engine/accounts.js, bin/agent-supervisor.sh):

- **Claude default account** (CLAUDE_CONFIG_DIR unset -> effective folder is the person's `~/.claude`):
  `{ reaches: true, reason: 'reaches' }`. No mismatch by construction.
- **Claude non-default account** (a separate config folder): `{ reaches: false, reason:
  'separate-account-folder', folder }`. A plugin installed in the person's own Claude app is not in it.
- **Codex** (any agent, default included): `{ reaches: false, reason: 'codex-isolated-runtime' }`. The
  private runtime home deliberately excludes the person's `~/.codex` plugins (#4592). Categorical, by
  design; NOT a per-plugin bug, so no per-plugin diff is attempted.
- **Other runners** (Gemini/Grok/...): `{ reaches: null, reason: 'not-applicable' }`.
- **Unreadable runner / missing person-home**: `{ reaches: null, reason: 'unknown' }` -- never a false
  `reaches: true`.

Two functions: a pure `reachFrom({runner, agentClaudeDir, personClaudeHome})` (all the logic, no I/O,
fully unit-tested) and a thin `reachForAgent(name, deps)` resolver mirroring `claudeAccountDirOf`
(plist `configDir` else `~/.claude`), injectable for tests.

## Deliberately NOT in this slice (honest scope)
- **Naming the SPECIFIC plugins** present in the person's home but absent from the agent's. That needs
  the plugin-file shapes (`plugins/installed_plugins.json` records, a populated `settings.json`
  `enabledPlugins`, Codex's enabled-plugin record), which slice 1 of #5309 deliberately did NOT pin
  ("names no file inside a provider folder", PR #5371 plan) and which cannot be verified on a box with
  no plugins installed. Asserting a shape I have not measured would risk showing a wrong plugin name,
  which is worse than naming none. Follow-up once the shapes are measured on a plugin-equipped box.
- **The board UI** (a new field on the `/api/status` per-agent agents map + a per-agent indicator + a
  docs/browser-checks surface via tools/browser-checks.sh, queued-heavy). That is slice 2; this slice is
  the signal only.

## Known limitation
`reachForAgent` reads the plist `configDir`; it does not see the EFFECTIVE_CCD leak-pin that
bin/agent-supervisor.sh can set on a default-account pane (agent-supervisor.sh ~888-902), so a
default-account agent with a leaked pin would read as `reaches: true` when it does NOT reach -- a false
POSITIVE (an over-report), the one residual over-report in this slice. The pure core already accepts the
effective dir as input, so slice 2 (which has the live pane env) passes the pane's actual
CLAUDE_CONFIG_DIR to close it.

## Validation
`node --test engine/pluginreach.test.js engine.reachable.test.js`: all pass, 0 fail (pure-core cases
incl. a both-ways control, path-normalization, Codex categorical, not-applicable, unknown, the
runner-normalisation + relative/non-string + default-launch-non-absolute-person-home regressions;
resolver via injected deps; plus the #265 reachability guard). Full suite through queued-heavy (big
bound, token unset) at the branch head before the PR.
