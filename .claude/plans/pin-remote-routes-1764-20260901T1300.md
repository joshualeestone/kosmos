# pin-remote-routes-1764 - guard REMOTE_AGENT_ROUTES against a write route

Kosmos #1764. Recommended by Shredder in the #1762 bind audit, filed by Splinter,
verified before filing. Owner: me (I built the bind + guard; pinning my own set is
not the audit).

## The property this protects

The #1762 finding is bounded by the fact that `REMOTE_AGENT_ROUTES` is report/reply
ONLY. A reverse proxy terminates loopback, so the socket-peer guard steps aside and
READS leak through it -- but WRITES stay closed (crossSiteWrite is a second,
independent guard). The moment a WRITE route is added to `REMOTE_AGENT_ROUTES`, the
proxy case stops being a read disclosure and becomes a NETWORK WRITE BYPASS, because
the socket-peer guard is the only thing standing there and a proxy defeats it. That
change would look completely reasonable in review and the suite would stay green.

## Why the current test is not enough (the #1751 lesson)

`server.remote-bind-1112.test.js:116` has a bare `deepEqual` change-detector. Its
failure carries no reason, so a person who adds a route learns that editing the list
IS the fix and edits it by reflex the day a write route lands. A change-detector that
goes red on an honest addition, with no WHY, trains the reflex that defeats it.

## What to build (test-only, plus a definition-site comment)

1. **Improve the exact-set pin with a WHY message** (in place). The `deepEqual` gains a
   failure message and a docblock explaining that adding a route moves it behind the
   socket-peer guard only, which a proxy defeats, and that adding a route is a security
   decision (see the remoteWriteGuard docblock and #1762/#1764), not a refactor.

2. **Add a behavioral REACH test** tied to the ACTUAL behaviour, not the set literal:
   for a curated set of dangerous write routes (`POST /api/agents` -- installs a
   `--dangerously-skip-permissions` launchd job -- plus `/api/agent-token`,
   `/api/settings`, `/api/you`, `/api/history`), drive `remoteWriteGuard` with a REMOTE
   peer holding a VALID token and assert each is REFUSED. This is the reach: it catches
   a dangerous route added to `REMOTE_AGENT_ROUTES` EVEN IF someone reflexively updated
   the exact-set assertion, because it reads the guard's behaviour rather than the set.
   Prior art: relay `crates/e2e/tests/claims.rs:473` pins `gate::admit(` to one call
   site so the mint cannot become token-only.

3. **A comment at the `REMOTE_AGENT_ROUTES` definition in server.js** pointing at the
   pin test and #1764, so a future editor is warned at the site, not only when red.

## Verify in both directions before believing it (the card requires it)

- **Red on add:** at runtime, add a dangerous route to the exported `REMOTE_AGENT_ROUTES`
  Set and confirm BOTH the exact-set pin AND the reach test would fail.
- **Green on a no-op refactor:** confirm the tests pass unchanged when the set is not
  changed (the whole suite staying green is that arm).
- Record the perturbation result in the PR, as Phase 2 did.

## Scope / not in this cut

Test + one comment only. No behavior change to the guard (it already refuses these; this
pins that it keeps doing so). The surface is on main but absent from shipped 0.6.20
(verified in the card), so this is preventive and should land with the surface before it
ships.
