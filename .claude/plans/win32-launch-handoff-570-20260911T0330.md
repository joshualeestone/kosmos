# win32-launch-handoff-570: Kosmos.exe hands the board to its logon task

Issue: #570 (Kosmos on Windows). Found while verifying a 0.6.55 zip built from main
(6182640d) end to end on the Windows box, 2026-09-11. It blocks shipping a current
Windows build.

## The defect, measured

A person runs `Kosmos.exe` from the unpacked zip. The launcher runs `app\server.js` in
the FOREGROUND of its own console window (a Windows Terminal window on Windows 11). On
that first boot the board registers `\Kosmos\board`, its at-logon task, which runs
headless (#2714). Two things are then wrong.

1. **The window is the board.** Closing it kills the board. Measured: `taskkill /T`
   on the launcher took the board off 16180, while all 6 agent supervisors lived. It
   is the same class as the visible task windows that killed Josh's agents before
   #2714. The only reason the window exists is that nobody handed the board to the
   task that is already registered for it.
2. **Every later launch looks broken.** After the first logon the task's board is
   already serving. Double-clicking Kosmos again opens the browser correctly (the
   opener waits for any board), but the launcher window says:

       Kosmos could not start: port 16180 is already in use. Is a board already running?
       Kosmos stopped. The lines above say why.
       Press any key to close this window.

   Measured on the box with the 0.6.55 zip. That is what the person sees every time
   they open Kosmos after the first reboot.

   An update by hand has the same shape. A new zip is unpacked and launched while the
   old version's task board serves. `ensureInstalled` repoints the task and the
   engine pointer at the new install, but the old board keeps serving until the next
   logon, and the launcher still reports "Kosmos stopped".

## The fix

A board started BY HAND from the unpacked zip on Windows does not serve from the
launcher's window. It hands itself to its logon task, then exits 0, so the launcher
window closes on its own. New module `engine/win32handoff.js`, called by server.js
right before `start()`.

It hands off only when every one of these holds:
- it is Windows;
- it runs from the bundle (a source checkout has no task);
- the task did not start it;
- live execution is armed;
- the launch sets no `PORT` and no `AGENT_WORKFORCE_*` root. The task runs with
  the account's environment, not this launch's, so a launch that asked for its own
  port or data folder would be handed to a board serving neither. The fallback
  would then end that working board as "not answering" (round 1);
- `ensureInstalled` just registered or refreshed the task, so the task is enabled
  and names THIS install. A task the person switched off or removed means they chose
  the window, so the window is what they get.

**Identity.** An answering board is "this one" only when its `x-kosmos-build`
header equals this process's build. That header is new: GET / sends the build
the process computed at start.
- The build is `buildIdentity(appDir)`: the `package.json` version plus
  `+<12 hex of manifest.source_sha>` when it runs from the bundle. Two 0.6.55 zips
  cut from different main commits are different code (round 1).
- Both sides call the same function. server.js computes it once at start, uses it
  for the header, and passes it to the hand-off.
- It is NOT the page's version meta. server.js reads `web/index.html` per request,
  so a new zip unpacked over the running install (the folder Explorer's Extract
  All offers) makes the OLD board serve the NEW page.
- A board without the header predates this change. It is never "this one", so its
  task board is replaced once.

**Budget.** The whole hand-off runs inside 12s measured from PROCESS START
(round 1). The launcher's opener waits 20s and then opens the plain url, which an
enforcing board answers with the #2007 403. So even the fallback has a board up
before the opener gives up. The budget is not the worst case, and the module says so: a probe already in flight at the deadline (2s), plus the port-release floor (2s) and its own last probe, make 18s from process start, inside the opener's 20s (round 2).

Then, for at most two rounds:
1. **This build already answers**: exit 0. On the first look that means "already
   running"; after our `/Run` it means "running in the background now".
2. **Another build answers, and the task is running**: this is the update by hand.
   - Wait a grace period (3s, an unmeasured allowance), so the launcher's browser
     can redeem its boot nonce on the old board. The cookie is durable, so it keeps
     working on the new board.
   - `/End` the task, and wait for the port to free.
   - An answering board the task did NOT start (a hand-started board in another
     window, or not Kosmos) is left alone: serve here, which gives today's "port in
     use" message.
3. `/Run` the task, and wait for ANY board to answer.
   - This build: exit 0.
   - Another build: that is a task board that was still booting at logon when we
     looked (round 1), and the second round replaces it.
4. **Anything not confirmed falls back to today's behaviour**: serve in the
   window, with a sentence saying why. After a `/Run`, `/End` the task first, so a
   late start does not fight the window for the port.
Measured first, and the design rests on these:
- Closing the launcher window kills the board and no agent. 6 of 6 supervisors
  lived.
- `/Run` of the zip's refreshed task gives a headless board on 16180 in 1.2s, under
  `conhost --headless`, serving 0.6.55.
- `ensureInstalled` re-registering the task (`/Create /F`) while its board runs leaves
  that board running, on the same pid, still listening.
- The launcher's opener waits 20s for a board. The hand-off needs about 4s (a first run), and about 9s for an update.

## Not changed

- `Kosmos.exe` (a committed, verified binary) is untouched; the fix is in server.js.
- The Mac is untouched: the hand-off returns "serve" for any platform but win32.
- The README text in `tools/build-kosmos-windows.sh` is a separate PR, once this
  lands, so it can describe the new behaviour.

## Tests

`engine/win32handoff.test.js` drives `handOffToTask` with injected board ops, probe,
clock and platform, so a Mac runs it. It covers:
- each skip reason;
- same-version already running;
- a hand-off;
- an update (with its grace period and the order: End, then Run);
- a foreign board holding the port;
- a `/Run` that never answers (fallback, with `/End`);
- a failed `/Run`;
- a probe that throws.

Live on the box: the rebuilt zip, launched first run, a relaunch, and an update over
a running older board.

## Weakest part

The grace period for the old board in the update case (3s) is an allowance, not a
measurement. A browser that loses the race loads the page without its cookie, and
the person gets the #2007 "open it with kosmos open" message until they relaunch
Kosmos. The cost is bounded (a relaunch signs them in), and it only happens on an
update by hand, not on first run or relaunch.

## Review log

- Round 1 (opus) found five bugs, all fixed:
  - the same version from a different commit (now build identity);
  - PORT and root overrides (now a skip);
  - a fallback that could outlast the opener (now one budget);
  - fact gathering outside the try (now inside it, plus a catch in server.js);
  - a task board still booting at logon (now a second round).
  It also found a server.js wiring test gap: now `server.board-build-header-570.test.js`
  does a real `start(0)` and GET /.
- Round 2 (sonnet) found one bug: the 2s port-release floor was not counted against the budget. The fix lowered the budget to 12s, spelled out the 18s worst case, and added two slow-release tests (one where the floor is honoured, one where it acts as a ceiling). A control run proves them.
