# win32-launch-handoff-570: Kosmos.exe hands the board to its logon task

Issue: #570 (Kosmos on Windows). Found while verifying a 0.6.55 zip built from main
(6182640d) end to end on the Windows box, 2026-09-11. It blocks shipping a current
Windows build.

## The defect, measured

A person runs `Kosmos.exe` from the unpacked zip. The launcher runs `app\server.js` in
the FOREGROUND of its own console window (a Windows Terminal window on Windows 11). On
that first boot the board registers `\Kosmos\board`, its at-logon task, which runs
headless (#2714). Two things are then wrong.

1. **The window is the board.** Closing it kills the board. Measured: `taskkill /T`
   on the launcher took the board off 16180, while all 6 agent supervisors lived. It
   is the same class as the visible task windows that killed Josh's agents before
   #2714. The only reason the window exists is that nobody handed the board to the
   task that is already registered for it.
2. **Every later launch looks broken.** After the first logon the task's board is
   already serving. Double-clicking Kosmos again opens the browser correctly (the
   opener waits for any board), but the launcher window says:

       Kosmos could not start: port 16180 is already in use. Is a board already running?
       Kosmos stopped. The lines above say why.
       Press any key to close this window.

   Measured on the box with the 0.6.55 zip. That is what the person sees every time
   they open Kosmos after the first reboot.

   An update by hand has the same shape. A new zip is unpacked and launched while the
   old version's task board serves. `ensureInstalled` repoints the task and the
   engine pointer at the new install, but the old board keeps serving until the next
   logon, and the launcher still reports "Kosmos stopped".

## The fix

A board started BY HAND from the unpacked zip on Windows does not serve from the
launcher's window. It hands itself to its logon task, then exits 0, so the launcher
window closes on its own. New module `engine/win32handoff.js`, called by server.js
right before `start()`.

It hands off only when every one of these holds:
- it is Windows;
- it runs from the bundle (a source checkout has no task);
- the task did not start it;
- live execution is armed;
- `ensureInstalled` just registered or refreshed the task, so the task is enabled
  and names THIS install. A task the person switched off or removed means they chose
  the window, so the window is what they get.

Then:
1. **A board of this same version already answers**: print that Kosmos is already
   running, exit 0. The launcher's opener is already opening the browser on it.
   The version is the `x-kosmos-version` header, which is new: GET / now sends the
   `package.json` version the process loaded at start. It is NOT the page's
   version meta. server.js reads `web/index.html` per request, so a new zip
   unpacked over the running install (the folder Explorer's Extract All offers)
   makes the OLD board serve the NEW page. A board without the header predates
   this change, so it is always "another version", and its task board is replaced
   once. This install's own version comes from its own `package.json`, the file
   the header is read from.
2. **An answering board of another version, which the task is running**: this is the
   update by hand. Wait a short grace period, so the launcher's browser can redeem its
   boot nonce on the old board (the cookie it takes is durable, so it keeps working on
   the new board). Then `/End` the task and wait for the port to free.
3. `/Run` the task and wait for a board that answers with this version. Then print
   that Kosmos is running in the background, exit 0.
4. **Any step that does not work out falls back to today's behaviour**: serve in the
   window, with a sentence saying why. Before falling back after a `/Run`, `/End` the
   task, so a late start does not fight the window for the port. An answering board
   the task did not start (a hand-started board in another window, or something that
   is not Kosmos) is left alone. Falling back there gives today's "port in use"
   message.

Measured first, and the design rests on these:
- Closing the launcher window kills the board and no agent. 6 of 6 supervisors
  lived.
- `/Run` of the zip's refreshed task gives a headless board on 16180 in 1.2s, under
  `conhost --headless`, serving 0.6.55.
- `ensureInstalled` re-registering the task (`/Create /F`) while its board runs leaves
  that board running, on the same pid, still listening.
- The launcher's opener waits 20s for a board. The hand-off needs about 4s.

## Not changed

- `Kosmos.exe` (a committed, verified binary) is untouched; the fix is in server.js.
- The Mac is untouched: the hand-off returns "serve" for any platform but win32.
- The README text in `tools/build-kosmos-windows.sh` is a separate PR, once this
  lands, so it can describe the new behaviour.

## Tests

`engine/win32handoff.test.js` drives `handOffToTask` with injected board ops, probe,
clock and platform, so a Mac runs it. It covers:
- each skip reason;
- same-version already running;
- a hand-off;
- an update (with its grace period and the order: End, then Run);
- a foreign board holding the port;
- a `/Run` that never answers (fallback, with `/End`);
- a failed `/Run`;
- a probe that throws.

Live on the box: the rebuilt zip, launched first run, a relaunch, and an update over
a running older board.

## Weakest part

A version comparison (the running process's header against this install's
`package.json`) decides whether an answering board is "ours". Two unpacked
copies of the SAME version in different folders compare equal. So launching the
second copy reports "already running" while the task has just been repointed at the
second folder, and the switch happens at the next logon. It is harmless (same code),
and it is noted rather than solved.
