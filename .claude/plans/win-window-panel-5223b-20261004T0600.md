# #5223: a Windows agent's page stops saying its window cannot be reached

**Posture:** production

## Done looks like
On Windows, an agent's AI Settings page (and, with Engineering mode on, a project's "Its screen"
block; with it off that block says Engineering mode is off, as on a Mac) says plainly
that a Windows agent runs without a window and its replies are in your messages with it,
instead of "we could not read its window just now (we could not reach the agents on this
computer)". Proven by a unit test that fails without the change, a Mac control that still
captures from the pane, and the new code run against this Windows box's real agent cards.

## What was wrong (measured on the Windows box, 2026-10-04, Windows 0.7.21 in prod)
`chat.viewport()` reads an agent's window with `tmux capture-pane`. Windows agents run
headless (`claude -p`, stream-json) under their supervisor; there is no tmux and no window.
The capture fails and its refusal sentence reads like an outage. Every agent page on every
Windows install shows it (checked on reh-a and on three brand-new agents during the Windows
pass of #5111).

## Change
- `engine/chat.js` `viewport()`: after the shared name and ownership gates, a card with
  `reachedByChannel === true` returns `{ text: null, because: 'on Windows an agent runs
  without a window, ...' }` before tmux is asked. The same card mark `send` already branches
  on (chat.js, #570 7c-4) and the Codex-hooks refusal uses; one derivation of "this is a
  Windows agent", made where the card is built (status.js from win32roster).
- The return also carries `noWindow: true`, so the two routes' question clause (an agent asking
  with no words of its own) says "on Windows there is no screen to read the question from"
  (`NO_WINDOW_QUESTION_BECAUSE`, server.js) instead of "could not read its screen", without
  matching the engine's wording.
- The two sibling Windows refusals that told the person to use the agent's "own window" no longer
  do. `keysAllowed` (Stop now, stop helpers, the Gemini quota Stop) says `WIN32_NO_KEYS_SENTENCE`:
  it was not stopped, use Restart under AI Settings (Restart works on Windows, #3431); the Codex
  hooks answer just says Kosmos cannot answer it on Windows yet.
- web/index.html, branches on `noWindow`: the agent page sets the sentence as a sentence (capital,
  full stop), its heading becomes "No window to show" instead of "The window it is running in", and the
  "Send a message into this window" composer is hidden (`setWindowBoxNoWindow`, the one writer of
  that state, called from every paint arm and the agent switch, so a Mac agent opened next never
  inherits it, and the 404 arm clears it too; the Direct Message composer is how to reach a
  Windows agent). The project page heading becomes "No screen to show" and it drops its
  "We cannot see its screen right now." lead, which would call a lasting fact a passing
  failure. Every other refusal renders as before.
- docs/browser-checks/render-projects.js: two #5223 arms, agent page (heading, sentence, composer
  hidden, then a control that the state clears when a Mac answer comes back) and project page
  (sentence without the lead, plus a control), using the engine's answer stubbed or patched into
  the real routes since the sandbox has no Windows agent. Not runnable on this Windows box (the
  check needs the Mac sandbox and fake tmux); CI's browser-checks job runs it.
- Restart pointer states its cost in the page's own words ("comes back with nothing in its
  memory", and it "ends what it is doing"), since Restart is heavier than the key the person pressed. The Codex refusal says why
  there is no answer (no window to answer it in).

## Not in scope

- The Windows section and box title "Live output" (data-win-copy terminalTab/terminalBoxTitle) predates
  this change and now sits over "No window to show": tracked as #5239 (retitle, or a real live view of

- A one-tick flash back to could-not-read when a single refresh of a Windows agent's window fails. Each
  answer decides afresh, and "could not read it just now" is true of that tick; keeping the state through
  failures was tried and dropped, since it added untested page state for a cosmetic, rare case.

## Why the per-card flag and not data-win-hide
The page's Windows copy layer (data-win-hide, windowsCopy) keys off the platform the BOARD runs on. Whether
an agent has a window is a fact about that agent, which the engine already marks per card
(reachedByChannel, from win32roster) and now states per answer (noWindow). Driving the page off the
answer keeps one source of truth and stays right on a board that shows agents from more than one kind of
computer (the Kosmos+ federation direction).
