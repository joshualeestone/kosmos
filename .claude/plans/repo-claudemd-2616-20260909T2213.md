  writes only the project portion; the auto-import block is inserted by *propagation*, and
  Kosmos is not in the claude-setup propagation list (repos.json is book-io-only). To make
  the block actually land tonight, self-contained, I concatenated the org `base` profile
  fragment verbatim between the standard markers. Verified byte-identical to
  `claude-setup/dist/profiles/base.md` (367 lines) so a future propagation can replace it
  cleanly.
- **Only the `base` fragment, no language fragment.** The `nodejs` profile fragment says
  "NodeJS code is TypeScript" and "standardizes on pnpm" (pnpm typecheck/build) -- all false
  for Kosmos (plain JS, `node >=26`, `npm test` -> `tools/run-tests.sh`, no TS/pnpm/build).
  So no existing language fragment fits; base (universal PROCESS conventions) is the only
  correct one. Kosmos's real stack + commands go in `(Project-Specific)` sections per the
  sanctioned override pattern (as booktoken-web deviates and documents).
- **Project-specific overrides:** Stack (plain JS, not org-default Rust), Pull Requests (no
  human reviewer -- challenge-loop + green CI is the gate, agents merge own green PRs, hold
  during a release cut; overrides the block's `gmoratorio` line), Pre-PR (npm test).
- **Repo-Specific Conventions:** April's 5, each sourced to the enforcing code
  (run-tests.sh:170-207 coverage assertion; store.js store.ROOT #1848/#1856;
  require.main===module fail-closed; browser-check gate run-tests.sh:213-222; two-derivations
  defect). Section marked explicitly incomplete + extensible.
- **Provenance note** above the block: it is a point-in-time copy; Kosmos is not yet in
  propagation, so nothing rewrites it on sync. Follow-up: register Kosmos in propagation with
  a plain-JS profile so the block stops being a snapshot.
