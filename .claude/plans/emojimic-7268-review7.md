## Findings

- [WARNING] ios/Kosmos/ComposerExtras.swift:142, :166, :201-210. The first time someone refuses permission, the refusal line can be wiped the moment it appears. Here is the sequence. The person presses the microphone for the first time. iOS shows the speech (or microphone) permission alert, which makes the app inactive. The person taps Don't Allow. Two things then go to the main actor independently, in no documented order. First, the authorization callback (Apple: "called on an arbitrary queue") resumes `start()`, which calls `refuse(.denied)`: `state = .denied`, `starting = false`. Second, the alert's dismissal posts `didBecomeActiveNotification`, which goes through `Task { @MainActor }` to `handle(.active)`. If the callback lands first, `.active` finds `state != .ready && !busy` and sets `state = .ready`, so "Kosmos is not allowed to use the microphone or speech recognition..." disappears. That is the only time the person ever made a choice, and the microphone now looks as if it simply did nothing. The line comes back only on a second press, which returns `.denied` at once without a prompt. The same race happens on the microphone alert after speech was allowed. Fix: in `.active`, clear only a `.denied` state, and only when permission is now really granted (`SFSpeechRecognizer.authorizationStatus() == .authorized && AVAudioSession.sharedInstance().recordPermission == .granted`). Alternatively, clear only when `didEnterBackgroundNotification` was seen since the refusal, since going to Settings is a background trip and an alert is not.

- [NIT] ios/Kosmos/ComposerExtras.swift:163. `.mediaReset, .headphones` stop when `live || starting`, and `live` stays true while finishing. So unplugging wired headphones in the 2 s after a stop by hand cancels the task and drops the last words, even though the microphone is already closed. Review 6 fixed exactly this for `.engineChanged`. Fix: use `active` here (`starting || state == .listening`) so finishing is left to complete.

- [NIT] ios/Kosmos/RoomView.swift:303-308 (takeReturned), ios/Kosmos/ChatView.swift:1141. A post or message that failed hands its words back only into an empty box. If the person has just pressed the microphone on that empty box and nothing has been heard yet, the handed-back words go in, `boxChanged` sees a change, and `stop()` runs with no announcement. The microphone turns grey while the person is talking, and VoiceOver says nothing. Here, `stop(say: true)` would at least say it.

- [NIT] ios/Kosmos/ComposerExtras.swift:251, :264-268. Only kAFAssistantErrorDomain 1110 counts as "nothing said". On devices or languages without on-device support, server recognition reports silence or a dropped request with other codes (203 "Retry" is common in the field). Pressing the microphone and saying nothing would then show "Dictation is not available right now", which is not what happened. Confirm on a device without on-device support. If it happens, treat 203 like 1110.

- [NIT] ios/LogicTests/composer/main.swift:77-84. The new `.active` branch (review 6) and the `ComposerMicButton` `.disabled(dictation.finishing)` have no pins. A refactor that drops the disable brings back the second-press loss that review 6 fixed, and nothing fails.
