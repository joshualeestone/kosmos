# bc-full-ci-2518 (#2518, CI-integration half)

## Problem
CI's browser-checks job runs only the headless-robust DOM-state allowlist on PRs. Every
other check (render-fields, render-thread, render-push-718, ...) first ran at the release
cut's 3b, so a PR that broke one merged green and blocked the next cut. Live instance
2026-09-24: #3493 (a CSS contrast change in web/index.html) broke render-fields on both
engines, merged green, and blocked the 0.6.91 staging cut.

## Measured before choosing (origin/main 21c3c64a)
- The surface map covers 71 of 195 browser checks; render-fields, render-thread and
  render-push-718 are not mapped.
- `git show 9628a617a -- web/index.html | tools/bc-surface-map.sh covering` returns only
  render-plus-blue-1615.js, so "run the covering checks" would not have caught #3493 (CSS;
  the map is DOM ids). Control: `pj-alltasks` resolves to render-alltasks.js.

## Change (current state)
- New `.github/workflows/browser-checks-full.yml`, triggered ONLY by `schedule` (nightly,
  09:30 UTC) and `workflow_dispatch`. Every run step is `bash -eo pipefail`
  (`defaults.run.shell: bash`; the plain default is `bash -e`, where a pipeline reports
  only its last command). Two jobs, least privilege each:
  - `browser-checks-full` (`contents: read`, checkout with persist-credentials false):
    runs `tools/browser-checks.sh` with no allowlist (every check, headless via run_one,
    the same script and pin as the cut's 3b). Timeouts: provision 20, checks 120, job 170
    minutes, sized generously because the runner's full-set duration cannot be measured
    until this file is on main. An always() step reads the driver's `FAILED-LIST:` line
    into a job output.
  - `file-red-card` (`needs` the checks job, `if: always() && schedule`, job-level
    `issues: write` only): any non-success (failure, a timeout, a cancel) opens a
    `nightly-browser-checks-red` card or comments on the open one; each comment leads with
    the entries NEW since the card's last report, read from the card itself (or says the
    last report could not be read); the first green scheduled run that is a first attempt closes the card. A
    dispatch run never reaches this job.
- `tools/browser-checks.sh` also prints `FAILED-LIST:  a|b (why)|c`: some failure entries
  contain spaces, so the space-joined `FAILED:` line cannot be re-split. Additive; nothing
  else parses these lines.
- `browser-checks.yml`: unchanged except for quoting its step name (an unquoted ` #` starts
  a YAML comment, so it had been parsing as "... (tools/browser-checks.sh,").
- `tools/test-browser-checks-workflow.sh`: pins each job by parsed YAML (the whole-file
  greps could be satisfied by any job); pins the full workflow's triggers, permissions,
  timeouts, needs and gate; guards unquoted ` #` in step names; and RUNS both embedded
  scripts under -e/pipefail with gh stubbed as a shell function; each of the card's reads (the paginated REST issues list, issue view) applies the script's own -q filter with real jq
  to fixture JSON. It also pins concurrency cancel-in-progress false.

## Rejected
- Covering-only (the surface map): misses the CSS class, measured above.
- A per-PR full job: a red check run on a PR stops /merge-on-green even with job-level
  continue-on-error; the full set false-reds on this runner (browser-checks.yml header,
  2026-09-07); a 30-75 minute job on each of about 129 weekly runs contends for the
  account's macOS runners; cancel-in-progress would kill it on every re-push.
- Replacing the allowlist job with the full set: its fast DOM-state green means something
  specific.

## Weakest premises
- A check red EVERY night on this runner is never NEW: a real regression inside it adds no
  signal and the card stays open. Stated in the header and the card; the remedy is to fix the
  check or record it as runner noise.
- That a card is seen before the next cut. It lands in the same queue as every other card,
  the best reach available without a secret; it is not a page.
- The runner false-red set. The 2026-09-07 first full run false-red on timing/paint checks.
  Nightly runs on an unchanged main measure the current set; no check is called
  runner-fragile from a single run. NEW is measured against the last report only, so a
  check that flakes every other night reads as NEW every other night.
- A pending run replaced by a newer queued one starts no jobs and is not reported (needs a
  third run queued on main).

Found, not fixed here: browser-checks.yml's header says the cut's 3b is "headed" in five
places, but the cut runs it headless (run_one sets HEADED=0; release.sh labels 3b headless).
