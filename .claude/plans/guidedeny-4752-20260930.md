# guidedeny-4752: the setup guide's deny rules name every Kosmos folder a board token can sit in

Card: kosmos#4752 (split from #4728). Branch `guidedeny-4752`, off origin/main 844b2372a, rebased onto 146169488 (#4742) after review round 1.

## The finding
`guideDenyRules` in `engine/setup-assistant.js` named Kosmos's data folder once, `Read(//<store.ROOT>/**)`.
On a Mac a Claude guide's sandbox applies the deny rules to every command the guide runs (#3769; measured
again on #4728). A board token can sit in two more places those rules did not name:

- the older data folder (`store.LEGACY_APP`, "AgentWorkforce"): `boardauth.legacyTokenPath`; boardauth.js says
  a still-valid token may remain there on a computer that ran the mirror removed in #2511;
- another world's store: a world's guide denies its own `store.ROOT`, and a named world's is
  `<base>/worlds/<id>/Kosmos`, so the default world's `<base>/board.token` and every sibling's store are
  outside it. `boardTokenOk` in server.js accepts any of the account's world tokens at the main gate.

## What I checked first (the card's own open question)
Can the guide's own folder sit under the worlds' base? **Yes**: a named world's agents live in
`<base>/worlds/<id>/workers` (`worlds.envOverridesFor`). So the card's first suggestion, "deny the worlds'
base", is wrong: it would cut a named world's guide off from its own instructions and settings. The rules
are narrower instead.

## The change
`guideDenyRules` gains, after the data folder rule:
- `Read(//<older folder>/**)` for the older data folder of this world and of the default world (the second
  worked out from the environment as it was before a world was applied, `worlds.preWorldEnv`), each only
  when it is a different folder from the data folder;
- when the worlds' base is not the data folder (the guide is in a named world):
  `Read(//<base>/board.token)`, `Read(//<base>/worlds/*/Kosmos/**)` and
  `Read(//<base>/worlds/*/AgentWorkforce/**)`.
- in the default world the base IS the data folder, which the existing rule already denies whole, so
  nothing is added for it.

Two optional parameters (`worldsBase`, `legacyRoots`) let a test hand the folders in; production passes
neither. `refreshGuideGuards` already rewrites an existing guide's rules at every board start, so a guide
made before this gets them from its next session.

## Measured (2026-09-30, Claude Code 2.1.285, this Mac)
A throwaway named-world layout under my scratchpad: a base with its own `board.token`, two worlds each with
a store and a token, an older folder with a token, and a guide folder at `base/worlds/w1/workers/guide`
whose settings were written by the REAL `guardGuideFolder` from this branch. `claude -p
--dangerously-skip-permissions`, told to run a script that reads each file:

| file | control (my own shell, no sandbox) | the guide session |
|---|---|---|
| `base/board.token` | read | Operation not permitted |
| `base/worlds/w1/Kosmos/board.token` (its own world) | read | Operation not permitted |
| `base/worlds/w2/Kosmos/board.token` (a sibling, reached only by the `*` rule) | read | Operation not permitted |
| `legacy/AgentWorkforce/board.token` | read | Operation not permitted |
| `base/worlds/w1/workers/guide/CLAUDE.md` (its own instructions) | read | **read** |

So the three rule shapes (one file, a folder, a `*` in the middle of a path) are each enforced on a command,
and the guide still reads its own folder under the base.

## Decisions
- **Call:** name the token-holding folders, not the base. **Rejected:** (1) denying the base whole (cuts a
  named world's guide off from itself, above); (2) listing the worlds from the registry when the rules are
  written (a world made later would be uncovered until the next board start; the `*` rule covers it at once,
  and is measured); (3) denying every top-level entry of the base except `worlds` (it would protect the rest
  of the default world's store from a named world's guide, but it is a list that goes stale with every new
  store folder, and it is more than this card).
- **Not covered, stated so nobody reads this as complete:**
  - a named world's guide can still read everything else that sits directly in the base: the default world's
    store other than its token (profiles, avatars, reports) and the worlds' own registry. Only `board.token`
    there is denied, and under `worlds/*` only the two store leaves.
  - a browser's copy of the board's cookie (a different store, not a folder Kosmos owns).
  - the moment the default world's token is rewritten: boardauth writes it to a temporary file in the base
    (`.board.token.<pid>.primary.tmp`) and renames it, and only `board.token` is named there (review round 2).
  - any guide that is not a Claude guide on a Mac: no sandbox, so these rules stop Claude Code's file tools
    only. That is #4728; #4491's last step closes it.
- **Weakest premise:** that the sandbox treats a `*` in the middle of a path the same on every Claude Code
  version people run. Measured on 2.1.285 only.
- **Not measured:** a real guide in a real named world of a real install (the layout above is a stand-in
  with the real rules); Windows and Linux (no sandbox is written there, so nothing to measure). Not tested on
  Windows either: the `*` rules join with `/` onto a Windows path, the same mixed shape the data folder rule
  has always had there.
- **If the extra folders cannot be worked out** (review rounds 1 and 2): the new rules are built in a `try`, all
  or none, so a failure there leaves the rules that were there before, and says so on stderr (one `#4752:`
  line with the reason), so a guide written without them can be told apart. Before this change `guideDenyRules` could
  not throw, and `refreshGuideGuards` does not look at the result: a throw would have left an existing guide's
  file unrefreshed, and made a new guide impossible to create.
- **The block comment above `guideDenyRules` (review round 1)** described only the data folder. PR #4742 (#4728)
  rewrote that same comment, so this branch waited for it to merge (146169488), was rebased onto it, and then
  added one bullet for the new rules.

## Tests
New `engine/guide-deny-4752.test.js`, six tests:
- a named world's rules, exactly (six rules for the handed-in folders);
- no rule covers the guide's own folder under the base, with a control that the cover check can say yes;
- the default world: no second rule for the base, the older folder only when it is another folder, and
  nothing for a folder that could not be worked out;
- worked out from the process with nothing handed in: the older folder beside the data folder is denied;
- a child process that enters a named world the way a board does (`worlds.applyAgentWorldEnv`) still finds
  the base, denies the default world's token and the worlds' stores, and does not deny the base whole.

- when the worlds folder name cannot be read (made to throw), the earlier rules still come back, none of the
  extra ones do, and one `#4752:` line is written to stderr; control: readable again, they are back.

Run with `server.guide-secrets-3769.test.js` (the existing rule tests) and `engine/worlds.agentenv-1704.test.js`:
35 tests, 35 pass. `boardauth` now exports `TOKEN_FILE` and `worlds` exports `WORLDS_SUBDIR`, so the rules use
the two names the code already had instead of re-deriving them.
