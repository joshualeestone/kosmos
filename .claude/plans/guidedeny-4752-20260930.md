# guidedeny-4752: the setup guide's deny rules name every Kosmos folder a board token (or the rest of a store) sits in

Card: kosmos#4752 (split from #4728). Branch `guidedeny-4752`, off origin/main 844b2372a, rebased onto
146169488 (#4742) after review round 1.

## The finding
`guideDenyRules` in `engine/setup-assistant.js` named Kosmos's data folder once, `Read(//<store.ROOT>/**)`.
On a Mac a Claude guide's sandbox applies the deny rules to every command the guide runs (#3769; measured
again on #4728). A board token can sit in more places than that one folder:

- the older data folder (`store.LEGACY_APP`, "AgentWorkforce"): `boardauth.legacyTokenPath`; boardauth.js says
  a still-valid token may remain there on a computer that ran the mirror removed in #2511;
- for a guide in a named world, the default world's store and every sibling's: a world's guide denies its own
  `store.ROOT`, and a named world's is `<base>/worlds/<id>/Kosmos`. `boardTokenOk` in server.js accepts any of
  the account's world tokens at the main gate. And the default world's store holds more than its token
  (review round 4): agent tokens (`sendertokens/`), device secrets (`secrets/`, `github-app.json`),
  `connect.json`, conversations.

## What I checked first (the card's own open question)
Can the guide's own folder sit under the worlds' base? **Yes**: a named world's agents live in
`<base>/worlds/<id>/workers` (`worlds.envOverridesFor`). So the card's first suggestion, "deny the worlds'
base", is wrong: it would cut a named world's guide off from its own instructions and settings.

## The change
`guideDenyRules` gains, after the data folder rule, in one all-or-none block:
- `Read(//<older folder>/**)` for the older data folder of this world and of the default world (the second
  from the environment as it was before a world was applied, `worlds.preWorldEnv`), each only when it is a
  different folder from the data folder;
- when the worlds' base is not the data folder (the guide is in a named world):
  - `Read(//<base>/board.token)` and `Read(//<base>/.board.token.*)` (the temporary copies boardauth writes
    while it rewrites the token), always;
  - every entry directly in the base, read when the rules are written: a plain file as `Read(//<base>/<name>)`,
    anything else (a folder, or a link that may point to one) as both that and `Read(//<base>/<name>/**)`. The
    base IS the default world's store, so this is that store, entry by entry. Not named one by one
    (`baseEntryToName`, review rounds 5 and 6): the worlds folder and its registry; the registry's lock; every
    DOT-named temporary file (`.<name>.<process id>...tmp`: the registry's, the token's, the world boot
    guard's), which the `Read(//<base>/.*.tmp)` and `.board.token.*` pattern rules cover instead; and a name
    the rule syntax would misread (one of `* ? [ ] ( ) { } !`, a backslash, or a space at either end; review
    rounds 5 and 11), which would deny more than the entry or not parse;
  - `Read(//<base>/worlds/*/Kosmos/**)` and `Read(//<base>/worlds/*/AgentWorkforce/**)`: every named world's store.
- in the default world the base IS the data folder, which the existing rule already denies whole, so nothing
  is added for it.
- if the store cannot be listed (not there is fine; any other error), only the entry list is lost, the other
  rules stay, and one `#4752:` line says so (review round 6).
- if any of the rest cannot be worked out (a require, `preWorldEnv` or `dataRootFor` throws), none of it is added, the rules that were there before still stand, and one `#4752:` line goes to stderr with
  the reason. Before this change `guideDenyRules` could throw only in a corner (`dataRootFor` on a relative root), and `refreshGuideGuards` does not look at
  its result, so a throw would have left an existing guide unrefreshed and made a new guide impossible.

`boardauth` now exports `TOKEN_FILE` and `worlds` exports `WORLDS_SUBDIR`, the two names the rules need, so
they are not re-derived. Two optional parameters (`worldsBase`, `legacyRoots`) let a test hand the folders in;
production passes neither. `refreshGuideGuards` rewrites an existing guide's rules at every board start, so a
guide made before this gets them from its next session, and the list of base entries is re-read then.

**On a rewrite, per-entry rules are made again, not piled up (review round 7).** `guardGuideFolder` keeps every
earlier rule and adds the new ones. For the entries of the default world's store that would mean one rule for
every entry that ever existed (a dated backup, a rotated log). So `guideDenyRulesFor` also says which store it
listed, and `guardGuideFolder` drops an earlier rule only if it is one this code could have written for ONE
entry directly in that store (`wasEntryRule`: the same `ruleAbs(path.join(...))` spelling as the writer, so it
matches on Windows too, and a name `baseEntryToName` lets through) and the new list does not name it. Every
other rule stays: a person's own rule for the registry, or for a name this code leaves alone, included (review
round 8). When the store could not be listed, or is not there at all (it may be moving; review round 9),
nothing is dropped. `guardGuideFolder` also leaves out any of THIS change's rules whose folder, followed through
links, is the guide's own folder or an ancestor of it (an older folder or a store entry a person linked there;
the sandbox follows links), and says so on stderr (review round 12). It checks rules naming one path (a Windows
rule is read with its drive letter; review round 15); a rule with a `*` is not checked, and the rules from before #4752 (the data folder, the account
folders) are left as they were even if a layout puts the guide under one (review round 13). A base or older
folder whose path has a character the rule syntax reads as a pattern gets no rule, and that is said (round 13);
the platform's own separator is not such a character, so a Windows path is not refused for its backslashes
(round 15). **Left as it is (round 15):** all-or-none means a failure working out the older folder also drops
the default world's token rules; round 1 asked for all-or-none so a failure never leaves half, and one
`#4752:` line says it happened.
A rule refused by that check is also kept out of the earlier rules, so one written on an earlier start does not
come back (round 14). The set of characters the rule syntax misreads is one constant (`RULE_SYNTAX`) for both
the entry names and the paths. Not unified (round 14, left): the temporary files' own name shapes stay in their
writers; the `.*.tmp` rule depends only on "starts with a dot, ends in .tmp", and `.board.token.*` on
`TOKEN_FILE`, which is read from boardauth. "The same folder" compares real paths when both exist, so a data folder and a base that
differ only by case or a link are not treated as two (review round 9). The token is not named again in the entry
list (it has its own rule), so no rule appears twice; the registry lock's name is now one function in
`worlds.js` (`registryLockName`) used by both the lock and this code. The older folder is worked out for the `home` the rules were asked about (it used the process's own
home before; review round 7).

## Measured (2026-09-30, Claude Code 2.1.285, this Mac)
A throwaway named-world layout under my scratchpad: a base holding a token, its temporary copies, a
`sendertokens/` and a `secrets/` folder, a `messages.jsonl`, a `notes.txt` and a `worlds.json`; two worlds, each
with a store and a token; an older folder with a token; and a guide folder at `base/worlds/w1/workers/guide`
whose settings were written by the REAL `guardGuideFolder` from this branch. `claude -p

a file rule, a folder rule, a `*` in the middle of a path and a `*` inside a file name are each enforced on a
command, and the guide's commands can still read its own folder under the base. That is not the same as "the
guide still works": no real `kosmos` command was run from it (below).

## Decisions
- **Call:** name what holds tokens and the default world's store entry by entry, never the base. **Rejected:**
  (1) denying the base whole (cuts a named world's guide off from itself, above); (2) a fixed list of known
  secret files in the base (sendertokens, secrets, and so on: the store has dozens of entries, conversations
  included, and a fixed list goes stale with every new one); (3) listing the worlds from the registry (a world
  made later would be uncovered until the next board start; the `*` rule covers it at once, and is measured).
- **Not covered, stated so nobody reads this as complete:**
  - an entry made in the default world's store AFTER the rules were written is readable until the next board
    start rewrites them (the token and its temporary copies excepted: those are always named).
  - a person's own rule for exactly one entry directly in that store, for a name this code would name, is
    dropped on a rewrite if the entry is gone (it cannot be told from one this code wrote).
  - per-entry rules written for an EARLIER worlds' base (the base moved, e.g. `AGENT_WORKFORCE_DATA` changed
    between starts) are never dropped: `wasEntryRule` knows only the current base. They only deny more (round 16).
  - when the store cannot be listed, the per-entry rules from the last listing are all kept, including one for an
    entry that has since become a link to the guide's parent; it goes at the first start that can list (round 16).
  - the worlds' registry, `worlds.json`, which lists the worlds by id and name: left readable on purpose.
  - temporary files WITHOUT a leading dot (`settings.json.tmp`, `remote.json.<pid>.<hex>.tmp` and others; review
    round 10): the pattern rules do not match them. One present when the rules are written is named like any
    entry; one left behind later is readable until the next board start, like any new entry.
  - the default world's workers and projects folders (`~/work/workers`, outside the store), and every named
    world's `worlds/<id>/workers` and `worlds/<id>/projects` under the base (round 18): other agents'
    instruction files. No token there, and outside this card.
  - an entry in the base whose name has one of `* ? [ ] ( ) { } !` or a backslash (a file a person put there,
    say `notes (1).txt`): Kosmos makes none, and a rule for it would be misread, so it is left readable.
  - a linked entry's target, reached by its own path outside the base.
  - a store entry that is a link to something INSIDE the guide's own folder (its `CLAUDE.md`, say; round 19,
    NIT): the own-folder check refuses only the folder itself and its ancestors, so that entry is named, and if
    the sandbox follows the link the guide loses that one file. Left: it needs a person to link into Kosmos's
    own store, and the fix (also refuse a target under the folder) would reopen the loop for a case nobody makes.
  - a browser's copy of the board's cookie (a different store, not a folder Kosmos owns).
  - any guide that is not a Claude guide on a Mac: no sandbox, so these rules stop Claude Code's file tools
    only. That is #4728; #4491's last step closes it.
- **Weakest premise:** that the sandbox treats a `*` in a path the same on every Claude Code version people run.
  Measured on 2.1.285 only.
- **Left as it is (review round 6):** the worlds' base is worked out from `preWorldEnv` here, while the board also
  holds the base it captured at boot (`worldenv.bootedBaseDir`). They agree because the marker round-trips, and
  `preWorldEnv` also works in an agent process that never booted a board; a second source was not worth it.
- **Not measured:** a real guide in a real named world of a real install (the layout above is a stand-in with
  the real rules), and so not `kosmos reply` or any other `kosmos` command run by such a guide under these rules
  (read from code instead: `board_token` reads only this world's own store, and the CLI's own home,
  `~/.local/share/kosmos`, is outside the base; review round 11); Windows and Linux (no sandbox is written there, so nothing to measure). Not tested on Windows
  either: the `*` rules join with `/` onto a Windows path, the same mixed shape the data folder rule has always
  had there.

## Tests
`engine/guide-deny-4752.test.js`, seventeen tests (some bullets below are assertions inside the same test) (POSIX rule strings; the file runs on the Mac and Linux jobs):
- a named world's rules for handed-in folders, exactly;
- no rule covers the guide's own folder under the base, with controls that the cover check can say yes, yes
  through a `*`, and no;
- the default world: no second rule for the base, the older folder only when it is another folder, nothing
  for a folder that could not be worked out;
- worked out from the process with nothing handed in: the older folder beside the data folder is denied;
- a child process that enters a named world (`worlds.applyAgentWorldEnv`, the agent's way; the board's goes
  through the same `applyWorldEnv`) still finds the base, and does not deny it whole;
- when the worlds folder name cannot be read, the earlier rules come back, none of the extra ones, and one
  `#4752:` line is said; control: readable again, they are back;
- a real base with folders and files: each entry is named, the worlds folder and registry are not, the base
  is not named whole;
- when `preWorldEnv` throws: said on stderr, and the earlier rules still there.
- odd entries: the registry's lock, its temporary file, a token copy and a world boot guard temporary file are
  not named one by one (the pattern rules are there), `notes (1).txt` and `a*b` are left out, `My Notes.txt` is
  named, and a link gets both forms.
- a store that cannot be listed (the base is a file): the token, older-folder and worlds rules stay, one line said.
- a rewrite after a store entry is deleted: its rule goes, the rule for an entry still there stays, and a
  person's deeper rule and a rule elsewhere stay.
- a rewrite after a person added a rule for the registry: it stays.
- a rewrite while the store cannot be listed (its folder replaced by a file, so it fails for any user, root
  included): the rules from the last listing stay.
- a real store with a token: no rule appears twice.
- the older folder follows the `home` passed in, not the process's (a child process with another home; only
  where AGENT_WORKFORCE_DATA is unset, since dataRootFor then ignores the home).
- an older folder that is a link to the guide's own parent: its rule is left out, said once, and the data folder
  rule is still written.
- a workers folder inside the data folder: the data folder rule stays; a linked store entry pointing at the
  guide's parent is left out.
- a base and an older folder with `(` in the path: no rule for either, both said.
- a linked entry named on one start, then re-pointed at the guide's parent: its rule is gone after the rewrite.
- (round 16) both of a linked entry's rules are checked: the plain `Read(//<base>/linked)` is left out as well
  as the `/**` one (mutation: the `/**` made required in the own-folder check, 2 fail).
- (round 18) a FOLDER entry deleted between two starts loses both its rules (mutation: `wasEntryRule` no longer
  strips `/**`, 1 fail); a store entry that is a link to the guide folder ITSELF gets no rule (mutation: the
  `own !== target` arm removed, 1 fail). Round 18 ran 18 mutations; the only other greens were Windows-only
  branches (same on POSIX, and no Windows run selects this file) and two shown equivalent.
