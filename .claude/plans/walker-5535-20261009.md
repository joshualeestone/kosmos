# walker-5535: E0.6 (#5535) build-order step 3, the snapshot walker

## Why
Everything a backup is made of is on main and reviewed: what may leave (engine/backupscan.js), the chunk and
manifest format (engine/backupformat.js), the uploader for chunks and the manifest (engine/backupupload.js). Nothing
composes them. The walker is the module that takes one snapshot of a work Kosmos: walk, decide, chunk, seal, upload
what the period has not got yet, then seal and upload the manifest LAST (design v1 section 4: a snapshot without a
manifest is incomplete and ignored, so a crash never leaves one that looks whole).

## Change: `engine/backupsnapshot.js`
- `periodOf(ms)`: the coordinator's period label (coordinator/src/backup.rs period_of: ISO week of the Monday 00:00
  UTC that starts it, "2026-W41"). The naming key is per period and chunks are named BEFORE any grant, so the Mac
  must name the same period the coordinator will grant in.
- `listFiles(root, fs)`: every regular file under the work Kosmos the deny-list allows, with the device and inode
  seen. The deny-list runs BEFORE anything is opened: a denied folder (.git, .ssh, secrets/ ...) is pruned and
  recorded once (every folder rule ends in '/', so `<folder>/x` matches exactly those), a denied file is recorded
  unread. LINKS ARE NOT FOLLOWED (file or folder): each is recorded as skipped.
- Reading (review 1): one open per file with O_NOFOLLOW and O_NONBLOCK (a FIFO swapped in cannot hang the run); the
  descriptor must be a regular file with the walk's device and inode, so what is read is the very file the walk
  found; then its real path must be inside the work Kosmos and pass the deny-list again; at most maxFile + 1 bytes
  are read from the descriptor.
- `takeSnapshot(input, deps)`:
  1. checks its inputs (keys, the five-field manifest context via checkBackupContext, ctx.period === periodOf(now)).
  2. for each file in order: pathDecision, size cap (MAX_FILE), read, scanFile; a skip is recorded `{ path, why }`;
     a store is chunked with chunkBuffer and each chunk sealed with sealNamedChunk. The file entry records the size
     and sha256 of the bytes UPLOADED (the redacted copy) and its chunk names in order.
  2b. the manifest's size is bounded BEFORE anything is uploaded (review 1): a file-count ceiling (restore's 500,000)
     and a running estimate against the coordinator's 64 MiB manifest ceiling, checked before every batch, so a
     manifest that could never be stored never leaves locked chunks behind (tooLarge, not a retry).
  3. a chunk already in the period index (from an earlier run) or earlier in this snapshot is not sealed into the
     upload twice. New chunks are uploaded in bounded batches (BATCH_BYTES of sealed objects) through uploadChunks,
     so a snapshot is never held in memory whole.
  4. every key uploadChunks returns must carry ctx.period as its period segment (the key layout is
     <org>/<account>/<epoch>/<period>/<random>, backupupload's own check), and every batch's bucket must equal the
     index's bucket: else the run stops (a period boundary between naming and granting; retry next period).
  5. the manifest `{ format: 1, takenAt, namingKeyId, files, skipped, redacted, objects }` (objects: chunk name to
     object key, for every chunk the files name, so restore can fetch by name) is sealed with sealManifest and
     uploaded with uploadManifest, passing the bucket and every referenced chunk's key and lock end.
- The index is checked first: every entry this period's, with a key, a lock end and a named bucket. A bad index, a
  grant in another bucket, or a manifest refused as outlasting the index's chunks is `staleIndex` (drop the index,
  keep `added` under the returned bucket), never `retryLater`, which would fail the same way again (review 1).
- Returns `{ ok, manifestKey, ... }` or `{ ok: false, because, retryLater?, staleIndex?, tooLarge?, grantSpent?, unsure? }`, and ALWAYS `added`: the index
  entries this run stored (name to key and lock end), so the caller keeps them even when the run failed (a later run
  then does not upload them again). Never throws.

## Not in this change
Key storage and the policy bundle (the member public key, the naming key per period: inputs here); persisting the
period index (the caller's); the schedule and freshness report (step 5); the Settings switch.

## Decided
- Links are skipped, not followed (rejected: follow file links whose real path is inside the root). A followed link
  needs a check-then-read with a race window, and a folder link can loop. Skipping loses only link targets, which are
  inside the root anyway and so backed up under their own path. Changes if agents keep real work behind links.
- The manifest carries the name-to-key map (rejected: a separate index object). Restore needs it for every file, the
  manifest is already sealed and signed, and design v2.1 item 7 keeps chunk names out of storage.
- Upload what the index lacks, by name (rejected: always upload). The index is the period dedup design v1 section 5
  describes.
- Weakest premise: the caller can keep the period index between runs (the next slice). Without it every run uploads
  a full copy, which is correct and only costs storage.

## Tests
`engine/backupsnapshot.test.js` (20; 8 added in review 1, of which 6 fail on the review-0 module and 2 guard behaviour it already had): periodOf across week and year boundaries; a round trip through the REAL restore
(engine/backuprestore.js) byte for byte, with the token redacted, the .env and both links skipped, and every stored
chunk decrypted and checked for the token and the outside file's text; a second snapshot uploads only the changed
chunk and still restores whole; bounded batches; a context in the wrong period refused before any upload; a key in
another period stops the run before the manifest; a failed chunk upload and a failed manifest upload each return what
was stored; the size cap; an index without its bucket; never throws; a chunk two files share is uploaded once across a
batch boundary; a denied folder pruned and nothing denied opened (an fs spy); a file replaced after the walk; a real path
outside; a FIFO; a bucket mismatch; a bad index; the manifest ceiling before any upload; outlastsChunks. Mutants (scratchpad wmut.sh, refuses a dirty tree): 12 of 12 red, after `nodedupwithin` survived the
first run and got its test.

## Noted, not changed here
The scanner skips uniformly random bytes more often as they grow (measured, 10 each: 1 at 100 KB and 500 KB, 5 at
1 MB, 9 at 3 MB; "binary file holding something shaped like a credential"): a long random run contains key-shaped
text by chance. Real media is not affected: 20 images and PDFs from 20 KB to 25 MB, and 12 HEIC photos from 8 to 25 MB,
were all stored. So what a backup may leave out is encrypted or random blobs, named in `skipped`; that is backupscan's
fail-closed rule, not this module's. The round-trip test uses text for its big file for this reason. (My first
version of this note said real binaries such as images may often be left out; measuring real files showed otherwise.)
