# walker-5535: E0.6 (#5535) build-order step 3, the snapshot walker

## Why
Everything a backup is made of is on main and reviewed: what may leave (engine/backupscan.js), the chunk and
manifest format (engine/backupformat.js), the uploader for chunks and the manifest (engine/backupupload.js). Nothing
composes them. The walker is the module that takes one snapshot of a work Kosmos: walk, decide, chunk, seal, upload
what the period has not got yet, then seal and upload the manifest LAST (design v1 section 4: a snapshot without a
manifest is incomplete and ignored, so a crash never leaves one that looks whole).

## Change: `engine/backupsnapshot.js`
- `periodOf(ms)`: the coordinator's period label (coordinator/src/backup.rs period_of: ISO week of the Monday 00:00
  UTC that starts it, "2026-W41"). The naming key is per period and chunks are named BEFORE any grant, so the Mac
  must name the same period the coordinator will grant in.
- `listFiles(root, fs)`: every regular file under the work Kosmos the deny-list allows, with the device and inode
  seen. The deny-list runs BEFORE anything is opened: a denied folder (.git, .ssh, secrets/ ...) is pruned and
  recorded once (every folder rule ends in '/', so `<folder>/x` matches exactly those), a denied file is recorded
  unread. LINKS ARE NOT FOLLOWED (file or folder): each is recorded as skipped.
- The naming key id the manifest records must be this naming key's (backupkeys namingKeyId), checked before
  anything is read (review 21): restore matches it against the key it unwraps, so a stale id would lock in a
  manifest that can never be opened. The tests' fixture used a made-up id and could not have caught it.
- Rebased onto main 2026-10-09 04:40 (82 commits, among them backupkeys and the uploader's reached-rule change); the
  walker, restore, uploader and reachability tests all pass on it (183).
- Names are checked for credentials too (review 19): secretmask on each segment, specific kinds only. Its generic
  long_token fires on ordinary long names (measured on 8,146 real paths: 271), the specific kinds on 1 (an "xai" in
  a plan name). A file or folder whose name fires is skipped and recorded under the MASKED name, so the token is in
  no part of the manifest. Fails safe on that rare false positive.
- The manifest's own key is checked after it is stored (review 19): Monday can pass between the walker's period check
  and the coordinator signing the grant, so a key in another period is reported as newPeriod (grantSpent), never ok.
- The deny-list also judges restore's equivalence of a name, collisionKey (review 18): `.git` with a zero-width
  space is `.git` to restore. Denied if either reading is.
- The deny-list judges every path AS RESTORE WILL WRITE IT, with '\\' read as '/' (review 15, measured): a Mac name
  like `.ssh\\id_rsa` passed every rule (they anchor on '/') and restore would write it as `.ssh/id_rsa`.
- Reading (review 1): one open per file with O_NOFOLLOW and O_NONBLOCK (a FIFO swapped in cannot hang the run); the
  descriptor must be a regular file with the walk's device and inode, so what is read is the very file the walk
  found; then its real path must be inside the work Kosmos and pass the deny-list again; at most maxFile + 1 bytes
  are read from the descriptor. A hard link (nlink > 1) is skipped: it has no real path of its own to check.
- Paths restore would refuse (engine/backuprestore.js pathProblem: unsafe or not portable) are skipped at backup time,
  and of names restore refuses as colliding (the same collisionKey, or a file whose key is another entry's folder:
  restore's collidingPaths) the first in sorted order is kept, the rest skipped and named (reviews 2 and 3); the kept
  set is checked with backuprestore's own collidingPaths, which it now exports with pathProblem and collisionKey. Stored and then refused at restore would
  lock bytes for weeks that could never come back.
- `takeSnapshot(input, deps)`:
  1. checks its inputs (keys, the five-field manifest context via checkBackupContext, ctx.period === periodOf(now)).
  2. for each file in order: pathDecision, size cap (MAX_FILE), read, scanFile; a skip is recorded `{ path, why }`;
     a store is chunked with chunkBuffer and each chunk sealed with sealNamedChunk. The file entry records the size
     and sha256 of the bytes UPLOADED (the redacted copy) and its chunk names in order.
  2b. NOTHING is uploaded unless the finished manifest is sure to fit (reviews 1 and 3). A file-count ceiling
     (restore's 500,000); then an upper bound per listed file from its size alone (every chunk but a file's last is at
     least CDC.min, and the stored copy may be at most twice the file: a bigger redacted copy is skipped), reserved
     until the file is done; keys charged at MAX_KEY_LEN (256) until granted, then at their real length. Before the
     walk, the exact skips plus every file's reserve must fit 80% of the coordinator's 64 MiB ceiling (Padme adds at
     most about 12%); that one check is enough by construction (see Mutants).
     A file over maxFile reserves only its skip entry (review 5: counting its size made one 20 GB disk image refuse
     every snapshot). The bound is pessimistic by design (CDC.min chunks, twice the size, the longest key), so one
     snapshot holds about 20 GB of files under maxFile; the tooLarge reason says so with the listed size. Tightening it
     (charging each file once read) is the next step if a work Kosmos gets near that.
     The pre-walk check is the guard and is enough by construction (no per-batch check: see Mutants).
     Review 3 measured my first version (a running "so far" check) locking 36 to 60 chunks before refusing; a test now
     sweeps ceilings with real-length keys and requires either a manifest that fits or zero uploads.
  3. a chunk already in the period index (from an earlier run) or earlier in this snapshot is not sealed into the
     upload twice. New chunks are uploaded in bounded batches (BATCH_BYTES of sealed objects) through uploadChunks,
     so a snapshot is never held in memory whole.
  4. every key uploadChunks returns must carry ctx.period as its period segment (the key layout is
     <org>/<account>/<epoch>/<period>/<random>, backupupload's own check), and every batch's bucket must equal the
     index's bucket: else the run stops (a period boundary between naming and granting; retry next period).
  5. the manifest `{ format: 1, takenAt, namingKeyId, files, skipped, skippedNotListed, redacted, objects }` (objects: chunk name to
     object key, for every chunk the files name, so restore can fetch by name) is sealed with sealManifest and
     uploaded with uploadManifest, passing the bucket and every referenced chunk's key and lock end.
- Every key, from the index or a grant, must be `<org>/<account>/<epoch>/<period>/<random>` with the context's org
  and period (review 4): one under another period was named with another naming key, and a manifest naming it would
  not restore. NOT the epoch segment (review 13): the coordinator writes a constant there (backup.rs EPOCH = 1), so
  it cannot say which member key sealed a chunk. That binding is each index entry's `memberKeyId` (a domain-tagged
  SHA-256 of the member public key, 16 bytes, hex), recorded by the walker in `added`; an entry for another member
  key, or with none, is stale. Weakest premise here: the context's org id is the coordinator's own (the key's first
  segment); spelled differently, every snapshot fails loudly, never silently.
- A chunk is named first and sealed only if it will be uploaded (review 13), so a second run in the period does not
  re-encrypt the whole work Kosmos. A folder is re-checked (device and inode) after it is listed (review 13 NIT).
- Every key must also be under ONE `<org>/<account>` (the index's, or the first grant's), use plain segments, and an
  index lock end must be one a grant could set (after 2020, at most 39 days and an hour ahead): the same rules
  uploadManifest applies, checked before anything is read so a bad index is `staleIndex`, not a failure every run
  (review 7). A file over maxFile at walk time is skipped before it is opened (review 7: one that shrank before the
  read was stored past its reserve).
- The week's allowance (review 9): before anything is spent, this period's earlier chunks plus this run's upper
  bound must fit the coordinator's 200,000 chunks, and this run's new bytes 64 GiB (review 10: the index records no
  sizes, and charging earlier chunks at the largest size refused ordinary second runs; bytes spent earlier are
  caught by backup_quota), per member per week; a `backup_quota` refusal is
  `overAllowance` (not this period), never a retry. The real path checked must be the very inode opened (review 9: a
  folder swapped for a link and back could make the path checked differ from the file read); a file that grows
  during the read is named as grown, not too large; an index lock that ends before this snapshot's manifest would is
  stale up front.
- No key is ever named for two chunks (review 5): every key from the index and every grant is kept in one set, and a
  repeat fails the run with `added` intact; the uploader's answer is accepted only for names this run asked to store.
- The walk is bounded (review 4): it stops once past MAX_FILES, and skips past MAX_SKIPPED are only counted. Device and
  inode are compared as bigints.
- The index is checked first: every entry this period's, with a key, a lock end and a named bucket. A bad index, a
  grant in another bucket, or a manifest refused as outlasting the index's chunks is `staleIndex` (drop the index,
  keep `added` under the returned bucket), never `retryLater`, which would fail the same way again (review 1).
- Returns `{ ok, manifestKey, ... }` or `{ ok: false, because, retryLater?, newPeriod?, staleIndex?, tooLarge?, overAllowance?, grantSpent?, unsure? }`, and ALWAYS `added`: the index
  entries this run stored (name to key and lock end), so the caller keeps them even when the run failed (a later run
  then does not upload them again). Never throws.

- A period boundary passed during the run means NO manifest grant (reviews 15 and 17): the manifest is sealed with
  ctx.period, but the coordinator would file it (key, record, lock) under the period it is granted in, so a restore
  looking it up by that period could not open it, and earlier chunks might not outlast its lock. The run stops as
  `newPeriod` and starts again in the new period. Rejected: allowing it when every chunk outlasts the new manifest
  lock (my review-15 version): the period mismatch alone makes the snapshot unrestorable by lookup.
- `newPeriod` (review 3), not retryLater, when the context's or a grant's period is not this one: the same input can
  never succeed; the caller needs the new period's context and naming key.

## Not in this change
Key storage and the policy bundle (the member public key, the naming key per period: inputs here); persisting the
period index (the caller's); the schedule and freshness report (step 5); the Settings switch.

## Decided
- Links are skipped, not followed (rejected: follow file links whose real path is inside the root). A followed link
  needs a check-then-read with a race window, and a folder link can loop. Skipping loses only link targets, which are
  inside the root anyway and so backed up under their own path. Changes if agents keep real work behind links.
- The manifest carries the name-to-key map (rejected: a separate index object). Restore needs it for every file, the
  manifest is already sealed and signed, and design v2.1 item 7 keeps chunk names out of storage.
- Upload what the index lacks, by name (rejected: always upload). The index is the period dedup design v1 section 5
  describes.
- node_modules and other dependency trees are walked and backed up (review 3 NIT: rejected pruning them here). What a
  backup covers is design v1 section 4's call ("its agent folders and their files ... work products"), not the
  walker's; a dependency tree in a work Kosmos is unusual, and the deny-list is where to add one if it is not.
- Hard links are skipped, which also skips a pnpm-style node_modules (hard links into the package store), named one
  per file in `skipped` (review 7 NIT). Recorded, not changed: a dependency tree in a work Kosmos is unusual, and the
  skip is the safe side.
- A grant in another bucket (review 8 asked the cost be stated): `added` is reported under one bucket, so it becomes
  that batch's chunks under the NEW bucket; chunks earlier batches of the same run stored under the old bucket stay
  locked and unnamed until their lock ends, and the period's dedup saving for them is lost. A bucket change mid-period
  is a coordinator configuration change, rare enough that keeping two buckets' worth of index is not worth it.
- One bad index entry discards the whole index (review 6 NIT: rejected dropping only the bad entries). A bad entry
  means the caller's index is not what the walker expects (another epoch, period or bucket), so its other entries are
  suspect too; a full upload of the period is safe and only costs storage.
- Mounted volumes inside the work Kosmos are not crossed (review 11): skipped and named.
- A collision partner skipped later (unreadable, replaced, refused by the scan) leaves its sibling skipped too
  (review 11 NIT): fails safe, both named in `skipped`; re-admitting siblings would mean a second pass. Recorded.
- Weakest premise: the caller can keep the period index between runs (the next slice). Without it every run uploads
  a full copy, which is correct and only costs storage.

## Noted, not changed here
The scanner skips uniformly random bytes more often as they grow (measured, 10 each: 1 at 100 KB and 500 KB, 5 at
1 MB, 9 at 3 MB; "binary file holding something shaped like a credential"): a long random run contains key-shaped
text by chance. Real media is not affected: 20 images and PDFs from 20 KB to 25 MB, and 12 HEIC photos from 8 to 25 MB,
were all stored. So what a backup may leave out is encrypted or random blobs, named in `skipped`; that is backupscan's
fail-closed rule, not this module's. The round-trip test uses text for its big file for this reason. (My first
version of this note said real binaries such as images may often be left out; measuring real files showed otherwise.)
