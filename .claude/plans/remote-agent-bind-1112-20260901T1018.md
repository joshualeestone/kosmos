# remote-agent-bind-1112 — Windows-agent bind + auth + remote token issuance (Phase 2)

Kosmos #1112 / #570 Phase 2. Approved by Josh 2026-09-01 09:15 ("ship them together
if that's safe... that's the recommendation"), re-confirmed by Splinter ("bind and
issuance together"). The report side and paneless roster (Phase 1) are already built
and tested; this is the network bind, the auth that makes opening it safe, and the
operator-driven remote token issuance, as one inseparable change.

## The security problem this must not get wrong

The board's write endpoints include `POST /api/agents`, which installs a launchd job
running Claude with `--dangerously-skip-permissions`. Today the ONLY thing stopping a
network client from reaching it is the loopback bind at `server.js:7804`
(`server.listen(port, '127.0.0.1')`). `crossSiteWrite` does NOT contain a direct
network client: a request with no `Origin` header and an `application/json` content
type passes it entirely. `crossSiteWrite` is a browser guard, not a reachability guard.
The warning at `server.js:7635` states this: "localhost is a default, not a guarantee.
Reachability and login arrive together or not at all."

So the bind cannot simply open. Opening it naively exposes agent-installing writes to
any network client with no auth. The bind and the auth are therefore one change.

## What a token can and cannot do (the justification for least-exposure)

A `KOSMOS_AGENT_TOKEN` (64-hex, 32-byte CSPRNG) IS an identity. `sendertoken.resolve()`
requires a MANDATORY roster tie (`isNamedOurs === true`); for a paneless agent,
`resolveAgentSender` uses `resolveName` + `liveness.alive(key) === true`. So a token can
only speak AS an agent that already exists and is already live. It cannot name a new
identity, cannot create, cannot escalate.

What the token-gated surface (`/api/report`, `/api/reply`) can DO is bounded to: write
that agent's own state + `because`, and send messages as it. No execution, no install,
no filesystem beyond the report/token records, ZERO reach to `POST /api/agents` or any
local-management write. So the worst case of a stolen/forged token on an open bind is:
impersonate one existing live agent's status and messages. Not machine compromise. That
bound is exactly why exposing only report+reply is safe, and why every dangerous write
stays loopback-only regardless.

## The design — three parts, one change

### 1. `remoteWriteGuard(req)` — the auth that contains the bind

A sibling to `crossSiteWrite`, run in the same before-every-route position in the
`http.createServer` handler. It keys on the connection's actual peer,
`req.socket.remoteAddress`, NOT on a header (a header is client-controlled; the socket
peer is not):

- **Loopback peer** (`127.0.0.1` / `::1` / `::ffff:127.0.0.1`) → returns null. Behaviour
  is exactly as today. This invariant guarantees nothing changes for the Mac operator,
  the board UI, or any local process. The whole existing suite must stay green.
- **Remote peer** (anything else, INCLUDING an undefined remoteAddress — fail closed) →
  permitted to reach ONLY an allowlist of token-authenticated agent routes:
  `POST /api/report`, `POST /api/reply`. It MUST present a valid `x-kosmos-agent-token`
  (validated via `sendertoken.resolveName(token).ok`, which is constant-time and needs
  no roster). Any other route, or a missing/invalid token → 403 with a SINGLE uniform
  refusal sentence (non-oracle: a network probe must not learn whether a route exists or
  a token is valid — same posture as `sendertoken`'s deliberately-identical `NO_MATCH`).

Containment property worth stating: because the guard keys on the socket peer, opening
the bind does NOT expose the board UI or any operator surface to the network. A browser
from another machine is a remote peer with no token → 403 everywhere except report/reply,
which it cannot reach without a valid token. Only token-holding agents get in.

Boundary explicitly out of scope for this cut (documented, not solved): a reverse
proxy / tunnel (Tailscale Funnel, warning arm #2) terminates locally, so the socket peer
is loopback while the real client is remote. Trusting `X-Forwarded-For` to recover the
real client is its own footgun and is NOT done here. The guard protects a DIRECT network
bind, which is the approved Windows-agent case. The proxy vector remains an operator
opt-in risk exactly as the existing warning documents it.

### 2. The bind opt-in (`server.js:7804`)

`server.listen(port, bindHost())` where `bindHost()` returns `'127.0.0.1'` by default and
a network host ONLY when the operator explicitly sets `KOSMOS_BIND_HOST` (e.g. `0.0.0.0`
or a specific interface IP). Default unchanged = loopback = an un-opted-in board binds
byte-identically to today. Opening it is now safe because `remoteWriteGuard` contains
what it exposes. Read at listen time (boot); a Settings toggle would need a restart to
take effect, so env is the honest mechanism. (A Settings switch that writes the env is a
clean follow-up; not in this cut.)

### 3. Remote token issuance — `POST /api/agent-token` (loopback-only)

The Mac operator mints a token for a named remote agent and hands it over. Body `{name}`
→ `sendertoken.mint(name)` (exists; returns `{ok, token, instance}`) → responds
`{ok, name, token, instance}`. It is loopback-only for free: it is NOT on
`REMOTE_AGENT_ROUTES`, so `remoteWriteGuard` 403s a remote peer, and `crossSiteWrite`
handles browsers on other origins. So issuance is reachable only from a loopback,
same-origin client (the board on the Mac, or curl on the Mac). Minting a token for a name
is not itself dangerous: the name does nothing until it is live and reporting
(`resolveAgentSender` still enforces liveness + tie). No UI in this cut (a web/ change
would pull in the browser-check dependency and needs Playwright); the "add a remote
agent" button that calls this endpoint is a clean follow-up card.

## Files

- `server.js`: add `LOOPBACK_PEERS`, `isLoopbackPeer(req)`, `REMOTE_AGENT_ROUTES`,
  `remoteWriteGuard(req)` (placed right after the `crossSiteWrite` refusal block);
  add the `POST /api/agent-token` route; change the bind to `bindHost()`.
- New unit test file(s) exercising the guard, the bind default, and issuance — each
  assertion red-capable, each with a control that can return the dangerous answer.

## Tests — the security-critical part, each red-capable with a real negative arm

1. **The core containment test**: a REMOTE peer to `POST /api/agents` → 403 (guard
   refuses). CONTROL: a LOOPBACK peer to the same route → passes the guard (reaches the
   route). This is the "owning the relay does not own the Mac" test; if the control did
   not reach the route, the 403 would prove nothing.
2. Remote peer to `POST /api/report` WITHOUT a token → 403. WITH a VALID issued token →
   passes the guard. CONTROL: remote peer to `/api/report` with an INVALID token → 403,
   and the refusal sentence is byte-identical to the no-token refusal (non-oracle).
3. Remote peer to `POST /api/reply` — same shape as (2).
4. **Loopback unchanged (regression)**: a loopback peer reaches every route exactly as
   today. Assert the guard returns null for each loopback-peer method/path, so the full
   existing suite stays green.
5. `bindHost()`: default (no env) → `'127.0.0.1'`; with `KOSMOS_BIND_HOST=0.0.0.0` →
   `'0.0.0.0'`. Assert the default is unchanged so an un-opted-in board binds identically.
6. Issuance: `POST /api/agent-token {name}` from a loopback peer mints a token that a
   subsequent `resolveName` maps to that name; a REMOTE peer to `/api/agent-token` → 403
   (loopback-only). CONTROL for "it really minted": before the mint, `resolveName(token)`
   is not-ok; after, it is ok — so the test cannot pass on a stale store.

The guard is validated by PERTURBING each arm: flip the peer to loopback (the 403 must
disappear), drop the token (the 403 must appear), change the route off the allowlist (the
403 must appear). Each arm must move the verdict, or it is decoration.

## Not in this cut (follow-up cards)

- UI "add a remote agent" button calling `POST /api/agent-token` (web/ change, needs
  Playwright / browser-check).
- A Settings switch that writes `KOSMOS_BIND_HOST` (UI + restart semantics).
- `X-Forwarded-For` trust for a reverse-proxy/tunnel deployment (a distinct, careful
  design; the direct-bind case is what is approved).
- Code signing of the Windows package (#1748, procurement).
