# twa-address-2854: the Android app opens the person's own address full screen

Card: kosmos #2854, Android half (Liu Kang m1005, claimed:kano). Mac half: kosmos-relay #161
(each Mac serves /.well-known/assetlinks.json), merged a87dd52.

## Finished means

- After sign-in inside the Android app, tapping "Open my Kosmos" opens
  `https://<name>.kosmosplus.com/#kst=<token>` as a TWA with that address (and the person's
  other valid addresses) passed to `setAdditionalTrustedOrigins`, so Chrome can verify it
  against #161's assetlinks and drop the URL bar.
- `launchUrl` is still `https://login.kosmosplus.com/`; nothing per-user is in the APK.
- The address choice is a pure Java class with JVM unit tests: 0, 1 and several addresses;
  foreign, malformed, punycode, uppercase-trick, port/path/userinfo and the coordinator's own
  host are rejected, by the same one-label rule as iOS `PushBridgeLogic.isMacHost`.
- `./gradlew testDebugUnitTest assembleDebug` is green and the debug APK exists.
- A companion kosmos-relay PR makes the sign-in page hand the address to the app (below).
- The on-phone measurement (Sonya, emulator) is NOT part of finished: it waits for a Josh-gated
  tunnel release carrying #161.

## Decision: how the address reaches the app

**Chosen:** the page hands it over. In the Android app, the sign-in page's `openKosmos(addr)`
still asks `/v1/account/handoff` for the short-lived token, then navigates to
`intent://open#Intent;scheme=kosmos-open;package=io.kosmos.app;S.address=..;S.addresses=..;S.kst=..;S.nonce=..;S.browser_fallback_url=..;end`
instead of `https://<addr>/#kst=..`. A new exported `OpenAddressActivity` validates the hosts and
launches the TWA. The app binds this to its own launch with a nonce (see Security notes). This mirrors iOS, where the page is also the only holder of the session and
hands the app what it needs (`handToApp`).

**Rejected:**
- The app calls `/v1/account/me` itself: it has no session. The session lives in Chrome's page
  storage; getting it into the app means passing the 30-day session through an intent, which is
  exactly what kosmos-relay #3837 A stopped doing in URLs.
- Custom Tabs postMessage channel: works in principle, but needs a page-side message protocol,
  origin handshake and Chrome 115+, for the same one-way value the intent carries.
- Letting the TWA navigate from login to the address: a TWA cannot add a trusted origin
  mid-session, which is the whole problem.

**Weakest part (named):** Chrome launches an `intent://` from a page only with a user gesture.
The tap is a gesture, but the handoff `fetch` sits between the tap and the navigation. Chrome's
transient activation lasts about 5 seconds, so a normal fetch should be inside it, but I have
not measured it on a phone. The automatic open after "your Mac allowed this device" (`arrived()`)
has no gesture at all, so in the app it must show the button instead of auto-opening.

**What would change my mind:** Sonya's emulator run showing the intent blocked after the fetch.
Then: fetch the token first and navigate synchronously on a second tap, or move to postMessage.

## Security notes

- `OpenAddressActivity` is exported and BROWSABLE, so any web page in Chrome (after a tap) or any
  installed app can fire it. My first version said the worst case was no more than a browser
  link; the first review round showed that was wrong: someone running their own Kosmos+ Mac could
  send their own valid address and token, and the app would show their page FULL SCREEN, with no
  URL bar, which a browser link cannot do.
- Fix: a per-launch nonce. `KosmosLauncherActivity` puts a fresh 128-bit value in the fragment of
  the sign-in page's launch URL (`#kosmos-app=<hex>`) and keeps it. The page stores it in
  sessionStorage and sends it back in the intent. `OpenAddressActivity` opens a TWA only when it
  matches; otherwise a plain Custom Tab (see round 4 below for why withholding
  `setAdditionalTrustedOrigins` alone was not enough).
- The page hands off to the app only when it holds a nonce, so an older APK (which never sends
  one) keeps today's web behaviour. The intent also carries `S.browser_fallback_url`.
- Hosts are still checked with the one-label rule, and the chosen host must be on the account
  list the page sends (an intent without the list is refused).
- The token is the existing short-lived handoff token, put in the fragment as the page does
  today; it is checked against a URL-safe charset so it cannot inject into the URL.
- **Residual:** a nonce stays valid for the whole launch, not one tap, so switching between your
  own Macs stays full screen. It is only ever in the page's sessionStorage and the app's private
  preferences.
- **Residual:** any start of the launcher (a relaunch, or a sign-in link opened while the app runs)
  mints a new nonce, so a sign-in page already open holds a stale one and its next open shows the
  URL bar. Fails safe; not signalled on screen.

## Challenge-loop rounds 11 and 12 changes

- Round 11: the RuntimeException catch for unreadable extras no longer wraps AddressChoice, so a
  bug there is not logged as a hostile caller.
- Round 12: a refused open now just finishes. Restarting the launcher (rounds 6 and 8) re-minted
  the nonce, so any page or app could fire a junk kosmos-open and silently downgrade the
  person's open sign-in page. Finishing leaves that page and its nonce as they were; the page's
  own refused-handoff latch (kosmos-relay be06fdd) covers a tap that goes nowhere.
- Round 12: the https scheme and the #kst= fragment are named constants in AddressChoice.
- Round 12: commit subjects reworded to the repo rule (single sentence, no special characters).
- Deferred: "OpenAddressActivity shows a blank white window while TwaLauncher binds". Its theme's
  windowBackground is @drawable/splash_screen, with values-night variants.
- Deferred (duplicate of round 10): no JVM test for the Uri rebuild and the activity branches.

## Challenge-loop round 10 changes

- Reopened the "no automated test for the launcher guard" deferral (rounds 5 and 9): the reason
  given, that android.net.Uri needs Robolectric, only held for the rebuild, not the decision.
  The decision is now AddressChoice.isSignInUrl(scheme, host, coordinatorHost), JVM-tested
  (http, other schemes, a Mac host, suffix tricks, null and misconfigured coordinator).
  Still untested: the Uri rebuild itself and the activity's fullScreen branch (the value it
  branches on is tested both ways).
- AddressChoice's doc no longer implies the account-list check tells the page from a forgery;
  it is a shape check, and the nonce decides fullScreen.
- README: a refused open, which any page or app can fire, also replaces the nonce.

## Challenge-loop round 9 changes

- Deferred: "another app can declare scheme kosmos-open and receive the kst token". The sign-in
  page's intent:// link names package=io.kosmos.app (kosmos-relay coordinator/src/signin.html,
  pinned by coordinator/tests/page/signin.test.js intentFor), and Chrome delivers a
  package-scoped intent only to that package. The dependency is cross-repo: dropping package=
  on the page would reopen it.
- The TWA launch is wrapped like the Custom Tab one: with no browser at all, TwaLauncher's
  Custom Tab fallback throws ActivityNotFoundException; it is now logged and the activity
  finishes instead of crashing.
- Deferred again: no JVM test for KosmosLauncherActivity's URL rebuild (same reason as the
  fullScreen branch: android.net.Uri needs Robolectric, which this module does not have).

## Challenge-loop rounds 7 and 8 changes

- Round 7 (deferred): "a rotation between onCreate and TwaLauncher's callback double-opens". Not
  reachable in androidbrowserhelper 2.5.0 (read from its bytecode): the launch and the completion
  Runnable run back to back on the main thread, and destroy() sets mDestroyed so a launch not yet
  made is skipped. The rotation item stays on the on-phone checklist.
- Round 8: the round-6 refusal path started KosmosLauncherActivity with no data, and
  LauncherActivity.onCreate finishes at once on a data-less intent while another launcher is
  alive (the usual case: the one under the sign-in TWA). The refused tap did nothing. It now
  carries the sign-in URL as data, so it launches and mints a fresh nonce (the old page's nonce
  goes stale, which fails safe).
- Round 8: the launcher's guard compared only the host and passed the caller's string through.
  It now requires https and rebuilds the URL from the configured host, keeping path, query and
  fragment. Weakest part: no automated test (android.net.Uri is not usable in the JVM tests
  without Robolectric); covered by on-phone checklist commands.
- The test file's lookalike characters are \u escapes, so an encoding round-trip cannot turn
  them into ASCII and leave the tests passing for the wrong reason.

## Challenge-loop rounds 5 and 6 changes

- Round 5: OpenAddressActivity's two catch blocks swallowed failures at an exported boundary. They
  now log the failure kind only (never the token or address), plus one line when AddressChoice
  refuses. Deferred: an automated test of the activity's fullScreen branch (module has JUnit only,
  no Robolectric; the value it branches on is tested both ways; on-phone checklist item).
- Round 6 BLOCKER-class (filed as WARNING): KosmosLauncherActivity is exported and passed any
  non-sign-in host straight to the TWA, so an installed app could open a foreign Mac address full
  screen with no nonce, going around OpenAddressActivity entirely. Any other host is now replaced
  by the sign-in page (with a fresh nonce). Nothing in this app launches it with another host;
  push taps go through the coordinator's sw.js in Chrome.
  Weakest part: not verified on a device that Chrome's delegated notification taps never re-enter
  through the launcher with a Mac URL; if they do, those taps now open the sign-in page instead.
- Round 6: a refused open launched a bare sign-in page without a nonce, so that page's later opens
  lost full screen. A refusal now restarts through KosmosLauncherActivity, which mints one.

## Challenge-loop round 4 changes

- BLOCKER: rounds 1 to 3 withheld `setAdditionalTrustedOrigins` without the nonce and called that
  "opens with the URL bar". False: Chrome verifies a TWA's LAUNCH origin against that origin's
  own assetlinks.json, and since #161 every Mac's vouches for this app, so a foreign Mac address
  launched as a TWA verifies and goes full screen regardless of the extra list. Now a choice
  without the nonce opens in a plain Custom Tab (URL bar kept, hiding disabled) and never a TWA.
  `AddressChoice.fullScreen` carries the decision and the JVM tests pin it both ways.
  Weakest part: the activity's branch on `fullScreen` has no automated test (no instrumentation
  tests in this module); it is an on-phone checklist item with an adb command.
- The wrong claim was deleted from AddressChoice, OpenAddressActivity and the manifest rather
  than rewritten.
- CI's report guard also requires `skipped="0"`, so an all-ignored suite cannot pass.
- Rotation during the open added to the on-phone checklist (inherited from LauncherActivity).
- Deferred: the sign-in page's refused-handoff latch lasting for the page's life. After the
  fallback tap the page navigates away, and clearing the latch on a guess would re-arm a tap that
  then does nothing for another 2.5 s.

## Challenge-loop round 3 changes

- A handoff Chrome silently refuses no longer leaves a dead button: after 2.5 s still on screen,
  the page says so and the next tap opens the address the web way (kosmos-relay signin.html,
  with a test for each arm).
- `OpenAddressActivity` keeps itself alive until the person comes back, as `LauncherActivity`
  does (read from the 2.5.0 bytecode: it sets a flag in the launch callback and finishes in
  `onRestart`), instead of finishing and unbinding the moment the launch completes.
- Back behaviour and board stacking are added to the on-phone checklist, not changed blind.
