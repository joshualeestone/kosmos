# undofsync13-5434: Undo flushes what it writes before anything relies on it (#5434 slice 13)

Addresses #5434. The last of group 1 in the rename inventory (the person's own files): `engine/undo.js`.
- **Restore** (`apply`, :481): copies the kept version to `.kosmos-undo-<rand>` beside the person's file and renames it
  over their file. Unflushed: a crash could leave THEIR file at full length but zero-filled (#5431).
- **Saved-aside copy** (`apply`): the current version, copied into Kosmos's folder before their file is replaced.
- **Kept copy / blob** (`keepOpen`, :286): content-addressed, written to `<hash>.tmp` and renamed, unflushed; and a
  blob that already exists is trusted on EXISTENCE alone, so a zero-filled one is never rewritten. Restore checks the
  hash first (it never restores zeros), so the effect was that the person's kept version was lost for good.
- **moveAside** EXDEV path: copies, then deletes the original, with the copy unflushed.

## Change
- `flushPath(p)`: open `r+` (or `r` when the mode forbids writing: POSIX fsync works on a read-only fd), then
  `securewrite.flushOrThrow`, close without masking an earlier error.
- Restore: `flushPath(tmp)` BEFORE the mode chmod (the temp is still writable then), rename, `syncDir(folder)`.
  A failed flush hits the existing catch: the temp is removed, the file is skipped as `failed`, their file unchanged.
- Saved-aside copy: `flushPath(keepAs)` after its hash check, then `syncDir(savedIn)` and `syncDir(savedRoot)`, before
  their file is replaced (review 1: flushed bytes in an unflushed new folder can survive a crash with no name).
- Blob: trusted only if it hashes to its name; otherwise written to its OWN temp `<hash>.<pid>.<rand>.tmp` (`wx`,
  0600; review 1: two keeps no longer share `<hash>.tmp`), flushed, renamed, `syncDir(blobs)`; the temp is removed on
  failure, and a dead one still ends in `.tmp` for the sweep.
- moveAside EXDEV: `flushPath(to)`, `syncDir` of its folder and of that folder's parent, before `unlinkSync(from)`; a flush failure removes the copy and throws,
  leaving the original.
- `securewrite` exports `flushOrThrow` and `syncDir` (the identical one-line change as slices 8 and 12).
- New `engine/undo.fsync-5434.test.js` (7 tests), in `tools/windows-tests.js`.

## Decided
- **Flushes inside the existing flow, not a move to writeSecret.** Undo's restore is guarded over many review rounds
  (folderStillSafe before and after, tmpReal, the credential verdict, never writing through a link); the flushes are
  added in place and nothing is reordered except the tmp flush placed before the chmod.
- **The blob heal costs a read and hash of an existing blob on each keep** of content already kept (bounded by
  MAX_BYTES). It is what makes a damaged kept copy recoverable instead of permanent.
- **Not in this slice:** the index rewrite in `sweep` and the switch file (Kosmos's own records, inventory group 2/3).
- **On Windows**, a read-only temp cannot be flushed (FlushFileBuffers needs write access; flushOrThrow skips EPERM
  there): only the saved-aside copy of a read-only file is affected, and only on Windows.

## Tests
- restore: temp flushed before the rename into the person's file, folder after (POSIX); saved-aside copy flushed
  before the file is replaced; a read-only (0444) file is still restored at 0444, through the read-only open (asserted
  it happened); a failed flush leaves their file as it was, no temp, skipped `failed`.
- keep: the blob is flushed before its rename; a zero-filled blob is rewritten and the undo then restores the file.
- moveAside EXDEV: the copy is flushed before the original is deleted (one ordered event list, review 1).
- the saved-aside folder and the saved root are flushed before the file is replaced (POSIX; mutation-checked).
- Mutation: main's undo.js fails 6 of 7 (the read-only arm passes there; it guards this slice's fallback, and
  removing the fallback fails it). Related set (65 files, list5434s13.txt): 2041, 0 fail, 3 skipped.

## Weakest premise
That re-hashing an existing blob on keep is cheap enough at the edit hook's frequency. What would change my mind: a
measured slowdown of the PreToolUse hook on large files; then compare size first and hash only when sizes match.
