# fsyncwrite7-5434: forgetCodexFolder's config.toml rewrite flushes before it renames (#5434 slice 7)

Addresses #5434. `engine/create.js` `forgetCodexFolder` takes Kosmos's trust entry back out of the person's
`~/.codex/config.toml` when an agent is removed. It wrote a fixed `<cfg>.tmp-<pid>` with `writeFileSync`, chmodded
it and renamed it: no flush, so a crash could leave the config at full length but zero-filled (#5431), and the
fixed name followed a link planted there. Found while correcting an overclaim on #5434 after slice 6.

## Change
- `engine/create.js`: the write is `securewrite.writeSecret(cfg, next, mode, { atomicOnly: true, ownTempsOnly: true })`,
  with the same mode as before (`stat & 0o777`, 0600 if it cannot be read) and the same refusal sentence
  ("we could not update the codex config"). `securewrite` is required at call time, beside the existing local
  `require('./trust')` in this function.
- New `engine/create.codexfsync-5434.test.js` (7 tests), in `tools/windows-tests.js` mid-list.
- `engine/create.test.js`: the #1797 create-mode test neutralizes `fs.fchmodSync` too, since securewrite sets the
  mode on the fd; without it the test would pass with a loose create.

## Decided
- **The old reason for keeping this off securewrite no longer applies** (#1797: securewrite's "nothing legitimately
  symlinks this" premise is false for the person's config.toml). That premise lives in `refuseSymlinkTarget`,
  which runs only in the in-place fallback, and `atomicOnly` never takes the fallback. A config.toml that is a link
  is replaced by a regular file by the rename, exactly as the old writeFileSync plus rename did. The comment says so.
- **Kept:** the temp is born at the mode (#1797), then the mode is set on the fd (best effort now; it was a chmod).
- **Gained:** a unique temp created `wx`, so a planted link is refused rather than written through. A file planted
  at the temp name now moves the save to a fresh name, where before the old name was simply written through.
  Only a temp this save created is ever unlinked.
- **The one new delete path** in the person's codex folder (beside `auth.json`): `ownTempsOnly` reaps a file with
  securewrite's exact temp shape for config.toml whose writer's pid is dead. This is the same trade as slices 3 and 6.
  The old `.tmp-<pid>` leftovers are not reaped.
- **Not in this slice:** `trustCodexFolder` (create.js:2575) adds the entry; its write path is a separate change.
- **Cost:** one flush of the file and one of the folder (about 8 ms) per agent removal that takes an entry back.

## Tests
- flush before the rename into config.toml;
- mode kept under umask 077 (POSIX);
- all three atomic attempts refused: the save is refused, with its sentence, and the file is unchanged;
- a link planted at the temp name: not written through, not removed, config.toml not made a link, entry taken back
  (POSIX; Windows symlinks need privileges);
- reap: config.toml's dead temp is reaped and auth.json's survives (both planted before the write).
- a flush that fails (EIO on the temp's fd): the forget is refused with its sentence, config.toml is unchanged, and no
  temp is left (review 2);
- a temp whose writer is alive (this pid, another thread) is never reaped (review 2).
- Mutation checks on a scratch copy: the old writer fails 4 tests; dropping `ownTempsOnly` fails the reap test;
  dropping `atomicOnly` fails the failure test; swallowing the flush error fails the flush-failure test; treating
  every temp as dead fails the live-writer test; and a temp created without its mode fails create.test.js's #1797
  test, which now neutralizes fchmodSync as well as chmodSync (review 1).

## Weakest premise
That nothing depended on a planted file at `<cfg>.tmp-<pid>` failing the save. The old code wrote through it rather
than failing, so the new behaviour is strictly safer. What would change my mind: a reader of the old temp name.
