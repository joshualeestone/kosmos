# hpke-5535: E0.6 (#5535) slice 1, HPKE base mode for the backup's per-object encryption

## Why
E0.6's design (v2 and v2.1 on #5535, two blind review rounds) encrypts each backup object TO a member's public key with a fresh ephemeral key, so a Mac that wrote a backup cannot read it back. fedseal's static-static pairing does not give that. HPKE base mode (RFC 9180) does, and it is a standard construction rather than a hand-rolled one. Slice 1 has no dependency on E0.1 / E0.2, so it lands first, on its own, with its own review, as the design says.

## Change
- **`engine/hpke.js`**: one suite only, DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 (0x0020 / 0x0001 / 0x0003), mode_base.
  - LabeledExtract and LabeledExpand, DeriveKeyPair, Encap and Decap with ExtractAndExpand, the key schedule (psk_id_hash, info_hash, secret, key, base_nonce, exporter secret), and the nonce as base_nonce XOR sequence.
  - The all-zero X25519 output is refused (RFC 9180 7.1.4) with a constant-time compare (the DH output is secret). On Node 26, OpenSSL refuses every canonical low-order point first (reviewer measured u = 0, 1, both order-8 points, p-1, p, p+1), so hpke.js's check is a backstop that no test can trigger today.
  - Exports: `hpkeSeal(pkR, info, aad, pt) -> { enc, ct }` (single-shot, sequence 0), `hpkeOpen(skR, enc, info, aad, ct) -> pt | null` (never throws), `hpkeKeyPair()` (raw 32-byte halves), and `hpkeVectorSeamsForTests()`, which refuses outside a test process (a fixed ikmE or a caller-chosen nonce would be nonce reuse in production).
  - Node's crypto supplies X25519, HMAC-SHA256 and ChaCha20-Poly1305. Raw X25519 private keys are imported through the PKCS#8 DER prefix, since Node takes X25519 keys only as DER or JWK.
- **`engine/hpke.test.js`**: RFC 9180 **A.2.1**, copied byte for byte from rfc-editor.org's text:
  - derived sender and recipient keys;
  - enc and the shared secret from both Encap (with ikmE) and Decap;
  - every key-schedule intermediate;
  - all six published encryptions (sequences 0, 1, 2, 4, 255, 256: the 255 and 256 cases exercise the nonce XOR across a byte);
  - a fresh-key round trip with distinct ephemeral keys per seal;
  - eleven wrong-input cases for open, each null and never throwing, against a working control. They include another member's key (restoring member B cannot read member A) and a wrong chunk name as aad (the v2 chunk-binding property);
  - seal refusing a short key and a low-order key.
- **`engine.reachable.test.js`**: `hpkeSeal`, `hpkeOpen` and `hpkeVectorSeamsForTests` are excused BY NAME, with their named caller slices (uploader, restore) as precedent `launchStreaming` does.

## Caught while building (two silent false passes in an existing guard)
1. engine.reachable.test.js reads an exports block only when `};` closes it on its own line. My first one-line block meant **none** of the module's exports were checked, and the test passed. The exports block is now multi-line.
2. The same test counts any extra in-module mention of a name as an internal caller. My header comment and error text named both exports, so they read as called, and it passed again. Both mentions were reworded, and **only then** did the test go red on the three exports it flags (`hpkeKeyPair` is genuinely called inside the module, by encap). That is the red the excuses answer.
   - The first export names (`seal`, `open`, `generateKeyPair`) also collided with fedseal's. They are now distinctive.

## Not in scope
The chunk and manifest format, signatures, the uploader, and restore (slices 2 to 5). No caller yet: inert until slice 3.

## Weakest premise
That a byte-exact match on ONE published suite's vectors, plus the open-failure cases, is enough review for a cryptographic composition. It pins correctness for honest inputs. It cannot show constant-time behaviour, which here rests entirely on Node and OpenSSL's primitives (nothing in hpke.js branches on secret data; the all-zero check on the secret DH output uses crypto.timingSafeEqual. The first draft used Buffer.equals and the plan called that output public; review round 1 corrected both). A second reviewer focused on crypto is still owed before slice 3 uses it.

## Review round 2 (sonnet) changes
- **A non-canonical public key** (bit 255 set, or u >= 2^255 - 19) is refused at seal time. X25519 ignores the bit, but RFC 9180 puts the raw pkR bytes into kem_context while the recipient rebuilds them canonically, so such a key sealed a message nobody could ever open: a backup that writes and cannot be restored. The reviewer measured it. Tests cover bit 255, u = p, u = p + 1, a canonical control, and 64 generated keys.
- The test fetches the vector seams inside each test, so a run outside the test runner fails with the guard's own words, not at load. The excuse now says the guard is an execArgv heuristic.
- I2OSP refuses an out-of-range value, and an empty plaintext round-trips to an empty Buffer (a test).
