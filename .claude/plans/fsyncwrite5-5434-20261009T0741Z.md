# fsyncwrite5-5434: the files Kosmos keeps in a provider's account folder flush before they rename (#5434 slice 5)

Addresses #5434 (slice 5). Slices 1 to 4 (merged) moved the stores and settings writers onto
securewrite.writeSecret. This slice moves the last two writers in the account folder.

## Change
- `engine/kosmos-statusline.js` `record`: the weekly reading (`kosmos-weekly.json`) is written through writeSecret
  (`atomicOnly`, `ownTempsOnly`, `umaskDefault`; an existing file's mode kept, not on Windows). securewrite is required
  only when a reading moves forward (the statusline runs on every repaint and must stay cheap). If it cannot be loaded,
  the old unflushed write still records the reading: the statusline must never show an error in the person's pane.
- `engine/allowance.js` `calibrate`: the calibration (`kosmos-weekly-calibration.json`) the same way. A failed save
  is not an error (the estimate is returned either way, as before).
- Bytes stored are unchanged (`JSON.stringify(next) + '\n'`).

## Decided
- ownTempsOnly: the account folder is the provider's, so only each file's own dead temps are reaped.
- Old `<file>.<pid>.new` leftovers from the earlier writer are not swept (harmless: never read).
- Cost: a flush of the file and the folder per write (~8 ms on an SSD, measured on slice 4). The statusline writes
  only on the repaint where the weekly figure moves forward, and THAT repaint now pays the flush before the process
  exits; unchanged repaints load nothing. The calibration is saved on the board's 60 s sweep (calibrateSwarmAllowances)
  whenever today's tokens grew, so about once a minute per active account, as main already wrote it (unflushed):
  ~8 to 20 ms per account per minute on the board's event loop. Accepted, as slices 1 to 4 accepted the flush.
- Only the permission bits (0o777) are carried, as store.js does: setuid/setgid/sticky bits have no meaning on these
  JSON files (reporthook.readSettings keeps 0o7777; a difference left for the slice that aligns the settings writers).

## Tests
`engine/allowance.fsync-5434.test.js`: for each writer, the temp renamed into place was flushed first; an existing file
keeps its mode and a new one takes the umask default (022 and 077); a save whose every atomic attempt fails leaves the
file; only the file's own dead temps are reaped (a provider file's temp is not); the statusline copied alone still
records a reading; the stored JSON is unchanged. Mutation checks: see the single list under "Measured (review 6)".

## Measured (review 4)
- A symlinked kosmos-weekly.json is replaced by a regular file holding the new reading (record returned true), as the
  old temp-and-rename did: writeSecret's atomic path renames over the link; only its in-place fallback refuses one,
  and atomicOnly never takes that fallback.
- An OLDER securewrite that loads (mid-update) and lacks umaskDefault throws on a new file; record returns false until
  the swap completes. Not falling back to the unflushed write on a throw is deliberate: a real flush failure must
  not be turned into an unflushed save.

## Measured (review 6)
- record() in a fresh process, this Mac (SSD), three runs each: branch 9 to 10 ms for the load plus first forward
  write (one cold outlier 34 ms) and 7 to 8 ms for a second; main 0.6 to 1.3 ms and 0.2 ms. The cost lands only on
  the repaint that moves the weekly figure forward (about once per percentage point), in the statusline's own short
  process, never on the board. Unmeasured on a slow disk.
- Mutation checks run for this slice (each on a copy, restored after): the statusline's securewrite forced off (4 arms
  fail), calibrate's old unflushed write (4 fail), ownTempsOnly dropped from either writer (that writer's reap arm
  fails on "another file's temp was swept"), record allowed to throw (the failed-save arm fails), calibrate's inner
  catch removed (the failed-save arm fails).

## Weakest premise
That the statusline's fallback (unflushed) is acceptable when securewrite cannot be loaded. It exists only for a
copy outside the app folder or a half-swapped engine folder during an update; the reading is re-recorded on the next
forward move. Likewise, when a save through securewrite fails (ENOSPC, a planted name), record returns false and
that reading is lost until the next forward move, silently, as the old writer was: a statusline must never print.
