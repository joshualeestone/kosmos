# Plan: the cut refuses a live install harness at its own start (kosmos#1713)

## Problem

`tools/test-install.sh` (the install harness) binds a fixed port and has a guard
(`kosmos_refuse_if_cut_live`) that checks AT START, so it protects the cut from a
harness that begins during it. It does nothing about a harness that was ALREADY
running when the cut begins -- and that case is not rarer:

```
harness starts, cut already running   -> GUARD FIRES        (protected)
cut starts, harness already running    -> GUARD NEVER RUNS   (unprotected)
```

Evidence (Ice Cream Kitty, reported unprompted): a harness run overlapped the
start of the 16:40 cut by ~32s. Nothing broke that time. The two share the
install gate's fixed port; two things wanting it is not a slow test, it is a
failed release step attributed to whatever the cut was doing then.

## Approach (the card's cheaper option: check where the decision is made)

Add the symmetric guard and wire it into the cut, not the harness:

1. `kosmos_refuse_if_harness_live` in `tools/lib/cut-guard.sh`, mirroring the two
   existing guards EXACTLY: the robust filter (only a real `bash tools/test-install.sh`
   counts, so a peer shell that merely MENTIONS the script -- a grep, a git log,
   the pkill that cleared the box during the 0.6.20 window -- does not match),
   self-subtree exclusion (#1391), a `KOSMOS_HARNESS_PROBE` seam so it can be shown
   red and green, and the posture "a probe that cannot answer is a refusal".
2. Wire it into `tools/release.sh` at the cut's start, beside the existing
   second-cut check. `KOSMOS_CUT_IGNORE_HARNESS=1` cuts anyway.
3. Extend `tools/test-cut-guard.sh` (already in `test:shell`).

## Weakest premise (checked)

PigeonPete's caveat on the sibling card #1669 was "does a legitimate non-export
deploy exist?" -- the analog here is "does a legitimate cut-during-harness exist?"
No: the harness holds the port for its whole run, and the harness's own start
check already blocks a NEW harness during a cut, so the only unprotected case is a
harness ALREADY running at cut start -- which a start check catches with no TOCTOU.
Over-refusing is the safe direction and matches the existing guards' posture. The
`KOSMOS_CUT_IGNORE_HARNESS=1` escape hatch covers a deliberate override.

## The guard must be able to return the dangerous answer

Proven end-to-end through the real pgrep: a real `bash tools/test-install.sh` IS
detected and refuses the cut; a mere mention is NOT. The end-to-end calls the
guard from a SEPARATE process so the spawned harness is a SIBLING, not a
descendant -- otherwise the self-subtree exclusion drops it and the arm passes for
the wrong reason (measured: the direct form silently dropped the real harness).
