# Plan: #2187 - group the Claude connect output on first-run step 3 into a light-gold box

Backfilled during the create-PR flow (this was a night-shift direct build, not a `/pplan`
session, so the plan file the `pre-challenge-gate` hook requires was missing). The design below
is exactly what shipped; it is a record, not a forward plan.

## The ask (Josh, 2026-09-04, 0.6.30 fresh-install test, screenshot 9.46.08 PM)

Put the "Claude Max 20 connected" checkbox AND all the preceding setup text (the setup/installing
notifications that lead up to it) inside a gold box with a light-gold background - the styled box
that fits right underneath the Claude row. Pure UI grouping/styling on the connection/setup screen.

## Where the work lives

The connection screen is the first-run wizard's step 3 (`#fr-pane-3` in `web/index.html`). Every
piece of connect-flow output is written into ONE element, `#fr-sub`, at different moments:

- during install: the notifications ("Downloading Claude...", "Setting Claude up on this
  computer...", the progress bar) - painted by `frPaintConnect`.
- after connect: the "... is connected" green checkrow - painted by `frPaintSubscription`.

They occupy the same spot, never both at once. The wizard's action buttons (Continue / Check again /
Cancel) render into the sticky footer via `frActions`, NOT into `#fr-sub`.

## The decision

Style that ONE element (`#fr-sub`) as the box. That groups both the setup text and the connected
checkbox exactly as asked, with no wrapper div and no JS change.

- `#firstrun #fr-sub:not(:empty)` carries the gold-wash box; `#firstrun #fr-sub:empty { display:none }`
  removes it, so there is no bare gold rectangle under Claude before Connect is pressed (`#fr-sub`
  is set to `''` before connect and on every not-connected repaint).
- Reuse the SAME gold wash `.fr-confirm` already uses (`rgba(184,137,32,.08)` fill /
  `rgba(184,137,32,.28)` border) rather than a new tone. `.fr-confirm` is the sibling box in this
  same connect sequence (the install-confirm panel), and the file's own comment says a second tone
  would say "different kind of thing" about the same kind of thing. So confirm → flow → connected
  reads as one contained treatment.

### What I rejected

- **A wrapper `<div>` around `#fr-sub` + `#fr-sub-msg`.** Unnecessary: all the grouped content is
  already inside `#fr-sub`; `#fr-sub-msg` is the separate error line and stays outside the box.
- **A new light-gold token.** The pack's `#firstrun` subtree is deliberately single-look
  forced-light and avoids scheme-aware tokens; matching `.fr-confirm`'s literal is the in-house
  pattern.
- **Phase-aware CSS to un-box the error/`stuck` state.** Considered because the gold wash is the
  attention treatment; rejected because it would couple the CSS to JS phase names for marginal gain,
  and the error rows keep their own red glyph for severity. Documented as a deferred NIT.

### Weakest premise

That grouping every connect phase (including `stuck`/error) in the confirm-style box reads well.
Mitigated: the gold wash IS the pack's attention treatment and the error rows carry their own red
mark, so it is coherent; left as a documented, deferred NIT rather than adding phase-coupling.

## Guard

`docs/browser-checks/render-firstrun-connect-box-2187.js` - hermetic (loads `web/index.html` over
file://, boots no server), wired into the `tools/browser-checks.sh` release-gate loop, indexed in the
browser-checks README. Drives the page's own `frPaintSubscription()` / `frPaintConnect()` into
`#fr-sub` and reads computed style; asserts the checkrow's real size before any style arm; the empty
control (empty `#fr-sub` → `display:none`) reds if the `:empty` guard is dropped. Verified 10/10
(chromium + webkit), proven RED (8/10 box arms) against the pre-fix page.
