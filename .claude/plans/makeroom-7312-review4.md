## Findings

- [WARNING] docs/browser-checks/render-chatbox-phone-4108.js:312-317 and 353-358. The only arm that can catch a deleted or broken make-room step depends on a 6px coincidence, and losing it is silent. Measured above: a one-line copy edit to the Conversation step (`'Talk to all of them here.'`) removes the squeeze, and with the make-room code ALSO deleted the gate is green; the only trace is a MEASURE line in a CI log nobody reads. The comment is honest that this is the design, but the coverage it buys is fragile in exactly the direction Josh edits most (shorter copy), and once lost it never comes back without someone reading logs. Fix: make the squeeze independent of the copy by growing the CARD, not the room (card growth was measured harmless: it only deepens the shortfall and scrollY 677 covers it). For example, in the forced arms only, inject a style before the walk that gives the Conversation step's body a floor, e.g. `#tipcard:has(#tipcard-title) .tip-bd { min-height: <measured body height + 40px> }` scoped to that step (set it from walkTip when `TIP_PLACES[TIP_STEP].title === 'Conversation'`, or add a class there), so the shortfall is about 46px whatever the copy says. Then the control can assert "flat without the scroll" as a hard setup check, and the MEASURE fallback is needed only if the card shrinks by more than the floor. If you keep the current design, at least count re-tune runs into a distinct exit summary line (`STALE n`) printed after `ALL PASS`, so it is visible in the job summary rather than buried.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:30-31. The file header states unconditionally that the control "leaves the card flat", and line 315 that "deleting the make-room code fails exactly here". Both hold only while the 6px squeeze exists; with it gone (measured above) the control passes green and deletion is not caught. Fix: say "while the squeeze holds (6px, measured 10-27); otherwise the control prints a re-tune MEASURE and make-room is untested that run".

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:355. The control's failure text attributes a missing scroll to "the make-room step is broken or gone", but the step also declines by design when its own preconditions fail (place not on screen, `r.bottom <= need`, or the window cannot scroll the whole shortfall). Today the headroom is large (scrollY 677 vs 6px) so this is unlikely, but the message would then send the reader to the wrong cause. Fix: include `scrollY`, the target's `r.top`/`r.bottom` and the card's `offsetHeight` in the detail, so a declined-by-precondition run is distinguishable from a deleted step.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:358. "the forced layout no longer squeezes the Conversation card" is also what prints if make-room is refactored to move the page without `window.scrollBy` (scrollTo, scrollIntoView, an element's scrollTop): the card then points in the control because the unintercepted scroll really happened. The line would tell the reader the layout changed when the code did. Fix: in the control, also record `window.scrollY` before and after the Conversation step and say "the page moved without scrollBy" when it changed.
