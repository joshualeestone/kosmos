# win32-prune-rows-2720: the ownership record stops growing with every restart (#2720)

Addresses #2720 and #570.

## The defect

`AppData\Roaming\Kosmos\win32-sessions\record.json` maps session id to
`{ name, runner, at }`. Every FRESH start records a new row for the agent. That
covers a task start, a reboot, and a crash before the first message (#2726). But
nothing removes the row of the session that ended. Measured on the box:
winstream-1 has about 20 rows, 19 of them for sessions long gone. The count grows
by one per fresh start.

- **Harmless to the board today.** `win32live` joins only ids that are live in
  `claude agents --json`, so a dead row never becomes a card.
- **But it grows without bound.** Every `record`/`forget` rewrites the whole file
  under a lock (#2728). The file, and the time that lock is held, grow for the
  life of the install.
- **A stale row is not inert.** A `claude --resume <old id>` would join the live
  list under the agent's name. That is the duplicate-name case `win32live`'s
  header warns about.

## Design

- **`win32sessions.pruneName(name, keepIds)`**: one locked `rewrite()` that drops
  every row whose `name` is `name` and whose id is not in `keepIds`. Rows under
  other names are never touched. It returns `{ ok, removed }` or
  `{ ok:false, because }`.
- **`superviseStreaming`: after a successful FRESH start** (not a resume), it
  prunes the agent's other rows and keeps only the id just started.
  - **Why nothing else needs keeping:** a fresh start happens only once
    `blockedBy` has read a live list that shows no session recorded under this
    name running. An unreadable list, or one showing any such session, makes it
    WAIT instead. So at that moment no other session of this agent is LISTED as
    running.
  - "Not listed" is not the same as "ended": a new session takes up to about 5s
    to appear in the list. See the Weakest part for why that is still safe.
  - An earlier draft also kept every live id, and pruned nothing on an unreadable
    list. Neither case can reach this point, so that would have been dead logic.
- **Said, never fatal.** A prune that fails or throws is reported on the task log
  (`prune-failed`), and the start stands. A prune that removed rows says how many
  (`pruned`).
- **Where not.** A resume keeps its own id and has no row to add, so nothing
  grows. The rekey (#2728) and the fresh start after `resume-impossible` (#2731)
  already forget their old ids.

## Tests

- `win32roster.test.js`, on the real sandboxed record:
  - `pruneName` drops only that name's rows outside `keepIds`;
  - other names' rows survive;
  - a name with nothing to drop writes nothing (the no-op pinned by file index);
  - the lock refuses when held.
- `win32supervisor.test.js`:
  - a fresh start forgets the agent's ended rows, keeps the new id, and never
    touches another agent's row;
  - a resume prunes nothing;
  - a prune that fails or throws is reported, and the start still stands.
- Live on the box: cycle winstream-1's task (a fresh start). Its rows go from
  about 20 to 1, and the card stays idle.

## Verified live on the box (2026-09-11 ~01:55 UTC)

- Before, on main: winstream-1 had **26** rows in the ownership record.
- The shared engine pointer was moved to this branch, and winstream-1's task was
  cycled, which is a fresh start. Afterwards it had **1** row: `817e86a1`, the
  session just started. The card stayed idle.
- The pointer was moved back to main and the task cycled again. That left 2
  rows: main does not prune yet, so this is expected. All 5 cards were idle.

## Weakest part

- **A session live but not yet listed.** Only the id just started is kept
  explicitly. Any OTHER session of this agent that is running but not yet in the
  live list would lose its row. A new session takes up to about 5s to appear in
  that list, as measured in `win32launch.js`, `win32stop.js` and `create.js`, and
  a spawn stuck on a trust dialog never appears at all. So a restart within about
  5s of the old child's start could prune that child's row. It is safe today
  because this agent has exactly one supervisor: the task is `IgnoreNew`, and the
  detached `launch()` path is not selected in production. A previous
  supervisor's child is also stopped by host-gone (#2714), so the row belongs to a
  process on its way out. A second launcher for the same agent would break this
  assumption (review round 1).
- **One test for "this row is the agent's"** (`win32sessions.rowIsUnder`). The
  prune, the supervisor's live-session check and create's wait for its new row
  all call it, so they cannot drift apart (review round 1).
