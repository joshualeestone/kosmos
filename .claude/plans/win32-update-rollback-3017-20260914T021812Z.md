# win32-update-rollback-3017 -- S5: a user-initiated "Roll back" button

Branch: `win32-update-rollback-3017`, off `origin/main` @ `43035808` (S4 armed the
updater). Design: `kosmos-scripts/win32-updater-design.md` (§0.4, §3 H8/H9, §5, the

## The ask (issue #3017)
S4's armed success path keeps one `previous-<from>` folder under
`<ROOT>/.kosmos-update/` (win32apply H9), "exactly so a rollback button can restore
it." S5 adds a Settings/Updates "Roll back" button that restores that kept build:
stop board, swap the current bundle entries aside, restore the previous entries,
re-anchor, restart, confirm the OLD identity -- reusing the win32apply swap/rollback
machinery. Josh: surface it so people know rollback exists.

## The reuse insight (why this is small and safe)
A user rollback IS structurally a forward update whose "staged build" is the kept
previous build. The whole H1-H9 helper already does: stop -> move ROOT entries to
`previous-<from>` (H3) -> move `staged` entries into ROOT (H4) -> swap interpreter
(H5) -> pointer (H6) -> start+confirm (H7) -> on failure reverse everything (H8) ->
keep one previous on success (H9). So S5 drives the EXISTING helper by:
  1. renaming the kept `previous-<oldV>` folder to `<WORK>/staged` (one atomic
     same-volume rename), so it fits the journal's derived `staged` path;
  2. writing a journal with `from`=current, `to`=old, and a new `rollback: true`
     marker; identities recomputed from the trees; `runtimeChanged` = old node.exe
     differs from the anchored one;
  3. spawning the SAME helper (`win32update.js --kosmos-update-apply <journal>`).
The helper then swaps the old build in and confirms the OLD identity; if that fails,
H8 puts the CURRENT build back and confirms current -- the H8 safety comes for free.
Crash-recovery/resumers/logon-shim all work unchanged (reversal is symmetric and
ignores the flag; only `applyRefusal` -- run by the fresh helper -- is rollback-aware).

The ONLY never-downgrade gate that would block this is `applyRefusal`'s
`newer(to, installed)`; skipped for a rollback journal (the whole point is to go
back), replaced by `newer(from, to)` (only roll back to a strictly-older kept build).

## Build

### engine/win32apply.js (rollback-aware core; minimal surgical change)
- `journalProblem`: accept an optional boolean `j.rollback` (reject a non-boolean).
- factor `stagedJournal` -> `buildJournal(spec)` taking explicit `spec.to`,
  `spec.runtimeChanged`, `spec.rollback`; `writeStagedJournal` maps `prepared`->`to`
  (forward, unchanged behaviour); new `writeRollbackJournal(journalAt, spec)` for S5.
- `applyRefusal`: rollback branch skips `newer(to, installed)`, requires
  `newer(from, to)` (and the folder-shape/entry checks are unchanged).
- `statusFor`: rollback-aware sentences (success "rolled back to X"; failure "the
  roll back did not take. Kosmos is still on <current>"). Stuck/abandoned unchanged
  (they already name `from`, which for a rollback is the current build -- correct).
- export `writeRollbackJournal`.

### engine/win32update.js (new board-side entrypoint)
- `keptPreviousBuild(root, opts)`: scan WORK for `previous-*`, pick the newest that
  is a whole app older than current; returns `{ dir, version }` or null. Light (no
  node spawn) -- for the status offer.
- `rollbackToPrevious(opts)` (analogue of `begin()`): B0 preconditions (reuse
  `preconditionRefusal` incl. unusual-location + journal + bundle + pointer), live
  gate, `boardTaskRefusal`; validate the kept previous build (whole app, older,
  required entries, its node.exe runs via `runStagedNode`); take the update lock;
  under lock re-check journal precondition + clear stray staged/download; rename
  `previous-<oldV>` -> `staged`; recompute from/to identities + runtimeChanged; write
  the rollback journal; release lock; spawn the helper. On any failure AFTER the
  rename, rename `staged` back to `previous-<oldV>` so the kept build is never lost.
  No-kept-previous -> clean refusal sentence.
- export `rollbackToPrevious`, `keptPreviousBuild`.

### engine/update.js (wiring, mirrors the S4 install arm)
- `rollbackOffer()`: win32 + installedRoot + not location-refused; `{ version }` of
  the kept previous build (via `keptPreviousBuild`) or null.
- `beginRollback(opts)`: reuse the `installStarted` single-flight + fresh lastAttempt
  + `armWindowsHelperWitness`; call `win32update.rollbackToPrevious` via a
  `windowsRollbackFn` seam; on {ok:false} release + record.
- exports + `setWindowsRollback` seam.

### server.js
- `/api/status`: add `updateRollback: updates.rollbackOffer()`.
- `/api/update/check`: add `rollback: updates.rollbackOffer()` (repaint parity).
- new `POST /api/update/rollback`: 409 no offer / not installedRoot / location refusal;
  idempotent when already installing; else `beginRollback()`, 200 `{ok, rollingBackTo,
  startedAt}`.

### web/index.html (Mac byte-identical; win32-only surface)
- new `#upd-rollback` button in `#upd-row` (NO `data-win-copy` -- label set in paint,
  "Roll back to X"; the offer is win32-only so it never shows on Mac). Avoids the
  `data-win-copy` surface token, so the #2518 surface gate is not triggered.
- `paintUpdateCard(... , rollback)`: show/label the button from the offer; thread the
  new arg through every caller (status handler x2, check-now, initial).
- rollback opens the existing `#updconfirm` in a `rollback` mode (title + body via
  windowsCopy keys `updateRollbackConfirmBody`); `uc-go` reads the mode and POSTs
  `/api/update/rollback`, overlay lead "Rolling back to X." (no download step); settle
  wording rollback-aware.
- new windowsCopy keys: `updateRollbackConfirmBody`, `updateRollbackOverlay`,
  `updateRollbackDidNotTake`.
