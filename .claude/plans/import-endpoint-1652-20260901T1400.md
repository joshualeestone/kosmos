# import-endpoint-1652 - the parse endpoint the fourth create-an-agent option calls

Kosmos #1652 (the wiring, still open). The import ENGINE shipped (#1768,
`agentfile.importAgent`), and the export engine before it (#1653), but nothing
calls importAgent from a route, so the operator cannot use it (Splinter, correctly:
mechanism-built, not done). This adds the backend the fourth create-an-agent option
needs. The fourth-option UI itself is web/ and needs a Playwright session; this
endpoint is the no-browser half that de-risks it.

## What it is: `POST /api/agent-import`

A thin PARSE endpoint. Body `{file: <text>}` -> `agentfile.importAgent(file,
{identityFromText, nameUsable})` -> returns the validated material the create form
pre-fills, or a whole refusal:
- ok: `{ok: true, name, displayName, provider, instructions}` (the `body` from
  importAgent is returned as `instructions`, the field name the create form and
  `POST /api/agents` already use).
- refused: `{ok: false, because}` (importAgent's refuse-whole reason, shown inline).

## Why parse-and-return, NOT create here

Creation stays in the ONE canonical path: the fourth option hands the parsed
`name`/`instructions`/`provider` to `POST /api/agents` exactly as the other three
options do, so import inherits all of create's correctness (id mint, projects,
first-agent home, launchd, tmux) rather than a second creation path. The endpoint's
only job is to turn a file into the form's fields. This mirrors export shipping as
an engine function: import is now reachable as a route without duplicating create.

## Security

Creating an agent is loopback-only; a PARSE that feeds it is too. This route is NOT
added to `REMOTE_AGENT_ROUTES`, so `remoteWriteGuard` refuses a remote peer and
`crossSiteWrite` refuses another origin. And the #1764 reach test (just merged)
scans server.js's dispatch, so it will automatically assert `POST /api/agent-import`
is refused for a remote peer -- the guard I built covers the endpoint I am adding.

## Files

- `server.js`: require `./engine/agentfile`; add `identityFromText` to the status
  destructure; add the `POST /api/agent-import` route (near `/api/agent-token`).

## Tests (server integration, boot the real server on loopback)

- a valid exported file (produced by the REAL exportAgent) POSTed to
  `/api/agent-import` returns `{ok:true, name, displayName, provider, instructions}`
  with the instructions body intact -- the round trip export -> import over HTTP.
- a hostile / non-Kosmos file is refused whole `{ok:false, because}` (no header /
  wrong marker / path-unsafe name / body names nobody), each with a control that a
  valid file is accepted, so the refusal means something.
- malformed JSON is a 400.
- (loopback-only is covered by the #1764 reach test, which now sees this route.)
