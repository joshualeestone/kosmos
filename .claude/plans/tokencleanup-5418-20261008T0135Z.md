# tokencleanup-5418: #5418 ask 2, the one-time cleanup tool

Addresses #5418 (ask 2). Ask 1 (PR #5452, merged 1683b0f3e) made it impossible for a test process to reach the real
data root. This adds the tool for the records test runs had ALREADY left in a real sender-token store (on one fleet
Mac, measured 10-06: 22 entries, 17 matching no agent and dated 08-28 to 09-08, one dangling symlink, two stray temps).

## The tool: `tools/cleanup-fixture-tokens-5418.js`
- Dry run by default; `--apply` to change anything. `--port` and `--cutoff` are required, never assumed (the board
  port is per account; the cutoff is the date before which a stray record can only have come from a test run).
- **The roster is the first guard for a live agent** (the store's own records are the others; the cutoff is in the past for every live file). Each row of
  `GET /api/status` (`agents[]`) and of the removal records counts under every spelling a token file can carry:
  `sessionName` (tokens are minted under it, via the supervisor's `token_roster_name`: `+world` stripped, then
  `-discord`), those stripped forms, and the display `name`. A display name alone is WRONG: Splinter's card reads
  "Splinter" but its tokens live in `claudebot.json` (review 1 found this; the e2e arm pins it, with the fixture's worker folders taken away so only the roster can
  keep: review 27 found that a display-name-only roster passed while they were there, and it now fails).
- **What it keeps, always:** a token file under any such spelling, at any age; a file whose name is not one the store
  writes (`safeKey(key) !== key`: `revoke` would remove a DIFFERENT file); anything written on or after the cutoff (a dangling link excepted: it is removed at any age unless named for a live agent);
  anything that is not a token file, a temp or a link; a link whose target exists; a token file written after the
  plan was made (re-checked UNDER the store's lock by a new `sendertoken.revokeIfUnchanged`); a file holding any
  `launcher: 'remote'` token (review 2: a remote or paneless agent is on `/api/status` only while its heartbeat
  is fresh, so an OFFLINE one would look orphaned). Age is a file's newest sign of life: the later of its newest
  token `mintedAt` and its mtime.
- Also kept, beyond the roster: a key with a worker folder or (macOS only) a launchd job (`com.kosmos.agent.<name>` or a
  fleet `com.<name>.discord`), both folders from `create.js`'s own derivation (review 13: an agent with no profile can be running where the board cannot see it,
  and the board's offline rows can drop a row silently); either folder there but unreadable stops the tool. And a key with a heartbeat (liveness) record of ANY age (review 3: a remote agent
  reports that way, and one minted before #4530 carries no launcher tag); a key the store keeps ANY profile for (review 6:
  adopted and Windows agents' tokens carry no launcher; a profile is the store's own record of an agent; fixture
  profiles leaked too, so this keeps some leftovers, which is the safe direction). Unreadable removal records stop
  the tool.
- The real tie between the board on `--port` and this store is the board token (a board refuses a token that
  is not its own); the "roster matches none of the files" stop is a backstop for a board that does not enforce it,
  and it counts the ROSTER only (review 5: this store's own heartbeat and removal records would satisfy it on any
  real machine, whichever board answered).
- **What it may remove:** a token file matching neither list and written before the cutoff; a temp in the writer's
  own `.kosmos-<pid>-...tmp` shape written before the cutoff whose writer is provably gone (securewrite's own
  `tempWriterGone`, the #1793 proof-of-death rule, shared rather than copied); a link pointing at nothing, unless named for a live agent, and only when the folder it pointed into still exists
  (review 24: a missing or unreadable target folder may be an unmounted drive, so that link is kept).
- **Before sending the board token** it asks `/api/health` (no token) whether a Kosmos board answers on that port.
- **Keep signals fail closed (review 9):** a board reporting `counts.unreadableLines > 0` (a partial roster), a
  heartbeat folder that exists but cannot be read, a profiles folder that cannot be listed (the board's offline
  rows come from it, and it fails silently there), each stop the tool; a profile file that exists but cannot be
  read still keeps its key.
- **No roster, no removal:** an unreachable board, a non-OK answer, no agent list, an EMPTY agent list, no board
  token for this store, or a roster that matches NONE of the store's token files (a board serving another store)
  stops it before planning.
- **--apply removes exactly the plan a person read (review 7):** the dry run prints a digest of its removals (name,
  kind, key, mtime, newest mint, launchers, token names); `--apply --confirm <digest>` rebuilds the plan and stops if the digest differs (an agent missing
  from a degraded roster at apply time, a file changed). `--port` must equal this account's own board port, derived
  as `install/kosmos` derives it, so the token never reaches another account's board. `--apply` needs live
  execution, which only the command line turns on (repo convention: destructive actions fail closed).
- On Windows a dangling link that cannot be re-made in the backup is recorded in `LINKS.txt` there (name and
  target), rather than stopping every other removal. `applyPlan` itself refuses unless live execution is on.
- **Backup first:** `--apply` copies exactly the entries it will remove (with modes; links as links) to a new
  `sendertokens.backup-5418-<time>` folder beside it, refusing to overwrite, and stops if that fails.
- A `--cutoff` less than an hour in the past (or in the future) and an out-of-range `--port` are refused: temps
  are removed without the store's lock (old AND writer provably gone), so nothing in flight may be old enough (a dangling link is removed
  at any age: it holds no credential). The dry run prints, per token file it would
  remove, the names its tokens carry (#4792), its launchers and newest mint, for a person to read against the
  agents they know. A failed backup removes its own partial copy (or names it).
- Token files are removed through `sendertoken.revokeIfUnchanged` (under its lock); temps and links are re-checked
  (still a file, still a link) just before unlinking. Prints names and counts, never a token.

## Rejected
- Matching by profile files instead of the board's roster: the 10-06 inventory found fixture-looking names WITH
  profiles, so fixture profiles leaked too. The board's live roster is the only list that means "a real agent here".
- Sweeping the store's other folders in this tool: each has its own shape and owner logic; the token store is the
  one the card measured. Others are a follow-up if a dry run of them finds strays.
- Running it automatically (at install or start): it is one-time, for machines that ran tests before ask 1.

## Tests
`tools.cleanup-fixture-tokens-5418.test.js`, 59 arms (2 platform-only) (plus `engine/sendertoken.revokeifunchanged-5418.test.js`, 7), also run by the Windows job (ALSO_ROOT): the plan's keep/remove
split for every kind of entry (a live agent kept at any age: fails if the roster check is removed); unknown age
never removed; links seen without following; backup copies modes and links and never overwrites; apply re-checks
and goes through revoke; port and cutoff required; no roster or an empty one changes nothing (fails if the empty
guard is removed); end to end in the test process's own throwaway store (ask 1 guarantees it is not the real one;
the test asserts so), with a display name differing from the session name, a `-discord` twin and a non-canonical
file all kept; a roster matching no file, and a missing board token, each stop it. Each guard added in review was
mutation-checked on this Mac (removing it fails an arm), EXCEPT: the Linux and Windows main-level job arms (they run
only on those CI jobs), the apply-time re-check of a link's target folder, and the isFile-first
order in revokeIfUnchanged (each covered by reasoning; the plan-time rule they mirror is mutation-checked).

## Running it (after merge)
From a checkout at the same commit as the installed app (the tool is not shipped in the app; the same engine takes
the same lock), with the board running, on each fleet Mac that ran tests before ask 1 merged (2026-10-08 00:13 UTC): dry run with that account's own board port
and `--cutoff 2026-10-08T00:00:00Z` (usable from 01:00Z: the tool refuses a cutoff less than an hour old). Fixture tokens a stale worktree wrote after
the cutoff are kept, and will remain until a later run. A person reads EVERY
"remove" line against the agents they know (the dry run shows each token file's launchers and newest mint: an
adopted or Windows agent that is offline is the case the tool cannot see), then `--apply --confirm <digest>`. Check the result, then
delete the backup folder it names (it holds the removed tokens, and any planned token that changed and was kept). A
"remove" line for a dangling link: check the link does not point at a volume that is only unmounted. Report
counts on #5418.

## Decided (review 26)
- A token file that vanishes between `revokeIfUnchanged`'s lstat and its unlink (both under the lock) counts as
  removed, not as already gone: only the count is inexact, and the window is inside the lock.
- On Linux each unit file is stat'ed by the tool itself: an unreadable one keeps its key (presence() would read it
  as no unit).

## Decided (review 28)
- A temp and a link are re-checked at apply without the lock and without re-asking whether the temp's writer is
  gone; the plan (and its digest) was rebuilt seconds before. A writer pid reused in that window would still lose its
  temp; the proof-of-death only ever errs toward keeping, and the window is seconds.
- On macOS a startup job keeps a token only through the two launchd label shapes the tool reads
  (`com.kosmos.agent.<name>`, `com.<name>.discord`); any other plist is not a keep. The roster, worker folders and
  profiles are the backstops, and the dry run lists every removal.

## Decided (review 29)
- A token file swapped for a FIFO between listing and reading would block the read (the folder is 0700; not guarded).
- The Linux arm's unit sandbox sits beside the store, not in the workers folder (an arm that clears the workers folder
  took the units with it: review 29 found the Linux arm could never pass). Token entries are read with the store's
  own filter (a string `token`), the launchd prefix and world separator come from create.js and launchidentity, a
  link's target is in the digest, and the backup folder itself is flushed (POSIX).

## Decided (review 30)
- The proof that a temp's writer is gone (`kill(pid, 0)` answers ESRCH) holds only for a writer in this machine's
  process namespace; a writer in a container would read as gone. The cutoff margin (over an hour old) makes a live
  writer holding such a temp implausible.
- A board answer over 8 MB is refused (the health route answers before any token is sent, so anything on the port
  could reply).

## Decided (review 31)
- Linux checks the unit files for `<key>` and `<key>-discord` rather than listing the folder and mapping every unit
  back (as macOS does): the same unless a unit's name differs from its token key beyond `-discord`, which
  `create.NAME_RE` (lowercase names) rules out today.

## Weakest premises
1. That the board lists every agent whose token must survive. Pane agents (running or stopped) and created agents
   are listed; remote agents are kept by their launcher or heartbeat record, and any agent with a profile is kept,
   even offline. Left uncovered: an agent with none of these. One shape is known (review 23 closed the other: Windows
   Scheduled Tasks and Linux systemd units are now keeps, read through register.jobReader, a Linux unit for the key or its -discord session; an unreadable task
   list or unit folder stops the tool; the test file stubs schtasks as "no such task" and sandboxes the unit folder): a named-world agent's heartbeat (`sam+w` is stored as `samw`) cannot reach its
   token key `sam` (pinned by a test). The dry run marks every removal whose tokens name no launcher. The dry run prints its token names, a person reads
   every line, and the backup restores a file if one is wrong.
2. That the spellings above cover every key a live agent's tokens can sit under. They match the supervisor's
   `token_roster_name` and the session/key names the Windows, adopt and remote paths mint under. A key minted some
   other way would look orphaned; the dry run lists every planned removal by name so a person reads it first.
3. That the board on this account's port serves the store being cleaned. Inside a NAMED world the store root can be
   that world's while the port is the account's default board (or the reverse); `/api/status` does not say which
   store it serves, so only the board token (refused by a board that enforces it) and the "matches none" backstop
   tie them. Run it with the same environment the board was started with, and read every line.
4. That this tool takes the same per-agent lock as the board and supervisors that mint tokens. It does when run from
   a checkout at the installed app's commit, which the run step asks for; a much older or newer engine could take it
   differently.
5. That the derived port's listener is this account's board. If this account's board is down, another local
   account could hold that port and answer the health check; the kosmos command has the same exposure (loopback is
   machine-wide, #1946). The health check is not protection against that; run it with the board up.
