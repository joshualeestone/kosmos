# kosmos#1761: a token file that is already loose stays loose

## The mechanism, measured rather than assumed

`writeFileSync(..., { mode })` and `mkdirSync(..., { mode })` apply the mode **on create
only**. On a path that already exists they are silently ignored. All four arms:

    fresh create with mode 0600                     -> 600
    pre-existing 644, rewritten with mode 0600      -> 644   <- IGNORED
    then chmodSync 0600                             -> 600   <- the fix
    mkdirSync recursive 0700 on an existing 755 dir -> 755   <- IGNORED

⇒ `engine/sendertoken.js` set the mode and never chmodded, so **a token file or
directory that was already loose stayed loose through every later mint.**

Ten sibling engine modules chmod after writing; this one did not. Measured:
`sendertoken.js` chmodSync 0, writeFileSync 1.

## 🛑 The trap, and why the existing test could not catch it

`engine/sendertoken.test.js` already asserted `0600` on a minted file. **That arm passes
without the fix**, because it mints into a fresh path where the create-time mode does
apply. An assertion built on a fresh create cannot fail for this bug.

✅ **So the new arms PLANT A LOOSE MODE FIRST**, and each carries a precondition
asserting the plant actually took, because a plant that silently failed would make the
arm pass for the wrong reason.

**Perturbation matrix, re-measured against the SHIPPED code.** An earlier version of
this table described a `chmodSync(file)` on the target that the shipped code no
longer has, so a reader could not reproduce it:

| perturbation | arms that redden |
|---|---|
| remove `O_NOFOLLOW` | the FALLBACK symlink arm |
| remove the DIR chmod | the directory arm |
| copy instead of rename (leaks a temp) | the inode arm, both symlink arms |
| baseline | none |

⇒ **Every mutation reddens at least one arm and no arm is standing in for another.**

📌 **The fresh-create arm passes green in BOTH broken states.** That is the trap
demonstrated rather than described.

## The directory matters as much as the file

0755 on the directory lets anyone list and read the token filenames even when each file
is 0600. The fix chmods both.

## ⚠️ A wider gap, found while fixing this and NOT fixed here

🛑 **AN EARLIER VERSION OF THIS SECTION WAS FALSE AND THE CORRECTION IS THE USEFUL PART.**
It said "nine production engine modules call `mkdirSync` and NONE chmods the directory"
and that `sendertoken.js` would be "the only production module that tightens a
pre-existing directory". **Both wrong**, and it listed `remote.js` among the offenders.

✅ **`engine/remote.js:106-107` ALREADY DOES EXACTLY THIS**, with the same best-effort
catch and the same rationale:

    fs.mkdirSync(STATE_DIR(), { recursive: true, mode: 0o700 });
    fs.chmodSync(STATE_DIR(), 0o700);

⇒ **`remote.js` is the PRECEDENT for this fix, not an instance of the gap.** Measured:
exactly two production modules chmod a directory, `remote.js` and now `sendertoken.js`.
The gap list is **eight**, not nine.

⭐ I asserted an absence without checking it, which is the same defect as claiming a
guard is missing without grepping the test tree. **An absence is a claim and needs its
own measurement.**

The remaining eight (`cloudflare`, `connect`, `create`, `githubdevice`, `reporthook`,
`runners`, `tokendoor`, `trust`) chmod the FILE and stop. Carded as kosmos#1763, with
the note that it should not become eight reflexive chmods: the work is deciding which
directories hold something worth restricting.

## 🛑 The window I argued about and did not close

Pass 1 caught that the DIRECTORY chmod ran after the write, and I hoisted it. **Pass 2
caught that I left the FILE one line below it unfixed, on the more sensitive object.**
The argument was made and not applied.

Measured on exactly the path this fix exists for:

    planted 0644, then writeFileSync(..., { mode: 0600 })
      -> 644 IMMEDIATELY AFTER THE WRITE, secret bytes readable on disk
    control: a fresh path -> 600, no window
    (umask 022, so the umask is not what is masking it)

✅ **Fixed with temp-chmod-rename**, the pattern `engine/trust.js` and
`engine/create.js` already use: write a fresh temp with `flag: 'wx'`, chmod it, rename
over the target. The target is therefore **never briefly loose and never partially
written**, because rename is atomic. `wx` also refuses a symlink planted at the temp
path. A direct-write fallback keeps a mint from failing outright, since an agent that
cannot mint cannot speak at all.

⭐ **The new arm asserts the INODE, not the mode**, and that is the point: both shapes
end at 0600, so a mode assertion cannot tell them apart. A write-in-place REUSES the
inode; temp-then-rename REPLACES it. Perturbed back to write-then-chmod: the inode arm
reddens and the two mode arms stay GREEN, which is what proves it measures a different
property rather than duplicating them.

## 🛑 Two of my own guards were VACUOUS, and I broke both by renaming the temp

**The leftover-temp assertion filtered `.includes('.tmp-')`.** The old name was
`<file>.tmp-<pid>`; the new one is `<file>.kosmos-<pid>-<start>-<seq>.tmp`, which
contains `.tmp` and **never** `.tmp-`. So the filter matched nothing and the assertion
had two identical outcomes. A reviewer proved it by adding a deliberate leak after the
rename: **the suite stayed fully green.** Fixed to `endsWith('.tmp')`.

⭐ **That is the bulletin's own failure in one file**: a control keyed on wording I then
changed. I renamed the temp to fix a real hazard and silently disarmed the guard that
watched it, in the same commit.

**And `O_NOFOLLOW` was not load-bearing.** Deleting it left the suite green, because the
symlink arm only ever drove the rename path. My "test the property, not the path"
argument was defensible and its result was **zero coverage on the fallback**. Fixed with
an arm that stubs `renameSync` to force the fallback: a contrivance, and the right one,
because it drives real production code down a path a crash or a planted temp reaches.

## 🛑 `O_NOFOLLOW` IS UNDEFINED ON WINDOWS, WHICH IS THE PLATFORM THIS FILE IS FOR

`x | undefined` is `x`, so the flag would have **silently vanished** on win32. Measured:
`O_WRONLY | undefined === O_WRONLY` is true, no error, no signal.

⇒ The one platform this module exists to serve is the one where the symlink guard would
have been absent, and nothing would have said so. The constant is now read explicitly
and, where it is undefined, the check is done by hand with `lstatSync` rather than
pretending it was applied.

## 🛑 I cited `trust.js` as the pattern while using the version it rejects

The first temp name was `${file}.tmp-${process.pid}`. **`trust.js` documents that exact
scheme as insufficient**, beside its own `tempPath`:

> with `pid-seq` alone, a process that died between create and rename left it behind, and
> the next process to draw that pid refused at seq 1 **FOREVER** - a permanent wedge from
> one crash.

I used pid ALONE, which is worse. **A reviewer planted one stale temp and every later
mint for that agent silently took the fallback, in place, permanently reopening the
window this card exists to close, with no signal.**

✅ The name now carries pid + start time + counter, the same scheme and the same reason.
A leftover is inert: nothing ever asks for that name again, so `wx` fails only for a
PLANTED file, and a planted file is one we must not delete. Verified by replaying the
exploit: a stale temp of the old scheme no longer diverts the write.

## The fallback followed symlinks, and the plan had claimed otherwise

The plan credited `rename` with "a symlink at the token path is replaced rather than
followed". **True of the main path only.** Measured by a reviewer: forced onto the
fallback, the minted token was written THROUGH a planted link into another file, which
was then chmodded to 0600.

✅ The fallback now opens with `O_NOFOLLOW`, so it throws instead. Verified by replay:
the victim file is unchanged and the token path is no longer a symlink.

⭐ **The new arm asserts the PROPERTY, not the path.** The fallback is nearly unreachable
by design now, so contriving reachability would test the contrivance. The arm plants a
symlink and asserts nothing is written through it, which both paths must guarantee.
Perturbed: reverting to a plain write reddens it AND the inode arm, and leaves the two
mode arms green.

## ⚠️ Known and NOT fixed here

- **A symlink at the DIRECTORY level is still followed.** `O_NOFOLLOW` covers the token
  file, not its parent. Out of scope for a one-line security card.
- **`mint` is read-modify-write with no lock**, so concurrent mints across processes can
  drop a token. Pre-existing, not introduced here, and worth its own card. Same-process
  concurrency cannot interleave: `writeTokens` is fully synchronous.
