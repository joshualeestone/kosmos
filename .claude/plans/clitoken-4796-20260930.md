# clitoken-4796: CLI tests give the CLI a data root of their own

Card: kosmos#4796 (found by Renet while writing #4774's tests).

## The finding
A CLI test that runs `install/kosmos` against a stub board, with the parent's environment and no data root of
its own, lets the CLI read the REAL board token from this computer's Kosmos data and send it to the stub.
Measured on cli.community-read-4373's own shape (a probe that prints only whether the header arrived, never its
value): without a temp data root the board token arrived at the stub; with one it did not.

## The change
- 16 cli.*.test.js files that start a stub board and spread `process.env` now pass `AGENT_WORKFORCE_DATA` set to
  a temporary folder, removed on exit (the pattern cli.community-follow-4774 uses). One of them,
  cli.token-off-argv-1970, copies the header files it is handed into a log, so it could also have written the
  live token to disk.
- cli.community-read-4373 and cli.community-post-4289 each gain a test: only the stub board is asked, and no
  board token reaches it.
- cli.sandbox-data-4796.test.js: every CLI test that runs the CLI against a stub board must name a data root, or
  build the CLI's environment from scratch (no `...process.env`, as cli.agent-create-3734 does with a temporary
  HOME). Control cases for both shapes; with one file's data root removed the guard names that file.

## Tests
All cli.*.test.js: 248 of 248 (concurrency 4). At full concurrency three slow tests timed out under load and
pass alone (13 of 13).

## Decisions
- **Call:** a temp data root per file, plus a guard. **Rejected:** a shared helper module for the env (touches
  every file's structure for no gain over one line each).
- **Weakest premise:** that `...process.env` is the only way a test inherits the data root. A test that sets
  HOME to the real home by hand would pass the guard; none does today.

## Review round 1 (1 blocker, 3 warnings), all taken
- **Blocker:** cli.task-2662's first test still sent the live board token (measured true), and the guard passed
  the file because a second test in it named a data root. Fixed, and the guard now counts per environment: a
  file must name a data root at least as often as it inherits the parent environment (`...process.env`,
  `Object.assign({}, process.env)`, `env: process.env`). (Round 3 found this file-wide count could be fooled; see below.)
- An empty `AGENT_WORKFORCE_DATA: ''` no longer counts (engine/store.js reads it as unset; measured, the token
  was sent). A file that runs the CLI with no env of its own inherits the parent's and is refused. A file that
  sandboxes another way says so with a `#4796-sandbox:` line: three tests do (a throwaway KOSMOS_HOME store).
- The two community sandbox tests no longer depend on this computer having a token: each plants a fake one in a
  data root of its own and shows it IS sent (control), then shows the empty sandbox sends none.
- The same leak outside cli.* tests: engine/agyhooks.test.js's two bridge runs now name a data root.
- Tests: every cli.*.test.js plus engine/agyhooks.test.js, 285 of 285 (concurrency 4).

## Review round 2 (1 blocker, 1 warning), all taken
- **Blocker:** the codex, gemini and grok report-bridge tests still sent the live token (measured, all three)
  through their shared `drive()`: it now defaults to a temp data root, and a caller's own still wins. The guard
  swept only cli.* files, so it now sweeps every top-level and engine/ test that runs the CLI or a report bridge
  against a stub, and asserts it reaches the bridge tests. That found agyhooks' four dead-port runs and
  agyseed's agytrust run, which now name a data root too.
- **Warning:** the file-wide `#4796-sandbox` marker is gone. A throwaway `KOSMOS_HOME` counts per environment,
  the same as a data root. A data root set on the test process itself (top-level `process.env.AGENT_WORKFORCE_DATA
  = ...`, as engine/feedbackpull does) covers the file.
- cli.task-2662's temp data root is removed on exit.
- Tests: all cli.* plus the three bridge tests, agyhooks, agyseed-4417 and feedbackpull: 362 of 363 at concurrency
  4; the one red (cli.agents-setE-2321, a 15 s timeout, a file this branch does not touch) passes alone, 3 of 3.

## Review round 3 (0 blocker, 1 warning), taken
- No live leak remains: the reviewer planted a fake token and watched every stub server in the 70 test files that
  start one (1534 tests, 0 sightings, with a control that sees a leak).
- **Warning:** the guard compared file-wide counts, so one environment's data root covered another's gap; it
  passed a revert of the fix in five files. It now checks each inherited environment on its own: the object
  literal (or Object.assign call) it sits in must name a non-empty AGENT_WORKFORCE_DATA or AGENT_WORKFORCE_HOME
  itself, or a KOSMOS_HOME for install/kosmos only (the bridges ignore KOSMOS_HOME). A spread from elsewhere
  (`...env`) does not count. New control: with the #4796 fix stripped from six real files (task-2662, react-2255,
  the three bridges, community-read-4373), the guard names each.
- The per-environment check found three files sandboxed another way (busy-health-4466, start-own-pgroup-4669,
  presents-board-token-1968); each now names its data root in the literal too.
- Tests: all cli.* plus the three bridge tests, agyhooks, agyseed-4417, feedbackpull: 364 of 364 (concurrency 4).

## Review round 4 (0 blocker, 1 warning), taken
- A key named with no real value passed: `AGENT_WORKFORCE_DATA: undefined`, `: null`, `: process.env.AGENT_WORKFORCE_DATA`
  (the parent's own value), and `process.env.AGENT_WORKFORCE_DATA = undefined` (measured: Node drops an undefined key
  from a child's environment, so the store falls back to the real root). All three patterns now refuse those; a
  control case for each (with the old lookahead, the control fails).
- Left (NITs, recorded): a key inside a comment or nested object in the literal still counts; braces inside strings
  can make enclosing() refuse a correct file loudly; other ways to copy process.env (a variable alias,
  structuredClone, Object.fromEntries) fall to the file-wide check. None is present in the tree today.
- Tests: 364 of 364.

## Review round 5 (0 blocker, 2 warnings), taken
- A data root BEFORE the `...process.env` spread passed, though the parent's value then wins (and an agent's pane
  sets AGENT_WORKFORCE_DATA to the real root on a non-default install): the sandbox key must now follow the spread
  in the same object.
- `KOSMOS_HOME: __dirname` (the repo) passed, though install/kosmos then loads the checkout's own engine/store.js and
  the real root: a KOSMOS_HOME of __dirname, REPO or ROOT no longer counts. A control for each; with either fix
  undone its control fails.
- Left (NIT, recorded): a data root deleted later (`delete env.AGENT_WORKFORCE_DATA`) or set from a variable that
  holds '' still passes. Neither is in the tree.

## Review round 6 (0 blocker, 2 warnings), taken
- `Object.assign({}, { AGENT_WORKFORCE_DATA: D }, process.env)` was not even seen as inheriting (the pattern wanted
  process.env as the second argument) and the order rule did not apply to it: process.env anywhere in an
  Object.assign call now counts, and the sandbox key must follow it in the call.
- The repo check matched names, not values: a KOSMOS_HOME built from __dirname anywhere
  (`path.resolve(__dirname, '..')`, `path.join(__dirname)`) or named REPO*/ROOT* no longer counts. Controls for each.
- Left (NIT, recorded): a later spread (`...extra`) can reset the key, like the recorded `delete`; the guard refuses
  a temp folder that happens to be named ROOT, and KOSMOS_HOME: __dirname inside an engine/ test (safe there),
  loudly, not silently.
- The guard is a regex tripwire over test source, not a parser; it cannot see every way JavaScript can build an
  object. The live measurement (a planted token watched at every stub server, rounds 3 and 4) is what shows the
  tree clean today.
- Tests: 364 of 364.

## Review round 7: 0 blocker, 0 warning, 0 convention (converged)
Left (NITs, recorded): an Object.assign match can run past a missing semicolon onto a later spread; the "after"
slice for Object.assign starts at the first `process.env` in the call, so `process.env.HOME` earlier in it moves
the start; a KOSMOS_HOME held in a variable built from __dirname passes (the guard reads what is written, not what
a variable holds). None is in the tree; round 6's changes refuse no existing test and cannot hang (200k input, 1 ms).
