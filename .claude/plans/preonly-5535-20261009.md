# preonly-5535: "could not be reached" only when the bucket never answered (#5535 follow-up)

## Why
In engine/backupupload.js both upload loops set `preOnly` on ANY pre-connect failure and read it as "only pre-connect
failures". So a chunk or manifest that met one connect blip and then reached S3 (400 IncompleteBody or RequestTimeout:
S3 committed nothing, so not troubled) was reported at the deadline as "the bucket could not be reached", and got no
new grant. The same run without the blip re-grants. Deferred from the manifest review (#5637) as a follow-up.

## Change
- Chunk loop: a `reached` flag beside `preOnly` (set on any attempt that got past connecting); a chunk is `unreached`
  only when `preOnly && !reached`. The manifest loop already tracked `reached`; its `cleanRanOut` now uses the same rule.
- Two tests, one per loop: one ECONNREFUSED, then 400 IncompleteBody until the grant runs out. Each asserts the
  reason is not "could not be reached", that a second grant was asked for, and that nothing is unsure.

## Decided
- Re-grant (rejected: keep the no-re-grant stop). The no-re-grant rule exists because a bucket that cannot be reached
  would not be reached by a new grant either. A bucket that answered is reachable, and the no-blip path already
  re-grants on exactly these answers (the manifest still stops at MAX_REGRANTS, the chunk run at its own cap).
- Weakest premise: one connect failure followed by a reachable bucket is a transient, not a sign the network is
  flapping in a way a new grant would also meet. If it is flapping, the re-grant caps still bound the cost.

## Tests
engine/backupupload.test.js: 93 pass, 0 fail with the fix. Red-capability: with backupupload.js at origin/main and the
new tests kept, both new tests fail.
