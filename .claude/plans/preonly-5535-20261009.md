# preonly-5535: "could not be reached" only when the bucket never answered (#5535 follow-up)

## Why
In engine/backupupload.js both upload loops set `preOnly` on ANY pre-connect failure and read it as "only pre-connect
failures". So a chunk or manifest that met one connect blip and then reached S3 (400 IncompleteBody or RequestTimeout:
S3 committed nothing, so not troubled) was reported at the deadline as "the bucket could not be reached", and got no
new grant. The same run without the blip re-grants. Deferred from the manifest review (#5637) as a follow-up.

## Change
- Chunk loop: one grant-level `anyReached`, set by any attempt on that grant, from any chunk, that got past
  connecting. Chunks that only failed to connect end "could not be reached" (no new grant) only when nothing on the
  grant reached the bucket; otherwise they join the chunks left and are granted again. (Review 1: my first version
  kept the flag per chunk, so a grant where chunk 2 reached S3 and chunk 1 never connected still said "could not be
  reached". A per-chunk flag is then redundant: with no chunk reaching, every unreached chunk never connected.)
- Manifest loop: one upload per grant, so its existing `reached` is already grant-level; `cleanRanOut` now requires
  it (`!troubled && !(preOnly && !reached)`).
- Tests: one connect blip then 400 IncompleteBody, for each loop (each must end on its re-grant cap: chunk "grants in
  a row stored nothing", manifest "manifest grants in a row ran out", retryLater, nothing unsure); and two chunks on
  one grant, chunk 1 never connecting while chunk 2 stores: grant 2 asks for chunk 1 alone, and only that grant ends
  "could not be reached". A fourth test is a guard, not a fix: chunk 1 never connecting beside chunk 2 in trouble
  must end with the trouble (unsure named, one grant). It passes at origin/main too, by design.
- The trouble return now comes before the unreached one, so the unreached check is just `!anyReached` (review 3:
  `!stuck.length` there was redundant, since trouble always means some attempt reached the bucket).

## Decided
- Re-grant (rejected: keep the no-re-grant stop). The no-re-grant rule exists because a bucket that cannot be reached
  would not be reached by a new grant either. A bucket that answered is reachable, and the no-blip path already
  re-grants on exactly these answers (the manifest still stops at MAX_REGRANTS, the chunk run at its own cap).
- Weakest premise: one connect failure followed by a reachable bucket is a transient, not a sign the network is
  flapping in a way a new grant would also meet. If it is flapping, the re-grant caps still bound the cost. Named
  cost (review 3): a chunk that never connects while its siblings store is granted again on each grant until it is
  the only one left, spending a key slot per grant (of 200,000 a week); nothing is at risk, since it never sent a byte.

## Tests
engine/backupupload.test.js: 95 pass, 0 fail. Red-capability: with backupupload.js at origin/main, the three fix tests
fail (92 pass, 3 fail); with my per-chunk first version, the two-chunk test fails. The guard test fails when the
trouble return is weakened to `stuck.length && !unreached.length` (measured, 94 pass, 1 fail).
