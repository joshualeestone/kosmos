# hookscripts-5774: the token-only guard covers the scripts start-time commands run (kosmos#5774 part 1)

## Why
#5516 part 2 denied the configuration Claude Code reads at a token-only agent's start. A command in that configuration can still name a script anywhere else on the computer: a hook, the status line, an auth helper, or a server's program file. The script runs outside the sandbox each time the command does, so if the agent's file tools can rewrite it, the guard is open through it. Of the routes #5516 left for a next part, this one was picked first because it is live on a real install (measured; the details are in private notes, as for #5122), and because such a script runs during the session, on every hook, not only at the next start.

## The change
- `engine/startcommands.js` (new): reads every command Claude Code will run for the agent and names the script files they point at. Sources, read from Claude Code 2.1.296: each config home's settings, local settings and remote settings; the agent folder's and each folder above's `.claude` settings and `.mcp.json`; each global config's own servers and its entries for the agent folder and the folders above (never other projects'); the managed settings, their drop-in folder and the managed server file; and each installed plugin's manifest, hooks, servers and language servers. Commands are an object's `command` (with a server's `args`), and the helper keys (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`, `proxyAuthHelper`, `headersHelper`, any later `...Helper`). Each command is split into words as a shell would, enough to find paths: quotes, known variables (`HOME`, `CLAUDE_PROJECT_DIR`, `CLAUDE_CONFIG_DIR` for the agent's own home, `CLAUDE_PLUGIN_ROOT` in a plugin), `~`, command substitution, operators, and the script after a shell's `-c`.
- `engine/setup-assistant.js` `tokenOnlySettingsRules`: the scripts found are denied in both layers, links followed, as the start-time config files are. A script inside a folder already denied whole is left to that rule. An installed plugin's folder outside the config homes is denied whole. A command whose script path is built when it runs is named, and the guard says it is not whole. A script path the rules cannot carry is named when it exists.
- `engine/hookscripts-5774.test.js`: every tier, both layers; controls; the not-whole cases; the splitter.

## Decided
- **Every config home, not only the agent's own:** Kosmos can move an agent to another account (failover), and the guard already covers every home the same way.
- **Redirection targets are skipped** (`>> notes.md`): written by the command, not run. Denying them would lock the agent out of its own files when a hook appends to one. Input redirection counts only for a shell or interpreter (`bash < x.sh` runs it; `jq . < state.json` reads it, review 10), and a here-string given to a shell is its script.
- **A bare program word** (`bash`, `node`) is found on PATH, which #5516 part 1 covers; a program given by a path is a script like any other (review 16). The script word after an interpreter (`bash check.sh`) counts whether or not it exists, since the agent could create it in its folder (review 1). Review 5: EVERY plain word after an interpreter counts, not only the first, because a flag that takes a value (`bash -o pipefail x.sh`, `ruby -I lib x.rb`) would take the slot and leave the real script as an argument, and any list of such flags is partial. Cost: a hook's data argument in the agent folder (`python3 hook.py notes.md`) is denied too, the safe direction for a file. A flag's value with a file extension counts anywhere (`--project=tsconfig.json`), as it may be code or carry it.
- **An existing folder is never a script** (review 1): `cd "$CLAUDE_PROJECT_DIR"`, `rg x ~/work` and `find /` name folders, and denying one would take the agent's own work away, not just profile size.
- **Variables:** a settings `env` value is known when every tier that sets it agrees; set two ways, it is unknown (review 1). A NAME=value before a program, its value quoted or not (review 5), is read as a path (`BASH_ENV=/x.sh`), `${VAR:-default}` takes the known value (`$PWD` is not known: review 11), and so are the commands inside `$(...)`, backticks, and after an interpreter's `-c` or `-e`. An unknown value is reported only where the script itself sits (the program, an interpreter's script position, input to a shell, a flag's path value, inline code); elsewhere (`mkdir -p "$X"`, or an argument the hook passes after its script, `node ~/x.js "$FOO"`: review 12) it names nothing that runs (review 2).
- **A dynamic path makes the guard not whole** (as an uncarriable link target already does in #5516). Rejected: guessing, or skipping silently. What would change it: such hooks turning out common on real installs. Measured on the fleet Mac: none.
- **An uncarriable path that does not exist is skipped:** a word that only looks like a path (a sed expression such as `s/(a)/b/`) is far likelier than a missing script with brackets in its name, and naming it would refuse token-only agents for nothing.
- **Global config: own servers and the agent's project entries only.** That file holds every project on the computer, and others' servers do not start for this agent.
- **Where something runs, versus an argument** (review 2): the program, an interpreter's script, input to a shell, a flag's path value, a NAME=value, and inline code count wherever they are. Any other argument is something the program reads or writes; it counts only OUTSIDE the agent folder (`jq . package.json` and `tee log/hook.log` leave the agent its own files). Outside the folder an argument file is still denied, the safe direction for a file, at the cost of profile size, which the size warning counts. Folders are never denied (above).
- **A program behind a wrapper is the program, for the wrappers listed** (reviews 2 and 4): `env` (and `env -S`), `nohup`, `sudo`, `timeout`, `xargs`, `npx`, `watch`, `parallel`, `find -exec`, `if`/`then`/`do`/`{`, with the value flags of the common ones; a runner's subcommand (`deno run`, `uv run`, `go run`) keeps the script slot, and its own value flags (`uv run --with x`) are skipped. What `node -r` and `bun --preload` load runs too. `python -m mod` names a module, not a file.
- **`cd` moves where a relative script is read** (review 4): a relative script is read from the agent folder and from every folder a `cd` on the line went to (a subshell's cd is not undone, so this over-counts rather than misses); after a `cd` Kosmos cannot follow, a relative script is named.
- **A flag's value counts as a path only when it looks like one** (a slash or a file extension), and a package name (`@scope/pkg`) is not a path (review 4): `--max-old-space-size=4096` and `npx @scope/server` must not deny files in the agent folder.
- **An empty config file holds nothing** (review 4), not an unreadable one; a byte-order mark is ignored.
- **Comments, here-documents and an unclosed quote** (review 6): a `#` comment runs to the end of its line (an apostrophe in it opens no quote); a here-document's body is skipped, except that given to a shell it is that shell's script and is read; an unclosed quote is named, since where the command ends is unknown.
- **`PATH=` before a program, or `export PATH=`** (review 6): a bare program is then also looked for in the folders it put first, and that file is denied; a PATH built from a variable Kosmos cannot read is named.
- **A word with a script's extension** (`.sh`, `.js`, `.py` and the like) is code wherever it sits (review 6), so an unlisted wrapper cannot hide it. On the fleet Mac this also denies the agent a file named `start` in its folder: Kosmos's own report hook passes that word to its script.
- **A hook or status line runs in the session's current folder, not the agent folder** (review 11, read from the 2.1.296 binary: both are spawned with the session's cwd, which the agent moves with cd inside its own folder). So a relative script there (`bash scripts/check.sh`, `.claude/hooks/x.sh`) could be one the agent makes in any of its subfolders: unless the line first cd's to an absolute folder (or `$CLAUDE_PROJECT_DIR`, or home), it is named and the guard says not whole, with the fix in the refusal (a full path, or one from `$CLAUDE_PROJECT_DIR`). It is still denied at the agent folder. Only the script position counts, so a later argument (Kosmos's report hook passes the word `start`) does not refuse anything. A server starts in the project folder, so its relative script is known. Rejected: a `**` glob deny in the agent folder for each such name, because the sandbox layer has no matching rule and it would deny ordinary files of that name anywhere in the agent's work. Measured on the fleet Mac: no relative hook scripts, so no agent is refused.
- **`CLAUDE_CODE_SHELL_PREFIX`** in a settings env is a command Claude Code puts in front of every hook (review 11), so it is read like one; set two ways, it is named.
- **Review 15 widened the folder-runner rule to every folder:** a runner moved elsewhere (`cd /opt/proj && make`, `make -C /x`, `npm --prefix /x`) runs THAT folder's Makefile, package.json, .git hooks or config, which the agent's tools can rewrite there too, and Kosmos cannot list every file such a program reads. So a folder runner is named wherever it runs, except inside a folder the guard already denies whole (a plugin's own folder, a config home's code folders), and the refusal says to change the command to run a script by its full path (it no longer suggests another folder, which was the uncovered route). A folder in the program position (`uvx --from /src tool`) is named as code too.
- **Code the agent folder supplies is named, not covered** (review 6): `npm`, `npx`, `make`, `cargo`, `git`, `pytest`, `python -m` and the like, run in the agent folder (no cd elsewhere), run the agent's own package.json, Makefile, build or test config outside the sandbox. Denying those files would take the agent's work; so the guard says it is not whole and names the program. Decided at the end of each command, so a runner's own change-folder flag counts (`make -C /x`, `uv --directory /x`, `npm --prefix /x`, `git -C /x`: review 7, which also reads the script from that folder); after a cd or flag Kosmos cannot read, the folder may be the agent's, so it is named. Cost (review 7, stated in full): a person with such a hook, status line or SERVER in their own settings cannot create a token-only agent until it changes. That includes `npx -y @scope/server`, the commonest way servers are started (npx prefers the agent folder's node_modules), and `git` in a status line (git reads the folder's .git/config, which can name a command). A server cannot be scoped with a cd: the refusal says to give the program by a full path to an installed copy, or run it from another folder. Measured on the fleet Mac: none of these, so no agent here is refused.
- **Package-script runners** (review 8): `bun start`, `bun run start`, `bun test`, `deno task start`, `uv run hook`, `uv sync` name a script or task in the folder's package.json, deno.json or pyproject.toml, not a file, so they are folder runners too; with a file (`bun run x.ts`) the file is the script.
- **The npx and git cost is a product trade, decided here, Josh can override** (review 8 asked for a product confirmation): the Claude Code docs' own status line example runs `git branch`, and `npx -y ccstatusline` is a popular status line. Either refuses creating a token-only agent on that computer. Rejected: trusting git or npx in the agent folder, because `git status` in a folder the agent controls runs a command its .git/config names (core.fsmonitor), and npx prefers the folder's node_modules. What would change it: a narrower measured rule (for example a git subcommand that reads no executable config), or Josh preferring a warning over a refusal for these.
- **A folder an interpreter runs as code is named** (review 7): `node /srv` (its index.js or package.json), `python3 ~/app` (its __main__.py), `java -cp ~/lib`. Kosmos never denies a folder whole, so the guard says it is not whole. Only the first plain word after an interpreter, or a code flag's value, counts as that position; common value flags (`ruby -I`, `bash -o`) are skipped so a library folder is not mistaken for it.
- **A pattern is not a script** (review 7): a word with a script extension counts anywhere except when it is a pattern (`case "$f" in *.py)`, `find -name '*.py'`, `--include="*.ts"`), so formatter and lint hooks keyed on extensions do not refuse token-only agents.
- **A server's command is one program, started directly** (review 2), with or without args, in the project folder. A hook given as a command with args (exec form) is also started directly, but in the session's current folder like a shell-line hook, and Claude Code expands only `${CLAUDE_PROJECT_DIR}` and the plugin variables in it (review 13), so `$HOME` there is literal text.
- **The test command is not a pattern** (review 3): `[` and `[[` as the program would otherwise have made the most common hook shape (`[ -f x ] && ...`) refuse every token-only agent on the computer. A pattern counts where it names a path or a script.
- **Runners that take their script after a flag** (review 3): `java -jar`, `awk -f`, `sed -f`, `jq -f`, `make -f` and a few more name the script where it runs, so an agent-folder one counts. Each interpreter's own inline flags (`bash -c`, `node -e`, `perl -e`), not one list for all.
- **A script path the rules cannot carry is named where it runs, even before it exists** (review 3), and where it is only an argument, once it exists.
- **On macOS the managed preferences are read** (review 3), device-level and per-user, through plutil; one that will not convert is named.
- **From the global config only its servers and helper keys** are read, not the rest of the file (cached runtime state could carry a `command` key) (review 3).
- **An unexpanded pattern where a script is named, a config file that exists but cannot be read, and a plugin whose recorded folder is not a full path or is (by its given or resolved path) the agent folder, inside it, a folder above it, the home or a config home are named**, so the guard says it is not whole (review 2). A file that does not parse is read once more first (review 10: the global config is written by every Claude Code process on the account), so only one caught mid-write twice reads as unreadable, and that refresh says not whole. Not the agent folder's own two settings files: the guard rewrites them (an unreadable one is kept as a dated copy, #4491 review 18), so their old text never loads; the guard-module tests caught that, by both the given and the resolved path.
- **Windows: not handled here, deferred** (review 2 asked for a Windows tokenizer). The token-only guard returns unsupported on win32 before any rule is built (guardTokenOnlyFolderNow), so this module never runs there; the Windows guard is #5664's.

## Gaps, stated
- What a script or a PROGRAM runs or reads in turn: a script that sources another, and a program not in the folder-runner list that reads the folder it runs in. The listed ones are named (review 6); the rest are a next part of #5774.
- The shell's own startup files, and environment settings that point a program at code (BASH_ENV, NODE_OPTIONS): a next part.
- Hooks declared inside skills, agents and commands: those definitions are denied whole where they live, but a script they name elsewhere is not read. A next part.
- A plugin loaded from a folder given on the command line, or from a skill folder, is not in the installed-plugins record. A script given inline in a managed policyHelpers entry is not read.
- A wrapper not in the list, or a value flag of a listed wrapper that is not in its table, hides the program behind it.
- A script named by a later edit to a config file the agent cannot edit (the person's, or Kosmos's) is covered at the next guard refresh, not at once.
- A file piped or substituted into a shell (`cat x | sh`, `bash <(cat x)`) is an argument of `cat`, not the shell's script; `sh < x` is read. A single-file source launch (`java Hook.java`) or another unlisted interpreter runs a relative file in the agent folder unread.
- A hook set to run under PowerShell (`"shell": "powershell"`) is still read as a POSIX line. A settings env value is taken from any config home's settings, though at run time it comes from the agent's own account's and the launch environment.
- On Linux with the person's own sandbox on, `sandbox.bwrapPath` and `sandbox.socatPath` name programs by plain path; not read.
- The splitter is not a shell: aliases, functions, `eval`, and words built by shell expansions other than `$VAR`, `${VAR}`, `${VAR:-x}` and `$(...)` are not read. Inline code for a non-shell interpreter (`node -e`, `perl -pe`) is not read as shell (review 9); only the absolute paths in it count. A program's own hook or config folders given by flag (`git -c core.hooksPath=dir`) are folders and are not denied.
- Cost: every refresh reads each config home's global config (often several MB) and up to two managed preference files through plutil, per token-only agent. Measured on the fleet Mac: 28 ms for 8 homes. Not cached.
- Tests elsewhere that do not pass `managedDir` read the real managed folder (absent on the fleet Macs).

## Weakest premise
That the commands Claude Code runs are the ones these keys hold. The list is read from 2.1.296's settings schema and loaders; a later version with a new command-carrying key is a gap until added, though any `...Helper` key is read already.
