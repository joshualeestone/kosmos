# dl-resume-3229: resumable + parallel-range Claude Code install download (#3229)

## Problem

kosmos#3229: the in-app "Installing Kosmos" one-large-download (the ~214MB Claude Code
binary from downloads.claude.ai / GCS) is slow and stalls on fresh Apple-silicon Macs.
The CDN is fast (measured ~15 MB/s); the root is that engine/connect.js `download()` fetched
the binary over a SINGLE non-resumable stream, so any interruption restarted the whole
~214MB from zero and there was no parallelism. The GCS object supports `accept-ranges: bytes`
and we were not using it.

## Goal

Make `download()` RESUMABLE and PARALLEL-RANGE while preserving every existing contract, with
the sha256 over the assembled file as the single correctness gate.

## Approach

- Detection folded into `fetchFile` on the response headers (no separate HEAD probe): a
  service that advertises `accept-ranges` with a known size at or under `MAX_DOWNLOAD_BYTES`
  aborts the single stream and delegates to `fetchResumableParallel`; a service that does not
  (and every existing test stub) streams once from the start, byte-for-byte as before.
- `fetchResumableParallel`: split into up to N contiguous segments (concurrency default 4,
  clamped [1,8], env `AGENT_WORKFORCE_CLAUDE_DOWNLOAD_CONCURRENCY`; files under
  `MIN_SPLITTABLE_BYTES` are one segment). Each segment is an append-only `.part.<i>` so a drop
  resumes per-segment with no holes; a bounded worker pool runs them; segments concatenate in
  order into `.part` behind one persistent error handler.
- `fetchSegment`: a Range GET expecting 206, appending, capped at its requested range length;
  redirect-downgrade refusal and close-before-settle error discipline mirror `fetchFile`.
- Resume: the top-of-`download()` unlink of a same-version `.part` was removed; the dir sweep
  keeps this version's `.part`/`.part.<i>` and removes other versions'. The installClaudeCode
  error sweep deliberately preserves segments so a retry resumes.
- Correctness gate: `sha256File(part)` over the assembled file for both paths; a corrupt resume
  fails it and the partial plus segments are discarded whole, so the next attempt restarts clean.
- Cancellation: `abortAllRequests()` (cancel/becomeStuck) tears down the single stream and every
  tracked segment; the driver-reassignment orphan self-destroy tracks all of the flow's segments
  via a per-flow Set.
- Fallback: if a service (or proxy) advertises ranges then answers a segment Range with a
  non-206, `download()` discards the partial and retries as one single stream, so the parallel
  path is never a permanent regression versus pre-#3229.
- Ceiling: `MAX_DOWNLOAD_BYTES` (~1GB) bounds both paths against a misbehaving service filling
  the disk before the sha verdict.

## Preserved contracts

willInstall/281MB confirm gate, platformKey refusal, onProgress/track callbacks, cancellation,
reuse-if-verified (#875), win32 `.exe`, the #458 cancel-while-part-open timing, dest/store
layout, `downloadBase()` and the manifest flow, and the override envs are all unchanged.

## Honest-success fold-in

The reported false-"installed" during a slow install is NOT connect.js download-completion
(which is honest: `download()` gates on sha + rename, `installClaudeCode()` gates on a real
`resolveBin` presence check). It lives in the installer-script / first-run path (the macOS .pkg
app placement completing before the in-app provider download). Filed as sibling card #3230
rather than scope-crept into this PR.

## Tests

Colocated in engine/connect.test.js: resume-from-partial (serves only the missing bytes) +
sha-gate red-capable (a same-length wrong-bytes segment caught only by the final sha);
range-advertised-then-ignored single-stream fallback; assembly write-error rejects cleanly;
cancel mid parallel-range download leaves nothing behind. Full `yarn test` green.
