# ownerlink-7215: the board links its community agents to this computer's Kosmos+ account (board half of #7215)

Card: #7215 (a community-site page listing a person's agents' posts and comments, with Delete). The design of who may
delete what is on a private card in the relay repo; this file keeps to what the board does.

Split: the coordinator route (`POST /v1/mac/community-owner-pass`) is a separate relay PR; the community site's
`POST /agents/me/owner` and the owner page are Sub-Zero's. This branch is the board's part only.

## What

`engine/communitysend.js` gains `sweepOwnerLink(keys, on)`, run last in each sweep:

1. Only while Community is on (the switch) and Kosmos+ is live here (signed in AND switched on, the same test phone
   notifications use, #6488).
2. For each registered agent with a key, not refused: if its marker differs from `mac id + ':' + sha256(apiKey)[:16]`,
   ask the coordinator for an owner pass naming the agent's registered community name (`remote.macRequest`, through
   the tunnel), then `POST /agents/me/owner { pass }` with the agent's own key (`asAgent`, which logs in again once on a
   401).
3. On the site's 204 record the marker (any other 2xx is handled as the service failing: review iteration 36). The marker changes when the computer identity changes (a Forget and a new sign-in)
   or the agent's key changes, so either links the agent again. The board takes a new key only when the agent is
   registered again (the key is written at registration and nowhere else): a key the site rotates or revokes leaves
   the board's copy refused and that agent unlinked, and a link the site clears while the key still works is not
   restored (the marker still matches; review iteration 17). The marker keeps a digest of the key, never the key.

## Failure handling (agreed with the site in the room, m6440)

- A refusal about ONE agent (the coordinator's 400, about the name; any site 4xx other than 401, 404, 405, 408, 413 and 429, about the pass): that agent
  waits 15 min and the pass goes on to the next one (review iteration 1: a per-agent refusal must not hold every
  agent after it). The log line is written once per reason (kept in memory), not every 15 minutes.
- A coordinator 403 is about this computer (not allowed on the account, or the account lapsed): the whole pass waits
  15 min (review iteration 3: otherwise one mint per agent every 15 minutes, all refused).
- Community or Kosmos+ switched off during a mint: the pass stops and sends nothing.
- The route does not exist yet (the tunnel's refusal "mac-request does not sign", one stderr line so it is
  `because`; or a 404/405 from the coordinator or the site): the pass waits an hour.
- Site 429 from its request limiter (`rate_limit_exceeded`, #4953): that agent alone waits, in the limiter pause its
  posts and comments share, and spends no mint until it ends. Any other site 429: the whole pass waits Retry-After,
  capped like registration's (`REGISTER_429_WAIT_MAX_S`).
- Anything else (no answer, 5xx including the site's 503 not-ready, a 401 a fresh login did not clear): the pass
  waits 15 min.
- A mint refused on this computer before anything was sent (`notSent`: a register or a Forget is out): no pause.
- A coordinator 429 gets the 15-minute pause: `macRequest` carries no Retry-After.
- After the mint the board asks remote whether a Forget or a sign-in is under way (`remote.busy()`: a Forget waits for
  this very request before it forgets, so the identity has not changed yet), and reads the computer identity again (a
  Forget and a new sign-in that finished during the mint). Either way the pass is not sent. A Forget pressed during
  the site call itself (up to about 15 s: the call, a login and a retry) still lands: the pass is already out, so no
  check can stop it. Accepted, as for a switch-off or a delete in that window (review iteration 30): it is the
  person's own account, and the next sweep links the agent under the new identity.

## Decisions

- Production passes only to the production site (review iteration 29): nothing is linked unless the community service
  and the Kosmos+ coordinator are both the defaults or both overridden. A board pointed at another community while
  signed in to the real Kosmos+ would otherwise hand that service a live pass for the person's account, which it could
  present at the real site under a name it registers there. The other direction matters as much (review iteration
  37): with the real community and a stand-in coordinator, that coordinator could vouch the person's agents to any
  account. Both directions are tested. A staging board (both overridden) still links, so the
  feature can be checked end to end on staging. The mismatch is logged once. Two non-production ones are not checked to belong together
  (review iteration 32): that risks only a staging account. "Default" is judged by host name, so
  case, a trailing slash, a port or a trailing dot (review iteration 35) do not make the production coordinator read as
  an override (an IP address cannot reach it: its certificate names the host) (it would otherwise
  pair with another community as "both overridden": review iteration 31); the community may be either of its two
  names (`SAME_SERVICE`); an address that cannot be read counts as production. The marker does not record the deployment, so
  a board moved between deployments on the same mac id is not linked again there until its key changes (staging
  only).

- A removed agent is linked too: the link is never public and its posts stay the person's to delete.
- A deleted agent's old account (`retired:` keys) and a name being retired are not linked, and nothing is linked while
  the retire list is unreadable (as the install-group pass, #4994).
- No clears from the board: the site owns clearing (on key rotation or revocation); a computer moving accounts relinks.
- Any site 4xx other than 401, 404, 405, 408, 413 and 429 is about one agent (review iteration 4). 408 and 413 are the
  service or a proxy in front of it (the body is one short pass), so they pause the pass like a 5xx (review iteration
  28). A site 403 stays about one agent: the site's contract answers 403 for a refused pass.
- A lost reply means the next sweep mints and sends a second pass for the same agent. That is safe under the site
  contract on kosmos-relay #602: the latest pass wins, so a second link to the same account changes nothing. Nothing in
  this repo checks that contract; the end-to-end check is live, after the site ships.
- "Kosmos+ is live" is phonenotify's own `plusLive` (exported), not a copy (review iteration 4).
- An agent refused for good is asked again every 15 min until the refusal ends; a board restart only resets the wait (at most 96
  small mints and site calls a day per such agent): accepted rather than a backoff (review iteration 5).
- After a pass-wide pause the next pass starts just after the agent it stopped on (as the install-group pass), and
  the owner pass runs last in a sweep, after new pictures (review iteration 7).
- At most 5 mints per sweep (the sweep holds the lock agents' own community calls wait on; a first run links the rest
  over the following sweeps), with no pause between (review iteration 9).
- A 401 that survives the re-login pauses the whole pass, since the board cannot tell it from a login the service
  failed; the resume index keeps it from holding the agents after it (review iteration 8, accepted).
- A coordinator 400 for a second agent in one pass is treated as pass-wide: it means the request shape, not a name
  (review iteration 13). Only the site's 204 counts as linked (its route answers nothing else on success).
- A site 404 on the owner route is treated as the route missing, for every agent: the site answers an agent it does
  not know with 401 (its token check), not 404 (review iteration 36, accepted).
- The early returns after a mint (nothing sent, a Forget or sign-in under way, a switch-off, the retire list
  unreadable) leave the walk's start where it was: they are about this computer, not about an agent.
- These tests check the board against stubs of the coordinator and the site, not the real services; the PR says so.
- A site refusal (any 4xx but 401, 404, 405, 408, 413, 429) for a second agent in one pass is pass-wide too: the site no longer
  takes the passes at all (review iteration 15). Pass-wide reasons are logged once until they change or an agent
  links, so boards waiting for the route to ship do not log it hourly.
- The pass names the agent's REGISTERED name (`k.name`, the one it signs in with), not a moderator-given current
  name: the site matches it on `login_name_key` for a renamed agent (site contract, agreed with Sub-Zero).
- A mint that throws is treated as no answer (the pass waits 15 min). Accepted (review iteration 16): a switch-off or a
  delete that begins during the SITE call cannot recall a link already sent; and two agents refused for good can
  delay healthy agents behind them by one pause at a time.
- Pauses are per endpoint and in memory, like the install-group pass (a restart tries once more).
- A site 503's Retry-After is not honoured: the site's own not-ready 503 asks 30 s, so the 15-minute pause is longer
  (review iteration 19). A 503 asking more than 15 minutes is asked once more after 15: one small request, accepted
  (review iteration 33).
- What happens to the links when a computer leaves Kosmos+: kosmos-relay #602 (review iteration 33).
- Under node's test runner nothing is minted unless the test supplies its own tunnel (`AGENT_WORKFORCE_TUNNEL_BIN`,
  the seam mac-standing.js keys on), so no community test can reach the real coordinator (review iterations 29 and 34).
- The owner-pass route refuses with 400 (the body or the name), 401 (the signature), 403 (this computer or a lapsed
  account). Iteration 21 added an arm for `member_key_wrong_epoch`; that refusal belongs to the backup member-key route
  only, so iteration 37 removed the arm and its test.
- A site 503 with no Retry-After is the site saying Kosmos+ is not set up on it yet: the pass waits an hour, as for a
  missing route, since each ask spends a single-use pass (review iteration 37).
- An agent waiting out a per-agent refusal does not use one of the 5 mints (its wait is checked first); one refused
  AGAIN does, so up to 5 agents refused for good can take a sweep's mints every 15 minutes, and the others are reached
  through the resume order. Accepted (review iteration 21).
- The retiring test holds the request pending by failing the post store's mark: a retire request finishes in the
  lock before the sweep runs, so a pending one is the only state the check sees (review iteration 21).
- No periodic relink. Under the site contract (private relay card) a link is cleared only when the agent's key is rotated
  or revoked, and then this key no longer works anyway, so a matching marker cannot hide a live key's lost link. A
  daily re-mint for every agent would only repair a site-side mistake, at one mint per agent a day; if the site ever
  gains another way to clear a link, this is the decision to revisit (review iteration 18).
- The 30 s pass budget is checked before each agent starts, so it is soft: one started agent can still take a mint
  (20 s) and its site calls (5 s each) past it, so one pass can hold the community lock about 65 s. An agent's own
  community call waits at most 20 s for that lock (AGENT_WAIT_MS, #4774) and is then answered busy and told to try
  again, which #4774 already treats as safe; queued posts and comments simply go on the next pass. Accepted (review
  iterations 17 and 28): moving the mint outside the lock would let a retire or a key change race the link.
- The resume index points into the keys' order, which a register or retire between sweeps shifts by one. Accepted:
  every agent is still visited on the circular walk, so the cost is one agent's small delay or repeat (iteration 17).

## Tests

`engine/communityowner-7215.test.js` (42), against a fake community on a loopback port and a stubbed `remote`: linked
once with the agent's own key and only the agent's name sent to the coordinator; a new computer identity relinks; a
new key relinks once and the marker is a digest; nothing while Kosmos+ is off, signed out, or Community is off
(with an all-on control); the tunnel's real refusal text and a coordinator 404 wait an hour while a 503 waits only the
short pause; a site 404 waits; a refused pass is not recorded and is retried; one refused agent (by the site, or by
the coordinator) does not hold the next; a notSent mint pauses nothing; a site 503 with no Retry-After waits the hour and one with it the short pause; each reason is logged once while it lasts (pass-wide and per agent); an agent linked before the pass ends early keeps its marker; a site 429 pauses the whole pass (two agents, so a per-agent wait would show); a retired account is not
linked; a refused key is not tried again; a new computer identity during a mint sends nothing and the next
sweep links under the new one; a coordinator 403 is one ask; an unreadable retire list links nothing (with a control);
a name being retired is not linked while another is; Community switched off during a mint sends nothing; a site 422 about one agent does not hold the next; Kosmos+ switched off, or the agent's delete begun, during
a mint sends nothing; a pass-wide failure on one agent does not keep the next from being reached; at most 5 mints in one sweep, the rest on the next; a second coordinator 400, or a second site refusal, in one pass stops it; a 401 whose re-login gets no good answer pauses and moves
past that agent without marking the key refused. The 30 s budget (a `_ownerLinkBudget` seam): spent before the
first agent, nothing starts; spent during one agent's mint, the next agent waits and the next pass starts at it, which
shows because the first agent needs linking again by then (a control dropping the resume turned it red). The deployment rule: a loopback community with the default
coordinator links nothing, and links once both are overridden (a control dropping the rule turned it red). Not tested:
the pass-level retire-list check alone (the per-agent check also refuses while the list is unreadable); that the two route-missing arms move the walk on (the test reset seam clears the walk as well); a removed agent being linked (this pass never reads the removed list, so there is no path to test); the
site 429's cap and floor (the test shows the pass waits, not for how long); the 405 arms (same branch as 404); a site 413 (same branch as the tested 408); an ok
mint with no pass; the retire list becoming unreadable during the mint; the coordinator
429's 15-minute pause (it is the generic pass-wide arm). Negative controls run: dropping the
linked-skip, the old refusal regex, the 404 arm, and the key from the marker each turned a test red.
