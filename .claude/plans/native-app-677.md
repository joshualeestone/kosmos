# Kosmos as a real native app, not a bookmark (#677)

Branch `native-app-677`. Josh (#admin, 24 Aug 16:20/16:24): "It's kind of weird to open an app and have it just launch a web browser... I do want to properly scope it out." Confirmed later: "a standalone .dmg, not a browser-based one." Scoping sent to and accepted by Splinter, 25 Aug 05:03.

## The decision

**Native Swift + WKWebView, not Electron, not Tauri.** Argued from the card's own words: a local-first product shipping a 150MB Chromium runtime is a statement. Everything a native build needs is already on this machine and needs no new provisioning: Xcode (`swiftc`, `xcodebuild`), the Developer ID Application cert already used for the `.pkg` (Stone Syndicate LLC, 864QZ69GF2), the same `kosmos-notarize` keychain profile, `hdiutil` for the eventual `.dmg`.

## What this reuses, unchanged

- The board itself: still Node, still `server.js`, still `127.0.0.1:16180` (or `$KOSMOS_PORT`).
- `kosmos start`'s existing health-check-and-start-if-needed logic (`install/kosmos`) -- the app shells out to it exactly as the current bash launcher does via `kosmos open`, it just points a native window at the URL afterward instead of handing the URL to `open` (the default-browser call).
- Signing/notarization pipeline, verbatim.
- Mona Lisa's quit-dialog spec (24 Aug 20:50), copy verbatim.

## What's genuinely new

- A compiled Swift/AppKit binary (`NSWindow` + `WKWebView`) replacing the current bash-script `Contents/MacOS/Kosmos`.
- One lifecycle decision point (Splinter's explicit design requirement): window-close, Cmd-Q, and Dock "Quit" all route through ONE place, so whichever way Josh answers "does closing the window quit" is a config change, not a rewrite. `applicationShouldTerminate` is that seam by AppKit's own design.
- **Provisional, not his ruling** (Splinter, pending Josh): closing the window does NOT quit -- the app stays running, the window hides (the Mail/Slack pattern). Agents keep working while the window is shut, which is the whole point of the product; a fat-fingered close can't kill your fleet. If Josh answers differently, this is `applicationShouldTerminateAfterLastWindowClosed`'s one return value plus `windowShouldClose`'s one branch -- not a rewrite.
- The quit dialog: Mona Lisa's spec says the second button ("stop every agent") cannot ship yet -- the engine has no fleet-stop, only a per-agent stop and a board-only `kosmos stop`. Ship with the FIRST button only ("Close the app"), so the sentence stays true. Add the second button when fleet-stop exists, not before.
- A runtime config mechanism for the compiled binary. The CURRENT bash launcher gets `$KOSMOS_HOME`/`$owner_uid`/`$PORT` baked in via heredoc string substitution at install time (`install/setup.sh` `build_app_bundle`) -- a compiled binary can't be re-baked that way without recompiling per install, and compiling on the user's Mac is explicitly ruled out elsewhere in this codebase (`install/kosmos`'s own comment: invoking a toolchain at install time risks an Xcode command-line-tools dialog, "exactly the kind of surprise this install must never produce"). So: the binary is pre-built once (the same shape as `kosmos-tunnel`, Baron's Rust connector, already pre-built and shipped rather than compiled locally), and reads its install-time values from a small companion file `build_app_bundle` writes into `Contents/Resources/` -- same baked-at-install-time contract, different mechanism.
- A `.dmg` builder (`hdiutil`), once there's a real app to put in it.

## Sequencing (agreed with Splinter)

1. **This phase**: a standalone prototype, NOT yet wired into the installer. Prove the AppKit lifecycle mechanics (window, WKWebView loading a live Kosmos board, stay-running-on-close, the quit dialog exactly as spec'd, the one-seam design) against a real running board, by hand, before touching `install/setup.sh` at all.
2. Once proven: design the runtime-config file, wire `build_app_bundle` to write it and to place the pre-built binary instead of generating the bash script, sign + notarize the binary the same way the `.pkg` already is.
3. `.dmg` packaging, once there's a real signed app to put in it -- Mona Lisa's cue to start the drag-window artwork. Tell her then, not before.

Windows stays explicitly out (#570 -- no machine to build or test on yet).

## Phase 3 design (installer integration) -- researched before touching install/setup.sh

Splinter's flag: `install/setup.sh` is the install surface, so this phase gets Pete's full five-leg walk, not a scoped one. Two real, load-bearing findings from reading the current code before writing any of it, plus the resulting design:

**Finding 1 -- `bundle_is_ours()` proves ownership by grepping the launcher's own text.** `install/setup.sh:191-203`: it requires `Contents/MacOS/Kosmos` to be a regular file (not a symlink) and greps it for the anchored token `:-$KOSMOS_HOME}"` -- the exact bash substitution syntax the current heredoc launcher contains, closing brace and quote included, specifically so a prefix-related `$KOSMOS_HOME` cannot cross-match. Every destructive path in the installer (replace-in-place, the stale-residue sweep, the uninstaller, the home-folder-foreign-app check) calls this before touching a `Kosmos.app` it did not just create. A compiled Swift Mach-O binary is still `[ -f ... ]`-true, but the literal text `:-$KOSMOS_HOME}"` will not appear in it -- this check silently fails closed (never proves ownership, so the installer would treat every existing binary-bundle install as a stranger's app and refuse to replace or clean it up).
  - **Design**: move the anchor off the executable and onto `Contents/Resources/kosmos-install.json`, which is written per-install (unlike the binary, which is identical across every install) and already carries `kosmosHome`. Written in one fixed, single-line, bash-`printf`-authored form specifically so it stays grep-anchorable the same way the current token is: `"kosmosHome":"$KOSMOS_HOME"` with the closing quote as part of the anchor. `bundle_is_ours()` gains a second leg: if `Contents/MacOS/Kosmos` is NOT a regular text file containing the old token, check for the new anchor in `Contents/Resources/kosmos-install.json` instead, gated on the JSON file also being a regular non-symlink file. This keeps old bash-launcher installs recognized (no forced reinstall) while proving ownership of new binary-launcher installs the same anchored way, not a weaker one.

**Finding 2 -- how a compiled non-JS binary gets into a Kosmos bundle, precedented by `kosmos-tunnel`.** `tools/build-kosmos-bundle.sh:119-202`: the Rust connector is NOT built by this repo -- it is built by a separate repo (`kosmos-relay`), handed over with `.commit`/`.sha256` provenance sidecars, verified as a universal x86_64+arm64 Mach-O, copied into the stage, and Developer-ID signed **in the build that produces the final shipped bytes** (not earlier, not by the relay build) using `KOSMOS_CODESIGN_ID` (defaults to the same `Stone Syndicate LLC (864QZ69GF2)` cert this session already has). `release.sh:9b` then re-verifies the SERVED bytes carry that exact signed sha256, not just the tested tree's.
  - **Why the app does NOT need the tunnel's cross-repo provenance machinery**: the tunnel lives in a separate repo because it is, structurally, a separate product boundary. The Swift app's source (`native-app/prototype/main.swift`, to be promoted out of `prototype/` once wired in) already lives IN this repo. `build-kosmos-bundle.sh` already refuses to package a dirty tree (`:358-362`, "its bytes would come from no commit anyone can name") -- that guard alone gives an in-tree-compiled binary the same provenance guarantee the tunnel needs sidecars for, with no sidecars needed.
  - **Design**: `build-kosmos-bundle.sh` compiles `native-app/main.swift` with `swiftc` as part of the SAME build that stages everything else (mirroring the dirty-tree-pinned guarantee, not the cross-repo sidecar mechanism), stages the result at `app/bin/kosmos-app`, code-signs it with the existing `_codesign_id`, and confirms the signed binary actually runs (`--version` or equivalent, the same "prove it loads under hardened runtime on this build machine" step already done for the tunnel at `:193`). Arm64-only, matching the bundle's own `LSArchitecturePriority arm64` / `LSRequiresNativeExecution` -- no lipo universal-binary requirement, unlike the tunnel which must run on both architectures.
  - `install/setup.sh`'s `build_app_bundle()` then copies `$KOSMOS_HOME/app/bin/kosmos-app` to `Contents/MacOS/Kosmos` (replacing the heredoc write at `:1860-1904`) and writes `Contents/Resources/kosmos-install.json` (the `KosmosInstallConfig` shape: `kosmosHome`, `ownerUid`, `port`) instead of baking those three values into shell text -- the #664 foreign-account logic and the "kosmos start failed" dialog wording move from the bash heredoc into the Swift `resolveInstall()`/`startBoard()` code already proven in phase 2, verbatim copy for the dialog text.
  - `release.sh` gets a `9b`-shaped check for `app/bin/kosmos-app` mirroring the tunnel's served-vs-tested sha comparison (`release-freeze.sh:146-172`), so a served app binary that silently drifted from what was tested is a release-time refusal, not a quiet ship.

## Phase 3 sequencing (each step proven and committed before the next, same discipline as phases 1-2)

1. `build-kosmos-bundle.sh`: compile + sign `native-app/main.swift` into the staged bundle, prove the signed binary runs on this build machine. No installer wiring yet.
2. `bundle_is_ours()`: implement the `kosmos-install.json` anchor leg, prove BOTH shapes are recognized (a hand-built old-style bash-launcher bundle, and a hand-built new-style binary bundle) and that a bundle carrying NEITHER anchor is correctly refused (the actual failure mode this function exists to prevent).
3. `build_app_bundle()`: copy the binary + write the config file, replacing the heredoc. Full local install: fresh sandboxed install produces a real signed `.app`, opens, loads the board, and the ownership-proof round-trips on reinstall/uninstall.
3a. **Found running step 3's own verification, not anticipated in the design above**: `tools/test-install.sh` hangs. Real gap, documented below, fixed as part of step 3 before it counts as done.
4. `release.sh` 9b-style served-vs-tested check for `app/bin/kosmos-app`.
5. Notarization for the standalone binary (separate from the `.pkg`'s own notarization -- Gatekeeper needs this so a copy of the `.app` outside the install path does not need an online check on first launch).

## Step 3a -- `tools/test-install.sh` assumed a script, not a GUI process (found and fixed)

Running the real harness against step 3's build hung for 38 minutes before being killed and diagnosed. Root cause, confirmed by process inspection (`ps` showed the compiled `Kosmos` binary as a live direct child of the harness, 38 minutes old) and by the harness's own log once read (it had been silently buffered the whole time by an unrelated `| tail -200` in how the run was launched -- a self-inflicted observability gap worth naming: piping a long-running background command through non-follow `tail` hides all progress until the pipe closes, so "no output yet" proved nothing either way):

`tools/test-install.sh:405` runs `KOSMOS_HOME="$SB/fakehome" "$SB/apps/Kosmos.app/Contents/MacOS/Kosmos" > /dev/null 2>&1`, directly, synchronously, waiting on its exit code -- exactly right for the old bash launcher (starts the board, exits). The compiled binary never exits: on success it runs the AppKit event loop (a real window, staying open, which is the entire point of #677); on the failure path this specific case exercises (`fakehome` has no real `bin/kosmos`), it reaches `showStartupFailureAlert`'s `NSAlert.runModal()`, which blocks until a person clicks the dialog -- and nobody can, in a headless harness. Phase 2's own verification notes already said "the app stayed alive blocked on the error dialog rather than crashing" as a feature; the same fact is exactly what breaks a test that waits on exit code.

**Blast radius, checked precisely rather than assumed**: only `tools/test-install.sh:345,405,407,415` touch the REAL built launcher path (`$SB/apps/Kosmos.app/Contents/MacOS/Kosmos`) at all. `:345` (`[ -x ... ]`) is unaffected and passed. The other three, plus the ~35-line block around them (`:395-438`, the #664 account-guard regression test), need rework:
- `:405` exec-and-wait-for-RC cannot work on a process that never exits by itself; the launcher must run detached, its `KOSMOS_APP_LOG` polled for the log line that proves the state (already emitted by the Swift code for every branch, from phase 1/2's own logging), then explicitly terminated (SIGTERM) once confirmed -- verified by observable effect, not exit code.
- `:407` (`grep -q "KOSMOS_PORT:-$PORT"` against the launcher file) assumed baked-in TEXT; the equivalent fact now lives in `kosmos-install.json`'s `"port":` field and gets checked there instead.
- `:414` `sed`-patches the launcher's TEXT (baked uid) to synthesize a wrong-owner negative control without needing a second real macOS account -- this is what actually threw `sed: RE error: illegal byte sequence` against the compiled binary. The same technique works unchanged against `kosmos-install.json`'s `"ownerUid":` field instead (still plain text, still `sed`-patchable), fed back in through the `KOSMOS_APP_CONFIG` env override the Swift code already reads for exactly this kind of test substitution (phase 1/2's own testing hook, never planned for exactly this reuse but built the right shape for it).
- Everything else in the file constructs its OWN synthetic/foreign `Kosmos.app` fixtures by hand (hardcoded bash text, never executed, only grepped as an inert fixture) to test `bundle_is_ours`'s negative cases -- those never touch the real launcher and are unaffected; confirmed by the 23 PASSes recorded before the hang, none of which regressed.

Not deferred: shipping step 3 without this fixed leaves the installer's only real end-to-end regression suite unable to run to completion at all, on the exact surface Splinter flagged for full scrutiny.
