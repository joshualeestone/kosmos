## Findings

- [WARNING] docs/browser-checks/render-chatbox-phone-4108.js:315. Rebinding `window.pjFitRoomPhone` does not switch off two of the five callers: `window.visualViewport.addEventListener('resize', pjFitRoomPhone)` (web/index.html:77746) and `window.addEventListener('resize', pjFitRoomPhone)` (77754) were registered with the original function object, so they still run the real fit. Measured: after the forced setup, dispatching a `resize` on `window` sets `--pj-room-fit` back to `399px`. Today nothing fires a resize during the walk (measured empty in all four arms), so the case is sound by luck, not by construction. Scenario: a later change that makes the tour or the dimming change the visual viewport (a scrollbar gutter on a non-overlay-scrollbar runner, an `isMobile` URL-bar emulation change, a Playwright upgrade that fires a resize on scroll) silently re-fits the room mid-walk; the forced arm then reads "the tour asks to make room" red for the wrong reason, or the room is re-fit between the Conversation step and the measurement. Fix: disable the fit at the one input every path reads, not at a name, e.g. `Object.defineProperty(PJ_ROOM_PHONE, 'matches', { get: () => false })` (the real function then removes `--pj-room-fit` on every call, whichever reference called it), or inject a stylesheet that pins `body:not(.consolidated) #pj-room.thread { min-height: 26rem !important; max-height: min(62vh, 44rem) !important; }`. Either way, add an assertion after the walk that `--pj-room-fit` is still empty (or the computed max-height is the unfitted one), so a re-fit reds as "the forced layout did not hold" instead of as a make-room failure.

- [WARNING] docs/browser-checks/render-chatbox-phone-4108.js:307 to 325. The forced case is decided by a 6px margin: the tour's scroll is `scrollBy(0, -6)` (measured, both engines), i.e. the Conversation card is flat because it is 6px short of room, and the scroll is only allowed because `scrollIntoView` happened to leave `scrollY` at 25 (>= 6). Nothing in the setup makes the shortfall large; it is whatever the 26rem fallback, the card's text height and the header heights add up to. Scenario: a copy edit to the Conversation step's body, a font or line-height change, or a different font stack on a runner shortens the card by 6px or moves the column down; the card then points without help, the forced arm reds "the tour asks to make room" and the control reds "the Conversation card is flat", for a reason unrelated to the make-room code. It fails red, not green, but it will look like a regression of #4108 and send someone to the wrong code. Fix: make the shortfall deliberate and large, e.g. after switching the fit off set the room's min-height so the column's bottom sits well below the card's needed line (computed from `innerHeight`, the room's top and the card height), and print the measured shortfall and `scrollY` as a MEASURE line so a red can be read at a glance.

- [WARNING] docs/browser-checks/render-chatbox-phone-4108.js:325 to 333. The forced arm drops two assertions the ordinary project-tip walk makes (lines 268 to 287): that the walk covered all four steps (`w.steps.length === 4`) and that only the Conversation step scrolled (`w.scrolled.every((t) => t === 'Conversation')`). Scenario: in the forced layout a change makes Members or Files also go flat and scroll; the forced arm stays green because it only requires that the list INCLUDES Conversation and that every step finally points, so "a pointing card is never moved" is unguarded in the one case where the make-room code actually runs. Fix: add both checks to the non-control arm (and the step count to the control arm too, so a missing Conversation step reads as such rather than as `conv` undefined).

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:309. The forced contexts register no `pageerror` listener, unlike the box phase (line 205). A page error thrown during the forced walk (for example from code that expects `pjFitRoomPhone` to return something) would not be reported. Fix: collect `pageerror` and `chk(errs.length === 0, ...)` as the box phase does.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:30 and 303. "the room's pre-#7196 layout" overstates the stand-in: only the room's height cap is removed; the rest of the current layout (#7272's header step-aside, the taller composer from this card) is post-#7196. The measured shortfall is 6px where the original #4108 report was 2px, so it is a similar squeeze, not the same one. Fix: say "the room with its #7196 height fit switched off" rather than "pre-#7196 layout".

The new comments say nothing about this; a reader may assume both engines are guarded. Fix: one line in the #7312 comment that WebKit is by-hand only (both pass today, measured).
