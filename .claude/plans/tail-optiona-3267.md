# tail-optiona-3267 -- message bubble tail: rebuild to the approved Option A + width cap

Addresses #3267. Refs #3244 (Josh picked Option A), #3247 (shipped, drifted). Josh 2026-09-18: the live tail "is not the right iMessage thing you showed yesterday" / "the graphic shows the messed up version"; also "message widths... too wide on both sides."

## Root cause
The approved Option A mockup (scratchpad/bubble-mockup.html, render bubble-options.png) draws the curved wing OVERLAPPING the bubble box, which is what makes the curve tuck under the corner and read as the Apple flick. The mockup used a SOLID tint, so overlap was fine. The app's user bubble was a TRANSLUCENT `--usermsg-tint`, so an overlapping wing double-composites into a darker triangle (#3130/6.72). #3247 dodged that by shrinking the wing onto a tiny no-overlap mask -> squished notch. My first #3267 attempt (bigger no-overlap) still rendered as a thin nub. Proven via the REAL-APP render tool: no-overlap cannot reproduce the curve; overlap-on-translucent shows the dark triangle.

## Fix (web/index.html)
1. **Option A overlap geometry** (matches the mockup): `.msg-bd::before` = colored wing 20x20 at left/right:-8 (overlaps 12px INTO the box), radius 18px 16px, z-index:-2; `.msg-bd::after` = **--k-surface** ground mask 14x22 at -14, radius 12px 16px, z-index:-1 (the visible curve is carved by this mask, not the ::before radius -- see the code comment at the rules); tail-side bottom corner 6px.
2. **BOTH bubble-fill tokens made SOLID/opaque in EVERY theme** so the overlap wing (background-color:inherit) does NOT double-composite into the #3130 triangle. `--usermsg-tint`: light `#e8ebf5` (:120), dark `#141c2f` (:330 + generated forced-dark twin :7655), navy `#1a2d58` (:7800). `--agent-msg`: light `#f4f1ea`, dark `#221f1a`, and **navy `#1b2a4b`** (:7802, was translucent `var(--k-sunk)` -- iter3 caught this; the wing double-composited it on navy). Each is the ~.10/.15/.08 wash baked to an opaque hex over its theme's --k-bg; the exact values are what Josh approved on the white render (2026-09-18). Not a byte-match of the old translucent-over-ground (one opaque token can't match every ground it serves: .dm.mine/.pj-msg on --k-bg vs the room on --k-surface), imperceptible in light. Guarded by server.test.js "every bubble-fill token is opaque". Reverses #2660's translucent tint (reversible design call; superseded Angel's #3264, DM `.dm-b` reads the token too).
3. **Width cap**: `.msg-bd { max-width: 52ch }` (:4758) so messages sit in from both edges. Previously only `#panel-detail .msg-b { max-width: 66ch }` (tab view) capped it; the consolidated view had NO cap -> full-width bubbles (Josh's "too wide on both sides"). The base cap covers both views.
4. **WHITE ground on BOTH views** (Josh 2026-09-18, verbatim "the background... whether it's on the consolidated view or the tab view, to be white"): tab `.thread` already --k-surface (#2711); consolidated `.pjmid` (:4196) + its `.composer` (:4231) flip --k-bg -> --k-surface (reverses #980's cream). BOTH tail carves `.msg:not(.you) .msg-bd::after` (:4819) AND `.msg.you .msg-bd::after` (:4820) are the GLOBAL rule at --k-surface, so carve == ground == --k-surface on both views and both themes -> no dark tail sliver (the operator's-own-tail sliver Angel's opus pass caught is covered here by construction).
5. **Agent cream** `--agent-msg` (light) #f9f7f1 -> **#f4f1ea** (:114), the approved-mockup Option A value. On the white ground the old cream dissolved; #f4f1ea reads as a clear subtle bubble. Dark stays #221f1a; **navy changed** to opaque #1b2a4b (see point 2 -- it was translucent and had to go solid for the overlap wing).
