# codexlock8-5434: the codex config.toml writers take one lock, and the trust append is flushed (#5434 slice 8)

Addresses #5434. `engine/create.js` has exactly two writers of the person's `<codexHome>/config.toml`
(measured: no other engine file writes it): `trustCodexFolder` (read, then `appendFileSync`) and
`forgetCodexFolder` (read, edit, `writeSecret` + rename, since slice 7). Neither takes a lock, so a trust
append that lands between a forget's read and its rename is lost (a lost update: the new agent's folder is
untrusted and its codex blocks on the trust dialog, #245). And the append is never flushed (#5431).

## Change
- Both functions run their read-check-write under `filelock.withFileLock(cfg)` (`config.toml.lock`).
  trustCodexFolder makes the codex folder FIRST (it always did before appending; a key already present
  implies the folder exists), so its lock always has a folder. forgetCodexFolder runs unlocked when the
  folder does not exist (trust.js `withWriteLock`'s shape, inlined so the busy sentence is ours), so its
  "there is no codex config to change" answer is not masked, and it creates nothing.
- trustCodexFolder stays an APPEND (`openSync(cfg, 'a')`, write, `securewrite.flushOrThrow`, close), and
  `securewrite.syncDir` on the folder when the append created the file. Both helpers newly exported.
- Lock busy: forgetCodexFolder answers `{ ok:false, removed:false, because:<sentence> }`; trustCodexFolder
  throws an Error with a sentence (every caller already catches; ensure-trust shows the message). remove.js
  reports a non-"changed by hand" ok:false as the step failing, which is true.
- An entry already present answers before the folder and the lock, unlocked, as before, so a re-trust that
  changes nothing never waits on or fails on the lock; the locked append checks again (review 1).
- A config.toml the append creates is 0600 (it was the umask's, usually 0644), the default forgetCodexFolder
  already uses for this file beside auth.json (review 1). An existing file keeps its mode.
- New `engine/create.codexlock-5434.test.js` (10 tests), in `tools/windows-tests.js` mid-list.

## Tests
- the append is flushed after it is written; the append that creates config.toml flushes its folder (POSIX);
- a second trust writes nothing; both writers release the lock;
- a held lock refuses both writers with their sentences and config.toml is unchanged;
- a trust run at the forget's read (the interleave) is refused, or if it reports success its entry survives:
  never silently lost;
- a forget with no codex folder answers as before and makes no folder;
- a re-trust of a trusted folder answers at once with the lock held (review 1);
- a created config.toml is 0600 and an existing one keeps its mode (POSIX, review 1);
- the interleave arm asserts its refusal is the lock's sentence, not any throw (review 1);
- a failed flush (EIO) refuses the trust and releases the lock.
- Mutation: slice 7's create.js (no lock, unflushed append) fails 5 of 8 (flush, folder flush, held lock,
  interleave, flush failure). Related set (64 files, list5434s8.txt): 2025 tests, 2022 pass, 3 skipped, 0 fail.
- Mutation (review 1): dropping the fast path fails the re-trust arm; dropping 0o600 fails the mode arm.

## Decided
- **Append, not a whole rewrite through writeSecret.** codex itself writes config.toml (its trust dialog, model
  choice) and does not take our lock. An append (O_APPEND) cannot lose codex's concurrent edit; a read plus
  rename can. The forget has to rewrite (it removes lines), and keeps slice 7's writer.
- **The lock covers Kosmos writers only.** It does not and cannot stop codex's own writes racing a forget.
- **A lock dir `config.toml.lock` appears briefly in the person's codex folder** beside auth.json; trust.js
  already does the same in ~/.claude. A stale one is stolen after LOCK_STALE_MS as everywhere else.
- **Folder flush after a first-ever append** (the file was just created): POSIX only, best effort.

## Weakest premise
That a 2 s lock wait (filelock LOCK_WAIT_MS) failing a create's trust step is acceptable where before it never failed. The holder is
another Kosmos create or remove touching the same file for milliseconds, so a timeout means a stuck holder.
What would change my mind: a caller that holds the lock across a slow step.
