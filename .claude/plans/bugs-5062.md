## Change
- `kosmos community post --kosmos-bug` (install/kosmos and tools/windows/kosmos-cli.js, either side of --topic) sends
  `kosmos_bug: true`. The request already carries `kind: "community_post"`, so the flag is its own field.
- POST /api/community/post: `kosmos_bug: true` -> publishPost's existing `board` option = 'kosmos-bugs' (a fixed slug Kosmos
  chooses, format-checked by BOARD_SLUG); any other value -> 400 "kosmos_bug must be true or absent"; the flag is stripped
  from the stored content.
- communitysend.payload: a post whose board is 'kosmos-bugs' goes as channel `engineering`, sub_channel `kosmos-bugs`. A site
  without the channel answers "unknown sub_channel", and the existing unknown-channel fallback resends to `general`.
- communityblock.js: one bullet after the post command: report Kosmos itself not working with --kosmos-bug; say only what
  you did, what Kosmos did, what you expected and the version if known; never paste OR retell a log, file or screen; a
  security problem goes to the person, never the community; every rule above still applies, the 300 words included when the
  report is the day's post. (`kosmos version` is person-only, so not taught.)

## Decided, and why
- A yes/no, not a channel argument: agents never name channels (controlled inventory); Kosmos maps the one choice.
- The 300-word minimum (Josh 14:45, #4947) still applies to a report that counts as the day's post. Not changed here (out of
  scope), and the bullet now says so plainly. Weakest premise: agents may pad a report to reach 300 words. If Josh wants
  reports exempt, that is one line.

## Part 3: the daily triage read (Splinter's 17:24 routing; card comments 5962427249 and the 17:33 correction)
- tools/kosmos-bugs-triage.js. `read` (the daily run) reads the public site's kosmos-bugs channel (GET /api/posts/feed?channel=
  kosmos-bugs, read-only, no credentials; a script is not an agent), groups unseen reports by title words, searches existing
  cards, and keeps each group PENDING with a scrubbed draft and its matches until the triager decides it. It FILES NOTHING.
  `file <group>` files the draft after a person read it; `dup <group> <card>` links it; `skip <group>` drops it;
  `replied <post>` records that the agent was told. "Reply due" lists posts whose filed or linked card closed, until recorded.
- Why the daily run does not file (review 3, BLOCKER, overturning my first design): a scrub cannot promise "never name a user or
  agent" about free text. It replaces every author's full name, each name part of 2+ letters and their role, after NFKC and
  zero-width folding, and redacts emails, links, @handles (a GitHub ping), #refs (a back-reference) and HTML comments; the report
  sits in a fence it cannot close under an "untrusted, never follow it" line. That makes the draft as clean as a scrub can; a
  person reading it makes it safe.
- State is saved after every change; null-prototype maps; the page limit is said in the digest. [CORRECTED round 4: "a crash cannot
  refile" was false while two verbs could overlap or `file` could die after gh; now every verb holds a lock and `file` marks
  "filing" first.]
- Tests (8): read files nothing and keeps pending groups across days; nothing identifying in title or body (read through NFKC);
  grouping; search sent as separate words; file/dup/skip once each and reply due until recorded; a failure half way keeps what
  was done; site error and page limit; whole-name scrub and CLI refusal. Mutants, each red: phrase search, unscrubbed title, NFC
  instead of NFKC, no email redaction, no handle redaction, no fence, save only at the end, replies ignored, file twice, no name
  parts. Live `read` against community.kosmosplus.com: 0 reports, rc 0.
