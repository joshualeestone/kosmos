# tkface-2762: the project member-faces list refreshes after a profile-image update

Card: #2762. Branch: `tkface-2762`. Author: April. Date: 2026-09-11.

## The defect

`tkFace` (web/index.html) rendered a **bare** `/api/agent/<name>/avatar`. That URL is
byte-identical before and after a picture change, so `paintProjectTasks`'s repaint
skip (`html !== TK_LIST_HTML`) fired, the `<img>` was never recreated, and the face
kept showing the old picture while grid and list (which rebuild their imgs every
poll) updated.

This is the same class #2698 fixed on the org chart, found by that card's own
challenge-loop review.

## The fix, which is the #2698 pattern and deliberately not a new one

- **Producer** (`engine/projects.js`): the member row carries `avatarVer`.
- **Consumer** (`tkFace`): appends `?v=` so the markup differs when the picture does.

The avatar route is already `no-store`, so a recreated `<img>` refetches. **The fix
only has to make the HTML change.**

### Why the producer line is a pass-through, not a store read

`status.js` (#2698) already puts `avatarVer` on the card, gated on `tied`.
`projects.describe` receives those cards, so this carries an already-gated value
rather than reading `store.avatarVersion` a second time. Two derivations of one
fact is this repo's stated worst habit; this avoids adding one.

`|| 0` keeps a card that predates #2698 harmless: `?v=0` is the stable no-picture
value, which is also what the initials path would have wanted.

## 🔑 The mutation result worth reading, because it nearly went the other way

Four single mutants, each alone with a green control between:

| mutant | arms killed |
|---|---|
| revert the page to a bare URL | 7/9 |
| **hardcode `?v=1`** | 8/9, killed ONLY by the two-render arm |
| producer drops `avatarVer` | 7/9 |
| **remove `projects.js`'s own `isNamedOurs` gate** | **9/9, SURVIVED** |

That survivor is the #2717 signature: a guard no mutation can kill is usually dead
code wearing a safety comment. **So I checked the other one.** Removing the
*producer's* `tied` gate ALSO survives 9/9. Removing **both** turns the stranger arm
red.

⇒ **These are genuine defence in depth: two independent gates, either sufficient.**

⭐ **A single-mutation battery structurally cannot distinguish that from one real
guard plus one dead one**, because whichever gate you remove the other still holds
the property, so both survive and neither looks load-bearing. **The double mutation
is the only experiment that separates them**, and it is the difference between
shipping a true disclosure and a false one in either direction. #2717 is the case
where the same experiment found the opposite and the guard really was vacuous.

The re-gate is kept for the reason the line above it re-gates `hasAvatar` (which
`status.js` also already gates): `describe(project, roster, all)` takes its roster
from the **caller**, so this file re-gates every name-keyed read rather than
trusting whichever producer supplied the cards.

## Two defects in my own first draft of the tests, both caught by running them

1. **`store.saveAvatar` was called AFTER `fleet.install`.** `install()` runs the real
   producers and builds the cards *then*, so an avatar written afterwards was
   invisible and `hasAvatar` came back false. The arm failed on its own
   precondition, which is what a precondition is for.
2. **The two renders used project names containing `Math.random()`**, so they
   differed because of the NAME. That arm passed while proving nothing about the
   avatar, which is the exact vacuity it exists to rule out. It now uses a fixed
   project, and additionally asserts that substituting B's version back into A's
   markup makes the two identical, so a difference from anything else fails it.

⚠️ Note that (2) passed while (1) failed. **Had I written only the "changes" arm, I
would have shipped a green vacuous test.** The arm that caught it was the boring
presence check whose precondition happened to be honest.

## Browser coverage, and the gate that made me add it

⚠️ **An earlier version of this section said the opposite and was left standing after
the commit that fixed it.** It said "no browser check observed a `?v=` URL" and "I
judged that out of scope". Both were true when written and false by the end of the
same commit. A reviewer caught the contradiction. Corrected here rather than quietly
deleted, because a plan that disagrees with its own branch is worse than no plan.

**What happened:** the repo's `#1720` gate refused the change, because it touches
`web/` and updated no `docs/browser-checks/` assertion. It was refusing exactly the
gap I had just written down. The gate offers a `Browser-check:` trailer as an escape;
using it would have been documenting the hole instead of closing it.

**Why no browser check could see this before:** no project-member fixture has an
avatar, so every check rendered the INITIALS path and the member-face URL was never
looked at in a browser. The surface had 1863 passing assertions and none of them
could see the defect.

`render-alltasks` now seeds a real avatar for its fixture member before the server
boots and asserts the rendered `src`. Measured, both arms:

| | result |
|---|---|
| fix in place | `PASS  /api/agent/tasker/avatar?v=1789108885626` |
| bare URL | `FAIL  /api/agent/tasker/avatar` |

plus a vacuity guard, so the version assertion cannot pass by rendering initials.

📌 **Two later corrections to that arm, both from review:** it matched `?v=\d+`, which
accepts `?v=0`, and `?v=0` is exactly what a dropped `avatarVer` produces, so the arm
would have greened on the failure it was added for. It now requires a NON-ZERO
version. And its selector had a fallback to an unscoped `.tkcard .lav img`; this
file's own header records that the page behind also renders `.tkcard`, so the
fallback could silently measure the wrong screen and still pass. Removed.

⚠️ **One thing the surface annotation does NOT buy.** I added `tkFace` to the check's
`Browser-check-surface` tokens. The gate keeps only `+`/`-` diff-body lines, so that
token fires when a line CONTAINING `tkFace` changes (a signature, a call site) and
NOT on an edit to the function body, which is where this defect lived. Measured with
a positive control. The token is still worth having; it is not coverage of the body.

## The fix was PARTIAL, and the sweep that found the rest

I shipped `tkFace` and stopped. That is the "repairs one of two call sites" failure,
and a review found it independently at the same time I did.

The question worth asking of every avatar emission, and the only one that matters:
**is its output painted through an identical-HTML skip, or assigned straight to
`innerHTML`?** `setIfChanged` IS `setLive`, which is `if (el.__lastLive === html)
return;` -- the same mechanism as `TK_LIST_HTML` and `ORG_HTML`.

| renderer | paint path | verdict |
|---|---|---|
| `tkFace` | `TK_LIST_HTML` guard | fixed |
| `pjMember` | `setIfChanged` -> `setLive` | fixed |
| `projectCard` | `setIfChanged(list, pjTreeRows(active))` | fixed |
| `addAgentsHtml` | `setLive(box, addAgentsHtml())` | fixed |
| `paintOrg` | org chart | already versioned (#2698) |
| `pjRoomRow` | `paintThreadInto` -> `setLive` | **still bare, carded #2770** |
| `lrow` | `getElementById('alist').innerHTML = ...` | clean, rebuilt every poll |
| `busyRow` | `el.innerHTML = busyRow(...)` | clean, rebuilt every poll |

#2698 asserted in prose that grid and list rebuild every poll. I checked rather than
trusted it, and it holds.

## 🛑 The invariant file made, twice, the exact mistake it exists to prevent

`web.avatarver-2762.test.js` was written because #2698 fixed the org chart and #2762
was the same bug found months later: the class needs something that asks the question
of ALL renderers, not four separate arms.

**First version: the pattern was vacuous and its control hid that.** It required
`/api/agent/` and `/avatar` to be contiguous; most renderers build the URL by
concatenation with quotes between the halves. Reverting BOTH `tkFace` and `pjMember`
left the file 6/6 green. The control passed because I wrote it against a
single-literal URL **no renderer on this page uses**. ⭐ **A control has to resemble
its subject; one that does not certifies the blind spot rather than finding it.**

**Second version: it claimed to cover "every renderer, including ones nobody has
written yet" and was a hardcoded four-name array.** A known-broken fifth
(`pjRoomRow`, #2770) sat outside it, the file was green, and nothing told a reader
anything had been excluded. A reviewer caught it. That is the same self-deception the
file was written to prevent, one level up.

**It now enumerates every emission and requires each to be CLASSIFIED** (behind a
skip, or an allowlisted direct assignment, or known-broken WITH a card number). A
renderer nobody has written yet fails the sweep until somebody says which kind it is.
The `KNOWN_BROKEN` entries additionally fail if the renderer is ever FIXED, so an
exclusion cannot outlive its reason.

Two bugs in that sweep, both caught by its own guards rather than by me:
- it matched `fetch('/api/agent/<n>/avatar', ...)` calls as emissions (the closing
  quote of an argument looks like the closing quote of a bare `src`), so it reported
  two false positives. Now restricted to lines that build an `<img>`.
- emissions are built ACROSS LINES, so a per-line `<img>` filter found only 3 of 5
  renderers. **The "at least four" guard is what caught that**, which is the whole
  reason to assert a floor on what a sweep finds.

## Weakest premise

**That `projects.describe`'s callers all supply cards from `status.snapshot`.** I
traced `safeRoster()` to `snapshot()` and confirmed both of its producers set
`avatarVer`, so the pass-through is not inert. But `describe(project, roster, all)`
takes the roster as an argument, and a future caller could supply cards from
somewhere else; then `|| 0` degrades to a permanent `?v=0` and the staleness returns
**silently**, with every test still green because they all go through the same
producer. That is the shape I would look at first if this recurs.
