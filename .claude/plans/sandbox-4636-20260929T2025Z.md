# sandbox-4636: a sandboxed shell is told the board is running but out of its reach (#4636, #4580 item 10)

Built on top of #4622 (sendsafe-4466, Baron), which fixes the proxy half (#4635) with loopback NO_PROXY/no_proxy
and `_listener_is_our_board`. My arms were run against #4622 and pass (#4635 comment 5897980282). This branch adds
only the sandbox half, which #4622 does not cover.

## Finished looks like
- In a sandbox that blocks connections even to 127.0.0.1 (measured with macOS `sandbox-exec (deny
  network-outbound)`): `kosmos status` says the board is running but this shell cannot connect to it, exit 5;
  `start` (person or agent) says the same and starts nothing; `post` and the other verbs say why nothing was sent.
  No verb says "not running", gives start advice, or blames another app.
- A truly hung board is still recovered by the watchdog's start (Liu Kang's caution, m3594).
- Outside a sandbox nothing changes; a stopped board is still "not running" at once.

## Cause (measured on main 5d26fa568 and on #4622 087bf0149)
In the sandbox curl cannot connect at all (curl 7, the same code as "refused"), which the probe reads as nothing
listening. `/bin/ps` is denied, so `port_listener_owner` and `running_pid` (and #4622's `_listener_is_our_board`,
built on them) come back empty, and `start` says another app holds the port. lsof still works there.

## Change
- `_health_refused`: after one re-probe half a second later (so a board that starts listening in between answers
  instead of reading unreachable), curl 7 while lsof shows an IPv4 listener on 127.0.0.1:PORT or *:PORT is HEALTH_STATE
  `unreachable` (an IPv6-only socket really refuses 127.0.0.1, so it is not evidence). An unrestricted shell connects
  to such a socket; a hung process still accepts on it, so a hang stays a timeout (busy) and its recovery is
  unchanged. The words: "Kosmos is running" only when the listener's pid (lsof) is the one this install recorded
  in board.pid (board-run writes it; read without ps); anything else is "something (name) is listening ... it may
  be Kosmos", and start refuses rather than calling it running.
- A start with KOSMOS_RECLAIM_BUSY=1 (the watchdog, setup.sh after pausing the board) FAILS on unreachable: it cannot
  see whether the old board stopped, so succeeding would let an update report success over a stale board.
- `restart` refuses on unreachable before stopping anything, in a sandbox (ps denied): it would restart the board
  inside the sandbox. In an ordinary shell (a local network fault) it goes ahead: stop works by the pid there.
- A start that launches the board from a blocked shell (the board was stopped): a board started from a SANDBOX
  inherits it (no outside connections for it or its agents), so when the new process is the listener this shell
  cannot reach, on two readings in a row, AND ps is denied here (positive evidence of a sandbox), it is stopped
  again, its pidfile removed, and the start fails with "start it from a normal Terminal". Without that evidence
  (a local network fault, which a normal Terminal's board has too) it is left running and the start says this
  shell cannot reach it (was: 30 tries, then "did not come up"). Under launchd (no pid; the board runs outside the shell) the
  start says it started but cannot be used from here. Tested (the STOPPED arm).
- `unreachable` in every verb: `say_not_up`; `status` exits 5; `start` returns before any reclaim; `board-run`
  does not launch (under launchd it exits 0 on each KeepAlive relaunch for as long as the fault lasts: two curls,
  two lsof, 0.5 s each time, silent); `stop` leaves it alone and writes no stop marker, with no pidfile and, in a
  sandbox, with one too (running_pid needs ps); the agent guard refuses stop/restart and
  answers start; `open` does not start one.
- `bin/board-watchdog.sh`: status exit 5 is "cannot tell from here": no start or kickstart, the down streak ends,
  logged once per spell (a marker file), cleared on any other answer. tools/test-board-watchdog-2955.sh arm 6u, with
  arm 6 as its control (red with the branch removed, measured).
- `cli.sandbox-4636.test.js`: every verb in the sandbox (status, start as person and agent, post, stop, restart,
  open, board-run, the watchdog's start), a non-node listener, the hung-board arms, and controls.

## Decided
- Exit 5, not 4 (busy) or 1 (down): the watchdog must not count it toward a restart.
- A person's `start` still clears the deliberate-stop marker first (#2955's load-bearing order). When it then finds
  the board unreachable and it is this install's board, the marker stays cleared: starting means "I want it
  running", and the board is. When it then REFUSES (KOSMOS_RECLAIM_BUSY=1, a listener that is not ours, or the board
  it launched from a blocked shell is stopped again), it started nothing, so it puts the marker back. An agent never
  reaches these lines (the guard answers first).
- A wedged board keeps its recovery: measured on this Mac (somaxconn 128), a listener with a full accept queue drops
  new connects silently, so curl times out (28, busy) and never gets the refusal (7) that reads unreachable. Tested
  (the full-queue arm).
- The watchdog does not escalate a long exit-5 spell. Under launchd it only sees 5 from a real local network fault
  (the TIME_WAIT-leak shape), where restarting cannot fix the kernel's state and would only black the board out;
  nothing reads its alert file for a person, so a person-facing alert would be a feature of its own.
- `open` exits 5 on unreachable in any shell, not only a sandbox: in an ordinary shell the cause is the machine's
  own local network fault, which the browser shares, so there is nothing to open from there either.
- No refusal advises starting or restarting: each says to run the command from a shell that can reach the board.
- `open` refuses with exit 5 even though the browser is outside the sandbox: opening an enforcing board needs a
  nonce minted over the network this shell does not have.
- `restart --force` refuses too on unreachable in a sandbox (setup.sh's `restart --force ... || true` from a
  sandboxed shell then does nothing, as it should: it cannot see the board it would restart); in an ordinary shell
  it goes ahead like any restart.
- A first cut (branch boardreach-4580) also added `--noproxy` to every curl; dropped in favour of #4622's
  loopback NO_PROXY/no_proxy, which covers the same arms (measured).

## Weakest part
- A board that starts listening between curl's refusal and lsof is covered by one re-probe after 0.5 s; one that
  takes longer to answer than that still reads unreachable for that call. Each refused probe now costs one lsof
  call, and one with a listener also the 0.5 s re-probe (also on the hook path while the board is down).
- A STRICTER sandbox (Sonya, m3799: `(deny process-info*)` too) kills curl itself with a signal (exit 133) and refuses
  lsof, so this shell sees nothing. It was read as "another app is using the port" (a person's own board). Now, with
  sandbox evidence (ps denied), a signalled curl or a refused lsof (return 2 from `_ipv4_listener`) is `unreachable`
  with no listener named, "Kosmos may be running, but this shell cannot check": status exits 5, start/stop do
  nothing. It says the same when nothing listens: that shell cannot tell, and a start there would launch a board
  inside the sandbox (#4655). Without sandbox evidence a signalled curl keeps the old reading, stranger.
  Tested, each route on its own: the curl-signal route by STRICT arms (status on a live board and a free port,
  start, stop) with a BLINDLESS control that is red; the lsof-refused route by LISTPIDS arms (`deny
  process-info-listpids`: curl refused with 7, lsof refused; round 23's measurement) with an LSOFLESS control (only
  that hook removed) that is red; and `_health_blind` both ways. stop in a "cannot check" shell says "cannot be
  stopped from here", never "not started by this command". Weakest: only two seatbelt profiles measured; a refused lsof is matched on its words
  "Operation not permitted".
- Measured only with macOS `sandbox-exec`; a sandbox that blocks lsof WITHOUT the ps denial keeps the old "down" reading, and so does
  a dual-stack or IPv6 bind (KOSMOS_BIND_HOST=::), which the IPv4-only lsof filter leaves out.
- The kill-or-keep decision in `_await_board_up` is tested with the real function and stubbed readings (no
  sandbox evidence: the board is left running and the start returns 0; with it: the process is stopped and the
  start fails; under launchd: two readings end the wait). The sandbox detector itself was checked both ways.
- `restart` now probes once before stopping: on a hung or busy board that is up to about 2 s more.
- The lsof on every refused probe, measured here at load 7.5 (2026-09-29): 0.034 s per lsof call, and a whole
  `kosmos status` on a stopped board 0.086 s. So "not running" stays effectively instant, and the hook's 12 s budget
  is untouched in practice; a stalled machine is bounded per kernel call by -S 2, not per run.
- Not fixed here (follow-up card #4651): setup.sh's pause check is a plain curl, which a sandboxed shell cannot make, so it
  reads a running board as paused and replaces the app and plist under it before failing loudly at the final
  `start --force`. The stale-board state is still reached, only no longer reported as a success. The pause's
  post-condition should be the CLI's status (exit 5 here). This predates the branch.
- NOT covered, the more common sandbox: one that allows 127.0.0.1 but blocks the internet. Every command reaches the
  board there, so nothing reads unreachable, and a `start` of a stopped board launches one that inherits the
  sandbox and cannot reach any AI provider. Guarding it means refusing to launch any board from a sandboxed shell
  (ps denied), a behaviour change beyond this card: follow-up card #4655.
- Under launchd, a start that cannot show the listener is ours (two readings) fails with "launchd was asked to start
  Kosmos, and this shell cannot confirm it did"; only this install's recorded board reads as started.
- A sandbox that blocks loopback connections but still lets /bin/ps run (not a macOS seatbelt profile) gives no
  sandbox evidence: `restart` there stops the board by its pid and starts a new one inside that sandbox, which is
  kept ("started, but this shell cannot use it") though it cannot reach any AI provider. Not a regression (the
  base restarted into it too), and not measured: no such sandbox was at hand.
- The sandbox detector (ps denied, twice 0.2 s apart so a passing fork failure is not one) means "under a macOS
  seatbelt profile", measured: any profile denies setuid
  /bin/ps. Combined with unreachable that is "a sandbox blocks this shell", which is what the kill needs.
- The per-verb sandbox arms (stop, restart, open, board-run, the watchdog's start) have no removed-branch control
  each; their assertions were checked against what each verb does without its branch (stop: writes the marker and
  says "not running"; restart: stop's "left alone" message; open: not exit 5; the watchdog's start: "another
  app"), all of which the assertions reject. Reasoned, not run. board-run is NOT covered: without its branch it
  still exits 0 (lsof finds the listener), so its branch only saves a probe and its arm cannot fail.
