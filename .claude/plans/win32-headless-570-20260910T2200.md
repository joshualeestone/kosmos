# win32-headless-570 -- Kosmos on Windows runs with no window to close (#570)

Addresses #570. Road: `.claude/plans/WINDOWS-ROADMAP.md`. This blocks the 7c-6
reboot test (R8) and v1.

## What happened

After the 7c-6 rehearsal (R1–R7 all passed), all three rehearsal agents died with
exit code 0xC000013A (STATUS_CONTROL_C_EXIT). Josh then said: "I closed out some
windows that had popped up."

## Measured on the box (2026-09-10)

- A task set up exactly like a Kosmos agent's (InteractiveToken, the current user)
  that runs `node.exe` directly **opens a new visible Windows Terminal window**
  titled `...\node.exe`. The process tree is `svchost (Task Scheduler) -> node`.
  Closing that window kills node with 0xC000013A. That is what killed the agents,
  and it also accounts for `winstream-1` and `winreh-2` dying the same way this
  morning.
- The same task running `C:\Windows\System32\conhost.exe --headless "<node>" <args>`
  opens **no window at all**, and node runs normally under the headless conhost.
- ⚠️ BUT `schtasks /End` / `Stop-ScheduledTask` on the headless task kills the
  conhost and **leaves node running** (it was still alive 10s later). Kosmos's own
  stops rely on `/End`: `win32job.end` for agents, and `win32board.end`, which is
  inside the board's End -> wait -> Run restart. So headless alone would orphan
  processes.
- A node that checks every 1s whether its parent pid is alive
  (`process.kill(ppid, 0)`) and exits when it is gone: after `/End` of the
  headless task, node **exited in about 2s**.

- Under `conhost --headless`, node's command line has its quotes REBUILT: none
  around an argument without spaces (`supervisor-boot.js reh-c C:\...\reh-c - -
  claude ...`). The question was whether a path WITH spaces survives, since a
  username like `C:\Users\Josh Stone` is ordinary. Measured through a real task:
  a script in `space dir\argv probe.js`, handed `"has space" "plain" "C:\a b\c" "-"`,
  received exactly those four arguments. Only unneeded quotes are dropped.

## Design

1. **`win32job.headlessExec(exec, env)`** is the ONE wrapper. The command becomes
   `%SystemRoot%\System32\conhost.exe` (`SystemRoot` from the env, defaulting to
   `C:\Windows`), and the arguments become `--headless "<the old command>" <the old
   arguments>`. Both `win32job.taskXml` (agents) and `win32board.taskXml` (the
   board) build their `<Exec>` from it, so the wrapping is derived once.
2. **`engine/win32orphan.js`, `exitWhenParentGone`.** It polls whether the parent
   pid is alive and calls `onGone` once when it is not. EPERM counts as alive. It
   never throws and its timer is unref'd.
   - The supervisor's `main()` arms it: when the parent is gone it runs
     `handle.stop()` (which closes the agent's stdin, so the agent exits ~800ms
     later), then does a hard exit after a grace period.
   - The board arms it when its task started it (`win32board.startedByTask()`),
     and exits.
   - Under an OLD, windowed task the parent is Task Scheduler's svchost, which
     never exits, so the watchdog does nothing and the change is safe for tasks
     registered before it.
3. Tasks already registered on a box keep their old definition until they are
   re-registered. Nothing ships to users on Windows yet (v1 is unreleased), so
   there is nothing to migrate. On this box the tasks are re-registered by hand
   as part of the live check.

## Tests

- `win32job.test.js` and `win32board.test.js`: `<Command>` is the headless
  conhost under `SystemRoot`, `<Arguments>` start with `--headless` and carry the
  quoted node and script, and escaping still holds.
- `engine/win32orphan.test.js`: it exits when the parent goes; EPERM is alive; it
  fires only once; `stop()` cancels it; a throwing `onGone` does not escape.
- `win32supervisor.test.js`: `main()` arms the watchdog, and when the parent is
  gone it stops the agent.

## Measured on the box afterwards

Re-register this box's tasks with the new definition, then check three things:
- starting a task opens no window;
- `/End` still stops the supervisor AND its agent;
- the board's restart still ends with exactly one board.

## Found in review round 1, and live on the box

Headless makes the OLD supervisor outlive `/End` by up to ~1s, and three things
did not account for that overlap:

- **W1, restart's channel.** `/End` then `/Run` starts a new supervisor while the
  old one still holds the named pipe. The new listen fails with EADDRINUSE as an
  async event, and `serve()` swallowed it, so the new supervisor ran with no
  channel. Fixed: `serve()` retries a busy pipe every 250ms for up to 30s and
  reports any other listen error via `onProblem`, which `main()` writes to the
  task log.
- **W2, remove.** Remove's `/End` is followed by the agent's taskkill. The
  still-running old supervisor saw its agent die and relaunched it, so a removed
  agent was back for 1-2s, owned by nobody. Fixed: `superviseStreaming` asks
  `mayStart()` right before every launch, and `main()` answers "is my host alive".
- **W3, state file (found LIVE, not by the reviewer).** After a restart, `reh-b`'s
  card read UNKNOWN. The old supervisor's stop deleted the state file BY NAME,
  after the new supervisor had written its own. Fixed: `clearState(name,
  ownerPid)` deletes only a file that still carries the stopping process's pid.
- Conventions:
  - two doc blocks had landed above the wrong function;
  - the EPERM case now has a test (`pidAlive` takes an injected kill);
  - the unref test now asserts `hasRef() === false`;
  - `win32stop.aliveFromError` now uses the one rule in `win32orphan`.

Live on the box after round 1, all five agents and the board ran headless.
Every Kosmos stop path (`/End`, restart, remove, restore, the board's End -> Run)
ended with exactly one supervisor and agent per agent, and exactly one board.
**No window appeared across two full runs.**

## Weakest part of this reasoning

Pid reuse: if the conhost's pid were reused by an unrelated process within one
poll interval, the watch would miss the death. Windows reuses pids slowly, but
the cost of a miss is real. The supervisor would survive the stop with
`running = true`, `mayStart` would still read the host as alive, and a remove's
taskkill would be answered with a relaunch. The removed agent would stay up
until someone ended it again. It is unlikely, but it is not harmless.
