# talk-gutter-3497: the Talk box reaches the right edge on a Mac that shows scrollbars (#3497)

## Problem (Josh, 0.6.91 QA, 2026-09-24 10:00, target screenshot with red bands)
#3586 fills the Talk box to the header, the right edge and the bottom, measured in a headless
browser at 1400 wide. On a Mac set to show scrollbars (Josh's, per the #1309 note), html's
`scrollbar-gutter: stable` (#1309) reserves a 15px strip down the right edge, so the box stops short
of the window edge. Reproduced headless at 1000x660: box right 985 in a 1000 window. That run's headless Chromium
reserved the gutter; later runs on the same machine overlaid scrollbars (width 0), so the geometry
red is runner-dependent.

## Decision
Exempt the wide Talk view from the gutter (`scrollbar-gutter: auto`): the page never scrolls there,
so the gutter only holds an empty strip. To keep #1309's promise (the header does not move between
views), a head script measures this Mac's scrollbar width (at load, and again on resize, pointer press, focus and the Windows stamp) into `--scrollbar-width` (0 with overlay
scrollbars, ~15px when shown), and every wide view pads the header's right side by that width less
the width the page gives up there (superseded the Talk-only padding in iteration 12, see below). The
header's controls and centred tabs sit at one x on every view. Narrow width scrolls, so
it keeps the gutter. Both new rules are scoped to `html:not([data-layout="consolidated"])`, as
#1309 is: with the consolidated layout chosen, data-layout stays on html even on an agent's page and
no gutter is reserved anywhere, so padding the header there would itself make it move.

## Rejected
- Removing the gutter everywhere: reintroduces #1309's page shift on long Settings panes.

## Rejected (added in review)
- Dropping the gutter in Talk only, with no compensation: the header jumped 15px (controls) and 8px
  (tabs) on every open/close of an agent on a scrollbar Mac, the #1309 complaint itself.

## Weakest premise
A1n forces a 15px classic scrollbar with a `::-webkit-scrollbar` style so every runner reserves a
real gutter. That is a Chromium custom scrollbar, not the macOS system one; the premise is that the
gutter and the probe see the same width either way. Corrected in review (iteration 10): an earlier
version of this plan said A1n could not run headless; render-win32-board-copy already showed
headless Chromium draws scrollbars once `--hide-scrollbars` is dropped.

## Verification
render-talk-fill-2622: A1b now measures the box against window.innerWidth (html's clientWidth hides
a reserved gutter, which is how the 1400-wide arms passed while Josh saw the strip), plus the edge
arms at Josh's window size 1000x660. Control: against origin/main A1b red at every size (box right
1385 vs 1400, 985 vs 1000) in a run where the headless runner reserved the gutter; under overlay
scrollbars the geometry arms cannot see the strip, so the runner-independent guards are A1m
(computed scrollbar-gutter per view) and A1o (a synthetic 15px scrollbar width).
Iteration 10: A1n runs in its own browser with real 15px scrollbars at 1000x660 (box right edge and
header no-move across board, Talk, Model), with a precondition arm so it cannot pass vacuously. A9c
asserts the wide Talk page does not scroll at 440 tall.
Iteration 12: A1n also runs in WebKit. Playwright's WebKit does NOT reserve `scrollbar-gutter: stable`
on a root that does not overflow (board header at 976 vs Model at 961 there), so padding only the
Talk header moved it between board and Talk in that engine. Decision: every wide view pads the
header by `--scrollbar-width` less the width the page actually gives up there
(`100vw - 100% - 2 * --space-8`), so the controls sit at one x whether or not an engine reserves the
gutter. Rejected: padding Talk only (engine-dependent, shown by the WebKit arm). Weakest premise:
whether the real Mac app's WKWebView reserves the gutter is unknown; the formula holds either way,
which is why it was chosen over guessing. It also assumes body padding stays --space-8 on wide
views. The measurer skips engines without scrollbar-gutter (A1s).
Iteration 14, the trade-off stated: in an engine that reserves no gutter on a page that does not
scroll (Playwright's WebKit), short wide pages get 24px + the scrollbar width of header padding, so
the header's controls sit 15px inside the content edge below them and the tabs about 7px left of
the body centre. Accepted over the alternative, Talk-only padding, which in that engine makes the
header jump 15px between the board and Talk (main already jumps between the board and a scrolling
Model there). Josh's report (a strip on Talk) says his engine reserves the gutter, and there the
two designs render the same: every non-Talk view gives up exactly the scrollbar width, so its
padding is the plain 24px. Deferred: the formula assumes 100vw includes a reserved root gutter;
the JS alternative (innerWidth - clientWidth) cannot work because clientWidth hides a reserved
gutter (measured: 1000 on the Chromium board with the gutter reserved). A1n guards both pinned engines.
Iteration 15 + render-full-width (a check outside this branch's set, run against a sandboxed board):
main 28/28, this branch 20/28. The measurer read an element's scrollbar (0 in a runner that hides
scrollbars) while the root still reserved a 15px gutter, so every wide header shifted 15px off the
content and the tabs 7px off centre. Decision: measure the root's own reservation (force
`scrollbar-gutter: stable; overflow: hidden` on html, read `innerWidth - html width`, restore, all in
one task so nothing paints). That is the value the formula needs by definition. Result: full-width
28/28; Chromium unchanged (15px); Playwright's WebKit reads 0, so its non-scrolling pages keep the
plain padding and stay aligned with the content, and the iteration-14 trade-off is gone there. What
remains in that engine: on a page that really scrolls, the header sits 15px right of the content
edge (padding 24 - 15) so that it does not jump. Weakest premise: html's layout width excludes a
reserved root gutter in every engine we ship on; A1o and A1n read the same quantity and pass in both.
