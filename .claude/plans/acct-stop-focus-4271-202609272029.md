# acct-stop-focus-4271: focus stays in the dialog when a Claude sign-in panel is put away

Card: kosmos#4271 (the #1918 stranded-focus class).

## Measured before building
On origin/main, acctFlowPaint's flow-ended branch hides #acct-flow and never moves focus. The
new browser check's control arm (page without the fix) reads document.activeElement = BODY after
Stop and after a failed poll while typing the code.

## Change
- web/index.html acctFlowPaint: read `flow.contains(document.activeElement)` before hiding the
  panel; if focus was inside and the phase is not 'connected', call acctFocusAfterFlow(btn).
- acctFocusAfterFlow: focus "Start the sign-in" (#acct-add) when it is enabled and rendered,
  else the provider picker's .pcombo-trigger (the fallback acctMuseShow uses).
- Connected is left alone: acctShowSuccess already focuses #acct-success-close.

## Call, and what I rejected
Target is #acct-add, not the picker the card suggested. It is the button right above the panel,
re-enabled in the same branch, and it is where the person starts again; Muse's own Stop does the
same (focuses its Go). The picker stays as the fallback. Rejected: the note (#acct-add-note,
tabindex -1): it is a live region already, and focusing it would announce the sentence twice.
Weakest premise: the picker fallback is not exercised by the browser check (no natural state
hides #acct-add while the panel is open). What would change my mind: a state where #acct-add is
hidden with the flow running, which the check should then cover.

## Tests
- docs/browser-checks/render-acct-stop-focus-4271.js: stubbed sign-in routes, real buttons and
  poll. Arms: Stop, failed-from-code-field, Connected. Each arm asserts focus was inside the panel
  before acting. 13/13 with the fix; control without it: arms 1 and 2 read BODY, arm 3 green.
- web.connect-success-1656.test.js: fake panel gets contains() => true on Connected; mutation
  (drop the connected guard) turns it red with ReferenceError.
