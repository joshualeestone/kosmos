## Scope (this PR)
1. fedseal: the two-way exchange (card comment 6381388572, superseding the one-directional code):
   ownCommit, ownHelloFrame/checkOwnHello (hello carries H(nW)), ownOfferFrame/checkOwnOffer (owner nonce nO),
   ownRevealFrame/checkOwnReveal (nW, checked against the commitment), compareCode over (room, mac, both keys,
   nW, nO), ownShareFrame (refuses unless the confirmed code matches the run) / openOwnShare (only from the
   confirmed owner key, bound to the run's nonces).
2. fedseats (every own frame must carry the relay's same_account stamp, kosmos#4657): own computer records keyless member seal state marked own on its first unopenable sealed message
   (posts held, never clear), runs the exchange on each connect, takes the FIRST offer only (nW revealed once),
   opens a share on arrival and keeps only a genuine one, adopts it only after its own person confirms
   (confirmOwn; ownStartOver for "does not match"), takes rotations from its pinned key. Seal owner: answers
   hellos with offers, lists a computer only after its reveal opens its commitment (ownWaiting, memory,
   bounded 16), allowOwn pins in st.own; a pinned key that says hello again runs the whole exchange again;
   sendRotates covers st.own. configure gains macId; server.js wires it.
3. server: GET own-waiting, POST own-allow (owner); GET own-compare, POST own-confirm (waiting computer). All behind
   the federation switch, screen only; the two POSTs step-up gated and under the family policy.
4. #5191 writer guard re-decided for noteOwnSealed, allowOwn and adoptOwnShare.

## Not in this PR (part B)
- UI rows (waiting computer's code; owner's Waiting list with Allow), with design shots.
- Lifting the two 409s (ownCodeRefusal 'sealed', invite 'self-shared'): after the coordinator half
  (relay ownseal-4658-v2) is merged and deployed.
- Two-board rig test.
- HARD REQUIREMENT before the 409s lift: an own computer must learn its room is sealed before its first post
  (today it posts in the clear until it sees a sealed message; unreachable while the 409s stand).
- Removing an own computer from st.own (a retired or stolen machine keeps getting rotations), and one forged
  envelope locking an unsealed own room: kosmos#7028. It must land before the 409s lift.
- Stated residual (graceAfter/revokeCheck count st.own as somebody left): with every guest revoked and an own
  computer allowed, the old key keeps its grace, and a removed guest's post in that window is refused only by the
  relay's member stamp (isRevokedPost), as it already is whenever guests remain.
- Stated residual (OWN_RUNS_PER_HOUR bounds guesses): anyone carrying the relay's same_account stamp (the owner's
  own computers, or a hostile relay) can spend a room's hourly budget and keep the real computer waiting for the
  hour. Availability only; the relay can already drop every frame.
  The same sender can also wipe a computer's revealed row by repeating its key with a fresh commitment (one run of
  the budget each); keeping the old row would instead block that computer's own genuine new run.
- Several waiting rows can share a `mac` (a copied commitment shows its own, different code): the UI must tell rows
  apart by more than the mac.
- The `mac` shown beside a waiting computer is the sender's own string (bounded to 128 characters, any
  characters): the UI must render it as text, through the same cleaner as other names from outside.
- The UI must show the code large on both screens and make comparing it the action; the code a route accepts
  binds the press to the run shown, it is not the authentication.

Inert in production until part B: behind the federation switch, and the 409s keep own computers out of
sealed rooms.
