# dailylog-chain-5855: the daily-log compiler reads a rolled-over conversation whole

Card: #5855, step 2. Step 1 (#5878) made the compiler refuse the whole run on any sign of a rollover. The rollover
itself (#5841 piece 2, #5875) is on main now, so the chain can be read. Stacked on `dailylog-asides-5866` (#5899),
because both change `engine/dailylog.js`; rebased onto main once that merges.

## Done looks like

1. A conversation that the real writer rolled over compiles: every day it had before the rollover is byte for byte
   what it was, the day after is added, and every message is in the days exactly once.
2. A chain that cannot be followed whole still refuses the run, and no day file changes.
3. Nothing changes for a folder with no `.full` file and no `continues`.

## Measured before building

- `chat.asideChain(projectId, agent, ...)` reads only Kosmos's own chats folder (`threadFile`), and the compiler is
  given a folder (`opts.chatsDir`; all its tests pass one). So the compiler cannot call it for a folder it was handed.
- `chat.chainRows(earlier, currentRows, currentCarried)` is a pure function over rows. It can be called as it is.
- `asideChain` keeps what it read when a link breaks. For a view that is right. For the compiler it is the hazard of
  step 1 again: the days before the break would be rewritten short and pruned.
- A full file's rows are filtered (`text` a string) before `carried` is applied; the current file's are not
  (`readThread`). The compiler does the same on each side.
- An earlier project's thread file that had rolled over keeps `continues` when it is set aside as `.superseded`, and
  its `.full` files keep the thread file's name in front. A later project's fresh file does not continue them.

## The change (`engine/dailylog.js`)

1. **`followChain(chatsDir, base, key, parsed)`** walks `continues` from a thread file (or a `.superseded` copy of
   one) by asideChain's rule, in the folder given, and says whether it reached a file that names no earlier one
   (`complete`).
2. **`readConversations`** follows every conversation file that names an earlier one. A conversation is compiled
   whole when its chain is complete, every file in it was in the listing, and no other conversation's chain holds
   the same file. Its rows are then `chat.chainRows(...)`, and its `.full` files are reported in `chainFiles`.
   A `.full` file no chain reached that is byte for byte a file a chain of the same thread did reach counts as read
   too (review round 1): the writer leaves one when a rollover is interrupted after the hard link, and nothing ever
   removes it, so without this one interruption would refuse every later run. It holds only while the two names are the
   same bytes: if the full thread file is changed between the interruption and the next message (a reaction or a
   delivery state on one of its rows), the first name differs, is not counted, and the run is refused (round 2,
   measured by the reviewer). That is the safe side, and it stays refused until someone removes the file.
3. **The refusal narrows, it does not go.** `rolledOverFiles` is now the `.full` files no complete chain reached;
   `continuedFiles` is the conversation files whose chain was not followed whole. Either still refuses the run.
4. **The refusal's words** (decided here, once; later objections to wording that is true in every state are
   duplicates of this decision):
   - `Files whose names end in .full after a conversation file's name, which no conversation file led this tool to:`
   - `Conversation files that refer to an earlier file this tool could not follow all the way back:`
   - `This tool does not compile while a file listed here is present, and it changes none of them. It compiles a
     conversation that reached its message limit only when it can follow every earlier file from the conversation's
     own file. They can be Kosmos's own files, so do not move or delete one unless you know that it is not Kosmos's.`
   The middle sentence states the tool's rule, not why these files are as they are; the tool cannot tell.

## Rejected

- **Calling `chat.asideChain` directly.** It cannot read a folder it is handed, and making it take one means
  changing a function in the conversation writer's file for a tool nothing runs yet. The rule is restated instead,
  and a test compares the two on files the real writer made (one rollover, and two).
- **Compiling what a broken chain did yield.** That rewrites days short. Refuse.
- **Treating an unreached `.full` file like #5866's unreadable files (hold the prune only).** The day that straddles
  the break would still be rewritten short, which the prune-only rule does not cover. Refuse.
- **Reading a `.full` file two conversation files both reach.** Its rows would be in a day twice. Refuse.

## Decided in review round 1: a current file damaged after a rollover

The writer sets it aside as `.damaged` and the fresh file continues from the newest `.full`. The chain is complete,
so the conversation compiles; the rows only the damaged file held (those written after the rollover) are not read.
The day they share with the full file's rows is written without them, and a day only they were on is kept from the
prune. Before this change that folder was refused.

- **Chosen:** compile, exactly as #5866 treats any `.damaged` file. Pinned in a test named KNOWN LIMIT.
- **Rejected: refuse while the thread has a `.damaged` file newer than its newest `.full`.** Nothing ever removes a
  `.damaged` file, so the daily log would stay off for every conversation until that thread rolls over again,
  about a thousand messages later. Three versions of #5866 that froze days to protect such rows were each found to
  be worse than the loss.
- **Weakest part of this call:** the day of a rollover is the day most likely to be shared, and the rows lost are
  ones an earlier compile had written. What would change my mind: the tool being wired to run on people's
  machines before unreadable rows are handled for every conversation, rolled over or not.

## Known and left to `engine/chat.js` (#5900)

A thread file with no `projectBornAt` that rolls over on a send that knows the project's date: the fresh file is
stamped, the full file is not, and neither `asideChain` nor this compiler follows the link. The compiler refuses
(nothing lost). A test asserts `asideChain` follows nothing there and says it is the one to change.

## Tests (`engine/dailylog.chain-5855.test.js`, 15 tests, 9 sub-cases; node counts 24)

Every rollover is made by `chat.appendMessage` on a full thread file. Against the compiler from before this change
23 of the 24 fail; the one that passes is the undated thread, which is refused before and after. Several of the 23
fail only because the summary has no `chainFiles` yet, so that count is not twenty-three separate proofs. The ones that carry the weight: compiles whole (days byte for byte, each message once);
two rollovers; the control (without the full file: refused, and from the current file alone two days pruned and one
rewritten short); nine ways a chain breaks; the orphan; the shared file; an earlier project that had rolled over.

`engine/dailylog.rollover-5855.test.js`: the pinned refusal words change, and the pin test loses its "the rollover
is not in this tree yet" arm. Its hand-made full files carry no `agent`, so those runs are still refused.

## Weakest part

The rule for following a file exists twice, in `chat.js` and here. The pin test checks five lines of `chat.js` by
text and the comparison test checks two real chains; a change to `asideChain` that keeps those lines and those two
results would not be noticed. Also not covered: a rollover that lands between the folder listing and the read of
the full file (the run is refused then, the safe way, because the file was not in the listing).

## What would change my mind

`asideChain` taking a folder, or the compiler losing its `chatsDir` option: then call it and delete `followChain`.
