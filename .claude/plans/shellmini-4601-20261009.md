# shellmini-4601: shell shards may run on the self-hosted Mac (#4601)

## Why (measured 2026-10-09, numbers on #4601)
Since 2026-10-08 12:00 UTC (60 test runs): the shell shards queued a median 56 and 77 min (p90 about 2 h) for
macos-latest and then ran about 26 min; the node part on the self-hosted kosmos-ci-mini queued 0 min and ran 5.2.

## Change
- test.yml scope job: a new repo variable KOSMOS_CI_SHELL_SHARDS ("1/2", "2/2", "1/2,2/2") routes each named shell
  shard to the same runner the node part gets ($mac). It inherits every #5488 rule: the switch KOSMOS_CI_RUNNER must be
  `on`, and only this repo's own code (push, or a PR whose head is this repo). Unset or anything else: macos-latest,
  exactly as today. Outputs shell1_runner and shell2_runner; the suite's runs-on picks per matrix.shard.
- tools/test-ci-runner-route-5488.sh: the wiring check pins the new runs-on and env; 8 new arms (unset, one shard, both,
  fork PR, switch off, a near-miss value). On main's workflow it fails 19 times.

## Decided
- A variable, not a code change, picks the split: the right number of shards depends on measuring a shard on the mini
  against its capacity (5 runs an hour at the busiest, node about 26 min of each hour).
- Start with ONE shard (1/2) once merged: by the node ratio (4.3x faster on the mini) a shard is about 6 min there,
  so one shard brings the mini to about 56 min an hour at the busiest; both would pass 60. The measured mini shard time
  decides whether the second follows.
- Mortals stays out (the release-cut box).
- Weakest premise: the shell tests are as safe on the CI user's home as the node tests are (they boot boards, use tmux
  and test the installer in sandboxes). The node part has run there for two days; a shell shard has not.
