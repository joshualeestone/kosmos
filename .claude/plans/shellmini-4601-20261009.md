# shellmini-4601: shell shards may run on the self-hosted Mac (#4601)

## Why (measured 2026-10-09, numbers on #4601)
Since 2026-10-08 12:00 UTC (60 test runs): the shell shards queued a median 56 and 77 min (p90 about 2 h) for
macos-latest and then ran about 26 min; the node part on the self-hosted kosmos-ci-mini queued 0 min and ran 5.2.

## Change
- test.yml scope job: a new repo variable KOSMOS_CI_SHELL_SHARDS ("1/2", "2/2", "1/2,2/2") routes each named shell
  shard to the same runner the node part gets ($mac). It inherits every #5488 rule: the switch KOSMOS_CI_RUNNER must be
  `on`, and only this repo's own code (push, or a PR whose head is this repo). Unset or anything else: macos-latest,
  exactly as today. Outputs shell1_runner and shell2_runner; the suite's runs-on picks per matrix.shard.
- tools/test-ci-runner-route-5488.sh: the wiring check pins the new runs-on and env; 16 new arms (unset, one shard, both,
  fork PR and switch off on both shards, near-miss and separator values).

## Decided (rewritten after review 3, which found the measurement I had missed)
- The shard time on the mini is ALREADY MEASURED (#5488 part b): shell 2/2 ran there in 14.0 min, 1.7x hosted, not the
  4.3x node ratio my first plan assumed. Node (5.2) plus one shard (~14 to 15) is ~20 min of the ONE mini per run: at
  the busiest (5 runs an hour) ~100 min of work an hour, and over the day (60 runs in about 20 h, ~3 an hour) ~60. So
  routing even one shard makes the mini the queue and slows node, the trade #5488's verdict already recorded.
- So the mechanism ships OFF (the variable unset; today's behaviour exactly). It earns its place when a second
  self-hosted runner with the kosmos-ci label exists, or for an off-peak window. The real fix for the shell queue is
  runner capacity (another Mac; Mortals excluded as the release box), which is a hardware call for Splinter and Josh.
- Known risk, from #5488's record, before anyone sets the variable: two mini-only shell 2/2 failures nobody explained
  (#5122 at 00:09 UTC, and #5485, which failed after 0.2 min). Shell shards DID run on the mini under part b (26 jobs
  drained there); the CI user's PATH was swept for every tool the tests probe except vercel.
- The red check: on main's test.yml the test fails 24 times, but only because the wiring raise stops before the step
  body is extracted. The real red checks are targeted mutants (review 3): dropping the $mac guard (2 FAILs), removing
  the 2/2 case line (3 FAILs), and s2 outside the guard (now caught by the new shell 2/2 arms).
- Mortals stays out (the release-cut box).
