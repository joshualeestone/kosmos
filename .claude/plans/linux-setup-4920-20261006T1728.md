# linux-setup-4920: Linux port piece D, the setup one-liner installs Kosmos on plain Linux (#4920, part of #4916)

Adopted by Ice Cream Kitty on 2026-10-06 (Splinter 15:08: the Mortals Gemini agents are out of quota). The original
author is Raiden (PR #4985), approved by Kano on 10-02. Rebased onto main on 10-06 with no conflicts (615 commits).

## What the PR does (from its description)
- Preflight accepts Linux (x86_64, aarch64).
- Finds tmux on Linux, or installs it with apt.
- Resolves a system node when the bundled runtime cannot run.
- Wires .bashrc or .profile.
- Skips the macOS app bundle and notes.
- Writes and enables a board systemd user unit, and enables linger.
- Adds a workflow that installs, starts, stops and uninstalls on ubuntu-latest.

## Change needed before review: one board unit, not two
- setup.sh writes its OWN kosmos-board.service in shell. Piece B (#4918, PR #4984) builds the board unit in
  engine/linuxboard.js, and B's review changed that unit in ways the shell copy does not have:
  - KillMode=process, so a board stop never kills the shared tmux server;
  - Restart=on-failure, because `Restart=always` restarted a stopped board every 5 seconds (measured on GitHub's
    ubuntu runner);
  - the system tmux path carried into the unit;
  - unsafe values refused.
- Two derivations of one unit drift, and the shell copy would bring back the restart loop.
- **Decided:** setup.sh calls B's `linuxboard.installBoard($KOSMOS_HOME)` through the node it has just resolved.
  This is also the production caller B deferred to D.
- Stacked on B's branch (2026-10-07 01:55; B's code was final, only its Mac CI run left), to be moved onto main
  (own commits only) once B squash-merges.

## Done on the stack (2026-10-07)
- setup.sh's Linux keep-alive step calls `linuxboard.installBoard($KOSMOS_HOME, $PORT)` through
  `$KOSMOS_HOME/runtime/bin/node` (the shell unit and the separate `loginctl enable-linger` are gone; installBoard
  turns linger on and reads it back). It says one of: will start when this computer starts (linger on); will start at
  login but stops at logout, with the loginctl line for an administrator (linger off); will not start itself (board
  off); or systemd's own reason when installBoard refused. A refusal does not stop the install (as before).
- `--uninstall` calls `linuxboard.removeBoard($KOSMOS_HOME)` before the app folder is deleted; with the app already
  gone it removes this home's unit by _kosmos_linux_unit_name (reviews 9, 15, 16) and names any other.
- The workflow checks B's unit (Restart=on-failure, KillMode=process, no Restart=always, enabled), that a stopped
  board stays stopped past RestartSec, and that uninstall leaves it disabled.
- install.linux-board-4920.test.js runs setup.sh's two node snippets (cut from the file) against a stand-in module,
  and pins that setup.sh carries no unit text. Planted: the old shell-unit setup.sh fails the snippet checks; the shell-block tests (added in review 2) catch swapped sentences, a lost prefix strip, and a restart of a board set off or already supervised.
- Harness fix (Splinter 18:53): install.reachable-1662 and install.claude-gate run setup.sh functions under
  setup.sh's own option line (set -eu; pipefail only under bash). Measured: dash refuses `set -euo pipefail`
  ("Illegal option -o pipefail") and accepts the setup.sh line; bash keeps pipefail under it.

## Carried here from #5419 slice 1 (its reviews 2, 3 and 23), for this branch or its next step
- **One tmux pick for sign-in and agents on Linux.** Sign-in (connect.tmuxBinPath) uses the launcher's tmux only when it
  runs, else create.linuxTmuxBin; agents (create.binPaths) use the launcher's value without checking it runs. A
  launcher bundle path that does not exist on Linux, with /usr/bin/tmux installed, signs in and then fails the first
  agent with ENOENT. install/kosmos's tmux pick needs a Linux branch (check it runs) so both read one value.
- **Alpine's musl Claude Code needs libgcc, libstdc++ and ripgrep** (Anthropic's docs): the installer should check or
  name them on musl.
- **The hand-off restart is only for a board systemd is not running (reviews 3 and 4):** after installBoard the snippet
  asks systemd (linuxboard.loadedBoardJob) whether the unit is active. On an update the start step already restarted
  it through systemd, so it is not bounced again; on a first install, or after an earlier run whose hand-off failed,
  it is handed over now. (Review 3 keyed this on the unit file existing, which missed that second case.)
- **The restart-loop check reproduces #4918 (review 3):** kosmos stop cannot show the loop (its systemctl stop cancels a
  pending restart), so the workflow marks board.stopped, ends the board with a plain TERM, waits two RestartSec windows
  and requires NRestarts unchanged and the unit not active.
- **Restart-loop check timing (review 4):** the NRestarts read is 12 s after the TERM, two RestartSec windows; a
  runner slow enough to restart after 12 s would read green vacuously. Accepted: a fixed wait on a real unit, not a
  poll on systemd timestamps; RestartSec is 5 s in B's unit.
- **A failed removeBoard still removes the unit (review 5):** uninstall deletes the app folder next, so the snippet
  deletes the unit file and its enable link itself when removeBoard fails (e.g. no user bus under su), as the shell
  code before #4920 did, and prints the systemctl line and path if even that fails.
- **No hand-off without linger (review 5):** without linger the unit dies at logout while the board setup.sh started
  survives it, so the hand-off restart runs only on 'loose lingering'; the unit stays enabled for the next login.
- **A launcher tmux pick is not written into the unit (review 5):** with KOSMOS_TMUX_BIN_PICKED=1 the snippet drops
  AGENT_WORKFORCE_TMUX_BIN before installBoard, so the unit does not freeze a per-run pick as a person choice.
- **A failed hand-off is said (review 6):** if kosmos restart does not bring the board back, the installer says so
  and names kosmos start, rather than ending on a success sentence with the board down.
- **Dropping the launcher tmux pick strands nothing (review 6, checked):** on Linux setup_linux_tmux symlinks the tmux
  it found into $KOSMOS_HOME/tmux/bin, the unit PATH lists that folder first, and install/kosmos falls back to
  $KOSMOS_HOME/tmux/bin/tmux when its own search finds nothing, so a tmux only on an odd PATH is still reached.
- **Behaviour change, accepted (review 6):** linuxboard.unitSafe refuses a HOME or KOSMOS_HOME containing $, %, a quote
  or a backslash, which the old shell unit wrote unchecked; such an install now gets no keep-alive and says so
  ("could not set itself to start with systemd" with the reason) instead of a unit systemd would misread.
- **The workflow runs the installer with sh (review 7):** people run curl ... | sh, and on Ubuntu sh is dash, so the
  install, uninstall and custom-home steps use sh install/setup.sh; the Mac test covers bash 3.2.
- **An update applies a changed unit (review 7):** Environment= reaches a running unit only at its next start, and the
  start step restarted the board before installBoard rewrote the unit; the snippet now also reports held-changed, and
  setup.sh restarts a board systemd runs once more only when its unit text changed (never when set off).
- **The workflow installs this checkout, not the last release (real-Linux run 37592812752):** the published bundle has
  no app/engine/linuxboard.js until B ships, so setup.sh truthfully said "could not set itself to start with
  systemd: Cannot find module" and left no keep-alive. The workflow now stages the bundle's file list from the
  checkout and installs it through KOSMOS_SRC. In production setup.sh and its bundle ship in one release, so the
  module is present; the refusal path is what an out-of-step pair would get, and it is said, not silent.
- **Uninstall removes a unit an earlier release wrote (review 9):** main's setup.sh (#4985, in 0.7.27) writes the shell
  unit and ships no linuxboard.js, so an uninstall by a newer setup.sh with the app present but older now removes that
  unit by the rule that wrote it (default home: kosmos-board.service; else sha256 of KOSMOS_HOME as typed, 8 hex):
  stop, disable, delete file and enable link, reload. This is the one place the old name rule stays, on purpose,
  because it is the rule those files carry.
- **No 'running now' after a failed hand-off (review 9),** the failed hand-off names board.log, a board set off with no
  systemctl is not said to have started, and a sandboxed uninstall says it skipped systemd on purpose.
- **One name rule in practice (review 10, measured):** setup.sh squeezes repeated slashes and strips a trailing one from
  KOSMOS_HOME and refuses a relative one, so the shell rule (hash of the value as typed) and linuxboard's (hash of
  path.resolve) give the same name for every home setup.sh accepts; only a . or .. component could differ.
- **Uninstall sets XDG_RUNTIME_DIR (review 10),** as install does, so removeBoard can reach the user bus under su or cron.
- **KillMode before an update pause (review 11; measured, see the end of this bullet):** the unit 0.7.27 wrote has no KillMode=, so
  systemd's default control-group kill would take the in-app update (a child of the board, in its cgroup) and the
  agents' tmux server with the pause. setup.sh now adds KillMode=process to this install's old unit and reloads,
  before the pause. The old name rule lives in one function, used by this and the legacy uninstall. Measured in the
  workflow (review 14): a step runs an old-format unit with a child process, CONTROL first (the stop kills the child),
  then setup.sh's own _kosmos_linux_unit_killmode on the running unit (the stop spares it). MEASURED on run 37600051076
  (952a3cfd7): "control: the old unit killed its child (cgroup kill)" and "fix: the child survived the stop".
