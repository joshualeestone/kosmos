# fsyncwrite4-5434: store.js saves flush before they rename (#5434 slice 4)

Addresses #5434 (slice 4). Slices 1 to 3 (merged) gave securewrite.writeSecret a flush before the rename, a
umask-default mode and own-temps-only reaping. This slice moves store.js's four writers onto it.

## Change
`engine/store.js`: one private helper, `saveFlushed(file, data)`, calls
`securewrite.writeSecret(file, data, modeOf(file), { atomicOnly: true, umaskDefault: true })`, where `modeOf` is the
existing file's mode (so it is kept) or null for a new file (the umask default, as `writeFileSync` gave).
- `writeProfile`: the per-agent profile (was a fixed `<file>.tmp`, unflushed).
- `mergeSettingsInto` (`writeSettings`, `writeSettingsIfReadable`): the account settings.json (same).
- `saveAvatar`: the agent's picture (was a dot-named random temp, unflushed).
- `keepAvatarOriginal`: the kept original before a refit (was copyFile then rename, unflushed). Its dest never exists
  when it writes, so it takes the umask default rather than the picture's mode (copyFile carried it); harmless.
- `removeAvatar` never takes a LIVE writer's temp in avatar-originals (`<key>.<...>.kosmos-...tmp` starts with the
  key, unlike the old dot-named temp), and takes a provably dead one (it holds a copy of the removed picture); it also
  reaps a dead writer's temp beside the picture in avatars.

Bytes written are unchanged (the same JSON.stringify(next, null, 2); the picture buffer).

## Decided
- atomicOnly: a failed save leaves the old file as it was and throws, as these writers already threw.
- Not ownTempsOnly: these folders (profiles, the data root, avatars, avatar-originals) are Kosmos's own, so reaping
  any provably dead writer temp there is right (slice 1's default).
- The temp name is writeSecret's `<file>.kosmos-...tmp`: the avatar lookup takes only `<key>.<ext>`, the profile
  listing only `*.json`, so a temp is never a picture or a profile.
- A leftover `<file>.tmp` from the old profile and settings writers, and an old dot-named `.<key>.<hex>.tmp` in avatars
  or avatar-originals, is not swept here (harmless: never read).

## Tests
`engine/store.fsync-5434.test.js`: each writer flushes the temp it renames into place; an existing file keeps its
mode and a new one takes the umask default; when every atomic attempt fails the old file is left as it was and the
save throws; the written bytes are unchanged; a temp is never taken for a picture or a profile (profile listers filter
`*.json`); removing a picture never takes a keep in flight.

## Cost (measured, review 4)
A save now flushes the file and its folder on the caller's thread: on this Mac (SSD) writeProfile went from 0.18 ms
(main) to 7.9 ms per save, writeSettings 8.7 ms (50 saves each, sandboxed store). Callers that save profiles in a loop
(adopt, worldstarts, doctrine, discover, the swarm patches in server.js) pay that per agent: about 160 ms for 20
agents, mostly at start-up or on a rare action. Accepted, as slices 1 to 3 accepted the same per-write cost, for a file
that a crash can otherwise leave zero-filled (#5431). Unmeasured on a slow disk or a Windows box with antivirus.

## Weakest premise
That every caller of these writers already handles a throw (they did: writeFileSync threw too). A caller that
relied on the in-place rewrite never existed here (the old code was write-then-rename too).
