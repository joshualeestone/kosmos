# #5406 Part 1: a Kosmos agent does not stop on a prompt the person's own ask rules raise

## Ruling
Josh, 2026-10-07 10:54 CDT (verbatim on the card): "On #1, i want it to override the safety rule and make it easy for end
user, not prompt white collar users with tech questions they wont understand." Splinter 10:57: mechanism is Angel's call;
never edit the person's ~/.claude/settings.json; Mac and Windows; arm B as the test. Reverses my 11:48 (10-06) rejection.

## Finished looks like
A Kosmos-launched Claude agent whose settings carry an ask rule (`Bash(rm *)`) runs the command with no prompt, on macOS,
Linux and Windows launches; a deny rule still blocks; the person's own settings files are not written; the person's own
Claude sessions (not launched by Kosmos) are unchanged.

## Change
- engine/agentpermission.js: a Kosmos-owned settings file in Kosmos's data folder with ONE PermissionRequest hook (posix
  shell form; Windows exec form, no shell, as the report hook #570). Written when missing or different, mode 600.
- engine/kosmos-permission-allow.js: the hook; allow, silent for AskUserQuestion and unreadable input, always exit 0.
- engine/agent-permission-config.js: the shim bin/agent-supervisor.sh runs (like agent-browser-config.js).
- bin/agent-supervisor.sh (macOS, Linux): `--settings <file>` on the Claude arm, only for an absolute existing path,
  before --dangerously-skip-permissions (after --mcp-config, which a flag ends).
- engine/win32supervisor.js + win32launch.js (Windows): spec.permissionSettings asked per launch; `--settings` for claude.

## Rejected
- Making the existing report hook (wired into the person's settings) answer allow: it fires in the person's OWN Claude
  sessions too, which would switch off their rule outside Kosmos.
- `--setting-sources project,local` for agents: drops everything in the person's user settings (connectors, hooks).
- Writing allow rules or additionalDirectories: measured no effect (an ask rule beats every allow rule).
- Auto-pressing "Yes" from the pane: the agent still stops until the board's next look, and races the screen.

## Decided after review 1
- Silent (the prompt shows as before) for AskUserQuestion and for anything touching a protected place (a .claude
  folder, .claude.json, .git), judged by the file path or the shell command's text. Measured P0/Q0: bypass mode does
  not prompt there today, so this changes nothing now; it keeps the hook from answering for that guard if Claude Code
  adds one, since the ruling is about the person's ask rules, not that guard.
- Claude also guards other folders (for example .vscode, .idea); the hook does not name them, and like .claude they
  are not prompted in bypass mode today.
- A long-running agent keeps the hook command it started with; if an update moves node or the script, the hook fails
  non-blocking and the prompt shows as before, until the agent restarts.
- ExitPlanMode is allowed: Kosmos runs agents unattended with no plan screen, so a plan waiting on approval only stalls.
- The hook also answers a MANAGED (employer policy) ask rule on a work Mac, which is a prompt the person could not have
  answered either; not measured. An org that sets allowManagedHooksOnly ignores this hook, and the agent prompts as before.

## Weakest premise
That PermissionRequest keeps answering for ask rules in future Claude Code versions (measured on 2.1.292 only), and on
Windows (same hook form as the report hook, but this hook was not run on a Windows box). The live test re-measures B/G/H.

## Not covered
- Codex, Gemini, Grok, Antigravity agents: their own approval systems (Claude only here, as the ruling's case).
- Agents already running keep their old launch until they restart.
- Part 2 (option buttons) stays the fallback for prompts this leaves silent (AskUserQuestion).
