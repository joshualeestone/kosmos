# win-inplace-acl-1765: Kosmos.exe refuses a run folder other people on the PC can change

**Posture:** production

Card: kosmos#1765 (Windows half). Kosmos installs itself into `%LOCALAPPDATA%\Programs\Kosmos` (MoveTarget,
#3286), inside the person's profile. A copy put somewhere deliberate (not Downloads, the Desktop, OneDrive or a
temp folder), with nothing installed, runs where it is (`RunInstallerDuties`), and every launch then runs
`runtime\node.exe` and `app\` from that folder. Outside the profile a folder usually inherits write access for
every local account (a folder made at `C:\` gives Authenticated Users Modify), so another person on the PC could
change the code Kosmos runs as this person.

## What changes
- `tools/windows/KosmosLauncher.cs`, `Main`: right after the launcher's own folder is known, BEFORE the uninstall,
  the window, the installer duties or anything else that runs node from the folder, `UnsafeRunFolderReason(here)`
  decides; a non-null answer is `RefuseUnsafeFolder`: a message box (or stderr with `--console`) and exit 1.
- `UnsafeRunFolderReason`: a folder inside the profile (`SpecialFolder.UserProfile`, a test seam
  `userProfileFolder`) is not read. Otherwise each folder from the run folder up to the drive is read
  (`Directory.GetAccessControl`, raw descriptor):
  - the owner must be this user, SYSTEM, Administrators or TrustedInstaller;
  - the run folder: no allow entry for anyone else may carry write data, append, write extended attributes,
    delete child, delete, change permissions, change owner, generic write or generic all; entries that reach
    only what is inside it count (that is where the code is);
  - a folder above it: only entries that apply to it, and only delete child, delete, change permissions, change
    owner, generic write or generic all (what would let someone rename the branch away and put another in place);
  - CREATOR OWNER and OWNER RIGHTS stand for the owner; a deny entry is never counted; an unreadable descriptor,
    a missing DACL (FAT, exFAT) or an ACE type it cannot read is a refusal.
- The message: "Kosmos will not start from <folder>, because other people who use this computer may be able to
  change the files in that folder, and Kosmos would run whatever they put there. Move the Kosmos folder into your
  Downloads folder and open Kosmos.exe from there. Kosmos then installs itself in a folder only you can change."
  plus a `Details:` line naming who can change what. The uninstall has its own first sentence and fix.
- `tools/windows/README.md` and the roadmap say so.
- The signed `Kosmos.exe` is rebuilt and re-signed as its own release step (as boardproof-win-1765 did).

## Decided
- **Refuse, not lock the folder down.** Kosmos never creates such a folder (the person extracted the zip there;
  setup.ps1 and the launcher only ever install into the per-user programs folder), so there is no moment of
  creation to set a safe ACL at, and by the first run the files may already have been changed. Rewriting the ACL
  of a folder the person chose could also take away access they meant to give. Refusing before anything runs
  matches the install design: the one place Kosmos installs to is already safe, and the refusal says how to get
  there (Downloads installs it, #3286). Would change my mind: an installer that lets a person choose a folder
  outside the profile, which would then create it with a safe ACL.
- **The uninstall is refused too**: it runs node from the folder. The message says how to uninstall (open the copy
  from Downloads once, which installs and re-registers it, then Settings > Apps).
- **Deny entries are ignored**, so the answer can only be stricter than Windows'.
- **Ancestors** are read only for the rights that let someone swap the branch; "add files" on a parent (C:\'s
  Authenticated Users entry) is allowed, since a new sibling folder does not touch this one.

## Weakest part (named)
- The run folder's own entries stand for its files: a file inside given extra rights on its own (which takes
  someone who could already change permissions there) is not read, to keep the check to a few milliseconds.
- A folder inside the profile is trusted by where it is; a junction from the profile to elsewhere is taken at its
  profile path.
- It guards launches through Kosmos.exe. A copy that already ran from such a folder before this change keeps its
  logon task pointed there until Kosmos is next opened from a safe copy; the board started by that task is not
  re-checked (code in that folder checking itself would prove nothing).
- An owner that is a different person cannot be made on this box without an administrator; that branch is
  covered by the source and the trusted-owner list, not by a live folder.

## Tests
- `tools.win-inplace-acl-1765.test.js`: the source (everywhere): the check precedes the uninstall, the window,
  the installer duties and every process start in Main; the rights masks and trusted SIDs; the wording. On
  Windows: a probe compiled beside the launcher reads real folders whose ACLs icacls sets (Users Modify, Everyone
  write, Authenticated Users on files only, Users delete-child, Users change-permissions: refused; Users read and
  run, a deny, a locked folder: safe; a parent granting Users delete-child: refused, naming the parent; a parent
  passing Modify down inherit-only, or granting add-file: safe; inside the profile: not read; a missing folder:
  refused). A launcher built from the source runs from real folders at the root of the system drive: refused in
  words, with the folder's own server.js never run, for start and uninstall, where Users can change it; started
  where it is locked down.
- Each check's test went red with it removed (eight mutations), then restored.
- Latency on the box: 7 to 15 ms per launch for a folder at C:\ (measured with the probe).
