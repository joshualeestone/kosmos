# win-inplace-acl-1765: Kosmos.exe refuses a run folder other people on the PC can change

**Posture:** production

Card: kosmos#1765 (Windows half). Kosmos installs itself into `%LOCALAPPDATA%\Programs\Kosmos` (MoveTarget,
#3286), inside the person's profile. A copy put somewhere deliberate (not Downloads, the Desktop, OneDrive or a
temp folder), with nothing installed, runs where it is (`RunInstallerDuties`): it points the Start menu, Settings
> Apps and the logon task at that folder, and the board and each agent run `runtime\node.exe` and `app\` from it.
Outside the profile a folder usually inherits write access for every local account (a folder made at `C:\` gives
Authenticated Users Modify), so another person on the PC could change the code Kosmos runs as this person.

## What changes
- `tools/windows/KosmosLauncher.cs`, `Main`: right after the launcher's own folder is known, BEFORE the uninstall,
  the window, the installer duties or anything else that runs node from the folder or points something at it,
  `UnsafeRunFolderReason(here)` decides; a non-null answer is `RefuseUnsafeFolder`: a message box (or stderr with
  `--console`) and exit 1.
- `UnsafeRunFolderReason`: a folder inside the profile (`SpecialFolder.UserProfile`, a test seam
  `userProfileFolder`) is not read. Otherwise (`Directory/File.GetAccessControl`, raw descriptor, SIDs only):
  - every thing read must be owned by this user, SYSTEM, Administrators or TrustedInstaller;
  - the run folder: no allow entry for anyone else may carry write data, append, write extended attributes,
    delete child, delete, change permissions, change owner, generic write or generic all; entries that reach
    only what is inside it count (that is where the code is);
  - the code inside that the launcher starts or points at, read on its own: `Kosmos.exe`, `runtime\`,
    `runtime\node.exe`, `app\`, `app\server.js`, `open-board.js` (a file another account made while the folder let
    them is theirs, and its owner can change its permissions whatever the folder says);
  - each folder above it up to the drive: only entries that apply to it, and only delete child, delete, change
    permissions, change owner, generic write or generic all (what would let someone rename the branch away);
  - CREATOR OWNER and OWNER RIGHTS stand for the owner; a deny entry is never counted; an unreadable descriptor,
    a missing DACL (FAT, exFAT) or an ACE type it cannot read is a refusal.
- The message: "Kosmos will not start from <folder>, because other people who use this computer may be able to
  change the files in that folder, and Kosmos would run whatever they put there. Download Kosmos again, extract
  it into <profile>\Downloads, and open Kosmos.exe from there. Kosmos then installs itself in a folder only you
  can change. Once you have next signed in to Windows, you can delete <folder>." plus a `Details:` line naming
  who can change what. The uninstall has its own first sentence and fix. The Downloads folder is spelled out as
  the profile's own: one moved to another drive is outside the profile and would be refused the same way.
- `tools/windows/README.md` and the roadmap say so, including the transition for a copy already running in place.
- The signed `Kosmos.exe` is rebuilt and re-signed as its own release step (as boardproof-win-1765 did).

## Decided
- **Refuse, not lock the folder down.** Kosmos never creates such a folder (the person extracted the zip there;
  setup.ps1 and the launcher only ever install into the per-user programs folder), so there is no moment of
  creation to set a safe ACL at, and by the first run the files may already have been changed. Rewriting the ACL
  of a folder the person chose could also take away access they meant to give. Refusing matches the install
  design: the one place Kosmos installs to is already safe, and the refusal says how to get there (a fresh copy
  opened from the profile's Downloads installs itself, #3286). Would change my mind: an installer that lets a
  person choose a folder outside the profile, which would then create it with a safe ACL.
- **"Download again", not "move the folder"**: a fresh download carries none of what others may have put in the
  folder, and a folder whose board is running cannot be moved.
- **The uninstall is refused too**: it runs node from the folder.
- **Deny entries are ignored**, so the answer can only be stricter than Windows'.
- **Ancestors** are read only for the rights that let someone swap the branch; "add files" on a parent (C:\'s
  Authenticated Users entry) is allowed, since a new sibling folder does not touch this one.
- **SIDs, not names**: a domain group (Domain Admins) is not one of the four; such a folder is refused, and a
  copy in the profile is the way round it.

## What it guards, and what it does not (named)
- It guards that this launcher never runs node, the uninstall, a hand-off or an update from such a folder, and so
  never points the Start menu, Settings > Apps or the logon task at it.
- It is NOT a boundary against a folder already changed: `Kosmos.exe`, and a `Kosmos.exe.config` beside it, come
  from that folder and load before the check.
- A copy that already ran in place from such a folder before this change keeps its logon task and in-app updates
  there; its Start menu entry now opens to the refusal. The fresh copy installs itself and repoints Kosmos, so the
  board starts from the installed copy from the next sign-in.
- Weakest part: below the six code entries, a file inside is taken at the folder's word (reading every file would
  cost far more than the few milliseconds this takes). A folder inside the profile is trusted by where it is; a
  junction from the profile to elsewhere is taken at its profile path.
- An owner that is a different person cannot be made on this box without an administrator; that branch is
  covered by the source and the trusted-owner list, not by a live folder.

## Tests
- `tools.win-inplace-acl-1765.test.js`: the source (everywhere): the check precedes the uninstall, the window,
  the installer duties and every process start in Main; the rights masks and trusted SIDs; the wording. On
  Windows: a probe compiled beside the launcher reads real folders whose ACLs icacls sets (Users Modify, Everyone
  write, Authenticated Users on files only, Users delete-child, Users change-permissions: refused; Users read and
  run, a deny, a locked folder: safe; node.exe or a cut-off app\ granting Users write in a locked folder: refused,
  naming it; a file below the six: safe, the named weak spot; a parent granting Users delete-child: refused,
  naming the parent; a parent passing Modify down inherit-only, or granting add-file: safe; inside the profile:
  not read; a missing folder: refused). A launcher built from the source runs from real folders at the root of the
  system drive: refused in words, with the folder's own server.js never run, for start and uninstall, where Users
  can change it; started where it is locked down. Assertions do not depend on the language of account names;
  folders a killed run left at the drive root are swept on the next run.
- Each check's test went red with it removed (nine mutations), then restored.
- Latency on the box: about 7 to 15 ms per launch for a folder at C:\ (measured with the probe).
