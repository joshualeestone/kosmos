## Finished looks like (this slice)
`engine/servicekeys.js` takes exactly the sets the relay verifier takes and refuses exactly the ones it refuses. Shown on the relay's published test vectors (same seeds, document bytes and signature), and by mutation: every guard FOUND whose removal changes an answer has an arm that turns red (sweeps in iterations 10 to 12 found the gaps, now closed). That is not a proof that none is left. Guards found shadowed by another check are listed in the log (the ones found, not a proof that there are no others). It is off as shipped: with RECOVERY_KEYS empty, no set verifies. It has no caller yet.

## Slices
1. (this) The verifier, plus matching the pinned coordinator key (base64url raw, as coordinator_pubkey holds it) against a set's SPKI keys.
2. The release ships service-keys.json(.sig) in the bundle (covered by the signed manifest; S-1 is live). The board compares the pinned key with it, and tells the PERSON on a mismatch with a state-only field on GET /api/remote, a fixed-sentence line beside the certificate watch in Settings, and a card in #topnotes (the cert-watch pattern, #6602/#6613). Not in remote.status().because, which is also sent to the coordinator, the party a mismatch suspects.
3. The tunnel (kosmos-relay, after #474 merges) refuses at setup and sign-in a service key that is not on the set.

## Decided
- JS mirrors the relay's rules where JSON.parse is looser than serde_json: a member named twice (at any depth, names compared after unescaping) is refused by a second walk of the bytes; seq is checked on its raw spelling, so 1.0 and 1e0 (which JSON.parse reads as 1) are refused; the .sig is strict base64 (padded and canonical); weak (small-order) keys are refused from libsodium's list, sign bit ignored.
- Rejected: reusing manifest-verify's release key list. It lists release keys, and the type tag is the domain separation the spec requires.

## Weakest premise / known differences from the relay
- Node verifies Ed25519 with OpenSSL, not ed25519-dalek's verify_strict. Both refuse a non-canonical S. verify_strict also refuses a small-order R in the signature, and Node may not. That matters only for a forged signature, which would also need the recovery key.
- No held seq is kept by this slice. The set arrives inside the signed release, so slice 2 decides where the held record lives (rollback of the set is then a release rollback).

## Validation

- engine.reachable.test.js passes with the two exports excused as unwired (the #6609 phase 1 pattern). The standing guards (fixture-discipline, sandbox-data-4796, no-brand-refs, no-name-refs) and bundle.* pass: 65/65.
