# win32-update-stage: download, verify and stage a Windows build, never swap it (updater slice S2)

Branch `win32-update-stage`, off `origin/main` at `3f8797b6` (which carries S1, #2938).
Design: the Windows in-app updater design (capability 7), §2, §3 B0-B4, §4, §7 S2.

## What this slice ships

1. `engine/win32zip.js`: a minimal zip reader on Node built-ins (`zlib.inflateRawSync`,
   `zlib.crc32`). Stored and deflate only. It refuses, before writing a byte:
   - zip64, multi-disk, encrypted entries, any method other than 0 or 8;
   - absolute names, `..` and `.` segments, empty segments, `\`, `:` (drive letters
     and alternate data streams), control characters, trailing dots or spaces in a
     segment (Windows strips them, so `app.` would alias `app`), reserved device names;
   - a top-level name outside the caller's allow-list;
   - duplicate names, compared case-insensitively (NTFS is case-insensitive), and a file
     that is also another entry's directory;
   - symlink entries (Unix mode bits in the external attributes);
   - an entry, a total or an entry count over the caller's caps;
   - a local header that disagrees with the central directory, overlapping entries,
     data past the central directory, and a truncated archive.
   While extracting it checks the inflated length against the declared size (and caps the
   inflate at it) and the CRC-32. Files are written with `wx`, so nothing already there is
   overwritten or followed.
   Measured: the real 0.6.55 zip (`kosmos-e2e`, 37 MB, 139 entries) has no zip64 locator,
   no data descriptors (flag 0 everywhere), methods 0 and 8 only, Unix-made entries, and
   seven top-level entries. So zip64 is refused, not supported.
2. `engine/win32update.js`, `prepare(opts)` only:
   - **B0**, each refusal a sentence: the platform is win32; the bundle layout is present
     (`win32board.bundleRoot`); `win32anchor.readPointer` names `ROOT\app\engine`; ROOT is
     not a drive root, and is not inside or equal to `store.ROOT`, `projects.projectsRoot()`,
     the workers root (`store.workersRootFor`) or the anchor dir (`win32anchor.anchorDir`);
     none of those sits inside one of ROOT's ENTRIES (the swap would move it); WORK is not a
     link or junction; no prepare is in flight (an in-process flag plus a `wx` lock file in
     WORK, stale when its pid is gone or it is older than the whole budget); live execution
     is allowed.
   - **B1**: reads `pointerFor('win32', channel)` under the base with `readManifest`, the
     S1 rule, fresh (not the look's 15-minute cache). `artifact` is never read. Refuses a
     version that is not newer than ROOT's own `app\package.json`, and, when the caller
     passes `expectVersion` (S4 will pass the offer the person accepted, which is the
     look's cache), a pointer that has moved since.
   - **B2**: fetches the `${versioned}.sha256` sidecar first, and refuses before the big
     download if it disagrees with the manifest. Then streams `${base}/${versioned}?v=${version}`
     into `WORK\download.part` while hashing, with named caps on bytes and wall time, and a
     truncation check against Content-Length. The free-disk precondition runs here, once the
     size is known: free space must be `DISK_HEADROOM_MULTIPLE` (4) times the Content-Length,
     or the byte cap when there is none. The rule is computed = manifest = sidecar.
     On any failure the part file is deleted and the reason recorded.
   - **B3**: extracts to `WORK\staged` with win32zip. The allow-list is ENTRIES, derived
     from `REQUIRED_ENTRIES`, which is pinned to the build script's own `for want in` check
     (`tools/build-kosmos-windows.sh`). A second pin reads every `$STAGE/<name>` the script
     writes, so a new top-level entry in the build cannot ship without the updater learning it.
   - **B4**: `manifest.json` says `win32`, the version, and the arch; `app\package.json`
     agrees; every required entry is present; the staged `node.exe -p process.version` runs
     through `execFileSync` with a timeout and prints the Node version the manifest names;
     `runtimeChanged` is the staged `node.exe` against the anchored one, size first, then
     sha-256; `expectedIdentity` is `boardIdentity(buildIdentity(staged\app), world)`,
     the same two functions `server.js` computes its header with. On failure `staged` is
     removed and the reason recorded.
   - Returns `{ok, version, sha256, stagedDir, runtimeChanged, expectedIdentity}` or
     `{ok:false, because}`. The last result is also written to `WORK\prepare-status.json`.
3. A CLI for the live check: `node engine/win32update.js --prepare --root <dir> --base <url>`.
   It is a dry run that prints what it would do and exits 2, unless `--yes` is given. `--yes`
   is the explicit operator opt-in that stands in for `allowLiveExecution()` (only server.js
   may call that, and `platform-gate-wiring` pins it). Guarded on `require.main === module`, so
   requiring the file does nothing.

## Live execution (convention 3)

`prepare()` downloads from the network, writes about 140 MB and runs a downloaded binary. B0
asks `opts.liveExecutionAllowed` (default `live-execution.liveExecutionAllowed`), and on false
calls `refuseOrWarn`, which throws in a `node --test` process (a suite reached the real
updater without a seam) and warns in production, then returns the refusal. Tests pass the
seam explicitly. The CLI passes `() => true` only under `--yes`.

## Nothing wired

No route, no UI, no `beginInstall` branch. `SELF_INSTALL` stays `['darwin']`. S2 writes only
under `ROOT\.kosmos-update\`: a path-guard test snapshots the sandbox (ROOT, anchor, store,
projects, workers) before and after and asserts that only WORK changed, and every write in
the module goes through one `insideWork` check.

## Tests

- `engine/win32zip.test.js`: every refusal above, a stored entry, a deflate entry, a correct
  extract, a truncated archive, a bad CRC, a zip-slip attempt, and a size cap. Zips are built
  in the test by `test-support/zipfixture.js`, a small writer that can also build the bad ones.
- `engine/win32update.test.js`: the three-way sha rule (manifest vs sidecar, computed vs both),
  truncation, the byte cap, the time cap, a wrong version in `manifest.json` and in
  `app\package.json`, stray entries, a missing required entry, a staged `node.exe` that does
  not run (stubbed), disk too low, each B0 refusal, the live-execution refusal (in-test throw,
  and the production arm in a child process without `--test`), the happy path (staged tree and
  expected identity), `artifact` never fetched, the path guard, and the two build-script pins.
  An injected fetch serves test-built zips; there is no real network.
- `engine.reachable`: the `readPointer` excuse is removed, because it now has a production
  caller (the excuse said it was dormant until one existed).

## Left for S3

`win32swap.js` and the atomic `engine-path` write; the journal in the anchor dir and the
"unfinished journal" precondition; the helper (`--kosmos-update-apply`) and H1-H9; the
"started by its task, task registered and enabled" precondition, which only matters once the
board is stopped; the B5 spawn.

## Review log

### Round 1 (review of `c8040fef`)

What held: no byte that fails the pointer's sha can be staged, and the traversal, name,
download-integrity, cap, migration, convention-3 and one-derivation claims. The real 0.6.55 prod
zip passes the real-sample test.

What was fixed:

1. **Raw control bytes in `win32zip.js`** made git treat the file as binary. The cause was the
   authoring tool turning `\u` escapes into raw characters. The sources now use `\x` escapes only,
   and a test pins that none of the updater's files holds a raw control or invisible character
   (it builds its own pattern from character codes, so it cannot be broken the same way).
2. **B0's protected-folder check was lexical.** It now also compares `fs.realpathSync.native`
   forms (a path that does not exist yet resolves through its nearest existing ancestor), so a
   junction, a `subst` drive or an 8.3 spelling cannot hide a protected folder inside an entry,
   or ROOT inside a protected folder. Junction tests run on Windows.
3. **The lock could let two prepares run.** It is now published whole: written to a draft, then
   hard-linked to the lock's name (atomic, or EEXIST). An unreadable lock younger than 5 s is
   held. A stale lock is renamed aside and read again, and put back if it turns out to be live;
   nothing deletes the shared name blind. Tests cover the empty-lock window, a racing clearer
   (driven through a seam between the look and the clear), four processes racing, and a spy
   showing the lock's name is never opened for writing.
4. **The path guard missed temporary files.** A write spy over `fs` now records every path a
   prepare writes (temporary files included) and asserts all of them are under WORK. The snapshot
   also records folder mtimes, except ROOT's, which WORK's creation changes. `workGuard` has a
   direct test.
5. **Untested zip refusals** now have tests: overlapping entries, per-entry and end-record zip64
   markers, multi-disk, a folder with contents, and a non-ASCII name without the UTF-8 flag.
6. **Untested guards**: the staged node's environment and timeout, and the world fallback, have
   tests. Every prepare test carries a timeout, so a reverted guard fails instead of hanging.
7. **8.3 short names** (`~` then a digit, in any segment) are refused, and a test pins that
   nothing the build stages has one. The `wx` comment now says what it still guards.
8. **Reserved names**: the full list, with `CONIN$`, `CONOUT$`, `CLOCK$` and spaces before an
   extension.
9. **The local header** is compared with the central directory for flags, and for CRC and
   sizes when bit 3 is clear, so Explorer cannot unpack a different tree from the one staged.
10. **The staged node.exe** runs from its own `runtime` folder, with only `SystemRoot`, `windir`,
    `TEMP`, `TMP` and `PATH` from the board's environment.
11. **The expected identity's world**: an explicit one, else this board's `bootedWorld()`, else
    the registry's active world (read as the boot reads it). The CLI's dry run names it.
12. **Download**: more bytes than Content-Length announced has its own sentence. B3 unpacks the
    bytes that were hashed, held in memory; `download.part` is written and never read back.
13. **One size rule**: `win32anchor.interpreterSizeDiffers` is `ensureAnchored`'s own expression,
    exported, with its behaviour unchanged. `runtimeChanged` starts from it and adds a sha-256 for
    equal sizes, and a test pins both call sites. The two can differ only for equal sizes with
    different bytes, where `runtimeChanged` says changed and `ensureAnchored` would not copy. S3's
    H5 swaps the interpreter explicitly whenever `runtimeChanged` is true, so it does not lean on
    `ensureAnchored` for that case.

Beyond the list: every entry name must be plain printable ASCII. That closes the probe's
case-folding, right-to-left-override and zero-width cases, and costs a real build nothing.

Revert controls: 90 guards (the 31 round-1 fixes and the 59 earlier guards restated against
the new source), each reverted on its own, all turn a test red and none hangs. The first full
run found four runs that hung or stayed green, all from two tests: the in-flight test polled
without a deadline, and the re-read test rewrote `download.part` after the point where a
re-read would happen. Both tests were fixed and those four reruns are red. `wx` is no longer in
the list: with short names refused it guards only aliases the name checks do not model, and the
code says so.

### Round 2 (review of `d64e1ea7`; rebased onto `origin/main` at `e113b870`)

The reviewer verified round-1 items 1, 2, 10, 11 and 13 clean, including live junction probes
both ways. The branch was rebased twice: first onto `57574825`, then onto `e113b870` after S0
(#2951, the Windows staging channel) landed while this round was in progress. Both rebases
applied without a conflict, because main had changed none of the files this branch touches. The
S2, S1 update, anchor, orphan and guard suites were rerun on the final base.

1. **A drive without hard links** (FAT32, exFAT) made the lock's link fail with a raw Node error
   that named internal paths. Any link failure other than EEXIST now refuses with a sentence
   ("this drive can't make the hard links the updater needs ... keep Kosmos on an NTFS drive"),
   and only the error code is logged. A draft that is gone because a holder swept it refuses as
   "already being prepared", not as a drive problem.
2. **Orphaned lock files.** Once a prepare holds the lock, it sweeps every `prepare.lock.*`
   sibling in WORK: drafts, clear claims, and asides from the lock's first design.
3. **The stale-lock race, fixed at the root.**
   - The rule: an owner that is verifiably running holds the lock, whatever its age. A verifiably
     gone owner does not. Only an owner that cannot be verified (an unreadable lock, no pid, or a
     pid check that errors) falls to the age rule. `win32orphan.pidState` keeps that third answer,
     and `pidAlive` now derives from it with its behaviour unchanged.
   - Rename-aside was replaced, not kept, because it could not pass the third-racer test. A judges
     a dead lock stale; B clears it and links its own in A's gap; A's rename moves B's live lock
     aside; C links into the next gap; A's restore can only fail, and B and C both hold. A loud
     refusal would stop only A.
   - Instead, a stale lock is removed only by the holder of its claim,
     `<lock>.<hash of its contents>.clearing`, published by link. The holder reads the lock again
     and removes it only if it is byte for byte the lock judged stale. No live lock is ever moved
     or removed. A claim left by a clearer that died is stepped past (the next claim's name hashes
     it in) and is never deleted by a clearer; the holder's sweep removes it.
   - Residual: a dead owner whose pid Windows has reused for another process reads as running,
     so the lock stays held until that process exits. The refusal names the pid.

Tests cover each rule and race through the lock seams (`beforeClear`, `beforeRemove`):
- an old lock with a running owner stays held;
- a gone owner's lock clears, fresh or old;
- an unverifiable owner follows the age rule (with `pidState` stubbed, and with no pid at all);
- a prepare that clears and takes the lock first keeps it;
- a third prepare arriving between the re-read and the removal is refused, leaving one holder;
- a dead claim is stepped past;
- the hard-link refusal (with a stubbed EPERM) and the swept-draft case.

The four-process race still ends with one holder.

Revert controls: all 12 guards for these three items, each reverted on its own, turn a test red,
and none hangs.

### Round 3 (review of `702cc710`; rebased onto `origin/main` at `cb5aa831`)

The rebase applied without a conflict, because main had changed none of the files this branch
touches. The S2, orphan, anchor, reachable and platform-gate suites were rerun on that base: 126
tests, 125 pass, 1 skip (the real-build test, which needs `KOSMOS_WIN_ZIP_SAMPLE`).

The reviewer found no break in mutual exclusion: 7 stress runs, 2,531 racers, 1,598 external kills,
never more than one holder, and no wedge. It found three cleanup races that only Windows shows, a
test gap, a pid-reuse residual worth narrowing, and three small points. The original builder died
in a machine crash; a fresh builder made these fixes.

1. **A swept draft read as a FAT drive.** When a holder's sweep deletes a racer's draft while the
   racer links it, Windows answers EPERM about as often as ENOENT (measured 7,884 to 12,036), and
   only ENOENT was read as busy. Now any link failure is read by what is on disk: a draft that is
   gone refuses as busy, with no probe. A draft that is there is linked to a fresh unique name. If
   that works, the drive can link, the lock's name was busy (a lock whose delete is pending cannot
   be linked over), and the caller looks again. Only when that probe fails too, with the draft
   still there, is the drive called link-incapable.
2. **Cleanup that threw.** `rmSync(..., {force: true})` still throws EPERM while another process is
   deleting the same file. In takeLock's `finally` that leaked a raw error with an internal path on
   a refusal. On success it threw after the link had worked, so the lock stayed with a live pid
   and prepare() never released it, wedging the board until restart. The draft, the clear claim
   and the link probe are now removed by `removeOwnLeftover`: it never throws, logs only the code,
   and leaves the file for the next holder's sweep.
3. **The holder's sweep threw.** It is now `sweepLockLeftovers`, and it is best-effort for every
   error code. The first cut ignored only ENOENT, EPERM, EBUSY and EACCES and threw anything else;
   the builder flagged that a stray `prepare.lock.*` folder would then fail every prepare, and the
   coordinator decided: the sweep is housekeeping in a prepare that already holds the lock, so no
   leftover it cannot remove (another prepare's cleanup, a scanner, a stray folder, EIO) may fail
   that prepare, and real disk trouble surfaces in the download and staging that follow. Each
   failure is logged as `code=… entry=<its own name>` (never the full path) and the entry is left.
4. **Tests** for each of the above, through fs stubs: EPERM with the draft gone (and gone during
   the probe), the busy-name retry, draft removal failing on the refusal path and on the success
   path (prepare stages and releases, and the next prepare runs), a claim removal failing, a
   sweep entry failing with EPERM, and a sweep that meets EIO and a stray folder, logs and leaves
   both, and still stages.
5. **Pid reuse after a restart.** Measured: Windows reused a dead pid after 186 to 1,315 spawns, so a
   prepare killed by a restart can leave a lock whose pid now belongs to a long-lived service.
   - The lock now carries `boot`, this computer's boot time (`Date.now() - os.uptime() * 1000`).
   - A lock is dead, whatever its pid, when its `boot` is earlier than this boot by more than
     `BOOT_TIME_TOLERANCE_MS` (2 minutes: the boot time is derived from two clocks read a moment
     apart, and time sync can step the wall clock) AND its `at` is before this boot began.
   - The second condition costs a real earlier-boot lock nothing. It means a forward clock step
     during a prepare cannot make that prepare's own lock look dead unless the step is larger than
     the uptime at which the lock was taken.
   - It is still removed only through the claim protocol. A lock with no `boot` (the earlier
     format) keeps the old rules.
   - `hooks.clock` ({now, uptimeSeconds}) is the test seam.
   - Residual: Windows Fast Startup keeps uptime across a shutdown, so a lock from before a
     shutdown with Fast Startup reads as this boot and falls back to the pid rule (the old
     behaviour, and the safe direction). A double holder still needs two prepares in different
     processes together with a forward clock step larger than the first one's uptime at lock time.
6. **Small points.**
   - A lock removed between the stat and the read is gone, not "unreadable, just written".
   - An owner that cannot be checked is aged from the earlier of `at` and the file's mtime, so a
     future `at` cannot hold forever.
   - A lock that is a folder, or stays unreadable after being read three times 20 ms apart
     (Windows answers EPERM for a moment on a lock whose delete is pending), refuses with a
     sentence that names the lock file and asks the person to remove it. It is never deleted
     automatically.

Revert controls: all 16 guards for these items, each reverted on its own against a saved copy of
