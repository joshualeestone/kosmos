# tokenfsync14-5434: board.token is flushed before it is published, and a zero-filled one heals (#5434 slice 14)

Addresses #5434. Group 2 of the rename inventory (tokens in Kosmos's data), first: `engine/boardauth.js`
`ensureTokenPrimary` writes `board.token` to `.<file>.<pid>.tmp` and publishes it with `link()` (a new token), or
`rename()` (the legacy-leaf backfill, and the empty-file heal). Nothing was flushed, so a crash could leave board.token
at full length but zero-filled (#5431). Worse than a lost file: `readToken` trims whitespace only, so 64 NUL bytes read
as a token that nobody holds. Every agent and browser was refused, and the heal for an EMPTY file never fired.

## Change
- `writeTokenTemp(tmp, data)`: open `w` at 0600, write, `securewrite.flushOrThrow`, close without masking an earlier
  error. Used for the new token and the backfill. The new token's write moved inside the try whose `finally`
  unlinks the temp, so a failed write or flush leaves no temp.
- `securewrite.syncDir(store.ROOT)` after each publish (link, backfill rename, heal rename).
- `usableToken(t)`: a token containing a NUL byte reads as absent in `readToken` (both leaves) and `readTokenFrom`. On
  board start `ensureToken` then takes the existing EEXIST-and-empty heal: the zero-filled file is replaced by a fresh,
  flushed token.
- `securewrite` exports `flushOrThrow` and `syncDir` (the identical one-line change as slices 8, 12, 13).
- New `engine/boardauth.fsync-5434.test.js` (4 tests), in `tools/windows-tests.js`.

## Decided
- **Heal, do not refuse.** A zero-filled token is unrecoverable: nobody holds those bytes. Replacing it is what the
  empty-file heal already does; this widens "empty" to "empty or NUL-filled". Agents re-read the token at their next
  start, as after any token change.
- **Only the board's reader changes.** Other readers of board.token (install/kosmos, the bridges via
  boardauth.readToken, tools) read the file the board has healed at its start. Before the board starts they present
  the NUL token and are refused, exactly as today.
- **A flush failure on a new token throws** out of ensureToken (the old write failure threw too); nothing unflushed is
  published.

## Tests
- a new token is flushed before link() publishes it, the folder after (POSIX); a zero-filled token reads as absent in
  readToken and readTokenFrom, and ensureToken replaces it with a flushed real token; a failed flush publishes nothing
  and leaves no temp; an existing real token is returned and not rewritten.
- Mutation: main's boardauth.js fails 3 of 4 (the no-rewrite arm passes on main, as expected).
  Related set (79 files, list5434s14.txt): 2413, 0 fail, 10 skipped.

## Weakest premise
That no legitimate board.token contains a NUL byte. generateToken writes 64 hex characters, and every writer goes
through it. What would change my mind: a token format that is binary.
