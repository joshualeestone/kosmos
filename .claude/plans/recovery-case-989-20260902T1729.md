# recovery-case-989 -- a case-mismatched name must still reach the agent

Card: kosmos#989. Josh changed an agent's model, was asked to restart, and the
agent never responded. Cause (Mona Lisa located, Angel reproduced live: `casey`
OK / `Casey` REFUSED, the refusal string being Josh's screenshot verbatim): the
restart wedges on Claude Code's first-run trust prompt, and the in-app recovery
route resolves a name whose case differs from the tmux session -- and the send
was refused.

## The real defect: two derivations of one fact, disagreeing

- The route gate `server.js:claimantFor` (which `knownAgent` gates every agent
  route on) resolves a name **exact-first, then `store.safeKey`** (lowercase +
  strip), preferring the `isNamedOurs` card. So `Casey` PASSES the gate.
- But `engine/chat.js:addressable` and `viewport` did a **bare case-sensitive**
  `roster.find(a => a.sessionName === key)` and refused "by exactly this name".
- So the same name the route just admitted was then refused by the send. That
  disagreement is the whole bug (server.js itself calls this the codebase's
  "worst habit").

Kosmos also lowercases every created session name (create.js:413), so no two
Kosmos agents differ only by case -- the collision Splinter worried about for a
case-fold cannot arise from Kosmos-managed agents.

## Fix: make the SEND tolerate CASE only (corrected in challenge-loop iter 1)

- Added `chat.resolveCard(roster, key)`: exact-first (an exact session wins
  outright, so `casey` still resolves to `casey` even beside an external
  `tmux new -s Casey`), else a CASE-INSENSITIVE match, preferring the
  `isNamedOurs` card.
- `addressable` and `viewport` now call `resolveCard` instead of the bare match.
- The caller's `isNamedOurs`/`isAgentPane` checks still run on the returned card,
  so tolerating case loosens no gate.

⚠️ **CASE-FOLD, NOT `store.safeKey` -- and NOT unified with claimantFor. The
first cut of this fix got that wrong.** My initial version used `store.safeKey`
in resolveCard and refactored `claimantFor` to share it. Challenge-loop iter 1
(BLOCKER) caught it: `safeKey` also STRIPS, so `deliver('Ca.sey')` resolved to
`casey` and SENT -- breaking `engine/chat.test.js:181`, a deliberate security
contract ("a spelling that merely sanitises to a live agent is refused"). The
SEND path is intentionally STRICTER than the read gate: a WRITE that merely
sanitises to a live agent must be refused (the repo has closed that hole three
times: profile route, projects.tellAgent, remove). So the corrected fix:
- resolveCard case-folds ONLY (closes the CASE disagreement #989 reported).
- `claimantFor` stays on `safeKey`, NOT unified -- the gate is deliberately more
  tolerant (keeps an agent REPORTABLE under its sanitised name, #18). The gate
  and send now AGREE on case and still DIFFER on strip, on purpose.
- I had also NOT run engine/chat.test.js before claiming "no regression"; that
  was the miss. It now passes 114/114.

## Why engine, not "frontend-only"

Splinter's initial steer was frontend, on the theory the UI sends a mis-cased
name. Measured: the BOARD frontend already sends the canonical `a.sessionName`,
so the mis-case enters via a non-board path (the recovery route / a typed name),
and the engine choke point is where the gate and the send diverge. Fixing the
engine resolver closes the class regardless of which path supplies the case, and
unifies with the route gate -- strictly better than chasing each frontend path.
(Flagged this refinement to Splinter on the card.)

## Verification (measured, with a control)

- `chat.resolvecard-989.test.js` (root, run by run-tests.sh's `*.test.js`), 6/6:
  the fix arm (Casey -> casey ok), no-regression (exact still exact), control (an
  absent name still refused), the isNamedOurs gate preserved (an exact stranger
  pane refused), resolveCard case-fold/prefer-ours + null controls, AND the
  send-stays-stricter arm (Ca.sey refused on the send).
- **Two perturbation controls, both proven to red:** (a) reverting `addressable`
  to the bare exact match reds "the fix: a mixed-case name reaches the agent"
  (Casey -> refused) -- the reported bug; (b) wrongly reintroducing `safeKey` in
  resolveCard reds "the send stays STRICTER than the read gate" (Ca.sey would
  resolve) -- the exact over-reach challenge-loop iter 1 caught.
- **engine/chat.test.js 114/114** (this is the suite whose :181 security test the
  first cut broke; I now run it). server.test.js name-resolution 7/7, incl. "#18
  an agent whose session name safeKey alters can report under its sanitised name"
  (claimantFor stays safeKey). No `web/` change, so the #1720 browser gate is not
  triggered; the node regression test is the guard.

## Not done here (deferred, documented on the card)

- **Josh's 3rd suggestion** -- the system sends a wake-message to an agent whose
  model/account changed -- is a separate enhancement, not the core reachability
  fix. Left for its own card.
- **Delivered-but-not-recorded for a mis-cased name (challenge-loop iter 3
  WARNING, deferred).** A mis-cased name now DELIVERS (the fix), but
  `chat.appendMessage(DIRECT, name)` -> `threadFile` throws BAD_THREAD when
  `safeKey(name) !== name` (true for any case-differing spelling), so the send is
  `recorded:false` and shows no thread bubble. This is PRE-EXISTING thread-keying,
  not introduced by this diff (before the fix the send simply failed), the client
  IS told via `recorded`/`recordedBecause`, and #989's core ("reachable") is met.
  Fully fixing it means canonicalising the thread KEY (record a mis-cased send in
  the agent's canonical thread), which has its own thread-keying semantics -- a
  scoped follow-up, documented on the card for team awareness (as the reviewer
  asked), not silently dropped.
- **NIT (iter 3): FIXED** -- the two route card/askingCard resolutions now share
  `ourCardByName(roster, name)` rather than duplicating the resolve-then-require-ours
  IIFE.
