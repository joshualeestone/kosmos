# tz-1668: capture the operator's timezone in Settings and speak it on the operator line

kosmos#1668 (Josh's own list, via Splinter). Capture the operator's timezone in Settings AND
consume it, so an agent is told the operator's local time on every direct message. The card's
bar: it is not done when the setting saves, it is done when an agent's greeting changes.

## The two halves

### CAPTURE (Settings > Your Profile)
- `web/index.html`: a "Your time zone" dropdown beside "Your name", listing the runtime's IANA
  zones (`Intl.supportedValuesOf('timeZone')`, with a small fallback list) and defaulting to this
  computer's own zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) so a person who never
  opens Settings still has the right one. A machine zone the enumeration omits is inserted so it
  stays selectable. Saving POSTs to the route below. `paintYouTz` + a save handler, painted from
  `paintSettings`.
- `server.js`: `GET/POST /api/settings`. GET returns the saved timezone (null until set). POST
  validates with `messages.validTimeZone` and persists via `store.writeSettings`. Never 500s for
  a state question, same contract as `/api/machine`.
- `engine/store.js`: account-level `readSettings`/`writeSettings` (one settings.json in the data
  root, write-then-rename), NOT keyed by agent -- one operator, one install.

### CONSUME (the operator line an agent sees)
- `engine/messages.js`: `OPERATOR_DIRECT` becomes `operatorDirect(nowLabel)` -- the same bare
  prefix with no label, and `[message from your operator at <time> ...]` with one. Plus
  `operatorNowLabel(tz, now)` (the local time as "1:14 PM CDT", '' when unset or on an id the
  runtime does not know, never throws) and `validTimeZone`. The opening `[message from your
  operator` is unchanged, so the anti-forgery MARKERS guard still matches.
- `server.js:5090`: at the single operator direct-message delivery point, the prefix is now
  `operatorDirect(operatorNowLabel(readSettings().timezone))`, so the stored zone reaches the
  agent's pane on every operator message.

## Why this shape
- The delivery point (5086, the `chat.DIRECT` path) is the ONLY site passing `OPERATOR_DIRECT`;
  the project-thread deliver (6931) passes an undefined prefix by existing design, so it is left
  untouched (adding an operator bracket there would be scope creep and change behaviour).
- Account-level, not per-agent: the timezone is a property of the operator, so it lives in a
  single settings.json rather than in each agent's profile.
- Client detects its own machine zone: in a local-first app the browser is the authoritative
  source for the operator's machine, so the default is detected client-side, not on the server.

## Demonstration (the card's hard requirement)
`engine/timezone-1668.test.js` proves the operator prefix an agent receives CHANGES once a
timezone is set: before, it is the bare `OPERATOR_DIRECT`; after `America/Chicago`, it carries
"1:14 PM CDT"; a saved `Asia/Tokyo` yields a different local time from the same instant. Proven to
red against a consumer that ignores the timezone.

## Deliberately not changed
- The project-thread delivery (6931) keeps its undefined prefix.
- No new dependency; IANA data comes from the runtime's Intl.
