# codexmigr-8597: answer Codex's model-migration menu ahead of time

Card kosmos#8597 (found by Renet in #8593). Codex opens "1. Try new model / 2. Use existing model" at launch when the
agent's model has an `upgrade` in the catalog in effect; the first line the board types lands in it and its Enter
switches the model.

## Measured (codex-cli 0.149.1, scratch home, fake provider, update notice dismissed as in production)
- The menu is reachable TODAY: 0.149.1's bundled catalog maps gpt-5.4 -> gpt-5.6-terra and gpt-5.4-mini -> gpt-5.6-luna.
- No entry: menu. Entry with a WRONG target: menu. The catalog's target: no menu, the agent stays on gpt-5.4.
- `codex debug models --bundled` prints the shipped catalog in about 0.05 s; `models_cache.json` is the fetched one.
- chat.js's menu hold is Claude-only (claudeMenuRefusal), so nothing holds a line on this Codex screen.

## Call
engine/codexupdate.js `pinModelMigration(home, model, codexBin)`, run by the existing launch shim beside the update
dismissal. It finds the target in models_cache.json (when it lists the model), else in the bundled catalog, and
writes `[notice.model_migrations] "<model>" = "<target>"`, the entry Codex writes for "2". It never throws, declines
on any doubt (an unusable id, a failing binary, model_migrations in another shape), and leaves the rest of the file
byte for byte. The supervisor passes the launch model (an endpoint's own -m, else $MODEL, else config.toml's) and
the runner binary.

## Rejected
- A delivery hold for the Codex menu (the agent would wait on a person; the pin prevents the menu instead).
  A hold stays a possible follow-up for the case the pin cannot cover.
- Pressing "2" in the pane at launch: typing into a pane from the supervisor is the harm the board's gates exist for.

## Weakest premise
That keeping the given model is always right. For a model the catalog calls "no longer available" (gpt-5.4), the
agent stays on it and its turns may fail visibly instead of silently switching. The model choice is the person's,
in Kosmos; a visible failure is the honest outcome.

## Residual (named, not measured)
- A signed-in account whose FETCHED catalog names a different upgrade target than the bundled one: on the first
  launch in a fresh home there is no models_cache.json yet, so the bundled target is written; if Codex then checks
  against the fetched target, that first launch can still show the menu (the wrong-target arm above). The next
  launch reads the cache and corrects it. Measuring it needs a real sign-in; the real API catalog Renet fetched
  (0.169.0) had no upgrade on any model.

- The lookup order (the fetched cache first when it lists the model) was not measured with a cache present: the
  arms above had no models_cache.json. If Codex ignored a cache that says "no upgrade" and used the bundled one, the
  menu could still show. Reasoned from Codex writing that cache as the catalog it uses; not measured.

## Found on the way (fixed here)
- An INSTALLED supervisor runs from Application Support/Kosmos/bin, which holds no copy of codex-dismiss-update.js
  and no engine/ (measured on this Mac 11-16), so `[ -f "$DISMISS" ]` was false and the #1315 update dismissal was
  skipped on every installed launch. The supervisor now runs engine/codexupdate.js (launchPrep) through its engine
  path, $_eng; the shim stays for a checkout run.
