# remote0600-6548: remote.json is written owner-only (#6548, from the #1760 shipped-artifact pass)

remote.json (the Kosmos+ account email, this computer's device ids, the relay) was opened with `'w'` and no mode, so
it landed rw-r--r-- under the usual umask. Measured on a real install: only its drwx------ folders (Kosmos/ and
~/Library) kept other users out. Every token and key beside it is already rw-------.

## Change
engine/remote.js `write()`: the temporary file is opened `0o600` and fchmod'd to `0o600` before it is renamed over
remote.json. The open's mode keeps it owner-only (a umask only narrows it); the fchmod puts back the owner's own read and
write bits if a strict umask took them (review 1); the rename then carries the mode. A file an earlier version left readable is owner-only after the next save.

## Test
engine/remote-mode-6548.test.js (tmpscope, sandboxed data root, fake tunnel): a save under umask 000 leaves
remote.json 0600; a remote.json chmod'd to 0644 (CONTROL: read back as 0644) is 0600 after the next save. Skipped on
Windows (POSIX modes). A third arm (review 1) saves under umask 0277 and expects exactly 0600, which only the fchmod
gives. Mutant (review 3, measured): the fix reverted fails all three arms (0666, 0644, 0400); with only the fchmod
removed, arm 3 fails (0400).

## Not changed
- Nothing chmods remote.json at startup: it becomes owner-only at the next save, which the board does on its own
  (fedLive, standing). A one-time fix-up at boot was rejected as more moving parts for a file already behind 0700
  folders.
- remote-status.json and other remote-*.json files: they hold no email or ids (status words and timestamps).

## Weakest premise
That every save goes through `write()`. Another writer of remote.json would keep the old mode.

## Review 2
Arm 2 now pins the usual umask (022) around its save, so a mode-less write would land 0644 and fail it on any machine. The code comment says why securewrite.writeSecret is not used (this writer keeps its own unique temp names and sweepStaleTemps).

## Windows-tests guard (#1777)
The test skips on a win32 host, so tools/windows-tests.js HOST_BRANCH_EXCLUDED names it with the reason (POSIX modes do not exist on Windows). The first Mortals validation failed only on that guard; it and engine.reachable and the #1732 coupling audit pass alone now.
