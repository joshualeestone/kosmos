# win32-chat-arm-570 -- the board can talk to a Windows agent (#570, 7c-4)

Addresses #570. Road: `.claude/plans/WINDOWS-ROADMAP.md` §3 (slice 7c-4).

## What finished looks like

A message typed on the board to a Windows agent reaches that agent through
`win32channel.say()` and the thread shows the same three verdicts the Mac shows:
`placed`, `could_not` (nothing typed, re-sending is safe), `unconfirmed` (it may
have arrived). No `tmux` is invoked for a Windows card, and nothing in `chat.js`
reads `process.platform`.

## Why this is the next slice

`deliver()` authorises a Windows card (the win32 roster emits it as ours and
typeable) and then refuses at `verifyAtSend`, because that probe is a
`tmux display-message` and Windows has no tmux. 7c-3 put a named pipe from the
board to each agent's supervisor and measured it on the box: `say()` answered
`ok` in 57ms and the real agent replied "PELICAN-7" ~1.7s later. Nothing calls it.

## Design

1. **The card says how it is reached, not the platform.** A Windows row carries
   `command === win32roster.WIN32_COMMAND` (`claude.exe`), a value tmux never
   emits on the Mac. `win32roster.isWin32Pane(pane)` is the ONE test for that
   mark; `status.js` uses it for its win32 capture arm and to set the card's
   `reachedByChannel`. `deliver()` branches on `card.reachedByChannel`, AFTER
   every shared gate (message problem, `addressable`, trust-dialog floor,
   trailer check) and BEFORE `verifyAtSend`. `chat.js` reads a fact about the
   card and never decides the platform itself.
2. **No `verifyAtSend` on that arm, and why that is not a weaker gate.** The probe
   exists because a tmux pane can fall back to a SHELL (typed text becomes a
   command) or be scrolled into copy-mode (keystrokes vanish). A stream-json stdin
   can be neither: it is a JSON line into `claude -p`, and the supervisor refuses
   if the child is gone. The equivalent re-check is the supervisor's own, at write
   time, and it is stronger (it is in the process that holds the stdin).
3. **Verdict mapping.** `ok` -> PLACED. A definite refusal (`down`, bad token,
   supervisor refused, helper never started) -> COULD_NOT with its sentence. An
   AMBIGUOUS outcome -> UNCONFIRMED: the client timed out waiting for the reply,
   the channel closed before answering, or the helper was killed at its deadline.
   `win32channel` gains an `unsure: true` flag for exactly those, because today
   they arrive as plain `ok:false` and would be reported as "not delivered" --
   the duplicate-send defect `chat.js`'s three-state design exists to prevent.
4. **The wire is raw.** `wireText` escapes tmux's `;`; JSON needs no such thing.
   The envelope + trailer composition is shared.
5. **A seam like tmux's.** `setChannel(fn)` injects the sayer; with none and
   DRY_RUN on, nothing is sent and the verdict is COULD_NOT with the same neutral
   sentence the tmux dry run gives. `resetForTests()` clears it. No test can reach
   a real pipe.

## Measured on the box afterwards

Start the real board, send to `winstream-1` from the thread route, see `placed`
and the reply in its transcript. Stop the supervisor, send again, see
`could_not` "not running".

## Weakest part of this reasoning

That `command === 'claude.exe'` (the mark `isWin32Pane` tests, and so
`reachedByChannel`) can never appear on a Mac card. It is true of tmux's
`pane_current_command` on macOS (it reports the process name without an
extension); status.js already relied on it. If a future Mac runner reported
`claude.exe`, its sends would go to a pipe that does not exist and fail HONESTLY
as `down` -- could_not, nothing typed -- not silently.

## Review of the contract by the Mac delivery owner (2026-09-10)

Baron, relayed by Splinter, confirmed the mapping matches the Mac's rc-based
contract verdict for verdict: `could_not` only when certain nothing reached the
agent, any post-commit doubt is `unconfirmed`. He asked two things:

1. **PLACED at the Mac's bar: transport-delivered, not agent-processed.** It is:
   the supervisor answers `ok` from the stdin write's flush callback. His note
   also exposed a gap: a write that failed IN that callback (already handed to
   the pipe, so part of it may be in front of the agent) came back as a plain
   `ok:false` and would have read `could_not`. Fixed: the supervisor marks it
   `unsure`, and `win32channel.serve` now relays `unsure` instead of dropping
   it. A synchronous throw from `write()` stays a definite no. Tests in
   `win32supervisor.test.js` and `win32channel.test.js`.
2. **Is the JSON line and its newline one write?** Yes: `messageLine()` appends
   the `\n` and the supervisor sends it with one `stdin.write`, so there is no
   typed-but-not-submitted case to map.

## Found in review round 2: one message per connection

`serve()` kept the parsed line in its buffer and only stopped reading once
`onSay` answered, so a second chunk arriving on the same connection while the
write was pending re-parsed that line and handed the SAME message to `onSay`
again (reproduced: `['hello','hello']`). This predates the branch and today's
only caller writes one line per connection, but it undermines exactly the
guarantee this slice makes, so it is fixed here: a connection stops reading the
moment it hands a message over. The test fails without the guard (control run).

## Found in review round 3: an unreadable answer is not a no

Three older paths answered a plain `ok:false` (so `could_not`) after the request
had been handed over: `clientMain` getting a reply it could not parse or that
was not an object, `say()` getting no readable verdict from a helper that RAN,
and `serve()` catching a throw from `onSay`. Each may follow a delivered message,
so each is now `unsure`, which makes `say()`'s doc line "every other `ok:false`
means nothing was typed" true. Tests for all three fail against the previous
commit (control run in a copy of `engine/`). Also: the header and a test comment
still described a two-verdict contract, and this plan still described branching
on `command` rather than `reachedByChannel`; all corrected.

## Found in review round 4: an array is not a verdict

Round 3's "is this a verdict object" guards used `typeof x !== 'object'`, which
lets a JSON array through (`typeof [] === 'object'`), so a `[]` reply still read
as `could_not`. Both guards now also reject `Array.isArray`, and both round-3
tests carry a `[]` case that fails without it (control run).

## Found in review round 5: one reading of a verdict

The guards still accepted ANY object as a verdict, so `{}` or `{"ok":1}` after
handover read as `could_not`. And they were two copies of one guard, which is
why round 4's fix had to land twice (convention 5). Both sites now call one
`readVerdict(line, handedOver)`: only `ok === true`, or `ok === false` with a
non-empty string `because`, is a verdict; anything else is unsure once the
request was handed over and a definite no before. Tests carry `{}`,
`{"ok":1}` and `{"because":"x"}` cases that fail against the previous commit.
`chat.js`'s comment on `unsure` now states the rule rather than a partial list.

## Not in this slice

- The token-on-resume defect (a crash-restarted agent resumes with an empty
  KOSMOS_AGENT_TOKEN, so its self-reports are refused). Separate, small.
- Mac parity note: neither platform resumes a conversation on reboot; the
  roadmap sentence claiming Windows would is corrected with this slice.
