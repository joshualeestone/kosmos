# statefsync17-5434: five records Kosmos needs to start are flushed before they count (#5434 slice 17)

Addresses #5434. Group 3 of the rename inventory (what Kosmos needs to start). Each wrote a temp with writeFileSync and
renamed it with no flush, so a crash could leave the file at full length but zero-filled (#5431), and each reads a
zero-filled file as empty:
- `engine/worlds.js` `writeRegistry`: the worlds registry (which world is active).
- `engine/projects.js` `writeAll`: projects.json (every project; its own comment says a bad file "silently loses every
  one of them").
- `engine/remove.js` `writeRemoved`: the removed-agents list (a bad file "would put every stopped agent back on screen").
- `engine/you.js` `save`: you.json (the person's profile).
- `engine/policy.js` `persist`: policy.json (the person's policies).

## Change
- `store.saveFlushed` (already used for profiles and settings; securewrite, `atomicOnly`, the existing mode kept, the
  umask default for a new file) is exported, and the five writers call it. Each still throws on failure, as before.
- New `engine/state.fsync-5434.test.js` (6 tests), in `tools/windows-tests.js`.

## Decided
- **Reuse store.saveFlushed rather than a sixth helper.** It is the save these folders' neighbours already use, with
  the same mode rule. One behaviour change comes with it: an existing file keeps its mode (the old temps took the
  umask's); a person who had narrowed one of these files keeps it narrowed.
- **Tests:** you.json, policy.json and (review 1) the worlds registry through their public saves (flush before rename; a failed flush throws and
  leaves the old file); the four store writers held, by reading their source, to calling saveFlushed and no bare
  renameSync (the registry keeps its own writer; it is driven through createWorld, review 3). Driving projects/removed/worlds through their public paths would need whole projects and agents set up;
  their existing suites run in the related set.

- **Old-shape temps a crash left under the old code** (`projects.json.tmp`, `you.json.tmp`, `.worlds.json.<pid>.tmp`
  and the like) are not reaped, as on main: harmless litter, no secrets (review 1).

- **The worlds registry keeps its own writer and its DOT-named temp** `.worlds.json.<pid>.tmp`, now written through a
  descriptor and flushed before the rename, the folder after (review 2). The guide's sandbox rules
  (`Read(base/.*.tmp)`, `Edit(base/.worlds.json.*)`, boardCredentialPaths, baseEntryToName) and Undo's protected
  paths recognise a registry temp only by that name; securewrite's `worlds.json.kosmos-...tmp` would have fallen
  outside all four while it held the whole worlds list. The other four writers use store.saveFlushed as planned.
- `securewrite` exports `flushOrThrow` and `syncDir` (the identical one-line change as slices 8, 12-14, 16).

## Tests
- (review 3) worlds registry: a failed flush throws, keeps the registry and leaves no temp.
- Mutation: main's files fail all 6 tests (re-measured after review 3). Related set (352 files: store is required almost everywhere,
  list5434s17.txt): 7308, 0 fail, 55 skipped.

## Weakest premise
That a source-reading test is enough for the three writers not driven behaviourally. It catches a reverted writer,
not a wrong argument to saveFlushed. What would change my mind: a reviewer showing a cheap public path for one of them.
