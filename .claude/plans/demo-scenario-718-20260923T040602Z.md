# #718 demoable browser-check: PWA installability + gated demo-flow spec

Branch: `demo-scenario-718` (off origin/main). Addresses #718 (non-closing).

## What "finished" looks like

A real, runnable-today browser-check in the repo's convention (`docs/browser-checks/*.js`)
that verifies the #718 "home-screen icon shows" third — the PWA is installable — and,
in its header, a discoverable GATED spec for the full demoable flow (install →
permission → push → notification) that grows into runnable checks as the
push/service-worker/front-door dependencies land.

## Why this shape (measure-before-build correction)

Liu Kang's original framing named `.claude/browser-test-scenarios.md` and assumed
Raiden's `/v1/push/subscribe` existed. Recon against origin/main corrected both:
- The repo's real, CI-enforced browser-test convention is `docs/browser-checks/*.js`
  (Playwright Node scripts, `// Browser-check-surface:` tag, `KOSMOS_URL`/argv board
  URL, in-file assertions, driven by `tools/browser-checks.sh`). No
  `.claude/browser-test-scenarios.md` exists anywhere — it was a generic global-doc
  reference, not this repo's format.
- The web-push path (service worker, `pushManager`, VAPID exposure,
  `/v1/push/subscribe`) is NOT on kosmos origin/main or any branch. Raiden's send
  path is in the separate `kosmos-relay` repo (a branch); Kano's service worker is
  unmerged. So a runnable push check now would be an unarmed guard testing nothing.

Liu Kang approved this corrected shape.

## Changes

- **`docs/browser-checks/render-pwa-installable-718.js` (new)** — the runnable check:
  - Negative control first (repo doctrine): an absent icon path must not resolve 200,
    or the "icon resolves" passes prove nothing. Verified it fires (absent → 404).
  - Head wiring: `<link rel="manifest">`, `<link rel="apple-touch-icon">`,
    `<meta name="theme-color">`, `<meta name="apple-mobile-web-app-capable">`.
  - Manifest served + valid JSON + install-eligibility fields (name, display:standalone,
    start_url, a 192 and a 512 icon).
  - Every declared icon (manifest icons + apple-touch-icon) resolves 200 + `image/*`.
  - Board URL from `$KOSMOS_URL`/argv, literal fallback (never assumes the port).
  - Header carries the GATED #718 DEMOABLE FLOW SPEC: step (1) armed here; steps
    (2) service worker [Kano, unmerged], (3) permission+subscribe [front-door #2854 +
    kosmos-relay], (4) push send [kosmos-relay, Raiden] marked gated, each growing into
    a real check as its dependency lands. Engine caveat noted (webkit != Safari;
    device emulation != real iPhone; real-device human verification still needed).
- **`tools/browser-checks.sh` (edit)** — one `run_one "render-pwa-installable-718"` line
  in the shared read-only `$B8` board group, so the check actually RUNS at the cut (not
  an unarmed guard). Read-only (HTTP GETs + head read, no POST), so the shared board is safe.

## Deferred / gated (documented in the check header, owned by others)

Service worker (Kano), web-push subscribe + VAPID exposure + front-door origin #2854,
the push send path (kosmos-relay, Raiden). These become armed check steps as they land;
until then they are a spec, deliberately not a runnable (unarmed) assertion.

## Weakest part of my reasoning

The check asserts install *eligibility* (manifest + icons + metas valid and served), not
that a real browser actually offers/completes Add-to-Home-Screen — Playwright headless
Chromium does not surface the native install prompt, and iOS Safari's Add-to-Home-Screen
is not drivable by Playwright at all. So this is the strongest install evidence available
headless; the actual on-device install (and the icon a user sees) still needs real-device
human verification. Called out in the check header. Would change if we later host a
Playwright/Chromium `beforeinstallprompt` drive on a secure front-door origin.
