# terminal-automation-2810: let macOS prompt for Terminal Automation

**Card:** kosmos #2810 (priority; night-shift, Baron Draxum — native app-shell lane)
**Branch:** terminal-automation-2810 (agent-workforce)

## The bug

Josh, testing 0.6.56 on Mortals: clicking "Open Terminal" for any agent fails with
`osascript ... 41:105: execution error: Not authorized to send Apple events to
Terminal. (-1743)`. Broken for every agent.

## Root cause

The board runs `osascript ... tell application "Terminal" ... do script "exec tmux
attach -t <agent>"` (engine/terminal.js) to open Terminal and attach the agent's
tmux session. `-1743` is a macOS Automation/TCC denial. The board's LaunchAgent
(install/setup.sh) carries `AssociatedBundleIdentifiers=com.chaoskosmos.kosmos`, so
macOS attributes that Apple-event request to the Kosmos app bundle for its TCC
decision. The app bundle's Info.plist had no `NSAppleEventsUsageDescription`, and the
app is signed with the hardened runtime (`codesign --options runtime`) with no
entitlements. Without a usage-description string, macOS does not show the one-time
"Kosmos wants to control Terminal" prompt and silently denies with -1743 instead.

## The change

- `install/setup.sh`: add `NSAppleEventsUsageDescription` to the app bundle Info.plist
  the installer generates (the string macOS shows in the Automation prompt). Once the
  person allows it, the grant persists for this Developer ID signature across updates.
- `tools/test-install.sh`: two install-gate assertions (run at cut step-4b, which
  builds the bundle) — the key is present, and the plist is well-formed XML (plutil).
- `tools/test-plist-heredoc-clean.sh`: extended to guard the app Info.plist heredoc
  (not just the board plist), since #2810 added a comment to it and both heredocs are
  unquoted (the #666/#667 backtick/`$`-in-comment hazard class). Verified red-capable.

## Verification

- Headless (this session): the plist lints clean (plutil -lint OK, key extractable);
  test-plist-heredoc-clean passes both heredocs and is red-capable; `sh -n setup.sh`

- Cut time (step-4b): the two test-install.sh assertions run against the built bundle.

## Decisions / rejected alternatives

- **Rejected: the `com.apple.security.automation.apple-events` entitlement.** That
  entitlement is for a hardened-runtime process sending Apple events IN-PROCESS. Here
  the board spawns `/usr/bin/osascript` (Apple-signed, already entitled) as a
  subprocess to send the events, so the app itself does not send them in-process; the
  gap is the missing usage description on the associated bundle, not an entitlement.
- **Routing correction:** the card was triaged as "cannot land in agent-workforce (no
  Info.plist here)". True that there is no Info.plist FILE, but the plist is
  script-generated by install/setup.sh, which is in this repo — so the fix lands here.
- **Weakest premise:** that a background LaunchAgent process reliably triggers the
  Automation prompt in the logged-in user's session, and that the usage description
  alone (no entitlement) suffices under the hardened runtime + responsible-process
  attribution. Both are standard for the osascript-subprocess pattern, but the only
  proof is a real-Mac click. If the prompt does not appear or the grant does not stick,
  the follow-up is the entitlement + a possible move to an in-process Apple-event send.
