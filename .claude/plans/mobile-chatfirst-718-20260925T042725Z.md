## Change (below 40rem, Talk section only)
- body is a flex column exactly the visible height (`--kosmos-visible-height` from a new visualViewport
  listener, else 100dvh); the panel fills it and #d-dmthread is the only scroller.
- The identity block is one row (40px avatar, name, role, small state); the "no name was chosen" note
  is left to Profile.
- The five tiles become one sideways-scrolling row of 44px tabs; same buttons, same click handler.
- Files is not shown on Talk, to keep the first screen for the conversation (it stays on the other
  sections).
- The "Direct Message to <name>" caption is hidden visually (the header names the agent) but kept for
  screen readers; search takes the row.
- While focus is on the composer's text box or Post (not add-a-file, which keeps focus after the file
  picker closes), the back link, header, tabs, search and the older-messages note step aside so the
  keyboard leaves room. Pressing Post while typing keeps focus in the text box (a mousedown handler;
  WebKit does not focus buttons on click), so the header does not flash back mid-tap and the
  keyboard stays up. While searching, the search row stays and the composer steps aside instead.
- The visible height is visualViewport.height x scale, so a pinch zoom does not shrink the page;
  only the keyboard does.
- The panel is ordered last among the body's in-flow children, so any notice that follows it in the
  markup stays above the chat (the connection banner already sits above the panels since #3708).
- The body is NOT scroll-locked (review iteration 2: a lock clipped the world-switcher menu with many
  instances); the thread fitting is what keeps the page from scrolling.
- The talk box keeps its vertical scroll (review iteration 3): with the keyboard up, the folder-trust
  box, file chips and a send error can outgrow it and must stay reachable.
- On a keyboard resize while typing in the phone chat, the page is scrolled back to the top, undoing
  an iOS pan that shows as window.scrollY (reasoned; a pan that shows only as visualViewport.offsetTop
  is not handled; both on Johnny's simulator list, with the Post tap on iOS).
- The identity block is capped at about a sixth of the visible height and scrolls on its own, so its
  notes cannot take the screen (review iteration 4); the memory ring is sized with the 40px avatar
  (iteration 5).
- Composer controls 44px; textarea 16px so iOS does not zoom on focus.
- The talk box runs edge to edge on a phone (negative margin of the page gutter, --space-8, measured
  equal by the check) and pads its bottom by Raiden's shared --safe-bottom (fallback 0px until his
  frame change lands; Liu Kang m597).

## Rejected
- A native chat screen: two more UIs to keep in step (Liu Kang's plan already rejects it).
- Scrolling the page to the talk box on open (keeps the profile above, but leaves page and thread both
  scrolling, and the keyboard problem unsolved).
- Hiding the top app bar while typing: that is Raiden's frame, told instead.
- The same compact layout for the other sections: not my screen, and tapping Profile showing the full
  profile is correct. Offered to Liu Kang as a follow-up.

## Weakest part
The keyboard is simulated. `100dvh` does not shrink for the keyboard; the visual viewport does, and
iOS WKWebView behaviour with a pinned-height body is reasoned, not observed (no simulator on this
Mac, Josh-gated). `env(safe-area-inset-bottom)` is 0 unless the page opts into `viewport-fit=cover`.
Johnny's ruling (iOS shell owner, m581, 2026-09-24): do NOT opt in for now; the shell keeps WebKit's
default safe-area handling as Safari does, which keeps a non-cover page's bottom above the home bar
(reasoned, on his simulator checklist). The env() padding is therefore a no-op today and correct if
cover is adopted later (which also needs env(safe-area-inset-top) on the header). The shell does not
resize for the keyboard, so visualViewport sees what Safari sees. The 189px top bar at 375 (status pill wraps to five
lines) is Raiden's and is what limits the thread on an SE.

Accepted trade: while the composer has focus, the stepped-aside header and tabs are also out of the
accessibility tree (display:none). Keeping them in the tree does not free the space the keyboard
needs. iOS may pan the layout viewport when the composer takes focus before the resize arrives; the
listener handles resize only, so this is the most likely place a device differs from the simulated
check. Both are on Johnny's simulator list.
