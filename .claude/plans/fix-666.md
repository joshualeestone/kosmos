# fix-666: the in-app update loop (the plist heredoc runs `kosmos start`)

## Finished looks like
An in-app update no longer runs `kosmos start` while writing the board plist,
so an existing install's update completes and the running version changes to the
new one. A fresh install no longer prints "kosmos: command not found" (#667).
The plist heredoc can never again execute a comment (guarded).

## Why
install/setup.sh writes the board LaunchAgent plist with an UNQUOTED heredoc
(required for $(_xmlq ...) escaping). A comment in the body contained a backtick
pair `kosmos start`, which command-substitutes as the plist is written: on an
update (kosmos on PATH) it RAN kosmos start mid-swap and spliced the output into
the plist (#666, the loop Josh hit); on a fresh Mac it printed command-not-found
(#667). Confirmed with a fake kosmos on PATH: unescaped -> CALLED:start; de-backticked -> not called.

## Changes
1. install/setup.sh: the comment is de-backticked ("kosmos start", no backticks),
   and the real warning moved to a SHELL comment before the heredoc (safe, and not
   shipped into every user's plist).
2. tools/test-plist-heredoc-clean.sh: guards the class -- the heredoc body may
   contain no backtick and no $ in a comment. In test:shell.

## Not in this change / open
Whether the bootout/parentage is ALSO a cause is not ruled out (Josh's board
stayed up through the failed update, which suggests setup.sh survived the bootout,
so probably not). Confirm #666 closed by Josh re-testing the in-app update on the
build carrying this fix, or by his install.log. Until then this is "the confirmed
mechanism fixed", not "#666 closed".

## Measured
Isolation control (fake kosmos on PATH): unescaped heredoc -> kosmos executed and
its output spliced into the plist; de-backticked -> kosmos NOT called, plist valid.
Guard test: 0 failures.
