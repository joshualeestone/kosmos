# winkillenv-8406: NAME=value and env before a command no longer hide it from the Windows kill guard (kosmos#8406)

## Problem
Homer, on installed Windows staging 0.8.04, through the installed hook: a leading NAME=value word, or env with its
options, gets past engine/winkillguard.js. MSYS_NO_PATHCONV=1 taskkill /F /IM node.exe is allowed. That spelling is
the standard Git Bash fix for taskkill's /F being turned into a path, so it is the natural way to type the command
the guard exists to stop. The same holds for env X=1 taskkill ..., X=1 taskkill ..., and A=1 B=2 Stop-Process -Name node.

## Change
commandReason's prefix loop now also skips:
- any number of leading NAME=value words;
- env with its options (-u NAME and -C DIR take a value; -- ends the options), then its NAME=value words;
- env -S "...": the string is split into the command and read as one.
Prefixes, assignments and env may come in any order: the loop repeats until none is left.

## Mac/Linux guard (#4671)
Measured, with and without jq: X=1, MSYS_NO_PATHCONV=1, env X=1, A=1 B=2 and env -i PATH=... before the shapes it
refuses are all refused, because it matches those shapes anywhere in the text, not at command position. The prefixed
forms are now pinned in report-hook-killguard-4671.test.js, so a future rewrite cannot open the gap there.

## Test
Homer's five forms plus env -i, env -u ... --, env -S, sudo/assignment in both orders, and cmd //c "set X=1 && ..."
are refused. Allowed: MSYS_NO_PATHCONV=1 taskkill /F /PID 4242 (Homer's control), a bare X=1, a bare env, and
MSYS_NO_PATHCONV=1 git status. Two mutations go red: no leading-assignment skip, and no env handling.
