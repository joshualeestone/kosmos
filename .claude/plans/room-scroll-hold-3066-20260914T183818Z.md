# room-scroll-hold-3066: hold a scrolled-up reader when a new post arrives (#3066)

Branch: `room-scroll-hold-3066`  ·  Card: #3066  ·  Slotted: 0.6.66 (Josh, 2026-09-14, "people are complaining about it a lot")  ·  Owner: Mona Lisa (dialog-UI lane, assigned by Splinter)

## The report (Josh, 2026-09-14, #chaoskosmos-design, verbatim intent)
In the project dialog, reading back a few messages, a new post immediately jumps
him all the way down to the newest message. With agents posting steadily he can
never catch up on older messages, because every new post yanks him to the bottom.

## Done condition (what is true when finished)
In the project room, a reader who has scrolled up to read history STAYS where they
are when a new message posts (a poll delivers it). A reader who is AT the bottom
still follows the tail. Opening the room, and clearing/switching the search, still
land on the newest post. Verified by a browser-check fixture that clamps (so an
"it did not move" assertion means something), with a negative control that reds
when the fix is removed; CI green; Josh confirms in-app on 0.6.66.

## Root cause
`paintThreadInto` (the shared room/thread painter) pinned to the bottom whenever
the POST LIST changed:

    if (!filtering && (keyChanged || box.__roomHeldAtBottom !== false)) pinToBottom(box);

`keyChanged` was `box.__lastRoomKey !== key`, and `key` mixed the message ids in
(`PJ_ROOM_QUERY + NUL + ids.join(NUL)`), so EVERY new post flipped it true and
forced a pin regardless of scroll position. The agent Talk thread (`setThread`)
has held a scrolled-up reader since #1926 using only `__heldAtBottom !== false`;
the room drifted from it. The room's own comment history even names this class:
"the room and the thread are painted by different functions, which is exactly how
the room missed the last fix."

## The fix (reversible, web/index.html only)
Separate the two triggers that were conflated under `keyChanged`:
- A change the READER made (the search query cleared or switched) -> reset to the
  newest post. Now keyed on a query-only signal: `queryChanged = box.__lastRoomQuery
  !== PJ_ROOM_QUERY`, tracked via a new `__lastRoomQuery` (replacing `__lastRoomKey`).
- A new post arriving from a poll -> `queryChanged` is false, so a scrolled-up
  reader is left put; a reader on the floor still follows the tail via the
  unchanged `box.__roomHeldAtBottom !== false` arm.
Project-switch reset now clears `__lastRoomQuery` to undefined, so a room re-entry
reads as a query change and lands on the newest post (preserving the old
A-to-B-to-A "do not land on the oldest post" behavior).

## Alternatives rejected
- Drop `keyChanged` entirely (pure parity with setThread): would also drop the
  documented "clearing the filter lands on the newest post" behavior, changing an
  unrelated intent. Rejected to keep the change scoped to the reported defect.
- Add a "new messages" jump-to-latest pill (my earlier spec on #3066): a good
  enhancement but not needed to stop the jump, and larger surface for an urgent
  0.6.66 fix. Left as a possible 0.6.67 follow-up.
- Give the room `threadAnchor` (message-anchored restore) like setThread instead
  of pixel restore: a refinement for content changing height ABOVE the reader; the
  reported bug is new posts appended BELOW, where pixel restore is exact. Out of
  scope.

## Weakest premise
That "clearing the search should land on the newest post" is still desired. It is
the pre-existing documented intent and I preserved it via `queryChanged`; if Josh
would rather clearing the search restore the prior reading position, that is a
one-line change (drop the `queryChanged` arm) and a separate call.
