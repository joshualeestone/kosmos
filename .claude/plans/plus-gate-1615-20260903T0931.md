## Problem

The Settings Plus tab showed a "Turn on" relay switch to every user with no paid gate.
`paintPlus()` (web/index.html) gated the connected flow (state 3, which contains the switch)
on `r.configured`. But `engine/remote.js` defines `configured = () => Boolean(RELAY())` and
`RELAY()` falls back to a production default, so `configured` is permanently true (server.js
says it outright: "'configured' is true with nothing set"). So the designed honest state1
(See Kosmos+, no switch) and paid-gate state2 were dead code, and every user saw the switch.

## Change

1. In `paintPlus()`, gate the flow on `r.enrolled` instead of `r.configured`. `enrolled` can
   be false, and the engine already gates the real connection on it (`remote.js:201`,
   `wanted = on && enrolled()`), so the screen agrees with the engine rather than inventing a
   UI-only rule. Interim result (nobody can pay/enrol yet, #1742/#1886): every machine rests
   at state1 with no switch; an enrolled machine keeps the flow so it can still turn Plus off.
2. Retitle the section heading, Settings nav pill, and section aria-label from "Plus Account"
   to "Kosmos Plus" (Josh, 2026-09-03).

## Tests

- `web.plus-stale.test.js` #1012: an unenrolled Mac rests at state1 with the flow hidden;
  falsifiable against the pre-change page via `PLUS_PAGE=`.
- `web.allow-card.test.js`: nav retitle.
- `docs/browser-checks/render-plus-gate-1615.js` (wired into `tools/browser-checks.sh`):
  on a screen, both themes, unenrolled shows no switch, enrolled keeps it; screenshots both.

## Known consequence (by design)

Gating on `enrolled` makes the in-flow enrol UI unreachable, leaving state2 (unwired) as the
only planned enrolment entry. Intended for the interim (enrol moves to the site + state2,
#1115); the on:true/enrolled:false edge is inert (engine `wanted` requires `enrolled()`), and
the change is strictly removal-direction. Wiring state2's paid signal is the follow-up.

fuller Plus redesign.
