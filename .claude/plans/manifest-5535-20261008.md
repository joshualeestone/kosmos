# manifest-5535: upload the sealed manifest (kosmos#5535 E0.6)

Stacked on bkupload-5535 (PR #5613, the chunk uploader). Rebased onto main once #5613 merges.

## Why now

Coordinator slice 2 (kosmos-relay#327, b4b99ebb3) merged and deployed 2026-10-08 17:42 CDT (backup still OFF).
It adds `POST /v1/org/backup/manifest`: body `{sha256, size}` (plus any extra field such as a nonce, ignored),
size 4,148 bytes to 64 MiB, answer `{epoch, period, retain_until, expires_at, upload: {key, url, headers}}`.
The upload is the same presigned PUT as a chunk's, signed over six headers, with `x-amz-checksum-sha256` (base64
of the SHA-256) in place of `content-md5`. Measured on the Object Lock bucket: other bytes 400 BadDigest, a second
write 412. Contract: kosmos-relay docs/coordinator-api.md and `PutUpload` in coordinator/src/backup.rs.

## What changes

1. `checkOne`: the per-upload checks factored out of `parseGrant`, parameterised by what binds the bytes
   (`chunkBind` = content-md5, `manifestBind` = x-amz-checksum-sha256). parseGrant keeps the checks that span
   uploads (repeated key or url, one bucket per grant and per run), with the repeated-key check still first.
2. `askSigned`: the grant request with its one fresh-nonce retry on `replayed`, shared by both routes.
3. `clockSkew`: the two clock checks, shared.
4. `parseManifestGrant(data, bytes, runPrefix)` and `uploadManifest(deps, bytes, { bucket, chunks })` (both required; chunks = [{ key, lockedUntilMs }], at least one).
   The PUT is retried and classified exactly as a chunk's (same url until expiry, 412 stored only after an attempt
   that may have written it, a new grant only after a clean run-out, bounded by MAX_REGRANTS).
5. `uploadChunks` success also returns `lockedUntil` (name to lock end, ms) and `bucket` (the bucket path).

## Decisions

- **The manifest must go to its chunks' bucket.** `bucket` is required, in the shape uploadChunks returns
  (`host/` or `host/bucket/`, checked before the grant so a bare bucket name costs no allowance); a grant naming
  another bucket path is refused before any byte is sent. Rejected: optional pinning (a guard that is optional is a guard that is skipped).
- **A manifest must never stay locked past the earliest chunk it names.** The coordinator locks a manifest to its
  own period's date and documents that it CANNOT check this (its request names no chunks), leaving the check to the
  uploader and slice-3 restore. So every chunk's `lockedUntilMs` is required (in `chunks`), the uploader takes the
  earliest, and it is compared EXACTLY (`retain > floor` refuses):
  the coordinator's dates are fixed per period (`retain_until_for(period_end)`), so a correct pairing is equal, not
  near. Before asking, a floor under now + 30 days + the 15-minute grant window is refused with no grant (a manifest
  granted now locks to at least its period's end plus 30 days plus that window), so no allowance is spent on a manifest that must be refused. After the grant, a
  refusal spends that grant's allowance (50 manifests a week) and says so; that is preferred to locking a manifest
  that would name deleted chunks.
  A lock end later than now + 39 days + an hour (no grant can set one) is refused before the grant: a value in the
  wrong unit, or never a lock date, would otherwise raise the floor until the check could not fire (review 7).
  Rejected: a tolerance window (the dates are exact); trusting the walker alone (no check at the one place the
  real lock date is known).
- **A manifest key must be this upload's alone** (the 412 rule rests on it): every chunk's `key` is required (in
  `chunks`) and a manifest grant naming a chunk key, or a key an earlier manifest grant in the call gave, is refused before any PUT
  (reviews 1 and 2). Required, not optional, for the same reason as `bucket`; the caller has the keys because the
  manifest lists them.
- **`outlastsChunks` is not retry-later.** The caller must upload the old chunks again first. `grantSpent` has three
  states (reviews 4, 7, 8, 9, 11): `true` on every refusal after a grant answered (allowance spent, a manifest's
  hash recorded), `false` on every refusal before a grant was asked for, absent when the grant request itself
  failed or was refused (it may still have spent one). The chunk path carries `true` the same way. Documented.
- **The uploader takes the earliest lock end itself** (review 6): the caller passes every chunk as
  `{ key, lockedUntilMs }` rather than a precomputed minimum and a separate key list, so passing the LATEST lock by
  mistake (which would disarm the outlast check) is no longer a step a caller can get wrong. A Map, a string, an
  entry without a key or a finite lock end, and an empty list are refused before any grant. The bytes are copied on
  entry, so what is hashed is what is sent.
- Weakest premise: the caller knows the lock end (and bucket path and key) of chunks stored by EARLIER runs. uploadChunks reports it for this
  run's chunks only; the slice-3 walker must record it for the rest. Would change my mind: the coordinator returning
  a chunk's lock date on a later lookup, which it does not today.

## Not in this change

The walker that decides what goes in a manifest and calls these (slice 3), and restore's own check of the manifest
hash. The cutover owed list (production key check, bucket policy, Node's Content-Length measured on the first real
run) stays on #5535.

## Tests

manifest coordinator stub answers in slice 2's shape. New tests cover: chunks then manifest end to end; bind,
signing, write-once, lock mode, length and shape refusals before any PUT; another bucket; outlasting the chunks
(one second past refused, exactly equal stored); the pre-grant floor (no grant asked); missing opts and size range;
the 412 rule both ways; trouble until expiry (retryLater, unsure key, one grant); a clean expiry re-granted with a

unreachable bucket (one grant, no unsure); each chunk's lock end equal to the date ITS upload signed (a 200 and a
412-after-trouble, two chunks with different dates).

Mutants, re-measured together at 81 tests on e4a278b30 (2026-10-08 18:49 CDT), all committed first (the script
refuses a dirty tree), 32 in all, every one red and none by failing to parse (node --check first): bind, regrant,
first412, map, elem, lockother, unsurearm, floorwin, earliest, copy, plausible, spentput, spentcap, lowerhost,

Chunk-path change, deliberate: a chunk grant that answered and was then refused (its checks, or the clock) now
carries `grantSpent: true` (review 12 asked for it to be named). Additive; no other chunk behaviour changes. The
slice-3 walker can rely on it. An unexpected throw in uploadManifest still reports grantSpent and the unsure key
from a per-call state object (review 12).

Refactor note: checkOne keeps every chunk check and its accept/refuse outcome, with the repeated-key check still
first. Only the ORDER in which some refusals are found changed: a repeated url or a second bucket path within one
grant is now reported after the per-upload header and lock checks rather than before. Both still refuse before any
byte is sent; only the reason text can differ.

## Deferred, with reasons

- A shared classifier for one PUT attempt (chunk worker and manifest loop each carry the rules, cross-referenced by
  "change both together" comments): a refactor of reviewed chunk code; no behaviour difference today (reviews 8,
  10, 13).
- The unreachable-bucket tests close a local server and reuse its port: no port is guaranteed never to listen, and
  port 1 does not work (fetch blocks it as a bad port, a different branch; measured). Same small risk as the chunk
  tests (review 13).
- The pre-grant floor uses this Mac's clock: a clock up to an hour fast refuses (grantSpent false) near a period's
  end; documented, errs toward refusing (reviews 1, 13).
- checkOne reads the retain date from the raw headers: deliberate, the validated copy stringifies a number, which
  would lose the refusal of a numeric date (review 7).
