# board-403-2023 -- a protected-read 403 renders as NOT SIGNED IN (#2023)

## The problem
#1946's loopback board auth shipped in 0.6.25. A board opened from a bookmark or a
typed 127.0.0.1 URL holds no board token, so every protected read (`/api/status`,
`/api/projects`) returns 403 while the static shell `GET /` returns 200. The board
drew that 403 as "We cannot read your agents right now" -- honest for a genuine
outage, but wrong here: it invites waiting, and waiting cannot supply a token.
This reached real outside testers within the hour.

## My half: the FALLBACK render
This branch is the frontend half. It makes a 403 render as a distinct
NOT-SIGNED-IN state with the correct remedy, WITHOUT swallowing the genuine
"cannot read" path a real (non-403) failure still needs. The engine half (the
update that re-opens the browser and re-mints the token) is Angel's #2023(a), a
separate branch touching `install/setup.sh` only.

## The remedy copy, and why it is what it is
- PRIMARY: "it fixes itself the next time Kosmos updates" -- needs no user action.
- FOOTNOTE (disclosure): the full-path CLI `~/.local/share/kosmos/bin/kosmos open`.

Every USER-ACTION remedy was measured to FAIL on a real machine and is therefore
NOT the lead:
- relaunch the app: a bundle older than the token-support commit cannot sign in
  at all (#2028);
- a bare `kosmos open`: not on PATH in a shell without `~/.zprofile`
  (command-not-found for Josh), and it can silently fall back to an
  unauthenticated URL;
- a page button: would need a token-exempt mint endpoint, which reopens #1946's
  cross-account hole (the "(b) safe self-open" was dropped for exactly this).

## What the change does
- A `BOARD_NEEDS_SIGNIN` flag, set by any protected read that gets a 403 and
  CLEARED on any non-403 outcome (success, a genuine 500, a network throw) so it
  cannot latch true and draw "not signed in" over "not answering" at once.
- Every board-read-failure render site honours it: `boardEmpty()`, the org note,
  `loadProjects()`'s pj-list / pj-one-msg / pjs-read-msg, `paintAddAgents()`, and
  the free-agent picker. A genuine non-403 failure still shows the old cannot-read
  copy (the signin copy narrows that path, it does not replace it).
- A browser check (`docs/browser-checks/render-board-signin-403-2023.js`) asserts
  the rendered signin state (self-heal leads, full-path footnote) with a 200
  control (neither message) and a 500 control (cannot-read survives).
- Test lift harnesses (`web.board-empty`, `web.offline-note`, `server.test.js`)
  bind the new global; a direct test guards the picker's signin option text.

## Out of scope
- `watchForAgent()`'s 30s creation-poll shows a create-specific message, not the
  signin remedy, on a 403. Documented in code as unreachable-by-construction: the
  poll runs only after a create SUCCEEDED (a gated write that 403s token-less), so
  the session holds the token this same-origin poll then carries.
- The engine self-heal (#2023(a)) and the dropped (b) button are not this branch.
