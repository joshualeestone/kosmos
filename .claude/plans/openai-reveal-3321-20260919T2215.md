# Plan: fix render-openai-install-refusal ARM-4 timeout (#3321)

Branch: openai-reveal-3321
Author: Mona Lisa (night shift), 2026-09-19
Card: #3321 (claimed:monalisa) - render-openai-install-refusal 3b check times out on
`#acct-openai-install-go`, blocking the Mac 0.6.82 staging cut.

## Problem

The cut-time-only 3b browser-check `docs/browser-checks/render-openai-install-refusal.js`
(added by #3291) times out for 30s on ARM 4's `page.click('#acct-openai-install-go')`. Both
0.6.82 Mac cut attempts died here. This check is 3b/cut-time-only, so no PR gate runs it,
which is why #3291 shipped it without it ever validating green.

## Diagnosis (measured, not assumed)

The check's three first-run arms all pass; ARM 4 (the Settings screen) is the one that hangs.
Root cause is test sequencing, not a product race:

- First-run (`#firstrun`, class `.fr-back`) opens on boot on `file://` because there is no
  board and `state.done` is falsy, so `frOpen()` runs.
- `.fr-back` is `position:fixed; inset:0; z-index:60` - a full-viewport opaque overlay.
- `frOpen()` also marks every `body > *:not(#firstrun)` element `inert` to trap focus.
- The Settings install modal `#acct-add-modal` (a direct body child) is therefore covered by
  the overlay AND left `inert` while ARM 4 runs.
- The check's `reveal()` helper clears `hidden`/`display:none`/`disabled` on the button's
  ancestors, but does NOT clear `inert` and does NOT hide the overlay. So Playwright's click
  is neither hit-testable (overlay on top) nor delivered (inert swallows pointer events), and
  it waits out its 30s timeout.

Verified with a headless Playwright probe: the button renders correctly and a native DOM
`.click()` fires the handler and paints the refusal message; the failure is purely the
force-reveal leaving competing first-run state up. So this is NOT user-facing: in the real app
Settings is reachable only after first-run is dismissed.

## Fix

In ARM 4, before revealing/clicking the Settings button, call the app's real first-run exit
`frClose()` (hides `#firstrun`, clears `inert` on all background elements). This reproduces the
real user flow (first-run finished, then Settings). Assert the postcondition (overlay hidden,
background no longer inert) so a partial-`frClose` regression fails with a clear message rather
than a generic downstream timeout.

Do NOT bump the 30s timeout (that would mask a genuine never-clickable state). Do NOT change
`web/index.html` - the product is correct.

## Done-condition

- All arms of `render-openai-install-refusal.js` pass, exit 0, under pinned Playwright
  (`~/work/pw-runtime`, HEADED=0).
- The change is confined to the check file (no `web/index.html` edit).
- The next 0.6.82 Mac cut running the 3b checks passes this check.

## Rejected alternatives

- Bump the 30s timeout: masks the never-clickable state, does not fix it.
- Fix `reveal()` to also clear `inert` / hide overlays generically: reimplements app internals
  in the harness; calling the app's real `frClose()` is more faithful and self-maintaining.
- Change the product `web/index.html`: no product defect exists; the button and modal work.

## Weakest premise

That no real user reaches the Settings OpenAI-install modal while first-run's inert/overlay is
active. Holds because `frClose` is the only first-run exit and it clears inert, and Settings
lives behind the main app which is inert during first-run. Would be falsified only by a code
path that opens `#acct-add-modal` without going through `frClose` while first-run is up.
