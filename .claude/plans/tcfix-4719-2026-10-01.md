# tcfix-4719: render-teamcreate-4557's #4719 lead arm depends on the machine (0.7.16 cut red)

## What failed
The 0.7.16 cut (Mortals, frozen 181dd33f7) failed the lead arm's last check in both engines, four times:
`[["Maya","openai"],["Maya","openai"],["Leo","openai"],["Ana","openai"]]`. The refused first Maya post already
carried openai, so the team menu was on OpenAI before the person "changed" it to OpenAI.

## Why
The arm reads the fixture board's real `/api/accounts`. Under the check runner `AGENT_WORKFORCE_HOME` is one
home shared by every check (`lib-sandbox-home.js` keeps a home the caller set), so an OpenAI-only account left
there by another check reaches this one. #4719's `tcProviderDefault` then starts the team on OpenAI (its rule:
OpenAI when it is the one usable provider). The page is right; the arm assumed a Claude default it never set.
On a clean home (Agent1s, measured: the sandboxed board lists no accounts) the default is Claude and it passes.

## Fix
The arm sets its own accounts, a Claude and an OpenAI account, through the same `page.route` the other #4719 arms
use, and asks the page to read them again. It now also checks the menu starts on Claude, so the change to OpenAI
is a change. No page code changes.

## Proof
One queue turn on Agent1s: (A) main's check with a home holding only an OpenAI account, expected to reproduce the
cut's FAIL; (B) the fixed check with that home, expected PASS; (C) the fixed check on a clean home, expected PASS.

## Not done here
The shared runner home letting one check's accounts reach another is the wider hazard (#3675's class). No card is
filed for it yet; this fix makes this arm independent of it.
