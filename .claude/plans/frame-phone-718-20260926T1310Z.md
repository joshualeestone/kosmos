# frame-phone-718: the app frame's controls are thumb-size on a phone

Issue: kosmos #718, row 5 of the phone-ready table
(https://github.com/joshualeestone/kosmos/issues/718#issuecomment-5842472848). Liu Kang assigned it (m986);
Johnny cleared it (m995): the iOS shell depends only on the board NOT using `viewport-fit=cover`.

## Problem (measured by the sweep, 375px)
The frame on every screen has tap targets under 44x44 CSS px: the K logo 34x34, the Kosmos switcher and You
32px tall, the menu button 40x40, the grid / list / org toggles 38x30, and the "← All agents" back link 70x15.

## Done looks like
Under `max-width: 40rem`, every frame control is at least 44x44 (the logo, switcher, You, menu, the three layout
toggles, and every `.back` link: the agent, create and Files pages and the four project pages), in Chromium and WebKit at the four harness sizes, with no
sideways scroll. At desktop width nothing changes. The `--safe-*` variables exist (Scorpion's composer already
reads `var(--safe-bottom, 0px)`), the viewport meta still has no `viewport-fit=cover`, and a test fails if cover
is ever added without the frame padding by all four.

## Change
1. `@media (max-width: 40rem)`: grow each control's box, with a negative margin on the header-row ones so the
   row keeps its height (the switcher's border and the menu's fill do draw larger; Johnny cleared a taller
   header and 44px controls, m995): the logo button gets padding around its
   34px mark, the switcher and You go to 44px tall, the menu to 44x44, the toggles to 44x44, the back link gets a
   44px tall box. Sonya's Settings fix (#3807) is the pattern: scoped to phone width so nothing else moves.
2. `:root { --safe-top/right/bottom/left: env(safe-area-inset-*, 0px) }`, carried from 19f94b886, with
   `web.safe-area-718.test.js` (the meta tag decides; comments are stripped before the rules are read).
3. A gate browser check (sizes, overlap, header height, the projects list's toggle, the back links, the
   640/641 edge of the rule, desktop unchanged): every frame control at least 44x44 at each harness size, no sideways scroll, desktop
   sizes unchanged, with a control measured against main.

## Rejected
- Growing the controls at every width: desktop layouts were not asked to change and are tuned.
- `transform: scale`: it enlarges the drawing, not just the hit area, and blurs the mark.
- Invisible `::after` hit areas (the Answer pattern): these controls sit in a header row with room to grow, so
  the box itself can be 44px; an overlay would take taps meant for neighbours in a tight row.

- Landscape (Opus review, iteration 1). A phone turned sideways is 667 to 932px wide and gets the desktop
  frame, with the old sizes. Row 4 fixed the composer fields for any touchscreen with `(hover: none)`, but doing
  the same for the frame would change the header on every touchscreen at desktop width (a touch laptop, an iPad
  in landscape): a desktop change Josh did not ask for. Portrait is the phone-ready target; landscape can be its
  own row if someone wants it.
- Scoping the 44px back link to the two agents-area links only (Opus review, iteration 1). Every `.back` link
  measured 15px tall and is a tap target on a phone, so all of them grow. The cost is ~29px of extra height
  above each page they head; the check measures one project page's link to cover the rule's reach.

## Weakest part
The header gets taller on a phone (44px controls instead of 32 to 40). The one-row header from 19f94b886 is not
carried here (it changed the notice chips too, a separate decision); if the taller controls wrap the header
onto two rows at 375, that is the next thing to fix, and the browser check measures the header height.
