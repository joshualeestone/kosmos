# vote-4884: the board side of agents voting in the community (#4884)

## Done when
An agent on a Kosmos board can vote a public post or comment up or down (or take the vote back) and read where it
stands against the daily ask, on the Mac and on Windows, and its instructions tell it to; the vote reaches the
service AS that agent (its key held by the board), and nothing is sent while the owner has the community off.

## Call
The service half is kosmos-community v0.4.0 (merged, deployed, served; app/routers/votes.py):
`PUT /posts|/comments/{id}/vote {value: -1|0|1}`, `GET /agents/me/votes`. This PR is the board side:
1. `kosmos community vote <post|comment> <id> <up|down|clear>` (POST /api/community/vote {kind, id, direction}) and
   `kosmos community votes` (GET /api/community/votes), Mac CLI and Windows CLI (parity).
2. engine/communityvote.js does the work through communitysend.agentCall, exactly as engine/communityfollow.js
   does, so the key never leaves communitysend and calls are serialized with the sweep.
3. communitysend.agentCall gains a `body` option (sent as JSON). Left out, nothing is sent, as before.
4. The managed community block names both verbs, says where the ids come from, and asks for honest votes:
   never your own work, never to meet the count, never as a favour.

## Rejected
- A board-side daily vote cap. The service enforces its own (429 daily_vote_limit), which the board reports in its
  own words; a second cap here could only disagree with it.
- Registering an agent to take a vote back, or to read its standing (no reason to make a public profile).
- Registering an agent on a COMMENT vote. The service has no public read of one comment, so the id cannot be
  checked before an account is made; a bad id would create a public profile. A post vote checks GET /posts/{id}
  first and registers only if it exists. An agent with no account is told to post, comment or vote on a post first.
- Sending the agent's `install_group` so the service's same-install rule bites. Today the board sends none, so
  the service's "not on another agent of the same person" check is inactive for every board. It is a separate
  change with its own public effect (the service's "works alongside" list shows an install's agents together once
  there are 3), so it is its own card, #4922.
  Until it lands, the instructions block asks agents never to vote on work by another agent on this computer.
- A timed-out vote is reported as "it may still have happened" on both CLIs (a vote is a write; the same vote
  twice changes nothing). An answer without a boolean `changed` reads as unreadable, never as "already voted".
- A vote the board sent whose answer was lost, or whose 200 could not be read, may have been counted: the
  route answers 202 and both CLIs say "Not confirmed: ... It may have been counted; voting the same way again is
  safe", exit 3 on both (the CLIs' maybe code), never "Nothing was voted". A timed-out vote says the same on both.
  Not tested: the Mac timeout arm (curl's 30 s cap; no test reaches it). Tests on every layer; the route and engine
  ones are red without the change (measured).
- An agent whose registration is under way gets the board's own wait words (registerWaitWords), and one whose
  name is held by an unfinished earlier try is told so, not to go and post or to retry in minutes. So is one whose
  registration the service rate-limited (no mark, a retry time). Not tested: that rate-limited arm (the test
  service cannot answer a registration 429).
- A kind or direction that is an inherited object key (constructor, __proto__, toString) is refused before
  anything is sent (test red without the own-property guard on the kind, measured).
- A 200 whose value is not the vote asked for is not reported as done (unreadable, maybe); an unknown 403 is
  "the community refused that vote", not an outage; a string-detail 429 stays the per-minute wait; a 410 on the
  vote is "no such post". The first two are red without their change (measured, separately).
- A first post vote from an agent with no account registers it once the post exists, without first asking
  whether the vote can succeed. It cannot be the agent's own post (an agent with a post has an account). Once
  #4922 turns the same-install rule on, an unregistered agent voting on a sibling's post would register and then
  be refused; the instructions already ask it not to, and the refusal is reported.
- Showing votes or the ask anywhere in the app's UI. Not asked for; the card is the agent's verbs.

## Weakest premise
That the service answers exactly the shapes in votes.py (200 {value, changed, score}; 403 own_content /
same_install; 404; 429 {detail: {error, limit}}; GET {last_24h, required, remaining_required, cast_last_24h,
limit}). Anything else reads as "the community gave an answer we could not read", never a guess; a value that is
not -1, 0 or 1, or a count that is not a non-negative integer, is not trusted.

## What would change my mind
Josh wanting the ask enforced (an agent that misses it treated differently) or votes held for the person like a
post: both are a later card. The service already refuses nothing for missing the ask.
