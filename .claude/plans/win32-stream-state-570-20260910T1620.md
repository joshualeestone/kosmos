# win32-stream-state-570 -- a Windows agent's working/idle, from its own event stream (#570, 7c-5)

Addresses #570. Road: `.claude/plans/WINDOWS-ROADMAP.md` §4 and "Do this next" item 2.

## What finished looks like

A Windows agent's card on the board reads WORKING while it is taking a turn and
IDLE when it has answered, instead of UNKNOWN. Measured on the box through the
real task and the real board, not only in tests.

## Why

Since 7c-2 every Windows agent is a STREAMING session, and its row in
`claude agents --json` carries no `status` field at all (measured 2026-09-10:
keys `pid, cwd, kind, startedAt, sessionId, name`). `win32capture` reads exactly
that field, so every Windows card reads UNKNOWN. The supervisor already holds the
agent's stdout, and `--output-format stream-json --verbose` puts every event of
every turn on it -- a better source than the Mac's pane scrape, which guesses
from screen text.

## Measured before designing (claude.exe on this box)

1. Nothing arrives on stdout before the first message: 4s idle on a fresh
   session, 6s on a `--resume`, zero events.
2. Each message is one turn: `system/init` ~50ms after the write, then
   `assistant` (text, tool_use, thinking) and `user` (tool_result) events, then
   exactly one `result` (`subtype: success`, `is_error`). `rate_limit_event`
   arrives mid-turn.
3. Two messages written back to back ran as TWO turns, init..result each, 6ms
   apart. Never batched. `queued_turn_count` was 0 on both results.
4. `claude agents --json` lists the streaming session before its first message,
   and its `pid` IS the spawned child's pid (19300 = 19300), with `sessionId`.
5. Closing stdin: exit 0 in 267ms. stderr was empty throughout.

## Design

1. **`engine/win32streamstate.js` (new).** `stateAfterEvent`: `assistant`,
   `user`, `system/init` -> busy; `result` -> idle; anything else (including
   `rate_limit_event`, other `system` subtypes, garbage) -> no claim. A start is
   idle, a flushed write is busy. NOTHING IS COUNTED: a counter that missed one
   event would be wrong forever; this reading self-corrects on the next event.
2. **The state crosses to the board as a file**, `store.ROOT/win32-state/<key>.json`
   = `{v, state, sessionId, pid, at}`, written write-then-rename, and only on a
   transition. Not over the channel: `snapshot` asks every card every tick, and a
   channel round trip is a ~60ms helper process per agent.
3. **The file is trusted only for the process it describes.** `stateFor(name, live)`
   returns a token only when the file's `sessionId` AND `pid` equal the live row
   from `claude agents --json`. A file left by a dead or earlier process (a
   supervisor killed hard, a crash restart) can never describe the one running now.
4. **The supervisor publishes.** `superviseStreaming` takes an injectable `stream`
   sink (default: does nothing, so no suite writes files); `main()` passes the
   real publisher. stdout is read line by line (UTF-8 safe, a line over a bound is
   skipped whole rather than buffered); stderr is drained and its tail rides on
   the `died` line so a death says why.
5. **The capture falls back to it.** An interactive session's own `status` still
   wins; a status-less row asks `stateFor`. Same tokens (`busy`/`idle`), so
   `status.classify`'s win32 arm is unchanged.
6. **A failed state write** is retried once; if that fails too the file is
   cleared, so the board reads UNKNOWN (honest) rather than a stale state.

## Tests

- `engine/win32streamstate.test.js`: the measured event sequences through the
  publisher; the line reader across chunk splits, a split multibyte character, an
  overlong line; `stateFor` rejecting a wrong session, a wrong pid, a missing pid,
  a wrong version, an unknown token, an unreadable file; write failure -> retry ->
  clear.
- `engine/win32supervisor.test.js`: stdout events reach the sink, a flushed send
  marks busy, a death clears, an OLD child's death after a restart does not clear
  the new one, stderr is drained and its tail is on the `died` event.
- `engine/win32capture.test.js`: a status-less row reads the stream state; an
  interactive status still wins; END TO END through the real `snapshot()`, a real
  state file makes the card WORKING, and a pid mismatch makes it UNKNOWN.

## Weakest part of this reasoning

That one message is always one turn with exactly one `result`. Measured for plain
and tool turns and for two back-to-back messages; not measured for an API error
mid-turn or an interrupted turn. If a turn ever ended without a `result`, the card
would read WORKING until the next event or the agent's exit -- wrong in the
direction of "it is doing something", and cleared by the next message.

## Found in review round 1

The reviewer measured two more turn shapes. An API error mid-turn (a bad model)
still ends in a `result` with `is_error: true`, and so do the local slash commands
`/cost` and `/clear`. So "every turn ends in a result" held there too. They also
measured the EPERM-on-rename comment: 896 of 2,069 renames failed while another
process read in a loop.

- WARNING: `main()`, the one production wiring of the publisher, had no test.
  Deleting its `stream:` line left every test green and every card UNKNOWN. The
  `main()` test's spawn stub now has a pid, and the test asserts the state file.
- WARNING, pre-existing: `/clear` changes a streaming session's id (measured), so
  the ownership join drops the agent from the board. Filed as #2669; it has been
  live since 7c-4 made delivery reach Windows agents.
- NIT: `handle.stop()` dropped the child before its exit, so a clean stop never
  cleared the state. It now does, and a test drives the stop path.
- NIT: one test's "clear" half passed on the `handled` flag, not the guard it
  claimed. Renamed; the stop test above covers clearing.
- NIT: `lineReader` rescanned the whole buffer on every chunk. A 16MB line took
  512ms, blocking the loop that also serves the channel. It now scans only new
  data.
- NIT: a retry armed for one process could fire as the next process's second
  attempt. It now carries a generation.
- NIT: stderr chunks were stringified one at a time, which could split a
  character. The stream now decodes them.

## Not in this slice

- `rate_limit_event` carries `rate_limit_info`; the Mac surfaces a rate limit from
  pane text. Worth a slice of its own.
- Removing an agent does not delete its state file; the pid join makes a leftover
  harmless.
- #2669: `/clear` on a Windows agent changes its session id and it drops off the
  board (pre-existing since 7c-4).
