# boardproof-win-1765: Windows clients verify the board holds the token before sending it

**Posture:** production

Card: kosmos#1765, Windows half. Builds on boardproof-1765 (#6394: the board's `GET /api/board-proof` route and
`engine/boardproof.js`).

## What changes
- `engine/boardproof.js`: `checkBoard(url, token, { timeoutMs, prove })`, the one check the three Windows senders
  share (`boardHoldsToken` with its reason kept, and whether nothing was there: refused, unreachable or timed out,
  as opposed to a listener that answered or reset and could not prove itself).
- `engine/kosmos-report-hook.js`: before its first send, the hook runs the check, once per process (passed or
  failed), within half the first send's bound; each send gets what is left. Not proven: nothing is sent and the
  hook exits 0. SessionStart's loud line tells a board that is down apart from a listener that could not show it is
  your Kosmos.
- `tools/windows/kosmos-cli.js`: every token-bearing request goes through `call()`, which checks first (half the
  request's bound, 0.5 to 15 s). A passed check is kept for the process, per token; a failed one is asked again on
  the next request. Not proven: nothing is sent, exit 1, never "may have happened" (3) and never a retry (including
  `task ran`'s). A board that is down reads as down, as before (and `task ran` asks again, checking each time).
- `tools/kosmos-open-board.js`: checks before the board token goes to the sign-in mint. Not proven, or an enforcing
  board (token on disk) that never answered: nothing is opened and no address is printed (exit 1), as `kosmos open`
  does on the Mac.
- `tools/windows/KosmosLauncher.cs` (source only):
  - `BoardProof`, the same exchange in C#, guards the one place the launcher sends `board.token` (the taskbar
    badge's status read, which keeps to its bound).
  - When the opener refuses (its own exit code 10, never node's crash code 1; no address), or names no address in
    any other way while a board token is on disk, the window shows a page saying so and loads nothing; opening Kosmos.exe again asks again. The browser fallback waits for the opener
    (bounded by the opener's own 20 s wait, check and mint limits) and says it opened nothing instead of "opened in
    your browser".
  - The signed `Kosmos.exe` is rebuilt and re-signed as its own release step.

## Decided
- **Open nothing on a failed check**, not the plain address: the sign-in cookie (the browser's, and the window's own
  web profile's) is scoped to 127.0.0.1, not to the port. Rejected: opening the plain address (what was first asked
  for). Would change my mind: a cookie scoped to the port.
- **Test seam**: `proveBoard` on each sender. A caller that passes its own fetch (or the CLI's hook) is a test and
  gets no check unless it passes `proveBoard`. Rejected: an explicit opt-out in every existing test (about 50 files
  of churn) and proving through the injected fetch (every existing fetch stub would need to answer the proof).
  Weakest part: a future production caller that passed a fetch would skip the check; tests pin that the hook's
  entry, `engine/win32codexsup.js` and the CLI's entry pass none.
- **Fail closed** when `boardproof.js` will not load (it ships in the same engine folder in every bundle).
- **A reset after connect is not "nothing there"**: the listener is there and did not prove itself.

## Not covered (stated)
- The gap between the check and the send (two requests), as on the Mac.
- A page that is already open and signed in (a browser tab, or the window) keeps talking to whatever answers on
  the port if the board goes away under it: its reloads and the page's own polling carry the sign-in cookie, which
  this change does not check. That is the page's and the cookie's to solve, not the senders' here.
- On an enforcing board, a first start slower than the browser fallback's 20 s wait opens nothing (and says so);
  the window waits 120 s, as before. The browser fallback (no WebView2) now shows its box once the opener ends
  (bounded at 60 s), not at once.
- A `board.token` that exists but cannot be read is still treated as no token by the opener (#2007's contract: a
  warning and the plain address). The helper sends nothing then; the launcher's window, which reads the same file,
  is likewise unable to tell.
