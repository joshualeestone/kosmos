# Plan: flag the not-ready federation UI OFF for prod (#3330)

Branch: fed-prod-gate-3330
Author: Mona Lisa (night shift), 2026-09-19
Card: #3330 (claimed:monalisa). Follow-up to #3312 (I built the fed UI). Prod-promote gate for 0.6.82.

## Problem

The #3312 federation UI is merged and LIVE + un-flagged on main (web/index.html: the Add-Project
create/join-external toggle, the two external-door buttons, the invite panel, the join/verify
flow). Federation is only partially functional: transport slice 3 (room-id) is unbuilt, the
coordinator is not deployed, and the /api/federation/* proxy routes do not exist, so the doors open
but messaging does not flow. Because the fed UI sits below #3321 in history, the 0.6.82 cut (which
carries #3321's 3b-check fix) necessarily includes it. Shipping it to PROD = a door that opens onto
nothing. Decision (Splinter, reversible, Josh-overridable): cut 0.6.82 to STAGING as-is; flag the
fed UI OFF for PROD so the real 0.6.82 fixes promote decoupled from federation-readiness.

## Approach (mirror the existing platform gate; no new flag system)

There is no feature-flag system in the app. The closest existing pattern is the Windows platform
gate: a server fact -> a data-* attribute on <html> -> a CSS `[data-...-hide]` rule. I mirror it
using the update channel, which the app already knows:

- `/api/status` returns `sourceChannel` ('staging' | 'prod', server default 'prod'), read on the
  5s status tick (the tick that calls paintBuildMark).
- At that tick I stamp `document.documentElement.setAttribute('data-source-channel', staging?...)`.
  (Placed at the TICK site, NOT inside paintBuildMark, because web.build-marker-2066.test.js lifts
  paintBuildMark against a stub doc with no documentElement.)
- One CSS rule gates the fed entry points:
  `html:not([data-source-channel="staging"]) .pj-mode, #pj-add-ext-person, #pj-add-ext-agent,
   #pj-invite-panel, #pj-join-mode { display:none !important }`.
  The `:not(=staging)` form hides them by DEFAULT (before the channel is known) and on prod, and
  reveals them only when the channel is confirmed staging (a review surface) -- matching the
  server's prod-by-default, so a slow first /api/status never flashes the not-ready UI.

Gated by EXISTING SELECTORS in CSS, so no HTML attribute is added -- which keeps web.add-project.
test.js's exact-markup regexes passing (they assert `<fieldset class="pj-mode">` and the two
`#pj-add-ext-*` buttons verbatim). `#pj-add-agent` (local agent add) and `#pj-create` are NOT gated.

## Why not user-facing / reversibility

Federation is client-only against unbuilt endpoints; hiding it removes a door to nothing. To ship
it to prod (transport + coordinator deployed, or a Josh-approved preview), remove the one CSS rule.
Staging still shows it (the review surface), so the default cut behaviour is unchanged there.

  staging they are shown; the local agent add is never gated. 0.6.82 can promote to prod without
  exposing the not-ready fed UI, and staging keeps it as a review surface.

## Weakest premise

That `data-source-channel` from /api/status reliably distinguishes prod from staging on a real
board. It is the same signal paintBuildMark already uses for the build marker's channel hover, and
the server defaults it to prod, so the failure direction (unknown -> hidden) is the safe one.
