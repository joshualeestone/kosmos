# Plan: standalone site deploy, decoupled from release cuts (#2014)

Branch: deploy-site-2014. Card: kosmos#2014.
Full context is on the card (Josh's ask, the two-site measurement, Baron's review + bless). This
is the in-repo plan record.

## Problem

Josh (#2014): marketing-site changes to installkosmos.com ride full Kosmos software release cuts,
so a copy change waits for a release. He wants web changes on their own track. kosmosplus.com is
already decoupled (publish-kosmosplus-www.sh); installkosmos.com is coupled (deploys only via the
release export, tools/release.sh).

## Why it was coupled (safety, not design)

- #1669: a bare `vercel deploy --prod` from a raw checkout took the site down ~13 hours because the
  checkout has the pages but not the gitignored dist/ installer artifacts, so every install 404'd.
- site_deploy_export does NOT fail-safe on missing artifacts: it prints "carried: no pkg" and
  proceeds (tools/lib/site-deploy.sh). The release path is safe only because the build populates
  dist/ first.

## Change

`tools/deploy-site.sh`: a standalone site deploy that ships installkosmos.com without a software
release, keeping the two safety properties the release path added:

1. Completeness: fetch the CURRENT live artifacts into the checkout's dist/ and verify each by sha,
   then refuse if any is still absent, so a clean checkout cannot recreate the #1669 outage. The set
   is new-install-critical: the current tarball (from latest.json), the macOS pkg triple, the
   Windows zip, tmux-arm64, and the unversioned kosmos-arm64 alias. Historical version tarballs are
   deliberately out of scope (rollback-only).
2. Honest marker: let site_deploy_export carry the artifacts and write .kosmos-release-export
   legitimately (never fabricate it), and refuse if the export did not carry the critical set.
3. The .vercelignore guard (pkg_upload_filter_excludes) exactly as the release runs it.
4. DRY-RUN by default; on --publish, deploy then verify the SERVED bytes by fetching them.

## Review

Baron (release/deploy owner) reviewed and blessed --publish after running the dry-run himself
(exit 0). His BLOCKER (add tmux + the alias to the fetch and the refuse-check) is fixed; his
Decision-2 (Windows-zip name interim, #2008) and Decision-3 (the vercel-prod-deploy-gate hook does
not fire for a nested deploy, so the in-script marker check is the whole guard; hook comment updated
on chaoskosmos-site to name deploy-site.sh as the second scripted deploy) are addressed; the NIT
(-fsSL for redirects) is done. A latent bug the dry-run surfaced (pkg_upload_filter_excludes lives
in pkg-inputs.sh, not site-deploy.sh) is fixed by sourcing both.

## Test plan

- `sh -n` clean.
- DRY-RUN passes end to end: fetches the current tarball + tmux + alias + win + pkg, verifies each
  by sha, builds the export, and both the honest-marker check and the .vercelignore guard pass.
- --publish is gated behind the DRY-RUN and blessed by Baron; it is run only when there is a real
  installkosmos change to ship (Josh's web copy), not as part of this PR.

## Out of scope

The Windows-zip unversioned alias (#2008), the fuller release-vs-site-deploy refactor, and running
--publish itself (a deploy action, timed to Josh's web changes).
