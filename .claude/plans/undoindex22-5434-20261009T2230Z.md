# undoindex22-5434: Undo's switch and index are flushed, and an unreadable index no longer deletes every kept copy (#5434 slice 22)

Addresses #5434. `engine/undo.js`, the two writers slice 13 did not cover:
- `setOn` wrote `undo.json` (the on/off switch) through `<file>.<pid>.tmp` + rename, unflushed. Zero-filled, it reads
  as off: copies stop being kept without anyone choosing that.
- `sweep` rewrote `undo/index.jsonl` (the record of every kept copy) through `<file>.<pid>.tmp` + rename, unflushed.

## Found while doing it (a data-loss path on main)
`sweep` builds the set of blobs in use from the records it can PARSE. An index that has content but yields no record
(zero-filled by a crash, or otherwise unreadable) made that set empty, so the sweep deleted EVERY kept copy as
unreferenced: every file Undo could have restored, gone, the next time the board swept.

## Change
- `setOn` -> `store.saveFlushed`; the index rewrite -> `securewrite.writeSecret(index, data, 0o600, { atomicOnly: true })`.
- `sweep` (review 1 sharpened this): when the index yields no record, collect nothing if the index CANNOT BE READ
  (any error but ENOENT: its records are intact and restorable) or has content but no parsable record (zero-filled).
  Dead `.tmp` blobs are reaped either way. An EMPTY index, and a readable index whose records no longer use a blob,
  still collect (controls). A torn last line from a crash mid-append still parses the lines before it.
- `store` exports `saveFlushed` (the identical one-line change as slices 17-21).
- New `engine/undoindex.fsync-5434.test.js` (7 tests), in `tools/windows-tests.js`.

## Decided
- **The two held states differ, and the code says so (review 1).** An UNREADABLE index (EACCES, EIO, EISDIR) holds
  every copy until it reads again: those are restorable. A ZERO-FILLED index holds its copies until the first sweep after
  the next record is appended (sweeps run at board start and at most daily; review 2); then it collects as usual. Its records are gone, so Undo cannot restore those copies;
  holding them forever (or until any damage is cleared) would keep files nothing can restore and let one torn line
  block collection permanently. Rejected for that reason: a damaged-line counter that blocks collection.
- **Partial damage (some records parse, the rest zero-filled) behaves as on main:** the parsed records keep their
  copies, the lost records' copies are collected. Not made worse; not fixed here.
- **Not in this slice:** the append in `keepOpen` (an appended record a crash loses is one copy's record, and a torn
  line is already skipped) and slice 13's areas (restore, blobs, moveAside).

## Tests
- the switch flushed before its rename; the index rewrite flushed before its rename, at 0600; a zero-filled index
  keeps every kept copy; controls: an empty index and an index that no longer refers to a blob still collect it.
- Mutation: main's undo.js + store.js fail 3 of 4 (the control passes on main, as it should). Related set (66 files,
  list5434s22.txt): 2045, 0 fail, 3 skipped.

## Weakest premise
That "content but no parsable record" is never a legitimate state worth collecting from. The writer only ever writes
JSON lines; anything else is damage, and keeping blobs is the recoverable side of damage.
