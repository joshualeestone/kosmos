# startupfiles-5774: the token-only guard denies the home folder's shell startup files (kosmos#5774 part 2)

## Why
#5774 route 2: shell startup files. Kosmos launches agents with --dangerously-skip-permissions, so a token-only agent's file tools can write any path no deny rule names. The home folder's shell startup files are read by every shell the same user starts outside the sandbox: anything that runs zsh (.zshenv, even non-interactive), a login shell, the person's own terminal, and each agent's shell snapshot. The sandboxed shell already cannot write the home folder (its write scope; setup-assistant drops additionalDirectories, allowWrite and excludedCommands), so the gap is the file tools'.

## The change
- `shellStartPaths(home, env, opts)` in engine/setup-assistant.js returns the files, the folders read whole, the permission-layer globs, and what it cannot work out:
  - zsh: .zshenv .zprofile .zshrc .zlogin .zlogout, each with its compiled .zwc, in the home folder and in every ZDOTDIR found. ZDOTDIR comes from the environment, from ~/.zshenv, and from each ZDOTDIR's own .zshenv (bounded to 8 rounds), and the conventional <XDG>/zsh is always included. Completion dumps (.zcompdump*): a glob in the home and each ZDOTDIR (the file tools), plus existing dumps by name in a ZDOTDIR that is not anywhere under the home (both layers).
  - ~/.ssh/rc (run by sshd outside any sandbox; review 13). tmux's config is already denied as a launch rule (#5516).
  - bash and sh: .bashrc .bash_profile .bash_login .profile .bash_logout .bash_aliases, and the file $BASH_ENV or $ENV names. csh and tcsh: .cshrc .tcshrc .login .logout.
  - XDG_CONFIG_HOME: ~/.config always, plus the environment's, plus one ~/.zshenv sets. fish's and nushell's folders are denied whole under each, with nushell's macOS default (~/Library/Application Support/nushell).
  - User-writable startup folders outside the home, where they exist: Homebrew's zsh site-functions and fish vendor_conf.d, vendor_functions.d and vendor_completions.d, under /opt/homebrew and /usr/local.
  - Links inside the whole folders are followed (3 levels deep; one budget of 500 links and 50,000 entries read, which names itself when spent), and every file goes through withTarget, so each target is denied too: a linked folder gets a whole-folder rule. Targets in a Homebrew Cellar or Caskroom are covered by one stable rule for that folder, only for the one a target is in.
  - Files are read as regular files only, up to 256 KB.
  - ${XDG_CONFIG_HOME:-default}, ${HOME:-default} and ${ZDOTDIR:-default} (and the :=, - and = forms) are read as both arms, with a plain ${HOME} or ${XDG_CONFIG_HOME} inside the default unbraced first; a brace left over is named.
  - A target that is truly read-only (not writable now, not owned by this user, in a folder this user cannot write: a read-only store such as /nix/store) is not listed: it protects nothing and its hashed name would pile up. The LINK to it is kept, for the file tools only (review 10).
  - A Homebrew Cellar or Caskroom under any prefix is found from a target's <prefix>/Cellar/<name>/<version>/ shape (Linuxbrew, ~/homebrew), not only under /opt/homebrew and /usr/local.
  - A folder to be denied whole that is the root, the home folder, or holds the agent's own folder (a link pointing there) is named instead of denied (review 6), since its rule would take the agent's own work.
  - What it cannot work out is named, so the guard is not whole: a relative BASH_ENV; a path-like relative ENV; a relative or unexpandable ZDOTDIR or XDG_CONFIG_HOME; a quote in the middle of a value.
- Both layers: the file tools' Edit rules, and the sandbox denyWrite through realOrLeaf.
- Tests: engine/startupfiles-5774.test.js, 30 tests, each fix mutated red (counts per iteration below).

## Decided
- Both layers, though the shell's write scope already refuses the home folder: consistent with part 1, and it covers a linked target that sits somewhere the shell can write. Cost, measured on this host at 618fdb5e6 (review 9 asked for a re-measure after the Cellar rule) with its real Homebrew folders, a linked .zshrc, ZDOTDIR set in .zshenv and BASH_ENV: 58 more denyWrite entries (132 against 74; 8.4 KB against 4.6 KB as JSON) and 66 more deny rules. The guard's own profile-size check (#5663) still passes.
- Homebrew's links point into its Cellar by VERSION (review 5). The deny lists only grow, and only launch rules are pruned, so following each target would add new versioned paths at every upgrade, for good. Each prefix's Cellar is denied whole instead: one stable rule, in both layers, which covers every version. Neither the agent's file tools nor its shell has any business writing there, and brew's own writes are not governed by deny rules (the sandboxed shell cannot write /opt/homebrew anyway).
- Link scanning shares one budget: 500 links (links into a Cellar or Caskroom do not count) and 50,000 entries read. When it runs out, the guard says it is not whole.
- The environment read is the board's own (deps.env or process.env): agents are launched from it, so it is what their shells see. Weakest premise: a launch that sets ZDOTDIR or BASH_ENV differently for one agent is not seen.
- Claude Code's own writes are not affected: deny rules govern its tools, not the app's own code (an installer or updater adding a PATH line still works).
- Not covered here: system-wide startup files under /etc (root-owned, not writable by the agent), and files a startup file pulls in (`source ~/x`), which is route 3 ("what start-time files pull in"). User-writable startup folders outside the home (Homebrew's zsh site-functions and fish vendor folders, review 3) ARE covered, where they exist.

## Gaps, stated
- A shell beyond zsh, bash, sh, csh and tcsh, fish and nushell is not listed (ksh's .kshrc, xonsh, PowerShell profiles); nor ~/.inputrc (key bindings, not code).
- ENV=rc (a bare name with no slash) is read as a label and skipped (review 2), which fails open, but only for an interactive sh. ENV=prod/us (a label with a slash) reads as a relative path and is named, which fails closed (review 12).
- Link targets that carry a version or a hash, outside a Homebrew Cellar or Caskroom and outside a read-only store (an asdf or mise shim folder, a store that rotates writable names), are listed by name, and can pile up at upgrades. DECIDED (review 12): rare among shell startup files, and capping it would need pruning these rules, which only launch rules have today.
- Dumps by name in a ZDOTDIR outside the home can pile up at zsh upgrades (rare; accepted in review 11).
- A ZDOTDIR or XDG_CONFIG_HOME set on an INDENTED line (inside an if, a function or a here-document) is not read (review 6). On a top-level line every form is read (review 14): `[[ ... ]] && export ZDOTDIR=x`, `typeset -x`, a second assignment, `: ${ZDOTDIR:=x}`. The conventional XDG folder is covered regardless.
- Links inside a linked folder are followed (review 19), within the same three levels and link budget as any folder.
- Other guard tests that pass neither deps.env nor deps.userShellDirs read this host's environment and Homebrew folders. Decided, not pinned in their nine files: only a relative BASH_ENV, path-like ENV, ZDOTDIR or XDG_CONFIG_HOME in the host's environment can change their result, and it fails closed. Homebrew targets are now covered by a stable Cellar rule rather than by name.
- A completion dump that does not exist yet, in a ZDOTDIR the shell can write, is covered by the file tools' glob only.
- A WRITABLE linked target whose path has a rule-syntax character (a dotfiles repo under `~/Dropbox (Personal)`) is named, so the guard is not whole and creation fails; review 19 made this true on every route (a home dotfile, a target found inside a startup folder, and a link on the way), where before only the first was named and the others stopped the whole guard with a message blaming the agent's folder. DECIDED, not changed: the file tools cannot be denied that target, so it is a real gap, and config files already behave the same way. The sandbox layer still carries it.
- ZDOTDIR set in /etc/zshenv is not read (root-owned); the conventional XDG folder is covered regardless. A column-0 assignment inside a here-document is read (it may give a false "not whole" when relative).
- A ZDOTDIR or XDG folder through any variable other than HOME, XDG_CONFIG_HOME, XDG_DATA_HOME and ZDOTDIR ($XDG_CACHE_HOME/...) is named, so not whole (review 16). Review 17 made XDG_DATA_HOME readable: it is now read from the environment and from every startup file, so resolving it no longer misses a value .zshenv sets.
- XDG_CONFIG_HOME and XDG_DATA_HOME are read from the home's .zshenv, .zprofile, .zshrc, .zlogin, .profile, .bash_profile, .bash_login and .bashrc, and from each ZDOTDIR's zsh files (review 17). A value set in a ZDOTDIR's files moves fish, nushell and the data folders, but does not add another conventional <xdg>/zsh folder (zsh has already chosen its folder by then).
- A content-addressed store other than /nix/store (a custom Nix store path, Guix's /gnu/store) is not recognised: a writable target there is listed by name and can pile up (review 17; read-only ones are filtered either way).
- Per-user drop-in folders other than ~/.bashrc.d (Fedora's default .bashrc runs it, review 16) are each a person's own convention (~/.zshrc.d, ~/.profile.d): not listed. Login items (~/Library/LaunchAgents, ~/.config/environment.d) are not shell startup files and stay with route 3 on the card.
- A link a chain passes through (review 18) is denied to the FILE TOOLS only: the sandbox side resolves every path to the chain's final target, so it cannot name the link itself. The sandboxed shell cannot write the home folder; a hop outside the home inside the shell's own write scope is not covered by the sandbox layer. Chains are followed 8 hops, and only at the leaf (a linked parent is resolved, not listed).
- Route 3 and on stay on the card.
