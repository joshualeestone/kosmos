# cutguard-flake-5914: wait for a stand-in process before its command goes into a marker

Card: kosmos#5914. Task 10 of Kosmos Inside Out.

## What finished looks like
1. The cause of the one red control ("#4498 CONTROL: a plain run did not queue") is named, from a reproduction or
   from the code path.
2. The control cannot fail that way again, or it prints what the guard read when it does.
3. The full suite is green and a pull request is open.

## Cause
A race in the test, not in the queue. `tools/test-cut-guard.sh` starts a stand-in with `sleep 60 &` and reads its
command with `ps` on the next line. For a moment after it starts, a new process still shows the command of the
script that started it. `_kosmos_suite_waiter_live` (tools/lib/cut-guard.sh) deletes a marker whose recorded
command differs from the live one, so the plain run finds nobody waiting and does not queue.

Measured by me: the early read happened 0 times in 400 on an idle box and 1 time in 600 with every core busy. The
whole control going red was not reproduced; that step is read from the guard's code.

## Change (tests only)
1. `q_ready <pid> [glob]` moves to the top of `tools/test-cut-guard.sh` and is called at every site that records a
   stand-in's command.
2. A check at the end of the file fails when a process is started and its command read within eight lines with no
   wait before the read. Two controls remove waits and expect the check to name them.
3. `tools/test-browser-run-guard.sh` gets the same wait at its one site.

## Decisions
- **Chosen:** fix the test's stand-ins and add a tripwire for the shape.
- **Rejected:** changing the product's stale-marker rule. A real waiting run marks its own process long after it
  has started, so the product cannot hit this.
- **Weakest part:** three stand-ins are read through a helper function, so their waits can be removed without the
  check noticing. The check is a tripwire, not a proof.
- **What would change my mind:** the same control going red again with every wait in place. Then the cause is
  somewhere else and the marker's contents at the moment of failure are the next thing to print.
