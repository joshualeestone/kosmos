# dm-tapreact-718: tap to react in the agent DM on a touchscreen

Addresses #718 (Josh, 2026-09-24: "really flesh out all the native mobile apps and pay close attention
to make sure the designs fit well on mobile"). Assigned by Liu Kang (m888): generalise Kano's room
tap-to-react (#3809) to take a container, with a browser check and a control.

## Finished looks like

On a phone (any touchscreen), a tap on an agent's message in its Direct Message opens the same
reaction bar the room opens, every emoji in it takes its own tap, and the bar closes the same ways as
the room's. The room behaves exactly as before, and a mouse on a computer is unchanged.

## What changed

- `web/index.html`, script: the room's handler now serves two threads (`RXN_HOSTS`: `#pj-room`,
  `#d-dmthread`). `RXN_SHOW_HOST` names the thread holding the open bar (unset means the room, so
  anything that sets `RXN_SHOW_POST` by hand, as Kano's check does, behaves as before). A DM row is
  keyed by its message's `at` (`data-at`; a DM row has no id) and scoped to the agent whose page is
  open (`CURRENT.sessionName`), a room row by post id and the project. The visible band's bottom edge
  is the DM's composer bar (`#d-talk-box .dmbar`) for the DM. Tap, repaint observer, focus flip,
  close and the outside-tap closer all take the thread from the event or the state.
- `web/index.html`, CSS: `#d-dmthread` twins of the room's `(hover: none)` rules, appended after the
  room's so none of the lines `web.room-phone-718.test.js` pins move. Only an agent's DM rows carry
  reactions, so the bar always starts at its bubble's left. The open row's lift is 1, under the DM's
  sticky composer bar on a phone (z 4, from #3882).
- `docs/browser-checks/render-dm-tapreact-718.js`, README row, `tools/browser-checks.sh` list.

## Rejected

- One `:is(#pj-room, #d-dmthread)` selector per rule: shorter, but it rewrites the exact room lines
  Kano's unit test pins, for no behaviour gain.
- A second, DM-only handler: two copies of the placement and close logic would drift.

## Weakest parts, named

- The DM's composer edge in the visible band (`#d-talk-box .dmbar`) is NOT isolated by any arm: in
  every layout measured the thread ends where the composer bar begins, so the thread's own edge already
  keeps the bar above it (a control that points the band at the room's composer stays green; the
  tall-message arm proves the behaviour). It is kept as the right element for the job, a backstop.
- Touch is emulated (Playwright hasTouch). Real iOS sticky hover, and the bar under a real keyboard,
  are on Johnny's simulator list. WebKit is an engine approximation, not Safari.
- #3882 (the DM's sticky composer, z 4) merged as 17a2b5529 and this branch is rebased onto it; every
  number above was measured on that base.
