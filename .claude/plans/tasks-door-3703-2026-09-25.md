# Plan: #3703 -- one list screen: the project View-all door opens the Tasks view; + New task there (April)

Author: April, 2026-09-25 (night shift). Branch `tasks-door-3703` off main caaf2e90. Follow-up to
#3559 (merged #3701, 692869fb), whose plan deferred exactly these two items.

Source of truth for the look: Mona's mock, `chaoskosmos-site` `tasks-view-3559`
(`design/tasks-view.html`): one list screen, and a primary `+ New task` button in the head beside
the title (`.mh` / `.newbtn`).

## 1. The View-all door opens the Tasks view, scoped to its project
- `#pj-alltasks` ("View All", no count) keeps its place and label on the project page. It now calls
  `openProjectTasks(PJ_CURRENT)`, which sets the Tasks view's scope to that project and opens the
  view:
  - in the tab layout, `showTab('tasks')`;
  - in the consolidated layout, `openConsolidatedTasks()` (in the display column, as the old
    screen was).
- Opening from a door is a fresh look at that project. The scope is the project, and the window
  resets to All (the old screen showed every task, closed included), along with search and tile.
  Group by and Sort are the person's own settings and are kept.
- The way back is the crumb that already exists: `All tasks › <project> · Open project`.
- Fix found while reading: `tskPaint` drops `TSK.proj` when the project is not in the data. It also
  did so BEFORE the first read (data null), which would wipe the door's scope on the arrival paint.
  It now drops it only once data is loaded.

## 2. Retire the old screen (`#pj-alltasks-view`)
It becomes unreachable once the door moves, and dead code that looks live is a trap.
- Remove:
  - the markup (`#pj-alltasks-view` and its children);
  - `openAllTasksView`, and the `alltasks-back` and `alltasks-list` listeners;
  - its CSS (`#pj-alltasks-view`, `#alltasks-*`);
  - `'alltasks'` from both pjView lists;
  - the `asbScreen` line for it (Tasks already reports `{screen:'tasks'}`).
- Keep `#pj-alltasks` (the door) and its label/count painter in `paintProjectTasks`.
- Tests and checks that exercised the old screen move to the new destination rather than being
  deleted blind. Each is read first and migrated or retired with a stated reason (see the ledger in
  the PR).
- The route `GET /api/tasks?project=` stays: `kosmos tasks` and the engine tests use it.

## 3. + New task from the Tasks view
- A primary `+ New task` button (`#tsk-new`, `btn uprime`) in `.tsk-head`, beside the title, as in
  the mock.
- It opens the existing New task dialog (`#nt-modal`), not a new form:
  - **A project is picked** (rail or dropdown): the dialog is for that project, exactly as from the
    project page.
  - **All tasks is picked:** the dialog shows a `Which project` select (`#nt-proj`) listing the
    non-archived projects. Changing it rebuilds `Who is on it` from that project's members. What
    you typed stays: it is one draft being aimed.
  - **No projects at all:** the button still opens, and the dialog says to make a project first
    rather than showing an empty picker.
- `openNewTask(projectId, origin)` replaces the zero-argument form. The project page passes nothing
  and behaves as before. The listener is wrapped, so the click Event is never read as a project id.
- On create from Tasks:
  - the dialog closes and focus returns to `#tsk-new`;
  - the view re-reads (not an arrival, so ticks stay);
  - `#tsk-msg` says `Added task N to <project>.`, plus the heard sentence when an agent was told.
  - The project page path is unchanged (pjReload + `pj-one-msg`).

## Decisions (reversible)
- One PR, not two. Moving the door without retiring the screen fails the checks that click the door
  and expect the old screen. Retiring the screen without moving the door removes a working screen.
  The two only make sense together.
- The door opens with window All. The old screen listed everything, and a person arriving from
  "View all" who sees fewer because of a window they set last week would read it as missing tasks.
- No "back to project" button is added. The crumb's `Open project` already is one, and adding a
  second would be two ways to say one thing.
- A view scoped to an ARCHIVED project (its own door) files "+ New task" there without the
  picker, as that project's own page does. The All-tasks picker leaves archived projects out,
  because that list sets them aside. Someone standing in the project chose it.
- On All tasks the draft is never wiped by the dialog's own default pick: the draft follows the
  pick, and only who is on it resets (as when the person changes it).
- Accepted, rare: with no project to file to, the who list is reset, so a draft kept for a
  project loses its assignee; and a scope to a project that has since been deleted opens the
  picker (visible) rather than naming the missing project.
- The door's scope stays after leaving the view, like a rail pick does. Tasks from the tab bar
  shows the last scope, and "All tasks" in the rail clears it.
- The dialog's accessible description follows its mode (`#nt-in`, `#nt-in-pick`, or `#nt-msg`),
  because a hidden element named by aria-describedby is still read.
- Weakest premise: that nobody relies on the old screen's plain Open/Closed list look. It was the
  #3171 design, and the Tasks view shows the same information grouped. Mona reviews the look.
