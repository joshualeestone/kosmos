# linuxclaude-5419: Linux downloads Claude Code (slice 1 of #5419, Kosmos Cloud #4903)

## Why
On Linux the board refused to download Claude Code ("this platform (linux) has no published Claude Code build").
Kosmos Cloud v1 is Claude first (#4903), and a fresh Linux server could not get Claude Code through Kosmos at all.

## Measured
Anthropic's release manifest publishes linux-x64, linux-arm64, linux-x64-musl and linux-arm64-musl
(downloads.claude.ai/claude-code-releases/2.1.292/manifest.json, read 2026-10-06), each with a sha256.

## Change
- engine/platform.js: CLAUDE_DOWNLOADS gains 'linux'.
- engine/connect.js `platformKey`:
  - linux maps to `linux-<arch>`, or `linux-<arch>-musl` when musl's own loader is present and Node's report does not
    name a glibc (the rule as reviews 1 and 3 left it; see Review decisions).
  - Musl is detected only when actually on Linux; there is a seam for tests.
- The rest of download() is unchanged and platform-neutral:
  - the manifest checksum is verified before the binary is placed;
  - the file is chmod'ed executable;
  - a key the manifest lacks is refused.

## Not this slice
The provider runners (OpenAI's Codex, Gemini, Grok, Muse) on Linux are slice 2. Each needs real Linux pins with
registry checksums in runners.js. That is about 29 of the card's 66 failures.

## Weakest premise
That `claude install`, run from the downloaded binary, places its launcher under HOME on Linux as it does on the
Mac (connect.installClaudeCode). To be checked by the Linux CI lane (#4919).

## Validation
- engine/connect.test.js, engine/platform.test.js, engine/platform-gate-wiring.test.js.
- The full suite through the queue.
- /challenge-loop.
- The Linux lane's connect tests on ubuntu.

## Review decisions (challenge loop)
- **runners.install('claude') stays darwin-only (review 1, parity).** Windows installs Claude Code through
  connect.download, not runners.install, and is refused there today; Linux now follows the Windows path. Provider
  runners on Linux are slice 2.
- **The install-and-resolve step on Linux is unverified here (review 1, deferred).** `claude install` placing its
  launcher at ~/.local/bin/claude needs a real Linux machine; it is checked in the Linux CI lane (#4919), which is
  this slice's weakest premise as stated above.
- **An arch Anthropic does not build keeps its own key on Linux** (linux-riscv64 and so on), so download refuses
  with "no build for this kind of computer" rather than placing an x64 binary.
- **musl detection** reads Node's report; with no readable report, musl's own loader file decides. Cached once.
- **Sign-in on Linux (review 2, a second weak premise, stated):** after the download, sign-in uses the tmux host, as
  on the Mac, with the launcher's exported tmux pick when it is runnable (install/kosmos sets AGENT_WORKFORCE_TMUX_BIN
  on every board it starts, but on Linux with no tmux server yet it falls back to a bundle path that may not exist, so
  an unrunnable pick falls through to create's picker: review 6); a board started another way now gets the tmux on PATH, not Homebrew's path. Nothing here runs that
  sign-in on a real Linux machine, and tmux's argument handling under glibc is unmeasured: the Linux CI lane (#4919)
  and piece D's end-to-end check are where it is proven. If it fails there, the screen must stop offering the
  install on Linux until it works.
- **The manifest measurement:** downloads.claude.ai/claude-code-releases/2.1.292/manifest.json, read 2026-10-06,
  lists linux-x64, linux-arm64, linux-x64-musl and linux-arm64-musl, each with a sha256 (moved out of platform.js).
- **canInstallClaude is not gated behind a flag until the Linux lane passes (review 3, decided).** No person can
  reach it yet: a board cannot be installed on Linux until piece D (#4920) lands, and D plus the CI lane (#4919) run
  the download, install and sign-in end to end before Linux ships. A flag would be a second answer to "can Linux
  install Claude". Changes my mind: D landing before #4919 proves the install and sign-in.
- **musl** is chosen only with musl's loader present: a report without glibc alone is not enough (review 3).
- **tmux for sign-in on Linux** is create's #4917 picker (PATH plus /usr/local/bin, /usr/bin, ...), then bare tmux.
- **What the checksum does and does not prove (review 4):** it proves the downloaded file is the one Anthropic
  published for that key, intact. It does not prove the key fits this machine: a wrong musl guess downloads a
  verified build that will not run, and shows as a failed `claude install`. That is why musl needs the loader as well.
- **No tmux on Linux is refused before the download (review 5).** Sign-in and every agent run in tmux, so a Linux
  host with none found gets a plain sentence and no 200MB download. The check runs only on a real Linux host (a test
  drives platform 'linux' from a Mac); the pure check is tested here, the wired one in the Linux lane.
- **The tmux guard in download() is tested as wired (review 6)**, through a test seam, on every platform: it refuses
  before any request reaches the download service. The install offer on Linux stays decided as above (review 3).
- **The install offer is the gate's answer only (review 9 reverses review 8):** hiding it on a Linux box with no tmux
  left a screen with no button and no reason (web/index.html has Linux-blind copy) and walked the filesystem on every
  state poll. download() refuses before any bytes move, in a sentence the screen shows. The no-tmux sentence claims
  sign-in only: agents take create.binPaths' own tmux pick, which still trusts the launcher's bundle path on Linux,
  and that is piece D's (#4920), as on piece B.
- **What runs the Linux-only paths:** .github/workflows/linux.yml (#4919) runs the node suite, connect.test.js
  included, on ubuntu-latest with tmux installed, so the #5419 tests run on a real Linux host there.
- **The Linux lane on this branch (review 10):** linux.yml runs only on dispatch or linux-ci-* branches, so it was
  dispatched against linuxclaude-5419 (run 37563836935, 2026-10-07 02:49Z). Its result is read before merge; the
  lane is red by design for other cards' files, so the reading is connect.test.js and platform tests, not the colour.
- **The agent path's tmux pick on Linux** (create.binPaths trusting the launcher's bundle path) is written into
  piece D's plan (#4920), which owns the Linux tmux pick.
- **No tmux at sign-in, not only at download:** Claude may already be installed, so launchSignin asks the same
  question (tmuxMissingForSignin) before the tmux host runs, and goes stuck with the same sentence. Every test file
  that reaches download or sign-in on the host platform pins the check to "present".
- **The Connect screen's stuck copy on Linux** (its way out says open Terminal, Mac-shaped) is #5449.
- **The lane reading behind linux.yml's header (measured 2026-10-07 03:05Z):** run 37563836935 on this branch had 84
  failing test names; mapping each name back to its file, engine/connect.test.js, connect.install-997, connect.nobinary-1580
  and connect.hookwiring-1569 hold none of them (0 each), while engine/runners (22), server.runners (4) and
  engine/muserun (2) do. Log kept at ~/.cache/ick-validation/lane-5419.log.
- **No tmux blocks the flow even when only the Claude binary is missing (review 17, decided).** Every Kosmos agent runs
  in tmux, so reinstalling Claude for a signed-in person without tmux leads nowhere; the plain sentence now beats a
  dead end later. Pinned by a test with Claude installed. runners.install('claude') says at its gate why it stays
  darwin-only (Claude installs through connect.download; provider runners are slice 2).
