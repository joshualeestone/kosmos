# setupfsync11-5434: the guard's Claude Code settings saves flush before they rename (#5434 slice 11)

Addresses #5434. From the rename inventory on #5434: `engine/setup-assistant.js` writes three Claude Code settings
files with `writeFileSync(<file>.<pid>.new)` then `renameSync`, no flush, so a crash could leave one at full length
but zero-filled (#5431). Claude Code cannot parse a zero-filled settings.json, so the agent would start with NO
sandbox: the guard this file exists to write would be gone.
- `guardGuideFolder` (:602): the guide's `.claude/settings.json` (sandbox, deny rules).
- `guardTokenOnlyFolderNow` (:1604): a token-only agent's `.claude/settings.json` (the board-token guard); the
  agent's folder can be the person's own.
- `cleanLocalSettings` (:1688): that agent's `.claude/settings.local.json`, keys that would undo the guard removed.

## Change
- One helper, `saveSettingsFile(file, text)`: `securewrite.writeSecret(file, text, mode, { atomicOnly: true,
  ownTempsOnly: true, umaskDefault: true })`, mode = the existing file's `stat & 0o7777`, null for a new file.
  The three sites call it; it throws as the old writes did, and each caller answers as before.
- New `engine/setupsettings.fsync-5434.test.js` (18 tests: slice 9's six arms for each writer), in
  `tools/windows-tests.js`.

## Decided
- **The same options as engine/groksettings.js / geminisettings.js / reporthook.js (slice 3)**, the other Claude Code
  and provider settings writers: an existing file keeps its mode, a new one takes the umask default.
- **That is a small mode change:** the old writers let the temp's umask mode replace the file's, so a settings.json a
  person had made 0600 was widened to 0644 on every guard refresh. Now it stays 0600. Narrower, never wider.
- **The temp:** unique and `wx` (the old `<file>.<pid>.new` was the same name for two saves in one process, and
  followed a link planted there). `ownTempsOnly` is the one new delete path in that `.claude` folder (this file's own
  dead temps only); old `.<pid>.new` leftovers are not reaped.
- **A save whose rename keeps failing writes the file three times before refusing** (small files).
- **Not in this slice:** the other setup-assistant renames (:1187 launch record, :1398/:1412 guard-state file),
  which are Kosmos's own records (inventory group 3), not settings Claude Code reads.

## Tests
- per writer: the temp is flushed before its rename; an existing file's mode is kept under umask 077 (POSIX); all
  atomic attempts refused leaves the file as it was and the guard reports failure; a link planted at the temp name is
  not written through or removed (POSIX); only this file's own dead temps are reaped (another file's and a live
  writer's survive); a failed flush refuses the save and leaves the file and no temp.
- Mutation: main's setup-assistant.js fails all 18 (the mode arms too, since main did not keep the mode).
  Related set (89 files, list5434s11.txt): 2600, 0 fail, 4 skipped.

## Weakest premise
That nothing depends on these files taking the umask mode at every refresh. The guard writes rules, not
permissions; Claude Code reads the file at any mode it can read. What would change my mind: a reader that needs a
mode wider than the person set.
