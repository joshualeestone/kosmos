# servedver-6738: every site deploy serves a served-versions table that includes its own pointers (kosmos#6738)

## What was wrong
The site's admin "version not yet served" rule (#6732, `api/_ours.js`) reads `api/_servedversions.js`, generated by the
site's `tools/served-versions.sh` from the git history of `dist/latest*.json`. Nothing regenerated it when a pointer
moved, so a just-released version counted as served from the table's last row on, and its release-test pings as real.

## Call (differs from the card's literal ask, on purpose)
Rebuild the table INSIDE THE DEPLOY EXPORT (`tools/lib/site-deploy.sh`, `_site_served_versions`, called by
`site_deploy_export` right after the archive is extracted), from the history of the exact commit being deployed:
`GIT_DIR=<site .git> bash <export>/tools/served-versions.sh <sha>`. The pointers in the export come from that commit,
so the table always includes them, for EVERY deploy path (release.sh step 8, deploy-site.sh, a promote's deploy),
not only release.sh. It never writes the shared site checkout.

## Rejected
- The card's ask, a regenerate-and-commit in release.sh's site step: a commit cannot hold its own row, so it needs
  a second commit and a second push in the cut's race-handled site commit (site_commit_on_fresh_main), and it covers
  release.sh only; promote-channel.sh, publish-kosmos-windows.sh and deploy-site.sh move or ship pointers too.
- Refusing the deploy when the generator fails: a stale admin count is not worth blocking a release. It WARNS, and the
  committed table ships unchanged (kept aside before the run and restored; review 1).

## Weakest premise
The served table is correct, but the COMMITTED table in the site repo still lags until someone runs the generator. Any
reader of the repo file (not the served page) sees the old rows. The admin page's "table is behind" warning compares
what is served, so it stops firing.

## Tests

  deployed commit moved (CONTROL: the committed table at that commit lacks it); the rebuild line names the commit and
  row count; the shared checkout is untouched byte for byte; CONTROL a commit with no generator ships its table; a
  failing generator warns, does not refuse, and the committed table ships.
- MUTANTS: the call removed (3 red); GIT_DIR dropped (2 red).
- The REAL site generator, copied out of the repo and run with GIT_DIR (as the export runs it): rc 0, 454 rows ending
  with today's 0.7.61 pointers; the site checkout untouched.
- tools/test-site-deploy-export.sh still 0 failures.

## Review round 2 (blind, sonnet)
- [WARNING] `want=$(grep -c ...)` / `rows=$(grep -c ...)` abort under a caller's `set -e` when they count 0 (grep -c
  prints 0 and exits 1); today masked because both callers run site_deploy_export inside `||` --> FIXED: every command
  that can exit non-zero for an expected reason is guarded (`|| true`, cp checked, mktemp warns), one temp DIR beside
  the export removed on every path, and an explicit `return 0`.
- The new bare-under-`set -euo pipefail` test then found a SECOND defect the reviewer did not name: `local ... out="$2"
  ... tab="$out/..."` on one line. bash 3.2 (/bin/bash, what release.sh's shebang runs) expands every word of a
  `local` before assigning any, so under `set -u` that reads `out` unbound (measured: `local a="$1" b="$a"` -> "a:
  unbound variable"). MEASURED, NOT ASSUMED: it never hit a real deploy, because called from site_deploy_export `$out`
  resolves to the caller's own local of the same name and value (bash's dynamic scope). I first wrote that it "would
  have aborted every deploy"; that was wrong, corrected here. FIXED: tab is assigned on its own line.
- [NIT] mktemp failures were silent --> FIXED (a warning). [NIT] temp files leaked on a signal --> one dir now, still
  no trap (the caller owns traps; a signal mid-deploy leaves one small dir beside the build root).
- [NIT] the plan credited the generator's temp file with protecting the table --> the keep-aside is the guarantee.
- Tests 11/11 under /bin/bash (the new case: called bare under set -euo pipefail, no committed table, zero rows).
