# dailylog-asides-5866: set-aside and unreadable conversation files no longer cost the daily log its days

Card: #5866. Built on #5855 step 1 (#5878), as the sequencing note on the card asked.

## What was wrong (on main before this)

`engine/chat.js` sets a thread file aside, beside it, in two cases besides the rollover: `.superseded` (the file
belonged to an earlier project of the same name) and `.damaged` (it would not parse). `engine/dailylog.js` saw
neither. A full run then pruned every daily file whose messages now lived only in such a file, and rewrote a shared
day without them. A thread file that could not be read when its turn came stopped the prune but not that rewrite.

## Measured before building (Liu Kang, m4976: can a superseded file overlap the live one?)

Driven through the real writer in a sandbox:

| After | Set-aside file | Live file |
|---|---|---|
| two messages under one project | none | 2 rows |
| one message under a later project of the same name | the 2 earlier rows | 1 new row |
| a second | the same 2 | 2 new rows |
| a message onto a thread file that will not parse | the unparseable bytes, as `.damaged` | 1 new row |

A superseded file is the whole earlier file, renamed; the later project's file starts empty. **No row is in both.**
Rows carry no id (`at`, `text`, `from`, `wire`, `delivery`), and two real rows can share one `at`, so there is
nothing safe to dedupe on. Agreed with Liu Kang (m4978): no dedupe, a test through the real writer, a separate
heading.

## The change (`engine/dailylog.js`)

1. **A `.superseded` file is read as a conversation of its own**, under its own heading (the thread's label plus
   "(an earlier project of this name)"). Its days are written and kept like any other.
2. **Messages that cannot be known hold the daily files that may contain them.** A held daily file is neither
   rewritten nor pruned. Three sources:
   - a thread file (or a `.superseded` file) that could not be **read** this run: nothing bounds what it holds, so
     every existing daily file is held;
   - a `.damaged` file, or a `.superseded` file that will not parse or is not a conversation: none of its messages
     is later than the moment it was last written (it is set aside by rename, which keeps that time), so only daily
     files for that day and earlier are held;
   - one of those that cannot be dated: every existing daily file is held.
3. **A day with no daily file yet is still written** in all of those cases. Nothing compiled is lost by that, and a
   later run with every source readable rewrites it in full.
4. The summary gains `unknownFiles` and `held`. The command prints one line when it left files alone.

A rolled-over conversation still refuses the whole run (#5855), whatever else is in the folder.

## Decisions, written once

- **Hold, not refuse.** A `.damaged` file is kept for good, so refusing would turn the daily log off for good for
  anyone who ever had one. An existing test already pins that a read error still lets a readable day be written;
  that stays true for new days.
- **Bounded by last-written time, not held forever.** Holding every existing day while a `.damaged` file exists
  would freeze each day at its first compile, for good. Its messages cannot be later than its last write, so later
  days are compiled as usual. If the file's time is later than its real last write (a copy, a restore), more is held,
  which is the safe way. If someone sets it earlier, a day could be rewritten short; nothing checks for that.
- **No dedupe**, as measured above. If a person copies rows into both files they show under two headings.
- **The command's one line, and its wording, decided here and not to be reworked in review:**
  `left N daily file(s) already there as they were (<first> to <last>), because M file(s) in the chats folder could
  not be read as conversations and may hold messages from those days`. It says what was done and the fact it rests
  on. It gives no advice and names no cause, because the tool cannot tell why a file is unreadable. A later objection
  that only prefers other words is a preference (Liu Kang, m4974).

## Done looks like

- Days that live only in a `.superseded` file survive a full run, with their rows, under their own heading.
- With a `.damaged` file last written on day D: existing daily files through D are byte for byte unchanged; later
  days are written and pruned as usual.
- With an unreadable thread file: no existing daily file changes; a new day is written.
- Without any of these the compiler behaves as before (the 48 existing tests).

## Measured (c0e1d5ca3 plus this change)

- `engine/dailylog.asides-5866.test.js`: 12 pass. Against main's compiler 11 of the 12 fail (the pin passes). Some
  of those 11 are controls that fail on main only because its summary has no `held` or `unknownFiles`; they are not
  evidence of the hazard. The evidence is the tests whose daily files change on main: superseded days pruned, a held
  day rewritten, a shared day rewritten after a read error.
- The other three compiler test files: 48 pass, unchanged.
- The tests caught one fault in my first cut: a held day was listed twice in `held`.

## Weakest part

**The bound rests on a file's last-written time**, which a copy or a restore can change in either direction. Later
is safe; earlier is not, and is not detected.

**A held day is frozen while the unknown file is there.** For a `.damaged` file that is for good: the daily files up
to its last write never pick up a later edit or deletion of a message from those days.

**Not run on Linux or Windows.** Nothing calls the compiler yet.
