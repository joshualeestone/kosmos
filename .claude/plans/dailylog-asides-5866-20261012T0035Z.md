# dailylog-asides-5866: set-aside and damaged conversation files no longer cost the daily log its days

Card: #5866. Built on #5855 step 1 (#5878), as the sequencing note on the card asked.

## What was wrong (on main before this)

`engine/chat.js` sets a thread file aside, beside it, in two cases besides the rollover: `.superseded` (the file
belonged to an earlier project of the same name) and `.damaged` (it would not parse). `engine/dailylog.js` saw
neither. A full run then pruned every daily file whose messages now lived only in such a file, and rewrote a shared
day without them. A thread file that could not be read when its turn came stopped the prune but not that rewrite.

## Measured (c0e1d5ca3 plus this change)

- `engine/dailylog.asides-5866.test.js`: 18 pass. Against main's compiler 16 of the 18 fail; the two that pass are
  the pin and the control that describes the old behaviour.
- `engine/dailylog.test.js`: 24 pass, one of them rewritten (the refined rule above); that one fails on main's

- The tests caught one fault in my first cut (a held day listed twice in `held`); reviewers caught the bigger ones
  (the freezes, below), which the tests now cover with second runs.

## Weakest part

**The bound rests on a file's last-written time**, which a copy or a restore can change in either direction. Later
is safe; earlier is not, and is not detected. The same goes for a computer whose clock was stepped back.

**A held day is frozen for as long as the set-aside file is there**, which for a `.damaged` file is for good. Daily
files from before its last write never pick up a later change to those days in a file that can be read: an edit, a
deletion, or a message kept late under its original time (chat.js keeps a caller's `at`; a drained reply carries its
send time). Main would have rewritten the day with that row and without the damaged file's rows. This change keeps
the damaged file's rows and misses that one. A test pins it as a known cost.

**A `.damaged` file is never read**, though chat.js also sets aside files that parse but fail its checks (a wrong
agent, a bad row). Their rows could be recovered; this change does not try. For such a file the day it was last
written is rewritten without rows that were compiled the day before, exactly as on main.

**Two earlier projects that began at the same moment share a heading.** It needs a project's birth time to recur.
No row is lost or doubled.

**Not run on Linux or Windows.** Nothing calls the compiler yet.

## Review notes

- Round 1 (opus). **One blocker, a regression from main:** holding every existing daily file on a read error froze
  each day at its first compile for as long as the file stayed unreadable. Fixed by the redesign above: read errors
  are as on main, and a set-aside file holds only days before its last write. Also fixed: the day of the damage was
  frozen (same redesign); two earlier projects of one name were merged under one heading; a `.superseded` file that
  had rolled over was compiled and not refused; five pieces of logic no test could fail (each has a test now, and
  two of the five no longer exist); a comment gave the wrong reason a file is set aside as damaged; the header, a
  docblock and the usage text described the old behaviour.
- Round 2 (sonnet), no blocker and no convention finding. Two warnings. (1) "Days before the last write cannot gain
  messages" was false: a readable file can gain a row under an earlier time. The comments no longer say it, the cost
  is in "Weakest part", and a test pins it. Not designed away: the choice is between that one late row and the
  damaged file's rows for the day, and merging old and new daily files is more machinery than a derived log with no
  caller has earned. (2) When the day of the last write could not be worked out, nothing was held; now everything
  is. Also: a superseded project's birth time goes into the heading escaped, and the real-writer test compiles
  under one fixed day so it cannot split at midnight.
- Round 3 (opus), no blocker. Fixed: (1) a file time in the future made the line follow the clock, freezing each
  yesterday at its last compile; the set-aside time in the file's own name now bounds it too. (2) A damaged file
  was skipped as junk until chat.js set it aside, so a compile in between pruned its days before the hold began;
  a live thread file that will not parse is now held from the start. That refines a rule #2924 pinned, as written
  under "Decisions". (3) This plan claimed more than is true for the day of the last write; corrected. (4) The
  title said unreadable files were covered when the body says read errors are as before. Two comments.
