# dailylog-asides-5866: set-aside and damaged conversation files no longer cost the daily log its days

Card: #5866. Built on #5855 step 1 (#5878), as the sequencing note on the card asked.

## What was wrong (on main before this)

`engine/chat.js` sets a thread file aside, beside it, in two cases besides the rollover: `.superseded` (the file
belonged to an earlier project of the same name) and `.damaged` (it would not parse). `engine/dailylog.js` saw
neither. A full run then pruned every daily file whose messages now lived only in such a file, and rewrote a shared
day without them. A thread file that could not be read when its turn came stopped the prune but not that rewrite.

## Measured before building (Liu Kang, m4976: can a superseded file overlap the live one?)

Driven through the real writer in a sandbox:

| After | Set-aside file | Live file |
|---|---|---|
| two messages under one project | none | 2 rows |
| one message under a later project of the same name | the 2 earlier rows | 1 new row |
| a second | the same 2 | 2 new rows |
| a message onto a thread file that will not parse | the unparseable bytes, as `.damaged` | 1 new row |

A superseded file is the whole earlier file, renamed; the later project's file starts empty. **No row is in both.**
Rows carry no id (`at`, `text`, `from`, `wire`, `delivery`), and two real rows can share one `at`, so there is
nothing safe to dedupe on. Agreed with Liu Kang (m4978): no dedupe, a test through the real writer, a separate
heading.

## The change (`engine/dailylog.js`)

1. **A `.superseded` file is read as a conversation of its own**, under its own heading: the thread's label plus
   "(an earlier project of this name, begun <when>)". Its days are written and kept like any other. One whose
   conversation had itself rolled over refuses the run, as a live one does (#5855).
2. **A thread file that is not read as a conversation keeps the daily files only it could have filled from the
   prune.** That is every `.damaged` file, a `.superseded` file that will not parse or holds no message list, and a
   live thread file that will not parse or holds no message list (chat.js sets such a file aside only at the next
   message; a compile in between used to prune its days first). A daily file with no readable messages left, for a
   day no later than the day that file could last have gained a message, is held: not pruned. That moment is the earliest of the
   file's last-written time, the set-aside time in a set-aside file's own name, and now.
3. **Nothing else changes.** Every day that has readable rows is rewritten exactly as before, so no day is ever less
   current than it was without this. A file that cannot be read this run is handled as before (no prune).
4. The summary gains `unknownFiles` and `held`. The command prints one line when it kept files from the prune.

A rolled-over conversation still refuses the whole run (#5855), whatever else is in the folder.

## Decisions, written once

- **The hold stops the prune and nothing else.** Three earlier cuts also stopped a held day being REWRITTEN, to keep
  the unreadable file's rows in days it shares with readable conversations. Reviewers found a freeze in each: every
  day on a read error, the day of the damage, the day before it. The reason is the same each time: not rewriting a
  day trades rows that can be read for rows that cannot, and a day can gain readable rows later than any line I
  could draw. So the rewrite is never stopped. What is lost is what main already loses: a day shared with readable
  conversations is rewritten without the unreadable file's rows. What is gained over main: days that only the
  unreadable file had are no longer deleted, which is what the card reported.
- **Hold, not refuse.** A `.damaged` file is kept for good, so refusing would turn the daily log off for good.
- **An earlier rule is refined, on purpose.** #2924 pinned that a thread file that is not valid JSON "is stable junk
  and does NOT block pruning". It now blocks pruning of days up to and including the day of its own last write, and only
  those; a stale day after that is still pruned, which is what that rule protected. The test that pinned it says both halves now.
- **No dedupe**, as measured above. If a person copies rows into both files they show under two headings.
- **The command's one line, and its wording, decided here and not to be reworked in review:**
  `kept N daily file(s) with no readable messages left (between <first> and <last>), because M file(s) in the chats
  folder could not be read as conversations and may hold messages from those days`. It says what was done and the
  fact it rests on. It gives no advice and names no cause. A later objection that only prefers other words is a
  preference (Liu Kang, m4974).

## Done looks like

- Days that live only in a `.superseded` file survive a full run, with their rows, under their own heading; the
  real writer driven through two and then three projects of one name shows every message exactly once.
- With an unreadable thread file: a daily file only it could have filled is still there after a full run; every
  day with readable rows is byte for byte what the same folder gives without that file.
- Without any such file the compiler behaves as before.

## Measured (first on c0e1d5ca3, again after the rebase onto ee001f284)

- `engine/dailylog.asides-5866.test.js`: 18 pass. Against main's compiler 17 of the 18 fail; the one that passes
  is the pin. Several fail there only because main's summary has no `held` or `unknownFiles`.
- `engine/dailylog.test.js`: 24 pass, one of them rewritten (the refined rule above); that one fails on main's

- One test compiles the same folder with and without a damaged file and compares every written day byte for byte.

## Weakest part

**A day shared between an unreadable file and readable conversations still loses the unreadable file's rows when it
is rewritten.** That is main's behaviour. Keeping them would need merging an old daily file with a new one, which is
more machinery than a derived log with no caller has earned. The originals are never touched.

**A stale day up to the line is never pruned while the unreadable file is there**, which for a `.damaged` file is
for good: a day whose messages were all deleted on purpose keeps its daily file.

**The line rests on a file's last-written time**, which a copy or a restore can change. Later keeps more from the
prune; earlier lets a day only that file had be pruned, and is not detected. With no time in the name and a file
time in the future, the line follows the clock, which only keeps more.

**A `.damaged` file is never read**, though chat.js also sets aside files that parse but fail its checks.

**A computer whose timezone moves west between compiles** can have a daily file named a day later than the line
worked out today, and that file is then pruned. Main prunes it too. Daylight-saving changes alone do not do this.

**Two earlier projects that began at the same moment share a heading.** No row is lost or doubled.

**Not run on Linux or Windows.** Nothing calls the compiler yet.

## Review notes

- Round 1 (opus). **One blocker, a regression from main:** holding every existing daily file on a read error froze
  each day at its first compile for as long as the file stayed unreadable. Fixed by the redesign above: read errors
  are as on main, and a set-aside file holds only days before its last write. Also fixed: the day of the damage was
  frozen (same redesign); two earlier projects of one name were merged under one heading; a `.superseded` file that
  had rolled over was compiled and not refused; five pieces of logic no test could fail (each has a test now, and
  two of the five no longer exist); a comment gave the wrong reason a file is set aside as damaged; the header, a
  docblock and the usage text described the old behaviour.
- Round 2 (sonnet), no blocker and no convention finding. Two warnings. (1) "Days before the last write cannot gain
  messages" was false: a readable file can gain a row under an earlier time. The comments no longer say it, the cost
  is in "Weakest part", and a test pins it. Not designed away: the choice is between that one late row and the
  damaged file's rows for the day, and merging old and new daily files is more machinery than a derived log with no
  caller has earned. (2) When the day of the last write could not be worked out, nothing was held; now everything
  is. Also: a superseded project's birth time goes into the heading escaped, and the real-writer test compiles
  under one fixed day so it cannot split at midnight.
- Round 3 (opus), no blocker. Fixed: (1) a file time in the future made the line follow the clock, freezing each
  yesterday at its last compile; the set-aside time in the file's own name now bounds it too. (2) A damaged file
  was skipped as junk until chat.js set it aside, so a compile in between pruned its days before the hold began;
  a live thread file that will not parse is now held from the start. That refines a rule #2924 pinned, as written
  under "Decisions". (3) This plan claimed more than is true for the day of the last write; corrected. (4) The
  title said unreadable files were covered when the body says read errors are as before. Two comments.
- Round 4 (sonnet), no blocker and no convention finding. Fixed: a live thread file whose key is 12 to 14 digits
  had those digits read as the time it was set aside, which lifted the hold; that time is now read only from
  set-aside names. A comment and a test title still stated the rule this change refines. The command's line says
  "between A and B", since held days need not be consecutive. **Round 4 read a broken copy of this plan:** my round
  3 edit had cut out everything between "What was wrong" and "Measured" by matching the wrong heading. It is
  restored here from the round 2 commit with the round 3 changes applied again; the code and tests were not
  affected. Round 5 reads the whole plan.
- Round 5 (opus). **A second blocker of the same kind as round 1's:** the day before the unreadable file's last
  write was frozen at its last compile, usually an incomplete one, where main keeps it current. Rather than move the
  line again, the design is cut back to what cannot freeze anything: the hold stops the prune only (see
  "Decisions"). That also removes the late-row cost of round 2 and the fail-open listing round 5 found. Also from
  round 5: a live file with no message list is unknown too; an unchanged idempotence test had been masked and is
  not any more; the name-time pattern is pinned to the line in chat.js that builds the name and run on a name the
  real writer made; comments and this plan no longer say "set-aside" where a live file is meant.
- Round 6 (sonnet). It ran main's compiler and this branch side by side over 1,200 simulated folders (about 13,000
  compiles): no day the branch deleted that main kept, and no day that differed from main without a `.superseded`
  file. **One blocker, an off-by-one in the line:** the day of the unreadable file's last write was not held, so
  the day most likely to hold its newest messages was still pruned. The line now includes that day (holding it is
  harmless now that the hold only stops the prune), and a test pins the boundary, which no test did. Also: wording
  that said "from the last write on" where "after that day" is meant; a garbled comment; a parameter that did
  nothing; a `.superseded` file that will not parse but names an earlier file is refused like a live one.
- Round 7 (opus), no blocker. It ran both compilers side by side over 1,350 folders (37,800 compiles, five
  timezones): the branch never deleted a daily file main keeps and never wrote a day differently without a
  `.superseded` file. Fixed: a `.superseded` file naming an earlier file but holding no message list was held, not
  refused; the name-time pattern took 12 and 14 digits, so a date typed into a file name was read as a time in 1976

- Round 9 (opus), on the rebased branch: no blocker and no warning. It compared main's compiler with the branch
