# bulk-clear-agents-2651 -- clear residual agents Kosmos refuses to remove (untied-session override), #2651(b)

## What this actually is (re-scoped by Josh's live report + screenshots, 2026-09-10 15:26)

Josh @-mentioned me: he has residual auto-imported agents (cut655, mortals-orch, a third) he CANNOT delete. Screenshots confirm the exact refusal from `engine/remove.js`: these run as bare-named tmux sessions (e.g. `mortals-orch`, not `mortals-orch-discord`), so `status.paneRoster().find(...).isNamedOurs !== true`, and `plan()` (remove.js:822) refuses: "something called mortals-orch is already running, and we cannot confirm it is this agent. Kosmos will not stop it, because doing so could stop the wrong thing." `removeInner` (953) refuses up-front on any `!plan().ok`, so the DELETE route returns REFUSED. The safety gate (never stop a session we cannot tie to the card -- the claudebot-bystander case) is CORRECT in general but TRAPS the user's own residual imports.

This supersedes the earlier "gate the getting-started seed" (no seed exists) AND the "generic multi-select bulk button" framing (Splinter: "a bulk-clear that calls a broken remove" helps nobody). The REAL fix is a user-confirmed OVERRIDE of the untied-remove refusal.

## Definition of done

From an untied agent's detail panel (where Remove is currently refused), the person gets an explicit, user-initiated way to REMOVE THE CARD FROM KOSMOS -- so cut655/mortals-orch/etc. leave the Agents page and stop cluttering it -- WITHOUT Kosmos stopping the untied terminal session (the safest action, since Kosmos cannot confirm the session is that agent; the person can close the session themselves). The default per-agent Remove for a TIED agent, and the general untied REFUSAL for anyone who does not opt into the override, are unchanged (the safety gate still protects a bystander's session by default). Real/imported agents are unaffected. This unblocks Josh clearing the residuals so he can import his real MK roster.

## Mechanism (mapped, cite by content)

- `plan(name)` (remove.js:761) refuses the untied case at 822 (`tie && tie.isNamedOurs !== true`). It returns `{ ok:false, because }` -- NO machine-readable reason today.
- `removeInner(name, {tmuxBin, platform})` (953): `const intent = plan(...); if (!intent.ok) return REFUSED`. So the override must go here.
- `sessionFor` (522) already classifies the untied session as `FOUND.UNTIED` (543).
- `recordRemoval(clean, job, stopped, shownAs)` (563) hides the name (removed-list) -- this is what makes the card disappear; it does NOT require stopping the session.
- Server: `DELETE /api/agent/<name>` -> `removal.remove(name)` (the `rm && DELETE` block). Web calls it from the detail-panel remove flow (`#d-remove-start` ~7897 -> openRemoveModal -> DELETE).

## Design (minimal, safety-first)

1. **plan()**: add a machine-readable marker to ONLY the untied refusal: `{ ok:false, because, untied:true }`. Every OTHER refusal (isHidden/not-there/unsafeToActOn) stays un-marked, so the override can NEVER apply to them.
2. **removeInner(name, { force, ... })**: `force` is the user-initiated "clear the card, leave the session running" op and is handled ABOVE the ordinary removal so it can NEVER reach the stop/disable path:
   - if `force === true` AND (`intent.untied === true` OR `intent.ok === true`): perform the clear-card-only op -- `recordRemoval(clean, null, false, shown, true)`, touch NOTHING on the machine. The record keeps `stopped:false` (the session genuinely is not stopped) and carries a distinct `leftRunningByChoice:true` flag; the ONE board-visibility predicate `hidesCard` hides the card on `stopped !== false || leftRunningByChoice === true`, so the card leaves the board while the stop-state readers (engine/messages.js) still see it as running. Return REMOVED (or PARTIAL if the record write fails, meaning nothing was cleared) whose sentence says the card was removed and the session left running. Message branches on `untied` so a now-tied agent is not told "cannot confirm it is this agent".
   - the `intent.ok === true` arm exists for the untied->tied RACE: the override is offered on a GET plan() and acted on later on the DELETE; if the session became tied in that window, plan() now returns ok and the OLD structure fell through to the STOPPING removal, silently breaking the button's "leaves the session running" promise. force now leaves the session running whether untied or (now) tied; it stops nothing either way.
   - `force` stays INERT on a refusal with nothing to clear (not-there / cannot-check / unsafe): returns the plain REFUSED, runs nothing.
   - non-force path is exactly as today (untied -> REFUSED; tied -> normal stop/disable removal).
3. **Server**: `DELETE /api/agent/<name>/removal` reads a `?force=1` (or `?force=true`) query param -- NOT a JSON body, because some proxies strip DELETE bodies -- and passes `{ force }` to `removal.remove`. Absent/false = unchanged.
4. **Web**: when the detail-panel remove is refused with `untied:true`, surface an explicit affordance: "This is running under a name Kosmos cannot confirm is this agent. If you know it is yours, you can remove the card from Kosmos (this leaves the terminal session running; you can close it yourself)." -> `DELETE .../removal?force=1`. A plain, non-alarming confirm; the safety default (refuse) is unchanged for anyone who does not opt in.
