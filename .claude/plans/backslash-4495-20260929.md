# #4495: engine/win32board.test.js no longer leaves backslash-named folders in the worktree

## Why
Baron measured 10 empty folders named like `\var\folders\...\aw-win32board-570-XXXX\Kosmos\runtime` in a
worktree root, one per suite run. Empty, so git and the validation helper's clean-tree check ignore them today;
one that held a file would turn every macOS validation red (the #2603 and #3795 class).

## Cause (measured)
The suite asks win32anchor.anchorDir('win32', ...) for its claim directory: a path.win32 join, so on macOS it is
ONE name starting with a backslash, which fs resolves against the process cwd. The test's own
`fs.mkdirSync(CLAIM_DIR)` made the folder in the worktree root, and the board's claim() wrote its claim file into
it mid-run; the test removed the file, never the folder. The product code is right on Windows (there the string is
a rooted path); this is the test simulating win32 on a Mac.

## Change (test only)
- engine/win32board.test.js runs from an isolated temp cwd, set at load and removed after: the same fix
  win32anchor.test.js and win32job.test.js carry for #2603.
- A last arm asserts the starting directory gained no backslash-named entry (CONTROL: a backslash name WAS written,
  into the temp cwd). Red with the chdir removed; it names the leaked folder.

## Checked
- A sweep of every engine/*win32*.test.js, root *win32*.test.js and tools.win*.test.js file (92), each run alone
  in a clean worktree: no other file leaves a backslash-named entry. Weakest premise: a file outside that naming
  pattern that simulates win32 would not have been run by the sweep.

## Review iteration 1
- BLOCKER: this file runs on the Windows CI runner (its name has "win32"), where CLAIM_DIR is an ordinary absolute
  path and no name holds a backslash, so the guard's CONTROL would fail there. The arm now runs only where its
  premise holds (CLAIM_DIR not absolute: macOS and Linux) and skips with a reason elsewhere. Hosts reasoned about:
  macOS (measured: arm runs, red without the chdir), Windows (the arm skips; the chdir is harmless there).
- The file's comment points at the #2603 fix and keeps only this file's specific fact.
