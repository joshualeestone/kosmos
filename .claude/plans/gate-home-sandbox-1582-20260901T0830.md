# kosmos#1582 - the release gate stops poisoning the shared settings.json

## The bug (measured, Josh + Baron, 2026-08-30)

Every release cut wired a frozen-export TEMP hook path into the REAL shared
`~/.claude/settings.json`, killing report-hook reporting for all 18 agents. The temp
dir is deleted when the cut ends, so the path is dead the instant the cut finishes,
and each cut re-poisons it with a fresh dead path. Measured: `neverRecorded=true` for
all 18 agents; six distinct dead temp paths across six cuts; 17 of 18 panes emitting
"No such file or directory" on every prompt, including 11 agents with no Kosmos
connection (the settings file is shared fleet-wide).

## Root cause (Baron Draxum, diagnosed read-only 2026-08-30)

The install gate `tools/test-install.sh` sandboxes `KOSMOS_HOME` but NOT the
report-hook's TARGET home:

- The cut runs the gate: `KOSMOS_INSTALL_GATE=1 bash tools/test-install.sh` (release.sh).
- `test-install.sh:190` sandboxes `KOSMOS_HOME="$SB/home"` (+ BIN/APP/PROFILE) but does
  NOT set `AGENT_WORKFORCE_HOME` or `HOME`.
- `install/setup.sh`'s hook-wiring block resolves its target settings files through
  `accounts.HOME_FOR_TEST` = `homeDir()` = `AGENT_WORKFORCE_HOME || os.homedir()`
  (engine/accounts.js:53). With the var unset, `homeDir()` = the REAL `$HOME`.
- `script = reporthook.hookScriptPath()` = the EPHEMERAL `$SB/home/app/bin/...` path
  (correct at write time, dead after `$SB` is deleted).
- So the gate writes the ephemeral path into the REAL shared settings.json.

This is Josh's own "the resolver is not the defect" correction: `hookScriptPath()` is
right at the moment it is called; the defect is persisting a correct EPHEMERAL value
into a DURABLE SHARED file.

## The fix (one line + a comment)

`tools/test-install.sh:190` now exports `AGENT_WORKFORCE_HOME="$SB/home"` alongside
`KOSMOS_HOME`. Then `accounts.homeDir()` resolves to the sandbox, so setup.sh's
wiring targets `$SB/home/.claude/settings.json` (deleted with `$SB`, harmless), the
gate's `refused === 0` check still passes (it wires the sandbox's own fresh default
settings.json), and the real shared file is never touched.

- **Scoped to accounts/home resolution, NOT `$HOME`** - setting `AGENT_WORKFORCE_HOME`
  rather than `HOME` keeps the change to the report-hook target and does not repoint
  everything that reads `$HOME`.
- **The consuming code already expects it**: setup.sh's block comment ("AGENT_WORKFORCE_HOME
  first, for sandboxing", Angel's review) shows the wiring was designed for the gate to
  set this var; test-install.sh simply never did.
- **Composes with #1634** (merged): its reporthook refuse-guard refuses an ephemeral
  script into a DURABLE settings file but PERMITS an ephemeral script in an ephemeral
  settings file (test isolation). With the sandbox home, both are ephemeral, so the
  write succeeds (refused===0) - the two fixes are complementary, not duplicate.

## Why this and not the alternatives

Josh listed three candidates; #1634 did (1) refuse ephemeral persistence (a defense).
This is (2) "do not write into the real home from a frozen export" at the true source:
the gate's incomplete sandbox. It is the minimal root fix. Option "change hookScriptPath"
is explicitly wrong (Josh) - the resolver is correct.
