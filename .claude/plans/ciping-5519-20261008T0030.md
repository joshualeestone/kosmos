# ciping-5519: our own Linux CI installs stop firing the live install beacon (kosmos#5519)

Josh, #admin 2026-10-07 19:21: "lets not track any more linux installs that we know are our own." Splinter's hard limit
(Josh 10-03): do NOT change, filter or edit the counter or the existing 298; stop new ones at the source.

## Source (measured)
.github/workflows/test-linux-setup-4920.yml runs on every pull request (ubuntu-latest) and installs twice per run
(default home, uninstall, custom home); 153 runs from its first (2026-10-06 22:28:29Z) x 2 = 306 vs 298 counted, matching
the pairs, the hours and the US origin. Each install starts a real board, whose engine/createdbeacon.js pingInstall
POSTs to the live counter.

## Call
- engine/linuxboard.js boardUnitFor: when the installer's environment has AGENT_WORKFORCE_CREATED_URL (the beacon's
  existing endpoint override) as a plain http(s) URL, the unit carries it, so a systemd-started board keeps it across
  restarts; an update re-runs setup from the board's own environment, so it persists. Unset (every real install): the
  unit is byte-identical (test). Unsafe values (whitespace, quotes, backslash, %, non-http) are left out, not fatal.
- The workflow sets it job-wide to http://127.0.0.1:9/api/created, asserts the unit AND the running board's
  /proc/<pid>/environ carry it, adds it to the 0.7.27 unit it restarts in the update step (that release's unit writer
  cannot), and asserts the updated unit keeps it.
- Stacked on linux-setup-board-4920 (#5485), which makes setup.sh write the unit through linuxboard.js.

## Rejected
- internal.json (rule C): an internal install still pings; the site only files it apart. Josh said do not track.
- Blocking the counter's host on the runner: setup downloads from the same host.
- Any change on the counter side: forbidden.

## Weakest premise
That all 298 are this workflow. The other Linux runs (the Mortals port, Cloud VM tests) can set the same variable.
