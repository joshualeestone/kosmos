# #4997: the full-page preview in the three Files lists (the half of #4930 its PR does not build)

Built stacked on preview-4930 (Mona, PR #4999, which builds pvOpen for conversation attachments); rebased onto main
once #4999 merged (2026-10-02 09:44). The measurements below were taken on that base. Split agreed on #4997

## Problem, measured on preview-4930 (ddc66a24b)
- The three Files lists (agent page Files and its "all files" view, d-files-list / d-filesall-list; the project Files
  panel; the Files screen) draw a row per file and, on a click, ask the board to OPEN the file on the computer
  (POST /api/agent/<n>/files/open, POST /api/project/<id>/open-file). No route serves a listed file's bytes to the
  page, so pvOpen has nothing to show.

## What this does
1. engine/projects.js: openFile's three gates (name shape; folder readable; resolved target inside the resolved
   folder and a regular file) move into `resolveListedFile(folder, name, where)`, which openFile now calls, so the
   refusal logic exists once and every new route goes through it.
2. engine/filepreview.js: `preview(folder, name, where)`: an image's own bytes (type from the extension, never
   sniffed; capped at attachments.MAX_BYTES), a PDF's first page as a PNG through attachments' renderer (from a
   private copy), cached under the board's data folder: one folder per resolved path, one page named by the file's
   stamp (device, inode, size, both times), at most 200 folders (never written into the person's folder).
   `download(folder, name, where)`: the bytes, for Kosmos+ (the preview's Download).
3. Routes, each through resolveListedFile and crossSiteRead:
   GET  /api/agent/<n>/files/preview?name=   GET /api/agent/<n>/files/download?name=   POST /api/agent/<n>/files/reveal-file
   GET  /api/project/<id>/file-preview?name= GET /api/project/<id>/file-download?name= POST /api/project/<id>/reveal-file
   Served with nosniff, a sandbox CSP, and attachment disposition for downloads; a refused name is 404/409 with the
   resolver's sentence, never the bytes.
4. web/index.html: a click on an image or PDF row in the three lists registers a PV_ATTS record
   (one record under the fixed plain id 'files-preview', so pvClose's selector never carries a file name: name, kind, meta, url: download route, preview: preview route, reveal) and calls pvOpen; any other
   row keeps today's open-on-the-computer.

## Decided
- Images and PDFs only (the card's "Done looks like"); a text file keeps opening on the computer. What would change
  it: Josh asking for text in the Files preview; then the preview route gains a snippet arm like attachments'.
- Weakest premise: that the rows' listed name always resolves. A file renamed or removed between the list and the
  click shows the preview's file card (its name and size, from the row) with no picture; the board's sentence is not
  shown there (pvOpen's card has no place for it), and Open in Finder then says the board's refusal.

## Tests
- Route tests with the refusal arms: `../`, an absolute path, a backslash, a dot-name, a symlink inside the folder
  pointing outside (refused by the listed walk before the containment gate), a directory, a missing file, a cross-site
  read; each must return no bytes. A parity test: the routes accept exactly what listFiles lists.
- A browser check that opens the preview from each list and clicks #pv-do, counting the Files route and never
  /api/attachment/ (Mona's ask).
