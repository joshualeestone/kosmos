# shortpath-5645: Windows CI red on 8.3 short TEMP paths (#5645)

## Why
Since ~23:20 on 10-08, main's `windows` check fails on some runners: tools.win-installer-native.test.js (W-20 and
the hand-off/update probes) and tools.win-launcher-native.test.js. Measured on run 37885046546, two different causes:
- installer: the product reports `C:\Users\runneradmin\AppData\Local\Temp\...`, the test expects
  `C:\Users\RUNNER~1\AppData\Local\Temp\...`. The runner's TEMP is spelled in 8.3 short form; os.tmpdir() returns it
  as-is. Same folder, different text.
- launcher: NOT the spelling. `EPERM` from `fs.rmSync(s.base, ...)` in the cleanup of "--console waits on the board and
  passes its exit code through": a file under the scratch dir was still held when the test removed it. The installer
  test retried two of its removals; the launcher test none (review 1 caught my first reading of this as 8.3).
Both test-only.

## Change
- Both test files: a `scratchBase()` = `fs.realpathSync.native(os.tmpdir())`, which expands 8.3 names (and links),
  used at every place a scratch path is built from os.tmpdir(). Expected and actual paths are then built from the
  spelling the product reports.
- Both test files: every recursive scratch cleanup (`fs.rmSync(<base>, { recursive: true, ... })`) gets
  `maxRetries: 10, retryDelay: 200`, as two installer cleanups already had, so a handle released a moment late no
  longer fails a test. Single-file removals inside a test body are left alone: they are what those tests do.
- A short-form arm (Windows only): cmd's `%~sI` gives the 8.3 form of the scratch base; it must expand to exactly the
  long form. Skips, saying so, where the volume keeps no 8.3 names. The cmd spawn uses windowsVerbatimArguments (node
  would otherwise escape the inner quotes) and windowsHide, as the launcher test's shortNameOf does.

## Decided
- Normalise at the source (one long-form base) rather than in each comparison: every expected path in these files is
  derived from the scratch base, so one change covers all of them, including ones not yet failing. Rejected: a
  case-insensitive, 8.3-expanding compare at each assertion (many sites, easy to miss one).
- Retries, not a process wait, for the launcher EPERM (review 2 asked whether a live process holds the folder):
  runConsole is spawnSync and the test asserts the board's exit code 7 came back through the launcher, so both
  have exited before the cleanup runs. What remains is a late release (an antivirus scan of the freshly copied
  node.exe and Kosmos.exe is the usual one), which is the case retries are for. If it recurs with retries, the
  holder is longer-lived and this reading is wrong.
- The short-form arm asserts the expansion equals scratchBase(), which already proves the base is long; a separate
  "no `~` in the path" check was dropped (review 2: a real folder name may contain `~1`).
- Weakest premise: realpathSync.native expands 8.3 on the runners' NTFS volumes (it calls GetFinalPathNameByHandle);
  the short-form arm measures exactly that on the runner.

## Tests
Windows-only; on macOS the files run and skip (56 tests: 21 pass, 35 skipped, 0 fail). The PR's `windows` check is
the measurement.
