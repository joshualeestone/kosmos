**Posture:** production (the installed app). **Status (11-25 11:30):** Agents, Projects and Tasks in two panes through ListAndOpen; run on iOS 27 (iPhone 18 Pro Max, sideways, the stand-in) up to b2a8d0c969, where 5 of 6 UI tests passed. The tab-bar change and the review fixes after it (head 3b2e8d0446) are NOT run.

**Finished looks like:** on Duo, folded (compact width) is the phone app as it is today, with nothing clipped at the
5.4" size. Unfolded (regular width), Agents, Projects and Tasks show a list on the left and the open chat / room / page
on the right. Folding or unfolding never loses the open item, the scroll position or a typed draft. Anything that says
"Face ID" where the device has Touch ID says "Touch ID". Screenshots per state in the card's shape (like #8952's).

## Decided (Apple, checked 11-24; links on the card)
- One switch: horizontal size class (compact -> the phone layout; regular -> split). Apple says not to use idiom or
  orientation (the inner display ignores orientation). ReservedRegion (iOS 27.1) exists for keeping content off the
  fold; not planned until the simulator shows whether it is needed.
- No Duo simulator here: Xcode 27.0 has none; Apple says it is in Xcode 27.1 (a person must download it). Stand-in: a DEBUG
  env (KOSMOS_SAMPLE_REGULAR=1, like the other sample envs) sets traitOverrides.horizontalSizeClass = .regular on the
  window, plus Device Hub's resizable simulator if it works here. A real Duo (or 27.1) run confirms later.

## Findings (read 11-24, origin/main)
- iOS/Kosmos is iPhone-only (TARGETED_DEVICE_FAMILY = 1), deployment 16.0. Duo runs it as an iPhone.
- Each tab list is `NavigationView { content }.navigationViewStyle(.stack)` (Agents, Projects, Tasks, Today, Settings,
  Account, New task / project). `.stack` forces one column at every width. Agents opens its chat through a hidden
  `NavigationLink(isActive: openAgent != nil)`; the open agent is `@State openAgent`, with its own kept copy in defaults
  (openChatKey) for relaunches. Projects similar (line 767). The chat is ChatView with `.id(agent.session)`.
- `UIScreen.main.bounds` sizes chat bubbles and attach menus (ChatView 18, 1887; RoomView 1883; ChatFiles 71; AttachMenu
  67; ChatChoices 232). In a split the pane is narrower than the screen, so these must use the pane's width
  (the container's size, via a GeometryReader or containerRelativeFrame), or bubbles overrun the pane.

## Plan (smallest change first)
1. `NavigationView` with the default style at regular width (two columns: list and detail), `.stack` only at compact
   width. Whether swapping the style keeps the same identity (state, draft) when the size class changes is the first
   simulator question; if it does not, use NavigationSplitView with the detail bound to the same `openAgent` state.
2. Detail placeholder at regular width when nothing is open ("Choose an agent"), the same words Mona Lisa's screens use.
3. Replace `UIScreen.main.bounds` with the pane's width, as an environment value (`\.paneWidth`, default the screen's width,
   which is today's behaviour at compact width). ChatView sets it from its measured `contentWidth` (#7034: already leaves out a
   landscape notch and changes only on a real resize); RoomView needs the same measurement. Call sites: ChatView 18, 1887,
   3040; RoomView 1747, 1883; ChatFiles 71; ChatChoices 232 and others found by grep.
4. Tab bar at regular width: whatever the system does for TabView is kept (sidebar-adaptable is iOS 18+ and not
   planned first); check nothing overlaps the split.
5. Wording that assumes Face ID (checked 11-24, no change needed): SettingsView already reads LAContext.biometryType
   (Touch ID, Face ID, or the passcode), no other user-facing text in ios/Kosmos says Face ID, and web/ and engine/ on
   origin/main have none. The sign-in pages Kosmos+ serves are in kosmos-relay and were not read.
6. Fold and unfold mid-use: change the trait override in a UI test; assert the same chat, scroll and draft.
7. Screenshots per state and per theme, filed as in the card.

## Agents slice (written 11-24, not run)
- Two panes only when width AND height are regular (TwoPanes.swift). Width alone is also a large iPhone turned sideways, which keeps its
  one column. This replaces step 1's "default style at regular width": NavigationSplitView with the chat bound to openAgent.
- Taking the one column down on an unfold can report the chat's link closed, which would close the person's chat (the #8055 class). The
  link's setter asks the window's live traits, since its closure still holds the environment it was drawn with.
- The two layouts sit in a ZStack, so a fold fires none of the screen's appear and disappear handlers. Assumed until run.
- A draft is kept by the client when the chat disappears (client.drafts); scroll is NOT carried across and is unmeasured.
- KOSMOS_SAMPLE_REGULAR=1 or =fold:<seconds> (Debug only, iOS 17+) is the stand-in.
- Other tabs (Projects, Tasks, Today, Settings) are not done.
- Run 11-25 (iOS 27, sideways): DuoPanesUITests pass; side by side, chat and draft kept. **They also pass with the live-traits guard removed**, so on iOS 27 nothing shows the guard is
  needed. Kept, unproven; judge again on iOS 16 and 17 and on a Duo. Scroll across a fold and the floating tab bar over the list's last rows are still to look at.

## One navigation for both layouts (11-25; replaces the Agents slice's NavigationSplitView)
- ListAndOpen (TwoPanes.swift), used by Agents, Projects and Tasks: the open page is pushed on ONE stack navigation in both layouts. Unfolding moves the
  list out of that navigation's root into a pane of its own, so the chat, room, info page or task is never taken down. Why: a chat's scroll, its loaded
  earlier pages and a room's open info page are the view's own state, and the split view rebuilt them at a fold.
- The live-traits guard (TwoPanesNow) is gone with it: the link is no longer taken down by an unfold. The link's setter is the old one again.
- Rejected: NavigationSplitView for every width (changes every phone; iOS 16 has no preferred column), and saving and restoring the scroll by hand.
- Tasks: one link for a task or a chat, so beside the list the newer one takes the other's place. Its New task sheet sits on the tab, not the list.
- Weakest premise: that swapping the ROOT under a pushed page leaves the push alone (#8055 saw a swapped page close a chat). The UI tests ask exactly that.
- Not kept through a fold: the LIST's own scroll, and the Tasks tab's project filter (that view's state). Today and Settings keep one column.

## Tab bar (11-25)
- Found in the pictures: after a fold with a project's info page open, the tab bar stays over the page. A page under another keeps the size classes it was
  drawn with, so its own .visible stayed in force. First fix (each page reads its own size classes) did NOT help; the test still failed.
- Measured in a scratch copy, six variants: where the CONTAINER carried the toolbar (B, F, G) the fold, the unfold and an upright phone were all right.
  A, C and D also carried an outer .automatic, which by itself made the bar show on an upright phone, so their phone rows are not a fair test.
- Decided: F. The container hides (one column, something open that covers the tabs) or says .automatic; pages only ever hide, never ask for it back.
- Changes a phone on purpose: a task opened from inside a project's page should keep the tabs hidden (expected, not run on main or here). Josh, 11-03: "I don't
  want to see the nav if I am inside a project". A task opened from the Tasks tab keeps its tabs, as today.
