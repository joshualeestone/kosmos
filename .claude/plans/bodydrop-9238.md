# bodydrop-9238: a community post's body is no longer dropped when its title is typed bare

Card: kosmos#9238. Finished means: `kosmos community post '<title>' <<'END' <body> END` (Mac and Windows) no longer sends the title alone and says it was queued; it is refused with the --topic form named, nothing sent. The same for comment, edit and endorse. Words alone, and --topic with a piped body, behave as before. The instruction block names --topic.

## Finding (measured 2026-11-27, comment on the card)
- One affected post, end to end on this Mac: the author's session ran `kosmos community post '<title>' <<'KOSMOS_END'` with a body of about 2,500 characters and no --topic (2026-11-26T23:15:30.869Z). The board's community store received it 0.2 s later with topic "" and body equal to the title line (57 characters). The CLI answered "Queued for the Kosmos+ community".
- Cause: install/kosmos `community post` takes the words as the whole post when there are any (`elif [ $# -gt 0 ]; then text="$*"`) and reads stdin only when there are none. comment, edit and endorse have the same branch; so does the Windows CLI (`let text = args.join(' ')`, stdin read only when `!args.length`).
- Why agents type it so: TITLE_RULE in the community block every agent's instructions carry said "A post title sits in single quotes on the command line" and never named --topic.
- The server and the reader are not involved: the board stored what the CLI sent.

## Change
1. install/kosmos: `_words_and_piped`, called by post, comment, edit and endorse when there are words and no --body-file. It refuses (exit 2, nothing sent) when stdin holds text that is not white space. One rule on both CLIs: a regular file the shell has already removed (a heredoc or here-string under zsh or bash 3.2: measured nlink 0) is read at once, to its end or its first text, while a named file (`< file`, a `while read` loop's input: nlink 1) is never read, so a loop keeps its lines; a terminal or a character device (/dev/null, NUL) is never read; anything else (a FIFO such as a bash 5 heredoc or `cat f |`, a Windows named pipe, the socket a program spawning kosmos hands over) is watched for at most 300 ms in all, stopping at its first text, so a writer that never stops cannot hold it. Only whether text came is kept. The probe failing is not a refusal. The three hints are the same words on both CLIs (a test reads both files); the post hint names --topic only when none was given, the edit hint only for a post with no --topic (a comment has no title); every refusal also says to give a loop's command < /dev/null.
2. tools/windows/kosmos-cli.js: the same rule, as `stdinHasText` (its own fixed deadline, not readStandardInput's quiet timer, which a steady writer resets for ever) and `wordsAndPiped`, through a ctx seam (`stdinHasText`); a caller that hands in its own `readStdin` and no probe gets none.
3. engine/communityguide.js TITLE_RULE names --topic, says never to type the title bare, and gives a file with --body-file (the one form the check cannot see is `< file`). The community block has a 4,000-character limit (engine/communityblock.test.js); with this rule it sits about 40 under it.
4. Tests: cli.community-words-and-piped-9238.test.js (the real Mac CLI against a stub board that records what reaches it: --topic plus a heredoc arrives whole with its title; the bare title with the body as a file, a FIFO, a socket, or a file whose text follows 70,000 spaces is refused with nothing sent and the exact hint; `yes` piped in is refused at once; words alone with /dev/null, an empty FIFO, white space, or an open empty socket post at once, and with an idle FIFO or `yes ' '` after the 0.3 s peek; comment/edit/endorse refused with their hints, and their controls; the three hints are the same words in both CLI files). tools.windows-kosmos-cli-words-and-piped-9238.test.js (the four verbs through main()'s seams with each exact hint, and the real probe against a file, a file with text after 70,000 spaces, white space, /dev/null, a socket, a FIFO with text, an empty FIFO, an idle FIFO, `yes`, and `yes ' '`).

## Verified
- Both new files pass (25/25 Mac, 28/28 Windows; the Windows file also runs the real CLI in its own process, so the production probe wiring is covered, not only the seams). Against main's CLIs (first version), the refusal arms failed (6 Mac, 8 Windows), so they tell the old from the new.
- The related set, 29 files plus engine/communityblock and engine/communityguide (every cli.community-*, every tools.windows-kosmos-cli-community-*, body-file, reply-stdin, both new files, engine.reachable, install.reachable, fixture-discipline): 424 tests, 0 failed.

## Rejected
- Leaving sockets unread (the first version): a program that spawns kosmos with words and a body still lost the body silently, and Windows (where the same pipe is a named pipe) behaved differently.
- Taking the words as the title when text is piped: matches every case seen, but publishes a public post on a guess; refusing costs one re-run and is never wrong.
- Fixing only TITLE_RULE: anyone who types the bare form would still lose the body silently.
- Reading stdin whenever there are words: a plain `post "words"` from a tool runner would wait the 3 s quiet read every time.

## Weakest premise
A body given as a NAMED file with the title typed bare (`kosmos community post '<title>' < body.md`) is still dropped and the post still says queued: a named file is never read, which is what keeps a `while read` loop over a file safe, and the two cannot be told apart. --body-file is the way to give a file, and the guide already says so. That the other two affected authors (other installs) hit this same path. Their stored posts have the same shape on the reader (a one-line body equal to the title), but their commands are not visible here. Also: text that reaches a pipe more than 300 ms after the command starts is not seen, and the words are sent as before. A `while read` loop fed by a PIPE (not a file) that runs these verbs with words is refused, and the peek has taken that text from the pipe; the refusal says to add < /dev/null. On Windows, a heredoc that Git Bash writes to a file with its name kept would not be seen (Git Bash 5 passes small heredocs as a pipe, which is).
