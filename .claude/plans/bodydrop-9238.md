# bodydrop-9238: a community post's body is no longer dropped when its title is typed bare

Card: kosmos#9238. Finished means: `kosmos community post '<title>' <<'END' <body> END` (Mac and Windows) no longer sends the title alone and says it was queued; it is refused with the --topic form named, nothing sent. The same for comment, edit and endorse. Words alone, and --topic with a piped body, behave as before. The instruction block names --topic.

## Finding (measured 2026-11-27, comment on the card)
- One affected post, end to end on this Mac: the author's session ran `kosmos community post '<title>' <<'KOSMOS_END'` with a body of about 2,500 characters and no --topic (2026-11-26T23:15:30.869Z). The board's community store received it 0.2 s later with topic "" and body equal to the title line (57 characters). The CLI answered "Queued for the Kosmos+ community".
- Cause: install/kosmos `community post` takes the words as the whole post when there are any (`elif [ $# -gt 0 ]; then text="$*"`) and reads stdin only when there are none. comment, edit and endorse have the same branch; so does the Windows CLI (`let text = args.join(' ')`, stdin read only when `!args.length`).
- Why agents type it so: TITLE_RULE in the community block every agent's instructions carry said "A post title sits in single quotes on the command line" and never named --topic.
- The server and the reader are not involved: the board stored what the CLI sent.

## Change
1. install/kosmos: `_words_and_piped`, called by post, comment, edit and endorse when there are words and no --body-file. It refuses (exit 2, nothing sent) when stdin holds text that is not white space. One rule on both CLIs: a regular file the shell has already removed (a heredoc or here-string under zsh or bash 3.2: measured nlink 0) is read at once, by position (nothing is taken from it), to its end or its first text, unless something has already read part of it (on the Mac, perl reports the place: a `while read` loop over a heredoc or here-string has moved past its first line, so the words are sent); on the Mac a named file is read on the same terms (`post '<title>' < body.md` is at its start and is refused; a loop's file is past its start and is left alone), and on Windows, or without perl, a named file is never read; a terminal or a character device (/dev/null, NUL) is never read; anything else (a FIFO such as a bash 5 heredoc or `cat f |`, a Windows named pipe, the socket a program spawning kosmos hands over) is watched for at most 300 ms in all, stopping at its first text, so a writer that never stops cannot hold it. Only whether text came is kept. The probe failing is not a refusal. The three hints are the same words on both CLIs (a test reads both files); the post hint names --topic only when none was given, the edit hint only for a post with no --topic (a comment has no title); every refusal also says to give a loop's command < /dev/null.
2. tools/windows/kosmos-cli.js: the same rule, as `stdinHasText` (its own fixed deadline, not readStandardInput's quiet timer, which a steady writer resets for ever) and `wordsAndPiped`, through a ctx seam (`stdinHasText`); a caller that hands in its own `readStdin` and no probe gets none.
3. engine/communityguide.js TITLE_RULE: "A title goes in --topic '<title>' (no apostrophes, quotes, backticks or $); a post in a file, in --body-file <file>." 116 characters, 13 more than before. Measured block sizes: Mac 3,915 with the introduction (the size test, limit 4,000) and 3,455 without; Windows 4,437 with (already 4,424 on main, over the limit the test only measures on the Mac) and 3,977 without.
4. tools/windows-tests.js: the new Mac test file is listed in HOST_BRANCH_EXCLUDED (it skips on Windows; engine/windows-tests-1777.test.js requires the listing).
5. Tests: cli.community-words-and-piped-9238.test.js (the real Mac CLI against a stub board that records what reaches it: --topic plus a heredoc arrives whole with its title; the bare title with the body as a file, a FIFO, a socket, or a file whose text follows 70,000 spaces is refused with nothing sent and the exact hint; `yes` piped in is refused at once; words alone with /dev/null, an empty FIFO, white space, or an open empty socket post at once, and with an idle FIFO or `yes ' '` after the 0.3 s peek; comment/edit/endorse refused with their hints, and their controls; the three hints are the same words in both CLI files). tools.windows-kosmos-cli-words-and-piped-9238.test.js (the four verbs through main()'s seams with each exact hint, and the real probe against a file, a file with text after 70,000 spaces, white space, /dev/null, a socket, a FIFO with text, an empty FIFO, an idle FIFO, `yes`, and `yes ' '`).

## Verified
- Both new files pass (28/28 Mac with 1 skipped, the bash-5 arm; 28/28 Windows; the Windows file also runs the real CLI in its own process, so the production probe wiring is covered, not only the seams). Against main's CLIs, the refusal arms failed (6 Mac, 8 Windows, measured on the first version of these files; every later arm was added for a case a reviewer reproduced against the then-current code).
- The related set, 29 files plus engine/communityblock, engine/communityguide and engine/windows-tests-1777 (every cli.community-*, every tools.windows-kosmos-cli-community-*, body-file, reply-stdin, both new files, engine.reachable, install.reachable, fixture-discipline): 452 tests, 0 failed.

## Rejected
- Leaving sockets unread (the first version): a program that spawns kosmos with words and a body still lost the body silently, and Windows (where the same pipe is a named pipe) behaved differently.
- Taking the words as the title when text is piped: matches every case seen, but publishes a public post on a guess; refusing costs one re-run and is never wrong.
- Fixing only TITLE_RULE: anyone who types the bare form would still lose the body silently.
- Reading stdin whenever there are words: a plain `post "words"` from a tool runner would wait the 3 s quiet read every time.

## Weakest premise
On Windows (no way to ask a file's place), a body given as a NAMED file with the title typed bare (`kosmos community post '<title>' < body.md`) is still dropped and the post still says queued; the Mac refuses it. --body-file is the way to give a file, and the title rule now says so. That the other two affected authors (other installs) hit this same path. Their stored posts have the same shape on the reader (a one-line body equal to the title), but their commands are not visible here. Also: text that reaches a pipe more than 300 ms after the command starts is not seen, and the words are sent as before. On Windows (no perl), a `while read` loop over a heredoc that runs these verbs with words is refused (nothing taken from it). On Linux, where bash 5 and dash hand a heredoc over as a pipe, a `while read` loop over a heredoc is a pipe-fed loop (the test measures which kind /bin/bash makes and runs the matching arm). A script run with a named file on stdin that it has not read yet (`script.sh < data.txt`) is refused on the Mac if it calls these verbs with words first. A `while read` loop fed by a PIPE (not a file) that runs these verbs with words is refused, and the peek has taken that text from the pipe; the refusal says to add < /dev/null. On Windows, a heredoc that Git Bash writes to a file with its name kept would not be seen (Git Bash 5 passes small heredocs as a pipe, which is).
