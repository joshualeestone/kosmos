# #2140 slice: split the accountModels 401 (scope-restricted vs invalid_api_key)

## The defect

`engine/openaiaccounts.js accountModels()` (the OpenAI model-picker discovery)
folded every 401 from `GET /v1/models` into one `because`:
`"this account's API key was rejected by OpenAI (401)"`. The client
(`openaiNoModelsNote` in `web/index.html`) renders that as
"OpenAI rejected this account's API key ... Reconnect this account".

But per #1315, a **scope-restricted** project key 401s (or 403s) on `/v1/models`
for a permissions reason while running inference fine. That account is not
broken; it simply cannot enumerate models. Telling it to "reconnect" overstates
a working key as broken. `checkLive()` and `addWithKeyLive()` already apply the
#1315 asymmetry (only OpenAI's own `invalid_api_key` code is a positive
rejection); `accountModels()` did not. This slice closes that gap. It was
flagged on the card by me after the merged error-matrix slice (#2180).

## The change

1. `engine/openaiaccounts.js` — in the `r.status === 401` arm, read
   `r.body.error.code`. `invalid_api_key` keeps the existing
   `"...rejected by OpenAI (401)"` (reconnect). Any other code, or a bodyless
   401, returns a new honest `because`:
   `"this account's key cannot list models, though the key itself works (401)"`.
   This joins the 403 shape: account works, cannot list, uses OpenAI's default.

2. `web/index.html` `openaiNoModelsNote` — a new branch matching the scope-401
   `because`, returning a note that says the key works for running the agent and
   will use OpenAI's default, never "reconnect". The strings are distinct so the
   existing `rejected by OpenAI (401)` branch is untouched.

3. Tests — `engine/openaiaccounts.test.js`: a 401 with `insufficient_permissions`
   and a bodyless 401 both give the scope `because` and never read as rejected.
   `web.openai-model-errors-2140.test.js`: the scope-401 note says
   works-but-cannot-list, never reconnect/rejected.

## Weakest premise

That a non-`invalid_api_key` 401 always means "works, cannot list" rather than a
genuinely bad key. This mirrors the exact rule `checkLive()` already enforces and
that #1315 established with a test; if OpenAI ever returned a bad-key 401 under a
different code, this would be slightly generous — but the failure mode is safe
(the agent still uses OpenAI's default and runs), and the alternative
(over-claiming a working key as broken) is the worse, user-visible error we are
fixing. The invalid_api_key path is unchanged, so a confirmed-bad key still says
reconnect.

## Not in scope

The "compatibility not verified" unknown-model-ID slice and the per-agent
connectionId/modelId persistence hardening (both documented on #2140) are
separate, larger slices left for follow-up.
