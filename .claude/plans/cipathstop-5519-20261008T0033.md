## Call
- `on.pull_request.paths`: `install/**`, `tools/test-installer-runnable-guard.sh`, `tools/test-plist-heredoc-clean.sh`,
  `tools/test-install-static*.sh`, `tools/lib/install-static-checks.sh`, `tools/test-install.sh`, and the workflow file.
  These are every repo file the job reads. A PR that changes none of them does not run the job, so it does not ping.
- `workflow_dispatch` for a hand run. It becomes usable once this file is on main.
- The engine modules are not listed. With no `KOSMOS_SRC`, setup.sh installs the PUBLISHED bundle, so a PR's engine
  change is never exercised here; listing them would add pings and a misleading green. If a later change makes the job
  stage the checkout's engine, add `engine/linuxboard.js` and `engine/linuxjob.js` then.
- Remove the filter once #5519 lands; its runs then no longer count as installs.

## What a green run means, and what the stopgap costs
- Green means the PR's setup.sh and guards work on Ubuntu against the published bundle. It does not exercise the PR's
  engine, web, or install/kosmos (the published copies are installed; the guards only read install/kosmos).
- The job used to run on every PR, so it incidentally exercised each new release on Linux. It never watched main (no
  push or schedule trigger). With the filter, a new release is exercised only by a listed-path PR or a hand run after
  a cut.
- A listed-path PR still pings until #5519 merges. Accepted: those are the PRs the job exists for.
- GitHub matches paths against at most the first 300 changed files, so a very large PR could skip the job.
