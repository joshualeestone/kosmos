# briefsync12-5434: an agent's brief and its kept previous version are flushed before they count (#5434 slice 12)

Addresses #5434. From the rename inventory on #5434: `engine/instructions.js` `write` saves an agent's brief
(`CLAUDE.md` / `AGENTS.md`, in the person's own folder for an agent Kosmos found) by writing `<file>.<pid>.tmp`
(`wx`, mode at create), keeping the previous version in `<file>.previous` through a checked descriptor, and renaming
the temp over the brief. Nothing was flushed, so a crash could leave the brief at full length but zero-filled
(#5431): the agent would start with no instructions, and the kept previous version could be zeros too.

## Change
- The temp is written through a descriptor opened `wx` at the same mode, then `securewrite.flushOrThrow`, then
  closed. A failed flush throws into the existing catch: the temp is removed and the save refused with the same
  sentence; the old brief stays.
- The kept previous version is flushed (`flushOrThrow` on its descriptor) before `keptPrevious` is set. That block is
  best effort and never blocks the save, as before; a failed flush leaves `keptPrevious` false, so a backup that may
  not be on disk is not claimed.
- After the rename, `securewrite.syncDir(folder)` (POSIX only, best effort, never throws).
- `securewrite` exports `flushOrThrow` and `syncDir` (the same one-line change as slice 8, so the two merge cleanly).
- New `engine/instructions.fsync-5434.test.js` (6 tests), in `tools/windows-tests.js`.

## Decided
- **Flush inside the existing writer, not a move to writeSecret.** This writer's guards were built over 39 review
  rounds (the `wx` temp, mode at create, the version check, the checked backup descriptor between the temp write and
  the rename, the identity-text head). writeSecret would re-order the backup around the save. Adding the two flushes
  keeps every guard where it is.
- **What it does not add:** a unique temp name or a reap. The name stays `<file>.<pid>.tmp` (already `wx`, so a
  planted link is refused, not followed, as before).
- **Cost:** two file flushes and a folder flush per brief save (a person pressing Save).

## Tests
- the temp is flushed before its rename into the brief; the previous version is flushed; the folder is flushed after
  the rename (POSIX); a failed flush of the temp refuses the save, keeps the old brief, leaves no temp; a failed
  flush of the backup does not block the save and is not claimed; the brief keeps its mode (POSIX).
- Mutation: main's instructions.js fails 5 of 6 (the mode arm passes against main, as expected).
  Related set (81 files, list5434s12.txt): 2427, 0 fail, 3 skipped.

## Weakest premise
That `flushOrThrow`'s "cannot flush" tolerance (EINVAL/ENOTSUP, and EPERM/EISDIR on Windows) is right for the brief
as it is for securewrite's saves: on such a file system the save proceeds unflushed, exactly as before.
