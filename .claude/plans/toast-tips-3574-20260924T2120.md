# toast-tips-3574: the update-toast browser check turns first-visit tips off in its own sandbox

## Problem (measured)
The 0.6.93 staging cut (Mortals, 2026-09-24 20:45) failed at step 3b: `render-update-toast` was red twice. Its `page.click('#upd-btn')` timed out because `<div id="tiplayer">` (the #3574 "Settings for this computer" first-visit tip card, merged in #3656) intercepts pointer events. It reproduces on Agent1s on origin/main f208f566, rc=1, with the same intercept line.

## Why no PR gate caught it
`render-update-toast` is self-contained: it boots its own board with its own AGENT_WORKFORCE_DATA, outside the shared board groups in tools/browser-checks.sh. So a fresh sandbox shows every first-visit tip. #3656 added its own check and touched no other check.

## Call
Seed this check's own sandbox with `tips.json` = `{ seen: [], off: true }` before the board starts. The path comes from engine/tips.js `FILE()` under the same AGENT_WORKFORCE_DATA the spawned board gets, so it cannot drift. This is the same mechanism render-help-tips-3574.js uses (resetStore({ off: true })).

## Rejected
- Dismissing the tip card by clicking it in the check. That couples an update-toast check to tip-card markup it does not test.
- Changing the product so tips never cover Settings controls. Whether a first-visit tip may cover a control until it is closed is a design question for #3574's owner (Mona). This card only unblocks the cut.

## Weakest premise
That no other self-contained check (one outside the board groups) lands on a page with a first-visit tip. The 0.6.93 3b run is the evidence: this was the only red, and every other check passed on the same tree.

## Proof
Red on unmodified origin/main (rc=1, tiplayer intercepts). Green with the fix (rc=0, "TOAST DRIVE OK"). Same box, back to back.
