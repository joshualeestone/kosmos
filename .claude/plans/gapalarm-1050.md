# gapalarm-1050: the gap alarm (kosmos#1050)

## Why
Merged work has outrun what reaches anyone five times on record (50, 167, 9, 44, 89 commits; about 330 to prod on 2026-09-28), and each time a person noticed by hand. PigeonPete decided the card on 2026-09-28 (needs-decision sweep for Splinter): a scheduled, read-only check that tells the release owner when main is more than 50 commits or 24 h past staging, or staging more than 48 h past prod. Cuts stay manual.

## Call
- `tools/gap-alarm.js`: reads the served pointers (latest-staging.json, latest.json) and each manifest's `app.commit` (the build's own sha, as tools/shipped-gap.sh does) and `built.at`, fetches origin main, and counts with git. Main's hours run from the OLDEST commit not yet in staging, read on main's first-parent line, where committer time is when the work landed whether it was squashed or merged with a merge commit: how long merged work has waited for a cut. Decided at review 3: without --first-parent a merge-commit PR (13 of the last 200 on main) carried side-branch commits up to 43 h older than the merge and would alarm the hour it landed. The count stays every commit, as tools/shipped-gap.sh counts. Staging's hours run from when the staging build was CUT (built.at), while it holds anything prod does not: how long a build has waited for a promote (gated on walks, so the step a person takes). Decided at review 1: measuring staging from its oldest commit double-counted the wait for the cut, which main's limit already covers.
- Posts, best effort, to the release owner's pane by claude-msg (GAP_ALARM_TO, default barondraxum-discord:0.0) and as a comment on kosmos#1050, so the figures keep their history on the card. It posts when an alarm starts or its reasons change, every 24 h while it lasts, once when it clears, and once a day while it cannot tell. The post clock advances only on a post that went.
- Exit 0 no alarm, 1 alarm, 2 could not tell (not a pass). `--check` prints the verdict and posts nothing.
- `--plist` / `--install`: an hourly LaunchAgent (com.kosmos.gap-alarm) with an explicit node path and a PATH for launchd, generated in JS with escaped values (no shell heredoc, so the #666 heredoc hazard class cannot apply). Installed once on the release owner's box after merge: `node tools/gap-alarm.js --install` from the main checkout.
- Rejected: registering it in engine/fleet-monitors.js. That registry is a per-box expectation audited on every box, and this runs on one box (the release owner's), so every other box would report it missing forever.
- Rejected (Pete's call): freezing main during cuts; a fully automatic cut and promote.
- Weakest premise: that an alarm gets acted on. If the gap stays high while it fires, the next step is automating the staging cut (Pete's stated change-of-mind).

## Evidence
- `node --test tools.gap-alarm.test.js`: 14 of 14 at review 5 (8 of 8 at review 1). Pure verdict (each limit both sides; nothing waiting is never an alarm) and post rule; end to end against a throwaway repo with dated commits (both channels once, a day later again, the all-clear once); a failed post does not advance the clock; could-not-tell exits 2 and says why; the pointers read from a local HTTP server, with a manifest lacking app.commit as could-not-tell FOR THAT REASON; under the test runner the real claude-msg and gh (stubs placed where the defaults resolve, and no real gh on PATH) are never called, with a control outside the runner that is; the plist lints and installs into a sandbox without loading.
- Mutants, each failing the suite: `>=` for the commit limit; no daily repost; the clock advancing on a failed post; either test-runner guard removed; hours counted with nothing waiting.
- Live `--check` 2026-09-28 08:15 CDT: main 71 commits past staging 0.7.05 (alarm: main-commits), staging 327 commits past prod 0.6.99 (oldest 41 h). Matches Pete's 07:30 measurement.

## Mistakes caught in flight
- A test's control ran the script outside the test runner with a stub gh, but post() prepended /opt/homebrew/bin to PATH, so the real gh came first. It failed only because that HOME had no gh login; #1050 was checked and got no comment. post() no longer rewrites PATH (the plist sets it), and the control's PATH holds no real gh.
- A pointer test's control used spawnSync while the same process served the files, so the child timed out and read could-not-tell for the wrong reason. It now spawns asynchronously and asserts the reason.

## Review 1
- BLOCKER fixed: claude-msg refuses without $TMUX, which a launchd job never has, so the pane post would always fail while the gh comment counted as told. post() now gives claude-msg the default tmux server socket (`$TMUX_TMPDIR/tmux-<uid>/default,0,0`, as the fleet's slack-relay does), and a pane message that fails is said in the #1050 comment, so that channel is never silently lost. Tested: the stub sees $TMUX; a failing pane stub puts its reason on the card.
- The plist's node is the stable Homebrew link (/opt/homebrew/bin/node), not the running binary's Cellar path, which an upgrade deletes. `--install` refuses a linked worktree (removed after merge), before writing anything. Tested with copies of the script in a throwaway repo as a main checkout and as a linked worktree.
- Staging's hours from the build's built.at (see Call). A manifest without built.at is could-not-tell, tested.
- Tests added: the exact 24 h and 48 h boundaries; the daily repost while could-not-tell; a real fetch from a bare origin that moved ahead (a stale local ref reads 0, the run counts 1).
- Nits: a dead ternary removed; after a could-not-tell spell the all-clear says "measurable again"; the header says --check still fetches.

Tests: the exit-8 test now asserts the card retry (red when either channel's success advances both), and an old-format state test. - Round 5 (Opus): WARNING round 4's per-channel clocks left a pane that REPORTS failure (exit 7, or killed at the 30 s timeout between paste and Enter) with no ceiling, so a message that landed could repeat hourly. Mutants: without the backoff, and without exit 7, each turns a test red. NITs taken: the state write is atomic and never fatal ("posted, but could not record"), and the log line names the channels that went, after they went.
