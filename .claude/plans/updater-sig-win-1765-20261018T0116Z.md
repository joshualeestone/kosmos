# updater-sig-win-1765: the Windows updater checks the new launcher's signature before installing

**Posture:** production

Card: kosmos#1765 (Windows half). Related: #3015 (code signing), not closed by this. The fresh install (`tools/windows/setup.ps1`, Assert-KosmosSignature) already
requires a Valid Authenticode signature on Kosmos.exe from Kosmos Agent Manager, Inc. under Microsoft's ID
Verified code-signing chain. The in-app updater (`engine/win32update.js`) checked only the published SHA-256 and
left the signature as a marked seam (AUTHENTICODE-SEAM, deferred until signing landed). Signing has landed, so the
seam is filled.

## What changes
- `engine/win32update.js`, B4 (`verifyStaged`): after the required entries are present and BEFORE anything staged
  runs (the staged node.exe), the staged `Kosmos.exe` is checked:
  - `authenticodeOf(exe, timeoutMs)` asks Windows PowerShell 5.1 (full path; its own Security module imported by
    full path, as setup.ps1 does) for the status, the signer's common name, and the chain built with the
    certificates the signature carries (no revocation, leaf expiry ignored: the same chain policy as setup.ps1).
    The exe path rides in the environment, not the command line. Asynchronous (execFile), so the board keeps
    answering. The answer is written as pure ASCII (every non-ASCII character escaped inside PowerShell, UTF-8
    output besides): redirected, PowerShell 5.1 writes in the console code page and best-fits what it lacks,
    which could turn a lookalike signer into the real name. A failure is reported by what PowerShell said, not
    by its command line.
  - `signatureRefusal(answer)` (pure) refuses unless: status `Valid`; signer equals `Kosmos Agent Manager, Inc.`;
    the chain's root thumbprint is `F40042E2...BFA2`; some chain subject matches
    `^CN=Microsoft ID Verified Code Signing PCA [0-9]{4}, O=Microsoft Corporation, C=US$`. ASCII case-insensitive,
    as PowerShell's `-ne`/`-match` are in setup.ps1; a signer, root or intermediate with anything outside
    printable ASCII is refused (JS's toLowerCase folds the Kelvin sign to `k`; PowerShell's `-ne` does not).
  - A check that cannot run (PowerShell missing, timeout, unparseable answer) is a refusal, never a pass.
  - A refusal goes through the existing `refuse()` path: prepare() returns `{ ok:false, because }`, removes the
    staged tree, records prepare-status.json; begin() writes no journal and starts no helper; the CLI
    (`--apply ... --yes`, headless) prints it and writes `REFUSED <sentence>` to its report. The installed build
    is untouched, nothing is downgraded.
  - New seam `checkSignature` on prepare()/begin() options (default: the real check); new limit
    `signatureTimeoutMs` (60 s).
- Both download and `--from` (#3286) paths reach the check (both go through B4).
- `test-support/signedkosmos.js`: Windows' answer for the committed signed Kosmos.exe, measured on the box, for
  suites whose staged Kosmos.exe is a stub.

## Decided
- **Pins are setup.ps1's, duplicated and held equal by a test** that reads setup.ps1. Rejected: reading setup.ps1
  at runtime (it is not shipped in the bundle) and a shared JSON file (setup.ps1 runs as `irm | iex`, standalone).
  Weakest part: two copies; the test is what keeps them one. Would change my mind: a pin file both could load.
- **No leaf thumbprint pin**, as setup.ps1: Azure Artifact Signing certificates last about three days.
- **Only Kosmos.exe**, as setup.ps1. `app\bin\kosmos-tunnel.exe` is not checked by setup either; app\ and
  runtime\ stay covered by the checksums.
- **Placed before the staged node.exe runs**, not just before the swap: nothing from an unsigned update is executed.
- **No environment override** for the expected signer in production (setup.ps1's test override needs its no-launch
  test flag; the updater uses a function seam instead, which no production caller passes).

## Not covered (stated)
- The signature proves the launcher only, as for a fresh install.
- The rollback to a kept previous build (`rollbackToPrevious`) restores a build that was already installed; it is
  not re-checked here.

## Tests
- `engine/win32update.signature-1765.test.js`: the rule (everywhere), the pins against setup.ps1 (everywhere), and
  on Windows only: the committed signed Kosmos.exe passes; a one-byte-tampered copy (HashMismatch), a copy with
  its signature cut off (NotSigned), node.exe (Valid, same Microsoft chain, other signer), a missing file, and copies
  signed by a throwaway certificate whose name only looks like the signer (fullwidth K, Kelvin sign, en dash) are
  refused, the last proving the name reaches the check unchanged. The cases needing a Valid answer skip, saying so,
  on a computer without Microsoft's Identity Verification root.
- `engine/win32update.test.js` (#1765 section): prepare refuses each bad answer before the staged node runs and
  cleans up; a check that throws or times out refuses; begin() writes no journal and leaves the install as it was;
  `--from` is checked; on Windows only, a real download with the signed/tampered exe, and the headless
  `--apply --from --yes --report` path refusing an unsigned launcher and starting a signed one; and the existing real-release test (KOSMOS_WIN_ZIP_SAMPLE) now asks Windows about the
  release's own Kosmos.exe (run against the published 0.7.55 zip: it stages).
- Each new test went red with its check removed (nine mutations), then restored.
- Full node suite on the Windows box, branch vs main, compared by test name and reason.
