# bkupload-5535: E0.6 (#5535) slice 3, the uploader

## Why
E0.6's pure parts are on main (hpke, backupformat, backupscan, the streaming chunker). The coordinator's grant
routes are live but OFF (kosmos-relay #322, slice 1), and slice 2 (Ice Cream Kitty, `putgrant-5535`) moves chunk
grants to write-once presigned PUTs on my ruling of 2026-10-08 (on #5535). This is the Mac half that consumes
them: sealed chunk objects to the bucket, through grants, refusing any grant that does not bind our bytes.

## Contract (slice 2, from #5535)
`POST /v1/org/backup/grant` `{ chunks: [{ size, md5 }], nonce }` -> `{ epoch, period, retain_until, expires_at,
uploads: [{ key, url, headers }] }`, one per chunk, in order. Each upload is a presigned PUT with Content-MD5,
Content-Length and If-None-Match: * signed. Measured on the Object Lock test bucket (#5535): matching body 200,
different body 400 BadDigest, dropped signed header 403, second PUT 412. A PUT after a delete marker would make a
new version; closed by a PutObject-only coordinator credential.

## Change: `engine/backupupload.js`
- `grantBody`: sizes and MD5s in order, and a fresh 128-bit nonce every request (a signed body is accepted once).
- `parseGrant`: one upload per chunk, distinct keys, https only (a test seam allows http), header values are text,
  and every upload BINDS OUR BYTES: Content-MD5 and Content-Length are the ones we asked for, If-None-Match is `*`.
  A grant failing any of that is refused before a byte leaves.
- `putOne`: one PUT, classified: 200 stored, 412 present (an earlier attempt of ours landed; the key is this grant's
  and the PUT is write-once with the MD5 signed), 403 expired, other 4xx refused, 5xx/429/network/timeout retry.
- `uploadChunks`: batches of 500 (the coordinator's limit); within a grant, up to 3 tries per upload with backoff,
  never past expires_at; uploads a grant could not finish get a NEW grant (each spends allowance again, Kitty's
  contract point 2), at most 3 more per batch. A name seen twice in one run is uploaded once. Refusals come back
  as the tunnel's typed text; `refusalOf` reads status and code: backup_quota (or any 429) ends with retryLater,
  replayed gets one retry with a new nonce, the rest stop. Returns the name -> key map the manifest needs.
- `engine.reachable.test.js`: uploadChunks excused (its caller is the slice-3 walker, which needs E0.1/E0.2).

## Measured
Node's fetch (v26 here) sends the signed headers as given, with Content-Length equal to the body; a mismatched
Content-Length throws locally (UND_ERR_REQ_CONTENT_LENGTH_MISMATCH) before anything is sent. The extra headers
fetch adds (accept, user-agent, ...) are not signed, so a presigned URL ignores them.

## Tests (`engine/backupupload.test.js`)
A local write-once, MD5-checking bucket and a stub coordinator. Stores every chunk under its key; a grant with
another MD5, another length, no If-None-Match, a short list, a repeated key or no expiry is refused with ZERO PUTs;
http refused without the seam; 412 counts as stored; 503 retried; 403 regrants only what is left, with a new nonce;
an already-expired grant is never used; re-granting is bounded; quota/replayed/other refusals; dedup by name; the
500 split; bad inputs refused before any request. Red-checked: removing the MD5 binding, the 412 rule, the fresh
nonce, the regrant bound, the expiry check or the dedup each turns the suite red.

## Not in this slice
The manifest grant and upload (slice 2's manifest shape is not published yet), the walker that decides what to
upload, and resume across runs (a later run re-grants; keys are coordinator-chosen per grant, so nothing dedups
across runs here: the walker's index of names already stored does that).

## Weakest premise
That 412 means OUR earlier write. It holds because the key is unique to this grant and the PUT is write-once with
the MD5 signed, so only these exact bytes could be there. If a future grant ever reuses a key across grants, 412
would no longer prove that, and putOne must treat it as refused.
