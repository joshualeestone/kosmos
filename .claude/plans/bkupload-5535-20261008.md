# bkupload-5535: E0.6 (#5535) slice 3, the uploader

## Why
E0.6's pure parts are on main (hpke, backupformat, backupscan, the streaming chunker). The coordinator's grant
routes are live but OFF (kosmos-relay #322, slice 1), and slice 2 (Ice Cream Kitty, `putgrant-5535`) moves chunk
grants to write-once presigned PUTs on my ruling of 2026-10-08 (on #5535). This is the Mac half that consumes
them: sealed chunk objects to the bucket, through grants, refusing any grant that does not bind our bytes.

## Contract (slice 2: kosmos-relay putgrant-5535, coordinator/src/backup.rs, read directly)
`POST /v1/org/backup/grant` `{ chunks: [{ size, md5 }], nonce }` -> `{ epoch, period, retain_until, expires_at,
uploads: [{ key, url, headers }] }`, one per chunk, in order; `expires_at` and `retain_until` are ISO-8601 UTC
strings. Each upload is a presigned PUT whose query signature covers content-length, content-md5, host,
if-none-match and the lock headers; `headers` lists what to send, WITHOUT Content-Length and Host (the HTTP client
sets those). Keys are random per upload (two new ids) and each url's path ends with its key. Measured on the Object
Lock test bucket (#5535): matching body 200, different body 400 BadDigest, dropped signed header 403, second PUT
412. A PUT after a delete marker would make a new version; closed by a PutObject-only coordinator credential.
(Review round 1 caught that the first version of this plan, and the code, assumed a numeric expires_at and a
Content-Length in headers: every real grant would have been refused after its allowance was spent.)

## Change: `engine/backupupload.js`
- `grantBody`: sizes and MD5s in order, and a fresh 128-bit nonce every request (a signed body is accepted once).
- `parseGrant`: before a byte leaves, every upload must bind OUR bytes: its Content-MD5 is ours, a Content-Length
  if listed is ours, `X-Amz-SignedHeaders` covers content-length, content-md5, host and if-none-match, If-None-Match
  is `*`, the url is https (a test seam in deps allows http), its decoded path ends with the upload's own key, and
  no key or url repeats. `expires_at` is read as ISO (or seconds or milliseconds).
- `putOne`: one PUT, `redirect: 'manual'` (a 3xx is refused, never followed), classified: 200 stored; 412 present
  ONLY on a retry of that key, refused on a first attempt; 403 whose body says expired: expired; other 4xx and 403:
  refused; 5xx/429/network/timeout: retry.
- `uploadChunks`: batches of 500; within a grant, up to 5 tries per upload ON THE SAME KEY while the grant lasts
  (so a lost answer that landed shows up as that 412, not as a second copy); an upload the grant could not finish
  gets a NEW grant (new key; at most 3 more per batch, so at most 4 locked copies of one chunk per run if every
  answer was lost); a refused PUT stops the run (a new grant would not fix it and spends allowance); a grant
  already expired on arrival stops the run as clock skew, without asking for another; a bad concurrency value
  falls back to the default; success only when every chunk has a key. Refusals come back as the tunnel's typed
  text; `refusalOf` reads status and code: backup_quota (or any 429) ends with retryLater, replayed gets one retry
  with a new nonce, the rest stop. Returns the name -> key map the manifest needs.
- Why a 412 on a retry is proof without reading the object (the coordinator's doc suggests checking its ETag; the
  uploader holds no read grant): the key is random, only this grant's url can write it, and that url's signature
  fixes our MD5, so whatever holds the key is our bytes.
- `engine.reachable.test.js`: uploadChunks excused (its caller is the slice-3 walker, which needs E0.1/E0.2).
- `engine/remote.js`: macRequest's comment names the backup grant routes, not only /v1/mac/.

## Measured
Node's fetch (v26 here) sends the signed headers as given, with Content-Length equal to the body; a mismatched
Content-Length throws locally (UND_ERR_REQ_CONTENT_LENGTH_MISMATCH) before anything is sent. The extra headers
fetch adds (accept, user-agent, ...) are not signed, so a presigned URL ignores them.

## Tests (`engine/backupupload.test.js`)
A local write-once, MD5-checking bucket and a stub coordinator in slice 2's real shape. 18 tests: stores and maps
every chunk; twelve kinds of bad grant each refused with ZERO PUTs; Content-Length absent from headers accepted;
http only through the seam; a first-attempt 412 refused with nothing recorded; a timed-out PUT retried on the same
key and its 412 counted, with no second grant; 503 retried; an expired 403 regrants only what is left; 400, a
signature 403 and 404 stop the run with no new grant; a redirect never reaches its target; retries then regrants
bounded; an already-expired grant stops as clock skew; quota, replayed and other refusals; dedup and the 500 split;
bad concurrency values; missing wiring. Red-checked, each mutant reds the suite: the MD5 binding, the 412 rules
(first try; same-key retry), the fresh nonce, the regrant bound, the expiry check, the dedup, the redirect, the clock
stop, a refused PUT regranting, the concurrency guard, the signed-headers check, the url-to-key check, the
repeated-url check and the ISO expiry. (Two of those were first vacuous, caught by the red check: the url-to-key
and repeated-url cases each tripped the other check; they now isolate one each.)

## Not in this slice
The manifest grant and upload (slice 2's manifest shape is not published yet), the walker that decides what to
upload, and resume across runs (a later run re-grants; keys are coordinator-chosen per grant, so nothing dedups
across runs here: the walker's index of names already stored does that).

## Weakest premise
That 412 means OUR earlier write. It holds because the key is unique to this grant and the PUT is write-once with
the MD5 signed, so only these exact bytes could be there. If a future grant ever reuses a key across grants, 412
would no longer prove that, and putOne must treat it as refused.
