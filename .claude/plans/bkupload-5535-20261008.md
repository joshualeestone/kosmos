# bkupload-5535: E0.6 (#5535) slice 3, the uploader

## Why
E0.6's pure parts are on main (hpke, backupformat, backupscan, the streaming chunker). The coordinator's grant
routes are live but OFF (kosmos-relay #322, slice 1), and slice 2 (Ice Cream Kitty, `putgrant-5535`) moves chunk
grants to write-once presigned PUTs on my ruling of 2026-10-08 (on #5535). This is the Mac half that consumes
them: sealed chunk objects to the bucket, through grants, refusing any grant that does not bind our bytes.

## Contract (slice 2: kosmos-relay putgrant-5535, coordinator/src/backup.rs, read directly)
`POST /v1/org/backup/grant` `{ chunks: [{ size, md5 }], nonce }` -> `{ epoch, period, retain_until, expires_at,
uploads: [{ key, url, headers }] }`, one per chunk, in order; `expires_at` and `retain_until` are ISO-8601 UTC
strings. Each upload is a presigned PUT whose query signature covers content-length, content-md5, host,
if-none-match and the lock headers; `headers` lists what to send, WITHOUT Content-Length and Host (the HTTP client
sets those). Keys are random per upload (two new ids) and each url's path ends with its key. Measured on the Object
Lock test bucket (#5535): matching body 200, different body 400 BadDigest, dropped signed header 403, second PUT
412. A PUT after a delete marker would make a new version; closed by a PutObject-only coordinator credential.
(Review round 1 caught that the first version of this plan, and the code, assumed a numeric expires_at and a
Content-Length in headers: every real grant would have been refused after its allowance was spent.)

## Change: `engine/backupupload.js`
- `grantBody`: sizes and MD5s in order, and a fresh 128-bit nonce every request (a signed body is accepted once).
- `parseGrant`: before a byte leaves, every upload must bind OUR bytes: its Content-MD5 is ours, a Content-Length
  if listed is ours, `X-Amz-SignedHeaders` covers content-length, content-md5, host and if-none-match, If-None-Match
  is `*`, the url is https on an AWS S3 host (only the module setter `allowHttpForTests` widens that), its decoded path ends with the upload's own key, and
  no key or url repeats. `expires_at` is read as ISO (or seconds or milliseconds).
- `putOne`: one PUT, `redirect: 'manual'` (a 3xx is refused, never followed), classified: 200 stored; 412 present
  only after an earlier attempt that may have written it (never after pre-connect failures or S3's "nothing
  committed" 400 RequestTimeout / IncompleteBody, which retry), refused otherwise; 501 refused; 403 whose body says expired: expired; other 4xx and 403:
  refused; 5xx (SlowDown), 429, 409, network, timeout: retry on the same url. (Local fetch failures: refused.)
- `uploadChunks` (as of review round 9; the round sections below say what changed when): grants are SIZED to one
  window: the first asks for 8 chunks, and each next one follows the rate the last achieved (80% of a window, at
  most double, 1 to 500), a grant that ran out counting as a whole window. Within a grant each upload is
  retried on the SAME url until the grant expires (backoff capped at 30 s), and its timeout is 60 s plus 16 KB/s of
  its bytes (since round 4 not capped at the grant: S3 checks expiry on arrival). A chunk that met bucket or network trouble and then ran out of time, or was told
  the grant expired, ends the run retryLater: it never gets a new grant, since an earlier attempt may have landed. A
  refused PUT stops the run. A grant expired on arrival stops as clock skew. 4 grants in a row that store nothing
  end the run retryLater. Bad concurrency falls back to the default; success only when every chunk has a key.
  Refusals come back as the tunnel's typed text; `refusalOf` reads status and code: backup_quota (or any 429) ends
  with retryLater, replayed gets one retry with a new nonce, the rest stop. Returns the name -> key map.
- Why a 412 on a retry is proof without reading the object (the coordinator's doc suggests checking its ETag; the
  uploader holds no read grant): the key is random, only this grant's url can write it, and that url's signature
  fixes our MD5, so whatever holds the key is our bytes.
- `engine.reachable.test.js`: uploadChunks excused (its caller is the slice-3 walker, which needs E0.1/E0.2).
- `engine/remote.js`: macRequest's comment names the backup grant routes, not only /v1/mac/.

## Measured
Node's fetch (v26 here) sends the signed headers as given, with Content-Length equal to the body; a mismatched
Content-Length throws locally (UND_ERR_REQ_CONTENT_LENGTH_MISMATCH) before anything is sent. The extra headers
fetch adds (accept, user-agent, ...) are not signed, so a presigned URL ignores them.

## Tests (`engine/backupupload.test.js`)
A local write-once, MD5-checking bucket and a stub coordinator in slice 2's real shape. 18 tests at review round 1 (34 at round 4; the round sections below list what each added): stores and maps
every chunk; twelve kinds of bad grant each refused with ZERO PUTs; Content-Length absent from headers accepted;
http only through the seam; a first-attempt 412 refused with nothing recorded; a timed-out PUT retried on the same
key and its 412 counted, with no second grant; 503 retried; an expired 403 regrants only what is left; 400, a
signature 403 and 404 stop the run with no new grant; a redirect never reaches its target; retries then regrants
bounded; an already-expired grant stops as clock skew; quota, replayed and other refusals; dedup and the 500 split;
bad concurrency values; missing wiring. Red-checked, each mutant reds the suite: the MD5 binding, the 412 rules
(first try; same-key retry), the fresh nonce, the regrant bound, the expiry check, the dedup, the redirect, the clock
stop, a refused PUT regranting, the concurrency guard, the signed-headers check, the url-to-key check, the
repeated-url check and the ISO expiry. (Two of those were first vacuous, caught by the red check: the url-to-key
and repeated-url cases each tripped the other check; they now isolate one each.)

## Not in this slice
The manifest grant and upload (slice 2's manifest shape is not published yet), the walker that decides what to
upload, and resume across runs (a later run re-grants; keys are coordinator-chosen per grant, so nothing dedups
across runs here: the walker's index of names already stored does that).

## Weakest premise
That 412 means OUR earlier write. It holds because the key is unique to this grant and the PUT is write-once with
the MD5 signed, so only these exact bytes could be there. If a future grant ever reuses a key across grants, 412
would no longer prove that, and putOne must treat it as refused.

## Ships
Through the connector a cut ships; it needs kosmos-relay backuproutes-5535 (the grant route on the tunnel's
mac-request allow-list) in that connector.

## Review round 2 (sonnet) and Ice Cream Kitty's S3 notes: fixed
- **Headers are allow-listed:** only content-md5, if-none-match, the two lock headers (and content-length if
  listed); a name twice in any case, or a value that is not printable ASCII, is refused. A CRLF or Transfer-Encoding
  from a coordinator bug would otherwise reach fetch.
- **The lock is checked, not just the bytes:** mode COMPLIANCE, retain-until 29 to 39 days from the grant's own start
  (expires_at minus the 15-minute window, never the Mac's clock), and both lock headers in X-Amz-SignedHeaders. A
  wrong lock on this bucket cannot be undone.
- **Local failures are not retried:** fetch refusing the request itself (a length mismatch, a bad header) is refused
  at once; only a timeout or a network code (ECONNREFUSED, ENOTFOUND, UND_ERR_SOCKET, ...) retries.
- **Bucket trouble never spends a new grant** (Kitty, from S3's docs): 5xx/SlowDown and 409 ConditionalRequestConflict
  retry the SAME url until the grant expires (backoff capped at 30 s); a chunk that met only that kind of trouble
  until expiry ends the run retryLater. New grants are only for a clean expiry or a 403 that says expired.
- **Dedup checks bytes:** two chunks with one name but different bytes are refused, not silently deduped.
- **Never throws, for real:** one outer try/catch.
- 24 tests at that round. Red-checked by mutant: header allow-list, duplicate names, lock mode, lock window, lock headers signed,
  local-failure classification, 409 retried, no regrant after trouble, same-name bytes, the outer catch. Not
  isolable: the printable-ASCII rule (every allowed header also has an exact-value check that catches a CRLF first);
  kept as defense in depth. The local-failure test first ran on the real clock, so its mutant spun for the whole
  15-minute grant instead of failing; it now runs on a fake clock and fails at once.

## Review round 3 (opus): fixed
- **Told "expired" after trouble, a chunk got a new grant** (reproduced: the same bytes locked twice under two keys).
  Now it ends the run retryLater like any troubled chunk.
- **Fixed 500-chunk grants charged a slow uplink for what it could not send** (about 2.1 GB per 15-minute window at
  5 Mbps). Grants are now sized to the window, as above.
- **A credential's expiry (ExpiredToken) read as a grant's expiry.** Only AccessDenied with "Request has expired" is.
- **An unknown network code was a permanent refusal.** Now only fetch's own local codes (and a TypeError with no
  cause) are refused; anything else retries.
- 28 tests at that round; each of the four red-checked. The plan's uploadChunks bullet was stale against the code (it still said
  "5 tries"); rewritten.
- NITs taken: an ISO time needs a Z or an offset (else Date.parse reads it as local time); a grant expiring more
  than the window plus 5 minutes ahead of the Mac's clock is refused before any byte (widened to an hour in round 5) (the lock check is measured
  from the grant's own start, so a far-ahead coordinator clock would otherwise pass it); the backoff is jittered.

## Review round 4 (sonnet): fixed
- **A PUT's timeout is no longer capped at the grant's remaining time.** S3 checks a presigned url's expiry when the
  request arrives, so a PUT started in time may finish late; aborting it turned a landed write into an unknown (and a
  slow link's ordinary expiry into "stuck"). Tested with a PUT that outlasts a 1-second grant: stored.
- **A stuck end names what may have landed:** `unsure: [{ name, key }]`, so the caller can record the possible
  orphans.
- **A grant request with no answer at all** (network, timeout) ends retryLater; one refused before sending (not
  enrolled, busy) does not.
- NITs taken: X-Amz-Expires must be at most the window; a bad putTimeoutMs falls back; the header says the regrant
  bound is grants in a row that store nothing; the lock window's edges (29 and 39 days in, 28 and 40 out) and a 412
  after only 5xx answers are tested; stale test counts here corrected.
- Not taken: constraining the upload host. The Mac holds no endpoint of its own to compare with, and the payload is
  sealed; the coordinator choosing the bucket host is the trust this design already places in it.
- 34 tests; the four fixes red-checked.

## Review round 5 (opus): fixed
- **The url's query string is allow-listed too:** only SigV4's six parameters (X-Amz-Algorithm, Credential, Date,
  Expires, SignedHeaders, Signature), each once. S3 honours x-amz-* request parameters in the query, so a legal hold
  (no end date), a retention, tagging or a multipart uploadId there would act on the locked bucket unseen by the
  header checks. Tested (legal hold, uploadId, a repeated parameter); red-checked.
- **A refusal still names the chunks that met trouble on the way** (`unsure`), as a stuck end does. Red-checked.
- NITs taken: the far-ahead expiry check tolerates an hour (a Mac a few minutes slow still backs up; S3 refuses real
  skew itself) and says the grant's allowance is spent; an S3 error body is read only up to 8 KB (a resource bound,
  tested for behaviour but not red-checkable); a redundant String() dropped.
- 36 tests.

## Review round 6 (sonnet): fixed
- **S3's 400 RequestTimeout and IncompleteBody retry the same url** (nothing committed; a slow link meets both);
  501 NotImplemented is refused instead of retried for the whole window.
- **The lock window is measured from the SIGNED time:** all six SigV4 query parameters are required, X-Amz-Date must

## Review round 10 (sonnet): fixed
- **Upload hosts are pinned to AWS S3** (path-style `s3.<region>` / `s3-<region>`, virtual-hosted
  `<bucket>.s3.<region>`, `.amazonaws.com`, default port only); only the test setter widens it. This REVERSES my
  round-4 call ("the coordinator choosing the bucket host is trust the design already places in it"). Round 10 put
  it against the brief's own rule: a Mac does not act on what a server tells it, and a coordinator bug must not be
  able to aim a Mac's upload at a LAN address or another service. If the bucket ever moves off AWS (B2, say), this
  pattern is the one line to change, deliberately.
- **Pre-connect failures (DNS, connection refused, TLS) retry but never make a chunk unsure:** nothing could have
  been written. A grant that only ever met those ends retryLater with no `unsure` and no second grant.
- **Every bad-grant case asserts WHY it was refused**, so a case can no longer pass on an unrelated earlier check.
  Doing that moved the repeated-url check first (it had been reached only after the bucket-path check), and showed
  the CRLF case isolates the printable-ASCII rule, which round 5 recorded as not isolable. It is now red-checked.
- NITs taken: the lock date must be an ISO string (a bare number would pass parsing but be refused by S3); a redundant
  regex clause dropped. Not taken: a worker in its backoff notices a stop when it wakes (up to 30 s); correct, only
  slower.
