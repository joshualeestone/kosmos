# flaky-2036-3986: the #2036 hang tests stop racing a 300ms clock

Card: kosmos#3986 (mine: I wrote the test with #2036).

## What was actually wrong (measured)
Two mechanisms, found in order:
1. PRODUCT: after a board call times out, tools/plus-signin-fresh.js sent the cleanup
   `signin-cancel` on the SAME budget (KOSMOS_PLUS_CALL_MS). A timeout is the sign the board is
   slow, so that cancel was the call most likely to be abandoned, leaving a half sign-in. In
   production the budget is 15s, so this bit only under the test's 300ms, but the ordering was
   wrong regardless. Now `CLEANUP_MS = max(CALL_MS, 5s)` for all six cleanup cancels.
2. TEST: at 300ms, the runner's EARLIER calls (board identity, /api/remote) timed out on a loaded
   machine, so it exited as "setup, nothing recorded" before ever reaching the hanging call. That
   is the code the test expects, so only the final "cancelled?" assertion noticed. Seen directly:
   run 24 of a load sweep failed both hang tests in ~600ms with "never cancelled", far inside the
   new 5s floor. Now the hang tests use HANG_MS = 2000 and assert the hanging call was REACHED
   (signin-start / signin-verify), so this can never pass or fail for the wrong reason again.

## Tests
- New: a fake board answering the cancel after HANG_MS + 1s; the runner must wait for it. Reverting
  the floor reds it ("abandoned the cancel"), measured.
- Load: 20 runs of the whole file alongside a full validation (load avg 16-28): 0 failures after
  the fix; before it, 2 of 40 (both hang tests together).

## Rejected
- Only widening the test budget: hides mechanism 1, which is a real ordering bug.
- Making the fake signal completion without a budget: the runner's budget IS what is under test.

## Weakest premise
2000ms is a margin, not a guarantee: a machine slow enough to take 2s for a local HTTP round trip
would still fail, but now with a message naming the call that was never reached.
