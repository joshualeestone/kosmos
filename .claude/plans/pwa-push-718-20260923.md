# pwa-push-718: PWA push client (the client half of #718 web push)

Author: Kano (Mortal Kombat fleet). Date: 2026-09-23.

## What "finished" looks like

A person can turn on notifications for a device (phone or desktop) from Settings,
grant the browser permission, and have the device subscribed so a push sent from
their Mac shows a system notification even when the board tab is closed, with the
notification naming who/what and opening their own Mac when tapped.

## Scope (this branch = the CLIENT half only)

`#718` is a bundle (push + installable icon + store). This branch ships the **push
client**: the service worker, the in-Settings subscribe flow, and the `/sw.js`
route that serves the worker. It does **not** ship the coordinator sender (already
shipped in kosmos-relay) or the board's `/v1/push/*` proxy routes (Raiden,
`webpush-718`).

## Architecture decision (reconciled live with Liu Kang + Raiden, 2026-09-22/23)

Original recon: kosmos-relay's coordinator **already ships web push end-to-end**:
a real minted VAPID key (`coordinator/src/keys.rs`), `POST /v1/push/subscribe`
(Bearer session token, deriving account/device, per-Mac `acked` gate, #1221),
`GET /v1/push/vapid-key`, `fan_out`, and a real `VapidSender` (RFC 8291/8292 plus
dead-subscription pruning) that is the **default** in `main.rs`
(`KOSMOS_PUSH=log` is the only opt-out). The Mac already emits events into it via
`engine/notify.js` to `POST /v1/mac/notify` to `fan_out`.

Decision: **client to board same-origin; the board proxies to the real
coordinator.** The board holds the coordinator session token server-side and
already proxies every other coordinator op (enrol, forget-mac, federation), so a
direct client-to-coordinator call (exposing the token to browser JS plus a
coordinator CORS change) buys nothing. Division of labor:

- **This branch (client):** subscribe flow uses same-origin relative paths
  (`/v1/push/vapid-key`, `/v1/push/subscribe`), `PushSubscription.toJSON()` shape;
  maps the coordinator's `EventSummary {kind, agent, project, id, address}` payload
  to notification title/body plus a click-through to the Mac address.
- **Raiden (`webpush-718`, board):** the two `/v1/push/*` routes become thin
  proxies to the coordinator (drop the local store and the static VAPID key).

## Files

- `web/sw.js`: root-scope service worker. Offline app-shell cache; a `push`
  handler that renders the coordinator payload; a `notificationclick` that
  focuses/opens the board (or the Mac address).
- `web/index.html`: the "Push to this device" control (in the **This computer**
  per-device section, beside Sounds, per the #3138 rule) plus the
  permission/subscribe/POST flow in an attributed `<script id="push-client">`
  block. A button, not a toggle (a browser permission cannot be revoked from
  script).
- `server.js`: serve `/sw.js` at the site root (`Service-Worker-Allowed: /`,
  `no-store`).
- `docs/browser-checks/render-push-718.js`: headed Chromium check. `/sw.js`
  serves as a worker, registers, controls the page, and a REAL push delivered
  through the worker's own handler (CDP) shows the notification mapped from the
  real coordinator payload.

## Testing

- Node suite (`yarn test`) green (0 fail). Behavioral changes touched shared
  page-test infrastructure; fixed the two greedy single-script extractors
  (`web.post-receipt`, `web.quoteb`) to be non-greedy so they remain correct now
  that the page has a second attributed script block, and satisfied the
  browser-checks README plus reason-grep count guards.
- `server.sw-718.test.js` covers the `/sw.js` route (status, JS content-type,
  `Service-Worker-Allowed: /`, `no-store`, HEAD, and that the page registers the
  worker). `web.sw-718.test.js` covers the pure functions `boardUrlFor` (the
  arbitrary-navigation allowlist, including hostile-input rejection) and
  `notificationFor` (the coordinator-payload mapping).
- `web.push-client-718.test.js` covers the client flow (`enablePush`,
  `reflectPushState`, `paintButton`) by eval'ing the push-client block with the
  browser boundaries stubbed: the happy path, a failed POST (asserting the
  orphaned subscription is unsubscribed and the button stays retryable), denied,
  dismissed, unsupported, the load-time On-vs-Turn-on paint, and that clicking the
  button drives the flow.
- `render-push-718.js` (headed Chromium) covers the WORKER end only: `/sw.js`
  serves as a worker, it registers and controls the page, and a push delivered
  through the worker's own handler (via the CDP `deliverPushMessage` verb, which
  needs no subscription) renders the mapped notification. It does NOT drive the
  subscribe flow and never calls `/v1/push/*`, so it passes today without Raiden's
  proxies. The full client-to-coordinator delivery path (subscribe, POST a real
  subscription, a real coordinator push landing on an installed PWA) has no
  automated check; it needs the live board plus Raiden's proxies and is verified
  by hand once both are deployed.

## Known external dependencies (not blockers for this client PR)

1. Raiden's board `/v1/push/*` proxies (`webpush-718`).
2. Deployed coordinator off `KOSMOS_PUSH=log`, with `KOSMOS_VAPID_SUBJECT` a real
   mailto (Splinter's coordinator-deploy checklist, tracked by Liu Kang).

A real push landing on an installed PWA requires 1 and 2; the client is complete
and green independently.
