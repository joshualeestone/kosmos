# #5039 Windows half: pre-accept the Claude settings at every Windows launch

**Posture:** production

## Done looks like
A Windows Claude agent gets `trust.preacceptBypass` (the settings write that, with Renet's
#5042, also carries `"switchModelsOnFlag": true`) at every launch and every streaming
launch/resume, not only at create and on an account move. So an agent made before the fast
update stops freezing on the Opus 5.5 "safeguards flagged, switch to Opus 4.8?" modal after
its next restart. Codex agents get no Claude settings.

## Change (Renet's spec on #5039)
`engine/win32launch.js`: next to each `trust.preacceptOnboarding` call (launch() and
launchStreaming()), on the same Claude-only path:
`try { trust.preacceptBypass(s.configDir || null, !s.configDir); } catch { /* best-effort */ }`.
Mirrors the Mac's ensure-launch-trust (every launch). Best-effort, idempotent.
Both calls go through a small `preacceptSettings(s)` that logs a refusal to stderr (the board
log): preacceptBypass reports failure by RETURNING ok:false, so a bare try/catch would drop a
write that fails every launch and leave the agent on the modal with no trace.

**Second behaviour change, deliberate:** the fence around both Claude writes is now positive,
`String(s.runner || 'claude') === 'claude'`, instead of `s.runner !== 'codex'`. gemini, grok,
antigravity and muse runners exist now; the old fence would have written Claude onboarding
(already) and Claude settings (new) into their homes, or into the shared default
~/.claude/settings.json when they have no configDir. This also stops the EXISTING #3383
onboarding write for those runners, which is the same correction. An omitted runner still
means Claude (tested). Tests: gemini gets neither key; putting the old fence back turns it red.

## Tests
`engine/win32launch.test.js`: own-account launch writes the account's settings.json;
default-account launch writes the default agent settings; a launch merges (other settings
survive); codex writes nothing into CODEX_HOME; a streaming resume writes too. Removing the
calls turns 4 red (codex passes either way, as it should).
**Sandboxing:** `AGENT_WORKFORCE_CLAUDE_SETTINGS` is now pointed into the sandbox in
win32launch.test.js and win32supervisor.test.js. Without it, every default-account launch in
those suites would write the REAL ~/.claude/settings.json of whoever runs them (on the
Windows box that file is shared by every agent). Checked: its mtime is unchanged by a run.

## Decisions
- This PR is independent of #5042: preacceptBypass already exists on main (bypass consent).
  The new key arrives through it when #5042 merges; until then this only re-asserts the
  bypass consent at launch, which the Mac already does every launch.
- An explicit `skipDangerousModePermissionPrompt: false` is overwritten at launch, as on the
  Mac and at create today (unattended agents need it). "Keeps an explicit false" in the spec
  is about switchModelsOnFlag inside #5042, not this key.
- Rejected: writing only on fresh launches. A resume is exactly the restart that should pick
  up a new default.

## Weakest part
Not measured live on a real Windows agent: the next Windows build plus a real agent
restart is the proof that the modal no longer stops it. Two trust.test.js arms fail on this
box on unmodified main (POSIX file modes); unrelated.
