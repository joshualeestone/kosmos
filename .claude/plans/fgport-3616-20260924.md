# fgport-3616: per-run ports in test-board-foreground-2956.sh

Card: #3616. Owner: Kano. Reviewer/merger: Liu Kang.

## Problem
`tools/test-board-foreground-2956.sh` cases 4-7 each started a stub port holder
on a FIXED port (18719, 18723, 18729, 18731). The script runs inside
`yarn test:shell`, so two agents running the suite on one Mac at the same time
bound the same ports. One run's holder failed to bind, and its board-run then
met the other run's holder, or nobody once that holder was killed, so one of
the two runs went red.

## Finished means
Two or more copies of the script run concurrently stay green, the lsof listener
cases (6, 7) still exercise a real listener on the port board-run is given, and
a holder that fails to start is a visible FAIL rather than a silent pass.

## Design
A `start_holder` helper: the stub node server binds port 0, writes the port the
OS chose to a temp file (tmp + rename, so a partial write is never read), and
the case reads it back. If no port is reported the case FAILS and skips
board-run, because running board-run with an empty KOSMOS_PORT would fall back
to a default port and could touch a real board.

Rejected: a random high port plus retry. It still has a window between choosing
and binding, and needs retry logic that bind-0 does not.

## Evidence
- origin/main, 10 rounds x 4 concurrent copies: 14/40 runs red, on the 18731,
  18729 and 18723 cases.
- This branch, same batch: 40/40 green.
- Controls: a holder reporting port+1 turns all four holder cases red (so the
  cases really use the holder's port); a holder that cannot bind reports
  "stub holder never reported a port".

## Out of scope
`run_br` passes `KOSMOS_PORT=17777` for cases 1-3. Nothing in the test binds
it, so concurrent runs cannot collide there. Any unrelated listener on 17777
would still make board-run defer (cmd_board_run exits 0 on healthy /
port_taken_by_stranger / port_has_listener) and case 2 would fail. Not changed
here; the card is about concurrent runs.
