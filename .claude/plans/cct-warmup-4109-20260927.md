# cct-warmup-4109: warm the browser before the Android app opens

Addresses #4109 (part of #4090 and #718). Routed to me by Liu Kang (m1245, 2026-09-27), from Kano.
#4105 read most of the 3.5 s Android sign-in wait (#4101's median) as Chrome starting up, and
estimated 0.5 to 1.2 s from Custom Tabs warmup plus mayLaunchUrl.

## Finished means
Seven cold runs before and after on the API 35 Moto AVD, measured the way #4101 did, with the
median change reported even if it is zero; the change kept only if it is cheap (Liu Kang, m1268).
The physical Moto repeat waits for the phone (#4090).

## What Browser Helper already does (checked, not assumed)
javap of Android Browser Helper 2.5.0 (Kano's read, confirmed): TwaLauncher binds the Custom Tabs
service only inside its own launch, calls `warmup(0)` only when
`ChromeLegacyUtils.supportsLaunchWithoutWarmup` is false (so not on current Chrome), then
`newSession` and launches at once. It never calls `mayLaunchUrl`.

## Decisions
- **Bind and warm up first thing in `KosmosLauncherActivity.onCreate`**, before
  `super.onCreate` starts Browser Helper's launch. Skipped offline, with no Custom Tabs browser,
  and when the activity is recreated (Browser Helper then finishes without launching). Unbound in
  `onDestroy`; the connection is kept even when the bind returns false, since Android still wants
  the unbind.
- **No `mayLaunchUrl`.** Built and measured (arm "bindpreload"): 1201 ms against 1212 for bind
  only, inside one capture interval. It runs on our own session, and a speculative load belongs to
  the session that asked, while Browser Helper launches on its own. Moving the preload onto the
  launch session is rejected too: the launch URL carries a fresh handoff nonce in its fragment
  (#2854), and a page preloaded without it would open without the nonce. (Challenge-loop
  iteration 1 raised both.)
- **Rejected: a native splash** that only looks faster (out of scope per the card).
- **The harness is new**, because #4101's was never committed and its crop not recorded. It
  follows #4101's README: force-stop app and Chrome, 2 s, `am start -W`, screenshot polling until a
  fixed crop of the sign-in heading matches #4101's own reference frame. Every arm is gated on
  `tools/heavy-gate.sh`.

## Findings so far
- Session 1 (same session, arms in sequence): main 1303 ms, bind only 1212, bind + mayLaunchUrl
  1201, main again 1350.
- Control (session 2): the exact APK #4101 measured paints in 1448 ms on this harness, not 3508.
  Same harness and AVD, only the APK swapped, so the 3.5 s was #4101's harness or AVD state, not
  the app. Posted on #4090.
- Session 2 also read main at 1884 ms, with the capture interval up: load between sessions moves the
  median by more than the warmup's ~100 ms. Hence an alternating run (main and the final build,
  three rounds each, one session) decides whether the gain is real.

## Weakest part
The effect is small against emulator noise, and the emulator's browser start is not the phone's.
The harness also measures a cold process with a warm HTTP cache over the host's fast network, so it
cannot see what preconnect might do on a real phone network. What would change my mind: the
alternating run showing no consistent gap (then the change is not worth keeping), or the physical
Moto showing a large one.
