# addr-reclaim-3079 - reclaim the port from your own stale Kosmos (#3079)

## What / why
Josh, updating the live app mid-onboarding, hit installing.html's "taken" message
("Something is already running on this computer at the address Kosmos uses ... often
THEIRS, not yours"). The address was held by his OWN old build, but the launcher punted
and explained instead of taking over. Josh: "if something is already on that address we
should just kill whatever's on that address and run ours over top - it's probably us in
an old build." The nuance he flagged: on a multi-account Mac the holder can be ANOTHER
account's process, and killing that would take down someone else's session.

The per-account port formula (`16180 + 1 + uid % 3999`) is usually per-user, so the
collision is normally the user's own build - but it WRAPS at 3999, so two accounts CAN
derive the same port and collide. So ownership must be checked, not assumed.

## Fix (install/kosmos, the launcher setup.sh + the app icon both call)
At `kosmos start`, when the port is held but NOT by our answering board, resolve WHO
holds it and act by ownership:
- `port_listener_owner()` - the pid + numeric uid (via `ps -o uid=`, not lsof's name
  column) + `is_kosmos` (1 only when the listener's command names the board entry
  `server.js` under a Kosmos path) for the process whose LISTEN socket collides with the
  board's 127.0.0.1 bind (same 127.0.0.1:PORT / *:PORT filter as port_has_listener).
  Empty/return 1 when lsof can't resolve it.
- `_kosmos_reclaim_decision(luid, myuid, iskos)` - PURE. `reclaim` ONLY for our own uid
  AND a Kosmos process; every other case `keep`. This is the safety-critical decision.
- `cmd_start` - on a held-but-not-healthy port: reclaim our own stale build (SIGTERM,
  wait ~5s, escalate to SIGKILL once, clear the stale pidfile, then start over it);
  a foreign account's process gets an explicit "another account, your copy is in
  Applications" guard; an unrelated same-uid app gets the "quit that app" guard.
  lsof-gated; the existing stranger/running-pid guards stay as the lsof-unavailable fallback.
- A sourced-guard before the dispatch so the pure helpers are unit-testable.

## Safety
The only destructive action (kill) fires ONLY when uid == our uid AND the process is a
Kosmos board. A foreign uid or a same-uid non-Kosmos process is never touched. The
FOREIGN-uid control is the load-bearing test (a wrong "reclaim" there kills another
account's session), pinned as prove-a-check-can-fail. If lsof/ps cannot resolve the
owner, the decision falls to `keep` (fail safe) and the pre-existing guards handle it.

The kill is guarded by the STOP_MARKER so a launchd-supervised holder is not relaunched
mid-reclaim (cmd_board_run honors the marker before binding; the job's PathState KeepAlive
is keyed on it). Known benign window: between clearing the marker and the start branch (a
few local checks, well under the 10s ThrottleInterval) a supervised relaunch could in
principle beat our own start; it is self-healing (the start below brings up the current
build regardless, and the token bind is race-safe), so it is documented rather than locked.

## Tests (tools/test-kosmos-addr-reclaim-3079.sh, 12/12)
The decision (own+Kosmos -> reclaim; FOREIGN+Kosmos -> keep; own+non-Kosmos -> keep;
unresolved -> keep), and owner-resolution against a REAL spawned 127.0.0.1 listener
(own uid; a Kosmos-shaped command -> is_kosmos 1, a non-Kosmos one -> 0). Skips the
listener arm (does not fail) if node is unavailable. Existing kosmos CLI tests stay green;
the executed path (no-arg -> help exit 2, help verbs) is unchanged by the sourced-guard.

## Scope / out of scope
- IN: the launch-time collision that produced installing.html's taken message (the
  reported bug). `cmd_start` is the single surface the app icon and setup.sh both use.
- OUT: a HEALTHY old build during an update - it answers as Kosmos, so `healthy()`
  returns "already running" and installing.html would JUMP to it, not punt; replacing a
  healthy old build is `kosmos restart` / the update flow's job, a separate change.
  installing.html's taken message stays as the correct UI for the foreign-uid case.

## Acceptance
Single-user Mac with a stale Kosmos on the address -> new build kills it + launches, no
manual step. Multi-account Mac with another user on the address -> guard message, no kill.

## Weakest premise
`is_kosmos` keys on the command naming `server.js` under a Kosmos path. An in-place
update (same install location) matches precisely; a differently-located old build matches
via the "Kosmos" path token. A Kosmos build whose install path contains neither token
would read is_kosmos=0 and be kept (safe: we decline to kill rather than risk it). This
is the conservative direction and is stated so a reviewer can challenge it.
