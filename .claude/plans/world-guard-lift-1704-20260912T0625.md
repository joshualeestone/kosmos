## Why the guard existed, and why it can go

#2849 (`718c72b8`) added `namedWorldSpawnRefusal()`: every agent spawn on a board BOOTED
into a named Kosmos was refused with a 409. At the time an agent's OS-level launch
identity (Scheduled Task, launchd label/plist, tmux session, channel pipe) was built
from the bare name, so a named world's agent collided with, or reached, Kosmos 1's. Its
board token was also refused, because nothing handed the agent its world.

Both platforms are world-keyed now, through the ONE key derivation
`launchidentity.launchKey(name, currentWorldId())`, where the board's
`currentWorldId()` is the booted world (`worlds.applyWorldEnv` sets `KOSMOS_WORLD` at
bootstrap, worlds.js:223):

- **Windows:** #2845 (`a677a0b5`): task `Kosmos\agent-<key>` (win32job.js:55-57), argv
  field 7 carries the world (win32job.js:183-184), pipe `kosmos-agent-<key>`
  (win32channel.js:88), the boot shim applies the world before any store require
  (win32anchor.js:177). #2852 (`fd19bb6e`): a board can actually boot into a named world.
- **Mac:** #2874 (`1b3b81b0`): label and plist `com.kosmos.agent.<key>`
  (create.js:750-754), the supervisor's tmux session is the key (create.js:1975-1977),
  the plist carries `KOSMOS_WORLD` (create.js:2041), and the supervisor hands the pane
  `KOSMOS_WORLD` plus the world's store roots (create.test.js:5076).

### Gaps found, and what this slice does about them

All five are fixed in this slice (the first two in round 0, the rest in review round 1).

1. **launchd's fleet probes answered in launch KEYS, and callers asked by bare name.**
   `create.disabledJobs()` and `create.runningJobs()` list every Kosmos's jobs
   (`ava`, `ava+test`). Three callers asked `.has(name)`: the pause's switched-off
   check, and the offline row's "switched off" (server.js `switchedOff.has`) and
   "running but unseen" (server.js `runningNow.has`) sentences. In a named world each
   read Kosmos 1's `ava` as its own and never saw its own `ava+test`; after a
   keep-running switch Kosmos 1's `ava` is running, so every like-named offline agent
   in the named world wore "background job is running, but no session is visible".
   FIX (round 1, replacing round 0's label slicing in worldstarts): the two probes
   answer in THIS Kosmos's names (`launchidentity.nameInWorld`, one helper), so every
   caller is right as written and worldstarts is back to `macOff.has(name)`. The
   Windows offline row reads neither list (they are launchctl-only and fail soft to
   empty there), so it has no equivalent.
2. **The legacy `com.<name>.discord` job is Kosmos 1's, and a named Kosmos reached it.**
   `remove.jobFor`'s second candidate is unkeyed. In a named world with no keyed plist
   for the name (a half-failed create, a same-name import, a plist deleted by hand, and
   NO live session needed), Remove switched it off (`disable` + `bootout`) and Restore
   switched it back on (`enable` + `bootstrap`); a resume could start it too. FIX (round
   1): `jobFor` offers the legacy candidate ONLY in the default world
   (`launchidentity.isDefaultWorld(currentWorldId())`), the one place that decides it.
   worldstarts' `ours:false` fences at pause and resume stay, now as Kosmos-1-only
   guards against starting or disabling another tool's job.
   **Angel's lane:** this is `engine/remove.js`'s Mac arm; the PR review should point
   her at `jobFor` and `unsafeToActOn`.
3. **A default board acted on a named world's agent when handed a crafted name.**
   `remove('ava+test')` on Kosmos 1 disabled and booted out `com.kosmos.agent.ava+test`
   (and Windows' `taskName` resolved `Kosmos\agent-ava+test` the same way), because
   `create.cleanName` only trims and `unsafeToActOn` allowed `+`. FIX (round 1):
   `unsafeToActOn` refuses any name holding `launchidentity.WORLD_SEPARATOR`, with a
   sentence; remove, restart and restore all pass through it. A NEW name already cannot
   hold `+`: create validates against `NAME_RE`, and `launchidentity-1704.test.js`
   reads `NAME_RE` from source and fails if it ever admits the separator, so that one
   rule is shared rather than restated.
4. **A named Kosmos's Windows roster was empty** (found in round 1, while building the
   Windows session-end test). `win32roster` emits only sessions recorded in THIS
   world's store (`store.ROOT/win32-sessions`), under the agent's PLAIN name, and #2874's
   `status.parsePanes` key filter then dropped every one of them in a named world
   (probe: default world `["ava"]`, world `test` `[]`). With the guard lifted, a named
   Kosmos on Windows could create agents it could then never show, pause, restart,
   remove or message. FIX: `parsePanes` names a Windows row (`win32roster.isWin32Pane`)
   by its session as it stands; tmux rows keep the key filter. Also `status.js`, also
   worth Angel's eye for the Mac side (unchanged there).
5. **Not changed, noted:** `worldstarts` freezes `store.ROOT` at require
   (`RECORD_FILE`) and is missing from `worldenv.js`'s frozen-module list. That list is
   documentation only (no test enumerates it), so it is left alone here.
