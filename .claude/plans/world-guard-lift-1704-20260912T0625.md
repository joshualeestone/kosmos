## Why the guard existed, and why it can go

#2849 (`718c72b8`) added `namedWorldSpawnRefusal()`: every agent spawn on a board BOOTED
into a named Kosmos was refused with a 409. At the time an agent's OS-level launch
identity (Scheduled Task, launchd label/plist, tmux session, channel pipe) was built
from the bare name, so a named world's agent collided with, or reached, Kosmos 1's. Its
board token was also refused, because nothing handed the agent its world.

Both platforms are world-keyed now, through the ONE key derivation
`launchidentity.launchKey(name, currentWorldId())`, where the board's
`currentWorldId()` is the booted world (`worlds.applyWorldEnv` sets `KOSMOS_WORLD` at
bootstrap, worlds.js:223):

- **Windows:** #2845 (`a677a0b5`): task `Kosmos\agent-<key>` (win32job.js:55-57), argv
  field 7 carries the world (win32job.js:183-184), pipe `kosmos-agent-<key>`
  (win32channel.js:88), the boot shim applies the world before any store require
  (win32anchor.js:177). #2852 (`fd19bb6e`): a board can actually boot into a named world.
- **Mac:** #2874 (`1b3b81b0`): label and plist `com.kosmos.agent.<key>`
  (create.js:750-754), the supervisor's tmux session is the key (create.js:1975-1977),
  the plist carries `KOSMOS_WORLD` (create.js:2041), and the supervisor hands the pane
  `KOSMOS_WORLD` plus the world's store roots (create.test.js:5076).

### Gaps found, and what this slice does about them

1. **Pause's switched-off check was not world-keyed on the Mac.** `create.disabledJobs()`
   returns launch KEYS (`ava`, `ava+test`), but `worldstarts.jobIsSwitchedOff` asks
   `macOff.has(name)` with the bare name. With the skip gone, a pause from world `test`
   would read Kosmos 1's `ava` being switched off as its own (and never see its own
   `ava+test`). Fail-safe (it only mis-reports), but wrong. FIX: the check asks about
   the key of the very label the pause would disable (`job.label` minus
   `create.SERVICE_LABEL_PREFIX`), so the check and the act name one job.
2. **Resume did not refuse a job Kosmos did not write.** `remove.jobFor`'s second
   candidate is the legacy `com.<name>.discord` plist (`ours:false`). It is unkeyed and,
   in practice, belongs to Kosmos 1's legacy fleet. Pause already refuses it; resume did
   not, so a named world's resume could enable and bootstrap it. FIX: resume holds an
   `ours:false` job with a sentence, symmetric with pause. (Kept in worldstarts, not
   `jobFor`, to stay out of remove.js's Mac core, which Angel owns.)
3. **Not fixed here, reported:** `restart`/`remove` through `jobFor` can still reach the
   legacy `com.<name>.discord` job from a named board. Those routes were NEVER behind
   #2849, so this is pre-existing and not the guard's; narrow reach (a named world
   would need a live `<name>+<world>` session AND no keyed plist AND a legacy plist).
   Also, the board's offline-row "switched off" sentence (server.js:2509) compares
   `disabledJobs()` keys against bare names: display-only in a named world. And a
   DEFAULT board handed a crafted `ava+test` name resolves Test's label (the reverse
   direction), also pre-existing and outside #2849.
