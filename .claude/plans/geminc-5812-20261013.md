# geminc-5812: a Gemini agent's workspace includes its projects' folders (#5812)

## Why
Gemini refuses write_file and replace outside its workspace (validatePathAccess), so a Gemini agent on a
project whose folder is not its own changes project files only through shell commands, which the
keep-copy hook (#6047) never sees: no undo copy, no "who changed this". The call on the card (comment
6148071895): include the agent's project folders with --include-directories.

## What gemini-cli 0.61.0 does (read in its bundle, 2026-10-13; card comment 6148248793)
- an included folder joins the WORKSPACE, so writes are allowed there (isPathAllowed ->
  isPathWithinWorkspace), not only reads.
- a folder that does not exist throws from Config._initialize: startup fails.
- the flag splits values on commas and trims them.
- interactive + folder trust ON (the schema DEFAULT is on; first read it as off, corrected in review
  iteration 1): an included folder with no trust record opens a dialog that an unattended pane sits on.

## Build
- engine/geminidirs.js: foldersFor(name, {workdir}) reads projects.json raw (projects.readAll, not
  describe), keeps existing, absolute folders of projects the agent is on, drops its own folder and
  anything inside it, repeats, comma/trailing-space paths, and anything past a length cap; each
  left-out folder carries a reason (also: the home folder, a folder holding it, the disk root).
  launchFolders (Mac) writes the agent its OWN trust file (store/gemini-trust/<name>.json, exactly its
  current folders, rewritten each launch) and the pane gets GEMINI_CLI_TRUSTED_FOLDERS_PATH. The
  person's trustedFolders.json is only read (comments stripped, as gemini does): a DO_NOT_TRUST folder
  there is left out, on the Mac and on Windows alike (honourMarks).
  CLI verb `launch-args` prints `TRUST <file>` then the folders.
- bin/agent-supervisor.sh: the gemini arm appends one --include-directories per folder at launch,
  keyed by token_roster_name (SESSION can carry +world / -discord).
- engine/win32keyed.js + win32codexsup.js: every Windows gemini turn reads the folders afresh.

## Rejected
- context.includeDirectories in ~/.gemini/settings.json: one file per account, not per agent.
- reading the folder-trust setting and including nothing when it is on: it is on by default, so the
  Mac half would do nothing almost everywhere.
- recording the folders in the person's own trustedFolders.json (built first, review iteration 2):
  that trusts the folder for every agent on the account and for the person's own gemini, forever.

## Known limits
- On the Mac a project joined mid-session reaches the agent at its next launch.
- The agent's trust file replaces the person's for that pane, so a folder the person trusted in their
  own file is not trusted for the agent unless it is one of its projects (its own folder is trusted
  by --skip-trust either way).
- The agent's trust file is not removed when the agent is deleted. It is read only through the pane's
  GEMINI_CLI_TRUSTED_FOLDERS_PATH, which a launch sets only after rewriting the file, so a stale one is
  never read.
- A child folder whose name starts with two dots counts as outside its parent in trustOf, exactly as
  in gemini's own isSubpath; kept the same on purpose, so the two never disagree.
