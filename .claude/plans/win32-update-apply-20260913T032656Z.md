Branch `win32-update-apply`, off `origin/main` at `04e23b70` (S2 #2971 and the v0661 bump).
Design: the Windows in-app updater design (capability 7), sections 0, 2, 3 (B5, H1-H9), 4, 7 (S3)
and 9 ("Weakest part"). A 0.6.61 release cut is active: build and commit locally only; no push, no

## Josh's decisions this slice honours (2026-09-12)

- Agents keep running. The helper never touches a `Kosmos\agent-*` task; its only scheduler calls
  are `/End`, `/Run` and `/Query` on `Kosmos\board` (a stub scheduler in the suite records them).

- **OneDrive and Program Files: AWAITING JOSH.** Implemented as one named B0 rule,

## Measured before writing code (this box, 2026-09-13)

- A directory rename fails while ANY file inside it is open, even when the opener allowed delete
  sharing (.NET `FileShare.ReadWrite|Delete`): access denied. A Node child holding a file with
  `fs.openSync` (libuv's share modes) blocks `fs.renameSync(app, ...)` with EPERM.
- A Node child whose working directory is inside `app\engine` blocks the same rename with EPERM.
  So the helper is spawned with its cwd in the anchor folder, never inside ROOT's entries, and an
  agent or tool whose cwd is inside `app`, `bin` or `runtime` makes H3 fail (which rolls back).
- Control: the same rename with a child holding nothing succeeds.

## What this slice ships

### `engine/win32apply.js` (new): the journal, the helper, the rollback and the resume

One module, so the apply, the rollback and every resumer run the same code.

**The journal**, `<anchor>\update-journal.json`, always written with `win32swap.writeFileAtomic`:

```
format        1
token         random hex, unique per update
phase         staged | stopping | moving-out | moving-in | interpreter | pointer | starting |
              confirmed | rolling-back | stuck
finished      false until the tree is whole again (new and confirmed, or old and restored)
outcome       null | updated | rolled-back | not-started
root, work, staged, previous, anchor           absolute paths
order         the entries in move order: runtime, bin, the top-level files, app LAST
presentBefore the entries ROOT had when the journal was written (H3 moves exactly these)
stagedEntries the entries the staged tree has (H4 moves exactly these; B4 made it all of them)
from          { version, identity }   the running build
to            { version, identity, sha256 }   prepare()'s version, expectedIdentity and sha256
runtimeChanged
board         { pid | null, port }
pointer       { at, before, after }   before is the exact text read at B5
interpreter   { at, source, copy, beforeSha256, beforeSize, stamp } filled in at H5
recoverFrom   [WORK\previous-<from>\app\engine\win32apply.js, ROOT\app\engine\win32apply.js]
helper        { pid } once a helper holds the update lock
steps         [{ at, step, entry?, from?, to?, state: intent | done | failed, because? }]
because       why it is rolling back or stuck
createdAt, updatedAt
```

Each move records its intent before the rename and `done` after it. Rollback is driven by what is
on disk, with the journal as the plan: renames are atomic, B5 makes sure `previous-<from>` does not
exist, and the staged tree has every entry, so each entry is in exactly one knowable place whatever
instant a crash hits (ROOT old, previous old, ROOT new, staged new).

**The status**, `<anchor>\update-status.json` (atomic): `{ outcome, version, from, to, sentence,
because, at }`, with the sentences:
- updated: "Kosmos is now on <to>."
- rolled-back or not-started: "The update did not take. Kosmos is still on <from>."
- stuck: "The update did not take, and Kosmos could not put <from> back by itself (<because>).
  Double-click Kosmos.exe in <root> to start it again."

**The helper**, run as `<anchored node.exe> ROOT\app\engine\win32update.js --kosmos-update-apply
<journal>` with its cwd in the anchor folder:

- **H1.** Every dependency is required at module load, before any step: `win32swap`, `win32orphan`,
  `win32anchor`, `win32board` (end, runNow, status), `win32handoff` (probeBoard), `win32update`
  (the S2 lock and ENTRIES), and the built-ins (`net` for the port check included). Nothing after
  H1 calls a function that requires lazily (`win32board.pidGone` is avoided for that reason). The
  suite instruments `Module._load` from H1 to the end of an apply and of a rollback, and asserts
  no call.
- Then: read and validate the journal (phase `staged`), take the S2 update lock
  (`WORK\prepare.lock`, `win32update.takeLock`) and hold it to the end, and check again that the
  staged build is newer than ROOT's `app\package.json` and that ROOT is still `from`. Any refusal
  here finishes the journal as `not-started`, with nothing moved.
- **H2.** `win32board.end()`, then wait up to 30 s (the board restart's own figure) for the board
  pid (when known) to be gone, the port to stop answering, and the port to be bindable on
  127.0.0.1, then settle 1 s. On failure: nothing has moved; `runNow`, confirm the old identity,
  status "did not take" (or stuck if the old board does not answer).
- **H3.** `mkdir WORK\previous-<from>`, then each entry in `presentBefore`, in move order, is
  renamed there with `win32swap.renameWithRetry`, journaled intent and done.
- **H4.** Each entry in `stagedEntries`, in move order (`app` LAST), renamed from `WORK\staged`
  into ROOT, journaled intent and done.
- **H5.** Only if `runtimeChanged`: hash the anchored `node.exe`, copy it to
  `WORK\previous-<from>\anchored-node.exe` and verify the copy's sha-256 (the rollback source,
  so a restore is byte-identical whatever the anchoring sweep does to the retired file), journal
  it, then `win32swap.replaceInterpreter(ROOT\runtime\node.exe, <anchor>\node.exe)`.
- **H6.** Journal `pointer.before`, then `writeFileAtomic(engine-path, ROOT\app\engine)`.
- **H7.** `runNow`, then poll `probeBoard(port)` every 500 ms for the header to equal
  `to.identity`, 20 s per run, up to 3 runs (60 s). Task status is never read as proof. Confirmed:
  phase `confirmed`.
- **H8.** Any failure from H2 on (a throw, a rename past its retries, an unconfirmed identity) runs
  the rollback below in helper mode.
- **H9.** Status `updated`, journal finished `updated`, then best effort: delete `WORK\staged`,
  `WORK\download.part` and the anchored-node copy, and every `previous-*` except
  `previous-<from>`. The interpreter's retired file is left to the next anchoring sweep.
- Release the lock. A transcript goes to `WORK\update-apply.log` (the helper's stdio is ignored).

**The rollback** (`rollBack`), one routine for H8 and for every resumer, reversing the journal in
exact reverse order and idempotent (a second pass after a crash does the rest):
1. helper mode only: stop the board (as H2, without aborting);
2. H6: if `engine-path` is not `pointer.before`, write `before` back atomically;
3. H5: if `interpreter.beforeSha256` is recorded and the anchored `node.exe` does not hash to it,
   `replaceInterpreter` from the first of [the verified copy, the retired original
   `node.exe.retired-<stamp>-<helper pid>`, the old runtime's `node.exe`] that hashes to it
   (the last only as a fallback, noted in the status), and remove this helper's staged side file;
4. H4 reversed (`app` first): an entry in `stagedEntries` that is in ROOT and not in staged goes
   back to staged;
5. H3 reversed: an entry in `presentBefore` that is in previous and not in ROOT goes back;
6. verify: every `presentBefore` entry is in ROOT and not in previous, and no other entry is in
   ROOT. Each rename gets `renameWithRetry`; a failed pass waits 2 s and the whole pass runs
   again, up to 3 passes. Still not whole: status stuck, phase `stuck`, journal NOT finished (so
   the next resumer tries again);
7. whole: remove the empty previous folder and the staged tree, journal finished `rolled-back`;
8. helper mode only: `runNow` and confirm `from.identity` the same way as H7. Not confirmed: the
   tree is whole (journal finished) but the status is stuck with the Kosmos.exe fix.

### Who resumes, and when (crash safety)

A crash can leave ROOT without `app` (between H3's move of `app` and H4's), so no resumer may live
only in ROOT\app. Three resumers, all running `win32apply.resume(journal, mode)`, all taking the
update lock first (a live helper holds it, so a resumer never races the helper):

1. **The board's logon shim, before it loads the board** (`board-boot.js`, written by
   `win32board.BOOT_JS`). At every task start: if `update-journal.json` sits beside it and is not
   finished, it requires the first file in `journal.recoverFrom` that exists (the OLD build's
   `win32apply.js`: after H3 moved `app` it is in `previous-<from>`, before that it is in ROOT) and
   calls `recoverAtBoot`. Boot mode: lock held, nothing; phase `staged` or `stopping`, finish
   `not-started`; phase `confirmed`, finish forward (H9); any other phase, roll back without
   stopping or starting a board. Then the shim goes on to read the pointer and boot whatever app
   ROOT now has. Any throw is written to stderr and the boot goes on. This covers a power loss or
   blue screen: the next logon, or any `/Run`.
   ⚠️ This is the one change to a production path: BOOT_JS is rewritten at every board boot, so it
   reaches the live anchor the first time a build with it boots. It does nothing without a
   journal (one `existsSync`).
2. **The next update (B0 and B5).** `prepare()`'s B0 refuses while a journal is unfinished, in
   words. `begin()` (B5) additionally spawns the helper in resume mode (`--kosmos-update-recover
   <journal>`): helper mode, the same rules as boot mode but it stops the board before rolling
   back and starts and confirms the old one after. This covers a helper killed while the new
   board keeps running (no logon ever happens then). An unreadable journal refuses, naming the
   file, and is never deleted automatically.
3. **The helper itself**: H8.

### `engine/win32update.js` (changed)

- **B0 additions** (`preconditionRefusal`), each a sentence:
  - the unusual-location rule (`UNUSUAL_LOCATION_POLICY`, PENDING JOSH): ROOT inside a OneDrive
    folder (`OneDrive`, `OneDriveConsumer`, `OneDriveCommercial`) or Program Files
    (`ProgramFiles`, `ProgramFiles(x86)`, `ProgramW6432`), spelled or resolved;
  - no unfinished (or unreadable) update journal, checked before the lock and again once the lock
    is held;
  - after the live-execution gate, so a process that never armed it never queries the scheduler:
    the board was started by its task (`win32board.startedByTask` on the launch environment), and
    `Kosmos\board` is registered and enabled. Seam: `boardTask`.
- **B5**, `begin(opts)`: `prepare()` with a hook that runs while the lock is still held: clear a
  stale `previous-<from>`, write the journal (phase `staged`) atomically. Then spawn the helper
  detached with the anchored `node.exe`, cwd the anchor folder, `stdio: 'ignore'`, `windowsHide`,
  an `error` listener and `unref` (the `win32board.restart` pattern). A spawn that fails finishes
  the journal `not-started`. Refuses up front when ROOT's own build has no `win32apply.js`.
- **The dispatch**: `--kosmos-update-apply <journal>` and `--kosmos-update-recover <journal>`.
- **The live-check CLI**: `node engine/win32update.js --apply --root <folder> [--base <url>]
  [--channel prod|staging] [--world <id>] [--board-pid <pid>] [--port <n>] [--wait] [--yes]`.
  A dry run (exit 2, nothing written) without `--yes`. With it, the CLI stands in for
  `allowLiveExecution()` as `--prepare` does, derives "started by its task" as the task running AND
  the port answering with ROOT's own identity, calls `begin`, and with `--wait` polls the status.

### Is N -> N+1 on a separate scratch install possible without the real engine-path or tasks?

**Partly, and here is the line.** Everything the swap does can run on a scratch install: its own
ROOT, its own anchor, `engine-path`, `node.exe`, APPDATA, LOCALAPPDATA and port, a real board
process from the scratch build, the real `prepare()`, the real helper code loaded from the scratch
old build, real renames, a real `replaceInterpreter`, and confirmation by the identity header.
**The Scheduled Task cannot be separated.** `Kosmos\board` is a constant, so a detached helper
started by `--apply --yes` against a scratch ROOT would `/End` and `/Run` the LIVE board. And a
scratch board booted the normal way re-registers `Kosmos\board` (`ensureInstalled` -> `/Create /F`)
against the scratch anchor, which would hijack the live task. So the scratch driver runs the helper
in its own process with a scratch scheduler that starts and ends the scratch board as a child, and
the scratch board runs with the schtasks guard preloaded. What the scratch checks therefore do NOT
cover: the detached spawn, `/End` through the headless conhost and the parent watch, IgnoreNew, the
logon shim run by Task Scheduler, and agents (none can exist without `Kosmos\agent-*` tasks). Those
are the real-install checks, R1-R5, and each needs Josh's go.

## Verification (build session, 2026-09-13; nothing pushed)

### Found while building

- **H6 rewrites the same path.** `engine-path` already names `ROOT\app\engine` (B0 requires it), and
  the new build lives at that same path, so H6's write is a re-affirmation. A pointer spelled
  differently (a trailing CRLF, a different case or short name that B0 accepts) does change bytes,
  so the rollback restores the exact bytes recorded at B5. The first suite run showed no test
  exercised the reversal (the bytes never differed); every sandbox pointer now carries a CRLF, so
  every rollback and crash case must put those exact bytes back.
- **The helper's cwd, and any cwd inside `app`, blocks the swap** (measured above), which is why
  B5 starts the helper in the anchor folder and why an agent or tool sitting in `app`, `bin` or
  `runtime` turns H3 into a clean rollback.
