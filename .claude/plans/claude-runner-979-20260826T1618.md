# claude-runner-979: Claude Code becomes an installable provider in the engine (kosmos#979, Claude half, branch A of two)

## Why

Josh's ruling (2026-08-26 10:32 CT, recorded on #979): Claude Code is a provider
like the others, not part of the platform. "Not everybody is going to have Claude
Code... we're not forcing people to have Claude Code as part of the installer."
Second-order consequence (Splinter, pinned on the card): today a failed Claude Code
download in setup preflight calls die() and kills the ENTIRE install; as a provider,
that failure must happen inside the Connect step and leave Kosmos working.

## The two-branch split, and why this branch is only A

- **Branch A (this one)**: the ENGINE knows Claude as a provider -- resolves it,
  reports it, LINKS one already on the Mac, and refuses in words when there is
  none -- with the same observable job shape OpenAI got in #987. Nothing about the
  installer changes; setup.sh still pre-installs Claude today.
  ⚠️ **It does NOT download.** The original wording of this bullet said "can
  install Claude Code in-flow", which is what two wrong implementations tried to
  deliver. Downloading is #996; see footnote two.
- **Branch B (later, gated)**: setup.sh stops pre-installing Claude. Deliberately
  held until the in-flow path exists END TO END (this branch, plus Mona Lisa's
  screens): removing the pre-install first would hand a bare-Mac Claude user the
  exact dead-end class #987 just fixed for OpenAI. Josh is walking installs today;
  the order of these two branches is the difference between his walkthrough
  passing and breaking.

## What (all engine-side)

1. **A second manifest KIND, `vendor-verified`.** Claude Code is not a pinned
   tarball: its version and per-platform SHA256 are discovered at run time from the
   vendor's own manifest, which `engine/connect.js` has been reading and verifying
   since 2026-08-12. So `MANIFEST.claude` carries no `url` and no `integrity` pin,
   and says why; `pinnedVersion` and `downloadBytes` are null, spelled as null so
   the absence survives `JSON.stringify`.
2. **`install('claude')` LINKS, and refuses in words when it cannot.** A Claude Code
   already on this Mac but not at the canonical path gets a symlink (phase
   `linking`), which is setup.sh's near-miss handling carried in-flow. With none
   found, the job FAILS with a sentence a person can act on. It does not download.
   ⭐ **Downloading is #996 and is deliberately not on this branch** — see footnote
   two. A failure is a JOB ANSWER: nothing exits, nothing kills an install, Kosmos
   keeps running. That is the `die()`-path replacement the card demands.
3. **`resolveBin('claude')`**: env `AGENT_WORKFORCE_CLAUDE_BIN` authoritative, then
   the canonical `~/.local/bin/claude`, both keyed on one `homeDir()`.
4. **Present means RUNNABLE** (`accessSync(X_OK)` on a plain file), for BOTH
   providers — the #133 folder-sails-through trap, closed on every rung.
5. **One definition of where Claude lives.** `create.js`, `connect.js` and
   `subscription.js` each held their own copy; all three now call the resolver.
   `connect.js`'s install child is passed the matching `HOME` so where we LOOK and
   where the vendor WRITES cannot disagree.
6. **Routes**: `/api/runners` and the install POST already iterate the manifest, so
   Claude appears with `present`/`job` for free; verified by test, not assumption.

## Out of scope

- setup.sh changes (branch B, still gated: it needs #996 plus the screens, or a

## ⚠️ Challenge-loop iteration 2: the mechanism was WRONG and was replaced (2026-08-26 13:40-14:0x CT)

A blind reviewer found the defect this plan's own item 1 encoded. Recording it here
rather than quietly rewriting the section above, because the plan was confidently
wrong in a way worth being able to find again.

**What item 1 claimed:** Claude installs through Anthropic's installer script, and
"there is no vendor-published checksum for it, and pinning is not possible at this
layer."

**What is true:** `engine/connect.js` has installed Claude Code since 2026-08-12 by
reading a per-platform SHA256 out of `<base>/<version>/manifest.json`, refusing a
binary whose hash does not match, and refusing any https->http redirect on the way
(`redirectDowngrades`). So the repo already held a verified install path for the
exact product, and branch A had added a second, strictly WEAKER one beside it:
`curl -fsSL <url> >script && sh script`, with no integrity check of any kind, plus
`curl` following redirects with no protocol floor.

**Why the wrong claim survived to a commit:** every guard I wrote in iteration 1 was
about the SHAPE of the script call (positional args, curl-then-sh sequencing, the
log). All real, all correct, and all of them hardening a mechanism that should not
have existed. Hardening the wrong mechanism reads exactly like diligence.

**The replacement:** kind `vendor-installer` -> `vendor-verified`. `installVendor`
now delegates to `connect.download()` and then runs the downloaded binary's own
`install`. Deleted outright: `installUrl`, `installUrlEnv`
(`AGENT_WORKFORCE_CLAUDE_INSTALL_URL`), the whole `runInstaller` curl/sh seam, and
the install-log plumbing that existed only to capture that script's output.

**What this closed at the same time**, all findings from the same pass:
- the executed-bytes env repoint (`installUrlEnv` no longer exists)
- redirect downgrade (connect.js already refuses it)
- two independent Claude installers in one process (now one download mechanism)
- bare PATH-resolved `curl`/`sh` (no shell at all now)
- byte counts became REAL rather than null, so the screen gets a true progress bar

**Other findings fixed in the same iteration:**
- `isRunnable` asks `accessSync(X_OK)` instead of `mode & 0o111` (a root-owned
  0o700 binary read runnable and failed at launch)
- `homeDir()`: one home for `resolveBin`'s canonical rung AND `findElsewhere`, which
  keyed on the real machine while the resolver was sandboxed
- the link step no longer `rmSync(force)`s the canonical path. It replaces a symlink
  (ours) and REFUSES anything else BY NAME, including the directory case that used
  to surface a raw `ERR_FS_EISDIR` to a person
- post-install gate is `isRunnable`, not `existsSync`
- `pinnedVersion: m.version || null`, so the honest absence survives `JSON.stringify`
- `create.binPaths().claudeBin` now has a test (every create.js suite passes
  `claudeBin` explicitly, so the changed default arm was covered by nothing)
- `engine/connect.js` and `engine/subscription.js` each held a THIRD and FOURTH copy
  of `claudeBinPath()` that disagreed with the resolver about the AGENT_WORKFORCE_HOME
  rung; both now call the resolver
- `tools/browser-checks.sh` sandbox 4 gains `AGENT_WORKFORCE_CLAUDE_BIN`: it set
  AGENT_WORKFORCE_HOME but the old claudeBin ignored it, so the sandbox had been
  reaching the operator's real Claude. Sealed with a fake, not by reaching out again.

**Live proof note, updated:** the no-network proof of the real installer line is gone
with the line it proved. The verified path's network behaviour is connect.js's, which
owns its own tests for the checksum and redirect refusals; this branch seams the
delegation and does not re-test connect.js.
