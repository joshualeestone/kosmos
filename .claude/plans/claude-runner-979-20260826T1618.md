# claude-runner-979: Claude Code becomes an installable provider in the engine (kosmos#979, Claude half, branch A of two)

## Why

Josh's ruling (2026-08-26 10:32 CT, recorded on #979): Claude Code is a provider
like the others, not part of the platform. "Not everybody is going to have Claude
Code... we're not forcing people to have Claude Code as part of the installer."
Second-order consequence (Splinter, pinned on the card): today a failed Claude Code
download in setup preflight calls die() and kills the ENTIRE install; as a provider,
that failure must happen inside the Connect step and leave Kosmos working.

## The two-branch split, and why this branch is only A

- **Branch A (this one)**: the ENGINE can install Claude Code in-flow, with the
  same observable job shape OpenAI got in #987. Nothing about the installer
  changes; setup.sh still pre-installs Claude today.
- **Branch B (later, gated)**: setup.sh stops pre-installing Claude. Deliberately
  held until the in-flow path exists END TO END (this branch, plus Mona Lisa's
  screens): removing the pre-install first would hand a bare-Mac Claude user the
  exact dead-end class #987 just fixed for OpenAI. Josh is walking installs today;
  the order of these two branches is the difference between his walkthrough
  passing and breaking.

## What (all engine-side)

1. **A second manifest KIND.** OpenAI's entry is a pinned tarball; Claude installs
   through Anthropic's own installer script (`https://claude.ai/install.sh`,
   overridable via AGENT_WORKFORCE_CLAUDE_INSTALL_URL, exactly the mechanism and
   env contract setup.sh uses today), landing at `~/.local/bin/claude`. So
   MANIFEST.claude is `kind: 'vendor-installer'` with `installUrl`, `binName`,
   and no integrity pin, and the honesty cost is stated in the manifest comment:
   the vendor script installs the vendor's LATEST; there is no vendor-published
   checksum for it, and pinning is not possible at this layer. The tarball path
   keeps its pin untouched.
2. **install('claude')**: phases `installing` (no byte counts; the vendor script
   reports none, so the job says null rather than inventing numbers) ->
   `proving` (`claude --version` must answer, same probe setup.sh does) ->
   `installed | failed {because}`. The vendor script's output goes to a log file
   whose path rides in the job on failure (setup.sh's own convention: the log
   must say what a run actually installed). A FAILURE IS A JOB ANSWER: nothing
   dies, Kosmos keeps running, the screen shows `because` -- the die()-path
   replacement the card demands.
3. **The found-elsewhere link step**: when `claude` exists on PATH but not at
   the canonical `~/.local/bin/claude`, install links it instead of downloading
   (announced in the job as its own phase `linking`), mirroring setup.sh's
   near-miss handling ("nothing is installed; a link is named as a link").
4. **resolveBin('claude')**: env AGENT_WORKFORCE_CLAUDE_BIN authoritative, then
   the canonical `~/.local/bin/claude`. create.js's claudeBin moves onto the
   resolver (the same consolidation #987 did for codex, closing the same
   drift-risk pair).
5. **Routes**: `/api/runners` and the install POST already iterate the manifest,
   so Claude appears with `present`/`job` for free once the entry exists; verify
   by test, not assumption.

## Challenge-loop iteration 1 additions (2026-08-26 11:20-11:32 CT)

Four WARNINGs, one CONVENTION, three NITs; all addressed except one accepted cost:

1. Shell-injection surface closed: the installer line passes URL, log, and script
   paths as POSITIONAL sh args (inert expansion, the same mechanism setup.sh's
   "$var" gives), never template interpolation into sh -c.
2. curl-then-sh SEQUENCED instead of piped: a pipeline without pipefail reported a
   curl failure as sh's success over an empty script and lost curl's stderr. Now a
   network failure exits nonzero with curl's own words in the log. Proven by a
   no-seam test driving the REAL installer line against an unresolvable domain.
3. findElsewhere probes the known Homebrew / usr-local / npm-global homes
   explicitly (a launchd board's stock PATH hides them from `which`), so the
   linking phase actually fires where setup.sh's login-shell `command -v` would.
4. Present now means RUNNABLE (isRunnable: plain file + exec bit, symlinks
   followed) across every rung of both providers -- the #133 folder-sails-through
   trap. Tested with a directory and a stripped file at the canonical path.
5. The status/job contract comment documents both kinds' phases and fields;
   status() exposes `kind` so screens branch on it instead of inferring from
   nulls (asserted for both providers in the route test).
6. Vendor install logs and script temps get the same age-gated, provider-prefixed
   sweep as tarball staging.
7. ACCEPTED, stated in the comment: the 10-minute ceiling kills the sh wrapper; a
   child mid-stage can briefly outlive it and exits with its own stage. A
   process-group kill is machinery this path does not earn.
