# Plan: win32-swap-atomic -- the rename-swap helpers get their own module, and the engine-path pointer is written atomically

Groundwork for the Windows updater's slice S3 (the design's §4 "new modules:
`engine/win32swap.js`" and §0 finding 6), and a real bug fix on its own.

## The defect

`engine/win32anchor.js` `ensureAnchored` writes `runtime\engine-path` with a plain
`fs.writeFileSync(pointerAt, String(engineDir), 'utf8')` (main, line 377). That
call truncates the file when it opens it, then writes. If it is interrupted in
between (power loss, a crash, the process killed, the disk full), the pointer
is left empty or partial. Two concurrent anchorings (the board and a CLI
create) can also interleave their truncate and write.

Both boot shims read the pointer the same way, `readFileSync(pointer).trim()`:
- `win32anchor.BOOT_JS` (supervisor-boot.js, every agent);
- `win32board.BOOT_JS` (board-boot.js, the board).

An empty pointer makes both exit 3 with "no engine pointer". A partial one names
a directory that does not exist, so they exit 3 with "... is gone". Either way the
board and every agent fail to start at the next logon, and nothing reports it.

## The change

1. **New `engine/win32swap.js`, using Node built-ins only (`node:fs`, `node:path`).**
   Moved verbatim from `win32anchor.js` (main, lines 185-319): `renameWithRetry`,
   `pauseSync`, `replaceInterpreter` (the node.exe rename-aside, #2825),
   `retireLeftoverInterpreters`, and their constants (`STAGED_INFIX`,
   `RETIRED_INFIX`, `RENAME_ATTEMPTS`, `RENAME_RETRY_DELAY_MS`,
   `TRANSIENT_RENAME_CODES`, `SWAP_RENAMES_AT_WORST`, `RETIRED_SWEEP_MIN_AGE_MS`,
   `STAGED_SWEEP_MIN_AGE_MS`). There is one copy of each, so win32anchor requires
   them back (convention 5).
   - **One signature change, internal only:** `retireLeftoverInterpreters(dir, clock)`
     becomes `retireLeftoverInterpreters(nodeAt, clock)`. It needed `NODE_NAME` to
     build the side-file prefix. That name belongs to the anchor's file layout, and
     S3 will swap the bundle's own `runtime\node.exe` too. It now derives the
     directory and the prefix from the interpreter path, the same path
     `replaceInterpreter` derives the side names from. So the two agree by
     construction, and win32swap needs no copy of `NODE_NAME`. win32anchor was the
     only caller.
   - **Exports, exactly what S3 needs:** `renameWithRetry`, `replaceInterpreter`
     (it was internal, and is now exported from win32swap only),
     `retireLeftoverInterpreters`, `writeFileAtomic`. Plus the three constants
     win32anchor already re-exports (`STAGED_INFIX`, `RETIRED_INFIX`,
     `RETIRED_SWEEP_MIN_AGE_MS`), so its surface is sourced from one place.
   - Nothing runs at require. The module only declares constants and functions.

2. **New `writeFileAtomic(target, data)` in win32swap:**
   1. open a temp file in the same directory, `<target>.writing-<time>-<pid>-<seq>`,
      with `wx`, so it never reuses or follows anything already at that name;
   2. write every byte in a loop that checks for short writes;
   3. `fsyncSync` it, so the bytes are on disk before the name moves;
   4. close it, then `renameWithRetry(temp, target)`. The rename retries through the
      transient EPERM/EBUSY/EACCES that antivirus or the indexer causes.
   - On any failure it unlinks the temp it created, then rethrows. An unlink failure
     other than ENOENT is added to the message rather than swallowed.
   - `data` is a string (written as UTF-8) or a Buffer. Anything else is a
     `TypeError`, thrown before any file is touched (review round 2: coercing a
     `Uint8Array` wrote the text "104,105"). No caller passes anything else.

3. **`ensureAnchored` writes the pointer with `writeFileAtomic`.** Nothing else in
   `ensureAnchored` changes.

4. **Review round 1: the boot shims are written atomically too.** The first cut
   left them as a follow-up, and the coordinator asked for them in this branch.
   A torn shim is a syntax error at logon, so it stops the board or every agent
   exactly as a torn pointer does.
   - `win32anchor.ensureAnchored` writes `supervisor-boot.js` with `writeFileAtomic`.
   - `win32board.install` writes `board-boot.js` with `writeFileAtomic`.

   Every write into the anchor directory, audited by grepping `anchor.dir`,
   `anchorDir(` and `anchorDirFor(` across `engine/`:

   | File | Writer | Who reads it | Now |
   |---|---|---|---|
   | `engine-path` | win32anchor | every boot shim | atomic |
   | `supervisor-boot.js` | win32anchor | every agent task at logon | atomic |
   | `board-boot.js` | win32board `install` | the board task at logon | atomic |
   | `board-task-claimed` | win32board `claim` | `claimed()`, by `existsSync` only | left |
   | `board-restart.log` | win32board restart helper | a person, afterwards | left |

   - **The claim file:** its content is never read, only whether it exists, and a
     torn write still exists. So a torn claim reads exactly as a whole one.
   - **The restart log:** a transcript for a person. It is rewritten on every line
     the helper says, and no boot or task reads it. Flushing and renaming per line
     would slow the restart it records, and would buy nothing for a reader that
     can cope with a short log.
   - **The task XML** is written to `os.tmpdir()`, not the anchor, and deleted once
     `schtasks` has consumed it.

   The branch was rebased onto origin/main `89418102` before this round. Main had
   changed none of the win32 files, and there were no conflicts.

## How atomicity is guaranteed

- A reader only ever opens `engine-path`, never the temp. Until the rename, that name
  holds the old bytes, untouched: nothing opens it for writing any more. After the
  rename it holds the complete, flushed new bytes. The rename is a single
  replace-existing operation on one volume (NTFS `MoveFileEx`/POSIX rename). The temp
  is in the same directory, so the rename can never be a cross-device copy.
- **A handle open on the target blocks the replace, on Windows.** The first cut of
  this plan said Node's `FILE_SHARE_DELETE` let a reading shim coexist with the
  replace. Review round 2 measured that as false. The numbers below are from this
  box (Win11 26100, Node 24.19), with the reviewer's probes rerun against this
  branch. A rename over a file fails with EPERM while ANY process has it open, a
  plain Node reader included. So a boot shim reading `engine-path` at that instant
  makes the rename fail, and `renameWithRetry` retries it (10 tries, 100 ms apart,
  about 1 s in all):
  - held for 300 ms: the write lands after about 330 ms;
  - held for 2.5 s: EPERM after about 1 s, the old bytes whole, no temp left;
  - four readers in tight loops against back-to-back writes: 19 of 26 renames
    failed at first and the slowest write took 932 ms. In the reviewer's run, 2 of
    4 writes gave up. Plain `writeFileSync` against the same readers never failed,
    but every reader saw 443 to 544 empty reads.
  - **The trade, chosen:** torn reads are exchanged for a write that fails closed.
    Under a handle held past the ~1 s budget, `writeFileAtomic` throws EPERM with
    the target whole and no temp left. `ensureAnchored` then returns
    `{ ok:false, because }`, and the sentence names both paths, the temp and the
    pointer, because Node's rename message carries both.
    - The budget is not raised: the pause is synchronous, and a longer one stalls
      every board request (see the note on `RENAME_RETRY_DELAY_MS`).
    - There is no non-atomic fallback, because that fallback is the torn write.
  - **S3 must account for it.** An updater that rewrites `engine-path` or a shim
    while the board or agents are starting can get `ok:false`. It must retry later
    or report, and never fall back to a plain write.
  - **A read-only target, or a directory at the target,** also fails the rename
    with EPERM, which is treated as transient. So it spends the whole ~1 s budget
    before it reports (measured: 972 ms and 983 ms). No code change: neither
    happens in the anchor, and telling them apart from a held handle would need a
    `stat` on every retry.
- A crash before the rename leaves the old pointer complete. On a first-ever
  anchoring there is no pointer yet, which is the same state as before anchoring
  ran, and no task is registered until `ensureAnchored` returns ok.
- The directory is not fsynced. Node cannot open a directory for fsync on Windows,
  and NTFS journals the rename's metadata. On a power loss at the exact rename, the
  outcome is the old pointer or the new one, never a torn one.

## A leftover temp is harmless (not swept), and why

A crash between the temp write and the rename leaves one
`engine-path.writing-<time>-<pid>-<seq>` of a few hundred bytes. It is harmless:
- no reader opens it;
- its name is unique (time, pid and a per-process sequence), so a later write never
  collides with it (`wx` into a fixed name would have wedged every later write on
  EEXIST, the trap `securewrite.js` documents from #1776);
- `retireLeftoverInterpreters` only matches `node.exe.staged-`/`.retired-`, so it
  never touches it.

A sweep would be a new delete path in the anchor directory. It would also need its
own in-flight age margin to avoid taking a concurrent writer's temp, which is the
race `securewrite.js` spent #1793 on. That is not worth it for a file that needs a
crash inside a microsecond window to exist and costs a few hundred bytes. S3 can
add one if its journal writes need it.

## Reuse check: is there already a helper that fits?

- **`engine/securewrite.js` `writeSecret`: not reused.**
  - Its in-place fallback, after three failed atomic attempts, opens the target with
    `O_TRUNC` and writes it. That is the exact torn write this branch removes. On
    Windows, a sharing violation on the target (the common failure) would send it
    there, because its rename has no retry.
  - It does not fsync.
  - Everything else it carries is shaped for a secret: 0600 mode semantics, symlink
    refusal, and a pid/thread-keyed orphan reaper.
  - Making it fit would change a security module's behaviour. That is out of scope
    here.
- **Every other temp-and-rename in `engine/` is inline.** Examples: `autoupdate.js:68`,
  `chat.js:2035`, `win32sessions.js:128`, `win32streamstate.js:121`. There is no
  shared helper among them to reuse, and no rename-with-retry anywhere except
  win32anchor's.
- So `writeFileAtomic` is new, and it sits beside `renameWithRetry`, which it must
  use. Consolidating the inline writers onto it is possible later, and is not this
  branch.

## Live execution (convention 3)

No new side effect is reachable at require, and no new caller is added. The helpers
are pure file operations. `ensureAnchored`'s existing callers (`win32job`,
`win32board`) are unchanged and keep their existing gates.

## Tests (each red when its change is reverted)

New `engine/win32swap.test.js`, sandboxed temp directories only. It never touches
the real anchor.

- **The crash arm.** A child process runs `ensureAnchored` against a sandboxed
  anchor. Its `fs.renameSync` exits the process when asked to move the pointer's
  temp into place: a real death between the flushed temp write and the rename.
  - It asserts the child really died there, and that the pointer still holds the
    OLD engine path, complete.
  - It asserts `readPointer` answers OLD, and that the temp holds the NEW path in
    full.
  - Then a normal `ensureAnchored` succeeds, and the pointer is NEW (the leftover is
    harmless).
  - Red if line 377 goes back to `writeFileSync`.
- **A torn write lands in the temp, never the target.** A child's `fs.writeSync`
  writes half the bytes and exits. The target is still the old content.
- **Flushed before it is renamed.** `fsyncSync` on the temp's fd precedes the
  rename.
- **Review round 2:**
  - **A short write is carried on:** a stubbed `fs.writeSync` takes half the bytes
    on its first call, and the target still ends complete.
  - **`wx`:** the one `openSync` is the temp's, and its flag is `wx`.
  - **Type guard:** a `Uint8Array`, a number, `undefined`, `null` and a plain
    object each throw `TypeError`, and nothing is written.
  - **Held by another process (Windows only; skipped elsewhere, where the rename
    succeeds under a reader):**
    - A child process holds the target open. Released within the budget, the write
      lands with the new bytes, and the first rename really was refused.
    - Held until killed: `writeFileAtomic` throws EPERM, the old bytes are whole,
      and no `.writing-` temp is left. `ensureAnchored` under the same hold returns
      `ok:false`, naming the temp and the pointer.
    - The child is killed in a `finally`, and it exits by itself after 30 s in any
      case.
- **A failed rename removes the temp** and leaves the target intact.
- **renameWithRetry, stubbed.**
  - EBUSY and EPERM are retried to success.
  - EIO throws at once.
  - A lock that never clears gives up and rethrows.
  - `writeFileAtomic` retries an EPERM on its rename.
- **Direct arms for `replaceInterpreter` and `retireLeftoverInterpreters`.** The
  sweep leaves a pointer temp and another executable's side files alone.
- **Exports.** win32swap's export set is exact. win32anchor's export set is
  unchanged, and its constants are win32swap's (the same values). win32anchor
  defines none of the moved functions. win32swap requires only `node:` built-ins,
  and requiring it touches no file.

Unchanged and run: `engine/win32anchor.test.js`, `engine/win32anchor.world-1704.test.js`,
