## Findings

- [WARNING] docs/browser-checks/render-chatbox-phone-4108.js:305-354 (the forced case). The squeeze is 6px of a card well over 100px tall, and the gate runs it on every PR that touches the gated surfaces. The case fails in one direction only: if the card gets shorter by 6px or more, `r.top < need` stops holding, the tour asks for nothing and BOTH arms go red. The most likely trigger is not a runner change but a copy edit: shortening the project tip's Conversation step body by one wrapped line (about 20px) turns this gate red on a copy-only PR, with no make-room regression. The re-tune wording tells the reader what happened but still blocks the PR. Growth in the other direction is harmless (scrollY 677 leaves plenty of room to scroll). Fix: make the squeeze deep and deterministic instead of incidental, for example give `#pj-room` an inline min-height in the setup evaluate (with the fit already off) so its top lands a known distance inside the card's need, aim for a shortfall of roughly 40 to 80px, and keep the MEASURE line. The make-room precondition `window.scrollY >= need - r.top` still has to hold, so assert the measured shortfall sits inside a band (for example 20 to 200px) as its own setup check, so drift is reported as a setup failure rather than as two product reds.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:323-329 (setup). `off` is true when `--pj-room-fit` reads empty after the call, which is also true if the room had never been fitted in the first place (for example loadRoom not yet run when `open` returned). Then the setup check proves nothing about the override taking. Today the fit is set by loadRoom before this point, so it passes for the right reason, but nothing asserts that. Fix: read the property before the override and require it non-empty, and also return `PJ_ROOM_PHONE.matches === false` after `defineProperty`, so the setup shows a fit that was on and is now off.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:139 and 336. The recorded value is `r.top - need`, which is negative, so the MEASURE line prints `asked to scroll [-6]px ... (the card's shortfall)`. A shortfall reads as a positive size; a reader comparing it with the comment's "6px" has to reconcile the sign. Also `Number(a[1]) || 0` would silently record 0 if a future caller used `window.scrollBy({ top })`, printing "0px" as though the tour asked for nothing. Fix: record `Math.abs`, or label it "scrolled by -6px (shortfall 6px)"; and record `a[0] && typeof a[0] === 'object' ? a[0].top : a[1]` so the options form is measured too.

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:341 (message text). The "tour asks to make room" line carries "(if the control is red too: ...)" in both arms, including inside the control's own tag, where "the control" refers to itself. Fix: in the control arm say "(if the forced arm is red too: ...)", or word it once for both as "if both forced arms are red here".

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:333-334. "the forced layout held through the walk" can only fail if some code writes `--pj-room-fit` while `matches` is false; no code path does today, and a future fitter that writes a different property (an inline max-height, a dvh rule) would pass it while undoing the squeeze. It is a reasonable tripwire, but the comment presents it as asserting "the layout stayed unfitted". Fix: also record the room's height before and after the walk and require it unchanged, which catches any fitter, not just this property.
