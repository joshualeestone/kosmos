# #5467: a queued-heavy waiter must not look like the job it is waiting to run

Handed over by Splinter 04:15 2026-10-07. Baron measured the 0.7.27 deadlock (his per-cut wrapper's
`pgrep -f "tools/browser-checks\.sh"` matched a queued-heavy waiter) and recommended option 1.

## Finished looks like
While a tools/queued-heavy.sh run waits for its turn, no `pgrep -f <its command>` finds the waiter process itself (its
parent shell is #5470); once its turn
comes, the command runs as its own process and IS found. Pinned by tools/test-queued-heavy-4977.sh with both controls,
and a control copy without the change showing the waiter matched (so the arm can fail).

## Call
Option 1 (Baron's): the wrapper writes its arguments, NUL-separated, to a private file (umask 077, mktemp under
TMPDIR) and execs itself with only `--queued-args <file>`; it reads them back, deletes the file and carries on. Same
pid throughout (exec), so waiter markers and held pids stay right; stdin is kept (exec).
Rejected: option 2 (a shared `kosmos_running` helper with an anchored match) alone. It fixes only the checks someone
remembers to rewrite; the hazard is every hand-written `pgrep -f X`, most of them in per-cut wrappers outside the repo.
The repo's own guard already anchors (tools/lib/cut-guard.sh), so a helper adds nothing there.

## Not covered (stated, not fixed)
- The CALLER's command line: a `bash -c "... queued-heavy.sh ... browser-checks.sh"` shell (the Claude Code Bash tool's)
  still carries the command, and Baron's pgrep matched that parent too (45360). queued-heavy cannot change its parent's
  argv. Such checks must anchor to the start of the line (`^bash tools/browser-checks\.sh`), as cut-guard.sh does.
  So #5467 alone does not stop a hand-written unanchored `pgrep -f` from deadlocking a release on a queued run (review 7):
  #5470 tracks one anchored helper for every such check. cut-guard.sh's own checks were never fooled.
- The installed copy agents run (~/.cache/claude-handoffs/queued-heavy.sh) is separate (#4977): after this merges it is
  replaced by writing the new version beside it and mv over (never in place: waiters are running it).
- A TERM, INT or HUP before the re-exec removes the file (a trap; exit 143, 130, 129), and so does a failed exec (it
  exits 3; execfail is set so a failed exec returns). A KILL in that window, a signal in the microseconds inside the
  mktemp or between dropping the traps and the exec, or one between the re-exec and the read, leaves one file in
  TMPDIR (mode 600).
- A stale TMPDIR (a folder since removed) falls back to /tmp for the file, as the capper's files already do (review 1).
- The re-exec is /bin/bash with no options: a `bash -x queued-heavy.sh` traces only up to it.
- `--queued-args` is refused unless the file is under TMPDIR (or /tmp) with the queued-heavy-args. prefix, with no path
  after that name, nothing after it on the command line, not a symlink, a regular file, and owned by this user.

## The cost, accepted
A person or tool can no longer tell from `ps` (or a waiter marker) what a waiting run is waiting for: every waiter reads
`queued-heavy.sh --queued-args <file>`, and the file is gone once read. Accepted: putting the label back in the command
line brings the hazard back (a label is free text, often naming the command), and the run's own log says it. If the
queue view needs it, the marker can gain a label line that no `pgrep -f` reads (a follow-up, not needed for the fix).

## Weakest premise
That nothing reads a queued-heavy waiter's argv for its LABEL. The label ("<what>") moves into the file too, so a
`ps` of a waiter now shows `queued-heavy.sh --queued-args <file>`. The label survives only in the run's own QUEUED-HEAVY
lines and, once it holds the box, in the machine claim; the waiter marker's line 2 (its `ps` command) no longer carries
it (review 2). The one argv reader found: the waiter marker's line 2 is the waiter's own
`ps -o command` (cut-guard.sh kosmos_mark_suite_waiting), read by _kosmos_old_qh_waiter_live and the side-turn check
for `*queued-heavy*`. The marker is written after the re-exec, and the new line still names queued-heavy.sh, so both
still find it (the 4911 side-lane tests pass).
