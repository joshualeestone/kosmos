# w4-4301: why win32apply W4 failed once on windows-latest, and removing the risk (#4301)

## Finished means (Liu Kang, m2067)
- The windows job's log shows the real failure message of a failing test.
- Either a root cause for W4's one failure with a fix, or evidence that it is a time budget on a
  loaded runner and a change that removes that risk. No budget raised alone, without evidence.

## The failure
windows run 36377105912, attempt 1, PR #4295: engine/win32apply.test.js "ROUND 8 decisions 1 and 2
(W4)" failed and the file took 428 s. The re-run of the same sha passed (309 s). The log showed only
the name, because the job kept only lines containing "Error".

## Measured (windows-latest, node v26.10.0)
- Probe run 36379665882, W4 alone, 8 runs at each load. Load is the number of whole
  win32apply.test.js runs alongside. 24 of 24 passed.

  | load | W4 duration |
  |---|---|
  | 0 | 14.7 to 15.9 s |
  | 1 | 14.8 to 17.5 s |
  | 2 | 14.9 to 23.6 s |

- Probe run 36380610883, the whole file twice at each load, every test over 8 s. W4 reached
  **28.0 s on a quiet runner** against its 30 s budget (T), 93%.
  - Other T tests each showed one outlier in 6 passes and ran under 8 s in the rest: PROBE6-E once
    36.0 s, SAFETY 1 not-whole once 22.8 s. That spread (one-off slowdowns of up to about 4.5x) is
    itself evidence for the slow-runner cause.
- Probe run 36385243566, the tests that await a real process (W4, W5, P8, P4, P3, P2), plus H1 for
  comparison (it spawns nothing real), three passes each at load 0 and load 2. Worst times: W4
  20.6 s, W5 8.5 s, P8 6.4 s, P4 4.1 s, P3 2.1 s, P2 1.8 s (H1 3.6 s).

## Root cause
- These tests run the product on sim.deps(), whose sleep and sleepSync only move a fake clock. The
  real time goes to what the sim does not replace:
  - the held renames win32swap.renameWithRetry really waits through, about 1 s per try, so about 6 s
    for a journal write held past OWNER_READ_BUDGET's tries;
  - the real shims a test spawns.
  W4 does two held-past-budget rollbacks, a hold of a window and a half, and spawns shims. Its floor
  is about 15 s before any slowness, so 30 s left under 2x headroom. The failing attempt ran the file
  about 40% slower than its re-run.
- A node:test timeout is a timer, so it can fire only while the test waits on real async work. Here
  that means awaiting a real process (bootShimAsync). A test that never does cannot be cut off by its
  limit: PROBE6-E ran 36 s on T and passed. So the tests at risk are the ones that await a real
  process, not simply the slow ones.
- The failing attempt's own log agrees. The old filter printed every line containing "Error", and
  under W4 it printed nothing. An assertion failure would have printed "AssertionError"; a timeout's
  "test timed out after 30000ms" contains no "Error".

## Build
- tools/windows-tests.js: failureDetail prints node's "failing tests:" section, one capped entry per
  failing test, instead of lines containing "Error".
  - Tests not expected to fail print first, and it says what it left out (lines per test, and whole
    tests past ten).
  - Only real stack frames are dropped.
  - A crash before the section falls back to the output's tail.
  - Tested in engine/windows-tests-1777.test.js.
- engine/win32apply.test.js: a HELD profile (150 s). The rule: a test that awaits a real process, and
  whose worst runner time times 4.5 passes 30 s, is HELD. That moves W4 (28.0 s) and W5 (8.5 s,
  W4's held-past-budget arm on its own). P8, P4, P3 and P2 stay on T (at most 28.8 s at 4.5x).

## Proven on the runner
- Run 36382303830 (windows job, the first version, which had one 60-line cap for a whole file):
  success. win32apply passed (381 s), with 1 known red and 0 new. Its failure detail first printed
  #4266's real message (RUNNER~1 against runneradmin), posted there. It also showed the whole-file
  cap hiding four of #4266's eight entries with no notice, which is why detail is now capped per test.
- Run 36385675093 (the rule and per-test detail, before iteration 2's entry-splitting fix): success.
  win32apply passed (325 s), 1 known red, 0 new. All 8 #4266 entries printed; the 6 longer than the
  per-test cap carried their "not shown" notice. The code as it merges is proven by the run cited in
  the PR.
- CONTROL, run 36383247607 (HELD set to 1 s): W4 failed, and the log printed `'test timed out after
  1000ms'` under its name. The job went red with NEW RED. W4 still ran 9,664 ms before the timer
  could fire, which is the yield behaviour above. So a timeout is what cuts W4 off, and the log now
  says so.

## Decided
- One slowdown factor, 4.5, for both the rule and the budget. HELD covers W4's worst (28.0 s) times
  4.5 = 126 s, rounded up to 150 s. That is a raise from 30 s, backed by that measurement (Liu Kang
  m2230), and a faster hang-guard than LONG (10 minutes).
- Rejected:
  - Raising T for the whole file: it widens 74 tests that do not need it.
  - Moving W4 and W5 to LONG: a hang would then take 10 minutes to show.
  - Shrinking the product budgets inside the test: that would stop testing the real budgets, which is
    what W4 is for.

## Weakest part
- The one failure's actual message was not captured, because the log fix came after. The cause is
  inferred from several pieces: W4 measured 93% of its budget on a quiet runner; the failing run was
  about 40% slower; the old filter's empty output is the signature a timeout leaves; and the control
  run shows a timeout is what cuts W4 off.
- The rule's 4.5x comes from one day of probes on one runner image. P8 is closest (28.8 s at 4.5x).
- The largest outliers may be a stall the runner adds (PROBE6-E ran 36 s once, against under 8 s
  otherwise) rather than a slowdown that scales. A stall of about 30 s could push ANY test that
  awaits real work past a 30 s budget, in this file or elsewhere. That would be a property of the
  runner, beyond this card, and the windows job's red would show it.
- Nothing keeps a NEW process-awaiting test that is slow off T; the rule is written where the next
  author of one will see it (beside HELD).
