# w4-4301: why win32apply W4 failed once on windows-latest, and removing the risk (#4301)

## Finished means (Liu Kang, m2067)
- The windows job's log shows the real failure message of a failing test.
- Either a root cause for W4's one failure with a fix, or evidence that it is a time budget on a
  loaded runner and a change that removes that risk. No budget raised alone, without evidence.

## The failure
windows run 36377105912, attempt 1, PR #4295: engine/win32apply.test.js "ROUND 8 decisions 1 and 2
(W4)" failed and the file took 428 s. The re-run of the same sha passed (309 s). The log showed only
the name, because the job kept only lines containing "Error".

## Measured (windows-latest, node v26.10.0)
- Probe run 36379665882, W4 alone, 8 runs at each load. Load is the number of whole
  win32apply.test.js runs alongside. 24 of 24 passed.

  | load | W4 duration |
  |---|---|
  | 0 | 14.7 to 15.9 s |
  | 1 | 14.8 to 17.5 s |
  | 2 | 14.9 to 23.6 s |

- Probe run 36380610883, the whole file twice at each load, every test over 8 s: W4 reached
  **28.0 s on a quiet runner** against its 30 s budget (T), 93%. Other T tests over half their budget:
  - PROBE6-E: 36.0 s (passed anyway; see below);
  - SAFETY 1 not-whole: 22.8 s;
  - ROUND 6 F2: 15.3 s.

## Root cause
- W4's floor is the product's own waiting. It drives the helper with the real OWNER_READ_BUDGET: a
  journal write held past its budget retries for about 7 s (6 tries, each a ~1 s rename window plus
  a wait). W4 does that twice, plus a hold of a window and a half. So about 15 s is spent before any
  slowness, and a flat 30 s T leaves under 2x headroom. The failing attempt ran the file about 40%
  slower than its re-run, which takes W4 past 30 s.
- W4 sits among W1, W2 and W3, which exercise the same held writes and are on LONG. W4 was given
  the quick profile.
- Why only W4 failed: a node test timeout is a timer, which fires only when the test yields.
  PROBE6-E blocks in sleepSync (Atomics.wait) and passed at 36 s. W4 awaits real shim processes, so
  its timer can fire. The 30 s budget is enforced only on async tests.

## Build
- tools/windows-tests.js: failureDetail prints node's "failing tests:" section, minus stack frames
  (or the output's tail if the file crashed first), instead of lines containing "Error". A timeout's
  "test timed out after 30000ms" now shows. Tested in engine/windows-tests-1777.test.js.
- engine/win32apply.test.js: a HELD profile (120 s) with a comment carrying these measurements and
  the rule: a T test that measured over half its budget on the runner moves to HELD. Four move: W4,
  PROBE6-E, SAFETY 1 not-whole and ROUND 6 F2. The sweep-throws test measured 40% and stays on T.

## Proven on the runner
- Run 36382303830 (windows job, the change): success. win32apply passed (381 s), and the verdict was
  1 known red, 0 new. The new failure detail printed #4266's real message (RUNNER~1 against
  runneradmin), posted there.
- CONTROL, run 36383247607 (HELD set to 1 s): W4 failed, and the log printed `'test timed out after
  1000ms'` under its name. The job went red with NEW RED. W4 still ran 9,664 ms before the timer
  could fire, which is the yield behaviour above. So a timeout is what cuts W4 off, and the log now
  says so.

## Decided
- 120 s: the file's own budget for its held-handle tests (WINDOWS_ONLY), more than 3x the worst
  measurement, and still a hang-guard (LONG is 10 minutes).
- Rejected:
  - Raising T for the whole file: it widens 74 tests that do not need it.
  - Moving the four to LONG: a hang would then take 10 minutes to show.
  - Shrinking the product budgets inside the test: that would stop testing the real budgets, which is
    what W4 is for.

## Weakest part
- The one failure's actual message was not captured (the log fix came after). The cause is inferred:
  W4 measured 93% of its budget on a quiet runner, the failing run was about 40% slower, and nothing
  else in W4 depends on the machine. The control run below shows a timeout is what cuts W4 off, and
  that the log now says so.
- The rule is applied by hand from one set of measurements. No check keeps a new held-budget test off T.
