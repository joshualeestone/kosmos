# guidemask-4733: mask the setup guide's words on task messages, built notes and status reports

Card: kosmos#4733 (found by Angel in review of #4491 slice 4; read from code, not run). Branch
`guidemask-4733`, off origin/main 4569e19a1.

## The finding, checked on main before building
#3769's third layer masks anything shaped like a secret out of what the setup guide says (`guideMasked` in
server.js, over `engine/secretmask.js`). On main it is applied to the guide's replies (`keepAgentReply`), its
messages and room posts (`messages.setSenderTextFilter`), the purpose it gives for an agent it makes, and the
thread as served. Three writes the guide can make with its own agent token took its text as sent:

| write | route | where the text went unmasked |
|---|---|---|
| `kosmos task message` | `POST /api/project/:id/task/:n/message` | `tasks.say(id, n, body.text)` (the task's record) and the preview typed to each assignee |
| the note on `kosmos task built` | `POST /api/project/:id/task/:n/built` | `tasks.setBuilt(..., { note: body.note })` (the task row and its history) |
| a status report | `POST /api/report` | `selfreport.record(who, { because: body.text, on, owner, until })` |

Still live at 4569e19a1: confirmed by reading the three sites, and by the mutation runs below (each site put
back as it was turns the new test red).

## The change
`server.js`, one call per site, each keyed on the sender the route has already identified:
- task message: `saidText = guideMasked(senderCard.sessionName, body.text)` when the caller is an identified
  agent; both the recorded text and the preview use it. The screen, and a caller nobody could identify (recorded
  as "An agent"), pass as sent.
- task built: the note goes through `guideMasked(by, ...)`.
- status report: `because`, `on`, `owner`, `until` and `project` go through a new `reportFieldMasker(who)`.
  The card names the text; the others are the same kind of field (`selfreport` stores each as text, capped, and
  the report shows them). `project` is meant to be an id but is stored as whatever string came (review round
  1). `waiting` is two numbers and `state` is a fixed word.
- `reportFieldMasker` exists because `selfreport` makes text of whatever it is handed (`String(value)`), and
  `guideMasked` returns a non-string as it came: a guide that sent `text: ["...key..."]` would have had it
  stored unmasked (review round 1, a blocker). The masker it returns makes the guide's value text first, then
  masks it; an absent value and any other agent's value pass as they came. For any agent that is not the
  guide it asks "is this the guide" once per report, not once per field (review round 2): the report route runs
  on every hook heartbeat. The guide's own fields each ask again inside `guideMasked` (review round 4).
- a guide report whose `project` is masked lights no project (the mask is not a project id). A real id is a
  short lowercase slug, which the mask does not take for a key; accepted.
- the mask runs in the route, BEFORE `selfreport` flattens and caps each field, so a cut cannot leave part of
  a key in the store (tested with a key that straddles the 1000-character cap).
- the same report is written AGAIN, by the post route, when a working agent posts into a project (the project
  is added and `because` / `on` / `owner` / `until` are carried from the latest stored line). Those carried
  fields go through the same masker, so a report the guide made before this ships is not re-written as
  it was (review round 1).
- `guideMasked` is unchanged: it returns a non-string, and any other agent's text, as it came. The task
  message and built routes already turn away a non-string (`tasks.say` treats it as empty; the built route
  checks `typeof body.note === 'string'`).

## Decisions
- **Call:** mask at the write, in the route, where the sender is already known. **Rejected:** (1) masking
  inside `tasks.say` / `selfreport.record`: neither is told who is writing, and both are called for the person
  too; (2) masking every agent's text: #3769 decided the mask is the guide's (other agents are given keys on
  purpose and must be able to say them to each other); (3) masking the task record as it is READ, the way
  `guideMaskedRows` does for threads: a task message's record does not say who wrote it, so there is no row to
  key on.
- **The length limits are judged on the masked words (review rounds 2 and 3).** The mask can make a text
  longer: a short password in a link (`ftp://u:p@h` gains three characters), and the whole-message sentence
  secretmask uses when it could not finish checking (`UNCHECKED`). So a guide message at the 2000-character
  limit, or a built note at 300, can be refused after masking with the usual "keep the ... to N characters or
  fewer", and nothing is kept. **Call:** leave the refusal. It fails closed, says what to do, and only the guide
  can meet it. **Rejected:** cutting the masked text to fit (a silent cut of someone's words), and judging the
  limit on the words as sent (the store would then hold more than its limit). Pinned by a test with a control.
  ⚠️ In round 2 I deferred this as "masking never makes a text longer", on seven measured shapes. That was
  false; round 3 read the two cases above out of secretmask.js and I reproduced the first.
- **A ceiling before the scan (review round 5).** The mask is a scan on the board's one thread and, at these
  three sites, it runs before the length limit (it has to: see the cap test). A request body may be 6 MB. So a
  guide text more than 8 times over its limit is not scanned whole: a task message or built note is refused
  with the limit's own sentence (it would have been refused after the scan unless over seven eighths of it were
  keys), and a report field is cut to 8000 characters first, back to the last space so no part of a word is
  left at the cut; the store then keeps its first 1000 as before. **Not changed:** `kosmos msg` and `kosmos
  post` have masked before their length check since #3769, with no ceiling. Same class, other routes; I left
  them, and it belongs on a card of its own (a ceiling inside `guideMasked` would cover every site at once, and
  changes what those two routes answer).
- **Not covered, stated so nobody reads this as complete:**
  - a task message or built note the guide recorded BEFORE this ships stays as recorded (no read-side mask, for
    the reason above).
  - a status report the guide made BEFORE this ships stays in its report file: the file is appended to, never
    rewritten, and only the latest line is read and shown. Its next report (or a post that carries it) adds a
    masked line, after which the old line's `because`, `on`, `owner` and `until` are no longer shown; they
    are still on disk. Its `project` is different (review round 5): `selfreport.read` carries a project
    forward from an earlier line until a later report names one or the run starts again, so a project string the
    guide stored before this ships keeps being read until then. It is only ever compared with project ids.
  - a caller that claims the screen (a `Sec-Fetch-Site` or loopback `Origin` header, `isViaScreen`) and presents
    no agent token is taken as the person on both task routes and is not masked. It needs the board token on an
    enforcing board, the same limit as the next line.
  - a guide that sends with no agent token and no pane is not identified, so it is not masked. A Claude guide
    on a Mac cannot do that (the board token is what such a call needs, and #4728 measured that its commands
    cannot read the data folder); other guides can (#4728 is that card).
  - the other writes open to an agent token were read, not changed: `react` takes an emoji only
    (`normalizeReactionEmoji`), `msg` / `post` / `reply` and the team purpose were already masked.
- **Weakest premise:** that these three were the last unmasked free-text writes an agent token reaches. One
  I read and left: the bulk close route writes a free-text note into a task's record unmasked
  (`taskchat.record(..., { kind: 'said', text: note })`). It is reachable from the screen only, so it is the
  person's note; if it is ever opened to an agent token it needs the mask (review round 4). I checked the routes an agent
  token opens (`AGENT_TOKEN_ROUTES`, `AGENT_TOKEN_ROUTE_PATTERNS`, `LOOPBACK_AGENT_ROUTES`) and not every route
  a board-token holder can reach: a guide with the board token can write anywhere the person can.
- **Not checked (the card's own open question):** whether the guide is ever on a project in normal use, which
  the two task writes need. The fix does not depend on the answer.

## Tests
New `server.guide-mask-4733.test.js`: eleven tests through the real routes with real agent tokens
(`sendertoken.mint`), reading what was stored:
- task message: the record and the route's answer hold the mask and not the key; the line typed to the assignee
  (captured at `chat.deliverAsync`) holds the mask and not the key. Control: another agent's same words are
  recorded and previewed as sent.
- built note: `builtNote` and the task history. Control: another agent's note as sent.
- status report: `because`, `on`, `owner`, `until`, `project`, each asserted as its masked text. Control:
  another agent's same five fields as sent.
- a report whose fields are lists: stored masked for the guide. Control: another agent's is stored as the
  store has always made text of it.
- a report with no `on` / `owner` still records them as absent.
- a report stored with a key (as an older build would have) and then carried onto a project by a post: the
  new line is masked for the guide in all four carried fields. Controls: the project was carried (so the second write happened), and
  another agent's carried report is unchanged.
- a long two-paragraph report whose key straddles the 1000-character cap: the stored text keeps the paragraph
  break, holds the mask, and holds no part of the key. Control: another agent's same report IS cut inside the
  key, so the cut is real.
- the pane arm: a caller named by `from_pane` with no token, on both task routes, masked when the agent its
  pane resolves to is the guide. Controls: the mark is recorded as that agent's (so the pane arm is what ran),
  and the same pane's words are kept as sent when that agent is not the guide.
- the limits: a guide note and a guide message exactly at their limits, each ending in a link with a
  one-character password, are refused (400, the limit's own sentence) and nothing is kept. Control: the same
  two texts from another agent are kept.
- the person: the same words with a key, sent from the screen, are recorded as sent. The mask is the guide's;
  what the person writes is never changed.
- far over the limit: a guide message and note ten times over their limits are refused and the mask is never
  called (a counter on `secretmask.mask`); a 9000-character report with a key across the 8000 ceiling is
  scanned as exactly 7990 characters (cut at the space before the key) and stores none of the key.
- a list-valued `project` is dropped by the route for everyone (`typeof body.project === 'string'`); the
  list test sends one and asserts no key is stored.
