## Findings

- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:360. The control's label contains its failure explanation, "(it did not: the make-room step is broken or gone, or declined by its own rules ...)", so every green run prints `PASS ... so the tour must ask to make room (it did not: ...)`. That reads as a contradiction (seen in both engines in my run). Fix: keep the label to the claim ("the card is flat without the scroll, so the tour asked to make room") and move the diagnosis into the extra argument, or print it only when `!w.scrolled.includes('Conversation')`.
- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:358. `conv && !conv.pointing` treats an errored step (`{ title, error: 'no card or no target' }`, where `pointing` is undefined) as "flat". In the control nothing else judges per-step errors. So a missing Conversation target is reported as "make-room broken or gone" when the tour did not scroll, and passes silently when it did (the main arm still catches it, so this is diagnosis, not coverage). Also, a missing `conv` falls into the else branch, which pushes STALE and prints "the Conversation card points", which is false (the `!!conv` chk reds that run anyway). Fix: `if (!conv || conv.error) { chk(false, `${tag} the control read its Conversation step`, JSON.stringify(conv)); } else if (!conv.pointing) ... else ...`.
- [NIT] docs/browser-checks/render-chatbox-phone-4108.js:141 and 159. `__tipScrollBy` stores `Math.abs(...)`, so a make-room step with its sign flipped (scrolling down by 6) prints the same `[6]px` "shortfall" as a correct one. Separately, the line 159 comment says the fields are "the geometry the make-room step reads", but in the main arm they are read after the scroll and the relayout (Conversation top 174, not the 168 the step saw). Only the control and declined runs show what the step read. Fix: record the signed value, and say "after the step's own scroll, if any" in the comment.
