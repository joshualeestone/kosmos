# kosmos#2615: grey out Restore when the account directory is gone

Frontend counterpart to #2609 (PR #2613), which made the ENGINE refuse the restore. Built by April,
night shift 2026-09-10.

## The defect

The removed-list offers a **Restore** button on every row. #2609 made the engine REFUSE when the
agent's account directory is gone, because restoring would re-enable a launchd job pointing at a
directory that no longer exists. That is the right backstop, but the person still clicks a live
button and is told no afterwards.

## 🛑 The card says "frontend counterpart". It cannot be frontend-only, and that is the first finding

`GET /api/removed` returns exactly four fields per row:

```
name, shownAs, removedAt, stopped
```

**Nothing there says whether the account directory exists, and a browser cannot stat a filesystem.**
So the greyed-out state needs a new field on that payload. This card is backend + frontend.

## The design, and what was rejected

**ONE predicate, exported, read by both the refusal and the API.**

```
engine/remove.js
  restoreBlockedByMissingAccountDir(name, platform)   <- the single source of truth
      |                        |
   restore() refusal      /api/removed field
```

🛑 **REJECTED: re-implementing the check in `server.js`.** It is four lines
(`readJob` -> `configDir` -> `existsSync`), which is exactly what makes copying it tempting. A second
copy of a fact that already exists is the defect class that produced **five separate findings on
#2612 in one night**, including two copies of a normalisation that drifted within a single
iteration. The whole point of a pre-click state is that it agrees with the post-click refusal; two
implementations is the one way to guarantee it eventually will not.

⭐ **A greyed-out control that disagrees with the engine is WORSE than the click-then-refuse it
replaces**, and it fails in the direction nobody reports: a button greyed out where the engine would
have said yes looks like a considered product decision, so nobody files it. Click-then-refuse at
least produces a sentence the person can read and disagree with.

## Scope inherited from #2609 rather than re-litigated

#2609 documented these at the code and they bound this card too:

- **Mac only, structurally.** The check reads the account dir out of the launchd plist; a win32
  agent has no plist (it carries a registered Scheduled Task), so `readJob` returns null.
- **A default-account agent has `configDir: null`** and is correctly untouched: `~/.claude` always
  exists.
- **A gone plist is the separate `plistGone` case** and does not fire this.
- 🛑 **A Windows agent whose account was deleted still restores unchecked.** Named as a follow-up by
  #2609, not closed by it, and not closed here.

⇒ **The greyed state must not be wider than what the engine actually refuses.** Where the engine
would allow the restore, the button stays live even if it looks doubtful.

## Test plan

- An arm asserting the API field and the engine refusal **agree for the same agent**, so the two
  cannot drift; it reds if either side changes alone.
- Arms for each inherited scope bullet: `configDir: null` is NOT blocked, win32 is NOT blocked, a
  gone plist is NOT blocked by this reason.
- A browser check on the rendered control: disabled + an accessible explanation when blocked, live
  when not, with the negative arm as a control so the check cannot pass by disabling everything.
- Mutation controls on every new arm, since an assertion that cannot fail is this repo's most-shipped
  defect.

## Weakest premise

That the engine refusal and the API field stay in step. That is why they share one function rather
than two copies, and why the agreement arm exists rather than two independent assertions that happen
to match today.


## Corrections after challenge-loop iteration 1

**The name in the diagram above was `restoreBlockedReason` and the code ships
`restoreBlockedByMissingAccountDir`.** Fixed, because the plan is the durable
forensic record and the name a future reader greps for has to be the one in the
tree.

**The first version of the control was `disabled` with the reason in a `title`
and an `aria-label`, and it cited the sibling reauth control as precedent.** The
sibling argues the opposite at its own code: a `disabled` button leaves the tab
order so a keyboard user never lands on it or hears the reason (the repo names
that a WCAG AA failure), and a `title` on a disabled control is not announced at
all. ⇒ **The first version put the only explanation out of reach of exactly the
people it was written for**, and the comment asserting otherwise was a claim
about another part of this file that I did not check. Now `aria-disabled`,
focusable, with the refusal enforced structurally by the absence of
`data-restore`, plus a handler so a press says why.

**The route's one new line was unasserted for the `true` case.** The agreement
arm compared `row.accountFolderGone` against the predicate on a fixture whose
plist body is `<plist/>`, so `readJob` returned null and both sides were
`false`. Measured: a hardcoded `accountFolderGone: false` passed it. ⭐ **`false
=== false` is the shape to remember: an equality between two expressions that
are both the boring value tests neither.** A new arm builds a real plist naming
a real account dir, deletes it, and asserts `true`; measured against the same
mutant, the new arm fails and the old one still passes.

**Both "cannot drift" assertions were tautologies**, comparing values the
preceding asserts had already pinned. The agreement arm now measures each state
independently and compares the pair. And nothing pinned that `restore()` READS
the export: a re-inlined byte-identical copy left every behavioural arm green,
because two copies agree perfectly on the day the copy is written. That needed a
source-shape assertion, which is a weaker instrument and is labelled as one.


## Corrections after challenge-loop iteration 2 (sonnet)

0 BLOCKERs, 1 WARNING, 1 NIT, both real. It also independently mutation-tested
every iteration-1 fix and confirmed they hold (the route true-case arm, the
source-shape arm, the browser check's negative arm), which is worth more than
its findings.

**WARNING: the explain handler destroyed an in-flight restore's status.**
`#removed-msg` is a single assertive live region shared by several flows, and I
added another writer to it without reading what the existing ones do. The
in-flight sentence ("Starting X again...") is written ONCE and cleared only by
the ARRIVAL it predicts, so anything overwriting it destroys it permanently:
press Restore on one row, then press an unavailable Restore on another, and the
first agent is still coming up with nothing on screen saying so.

Both sentences are true at the same time, so both are now said. The in-flight
one is RE-ASSERTED from `RESTORE_WAITING_SENTENCE` rather than reconstructed at
the second site, which is what stops the two copies drifting; that variable is
new precisely because the old code had no way to re-assert what it had said.

**RESIDUAL, stated rather than hidden:** the arrival clears the whole region, so
an explanation still on screen goes with it. That is the right trade (the
arrival is a real event and the status it clears is the one the person was
waiting for) and the explanation is re-obtainable by pressing the control again.

⭐ **A shared surface has no owner, so the interaction is nobody's code and shows
up in nobody's diff.**

**NIT: the browser check depended on render order.** It searched `.acts button`
by `data-shown-as`, and the "Delete its files" button in the same row carries the
SAME attribute, so it silently depended on Restore rendering before Delete. Now
scoped to the union of the two Restore attributes.

## Iteration 3 (self-probed, plus one found by reading the doc against the code)

**Pinned the other direction of the listener seam.** There are now THREE click
listeners delegated on `#removed-list` (restore, explain, delete-leftover), each
selecting a different attribute. Iteration 2 covered one direction; nothing
covered the other: a press on a LIVE Restore, or on "Delete its files", must not
fire the explain handler and tell the person a working control is unavailable.
Measured first and it was already correct, but reasoning had been wrong twice on
this card, so it was run rather than argued. Control: widening the explain
selector to `.acts button` reds the arm.

**🛑 The check's own README row documented the exact defect the check reds on.**
The row said it "asserts the blocked row's button is `disabled`". The check
asserts the OPPOSITE and reds on hard `disabled`. That sentence was written for
the first version of the control and never updated when iteration 1 replaced
`disabled` with `aria-disabled` + focusable.

⭐ **Third instance on this card of one class: a confident claim about code I had
not re-opened.** Iteration 1's was a comment citing the sibling reauth control as
precedent for `disabled` when the sibling argues the opposite. This is that same
wrong sentence surviving in the durable doc after the code was fixed. **Fixing
code does not fix the prose that justified it**, and the doc is what a future
reader consults: someone reconciling code to doc would have reintroduced the
WCAG AA failure, with the check going red against a doc saying the red was wrong.
Nothing pinned it, because no test reads that README.

### Checked and found CLEAN, recorded so they are not re-probed

- **The double clean of the name.** `restoreInner` passes an already-cleaned name
  into the shared predicate, which cleans again, while the route cleans once. That
  is only safe if `cleanName` is idempotent, and it is: `String(raw).trim()`.
- **`readJob` cannot throw into the route.** It try/catches its read and returns
  null on a bad name, and `existsSync` does not throw, so the new per-row call
  cannot 500 the whole removed list.
- **`#removed-list` is static markup**, so both module-scope listener bindings are
  safe.
- **`RESTORE_WAITING` and `RESTORE_WAITING_SENTENCE` have exactly two write sites
  and they are paired**, so the two cannot fall out of step.

### Named follow-up, deliberately NOT fixed here

`#removed-msg` has roughly eight writers and several bare-overwrite each other,
including the restore handler's own `partial` branch. **That is pre-existing on
`origin/main`, not introduced by this card**, and iteration 2's finding was
specifically that MY new writer must not destroy. Teaching every pre-existing
writer to re-assert is a separate card; doing it here would widen this one well
past greying out a button. Recorded so the next person sees it was seen.
