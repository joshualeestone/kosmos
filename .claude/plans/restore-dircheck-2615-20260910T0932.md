# kosmos#2615: grey out Restore when the account directory is gone

Frontend counterpart to #2609 (PR #2613), which made the ENGINE refuse the restore. Built by April,
night shift 2026-09-10.

## The defect

The removed-list offers a **Restore** button on every row. #2609 made the engine REFUSE when the
agent's account directory is gone, because restoring would re-enable a launchd job pointing at a
directory that no longer exists. That is the right backstop, but the person still clicks a live
button and is told no afterwards.

## 🛑 The card says "frontend counterpart". It cannot be frontend-only, and that is the first finding

`GET /api/removed` returns exactly four fields per row:

```
name, shownAs, removedAt, stopped
```

**Nothing there says whether the account directory exists, and a browser cannot stat a filesystem.**
So the greyed-out state needs a new field on that payload. This card is backend + frontend.

## The design, and what was rejected

**ONE predicate, exported, read by both the refusal and the API.**

```
engine/remove.js
  restoreBlockedByMissingAccountDir(name, platform)   <- the single source of truth
      |                        |
   restore() refusal      /api/removed field
```

🛑 **REJECTED: re-implementing the check in `server.js`.** It is four lines
(`readJob` -> `configDir` -> `existsSync`), which is exactly what makes copying it tempting. A second
copy of a fact that already exists is the defect class that produced **five separate findings on
#2612 in one night**, including two copies of a normalisation that drifted within a single
iteration. The whole point of a pre-click state is that it agrees with the post-click refusal; two
implementations is the one way to guarantee it eventually will not.

⭐ **A greyed-out control that disagrees with the engine is WORSE than the click-then-refuse it
replaces**, and it fails in the direction nobody reports: a button greyed out where the engine would
have said yes looks like a considered product decision, so nobody files it. Click-then-refuse at
least produces a sentence the person can read and disagree with.

## Scope inherited from #2609 rather than re-litigated

#2609 documented these at the code and they bound this card too:

- **Mac only, structurally.** The check reads the account dir out of the launchd plist; a win32
  agent has no plist (it carries a registered Scheduled Task), so `readJob` returns null.
- **A default-account agent has `configDir: null`** and is correctly untouched: `~/.claude` always
  exists.
- **A gone plist is the separate `plistGone` case** and does not fire this.
- 🛑 **A Windows agent whose account was deleted still restores unchecked.** Named as a follow-up by
  #2609, not closed by it, and not closed here.

⇒ **The greyed state must not be wider than what the engine actually refuses.** Where the engine
would allow the restore, the button stays live even if it looks doubtful.

## Test plan

- An arm asserting the API field and the engine refusal **agree for the same agent**, so the two
  cannot drift; it reds if either side changes alone.
- Arms for each inherited scope bullet: `configDir: null` is NOT blocked, win32 is NOT blocked, a
  gone plist is NOT blocked by this reason.
- A browser check on the rendered control: disabled + an accessible explanation when blocked, live
  when not, with the negative arm as a control so the check cannot pass by disabling everything.
- Mutation controls on every new arm, since an assertion that cannot fail is this repo's most-shipped
  defect.

## Weakest premise

That the engine refusal and the API field stay in step. That is why they share one function rather
than two copies, and why the agreement arm exists rather than two independent assertions that happen
to match today.

## Corrections after challenge-loop iteration 2 (sonnet)

0 BLOCKERs, 1 WARNING, 1 NIT, both real. It also independently mutation-tested
every iteration-1 fix and confirmed they hold (the route true-case arm, the

**WARNING: the explain handler destroyed an in-flight restore's status.**
`#removed-msg` is a single assertive live region shared by several flows, and I
added another writer to it without reading what the existing ones do. The
in-flight sentence ("Starting X again...") is written ONCE and cleared only by
the ARRIVAL it predicts, so anything overwriting it destroys it permanently:
press Restore on one row, then press an unavailable Restore on another, and the
first agent is still coming up with nothing on screen saying so.

Both sentences are true at the same time, so both are now said. The in-flight
one is RE-ASSERTED from `RESTORE_WAITING_SENTENCE` rather than reconstructed at
the second site, which is what stops the two copies drifting; that variable is
new precisely because the old code had no way to re-assert what it had said.

**RESIDUAL, stated rather than hidden:** the arrival clears the whole region, so
an explanation still on screen goes with it. That is the right trade (the
arrival is a real event and the status it clears is the one the person was
waiting for) and the explanation is re-obtainable by pressing the control again.

⭐ **A shared surface has no owner, so the interaction is nobody's code and shows
up in nobody's diff.**

**NIT: the browser check depended on render order.** It searched `.acts button`
by `data-shown-as`, and the "Delete its files" button in the same row carries the
SAME attribute, so it silently depended on Restore rendering before Delete. Now
scoped to the union of the two Restore attributes.

## 🛑 Iteration 3, blind reviewer: BLOCKER. The card greyed nothing out.

**This is the most important finding on the card and it survived three
iterations, two of which read this exact control closely.**

The "unavailable" Restore was **visually identical to a live one.**
`getComputedStyle` on both rows, driven through the real `paintRemoved`:

```
blocked: opacity 1, cursor pointer, bg rgb(250,249,247), color rgb(20,22,26)
live:    opacity 1, cursor pointer, bg rgb(250,249,247), color rgb(20,22,26)
```

Identical on every property including border. Reported by a blind reviewer and
**reproduced by me before acting**, because a report is a claim until measured.

### The mechanism, which is the part worth keeping

**`disabled` was doing TWO jobs: the semantics AND the dimming**, via
`.btn:disabled`. Iteration 1 moved this control to `aria-disabled` so it keeps
the tab order and a keyboard user can reach the reason. That was right. It
**preserved the semantics and silently dropped the styling**, because
`:disabled` stops matching and no `.btn[aria-disabled="true"]` rule exists.

⭐ **An accessibility fix took a visual affordance with it, because the CSS
matched the OLD attribute.** Nothing in the suite could see it: every arm
asserted an attribute, and the check passed clean the entire time.

⭐ **The generalisable form: when you change the attribute a control is
identified by, ask what ELSE was keyed on the old one.** CSS is the easy one to
forget, because it is in a different file region, owned by nobody, and absent
from the diff you are reading.

### The value is WCAG, not taste

The reviewer suggested `.5`, mirroring `.btn:disabled`. **Rejected, with the
numbers.** A hard-`disabled` control is EXEMPT from the contrast minimum, so
`.5` is correct there. **This one is not exempt: it stays focusable and a press
does something.** Computed on `--label` #14161a over `--bg` #faf9f7:

| opacity | contrast | AA (4.5) |
|---|---|---|
| full | 17.21:1 | passes |
| .8 | 9.36:1 | **passes** |
| .7 | 6.55:1 | passes |
| .5 | 3.39:1 | **FAILS** |

`.8` is also the sibling `.acct-disconnect[aria-disabled="true"]`'s value, which
did this math first.

📌 **Scoped to `.acts` deliberately.** A bare `.btn[aria-disabled="true"]` ties
`.btn:disabled` on specificity and wins on source order, which would quietly
restyle `#fr-next` in the first-run wizard (it sets BOTH attributes) from .5 to
.8: a different flow, changed as a side effect of this card.

### The fix's other half, and the more important one

The check now asserts **computed style**, not only attributes. Asserted as
"dimmed at all" rather than a specific number, so a future contrast adjustment
does not red it for no reason; the value is argued at the CSS rule.

| mutation | measured |
|---|---|
| baseline | **exit 0** |
| delete the new CSS rule (the shipped defect) | **exit 1**, "renders at full opacity (1), so it looks exactly like a live button" + the not-allowed arm |
| widen the rule to every `.acts .btn` | **exit 1**, "a row whose account folder is PRESENT is dimmed" |

### Weakest premise in this fix, named

That `.8` reads as unavailable to a sighted user at a glance. It is deliberately
subtle to hold AA, and it leans on `cursor: not-allowed` to carry the rest.
**What would change my mind: Josh saying it does not read as greyed out.** That
is a reversible style value, so it is mine to decide now and cheap to deepen
later; the mechanism and its guard do not change if the number does.

### Considered and accepted: the route now touches the filesystem per row

`/api/removed` went from pure in-memory to one `readJob` (a small plist read)
plus one `existsSync` per removed row. `paintRemoved` is called from the 5-second
`tick`, gated on `onAgentsTab()`, so that is N small reads every 5 seconds while
a person is looking at the Agents tab.

Accepted: this is a local single-user desktop app, removed agents number in the
handful, and the reads are microseconds. Rejected caching the answer, because a
cache is exactly how the pre-click state starts disagreeing with the engine, which
is the one failure this card must not introduce. Recorded because the change from
"never touches disk" to "touches disk per row per poll" is the kind of thing that
is invisible in a diff and expensive to rediscover.

## 🛑 And the check was measuring a page state nobody sees

Self-found while verifying the accessibility claim, and it changes how much
every earlier green on this card was worth.

**Every arm ran against a COLLAPSED list.** `#removed-list` ships `hidden` and
opens on a toggle the check never pressed. Measured on the old version:
`listHidden: true`, `btnVisible: false`, and `b.focus()` left `activeElement` on
`BODY`. **The arms passed anyway**, because attribute reads and programmatic
`.click()` both work perfectly on an invisible element.

**And `focusable: !b.disabled` was a definition wearing a measurement's name.**
It never focused anything. An element inside a collapsed container is not
focusable however un-disabled it is, which is precisely the state it was
asserting in.

⭐ **The field is named for the property, so a reader checks the NAME against the
requirement and never the name against the EXPRESSION.** Three iterations,
two of which reviewed this control's accessibility specifically, went past it.

⚠️ **The product was fine the whole time.** Measured with the list expanded the
way a person opens it: focusable, on screen, in the tab order, and **both Enter
and Space announce the reason**. So this was an INSTRUMENT defect, not a
behaviour one. It matters because the instrument is what has to catch the next
regression, and it could not see the state one would happen in.
