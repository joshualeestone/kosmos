# uici-7609: the sample-board UI tests in CI, and an off-screen chat keeps nothing (kosmos#7609)

Follow-up to #7344 (Mona Lisa's PR #7608), items 3 and 4 of four. Items 1 and 2 are judged on a phone or an older
runtime; this PR gives item 1 a partial answer, since the CI runner's simulator is not the iOS 27 the tests were written on.

## Finished looks like
- `ios/tools/ui-sample.sh` runs every UI test that needs no account on a fresh simulator (the newest installed runtime,
  the smallest iPhone it offers): AttachMenuUITests 6, RoomTitleUITests 2, ChatOpensAtNewestUITests 1,
  KeyboardSlideUITests 3. It prints PASS only when exactly those 12 ran and none failed (a filter that matches nothing
  also exits 0), and stops if the Simulator's hardware keyboard preference is on, without changing it.
- `.github/workflows/ios.yml` has a second job, "ui tests (sample board)", which runs it on every iOS change. Advisory,
  like the rest of the workflow.
- `ChatView`'s keyboardWillShow records `keepNewestInView` only for the chat on screen; an off-screen chat sets it false.
  The handler that acts on it already required `visible`, so on-screen behaviour is unchanged.

## Decided
- Item 3 by removing the asymmetry (the card allows either), not by a UI test of a chat kept alive under another tab:
  that state is hard to reach deterministically in a UI test, and with the flag only ever true for the chat on screen
  there is nothing left for such a test to catch. Weakest premise: that the flag has no other reader; checked by grep
  (only keyboardDidShow reads it).
- Item 4 as a separate job, not more steps in the build job: the build job is near its timeout with the archive checks,
  and a UI failure should be named on its own.
- SignInUITests stays out (it needs a real account; ui-signin.sh).

## Not in scope
- Item 1 on a real phone, and item 2 (the cover-then-jump, judged on a phone).

## Review ledger
- Round 1: no BLOCKER. WARNING, the runtime was the newest installed, not the newest the selected Xcode can run (a CI
  image with several Xcodes could hand xcodebuild a runtime it refuses); WARNING, the device type pick had the same
  mismatch. NITs: test names limited to letters; one total count, not per class; two comments still said no CI job
  runs the UI tests. All taken: runtime capped at `xcrun --sdk iphonesimulator --show-sdk-version`, per-class counts,
  names with digits and underscores, comments name the job, ui-keyboard.sh's --help range follows its header.
- Found by running, not by review: KeyboardSlideUITests' "read higher up" check failed once in 8 runs, the one run with
  heavy load beside it (6 of 6 alone, 3 on main, 3 here); it is Mona Lisa's test and she is fixing its fixed 4.2 s wait.
  AttachMenuUITests' Files check failed once when a system picker took over 8 s to first launch: now 20 s (a dropped
  picker still fails: the + stays tappable).
- Round 2: no BLOCKER and no logic finding. WARNING, the "no runtime" message would be false on an image whose runtimes
  are all newer than the SDK; NITs: the reason line's name pattern, the header's wording, a silent uncapped fallback.
  All taken (wording only).
