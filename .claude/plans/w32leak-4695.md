# w32leak-4695: win32apply's first-run mode cases stop writing into the worktree (kosmos#4695)

## The defect
engine/win32apply.test.js's #4381 cases write %LOCALAPPDATA%\Kosmos\mode through the real reader's path,
`computerModePath(process.env)` = `path.win32.join(<POSIX temp path>, 'Kosmos', 'mode')`. On macOS that is ONE
relative file name full of backslashes, so `setMode` wrote it (and the helper's real reader read it) in the process's
cwd: the worktree. The file was removed in each test's `finally`, which is why nothing is left after a run, but it sat
there for about half the file's run, and engine/win32board.test.js's #4495 guard, running at the same time in
another test process, saw it as a leak (CI, PR #4689, run 36670783246).

Measured with a poller (scratchpad leakwatch.sh, 20 ms): origin/main 9bce3a6f2, 417 of 867 polls saw
`\var\folders\...\kosmos-w32apply-*\localappdata\Kosmos\mode` in the cwd. This branch: 0 of 791. Both 84/84 pass.

## The call
The three cases that use setMode (H7, H8, the held-run case) run inside `inSandboxCwd`: the cwd moves into this file's
SANDBOX, so the file is written and read there, and the cwd is always restored. It asserts first that the mode file
resolves inside the sandbox.

## Rejected
- Changing `computerModePath` for macOS: the product runs it only on Windows, and the "by the same rule as
  Kosmos.exe" test pins the win32 join. A test-only problem gets a test-only fix.
- A seam for the mode reader: the cases deliberately use the real reader ("no mayStartBoard seam").

## Weakest premise
That nothing else in these three tests depends on the cwd. freshInstall and the journal use absolute SANDBOX paths;
the file's 84 tests pass with the change.

## Blind review round 1 (Sonnet): nothing above NIT
Traced and safe: nothing in the three tests or the helpers they call reads the cwd; the file has no subtests or
concurrency option, so nothing else runs while the cwd is moved; every MODE_FILE writer and the real reader are inside
the wrapped region; the realpath check does not fail on /var vs /private/var and is not vacuous.
- [NIT] startsWith had no trailing separator. TAKEN.
- [NIT] a 30 s timeout fires before the finally could leave the cwd moved for the next test. ACCEPTED: nothing in this
  file reads the cwd, and the wrapped bodies have no real async waits.
