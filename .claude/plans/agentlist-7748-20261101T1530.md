# agentlist-7748: small CLI gaps from feedback (kosmos#7748)

1. `kosmos agent list`: every agent, its role, running or not. GET /api/agents/list runs the same branch as /api/status, because stopped agents exist only in that derivation, and answers three fields per agent with the guide left out: the name, the role (profile.role, else the line parsed from the instruction file), and the card's own word (`cardWord`). The state word equals the card by construction. The role can differ in spelling: the page also looks a parsed line up in the catalogue titles and sentence-cases it, so a parsed `project manager` shows lower-case here. Left so: the meaning is the same, and the lookup lives in the page. It joins AGENT_TOKEN_ROUTES because a Windows agent holds no board token. Rejected: reading /api/status from the CLI (far more than an agent needs, and closed to a token-only agent); the roster from `snapshot()` (the first version: it lacks every stopped agent, and its captures hold the board).
2. `kosmos project create` on a missing folder prints the command that makes it, on both CLIs. Rejected: the board making the folder, which would let an agent's request create a folder anywhere on the computer.
3. `kosmos agent roles` groups by the catalogue's group, and `kosmos agent roles <word>` narrows by key, label or group. A word that matches nothing exits 1. The line format changes: rows are indented under a heading.
4. `kosmos connections` exiting non-zero: NOT reproduced and not changed. rc=0 on 0.7.81 on a plain run, with `| head -1`, and on six runs with stdout closed early (`| true`). On reading, the only non-zero exits follow an unreachable board or an unreadable answer, and each prints its own line. Would change my mind: a report with the shell, the output and the exit status.
5. GitHub and Vercel: `connectionsHeld` now reads the tool's own file (engine/signedin.js), gh's hosts.yml and Vercel's auth.json, with no call to either service. A file holding a sign-in reads connected, "signed in with its own tool". No file stays "not known without a live check", because a tool can keep its sign-in elsewhere.

The agent and role words live once in engine/clilists.js, which both CLIs run. The connections sentences are two copies, as they already were, and a test on each CLI pins the new one. `kosmos agent list` is taught in the two role texts that name `kosmos agent roles`, and `kosmos agents` says what it lists.

Role text reaches new agents only: `refreshGuideRole` swaps the pre-#3734 paragraph, and no refresh carries this sentence to agents already made. They learn the verb from `kosmos agent --help`, `kosmos --help` and the `kosmos agents` row. Left so: one sentence does not justify a refresh path.

When the board could not read every job (`counts.notRunning` is null) the answer carries `partial: true`, and both CLIs say the list may be incomplete rather than that there are no agents. Not covered: the offline builder's own catch returns nothing and sets no flag, so that failure still reads as complete, on the board as well. The `|| a.role` fallback has no test, because the fixture cannot supply a parsed role.

The review stopped at the 8-round cap with no BLOCKER open. Left from round 8: on a Mac a missing `clilists.js` reads as an answer that could not be read; gh and Vercel's folder rules are a second copy of what the doors pass; "No role matches" prints on stdout. None is worth a ninth round.

Cost: the list runs the whole /api/status derivation, side effects included, to keep three fields, and has no valve, so an agent looping on it repeats that work. On a Mac concurrent reads share the captures and those do not hold the board, while the other per-agent reads repeat. On Windows `snapshotUnheld` is plain `snapshot()`, so neither holds, and this costs most there. Rejected for now: extracting a row builder from an 800-line route in a change this size. Would change my mind: one agent seen looping on it.

Weakest premise: a file holding a sign-in says nothing about whether the service still accepts it. A token row has the same limit and says so; so does this line ("Settings > Connections checks it when opened").
Not measured: Windows paths in engine/signedin.js for gh and Vercel are from their documentation and code, not from a Windows box. They fail to "not known". Vercel's Windows folder is from memory of its tool, so both candidates are read.
