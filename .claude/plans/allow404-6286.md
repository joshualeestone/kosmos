Relay half: kosmos-relay branch allow404-6286, with the full root cause in its plan. Claimed by Angel at 23:26 CDT on 2026-10-15.

**Finished looks like:** `POST /api/remote/devices/allow` for an id the coordinator does not hold answers 400 "Kosmos+ has no sign-in waiting with that id, so nobody was let in. It is on this computer's list of devices you let in: remove it there.", never `allowed: true` with `acked: true`.

## What changes
- `engine/remote.js deviceAllow`: when the tunnel answers `account_ack: "unknown_device"` (its ack got a 404, and the entry stands on this computer's list; see the relay plan for why there is no automatic take-back), it returns `{ ok: false, because: <that sentence> }`. server.js already turns a refusal into a 400 with the reason.
- The vouch path (#5786), which calls `deviceAllow` itself, sees a plain refused allow, which it already handles (three tries, then the secret ends).
- The self-grant (#4610, `allowSelfQuietly`) sees the same refusal while the Mac's own sign-in row does not exist yet, and retries about once a minute. Both are reasoned from the code, not driven by a test here.

## Tests
`engine/remote.test.js`: the fake tunnel gains an `allow-unknown` mode that answers as the fixed tunnel does. The new test checks that the allow is a refusal with the sentence. Control: the ordinary answer is still allowed.

## Order
The board half is harmless on its own. Today's tunnel never sends `unknown_device`, so nothing changes until the relay half ships in a Kosmos build.

## Order, the other way
A NEW tunnel with an OLD board prints `acked: false` with `allowed: true`, which the old board shows as allowed (as it does for any not-yet-told allow). The tunnel and the board ship in the same Kosmos build, so that pairing does not happen in a release.
