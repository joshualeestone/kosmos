# Per-model daily token usage, the engine piece (#853)

Josh (in `#chaoskosmos-design`, 25 Aug 08:14): "Could the stats page show daily token usage by model." Mona Lisa wrote the requirement as kosmos#853; the stats page UI itself is explicitly out of scope there and here -- this is the data underneath it: a mechanism that produces an honest per-model, per-day token total, plus an API route so a stats page has something real to call.

## What's wrong with the obvious answer (from #853, confirmed by reading the code)

`readContext` (`engine/status.js:2005`) looks like the field for this and isn't: it reads the LAST `usage` entry in ONE transcript file, so it (a) doesn't accumulate, (b) drops on compaction, (c) never sees forked-subagent transcripts. Confirmed directly against this repo's own code, not just Splinter's card.

## The real data model, verified against live transcripts, not assumed

- `engine/status.js`'s `configRoots()` already discovers every `~/.claude*` directory with a `projects/` subfolder (not a hardcoded list -- a future fourth account root is found automatically). Reusing it directly rather than re-deriving root discovery, which the codebase already treats as its worst-shipped defect ("a private second reader... is the most-shipped defect in this codebase" -- `status.js`'s own comment on `readModel`).
- Each config root has `projects/<project-dir>/<sessionId>.jsonl` (the main session transcript) as a FILE, and, when that session used the Agent/Task tool, a SIBLING DIRECTORY `projects/<project-dir>/<sessionId>/subagents/agent-<hash>.jsonl` (one file per forked subagent) plus a `.meta.json` sidecar (agentType/description/spawnDepth, no usage data -- has to come from the transcript itself). `spawnDepth` implies subagents can nest, so the subagents/ walk needs to be recursive, not one level.
- A usage-carrying row: top-level `timestamp` (ISO8601 UTC), `isSidechain` (true for subagent rows), `sessionId`; `message.model` (e.g. `claude-sonnet-5`), `message.usage` with `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` at the TOP of the usage object, but the object also nests `output_tokens_details`, `cache_creation`, `iterations` -- confirmed by reading a real row. `readContext`'s existing extraction is a non-greedy regex (`"usage":\{([^}]*)\}`) that happens to still work for ITS three fields only because they appear before the first nested `}`, but it is not safe to reuse for a system that needs the full row reliably -- this uses `JSON.parse` per line instead.
- Synthetic rows (Claude Code's own `"model":"<synthetic>"` placeholder, e.g. a usage-limit notice) carry a `usage` object that is not the agent's own -- `readContext` already excludes these by regex on the raw line; matched here the same way, not re-derived.

## Design

**Splinter's one hard constraint, from the HEADS-UP**: store `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` SEPARATELY, never pre-summed into one blended total. Measured today: real work 277M, cache reads 18.2B -- a blended total is off by ~66x and looks plausible on sight, which is worse than an obviously-wrong number. The four buckets travel together through every layer of this; nothing sums them until a caller (the eventual stats page, not this code) explicitly chooses to and can say what it summed.

**Shape**: `engine/usage.js`, new module.
- `walkTranscripts()`: for every root in `status.configRoots()`, every `<sessionId>.jsonl` under `projects/*/`, plus a recursive walk of any sibling `<sessionId>/subagents/**/*.jsonl`. Explicit root enumeration (via the existing, already-tested `configRoots()`), never a hardcoded list -- Splinter's own three-config-dir miss from tonight, avoided by reusing the function that already doesn't have that bug rather than writing a second one that could.
- `scanUsage({ since, until })`: reads every matching file, line by line, `JSON.parse` per line (skip unparsable lines rather than aborting the whole file -- a transcript can be mid-write), skips synthetic-model rows, and for every row with `message.usage` buckets it by (UTC calendar day derived from `timestamp`, `message.model`), accumulating the four fields separately. Returns `{ [date]: { [model]: { input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, rows } } }`. `rows` (a count) travels too, so a caller can sanity-check a day against Splinter's own manual-sweep style verification.
- **UTC calendar day, explicitly, not local time.** Transcripts store UTC timestamps; bucketing by UTC is unambiguous and matches the stored data. A stats page wanting Central-time days is a display-layer choice for whoever builds it, not this module's to guess -- documented in the module header so it isn't silently assumed either way.
- Persistence: `store.js`'s `ROOT` pattern (honors `AGENT_WORKFORCE_DATA` for sandboxing, already the established convention). A completed UTC day, once scanned, is frozen to `ROOT/usage/<date>.json` and never rescanned -- transcripts for a past day do not grow. The CURRENT UTC day is always rescanned live (no caching risk of a stale in-progress total). A scan explicitly reports which roots it read, so a route (or a future consumer) can say "N of N config roots" rather than imply completeness it cannot back up -- the same "say what it cannot see" rule #853 asks for at the UI layer, honored here at the API layer so nothing downstream has to invent the caveat.
- Route: `GET /api/usage?days=N` (default a small window, e.g. 7) -- returns the per-day, per-model, per-bucket breakdown plus the roots-read list. No new UI; this is the thing a stats page calls.

## Verification -- done, not just planned

- `engine/usage.test.js`, 12 cases, all against a sandboxed `AGENT_WORKFORCE_CONFIG_ROOT` fixture (`status.test.js`'s own sandboxing pattern): a normal session transcript; a subagent transcript nested under `subagents/`; a nested sub-subagent two levels deep (`spawnDepth` 2); a `.jsonl` in a sibling directory NOT named `subagents/` (`memory/`, matching a real shape this machine carries) correctly excluded; a synthetic-row line (Claude Code's own `"model":"<synthetic>"` placeholder) correctly excluded; a day-boundary row at `23:59:59.999Z` vs `00:00:00.000Z` the next day landing in the right UTC day each; a malformed/truncated JSONL line that does not abort the rest of the file; the four buckets staying separate through a fixture whose cache-read count would look absurd if blended (mirroring today's real ~66x gap); a past day freezing to disk and NOT being rescanned (proven by deleting the source transcript and confirming the cached number survives); `rootsRead` reported on every call, cached or not; an absurdly large `days` value clamped, not a crash; the scan yielding to the event loop during a large multi-file run (a real, discriminating measurement -- see below). All 12 pass.
- **Found and fixed two real bugs while writing the tests, not after**:
  1. An "absurdly wide" `days` value (`1e9`, meant as a stress case) overflowed `Date`'s own valid range and threw `RangeError` out of `toISOString()` inside `dailyUsageByModel` -- a real crash an HTTP caller passing `?days=999999999999` would hit. Fixed with an explicit clamp (`MAX_DAYS = 3650`, ~10 years) inside `dailyUsageByModel` itself, not left to callers to validate; pinned with a dedicated test.
  2. Found in challenge-loop review (iteration 2), not by me first: the whole read path used `fs.*Sync`, blocking Node's single event loop for a scan's full duration -- every other route on this server would stall while `/api/usage` was in flight. Fixed by converting the entire read path to `fs.promises`. The regression test for this went through two real, verified iterations of its own: a first version routed through a real HTTP `fetch()` and passed even against a fully `fs.*Sync`-reverted copy of the code (the socket round-trip alone gave a 1ms timer enough chances to fire, regardless of the handler's own blocking) -- caught by deliberately reverting the code and confirming the test still passed when it should not have. Rewritten to call the function directly (no HTTP layer): the same sync-reverted copy then correctly showed 0 timer ticks over 19ms, against dozens of ticks for the real async code over a comparable window -- a genuinely discriminating measurement, not an assertion on source text.
- **Cross-checked against Splinter's own manual sweep**, a real, already-measured control this code did not have to invent: his sweep (mid-morning) reported `claude-opus-4-8` output tokens at exactly `1,057,095`; running the real (unsandboxed) `scanUsage` against the live transcripts hours later returned the identical `1,057,095` for that model -- exact match, consistent with no new `opus-4-8` activity since his sweep. The other three models were all higher than his numbers by a plausible amount (more real work happened in the intervening hours), and `rootsRead` correctly named all three config directories (`~/.claude`, `~/.claude-account-b`, `~/.claude-account-c`) unprompted, matching his three-root finding without being told to look for it.
- `server.usage.test.js`, 2 cases against a fully sandboxed in-process server (`start(0)` + `fetch`, the lightweight pattern `server.manifest.test.js` already uses): the route returns the four buckets unblended with `rootsRead` present; a non-numeric and an absurdly large `?days=` both return 200, not a crash. Deliberately thin -- the scan/bucketing logic (including the event-loop-yield property) is `engine/usage.test.js`'s job; a second, redundant reader of the same question at the route layer is exactly the class of drift this codebase's own comments call its worst-shipped habit, and, concretely, a first attempt at exactly that redundancy (an HTTP-level version of the yield test) is the one that turned out not to discriminate anything.
- Full suite: `node --test engine/*.test.js *.test.js` -- **2091 passed, 0 failed** (was 2079 before this card; +12 new). No existing test touched or modified. Full `bash tools/run-tests.sh` (the repo's canonical pre-PR validation, run via `validation_log_run_or_skip`) also passes clean.
