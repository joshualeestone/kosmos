# skills-sandbox-3801: seal fixture boards off the host's real global skills

Issue: kosmos #3801 (found by Sonya Blade during #718 Settings screenshots; confirmed and assigned to Raiden by Liu Kang).

## Problem
`engine/skills.js` `globalDir()` returned `AGENT_WORKFORCE_SKILLS_DIR || os.homedir()/.claude/skills`.
`docs/browser-checks/lib-sandbox-home.js` (#3675) seals the Kosmos home and Claude config but never
set `AGENT_WORKFORCE_SKILLS_DIR`, and deliberately leaves `HOME` alone. So a fixture board:
- listed the Mac's real skills in Settings (73 on Mortals), which screenshots carry into PRs (#3675's leak by another route);
- could delete a real skill through `DELETE /api/skills/:key` (`fs.rmSync` recursive) from the folder every agent loads.

## Done looks like
A fixture board, however it is booted (lib-sandbox-home, tools/browser-checks.sh, or neither),
lists no host skills and cannot add to or remove from `~/.claude/skills`; a real (non-fixture) board is unchanged.

## Change
1. `lib-sandbox-home.js` names a fresh empty skills folder unless the caller named one other than the real folder. Same for the projects root (`AGENT_WORKFORCE_PROJECTS`), which has the same fallback to the real `~/Kosmos/Projects`.
2. `tools/browser-checks.sh` exports `$RUN_DIR/skills` for the boards it boots itself.
3. `engine/skills.js` refuses the real folder to any process whose data dir is in temp but whose home is real (`status.sandboxIsInconsistent()`, the guard status.js already uses for config roots). Belt and braces for a harness that uses neither.

## Rejected
- Changing the fallback to live under `AGENT_WORKFORCE_HOME`: breaks every real install, whose skills really are in `~/.claude/skills`.
- Only the lib line: a harness that does not require the lib would still reach the real folder.

## Tests
`tools.browser-checks-skills-3801.test.js`: fixture lists empty, Add lands in the sandbox and the real folder's mtime is unchanged, Remove cannot touch the real folder; CONTROL boots a non-fixture board and shows list/remove still work. Removing each seal reds only its own test.

## Sweep of other os.homedir() fallbacks in engine/
status.js config roots and discover.js already use the same guard; trust.js's unguarded `SETTINGS(null)` is unreachable (callers pass `agentDefaultAccount = !configDir`); projects.js is now covered by the lib (and server.js #634 already refuses a board without it); the rest are read-only app/install paths or win32 only.

## Weakest part
The engine guard depends on `sandboxIsInconsistent()` staying a correct fixture detector; if that heuristic changes, the third seal changes with it. The lib and runner seals do not depend on it.
