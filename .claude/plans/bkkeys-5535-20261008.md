# bkkeys-5535: E0.6 (#5535) the pure half of the backup KEYS

## Why
The walker cannot start without keys. backupformat.js seals each chunk to a member backup PUBLIC key and names it
with a per-period naming key, and restore (#5536) opens with the member PRIVATE key; nothing yet creates, wraps or
recovers either. Design v2.1 on #5535 (Keys section) fixes the model; this is its pure half: no I/O, no storage,
no coordinator, built on engine/hpke.js like backupformat.js.

## Change: `engine/backupkeys.js`
- **`newMemberKey()`**: a fresh member backup key pair `{ sk, pk }` (raw 32-byte X25519 halves, hpkeKeyPair).
- **`wrapMemberKey(memberSk, recipientPk, ctx)`** -> `KBK1 | enc(32) | ct`. HPKE base mode to ONE X25519 public
  key, info `kosmos-backup v1 key-wrap`, associated data = the member-key context (org, member, epoch). One form
  for all three uses in v2.1: to the org public key (escrow), to the member's enrolled device sealing key
  (self-restore), and the unwrap service's re-seal to a restore destination (restorerequest.js fingerprints that
  same raw 32-byte key). Throws on a caller mistake (sizes, context, a non-canonical recipient key: hpke refuses it).
- **`unwrapMemberKey(recipientSk, wrapped, ctx, expectedPk)`** -> the member sk, or null on ANY failure. Never
  throws. `expectedPk` is REQUIRED: the unwrapped key must derive to it, so a wrap of the wrong key (a wrapper bug,
  a stale epoch's key under the right context) is refused rather than restoring to the wrong place.
- **`newNamingKey()`**: 32 random bytes per period, wrapped to the member key so it is recoverable after the Mac is
  lost. A deliberate departure from v2.1's wording "derived per period": the Mac never holds the member PRIVATE key
  (it backs up with the public key alone), so it has nothing to derive from (review 7).
- **`wrapNamingKey(namingKey, memberPk, ctx)`** -> `KBN1 | enc | ct`, same info, associated
  data = the naming-key context (org, member, epoch, period).
- **`unwrapNamingKey(memberSk, wrapped, ctx, expectedId)`** -> the naming key or null; never throws. `expectedId` is
  REQUIRED (review 4): the key's `namingKeyId` must equal the id the signed manifest records, so a forged naming key
  is refused outright and only the manifest's key opens among a period's wraps.
- Domain separation: distinct magic and a context line that names its kind, so a member-key wrap can never be
  opened as a naming key or the reverse. (A separate HPKE info per kind was dropped: a mutant showed the kind line
  already decides it, so the second separator could not be tested.)
- Wraps are NOT authenticated (HPKE base mode): anyone with a public key can make one. So each unwrap is anchored to
  a value from an authenticated source, never from storage beside the wrap (reviews 5 and 6): `expectedPk` from the
  coordinator-signed policy bundle, `expectedId` from the device-signed manifest. Both are REQUIRED. A forged member
  key does not derive to `expectedPk`; a forged naming key cannot have the manifest's id, so it is refused outright
  (review 7: an earlier version of this paragraph still called chunk-name verification the defence). A wrapped
  secret must also be exactly 32 bytes. unwrapNamingKey is for RESTORE only, and restore must take every chunk NAME
  from the signed manifest too. A Mac never unwraps a naming key to name NEW chunks (a forged one would make those
  names predictable to the forger); a Mac that lost its naming key mid-period makes a fresh one, losing only dedup in
  that period, so a period can hold more than one naming key and each manifest records `namingKeyId(nk)` (a
  domain-tagged SHA-256, first 16 bytes); no context field was added, so the pinned bytes stay (review 3). If a
  stored wrap is ever reused for new data it first needs an authenticator (review 2).
- Context ids use backupformat's alphabet (letters, digits, `. _ : -`, 1 to 128): a lone surrogate or a newline
  cannot make two contexts share bytes.

## Deferred, with reasons
- An expected public key on WRAP (review 8, "a design call, not a defect"): the caller generates the pair moments
  before it wraps, and unwrapMemberKey's required expectedPk refuses a mismatch at the one place a wrong key would be
  used. Reconsider if wrapping ever happens far from key generation.
- Returning a clamped (canonical) secret from unwrapMemberKey (reviews 7 and 8): it would make the returned bytes
  differ from the wrapped ones; instead the function's own doc states the contract (compare public keys).
- publicKeyOf duplicates hpke.js's privFromRaw (reviews 2, 3, 5): exporting one helper means editing reviewed hpke.js.
- wrap() tells hpke's non-canonical error from others by its text (review 8): coupled to that wording, safe either
  way (both are refusals), and a test pins the sentence.

## Not in this change
Storage of the keys and wraps; the org key pair and escrow (coordinator / unwrap service); delivery of the member
public key in the coordinator-signed policy bundle (decision 7); rotation (new epoch) policy; the walker.

## Decisions
- One wrap form for escrow, device and destination (rejected: a separate format per recipient; the unwrap service
  would need three openers and the destination re-seal is the same operation).
- `expectedPk` required on unwrap (rejected: optional; an optional check is a skipped check).
- Weakest premise: the unwrap service (#5536 / Ice Cream Kitty) opens member-key wraps with exactly these bytes.
  Asked on #5535 to object before merge; the associated data is pinned, and known-answer wraps for BOTH kinds (hpke's
  vector seams: fixed keys and ephemeral) pin whole wraps end to end (review 6 asked for the naming one).
