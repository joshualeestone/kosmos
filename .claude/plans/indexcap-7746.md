# indexcap-7746: the rest of kosmos#7746 (items 2 to 5), stacked on topplan-7746

## Item 2: a company's index cap
backupstate capped every index at 600,000 (the top plan), while a company's allowance is 200,000. Now backupsnapshot exports indexCapFor(planGb), the one formula its own chunkCap uses, and backuprun passes it to withRun as maxIndex (never above MAX_INDEX), at the checkpoint and after the run.
Measured: a company run reporting 200,005 rows keeps 200,000 and says leftOut 5; red when backuprun passes no cap.
Weakest premise: that the coordinator's company allowance stays 200,000. It is one constant (CHUNK_ALLOWANCE), so a change there moves both limits together.

## Item 4: a malformed backupWeeklyGb
The coordinator sends null or one of BACKUP_PLAN_GB (kosmos-relay coordinator/src/db.rs set_backup_weekly_gb refuses anything else, org.rs sends it only for a personal org). A value in any other shape fell through to undefined, the same as an older Kosmos+ that does not send it, and the run went on under the company bound with no word said.
Decided: a field that is present but not null or a positive whole number makes that run wait for the next try, with its own fixed sentence. It carries `planUnreadable`, which the panel turns into its own sentence ("Updating Kosmos may fix it"): version skew is persistent, so the person is told rather than seeing an ageing last backup. An absent field behaves as before.
Measured: '25', 2.5, -1, 0, {} and true each wait without running; red with the old fallback.
Rejected: stopping until a person acts. A bad value is a version skew or a fault. What actually happens next (reasoned from backuptick.js, not tested here): the result carries no personActs and no pair, so the backup tick backs off, doubling from an hour to a day, as it does for any refusal before Kosmos+ names the company; a lasting version mismatch is then asked about once a day, and the panel's sentence tells the person that updating Kosmos may fix it.

## Item 5: a checkpoint that fails is invisible
Each checkpoint write that throws is counted, and the run's answer carries `checkpointsLost` when any was lost (nothing when none). The run still never stops for one, as before: a lost checkpoint only loses what a kill would have lost.
Measured: two failing checkpoints give checkpointsLost 2; none give no field; red without the count.
It also rides the answer of a second pass (a granted week) whose state write failed after the first pass's checkpoints (reasoned; that path is not separately tested). Not done here: the panel showing it (personalbackup's note picks fixed sentences per flag); that is the screen's step.

## Item 3: a folder that can never finish re-walks hourly
A plan's run that stopped on the measured manifest size had uploaded chunks first. Within a week the index made the hourly repeats cheap, but each new week uploaded everything again and stopped again, spending the allowance with no snapshot.
Decided: the stop names its listing and what it was measured under (`measuredStop: { files, bytes, budget, at, roots, period }`), backuprun keeps it in the state file beside the job (not per period, since the manifest limit is the same in every week and every plan), and hands it to the next run as `priorStop`. A run whose listing is at least as large in both files and bytes, under the same manifest budget, stops before anything is uploaded (`stoppedBefore`, with personActs and its own sentence). Smaller in either, or another budget, it tries. A run that finishes forgets the stop. An early stop measured nothing, so it names no stop and the kept one stays as it was (it never climbs to a larger listing); a stop measured on a smaller listing replaces it, since it follows the latest measurement. The stop also records which folders it was measured on (a 16-hex hash of their sorted paths), so another set of folders of the same size is tried. A stop dated after now (a clock that was ahead) counts as expired. A kept stop older than 28 days is not handed on, so one real attempt measures again. Stated plainly, both ways: a right stop costs one spent attempt in 28 days instead of one a week; a WRONG stop (the estimate counts keys not yet granted at a fixed length, and skips and redactions vary between runs) holds every run for up to 28 days, with the person told to move files out. The early stop applies only in a later week than the stop's (it records its week): within its own week the repeat is cheap (the index) and may even fit (stored chunks charged at their real key length), so it goes on, exactly as before this change; the spend this item is about happens at a new week. Only a stop kept before the run is handed on, so a second pass in a granted week is never stopped by the stop its first pass just measured; and "later" is by week order, not merely a different week. Accepted gaps: a run that finishes but cannot write its state leaves the old stop in the file, so a later week whose listing has grown back to the stop's size is stopped without a try (needs a failed state write plus a shrink and a regrowth; bounded by the 28 days); near Monday 00:00, with this clock already in the next week while the coordinator is not, the first pass is labelled with the next week and an unchanged listing is stopped before it asks for a grant, so it never reaches the granted-week retry inside the stop's own week (one skipped attempt during the skew window, the person told "did not try again"); a later-week attempt that fails for another reason (no answer, a refusal) leaves the old stop in place, so the next run no smaller is stopped again until 28 days pass; and the 28 days run from the last measurement, which is refreshed while the stop is measured again within its week. Every tooManyPieces() call is a measured-size stop (the per-file check and the backstop after the walk), so every measuredStop is one. The person's sentence says it: move files out and it tries at the next backup, otherwise within four weeks. Rejected: a shorter window, which re-spends the allowance about as often as before this change. The early stop runs after the plan's own checks, so a person over their plan is told that, not this.
Measured: the same listing stops with zero batches and names no stop; a stop with more files than the listing lets it try; another budget lets it try; kept, unchanged by an early stop, handed on and forgotten through backuprun; a stop past 28 days is not handed on; a malformed stop in the file is dropped. Each red without its part.
Rejected: remembering it for the period only, which spends a week's allowance every week (what the card describes).
Weakest premise: that files and bytes no smaller means pieces no fewer. A person who replaces many small files with fewer large ones of the same total keeps the file count only if they add files elsewhere; the comparison needs BOTH to be no smaller, so most real tidy-ups get a fresh try.
