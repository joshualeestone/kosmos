# grokuse-6176: a Grok subscription's usage on its account row (kosmos#6176 slice 3)

## Why
#6176 asks for usage at a glance for every provider. Claude (weekly, five-hour) and ChatGPT sign-ins (Codex's own
limits) are built and served. Left: Gemini and Grok. A read-only survey of the tools on this computer (report kept
locally) found: a Grok subscription logs its own billing reads; a Gemini subscription (Antigravity) has a usage command
that is not yet measured; an API key for either has no source of limits at all.

## Change
- `engine/groklimits.js`: reads `<account folder>/logs/unified.jsonl` (Grok's own log) from the end, 256 KB, then 1 MB,
  then 4 MB while no reading is found (measured: the last 09-29 reading sits about 355 KB from the end of a 1.5 MB
  log; the 4 MB step is headroom). Takes the
  newest line `msg: "billing: fetched credits config"` with `ctx.config.creditUsagePercent` and
  `ctx.config.currentPeriod {start, end}`. Only a reading logged since the folder's current grok.com sign-in began
  counts (`signedInSince`: the login is the hashed auth.x.ai entry keys and user_id, its start recorded in
  `grok-signins.json` so a token refresh does not move it): a folder signed in again, or reused, keeps the earlier
  login's log. Returns codexlimits.read's shape `{ windows: [{ usedPct, windowMinutes,
  resetsAt }], plan, at }`, or null (no log, no reading, or its period is over). A line of another shape is skipped.
- `server.js` GET /api/accounts: a Grok row (provider xai) with authMode subscription gets `limits` from its own
  folder; an API-key row gets none.
- `web/index.html`: `acctLimitsUsageHtml(a, who, none)` draws a provider's own limit reports; `acctCodexUsageHtml`
  calls it as before and the new `acctGrokUsageHtml` calls it for xai rows ("Grok last reported it", and its own
  no-reading line).

## Known limits
- Only the account's own folder is read. That is where every Grok agent logs today: the supervisor runs Grok with
  GROK_HOME set to the account folder.
- Grok does not log a billing read every session (none on this computer after 09-29 though Grok ran later), so a row
  can show no reading while the account is in use. The no-reading line says when Grok reports it.
- The line's shape is Grok's, not a published format. A billing line with no percent is 0% (review 3: protobuf JSON
  leaves out a zero). An ASSUMPTION from one sample (review 4): the only two such lines come late in a period before
  the account's first use, and the next period's first line read 1.0. The weakest premise in this change: if Grok
  dropped the field for another reason, the row would show 0%. A line with no valid period, or a
  percent that is not a number, is skipped, so after a shape change the row shows the last good reading, with its age, until its period ends; never a figure
  read from a line it does not understand.
- First sight on an existing install: the sign-in's start is taken as auth.json's time, which a token refresh moves
  forward, so an older reading in the same period is hidden until Grok logs a new one. Hidden, never wrong (the same
  rule as Codex).
- A signed-out subscription still shows its last reading in its period, with its age, as Codex rows do. Deferred:
  the reading is still that account's usage.
- The newest reading is kept per log file with its inode and size: an unchanged log is not read, a log that grew has
  only its new bytes read (16 KB overlap for a half-written line), a replaced or shorter log is read again (review 2, 3); a read that fails is not kept (review 4).
  Deferred: a log truncated and rewritten past its old size on the same inode between two reads would be read only
  from the old size; Grok's log is append-only.
- Deferred: auth.x.ai entries carry a `create_time` field that might be a truer sign-in start than auth.json's time on
  first sight. Unmeasured whether a token refresh keeps it, so it is not used.
- Not in this slice: Gemini on a Google subscription (needs one measured run of `agy -p "/usage" --output-format
  json` first); API keys for Gemini or Grok (no source of limits; token totals are already shown, #5158).
