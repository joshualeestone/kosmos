# cutroot-2724: give the cut an empty home so its gates stop reading the live fleet

Card: #2724. Branch: `cutroot-2724`. Author: April. Date: 2026-09-10.

## The class

`tools/release.sh` runs on a box that is also running real agents and carrying a
live board, roster and data root. Several cut-time gates read that live state
instead of the tree they froze, so a cut reds on what the machine happens to be
doing rather than on what it is about to ship.

Each instance has been fixed as a one-off (#2259 the block-delivery harness
reading the real `you.json`; #2124 the install-gate running-app dedup; the
`fleet.install` created-agents leak near #2696; #2718 the paneless-beat leak).
They keep arriving because the list is open-ended: **any new gate that reads the
store is a new instance**, and it only ever shows up on the box that carries live
state, never on a quiet dev box.

## What I built

One line of real behaviour: `release.sh` exports `AGENT_WORKFORCE_HOME` at an
empty, recreated-per-cut root before any gate runs. Every gate subprocess
inherits it, including `kosmos_isolation_rerun_verdict`, which matters more than
it looks: the contention rerun has to adjudicate the same world the gate ran in,
or it is comparing two different machines and its verdict means nothing.

## The decision that took the measuring: HOME, not DATA

The card proposes "at minimum an `AGENT_WORKFORCE_DATA` pointing at an empty
root". **Measured, whole suite, empty root, same tree:**

| arm | result |
|---|---|
| no override (CONTROL) | **5930 tests, 5930 pass, 0 fail** |
| `AGENT_WORKFORCE_DATA=<empty>` | **20 fail** (and a different test count, 5923) |
| `AGENT_WORKFORCE_HOME=<empty>` | **9 fail**, same test count (5930) |
| `AGENT_WORKFORCE_HOME=<empty>` + the four test fixes below | **5930 pass, 0 fail** |

`DATA` fails for two independent reasons, and both are structural rather than
incidental:

1. **It is one of the four dirs in `engine/sandbox.js`'s #634 all-or-nothing
   rule** (`DATA`, `PROJECTS`, `WORKERS`, `LAUNCH`, plus an inert tmux). Setting
   exactly one of them is the precise half-sandboxed shape that card was filed
   about, after a fixture board with two of five knobs set typed into two real
   agents' terminals and rewrote two real workers' `CLAUDE.md`. Two of the 20
   failures are that guard refusing by name. **The card's "minimum" option is not
   a smaller version of the fix; it is the shape the repo already refuses.**
2. **It breaks tests that were already isolating correctly.** A large group of
   discovery tests (#1159, #2243) sandbox themselves *through*
   `AGENT_WORKFORCE_HOME` and derive their data root from it. An ambient `DATA`
   overrides that derivation (`DATA` beats `HOME` by design in
   `store.dataRootFor`), handing them a root inconsistent with their own fixture.

`HOME` is the seam the repo already built for exactly this. `engine/store.js`
(#1780), verbatim: *"one var (HOME) isolates BOTH this store and the workers root
(`create.homeDir`)"*. It sits **below** `DATA` in precedence, so a test that sets
its own `DATA` still wins: this changes the ambient default without overriding
anybody's deliberate sandbox. And it is not one of the #634 four, so it cannot
trip the half-sandbox refusal.

## The finding I did not expect, and it is the best instance on the card

**Five of the nine `HOME` failures were tests that passed only because the
operator is signed in to Claude on this box.** With an empty home:

```
"there is no Claude account signed in on this computer, so an agent created
 on Claude could not run."        actual: 400, expected: 200
```

`server.test.js` and `server.projects.test.js` both seal `$HOME` and seed a
`.claude.json` into it, but never set `AGENT_WORKFORCE_HOME`. Since `accounts.js`
resolves `AGENT_WORKFORCE_HOME || os.homedir()`, an ambient value sends the
account lookup straight past their own fixture.

⭐ **That is not a new rule I am inventing. `engine/create.no-account-2145.test.js`
already states it in so many words: "Seals `AGENT_WORKFORCE_HOME` and the codex
roots BEFORE requiring anything, the suite rule: an unsealed home reads the
operator's real accounts."** The rule existed; these files did not follow it; and
nobody could tell, because on this machine the operator *is* signed in. So the
cut's suite has partly been passing on who is logged in.

⇒ **The change is better understood as an enforcement mechanism for a rule the
repo already has than as a new isolation feature.**

The other two failures are controls that assert the *unsandboxed* default while
depending on ambient environment to supply it. They now control both seams
explicitly, which strengthens them: each previously passed by luck of the
environment rather than by construction.

## Why the test drives a child process

The property that matters is **not** that `release.sh` contains a line. It is
that the variable is **exported**, so a gate child sees it, and exported **before**
the gates run. A source grep for `AGENT_WORKFORCE_HOME=` passes on a bare
assignment no child can ever see, and on a line moved below the suite gate that
isolates nothing. **Both of those are the defect**, so the arms drive the real
script with a fake `git` earliest on PATH that prints what the child sees.

Four mutants, each applied alone with a green control either side:

| mutant | result |
|---|---|
| drop `export` (assignment only) | 4/6, kills the child arm and the ordering arm |
| do not wipe a pre-existing cut home | 5/6, kills only the leftover arm |
| point the cut home at the real `$HOME` | 2/6, kills four arms |
| ignore `KOSMOS_CUT_LIVE_HOME` | 5/6, kills only the opt-out arm |

## The trap this file walked into, worth the next person's two minutes

**The six arms passed standalone and failed two-of-six inside the full suite.** That
is the exact shape that gets waved away as contention on this shared box, and it was
not contention.

`release.sh`'s live-cut guard asks `pgrep` whether a `bash tools/release.sh` is
running. `tools.release-gate.test.js` spawns its own sandbox copies of `release.sh`
concurrently, so my arms saw them and refused.

⭐ **That file never trips the guard itself, and the reason is the interesting part:
every refusal it asserts happens at the version gate, which is ABOVE the line where
the guard is even sourced.** So the hazard is invisible until somebody writes an arm
that drives the script FURTHER, which is exactly what this file is. A second one of
these is now likely, so it is written down here rather than rediscovered.

Two related facts found the same way, both of which cost a red run before they were
understood:

- **The sandbox must copy `tools/lib`.** `tools.release-gate.test.js` copies only
  `release.sh` and is correct to, because it never reaches the sourcing. Under
  `set -e` a missing `source` kills the run at that line, so an arm about anything
  late silently asserts on a script that already died.
- **Copying the libs makes `kosmos_claim_machine` real.** With `HOME` sandboxed the
  claim lands inside the fixture rather than the operator's marker directory, so this
  does not leak; it is worth knowing before someone sandboxes a run without `HOME`.

Pinned to `cut-guard.sh`'s own documented seam (`KOSMOS_CUT_PROBE`, *"so the guard can
be shown red and green without a cut"*) rather than the `KOSMOS_HARNESS_IGNORE_CUT`
bypass: **the seam exercises the real self-exclusion logic; the flag skips it.**

## Alternatives rejected

**The separate macOS user.** This is the card's headline proposal and it is the
more complete answer. It needs a new user, keychain access for the Developer ID
identity, notarization credentials, and a console Aqua session for codesign, and
its acceptance ("a staging cut under the isolated user is green") cannot be
checked without running a cut. That is the release gate and an operator, so it is
not mine to verify tonight. **I built the half that is verifiable from here and
have said plainly what remains.**

**Setting all four #634 dirs plus a tmux stub.** The complete env-var isolation.
Rejected for this change because it is a materially larger blast radius and needs
its own measurement, and because the HOME lever already covers every instance the
card actually lists. Named as the next step rather than half-done.

**A fresh `mktemp -d` per cut instead of a fixed leaf.** Rejected: a fixed leaf
under `TMPDIR` leaves a failed cut's home behind to inspect and cannot accumulate.
The cost is that it must be wiped at the start of each cut, which is its own test
arm, because a leftover from the previous cut is the same leak one cut removed.

## Why `AGENT_WORKFORCE_HOME` and not `HOME` itself, which is the other obvious lever

Moving `$HOME` would isolate strictly more. It would also **break the cut's own
mutual-exclusion guards**, which is a worse failure than the one being fixed.

Measured: `$HOME` inside `release.sh` and `tools/lib/*.sh` resolves the run-marker
directory (`$HOME/.cache/kosmos-run-markers`), the cut audit trail
(`$HOME/.claude/logs/cut-suite-runs.log`), the browser-run log, and the default site
checkout (`$HOME/work/chaoskosmos-site`). Point `$HOME` at a scratch dir and:

- two concurrent cuts stop seeing each other's markers, so the #708 live-cut guard
  silently stops guarding;
- a red cut leaves no record, because the audit line is appended under the temp home
  and thrown away with it, and the reds were already the least-recorded events in the
  pipeline;
- the site checkout is not found, so the cut refuses for an unrelated reason.

`AGENT_WORKFORCE_HOME` moves exactly the engine's notion of home and leaves the
shell's alone, which is the split this needs. Verified by grep that neither
`release.sh` nor any lib reads a data root through the `AGENT_WORKFORCE_*` family, so
nothing in the cut's own logic changes.

## On the PROJECTS residual, since it is the one I would attack first

Leaving `PROJECTS` live while `HOME` moves does create an asymmetric state (data root
empty, projects root real), and it is fair to ask whether that is worse than both
being real. Two checks say no:

- `engine/projects.js` contains **no delete operation at all** (no `rmSync`,
  `unlinkSync` or `rmdirSync`), so there is no prune path that could read an empty
  store and act destructively on the real folder.
- After every isolated run tonight, `find ~/Kosmos/Projects -maxdepth 2 -mmin -180`
  returned **nothing**: no entry in the operator's real projects root was created or
  touched.

So this is a gap in coverage rather than a new hazard. It should still be closed by
the full four-plus-tmux sandbox, and it is named in the residuals for that reason.

## Weakest premise in my own reasoning

**That an empty `HOME` is what the cut's gates should see, rather than a
*representative* one.** Every failure I fixed was a test that wanted state which
an empty home does not have. I fixed them by making each supply its own fixture,
which is right. But it means the cut now runs its suite against a home with
nothing in it, and a future gate that legitimately needs a populated home will
fail in a way that looks like this change's fault and will be tempting to "fix"
by setting `KOSMOS_CUT_LIVE_HOME=1`, which silently restores the whole class.

What would change my mind: a gate that genuinely needs real machine state to be
meaningful. I did not find one, but I did not prove there is none.

## What this change actually moves, and what it does not

The heading on the first draft of this plan said the cut's "gates stop reading the live
fleet". **That overclaims, and the correction matters more than the change.** What
`AGENT_WORKFORCE_HOME` moves is the STORE and the ACCOUNTS. The roster and the
discovery scan are untouched. Measured, by reading the resolvers rather than reasoning
about them:

| root | resolver | under this change |
|---|---|---|
| data store | `store.js` `root()` -> `AGENT_WORKFORCE_HOME \|\| os.homedir()` | **moves** |
| workers root | `create.js:227` / `instructions.js:55`, same seam | **moves** |
| Claude accounts | `accounts.js` `homeDir()`, same seam | **moves** (5 accounts -> 0) |
| LaunchAgents **writes** | `create.js:237` `agentsDir()` -> `homeDir()` | **moves** |
| LaunchAgents **reads** | `machine.js:52` / `boardrestart.js:69` -> `process.env.HOME` | **stays** |
| projects root | `projects.js:1384` -> `os.homedir()` | **stays** |
| config-root scan | `status.js:46` `homeDir()` -> `os.homedir()`, never consults the var | **stays** |
| agent roster | `AGENT_WORKFORCE_TMUX_BIN \|\| 'tmux'` (`status.js:294,451`) | **stays** |

### 🛑 Two consequences I would rather state than have found

**1. A cut-time gate can still enumerate the live fleet by name.** The roster comes from
`tmux list-panes -a` and the config roots from the real home; neither consults
`AGENT_WORKFORCE_HOME`. `engine/sandbox.js`'s own #1651 note says this in as many words:
only `AGENT_WORKFORCE_TMUX_BIN` redirects a read. So the class this card names is
**narrowed, not closed**, and the next instance will most likely arrive through the
roster rather than the store.

**2. LaunchAgents now has a writer and a reader that disagree.** `create.js` writes
plists into the cut home while `machine.js` and `boardrestart.js` read the operator's
real `~/Library/LaunchAgents`. Before this change all three resolved to one directory.
The write direction is arguably an improvement; **the disagreement is not**, and it is a
state the codebase has never been in. Not carded as a fix here because making the
readers honour the seam is product-code scope with its own blast radius, but it must not
go unnamed.

**3. It manufactures a combination no real machine can be in:** six discoverable Claude
config roots and zero signed-in accounts. Previously those agreed. `browser-checks.sh`
records that this exact axis has already produced a false green once (the first-run
create painting the FOUND screen whenever the agent scan returns anything).

### And the honest framing of #634

`HOME` moves the data root and the workers root while `PROJECTS`, the LaunchAgents
readers, tmux and the config-root scan stay live. That is the two-of-five shape #634 was
filed about, reached through a variable `sandbox.js`'s `DIRS` does not watch, so
`audit()` returns `partial: false` and the guard cannot see it.

**This change does not break #634. It steps around its premise, on every cut, by
design.** That sentence belongs here rather than the softer "not whole-box isolation",
because the softer version is what stops the next person looking.

### The residual that IS benign, with its evidence

Leaving `PROJECTS` live is safe: `engine/projects.js` contains no delete operation at
all (no `rmSync` / `unlinkSync` / `rmdirSync` / `fs.rm`; its only `renameSync` is the
atomic write of its own temp file), and `find ~/Kosmos/Projects -mmin -180` returned
nothing after every isolated run. That one is a coverage gap, not a hazard.

## Round 1 of the challenge loop, and what it cost me

A blind reviewer found **1 BLOCKER, 4 WARNINGs, 2 NITs**. The BLOCKER is the one worth
recording, because it is this card's own defect turned on the file that asserts the fix.

`tools.cut-home-2724.test.js` built its child env from `...process.env` and never
cleared `AGENT_WORKFORCE_HOME`. **Step 3 of `release.sh` runs `yarn test` WITH that
variable exported**, so on a real cut the file inherits it, the opt-out arm (which
asserts the child saw `<unset>`) reds, the #2006 isolation rerun reproduces it under the
same exported env, it is classified a real red, and **the cut aborts at step 3**.

⭐ **The arithmetic that found it is the transferable part.** The "+ test fixes" arm ran
5930 tests, which is the count WITHOUT the new file. The final arm ran 5936, which is
the count WITHOUT an ambient home. **So the two variables were never set at the same
time, and the one combination that describes a real cut was the one combination never
measured.** A results table with more rows than the thing has states will always have a
hole; the hole is found by counting, not by reading.

Now measured: **5938/5938 under both conditions**, ambient home and none.

The other findings, each confirmed by me before acting on it rather than taken on trust:

- The `rm -rf` guard **could never fire** (the leaf is always appended, so the derived
  path can never equal `/`, `/tmp` or `$HOME`), and it guarded the wrong value:
  `TMPDIR=$HOME` would have made it `rm -rf ~/kosmos-cut-home` and passed. It now asks
  about `TMPDIR` itself and has an arm proving it fires.
- **`browser-checks.sh` was worse than my own correction found.** I had caught that the
  four-var sandbox is per BOARD, not per check. The reviewer found the half I missed:
  **7 of the 9 board boot sites never set `AGENT_WORKFORCE_HOME` at all**, so they read
  the operator's home for accounts. Measured here: `accounts.list()` is 5 ambient and 0
  under an empty home, and `create.js` refuses a Claude create with no default account.
  Step 3b is now explicitly excluded with `env -u`.
- The ordering arm used `indexOf` on a bare substring, which takes the FIRST occurrence
  and could be satisfied by a future comment line above the gate. Now anchored to a
  real statement at start-of-line.

📌 **Seven of my claims about neighbouring code failed to survive re-opening tonight,
across four cards. This is the eighth.** The pattern is stable enough to name: I write
the sentence at the moment I form the belief, and the measurement happens later or not
at all. The repair that works is not "check more", it is **do not write the sentence
until the command has run**.
