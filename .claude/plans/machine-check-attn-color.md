## Change

`web/index.html`, the `.chk.att` icon badge, edited only at its source
(the `@media (prefers-color-scheme: dark)` block) -- the mirrored
`:root[data-theme="dark"]` copy is GENERATED by
`tools/sync-forced-theme.js` and regenerated with that tool, never
hand-edited (learned this in challenge-loop iteration 1 after first
hand-editing the generated section and having to revert it):

- Light (base rule): background `rgba(179,38,30,.13)`, border
  `rgba(179,38,30,.45)`, icon color `#b3261e`.
- Dark (media query source, mirror generated by the sync tool):
  background `rgba(255,140,130,.13)`, border `rgba(255,140,130,.5)`,
  icon color `#ff8c82`.
- `#firstrun`-scoped pin, both forms (media query + generated mirror):
  forces the LIGHT values back even when the OS/data-theme reports dark.
  Required because `#firstrun` pins its own background to white in every
  theme (its own single-look ruling, `FROZEN-2026-08-16`) -- the plain
  dark red measured against that ACTUAL ground comes out to ~2.03:1,
  well under the 3:1 floor, in exactly the screen this fix targets. Caught
  in challenge-loop iteration 1; fixed with the same `#firstrun`-scoped
  re-pin pattern the file already uses for `--label-2`/`--separator`.

Not a new color: this is the exact red pair already used everywhere else
in this file for attention/failed states (`.astate.st-attn`,
`.delivery.failed`, `.acard.attn`, `.onode.attn`) -- reused for
consistency with the rest of the design system rather than inventing a
third red.

## Measured, not assumed

Contrast computed with the exact WCAG relative-luminance formula (linearize
each sRGB channel, `L = 0.2126R + 0.7152G + 0.0722B`, `contrast =
(L_lighter+0.05)/(L_darker+0.05)`), each icon color composited onto its
own 13%-alpha tint over the ground it actually sits on:

| case | ground | contrast |
|---|---|---|
| light, `#b3261e` on 13%-red-tint over `#ffffff` | white | **5.27:1** |
| dark, `#ff8c82` on 13%-red-tint over `#17191c` | dark surface | **6.27:1** |
| dark red on `#firstrun`'s REAL ground (unpinned, the bug) | white | **2.03:1** -- fails |
| dark theme, inside `#firstrun`, after the pin | white | **5.27:1** (same as light) |

The first two clear the 3:1 floor a status glyph needs. The third is the
challenge-loop finding: a plausible-looking dark-mode value that fails in
the one subtree it would actually render in. The fourth is the fix,
verified by a regression-sensor test that fails loudly if the unpinned
value ever legitimately clears 3:1 in the future (meaning the underlying
measurement changed and the pin's own justification needs re-deriving,
not silently deleting).
