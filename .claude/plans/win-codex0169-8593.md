# win-codex0169-8593: the Windows half of kosmos#8593 (Codex pin 0.169.0 reaches existing Windows installs)

**Posture:** production

## Finished looks like
1. The Windows Codex pin is 0.169.0 (x64 and arm64 tarballs, registry sha512, measured on the Windows box), and the
   Windows hook-trust list includes 0.169.0 (the real-Codex 8348 arm passed against it on 2026-11-16).
2. A Windows Codex an older build installed (its `.verified` marker names an older version for the same binary path)
   reads present + stale, not absent, so its agents keep starting.
3. The board's upgrade sweep replaces it on Windows, only while no process runs from the managed folder; a failed
   upgrade puts the previous tree AND its marker back.

## Decision (Homer, 2026-11-17)
- Chosen: on Windows, swap only while nothing runs from `<runners>/openai` (asked by the sweep before a try, and by
  install() just before the swap; an unreadable answer counts as running).
- Rejected: porting engine/runnerrestart.js (#8598) to Windows. It reads tmux panes and `ps`, neither of which Windows
  agents have; a Windows port is its own card.
- Rejected: Windows upgrades with agents running. Measured: Windows lets the folder be renamed under a running exe, so a
  running 0.149.1 Codex would start its code-mode host from the new tree, the #8598 failure.
- How Windows agents run (corrected in review 6): a Windows Codex agent runs one `codex exec [resume <thread>]` per
  turn (engine/win32codex.js codexTurnArgs), not a long-lived process. So "nothing running" holds between turns, the
  swap normally lands between two turns of a live conversation, and only a turn in flight can block it. An earlier
  draft said "a box whose agents never stop never upgrades": that was wrong for Windows.
- What that means, and what was measured (2026-11-17, the real 0.169.0 win32-x64 codex.exe, an empty CODEX_HOME):
  0.169.0 accepts every argument Kosmos passes per turn (`-c project_doc_max_bytes=...`, `exec`, `resume <id>`,
  `--json`, `--skip-git-repo-check`, `-m`, `--dangerously-bypass-approvals-and-sandbox`); a fresh turn goes on to
  read its prompt and a resume goes on to look up the thread ("no rollout found" for an unknown id), so no argument
  is refused. NOT measured: 0.169.0 resuming a thread 0.149.1 wrote. This box has no signed-in Codex and no 0.149.1
  rollouts, so it cannot be made here. It is the same step every Codex user takes when an update lands between two
  `codex resume`s, and the Mac half ships the same cross-version resume. Owed: a live check on the first Windows box
  with a signed-in Codex agent (start on 0.149.1, let the sweep upgrade, send the next turn).
- How a turn is kept off a tree being swapped (review 7): a Windows Codex supervisor resolves codex.exe once and spawns
  it per turn without asking resolveBin, so the marker alone does not stop a turn. install() therefore puts up a swap
  lock (`<runners>/openai/.swapping`) before the marker comes down and takes it down when the job ends either way; the
  supervisor waits on it before each Codex turn (runners.waitForSwap, capped at 3 minutes, a lock older than 15
  minutes is a dead board's and ignored). A last process look runs after the lock is up.
- Weakest part: a turn whose supervisor read the lock as clear in the instant before it was written, and spawned after
  the last look's process snapshot, is not covered (the gap between a file read and a spawn). The not-measured
  cross-version resume above is the other weak point. A wait does not spend one of the sweep's three tries.
- Would change my mind: a measurement that Windows Codex resolves its code-mode host from its load-time path in a
  way that survives the rename (then the running check could go).
