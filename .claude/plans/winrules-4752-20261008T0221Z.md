# winrules-4752: the setup guide's absolute Read rules, in the path form Claude Code matches on Windows

Follow-up to #4752 (closed), from a peer's note. Claude Code's permissions docs: "On Windows, paths are normalized to
POSIX form before matching. C:\Users\alice becomes /c/Users/alice, so use //c/**/.env". The guide's absolute rules
came from `ruleAbs`, which wrote the native spelling (`//C:\Users\...`). That is not a form the docs say is matched,
so on Windows those rules were at best unverified. The `~/` rules are unaffected.

## Change
- `engine/setup-assistant.js` `ruleAbs(p, platform = process.platform)`: on win32, backslashes become `/` and a
  leading drive `C:` becomes `c/`, then the usual `//` prefix: `C:\Users\x` -> `//c/Users/x`. macOS and Linux are
  unchanged (a backslash there is part of a file name). Exported, so the form is pinned from any host.
- Every writer of an absolute rule goes through `ruleAbs`, and `wasEntryRule` builds its prefix with it. The other
  reader, `guardGuideFolder`'s own-folder check, parsed rules back by hand for the old native form, so with the new
  form it would have resolved `c/Users/...` against the current drive and never matched (review 1, BLOCKER). It now
  uses `rulePath`, the exact inverse of `ruleAbs` (it also reads an older native-form rule as it is).
- Which earlier rules stay is now one pure function, `migrateKept(had, fresh, platform)` (review 3: the migration was
  reachable only on a Windows host; `wasEntryRule`/`rulePath` take the platform too, so the Windows answer is pinned
  from any host). `guardGuideFolder` passes the process's own platform, not `deps.platform` (which only its sandbox
  block reads), so a test giving `deps.platform: 'win32'` on macOS still gets POSIX rules. A rule written before this change in the native form (or as `C:/...`) STAYS beside its new-form equivalent
  (review 4: these are deny rules, and the new form rests on Claude Code's docs, not a Windows measurement; a
  duplicate deny costs nothing, a removed working one exposes the file). It is dropped only when its equivalent is
  a per-entry rule for an entry gone from the store just listed in full: nothing is left to protect
  (`legacyWinEquivalent`).
- The deny list written is `finalDeny(kept, safe, refused, platform)`: on Windows a refused rule (one that would take
  in the guide's own folder) is left out in BOTH spellings, since the old one is now kept beside the new (review 5
  BLOCKER: otherwise the old copy of a refused rule stayed and could cut the guide off).
  A person's own rule elsewhere stays; one they wrote by hand in the `C:/` form under the default store, for an
  entry that is gone, is dropped like the rules this code wrote there (it protects nothing any more).
- The path check (`plain`) runs on what `ruleAbs` writes, so both see one spelling; it refuses only rule syntax, on
  every platform, as main does. `ruleAbs` writes the Windows extended-length forms as their
  plain paths, and never a trailing slash (a drive root's folder rule is `//d/**`) (`\\?\C:\...` as `//c/...`, `\\?\UNC\host\share`
  as `//host/share`): the prefix's `?` is a glob character in a rule.
- Follow-up, not a regression: an old-form rule whose path is still made (the data root, the home folders, the
  worlds pattern) stays for as long as that path is written; one for a data root a person later moved stays too,
  as a new-form rule already does on main. A sunset for those (once Windows matching is measured) is its own card.
- Decided, not missed: two spellings of one rule that differ only in case are BOTH kept (review 18): matching may
  be case-sensitive (undocumented), a duplicate deny costs nothing, and folding could drop a person's own rule. The
  case-blind REFUSAL applies to Read rules only.
- `tools/windows-tests.js` judges a file that skips only SOME tests as a pass, so the test file itself fails on a
  win32 host when the Windows-only end-to-end arm did not run (a `test.after` guard, review 21).
- Not handled, recorded (one current list, review 25):
  - `wasEntryRule` matches the store base case-sensitively: if the base is spelt in another case from one start to the
    next, per-entry rules from the earlier spelling are never seen as stale and stay (extra denies only).
  - A share rule written by main (`Read(//\\srv\share\K/**)`) maps to nothing in `legacyWinEquivalent`, so it is kept
    and a later refusal of `//srv/share/K` does not reach it; old per-entry share rules for gone entries also stay.
  - An old rule under an 8.3 short name is not mapped to its long-name new form; an 8.3 short name in a home or
    data-root value is written as given and may not match Claude Code's long-name path.
  - The data-root and home-folder rules do not go through `plain` (as on main): they are written as they are.
  - A rooted path with no drive (`\Users\x`) is written `//Users/x`, which reads like a share (real home and temp
    paths always carry a drive).
  - A one-letter share host (`\\s\share`) is written `//s/share`, also drive S: in the documented form (a small
    over-deny); the own-folder check reads such a rule BOTH ways (`rulePaths`: `S:\share` and `\\s\share`) and refuses
    it if either holds the guide's folder.
  - Per-entry names do not go through `plain`, but `baseEntryToName` refuses a name with rule syntax, so an entry like
    `notes (1).json` gets no rule; a home or data-root path with a bracket or parenthesis gets one as on main.
  - The twins written by guardGuideFolder, and its use of `rulePaths`, are asserted only by the Windows-only arm (the
    guide reads the host's platform), so they are proven on the Windows job, not by a mutation check here.

- On Windows every absolute rule that passes the own-folder check is also written in its old native spelling
  (`withNativeTwins`, review 12; review 14: twins are made after the check, so a refused rule never gets one): a new
  install gets the same belt-and-braces an older one keeps through `migrateKept`; each twin is exactly the old
  writer's spelling, so the migration and `finalDeny` treat it as that rule's old form. A share (`\\host\share`,
  `\\?\UNC\...`) is WRITTEN, as `//host/share/...` (review 21): whether Claude Code matches it is undocumented, an
  extra deny costs nothing, and refusing it left a redirected-profile store's token files with no rule. Review 24: nothing else is
  refused either (as on main): the device form, a drive-relative path, a share root are written as they are; only rule
  syntax refuses (a `\\?\Volume{...}` path, by its braces). `ruleAbs` never maps a bare `C:` to the whole drive. `legacyWinEquivalent` converts the path apart from its suffix, so a
  drive root maps to `//d/**` as written now.
- POSIX change, recorded: `ruleAbs` drops a trailing slash, so a path given with one now gives `//a/b/**` where it
  gave `//a/b//**`; an old doubled-slash rule in a settings file stays as a harmless stale duplicate.

## Tests
`engine/setup-assistant.winrules-4752.test.js` (in `tools/windows-tests.js` ALSO):
- `ruleAbs`: drive paths to `//c/...`, extended-length paths (`\\?\C:`, `\\?\UNC`) as their plain paths (fails on main:
  not exported, native form); macOS and Linux unchanged (control, a backslash in a POSIX name kept).
- `rulePath` reads every written rule back to its exact path, both forms; a drive-less share rule reads back as
  its UNC path on Windows (review 23), and a lone name as nothing (never resolved against the current drive).
- `legacyWinEquivalent` maps an old native-form rule to its exact new-form equivalent, suffixes included.
- `migrateKept` keeps a person's own rules and an old rule whose path is still protected, and drops an old or new
  rule for a gone file or folder entry (Windows), with a no-listing arm and an off-Windows control.
- `finalDeny` leaves a refused rule out in both spellings on Windows (control: unrefused kept; off Windows exact).
- On the host it runs on, no new-form Read rule carries a backslash or a drive colon (the deliberate native twins on Windows excepted) (Windows: in the `//c/` form).
- Windows only, end to end: `guardGuideFolder` leaves out a rule taking in the guide's folder in both spellings,
  says so, keeps a person's own rule, writes the data folder rule in `//c/` form (skips elsewhere).
Not done: running `engine/guide-deny-4752.test.js` on Windows (its expected rules use a POSIX helper).

## Weakest premises
- The native twins are belt-and-braces ONLY if Claude Code reads a backslash literally in a rule; if it reads it as
  an escape (as gitignore-style matching does), a twin matches nothing. Harmless either way (a deny, deduplicated,
  removed with its refused new form); not counted as protection.
- Claude Code's documented normalisation is what the version a person runs does. New rules trust the docs (the
  permissions page: "C:\Users\alice becomes /c/Users/alice"); the drive letter is written lower case as in the docs'
  example, and whether matching is case-blind is not documented. Not measured on a Windows machine here. Old
  native-form rules are kept beside the new ones during migration only as a cheap belt-and-braces (a duplicate deny
  costs nothing), not because the docs are doubted.
- The Windows-only arm must RUN on the Windows job: the test file's `test.after` guard fails it on win32 otherwise
  (tools/windows-tests.js alone would not catch one skipped arm in a file whose other arms run).
- `guardGuideFolder`'s Windows wiring is now run end to end by a Windows-only arm in the new test file (the Windows
  job runs it; it skips elsewhere): a rule taking in the guide's folder is left out in both spellings, a person's
  own rule stays, and the data folder rule is in the `//c/` form. Not run on this Mac: no drive paths here.
