## The one real gap

The card names a contributing cause separately: **a board running in the MAIN CHECKOUT**, which the
worktree rule exists to prevent, "invisible until someone else's tests go red".

The current output prints the cwd and stops there. It says `running from /Users/agent1/work/agent-workforce`
and leaves the reader to recognise that string as the main checkout. **At 4am, reading someone
else's red, nobody does.** That is the difference the card itself draws between "flaky, re-run" and
"something else is using :16180".

## The call

**Classify the board's cwd and say which kind it is**, using the mechanical discriminator rather
than path shape: a main checkout's `.git` is a **directory**, a linked worktree's `.git` is a
**file**. Confirmed on this machine both ways.

- main checkout -> say so, and say it is the thing the worktree rule forbids
- worktree -> say so (this is the normal, fine case)
- not a repo -> unchanged wording (an installed board runs from `$HOME`; that is not a violation)

## What I rejected, and why

- **A hard refusal when any board is listening.** The card floats it. **No.** On a machine where
  ~30 agents work concurrently a board is normally up: one is listening right now. A refusal would
  fail correct work constantly, and a gate that fails correct work is worse than no gate. I pulled
  my own instrument out of CI last night for exactly this. Report beside the red is the right shape.
- **Refusing only when the board is in the main checkout.** Tempting, and still wrong: the board may
  belong to an operator doing something deliberate, and refusing another agent's suite for it
  punishes the wrong session. Name it loudly; let a human decide.
- **Path-shape detection** (`~/work/<repo>` vs `~/work/<repo>-<branch>`). Rejected: it encodes a
  naming convention rather than the actual git fact, and it breaks for any checkout elsewhere.

## Weakest premise

**My first version of this section was WRONG ABOUT THE DIRECTION, and a reviewer built both fixtures
for real rather than reasoning about them.** I claimed a bare repo or a `--separate-git-dir` checkout
"would classify as a main checkout". Measured, both arms, independently reproduced by me:

```
bare repo (git init --bare)        -> UNCLASSIFIED, the raw path
                                      (rev-parse --show-toplevel fails: not in a work tree)
git init --separate-git-dir=...    -> "the worktree <path>"   <- its .git is a FILE
```

So neither becomes a main checkout. The `--separate-git-dir` case fails in the **opposite and worse**
direction: it gets the *reassuring* label, the one this file calls the normal fine case, so a primary
checkout serving a board would be labelled as though it were a worktree and flagged as nothing.

Still accepted rather than fixed: neither form exists on this fleet, and probing for a git layout
nobody uses would add a branch nothing tests. **What would change my mind:** any real checkout here
using `--separate-git-dir`.

**The residual I did NOT anticipate and a reviewer did:** a board's cwd is usually a SUBDIRECTORY of
a checkout, not its root. That one was not exotic, it was the likely real case, and it is fixed
rather than documented.

## 🛑 THE BIGGEST CHANGE THIS LOOP MADE: THE `git` CALL IS GONE AGAIN

Iteration 1 found that testing `$dir/.git` misses a board sitting in a SUBDIRECTORY, so I replaced
it with `git rev-parse --show-toplevel`. **Iteration 3 measured three new failure modes that arrived
with that one call**, every one of them in the place designed to stop a misread:

1. `rev-parse` searches **UPWARD**, so a board merely somewhere under a repo was labelled the MAIN
   CHECKOUT. With a git-managed `$HOME`, an ordinary dotfiles setup, the INSTALLED board would be
   reported as a violation it is not. (Not live on this machine: `$HOME` here is not a repo. Live on
   any machine where it is.)
2. `GIT_WORK_TREE` in the caller's environment made it describe a directory the board is not in.
3. It was the only unbounded probe in `seen_before()` against an arbitrary, possibly remote path.

**So it is reverted to testing the directory it was handed.** The accepted cost is that a
subdirectory is not classified: it prints the bare path, which is what this file printed before #708
and is ALWAYS TRUE. **A label that stays silent beats one that can assert a violation that is not
happening**, and the #708 incident itself was a board at a checkout ROOT, which is where a server is
normally started. There is an arm asserting the limitation so it stays a decision rather than drifting.

⭐ **The general shape, which is this branch's own card looking back at it:** iteration 1's fix
introduced all three, and the honest response was to back the fix out rather than defend it with
three guards. Piling guards on a change is how you end up maintaining the guards.

## The revert did NOT close the $HOME case, and my own comment said it did

Iteration 3's revert removed the false MAIN CHECKOUT label for a board merely somewhere UNDER a
repo. **It did not remove it when `$HOME` IS the repo root**, which is what `git init ~` dotfiles
gives you, and the header comment I wrote to document the revert claimed otherwise. Measured:

```
a git-managed $HOME                     -> "the MAIN CHECKOUT ..."   (before the fix)
the REAL installed board's cwd          -> /Users/agent1  i.e. $HOME
```

⇒ On any fleet machine with dotfiles in git, **every red suite would have accused the installed
board** of the violation #708 exists to name. Not live on this box (`$HOME` here is not a repo), and
that is luck rather than design.

Fixed with a subprocess-free decline when `$dir` is `$HOME`, plus a control arm proving the same
directory still classifies when it is not `$HOME`, so the guard cannot pass because classification
broke generally. Perturbing the decline out reds the arm.

⭐ **This is the third time in this loop that a claim written INSIDE a fix was false about the
behaviour that same fix had just changed**, which is precisely what kosmos#120 describes. The other
two: a header claiming the discriminator keyed on the git fact when it keyed on a path shape, and a
FAIL-OPEN test arm that asserted against a hand-typed copy of the code it claimed to test.

### And the $HOME decline's first version was a string compare

Measured false two ways by the next blind pass: a **symlinked** `$HOME`, and a `$HOME` carrying a
**trailing slash**, each defeating the decline so the installed board was labelled again. The comment
asserted "the caller's cwd comes from lsof in the same spelling", which is not true in general and
was the fourth claim in this loop written inside a fix and false about that fix's own behaviour.

Now `[ "$dir" -ef "$HOME" ]`, comparing device and inode. `-ef` is a `test` builtin, so the function
is still subprocess-free, and it is false when either path is missing, which is the safe direction.
Three arms cover it and reverting to `=` reds two of them.

## The deferral I got wrong, and what falsified it

I deferred bounding the `git` call, reasoning that `lsof -a -p <pid> -d cwd` runs three lines earlier
and would hang on the same wedged mount first, so a bound here "cannot help". **That was wrong, and
it was falsified by the exact measurement I had named as my mind-changer.** `lsof(8)` on this machine
documents `-S [t]`, which bounds `lstat`/`readlink`/`stat` calls "that might otherwise deadlock",
**default fifteen seconds**. lsof is self-bounded; the `git` call was not. The neighbouring `find` is
`-maxdepth 1` over a local `TMPDIR`, so `git` was the only unbounded probe against an arbitrary path.

The resolution is not a bound: removing the call removes the exposure entirely, which is strictly
better than bounding it. But the reasoning I published was unsound before the code changed, and
naming a falsification condition is worth nothing unless it is honoured when somebody meets it.
