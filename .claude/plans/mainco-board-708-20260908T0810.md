## The one real gap

The card names a contributing cause separately: **a board running in the MAIN CHECKOUT**, which the
worktree rule exists to prevent, "invisible until someone else's tests go red".

The current output prints the cwd and stops there. It says `running from /Users/agent1/work/agent-workforce`
and leaves the reader to recognise that string as the main checkout. **At 4am, reading someone
else's red, nobody does.** That is the difference the card itself draws between "flaky, re-run" and
"something else is using :16180".

## The call

**Classify the board's cwd and say which kind it is**, using the mechanical discriminator rather
than path shape: a main checkout's `.git` is a **directory**, a linked worktree's `.git` is a
**file**. Confirmed on this machine both ways.

- main checkout -> say so, and say it is the thing the worktree rule forbids
- worktree -> say so (this is the normal, fine case)
- not a repo -> unchanged wording (an installed board runs from `$HOME`; that is not a violation)

## What I rejected, and why

- **A hard refusal when any board is listening.** The card floats it. **No.** On a machine where
  ~30 agents work concurrently a board is normally up: one is listening right now. A refusal would
  fail correct work constantly, and a gate that fails correct work is worse than no gate. I pulled
  my own instrument out of CI last night for exactly this. Report beside the red is the right shape.
- **Refusing only when the board is in the main checkout.** Tempting, and still wrong: the board may
  belong to an operator doing something deliberate, and refusing another agent's suite for it
  punishes the wrong session. Name it loudly; let a human decide.
- **Path-shape detection** (`~/work/<repo>` vs `~/work/<repo>-<branch>`). Rejected: it encodes a
  naming convention rather than the actual git fact, and it breaks for any checkout elsewhere.

## Weakest premise

**My first version of this section was WRONG ABOUT THE DIRECTION, and a reviewer built both fixtures
for real rather than reasoning about them.** I claimed a bare repo or a `--separate-git-dir` checkout
"would classify as a main checkout". Measured, both arms, independently reproduced by me:

```
bare repo (git init --bare)        -> UNCLASSIFIED, the raw path
                                      (rev-parse --show-toplevel fails: not in a work tree)
git init --separate-git-dir=...    -> "the worktree <path>"   <- its .git is a FILE
```

So neither becomes a main checkout. The `--separate-git-dir` case fails in the **opposite and worse**
direction: it gets the *reassuring* label, the one this file calls the normal fine case, so a primary
checkout serving a board would be labelled as though it were a worktree and flagged as nothing.

Still accepted rather than fixed: neither form exists on this fleet, and probing for a git layout
nobody uses would add a branch nothing tests. **What would change my mind:** any real checkout here
using `--separate-git-dir`.

**The residual I did NOT anticipate and a reviewer did:** a board's cwd is usually a SUBDIRECTORY of
a checkout, not its root. That one was not exotic, it was the likely real case, and it is fixed
rather than documented.

## Deferred, with reasoning

**The `git` call is unbounded and stays unbounded.** On a wedged mount it could hang the pre-PR gate
every agent runs, which is a real concern. Measured before accepting it: this machine has neither
`timeout` nor `gtimeout` (kosmos#2474), and `seen_before()` already runs `lsof -a -p <pid> -d cwd`
against the same path three lines earlier, plus an unbounded `find` over TMPDIR after it. A bound
here would be a visible guard that cannot help, because the call before it reaches the same wedged
mount first. Bounding one of four unbounded probes is the "safety mechanism that does nothing" shape.
**What would change my mind:** a portable bound existing on the fleet, or a measurement showing `git`
blocks where `lsof -d cwd` does not. The right fix is bounding the whole function, a different card.

## Corrections made during the challenge loop

- **The subdirectory case.** The first version tested `$dir/.git` directly, which sees the git fact
  only at the top level, so a board running in `<repo>/engine` fell through to the bare path: exactly
  the output this change exists to replace. It also made the header comment's "keys on the git fact,
  not the path shape" claim FALSE, since testing for `.git` in the directory you were handed **is** a
  path shape. Now `rev-parse --show-toplevel`, which resolves from any depth.
- **The integration was untested.** Every arm called the library directly, so deleting the source
  line or the call in `run-tests.sh` left the suite green with the feature gone (the fail-open path
  is deliberately silent). Two integration arms added.
- **And the first version of one of those arms was itself vacuous:** it grepped the bare name
  `board_origin_label`, which also matches the `command -v` guard one line above the call, so
  deleting the call did not red it. Caught by perturbing the arm rather than by reading it. It now
  matches the call.
- **The residual list was incomplete in two directions:** it named bare repos and
  `--separate-git-dir` but not the subdirectory case (now fixed rather than documented) or a git
  submodule, whose `.git` is also a file.
