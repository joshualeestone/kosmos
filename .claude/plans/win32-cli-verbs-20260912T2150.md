# win32-cli-verbs: every verb Kosmos teaches an agent works on Windows

Branch `win32-cli-verbs`, off `origin/main` at `cfaa273e`. P0 #2 of the Mac/Windows
parity audit (2026-09-12, rows #43-#46): "Windows agents are told to use commands their
kosmos doesn't have". The same class as BLOCKER 5 (WINDOWS-ROADMAP.md §3c): a Windows
agent silently could not talk back.

## The defect

`tools/windows/kosmos-cli.js` (the agent's `kosmos` in the Windows zip) is a subset of
`install/kosmos` (the Mac CLI), and nothing ties the two to the words Kosmos teaches:

- `kosmos feedback write` / `feedback show`: taught daily by the Project Manager role
  (`engine/roles.js:147-163`). Windows: not a verb, usage and exit 2.
- `kosmos task message <project> <n> "..."`: in every task notification the board delivers
  (`server.js:11457`). Windows: "Unknown: kosmos task message".
- `kosmos room reopen <project>` (Mac help, and the post refusal text at
  `install/kosmos:919`). Windows: "reopen" is read as a project id and gives a 404.
- `kosmos reply --help` sends the literal "--help" to the person (#1674 was fixed only in
  bash). The same goes for `msg <agent> --help` and `post <p> --help`, and `report --help`
  records a state.

## Inventory (before)

Scanned: every non-test source (engine/, server.js, bin/, install/, tools/, docs/, web/,
README.md), the rendered instruction block (`engine/defaults.js` `block()`), every role
text (`engine/roles.js` `ROLES`), and the Mac CLI's dispatch and help. Prose matches
("kosmos and", "kosmos is") are not verbs in either CLI and are ignored.

| Verb / sub | Taught where | Mac | Windows before |
|---|---|---|---|
| msg, reply, post, react, whoami | defaults block, messages, notifications | yes | yes |
| report (+ show/status) | defaults block, server | yes | yes |
| room | defaults block, messages | yes | yes |

| `--help` / `-h` never sends | (#1674) | yes | NO |

No Windows verb is missing on the Mac.

## The fix

1. **`tools/windows/kosmos-cli.js`: the dispatch becomes one table.** `VERB_HANDLERS`
   (verb to handler) plus `SUBCOMMAND_HANDLERS` (verb to {subcommand to handler}). `VERBS`
   and `SUBCOMMANDS` are exported as `Object.keys` of those tables, so the exported list
   IS the dispatch, not a claim about it. Existing verbs move into handlers unchanged.
2. **New handlers, reusing the Mac verbs' routes and engine calls:**
   - `task message <project> <n> <text...>`: POST `/api/project/<slug>/task/<n>/message`
     `{text, from_pane:''}`, the Mac's body. It also presents the agent token. The
     sentences are the Mac's own. A timeout is exit 3 (the Windows CLI's rule for a send
     the board may already have acted on).
   - `room reopen <project>`: POST `/api/project/<slug>/room/reopen`, with the board token
     only, as the Mac sends it. The 2xx/404/other sentences are the Mac's.
   - `feedback write|show|list|triage|pull`: engine-direct, as on the Mac. It requires
     `engine/feedback.js`, `feedback-triage.js` and `feedbackpull.js` and runs the same
     logic the Mac's `node -e` snippets run, with the same sentences and exit codes.
     `write` takes the args, or stdin when there are none (as the Mac). A console stdin
     is not read: an agent has none, and a person at a console gets the "nothing to write"
     sentence rather than a hang.
3. **Server: `/api/project/:id/task/:n/message` resolves the sender from the agent token**
   (`senderFromAgentToken`, the chain /api/msg, /api/post and /api/react use), falling
   back to the pane as before. Without it a Windows agent's task message goes out as "An
   agent said" and echoes back to the sender. A presented token that does not resolve is
   refused (403 `{error}`) before anything is recorded, the same rule as the other sends:
   a bad credential is never swapped for a weaker one. With no token, the Mac path is
   byte-for-byte unchanged.
4. **`--help` / `-h`, anywhere in the arguments, never sends (#1674 on Windows).** It
   prints the verb's usage to stdout, exits 0, and makes no request. That includes
   `whoami`, which the Mac guard runs (read-only). Windows is stricter because the brief
   is "never send anything". Bare `kosmos`, `kosmos --help` and `kosmos help` print the
   Windows banner.
5. **Stdin, final design (after review round 1): `kosmos` never waits on a stdin it was
   not handed input on.**
   - `kosmos.ps1` never reads PowerShell's `$input`, and says so in a header note.
     History: round 1 of the build piped `$input` into node, which dropped non-ASCII
     to `?`; the next version handed `$input` over as a temp file. Review round 1 then
     measured that merely referencing `$input` under `powershell -File` waits for
     stdin to close, so with a runner's open pipe EVERY verb hung.
   - Only the two Mac readers read stdin: `feedback write` with no text, and `feedback
     triage --cards -`. The CLI reads until the input ends, or until it has been quiet
     for `STDIN_QUIET_LIMIT_MS` (3 s). An open, never-written pipe therefore gives
     "Nothing to write" (exit 2) in about 3 s instead of hanging.
   - **Accepted limitation:** text piped into `kosmos` from PowerShell does not reach
     it. The `feedback` usage and the "Nothing to write" answer both say to pass the
     text as an argument there. Git Bash pipes work, non-ASCII included (the sh shim
     `exec`s node).
   - **Triage is one derivation, also revised:** rather than copy the Mac's `node -e`
     triage logic, it moved into the engine as `feedback.reportsForTriage` (store or
     --dir, --since, the guarded per-file read) and `feedback-triage.digestFor` (the
     range line and card list). install/kosmos's triage now calls both, and so does
     Windows. `tools/test-feedback-triage.sh` is the Mac control; it runs here under
     Git Bash.
6. **Convention 5, the drift guard: `tools.windows-kosmos-cli-verbs-parity.test.js`.**
   It asserts the SHAPE:
   - Mac verbs are parsed from install/kosmos's final dispatch `case` and pinned equal to
     its help banner. Mac subcommands are parsed from the case arms and literal `= "x" ]`
     compares inside each `cmd_<verb>()`.
   - The Mac-minus-Windows verbs must equal a declared `PERSON_ONLY_VERBS` list, with a
     reason. A verb the Mac gains is then red until Windows implements it or someone
     deliberately calls it person-only.
   - Every Mac subcommand of a shared verb must be in Windows `SUBCOMMANDS`.
   - Reverse: every Windows verb and subcommand must exist on the Mac.
   - Taught side: every `kosmos <verb> [<word>]` in the scanned corpus, in the rendered
     instruction block and in every role text must name a Windows verb or a person-only
     one. A second word must be a Windows subcommand wherever it is one of that verb's
     subcommands on either side, and for a subcommand-required verb (task, feedback).
     The texts agents actually receive may name NO person-only verb.
   - It also matches the variable-built teaching lines (`${cliShown} task add`,
     `kosmosCliShown() + ' post'`), which a plain grep for "kosmos " misses.
   - Behaviour: every (verb, subcommand) pair is dispatched (running it never gives
     "Unknown"), its `--help` sends nothing and exits 0, and the verb's usage names it.
7. **Docs:** the kosmos-cli.js header (the verb list), and WINDOWS-ROADMAP.md BLOCKER 5
   (that talk ✅ now covers task message and feedback). tools/windows/README.md lists no
   verbs.

## Live check, once this ships in a Windows build (staging first)

A delivery plus a transcript missed BLOCKER 5, so the answer must be SEEN in the board
thread. On a candidate zip built from main with this merged, on a sandboxed Windows
account or a throwaway Kosmos (never the live fleet):

1. Create two test agents A and B on one project, with a task assigned to both.
2. In the board, post a task message to that task as the person. Confirm A and B each
   receive "[Kosmos task N - P] The person said: ... reply in the task: kosmos task
   message ...".
3. Tell A (board chat): "answer in the task with kosmos task message, using the exact
   words ALPHA-TASK". **Pass:** the task's conversation on the board shows ALPHA-TASK
   from A, B receives "A said: ALPHA-TASK", and A receives nothing about its own message.
4. Tell A: "run `kosmos reply --help`, then answer me with kosmos reply BRAVO-HELP".
   **Pass:** the board thread shows BRAVO-HELP and NO message reading "--help".
5. Tell A: "save a feedback note with `kosmos feedback write "CHARLIE é"` (text as an
   argument, in PowerShell), then check it with kosmos feedback show, and reply with
   what show printed". **Pass:** the board thread shows the reply with "CHARLIE é"
   intact. Then ask for the same with a Git Bash pipe (`printf 'DELTA é' | kosmos
   feedback write`): its show must print DELTA é. And ask A to run a bare `kosmos
   feedback write` in PowerShell. **Pass:** it answers "Nothing to write" within a few
   seconds and never hangs the agent's tool.
6. Trip a room's loop guard (or post in a held room), tell A to run `kosmos room reopen
   <project>` and then post DELTA. **Pass:** DELTA appears in the room on the board.
7. Repeat 3 and 4 from Git Bash.

**BUG: a slow pipe was cut short silently.** `(printf 'PART1 '; sleep 5; printf 'PART2') |
kosmos feedback write` said "Saved" with PART1 only, and `gh issue list ... | kosmos
feedback triage --cards -` with a late card printed "Likely already carded (0)" and exited
0. Rule now: never exit 0 on input that may be truncated.
- `readStandardInput` resolves `{ text, ended }`. `ended` is true only on the input's
  real end; the quiet limit, an error or a console give false.
- `feedback write`, no text:
  - nothing arrived: "Nothing to write" (exit 2), as before;
  - text arrived but the input never ended: refused, exit 2, nothing saved, with the
    advice to pass it as an argument;
  - the input ended: saved.
- `feedback triage --cards -` waits for the END through up to
  `CARDS_STDIN_QUIET_LIMIT_MS` (120 s) of silence, since `gh` can be slow before its first
  line. If the list never ends it exits 2 with a sentence and prints no digest. An open,
  never-written pipe therefore costs 120 s there, then exit 2; the usage text says so.
- Both limits are stated in the `feedback` usage, and a unit test pins the numbers to the
  constants.
- A console stdin is still never read. The no-hang shim tests still pass.
