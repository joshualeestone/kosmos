# Plan: #2911 / #2189 -- request + secure BOTH Kosmos and tmux accessibility grants up front

## Josh's ruling (via Splinter, 2026-09-14)
KEEP the accessibility ask -- it IS needed. At RUNTIME, when agents act, macOS prompts for
accessibility. The up-front screen must REQUEST + SECURE the grants BEFORE the user is
ambushed mid-work. Goal: the user grants everything up front and is never surprised by an
a11y prompt later.

## What finished looks like
On the "Kosmos never sleeps" (S3) install screen, the up-front flow triggers and secures the
accessibility/automation grant(s) for BOTH the process macOS actually prompts at runtime AND
Kosmos, so that once onboarding is done, using agents raises no further permission prompt. The
screen shows both, the check verifies both, Josh's "Kosmos and tmux not activated, turn on"
copy (Mona's #3032) sits on a settled gate.

## Root cause / crux (identified 2026-09-14, empirical + code)
1. EMPIRICAL (this Mac's system TCC db, `kTCCServiceAccessibility`):
   - `/opt/homebrew/.../tmux` -> GRANTED (auth 2)
   - `AEServer` (AppleEvents/Automation) -> GRANTED (auth 2)
   - `com.chaoskosmos.kosmos` -> NOT granted (auth 0)
   So the runtime prompt lands on TMUX (and AppleEvents), not Kosmos.
2. THE TRIGGER (code): `engine/terminal.js` runs `osascript` -> `tell application "Terminal"
   ... do script`. Controlling Terminal.app needs Automation (AppleEvents) and, for System
   Events UI scripting, Accessibility. macOS attributes it to the RESPONSIBLE process, which
   for anything under tmux is TMUX. So "as soon as you use agents" a terminal op fires and
   macOS prompts "tmux wants to control your computer."
3. THE GAP: the up-front `axprompt` hatch (`spawnAxHatchUnderTmux(hatch:"--kosmos-app-axprompt")`)
   runs the KOSMOS-APP EXECUTABLE under tmux and calls `AXIsProcessTrusted()` INSIDE it.
   AXIsProcessTrusted reads the CALLING binary (#2451), so even under tmux it registers the
   Kosmos app, never tmux. So onboarding secures Kosmos and leaves tmux to ambush the user.

## Approach (the HOW)
The up-front screen must ALSO fire the TMUX prompt. Instead of (or in addition to) the
kosmos-app AXIsProcessTrusted hatch, run the ACTUAL triggering operation under the BUNDLED tmux
at onboarding: a benign `osascript` that touches `System Events` / `Terminal` automation, spawned
via a tmux `new-session` the same way `spawnAxHatchUnderTmux` already spawns (it runs
`tmux -L kosmos-axcheck new-session -d '<exe> <hatch>'`; here the payload is the osascript, not
the app executable). macOS then raises the prompt for the bundled tmux (the responsible process),
and the user grants it up front.

- Determine WHICH TCC service(s) fire: Accessibility (`kTCCServiceAccessibility`, System Events
  UI scripting) and/or Automation (`kTCCServiceAppleEvents`, `tell application "Terminal"`). The
  screen must request every one that fires. Likely BOTH.
- Detection: the gate must verify the grants are secured. Reading the system TCC db directly (as
  `a11ystatus.tmuxGrant()` already does for tmux's a11y row) is the live-truth source, and pairs
  with the #2559 live-detect work.

## The one real-Mac dependency (Splinter's fresh-install verify)
TCC is per-binary. This dev Mac shows the HOMEBREW tmux granted (dev agents ran under it); a
fresh install runs agents under the BUNDLED tmux (`<home>/tmux/bin/tmux`), a different binary.
The build fires the osascript under the BUNDLED tmux; Splinter's fresh-install verify confirms
macOS names the bundled tmux in the prompt (attribution). If it names something else, retarget
to whatever it names. Weakest premise: that responsible-process attribution puts the bundled tmux
(not osascript, not the app) on the prompt -- consistent with the empirical tmux grant + the
responsible-process model, but only a clean install proves it.
