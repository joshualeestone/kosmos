# sealworker-7746: the backup manifest is sealed off the board's main thread (kosmos#7746 item 1, last part)

Finished means: at the top plan, sealing a manifest no longer freezes the board for seconds; the sealed bytes open to exactly what an in-process seal opens to; and a worker that cannot run never means no seal.

Measured (477,000 chunks, a 117 MiB manifest, a 10 ms timer, the in-process seal as the control on the same runs): in-process 1.6 to 1.8 s in one block; sealOffThread 1.8 to 1.9 s in total with a longest stall of 225 to 232 ms (the JSON.stringify left on the main thread, and the copy of that string into the worker's message). Opened, the two seals deep-equal each other and the original manifest.

Decided:
- The worker gets the manifest as one JSON string, not the object: handing the object costs a 464 ms synchronous structured clone (measured on #7746) before the worker starts. The worker parses it and calls the same sealManifest.
- A worker that cannot start, ends without answering, does not answer within 10 minutes, or cannot be posted to, is ended and the seal is made in process (as before this change); the run's answer then carries `sealedInProcess` with which way ('not-sent', 'no-worker', 'worker-ended', 'no-answer'), so a worker that never works is visible, and why. A fallback seals as before this change, so it freezes the board for the seal again. An unreadable answer (messageerror) falls back at once rather than after the wait; the manifest is stringified before any worker starts. A seal error in the worker rejects with the seal's own message, as a throw here would. The manifest string is not held past the post, so a fallback does not hold it as well.
- One worker per seal, ended once it answers (once a run).
Tests: the worker's seal opens to the in-process one AND was made by the worker (a report of the path, so a broken worker that the fallback covers is caught); a missing worker file and a worker that never answers still seal, by the fallback; a refused manifest gives the same message, from the worker.
The manifest is stringified with a replacer that refuses what canonicalJson refuses and JSON.stringify would rewrite (undefined, NaN, Infinity, -0, unsafe integers, a Date or any non-plain object, functions, symbols, bigints): such a manifest is sealed here, where the seal refuses it with its own message, as before. Measured: 60 to 150 ms more than a plain stringify at 477,000 chunks. Tested with six bad values, each refused with the in-process message and no worker started.
Weakest premise: the three rules the replacer does not mirror, because each needs a look at every object's keys (an array's extra properties, symbol keys, hidden properties). JSON.stringify drops those silently; the snapshot builds none of them.
Not pinned by a test of its own, stated as such: the messageerror listener (falls back at once instead of after the wait) and the settled guard in the answer handler (harmless if removed). Termination is tested directly: the test waits for the worker that answered, and the one that never did, to exit (red, not a hang, without the terminate in the fallback). The exit listener is tested by a worker that exits on its message (red without it: the test times out). The cleared timer is not: left armed, it only holds the test file open (a hang, not a red).
