# codex-choices-998: a Codex agent's choice prompt gets buttons (kosmos#998)

## Why

Found while validating a fleet "can this agent actually hear me" instrument, not
by hitting it. **It is a second, deterministic path to the failure Josh reported
on #989**, and it hits the provider his 10:32 ruling is about to make first-class.

Two parsers read the same prompt and disagreed about which selector glyph exists:

- `engine/status.js`'s needs-you markers know **both** `❯` (U+276F, Claude) and
  `›` (U+203A, Codex). #249 exists entirely because of that difference, captured
  from a live codex-cli 0.149.0 pane on this machine on 2026-08-23.
- `engine/chat.js`'s `OPTION_LINE` knew **only** `❯`.

`optionsIn` returns null unless it saw a selector (`if (!marked) return null`),
so for any Codex menu Kosmos did exactly half the job: correctly announced
"waiting on an answer" and showed the raw prompt, then drew **no buttons**. The
person is told their agent is stuck and handed nothing to unstick it with.

⚠️ Measured before changing anything, same prompt, only the glyph varied:

```
❯ heavy angle    question: FOUND   options: ["1:Yes...","2:No..."]
› single angle   question: FOUND   options: null      <-- the defect
> ascii          question: null    options: null
```

## What

1. **`SELECTOR_GLYPHS` moves to `engine/status.js` and is exported.** It lives
   beside the marker lists whose docblocks record the observation, and it is the
   fix for the general shape rather than the character: two files keyed on a
   hardcoded glyph separately and forked silently.
   📌 **Scope, stated rather than overclaimed:** it governs the three MENU-PARSING
   patterns. The needs-you marker lists keep their own literals on purpose -- each
   is an OBSERVED capture from a specific CLI, and its docblock records what was
   seen, which is a different kind of fact from "these characters can precede an
   option". Collapsing those into this constant would lose the observation.
2. `engine/chat.js`'s `OPTION_LINE` **and** `ANY_NUMBERED` both build from it.
   ANY_NUMBERED matters too: it is the "a menu longer than we can read is
   refused rather than served as its first nine" guard, and a Codex menu of ten
   options would have slipped past a half-fixed version.

## Out of scope

- Plain ASCII `>`. It matches neither parser, and this file's own standing rule
  is *"add to this list by OBSERVING"* -- no runner has been observed drawing it,
  and a guessed glyph is the same 0-for-1 bet as a guessed wording. Recorded on
  the card so the next reader knows it was considered, not missed.

## Verification (done when)

1. A Codex-shaped menu (`›`) produces the same buttons a Claude-shaped one does.
2. **Two controls in the same test, both load-bearing:**
   - the Claude shape still works -- a fix that traded one glyph for the other
     would pass the first assertion and break every agent we currently run;
   - an unmarked numbered list still returns null -- widening the glyph class
     must not have widened "a numbered list is a menu", which would turn prose
     into buttons.
3. ⭐ **Revert-sensitivity, stated per assertion rather than per run.** The
   happy-path test was run against the UNFIXED code and FAILS there, then passes
   with the fix. Every other fixture in `chat.test.js` uses `❯`, which is why the
   suite was green while the defect was live.
   ⚠️ **AND THE HONEST QUALIFICATION, because the first version of this line
   overstated it.** That run covered ONE of the new tests. Checking the other:
   in the guards test, the ten-option refusal assertion PASSES against unfixed
   code -- unfixed `optionsIn` returns null for that fixture for an unrelated
   reason (`found[0].n === 2`, so the 1..n rule refuses it first). Only its
   nine-option CONTROL is revert-sensitive. So "the tests fail on revert" is
   true of two assertions and not of a third, and a claim that a whole test
   catches a revert is exactly the kind that survives review by sounding
   thorough.
4. Full suite; challenge-loop to convergence; PR per house flow.


## 🛑 BLOCKED: a FOURTH copy of the pattern lives in web/index.html, and this must not merge without it

A blind review found what I missed, and it is the exact trap this plan's own step 2
was written about, one file further out.

`web/index.html`'s `talkKey` carries the option-run pattern a fifth time, as a literal
`/^(?:❯\s*)?[1-9][.)]\s+\S.*$/`, with its own comment saying it is `optionsIn`'s
pattern "verbatim" and listing four previous drifts. This change makes a fifth, and it
disagrees UPWARD -- the engine now reads a Codex menu that the page still cannot.

**Measured consequence, on `Edit file src/a.js?\n› 1. Yes\n  2. No`:** the page's
`findIndex` skips the marked line and lands on `2. No`, so its `above` is
`Edit file src/a.js? › 1. Yes` while the engine's `questionAbove` returns
`Edit file src/a.js?`. The page sends its value as `body.asked`, the server compares
the two for equality, they differ, and the route answers **409 "its screen moved
between drawing that button and sending it"**.

⇒ **Shipping this half would give a Codex agent buttons that ALWAYS fail, with a
message blaming the agent's screen.** It fails closed, so no wrong keystroke is ever
typed -- but before this change a person got no buttons and typed one line themselves;
after it they get buttons that never work and a false explanation of why. That is not
an improvement, so the branch waits.

**Why it is not fixed here:** `web/index.html` is where Mona Lisa's #980 restyle is
mid-review. Two of us in that file costs more than the sequencing does. The page half
goes in the moment hers merges, and this branch does not merge before that.

**And the completeness question I should have asked and did not:** "where else is this
pattern spelled out" was asked of `engine/`, not of the tree. `server.test.js` even has
an agreement test for exactly this page-versus-engine drift -- and it is GREEN, because
every fixture in it uses `❯`. The same blind spot as `chat.test.js`, in the test written
to catch this class.
