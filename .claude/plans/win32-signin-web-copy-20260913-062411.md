# win32-signin-web-copy

Follow-up to #2993 (`feb30b80`, win32-claude-signin-host): the board page's copy for the
Windows Claude sign-in. Base: origin/main `feb30b80`. Design intent:
`kosmos-scripts/win32-claude-signin-design.md` (slice 1, Page) and the "Web follow-ups" section
of `.claude/plans/win32-claude-signin-host-20260913-034641.md`.

## Gaps, confirmed on feb30b80 before building

1. **Install note on a PC that has Claude Code: REAL.** `frPaintConnect`'s stuck card showed
   `windowsCopy('claudeInstallNote')` when `onWindows(st.platform) && st.canInstallClaude === false`.
   `canInstallClaude` (`platformGate.canDownloadRunner`) is false on every Windows PC, so a PC
   where `runners.resolveBin('claude')` found Claude Code (`canRunClaude: true`) and then hit the
   new "Kosmos cannot run the Claude sign-in on Windows yet" stop was told "this one step is
   yours" with `irm https://claude.ai/install.ps1 | iex`. `server.connect.test.js` even pinned
   that ("a Windows box that already has claude.exe keeps the hatch as well", both notes).
2. **Stuck-reason wording: PARTLY REAL, and not where the brief expected.**
   - There is no reason-to-copy table. `FR_CONN_SAY` and `ACCT_FLOW_SAY` are keyed by PHASE
     (`FR_CONN_SAY.stuck` is the generic live-region sentence; `ACCT_FLOW_SAY` has no stuck
     entry). The first-run card shows `st.because` verbatim as the check row's detail, and
     Settings > Accounts shows `pjSentence(st.because)`. The engine owns both sentences, so a
     page copy would be a second derivation (convention 5).
   - "Kosmos cannot run the Claude sign-in on Windows yet" is already plain. What the card
     lacked is the next step: the manual path sat CLOSED behind "Already use PowerShell?", a
     question that assumes the person uses PowerShell. The host plan's follow-up list says it
     should be shown open.
   - The script reason (`engine/win32signin.js` `SCRIPT_ONLY_BECAUSE`, "Kosmos can only start
     the Claude Code program file (claude.exe), and this computer has a script version it
     cannot start directly") is internals. It is unreachable in production while
     `WINDOWS_SIGNIN_HOST_ENABLED = false`, and its one owner is the engine, so the plain
     wording goes there.

## Changes

- `web/index.html` `frPaintConnect`: the install note also requires `!st.canRunClaude` (the
  flag `publicView` already serves; nothing re-derived).
- `web/index.html` `windowsCopyTable().claudeTerminalHatch`: `<details class="fr-hatch" open>`,
  summary "Sign in to Claude yourself", body opens with "Claude Code is already on this PC, so
  you can sign in to Claude outside Kosmos." (rendered only under `canRunClaude`). Mac hatch and
  every Mac string untouched.
- `engine/win32signin.js` `SCRIPT_ONLY_BECAUSE`: "Kosmos cannot start the copy of Claude Code on
  this computer by itself".

## Not changed, on purpose

- Settings > Accounts: it shows the engine's reason and offers no manual path. Its flows are
  "add another account" and "sign in again" for a given config folder, where typing bare
  `claude` would sign in the default account instead, so offering the first-run hatch there
  would be wrong.
- "the sign-in window closed before Claude finished" on Windows: only reachable once slice 3
  switches the host on (host plan follow-up list).
