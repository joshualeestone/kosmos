## Why

The measured design (`~/kosmos-scripts/win32-inbound-path-design-2042.md`) proves the
premise of #2042 is already solved for supervised Windows worker agents: they run as
streaming children whose stdin the supervisor holds, reachable over a per-agent named
pipe (`win32channel`), and injection was measured end to end (an agent replied `PONG`).
What is still missing is the **cross-machine last mile**: a received Slack envelope
addressed to a local worker is never turned into a delivery. `~/.local/bin/kosmos-inbox.ps1`
today only PRINTS envelopes addressed to `windows-orchestrator`; it does not deliver.

S1 (this slice) grows that poller from "print envelopes" into "deliver envelopes" for
**worker agents only** (W1–W4 of the design §3). Approved decisions honoured: Q3 grow the
existing ps1; Q4 Slack stays the transport, add only the last-mile poller; Q1 orchestrator
model is PENDING Josh, so no orchestrator-specific delivery path here; Q2 native
messaging-socket deferred.

## Shape: a thin PowerShell shell over a tested node module

The testability requirement ("delivery + verdict→cursor logic must be unit-testable, not
buried in un-testable PowerShell") drives a split:

- **`engine/win32inbox.js` (new, node, unit-tested)** — ALL of W1-parse / W2-resolve /
  W3-deliver / W4-verdict→cursor. Pure, seam-injected functions plus one `run` verb the
  ps1 invokes once per poll:
  - `parseEnvelope(text)` → `{ from, toNames[] }` using the SAME envelope grammar the ps1
    used (multiline `^from:` / `^to:`, comma-split, strip a trailing `(...)`, trim). One
    grammar, now tested — including a malformed envelope (no `to:` → no target).
  - `resolveTarget(toNames, liveNames)` (W2) → the first to-name that is a live local
    worker, or `null`. `liveNames` comes from `win32live.byName` (the ONE ownership join
    `win32roster`/`win32live` already use — reused, not reinvented).
  - `verdictToDisposition(verdict)` (W4) → mirrors `chat.js deliverThroughChannel`
    EXACTLY: `ok===true`→`placed` (advance); `unsure===true`→`unconfirmed` (advance+log);
    anything else `ok:false`→`could_not` (do NOT advance). One verdict contract, reused
    from `win32channel.say`.
  - `runInbox({ messages }, opts)` — iterate messages oldest-first, resolve+deliver each,
    and compute the cursor decision (below). Delivery goes through `win32channel.say`
    (injected in tests so no real agent is ever touched).
- **`~/.local/bin/kosmos-inbox.ps1` (grown) + `tools/windows/kosmos-inbox.ps1` (repo copy
  for review)** — pure I/O: fetch Slack `conversations.history` since the cursor, hand the
  raw `{ts,text}` messages to `node win32inbox.js run` on stdin, write the returned cursor,
  print the per-message dispositions. Keeps `-Peek`/`-All`/cursor-file semantics. A new
  `-Deliver` switch turns delivery ON; without it the script keeps the old print-only
  behaviour (safe default, so a bad deploy cannot start typing at agents).

## W4 verdict → cursor rules (the load-bearing decision)

Cursor is a single Slack `ts`; Slack `oldest=<ts>` is EXCLUSIVE (inclusive defaults
false), so advancing the cursor TO a handled message's ts excludes it next poll and
includes the next one. Rules, per message oldest-first:

- **not addressed to a live local worker** (resolveTarget→null), OR **from a live local
  worker** (our own outgoing): not ours → advance past it (each box has its own cursor;
  "left for others" is safe because remote boxes poll independently). `advanceTo = ts`.
- **placed** → advance. `advanceTo = ts`.
- **unconfirmed** → advance but log (may have arrived; re-sending could duplicate).
  `advanceTo = ts`.
- **could_not** (supervisor down / ENOENT on the pipe, or any non-unsure `ok:false`) →
  **STOP**. Do not advance past it and do not process later messages this poll. The
  un-advanced cursor IS the retry; no spool. `advanceTo` stays at the previous message.
- **roster unreadable** (`claude agents --json` / record read failed → `win32live.byName`
  returns null): we cannot tell whether ANY envelope is for a live local worker, so we
  refuse the whole poll and advance nothing (the false-zero rule the win32 family is built
  around). `advanceTo = null`.

An unknown/dead name resolves to `null` (it is not in the live-owned map) → treated as
not-ours → advance past (skip), NOT could_not — a name with no live supervisor must not
block the cursor forever. `could_not` is reserved for a target that DID resolve live but
whose pipe was down at send time (the genuine transient-retry case).

## Tests (revert controls must go red)

`engine/win32inbox.test.js`, all seam-injected (fake `liveNames`, fake `say`, fake
`record`/`run`) — NEVER a real agent, board, pipe, or `\Kosmos\*`:

1. `to:` routes to a live worker (resolveTarget picks the live name among several).
2. placed → advance.
3. unconfirmed → advance + logged.
4. could_not → cursor UNMOVED (retry next poll), later messages not processed.
5. envelope for an unknown/dead name → not delivered, advanced past (does not block).
6. malformed envelope (no `to:`) → not delivered, advanced past.
7. from a live local worker (own outgoing) → not delivered, advanced past.
8. roster unreadable (`win32live.byName`→null) → advance nothing.
9. verdictToDisposition parity with chat.js's three-way contract.

Revert control: flip `could_not`'s `advance` to true (or resolveTarget to ignore
liveNames) and the suite must red. `parseEnvelope` gets its own malformed-input arms.

Off-win32: the module is pure JS (no win32-only paths at require time beyond requiring
`win32channel`/`win32live`, which are plain JS), so the suite runs on macOS CI too; no
win32 gate needed. Confirmed against a `git archive` of origin/main by name + first error
line.
