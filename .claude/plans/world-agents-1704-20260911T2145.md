# Plan: named-world agents (kosmos#1704 lane; fixes #2827, #2828)

**Status: DRAFT FOR ANGEL'S REVIEW. No code until she confirms.** The multi-Kosmos lane
is Angel's (#1704, #2238, #2563, #2827, per Splinter, 2026-09-11). This plan was
drafted by windows-orchestrator from three read-only surveys. Base: main `03b99146`.

## Josh's decisions (2026-09-11, given directly)

1. **The full fix** ("do it right so we are not leaving loose ends"). Agents in a
   named Kosmos fully work on Mac and Windows: reports, replies, msg, capture, and
   restart/remove/restore.
2. **On a world switch, the dialog ASKS EACH TIME:**
   - pause this Kosmos's agents: they are stopped, remembered, and back when that
     Kosmos is opened again;
   - keep them running: nothing they send the person may be lost while their
     board is not the one serving.
3. **Import (#2563) as Josh described it:**
   - When creating a new Kosmos, pick INDIVIDUAL existing agents from any other
     Kosmos to copy in, or skip.
   - The cog next to EACH Kosmos opens that Kosmos's settings, with the same "add
     agents from another Kosmos" pane, for an existing Kosmos.
   - Copies are complete (avatar and instructions), and they run when their Kosmos
     is opened.
4. **The default world stays byte-identical:** the same task names, plist labels,
   tmux session names and paths, so no migration.
5. Josh's switch-modal wording stays. Only the minimal choice is added.

## 0. Verified facts that shape the design

- **`+` is a safe separator.** `NAME_RE = /^[a-z0-9][a-z0-9_-]{1,31}$/`
  (create.js:379) and world ids `CLEAN_ID = /^[a-z0-9_-]+$/` (worlds.js:47) can
  never contain it.
- **Pipe names must be built from the key.** `store.safeKey` (store.js:262) strips
  everything outside `[a-z0-9_-]`, and `pipePath` (win32channel.js:82) uses it, so
  building the pipe from `safeKey(key)` would drop the `+`.
- **No carrier gives agents their world env today:**
  - the plist env (create.js:1950-1954);
  - the pane `-e` list (agent-supervisor.sh:379);
  - the token-mint one-liner (agent-supervisor.sh:316-322);
  - the task argv (win32job.js:166).
- **The Windows anchor moves under a named world.** `anchorDir` honours
  `AGENT_WORKFORCE_DATA` (win32anchor.js:100), and so does `win32board.anchorDirFor`
  (win32board.js:280-285).
- **Board tokens are per world** (`store.ROOT/board.token`, boardauth.js:97). Board
  B answers world A's token with a 403 (server.js:1968). Today "keep running"
  would therefore lose replies.
- **Resume is a fresh conversation on both platforms.** On Mac the supervisor runs
  plain `claude` with no `--continue` (agent-supervisor.sh:436-440). On Windows a
  task start mints a new session (win32supervisor.js:405-410). So pause and resume
  behave like a restart: the Kosmos thread survives, the runner transcript does
  not. That is stated in the docs, and this plan does not change it.
- **Import copies whole worlds, and each copy keeps its `dir`.** The checkboxes are
  per world (web/index.html:18472-18493, payload :18510), and
  `worlds.importAgents` (worlds.js:402-450) copies every profile. `stripIdentity`
  (store.js:419) removes only `id` and `idInstall`, so a copy keeps `dir` and
  `agentDirRecorded` (create.js:562) points it at the SOURCE world's worker folder.
  That is a latent bug.
- **tmux cannot be tested here.** There is no tmux on the Windows box, so every
  tmux-accepts-`+` claim is for Mac CI or a Mac builder to verify.

## 1. The world carrier: how every agent process learns its world

**One env var, `KOSMOS_WORLD=<id>`. When it is absent, the agent is in the default
world.** Roots are always derived from it, never passed separately.

- `worlds.js` gains `WORLD_ENV_VAR = 'KOSMOS_WORLD'`,
  `PRE_WORLD_DATA_ENV_VAR = 'KOSMOS_PRE_WORLD_DATA'` and `preWorldEnv(env)`. That
  function takes the world vars off and restores `AGENT_WORKFORCE_DATA` from the
  marker, where `''` means unset.
- `worldenv.applyWorldEnvForAgent(env)` is the ONE agent-side bootstrap.
  - It does nothing for the default world, and nothing if the marker is already
    set (idempotent for inherited children).
  - Otherwise it records the marker, then applies
    `envOverridesFor(baseRoot(env), {id})`.
  - It never reads the registry: `worldBaseDir` derives from the id and validates
    against `CLEAN_ID`.
  - The board's `bootstrapWorldEnv` (worldenv.js:92) sets the same var and marker,
    so the board and its agents share one source.
- `launchidentity.currentWorldId(env)` reads `KOSMOS_WORLD`. A one-derivation test
  pins it equal to `bootedWorld()`.
- `boardrestart.kosmosRestart` (boardrestart.js:266-270) uses `preWorldEnv`
  instead of deleting the three vars by hand.
- **Mac:**
  - `plistFor` (create.js:1954) adds `KOSMOS_WORLD` ONLY for a named world, so the
    default plist is unchanged byte for byte.
  - The supervisor adds `KOSMOS_WORLD` to the `-e` loop (:379).
  - The mint one-liner (:316) calls `applyWorldEnvForAgent` BEFORE requiring
    `sendertoken.js`, which freezes its DIR at require (sendertoken.js:58).
  - The roster name (:315) strips `+$KOSMOS_WORLD`. A test pins that equal to
    `launchidentity.nameFromSession`.
  - `install/kosmos` `board_token` (:333) applies the world env first.
  - `supportDir` stays per world, which is where the supervisor and its secrets
    live.
- **Windows:**
  - Append `world` as argv field 7 (index 6, `'-'` for the default) in `taskExec`
    (win32job.js:166). This is append-only. Exec actions carry no env, so the task
    XML is the only carrier.
  - Move `specFromArgv` (win32supervisor.js:220) into a leaf `engine/win32argv.js`
    with no requires. The supervisor re-exports it, and `configDirFor`
    (win32job.js:619) keeps working.
  - `BOOT_JS` (win32anchor.js:133-152) runs these steps in order: resolve the
    engine, require `win32argv.js`, set `process.env.KOSMOS_WORLD`, call
    `worldenv.applyWorldEnvForAgent`, and only THEN require `win32supervisor.js`.
    Everything downstream then inherits the world: `claude.exe`, the hooks, and
    kosmos-cli.js. So do `win32sessions`, `win32streamstate`,
    `win32channel.secretDir` and `sendertoken`.
- **The anchor stays machine-level.** `anchorDir` maps its env through
  `worlds.preWorldEnv`. A world override carries the marker, so it is ignored. A
  test sandbox has no marker, so it is honoured. The result is one node.exe and
  one pointer for all worlds.

## 2. One module for launch identity: `engine/launchidentity.js`

- **The key:** `launchKey(name, worldId)` is `name` for the default world, and
  `name + '+' + worldId` otherwise. `WORLD_SEPARATOR = '+'` is documented.
- **The identities built from the key:**
  - `taskName`: `Kosmos\agent-<key>`
  - `serviceLabel`: `com.kosmos.agent.<key>`
  - `plistPath`: `agentsDir()/<label>.plist`. LaunchAgents stays machine-level.
  - `pipeName`: `\\.\pipe\kosmos-agent-<safeKey(name)>[+<id>]`
  - `tmuxSession`: `<key>`
- **The reverse mappings:** `parseKey`, `nameFromSession(session, worldId)` (null
  when the session is another world's), `parseLabel` and `parseTaskName`.
- **Why `+` is safe in each system:**
  - Task Scheduler: it is not in schtasks' forbidden set.
  - launchd and filenames: it is legal in labels and in filenames.
  - Named pipes: it is legal in pipe names.
  - tmux: it is not a target delimiter (`:` and `.`). Every destructive tmux target
    is already `=`-anchored (agent-supervisor.sh:85, remove.js:479).
  - Mac CI must still verify each of these.
- **Call sites that switch:**
  - create.js:735-736 (these become delegates), :1878, :2114, :2137, :2420-2446,
    :3130, :3428-3431 and :3769-3917;
  - `win32job.taskName` and `TASK_PREFIX` (:44-46); `list()` (:483-497) returns
    keys, and a new `namesForWorld(id)` is added;
  - `win32channel.pipePath` (:82);
  - remove.js:500 and :503;
  - createdroster.js:111-117;
  - register.js:178 and :251;
  - delete-leftover.js:203 and :231-233;
  - the supervisor's `SESSION` (the plist passes the key as `$1`);
  - `status.parsePanes` (status.js:878).
- **The Windows roster session stays the plain name.** The record lives in the
  world store, so win32roster (:117-150) is already world-scoped. Only the
  OS-global names take the key.
- **A shape test** fails if `com.kosmos.agent.`, `Kosmos\\agent-` or `kosmos-agent-`
  appear in engine/ outside launchidentity.js.

## 3. Ownership guards and the roster

- **The roster shows this world only.** `parsePanes` maps each session through
  `nameFromSession(session, currentWorldId())` and drops the nulls. The default
  board drops `*+*`, and a named board keeps only `*+<id>`. `-discord` stripping
  happens first. `disabledJobs`, `runningJobs`, createdroster and register strays
  filter through `parseLabel` or `namesForWorld`.
- **remove, restart and restore act only in this world.** `jobFor` and
  `sessionFor` resolve this world's key. As defence in depth, `unsafeToActOn`
  refuses any key that `parseKey` attributes to another world.
- **create checks before `/F`.** It gains `installJob`'s
  `jobPresence(clean) === 'yes'` refusal (create.js:2289-2295), keyed on the world
  key, before `win32job.install` runs `/Create /F`. An unknown answer is refused on
  win32. So the cleanup at :2246-2250 can only remove a task it just made (#2828).

## 4. Switching: pause or keep running (Josh: ask each time)

**The API:** `POST /api/worlds/active {id, agents: 'pause'|'keep'}`.
- An invalid value is a 400.
- An absent value means `keep`, which is today's behaviour, for older pages.
- The response: `{ok, world, restartRequired, restarting, agents,
  paused:[names], notPaused:[{name,because}]}`.

**The route order** (server.js:2843-2912):
1. Validate the id.
2. If this is a real switch and `pause` was chosen, call
   `worldstarts.pauseForSwitch(names from safeRoster())`.
3. Call `setActiveWorld`. If that throws, resume the agents just paused and
   return the classified error.
4. Respond, then self-restart as today.

**`engine/worldstarts.js`** is new and gated by
`liveExecutionAllowed()`/`refuseOrWarn`.
- **The record:** `<store.ROOT>/world-starts.json`, written atomically:
  `{entries:[{name, why:'paused'|'imported', at, because?}]}`. It is in the store
  of the world being left.
- **Write-ahead:** the entries are written before any stop.
- **The stop reuses remove.js.** Export `jobOps(platform)`/`sessionOps(platform)`
  (remove.js:391, :466). For each agent: `disable`, then `stopNow`, then
  `sessionOps.end`, then `recordDisruption`, as `restartInner` does. There is NO
  `recordRemoval`, so the agent is never marked "removed". Disable is required,
  because RunAtLoad or the logon trigger would otherwise revive it at login.
- **Partial failure:** a failed name comes out of the record and goes into
  `notPaused`. It keeps running, and §5 makes that safe.
- **Resume at boot:** `drainAtBoot()` runs from server.js after
  `allowLiveExecution()` (:11981), once the board is listening.
  - For each `paused` entry that is not removed (`remove.isRemoved`), it enables
    and starts the agent. On Mac that is `launchctl enable` plus `bootstrap`; on
    win32 it is `/Change /ENABLE` plus `/Run`.
  - A success clears the entry. A failure keeps it with a `because` and is retried
    at the next boot.

**The UI** (web/index.html:8511-8518, :18588-18624):
- Josh's `<h2>` stays as it is.
- Add two radios: "Pause this Kosmos's agents" and "Keep them running". Neither is
  preselected, and "Restart Kosmos" stays disabled until one is chosen.
- Cancel keeps its initial focus.
- `notPaused` shows in `#worldsw-restart`.
- The browser check `render-worldswitch-2238.js` asserts the labels, the missing
  default, the enable logic and the posted body.

## 5. Keep running: nothing sent is lost

- **Every agent request names its world** with an `x-kosmos-world:
  <KOSMOS_WORLD||default>` header. The clients that send it:
  - kosmos-cli.js `headersFor` (:121);
  - `install/kosmos` `kosmos_curl` (:367);
  - `kosmos-report-hook.deliver` (:208);
  - codex-report-bridge.js (:88).
- **The board refuses a mismatch before its token check** (server.js:1945, before
  the 403 at :1968). This covers loopback POSTs to report, reply, msg, post and
  react.
  - When the header is PRESENT and differs from `bootedWorld()`, the board returns
    `421 {wrongWorld:true, serving}`.
  - An absent header (older clients, the UI) behaves exactly as today.
  - Nothing new leaks: `x-kosmos-board` already publishes `build@world`
    (server.js:183, :11642).
- **On a 421, the client saves to an outbox.** `engine/outbox.js` writes into the
  agent's OWN world store, which is right because its world env is already applied:
  `<store.ROOT>/outbox/<ts>-<rand>.json {verb, body, from, at}`, written atomically.
  - `from` comes from `sendertoken.resolveName(KOSMOS_AGENT_TOKEN)`. On a Mac with
    no token it falls back to the tmux session name.
  - reply, msg and post are saved, and the command exits 0 with: "Kept. Your
    Kosmos is not the one open right now; it will be there when it is."
  - A report is dropped as stale.
  - whoami, room and task exit 1 with a sentence.
- **The board drains the outbox** at boot, after `drainAtBoot`, and then every
  60s.
  - A reply goes through `chat.keepReply(who, text, at)`. That function is
    extracted from server.js:8242-8248 so the route and the drain share one path,
    and the original `at` is kept.
  - A post goes through the shared post function, extracted from `/api/post`.
  - A msg goes through `chat.deliver`, and the entry is kept until it is placed.
  - A msg to a name not in this world is dropped, and the sender gets a note.
  - `name@world` is refused with "Agents in different Kosmoses cannot message each
    other."
  - A `from` that names no profile here is dropped and logged.

## 6. Import (Josh's flow)

- **Pick individual agents.** A new `GET /api/worlds/agents?id=` returns
  `{agents:[{name, displayName}]}`, read ONLY through `worlds.worldProfilesDir`.
  - `worldImportRender` shows each Kosmos as a group of agent checkboxes, and the
    Kosmos checkbox selects all of them.
  - The payload is `importAgents:[{from, name}]`. `worlds.importAgents` accepts it,
    and maps the legacy string array to "all names".
- **Each copy is complete.** Per agent, it copies:
  - the profile, run through `stripIdentity` with `dir` deleted;
  - the avatar, from `worldStoreRoot(src)/avatars/<safeKey>.<ext>`;
  - the brief (`briefFilename(runner)`, create.js:696), into
    `worldWorkersDir(target)/<slug>/`.

  The worker-root formula moves into `store.workersRootFor(env, home)`, which both
  `create.workersDir` (:232) and the new `worlds.worldWorkersDir(base, world, env)`
  use. That one takes `preWorldEnv`.
- **Every Kosmos gets a cog**, including the default one (web/index.html:
  18175-18184). It opens "Kosmos settings": the rename field (hidden for the
  default Kosmos) plus the same picker. It posts
  `POST /api/worlds/import {id, importAgents}`, which writes into ANY world by path
  helpers.
- **When imported agents start:** `worldstarts` records them with
  `why:'imported'` in the target store. `drainAtBoot` launches them through
  `create.installJob(name, {runner, model, configDir from the profile})` when that
  Kosmos is opened, and at once if it is the current one.
- **The browser checks to update:** `render-world-import-2563.js` (per-agent rows)
  and `render-worldrename-1704.js` (the cog now opens settings, and the default
  Kosmos has one).

## 9. Cross-cutting risks

- If `BOOT_JS`'s require order is wrong, agents write to the default store
  silently. The child-process test guards against it.
- The 421 leaks the booted world id to a local caller. That id is already public
  through `x-kosmos-board`.
- Each named world has its own `supportDir/bin` supervisor copy, and it is
  refreshed only when that world boots. So a kept-running agent may run an older
  supervisor. That is accepted, because the argv and env contract stays
  append-only.
- **create.js contention:** PigeonPete is building #2826 (`setAccount`) now. The
  create.js edits here must be sequenced with him.
