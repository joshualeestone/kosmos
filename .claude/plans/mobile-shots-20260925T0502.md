# mobile-shots: the shared phone screenshot harness (#718)

Addresses #718 (mobile priority, plan comment
https://github.com/joshualeestone/kosmos/issues/718#issuecomment-5825987811, step 1).

## Finished looks like

One command gives everyone on the mobile work (Liu Kang, Scorpion, Kano, Sonya, Johnny,
Raiden) the same phone screenshots of the same seeded board: named screens x 4 phone sizes
(375x667, 393x852, 430x932, 412x915) x light/dark x Chromium/WebKit, into one folder with a
`report.md`, horizontal overflow flagged. It never touches the live board or this Mac's
accounts, and the gate proves that on every run.

## Change

- `docs/browser-checks/mobile-shots.js` (new): boots a throwaway board on a free port with
  temp HOME, data and config roots and a fake tmux, seeds sample agents, a DM, a project room
  and an ask, drives each named screen, shoots it, and measures overflow. A leak guard reads
  every page before its shot and exits 3 on a non-example.com email, an `sk-` fragment, or
  this Mac's home path, user name or host name. Screens are a list other lanes append to.
- `tools/browser-checks.sh`: wire a strict slice (home, nav menu, agents list, accounts page;
  375px; light; both engines), plus the leak guard's two controls, each required to exit 3:
  `MSHOTS_LEAK_CONTROL=account` plants a signed-in Claude account in the sandboxed home (the
  accounts preflight must stop it) and `=page` plants an address in an agent's role (the page
  scan must stop it). These replace an "unseal the sandbox" switch nothing ran, which also
  proved nothing on a Mac with no accounts.
- `docs/browser-checks/README.md`: index row (browser-checks-indexed requires it).

## Rejected

- Gating the full 160-shot sweep: 315s measured, too slow for every run; it is a by-hand tool.
- Gating the Projects screen: it overflows by 3px at 375px in Chromium on main today (Kano's
  lane, reported to him). Adding it would red the gate for a defect this PR does not own.
- Keeping `module.exports`: nothing required it, and the wiring test reads an export as a
  library claim that must be earned.

## Challenge-loop changes (iteration 1)

- The leak scan judges what a shot or a hover can show (rendered text, form values, title /
  aria-label / alt / placeholder), not the page source, so a login name that happens to be a
  word in a code comment no longer stops every run; user and host match case-insensitively and
  escaped; every hit is masked in the message.
- The accounts preflight treats a refused or unparseable answer as a failure, not as "none".
- nav-menu and agents-list wait for the opened state, so a renamed control fails the shot.
- The overflow "widest" scan skips elements wholly off screen and children of sideways scrollers.
- The board's stderr goes to a file and its tail is printed if the board does not come up.

## Challenge-loop changes (iteration 2)

- Every red now prints a line starting `FAIL  ` (a leak stop, shots that could not be taken, the
  --strict overflow summary, and a leak control whose guard did not fire), because
  tools/browser-checks.sh quotes a failed check's reason only from such lines. Before this, a real
  leak stop would have gone red in the gate with no reason shown.
  browser-checks-reason-grep's site count moves 135 -> 138 for these three lines.

## Challenge-loop changes (iteration 3)

- Each leak control must exit 3 WITH its own guard's message (preflight: "the throwaway board
  lists"; page scan: "this screen shows real data"). Exit 3 alone let the page arm pass when the
  preflight fired first. Stub-tested all four cases: right arm -> pass, wrong arm, exit 0 and
  exit 2 -> fail.
- The user-name and host-name checks switch themselves off, with a `note` line at the start of
  the run, when that name is a word in web/index.html (a login such as `josh` would otherwise
  stop every run on the first-run placeholder). The home-path, email and key checks stand.
- The attribute and form-value pass skips elements that are not visible.
- agent-chat and ask-waiting fail when their target is missing instead of photographing
  whatever is showing.

## Weakest part (added in iteration 3)

On a Mac whose login name is also a product word, the user-name check is off. A leak of that
name alone, with no home path, email or key beside it, would not be caught there.

## Weakest part

WebKit here is Playwright's engine, not iOS Safari, and Chromium at a phone viewport is not
an Android phone. The harness says so in its header; reports must too.

## What would change my mind

If the gate slice flakes on the headless CI runner (WebKit timing), narrow it to Chromium
there rather than dropping it.
