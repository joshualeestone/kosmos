# kosmos#988: the engine half. Tell the coordinator while an update is applying.

branch `updating-signal-988`, merge-base with `origin/main` = `3bfed3b1`

## What this card is, and what is already done

From Josh's phone, one minute after 0.5.68 served: the board showed "Kosmos is not answering on
this computer". His Mac had taken the update and restarted the board. **A person on their phone
cannot tell an update restart from a broken Mac**, and the honest reading of what they can see is
"it broke".

Ice Cream Kitty split the card into four halves and finished hers. Measured before starting:

| half | state |
|---|---|
| relay (Baron Draxum) | CLOSED, unbuildable: rendering it would need the relay to terminate the person's TLS |
| coordinator (Ice Cream Kitty) | **FINISHED**, `ce84b4f`, merged, not deployed by choice |
| **updater signal (engine)** | **NOT STARTED. This branch.** |
| rendering surface | NOT STARTED. `/v1/account/macs` carries `updating_until` when it is live |

**Verified still live before claiming**, because a card is a snapshot: `grep` for `v1/mac/updating`
and for `updating_until` across the engine returns **nothing**. No caller exists.

## The contract, from the coordinator's author

`POST /v1/mac/updating {"seconds": N}` when it begins applying, `{"seconds": 0}` when it finishes.
Mac-authenticated like the other `/v1/mac/*` routes. **The deadline is capped at 15 minutes
server-side, so asking for more is safe and simply gets the cap.**

## The call has to come from node, and that was the real decision

`engine/remote.js` does not speak HTTP to the coordinator: it spawns `kosmos-tunnel` with
subcommands (`run`, `devices <verb>`). So there were two shapes.

- **A new `kosmos-tunnel` subcommand. REJECTED.** Measured: there is no `crates/` in this repo at
  all, so the tunnel source is not here. It is also a bundled, shipped binary, so a new subcommand
  would not reach a single Mac until a release cut. That makes the smallest change the slowest one.
- **A direct mTLS request from node. CHOSEN.** Measured: the mac already holds `tls.crt` and
  `tls.key` in the tunnel state dir, and `remote.js:174` requires exactly `mac_id`, `address`,
  `tls.crt`, `tls.key` for `enrolled()` to be true. Node's `https.request` takes `cert`/`key`
  directly. Self-contained, no binary rebuild, ships with the engine.

## The lifecycle, which already exists and which I am not inventing

`engine/update.js` already has the two moments this card needs:

```
markInstallStarted(owner.startedAt)   the child exists: applying has begun
child.on('error')                     never started
child.on('exit')                      stopped before it could restart the board
```

(Named by function rather than by line: an earlier version of this block cited 466, 469 and 487, and
two of the three were already wrong at the branch's own base. Line numbers in a plan go stale the
moment anything above them moves.)

🛑 **AND THE SUCCESS PATH HAS NO FINISH HOOK, BY CONSTRUCTION.** The file says so itself: "a
SUCCESSFUL install kills this server before the listener matters". So `seconds: 0` on success can
only come from the **restarted board**, and `startPolling()` is that boot entry. Three hooks, not
two, and the third is the one a reader would miss.

## 🛑 THE SPAWNED SHELL MASKS THE INSTALLER'S EXIT STATUS

The child is `/bin/sh -c 'curl -fsSL "$1" | sh; code=$?; printf … > "$2"; if [ "$4" != /dev/null ]; then rm -f "$4"; fi'`.
**The child's exit status is the trailing `if`, not the installer's.** Measured:

```
installer exits 7  ->  status file records "7"  ->  child exit = 0
```

So `if (code !== 0)` is FALSE on ordinary installer failures. A clear placed inside that branch, which
is where I first put it, never ran in production. Combined with the #2055 abort path, which dies
WITHOUT restarting the board, the deadline then stood for the full 15-minute cap on a Mac that was up
and serving: **exactly the false "back in a moment" this card exists to prevent, reached through the
production path rather than the suite.** The clear is now outside that branch, which is safe by this
file's own argument that a successful install kills the process before any listener runs.

## What the shipped code actually does, which is more than this plan first described

The plan was written for three hooks. The review loop added two more call sites and two gates, and
a plan that lags the code is the same defect as a comment that lags it:

```
wireChild, after both child listeners   announce(DEFAULT_SECONDS)
child 'error'                           announce(0)
child 'exit'  ANY exit, not code!==0    announce(0)   <- the shell masks the installer's status
startPolling() boot                     announce(0)   gated on installedRoot()
first poll tick, once                   announce(0)   gated on installedRoot()
```

**The `installedRoot()` gates are a design decision this plan did not originally record.** A board
run from a SOURCE CHECKOUT (`node server.js`, `tools/restart-local-board.sh`, routine on this fleet)
would otherwise make real mTLS POSTs to the production coordinator with the operator's certificate,
and could CLEAR a deadline the INSTALLED board had just set. The three non-boot sites are not gated
because they are only reachable through paths already gated on `installedRoot()`.

**The first-tick repeat** exists because the boot clear is a single unretried request at the moment
the machine is busiest; if it is lost the phone shows "back in a moment" until the cap.

## The rule this must not break

**An update must never fail because a status call did.** `engine/notify.js` is the precedent and
the shape to copy: an outer `try/catch` that swallows everything, a 3s abort, fire and forget, and
an explicit comment that nothing may reach the caller. The same applies here, harder: the caller is
the one route that installs software.

## What I rejected

- **Blocking the install on the announce.** No. A wedged coordinator would then stop updates.
- **Retrying.** No. The deadline is a hint with a server-side cap; a missed announce degrades to
  exactly today's behaviour, which is the whole fail-open point.
- **Writing a state file for the tunnel to read** (the card's own "smallest shape" suggestion). The
  coordinator route already exists and is the contract its author asked for; a second mechanism
  would need the tunnel to grow a reader, which is the rejected repo.

## Weakest premise

**I cannot test against the real coordinator route**: it is merged but deliberately not deployed,
and this machine's board is the installed one rather than this checkout. So the tests will assert
the REQUEST the engine makes (method, path, body, client cert wired, timeout, fail-open on every
error shape), not the coordinator's response to it. **What would change my mind:** the route
reaching a reachable environment, at which point one end-to-end arm is worth more than five unit
arms.

**A third, found by review and not by me: the two POSTs can race.** The begin-announce is sent by the
pre-restart process and the boot clear by the post-restart one, over independent connections with no
ordering guarantee. If a begin-announce is slow (up to the 3s timeout) and the new board finishes
booting inside that window, the coordinator could process the clear BEFORE the begin, and then report
"updating" until the 15-minute cap after a successful update had already finished. Real installs take
far longer than 3 seconds, so this is unlikely rather than impossible, and the harm is a stale banner
rather than a lost update. Not fixed: ordering would need a sequence number the route does not have,
which is the route author's call and not mine to invent.

**A fourth, found at iteration 13: the begin-announce races the board's own shutdown.** It is a
fire-and-forget POST, and `install/setup.sh` runs `kosmos stop` early, killing the board before the
bundle download. If the handshake and POST have not reached the wire by then, the one message this
card is about is lost and the phone shows the same "not answering". Usually the announce wins, since
setup.sh does a network fetch and preflight first, but nothing makes it so and nothing measures it.
Not fixed: waiting for the response would violate the governing constraint, and the failure direction
is exactly today's behaviour.

**A fifth: `DEFAULT_SECONDS` is 900, which is EXACTLY the server's 15-minute cap, so there is no
headroom and no renewal.** An install running past fifteen minutes drops the banner mid-apply and the
phone reverts to "not answering". The code says it asks for "more than any install should need",
which is not true of a value equal to the cap. Left as is because a renewal timer would add a second
moving part to the install path, but it is a real limit rather than an oversight.

**A sixth, and this one was a real defect rather than a premise, found at iteration 14: the guard
read the FILES and not the SWITCH.** `announce()` gated on `remote.enrolled()` alone, which is pure
file existence. `setOn(false)` writes `{on:false}` and calls `ensure()`; it does NOT remove the
identity, which only `forget()`/retire does. So a Mac that once enrolled in Kosmos Plus and later
switched it off reads `enrolled() === true` forever, and this route would have kept POSTing to the
PAID coordinator, carrying that Mac's client certificate, after the customer turned the feature off.
`remote.js` gates every other "is there anything live to say" question on the switch too
(`pendingDevices()` is `!settings.on || !enrolled()`, `ensure()`'s `wanted` is
`read().on && enrolled() && ...`, `status()` answers 'the switch is off'), so this was inconsistent
with the file's own convention, in the direction of sending traffic the customer had switched off.
Fixed as `if (!remote.read().on || !remote.enrolled()) return;`, the same shape as line 517.
`read()` never throws and returns `{on:false}` on ENOENT, unreadable, unparseable and non-object, so
a damaged settings file now fails CLOSED, which is the safe direction for a paid route.

⭐ **Armed, and measured both ways.** Adding the guard turned 30 of 50 arms red, because the fixture
set the identity files and never the switch: proof the gate is load-bearing rather than decorative.
Three new arms cover it (switch off is silent; the CONTROL with the switch on does send; a damaged
settings file is silent). Deleting the switch half reds exactly those and nothing else; deleting the
enrolment half reds only the enrolment arm. **The `test.afterEach` now resets the switch**, because
unlike the env vars it lives in a FILE and survived into later arms, silencing them as if the
product were broken.

## Iteration 15, and what I decided rather than fixed

**Fixed:** `seconds()` mapped every `0 < v < 1` to 0, the FINISH signal, while the comment three
lines above claimed "only 0 itself means finished". Measured: 0.5, 0.9 and 0.0001 all returned 0.
Now floored at 1, with an arm; deleting the floor reds exactly that arm. This is the negative-number
bug from the other side, in code whose comment asserted it was covered.

**Fixed:** four arms could pass or fail for scheduling reasons rather than product ones. Two counted
clears inside a fixed wall-clock window and could go red on a loaded box; they now poll for the low
side and keep a fixed window only for the high side, where load can only reduce the count. The other
two assert that NOTHING was announced, which is also what a run where no tick ever fired produces:
they now witness a tick through the fetcher. Measured with a discriminating control (a 10ms interval
produces one fetcher call in 90ms, a 60s interval produces zero, so a call is tick evidence and
startPolling does not fetch at boot), and the new assertions were shown to be able to fail.

**Fixed:** the arms are no longer order-dependent. The Plus switch lives in a FILE, so an arm run
alone under `--test-name-pattern` found remote.json missing and failed for a fixture reason;
`beforeEach` now sets it as well as `afterEach`.

**Fixed, a false claim of mine:** the error listener's owner guard is UNREACHABLE today and its
comment described the exit listener's scenario. Single-flight refuses a second attempt while
`installStarted` is true and that handler is what releases it, so `mine` is always true there.
Measured: replacing it with `true` leaves every suite green. Kept for symmetry with its armed twin
and because it costs one comparison, but the comment now says it is unarmed BY CONSTRUCTION rather
than implying coverage.

**Filed, not fixed: kosmos#2503.** The same exit-status masking that this card measured makes the
whole `if (code !== 0)` bookkeeping block dead in production: installStarted is never released,
noteAttemptEnd never records, autoFailedAt is never stamped. Pre-existing on main. It is a
behaviour change to failure bookkeeping with its own blast radius, and it is not the announce card.

**Decided, not changed: the non-2xx log line stays.** It fires only on a non-2xx answer, which
today means every answer, so it is two lines per boot per enrolled Plus Mac plus two per install
attempt. Kept because this route's own weakest premise is that it cannot be verified until it is
deployed, and a silent undeployed route is the worse failure. What would change my mind: the route
going live, after which a permanently-failing status deserves back-off rather than a line per call.

**Not covered, and out of scope: the paste-the-install-line path.** Someone who updates by running
`curl -fsSL .../setup | sh` in a terminal bypasses the board entirely, so no announce is ever sent
and the original symptom persists for that person. This card is the engine half, which can only
speak for updates the board itself starts.

Second premise, stated because it decides the boot hook: I am assuming a restarted board reaching
`startPolling()` means the update finished. A board restarted for any other reason also clears the
flag, which is the safe direction (it can only end a "back in a moment" early, never start one
falsely).
