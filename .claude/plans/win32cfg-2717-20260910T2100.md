# win32cfg-2717: stop `/api/removed` spawning a `schtasks` per removed agent per poll

Card: #2717. Branch: `win32cfg-2717`. Author: April. Date: 2026-09-10.

## The defect

`/api/removed` computes `accountFolderGone` for every removed agent, on the board's
five-second poll. Since #2614 that predicate reads a win32 configDir through
`win32job.configDirFor`, which shells out to `schtasks /Query /XML`.

On Windows that is one process spawn per removed agent, every five seconds, for as
long as a board is open. On darwin the same predicate is a cheap plist read, which is
why nobody noticed: the cost is entirely on the platform none of us develop on.

## The design

Cache the configDir **path** per task name. Do not cache existence.

The property that makes this safe, and it is the whole plan:

> The configDir path is immutable for the life of a task. Only whether that
> directory still EXISTS can change, and existence is checked live by the caller
> (`fs.existsSync` in `remove.js`) on every ask and is never cached.

So the mutable half never enters the cache, and the cached half cannot go stale while
the task exists. This is what separates it from the naive TTL cache the card warns
against: there is no staleness window to bound, because there is no staleness.

### Verified, not assumed

- `install` is the only writer of a per-agent task. `win32board.js` writes a task
  under a different name, so it cannot collide.
- `restore` re-enables through `/Change /ENABLE`. It never `/Create`s, so it cannot
  move the path.
- Neither fact was taken on faith; both were re-checked against the tree, and
  corroborated independently during review.

### Invalidation

- `forgetConfigDir(name)` at the **top of `install`**, before anything can fail
  partway.
- `forgetConfigDir(name)` in `remove`, before the `/Delete`.
- `CONFIG_DIR_CACHE.clear()` in `setRunner`, so a mocked runner can never return a
  result the real `schtasks` produced, or the reverse.

### What is cached

Only `known` answers, written through a single writer, `rememberConfigDir`.

- A `known: false` is a fact about the **moment**, not about the task. Caching it
  would turn one transient failure into a permanently disarmed safety check.
- "There is no task" (`known: true, configDir: null`) **is** cached, deliberately.
  That is precisely the case a removed agent whose task is already gone hits on every
  poll, so excluding it would have left the spawn in place for exactly the agents the
  card is about.
- The cached answer is frozen, so a caller cannot mutate a shared object and change
  what the next ask returns.

## Alternatives rejected

**A TTL cache (30s or similar).** Rejected. A TTL does not remove staleness, it
bounds it, so the design still has to argue that nothing important can change inside
the window. That argument turns out to rest on a guard in a *different file*
(`create.js` refusing to reinstall under a removed name). Explicit invalidation at the
two places that can actually move the path needs no such argument, has no window at
all, and costs one re-read after an install instead of a re-read every 30 seconds per
name forever.

**Batching the reads into one `schtasks` call.** Rejected for this card. It reduces
the constant but keeps the per-poll cost proportional to the roster, and it is a
larger change to a safety path. The cache makes the steady-state cost zero, which is
strictly better.

**Not caching at all and moving the field off the poll.** Larger blast radius, touches
the screen contract, and #2615 put the field there on purpose.

## Weakest premise in my own reasoning

**That `install` and `remove` are the only two operations that can move a task's
configDir.** I verified it by reading every caller of `win32job` on `origin/main`, but
it is a whole-tree claim, and whole-tree claims are exactly the kind that quietly stop
being true. If someone adds a third writer without a `forgetConfigDir` call, the cache
goes stale silently and the safety check is the thing that suffers.

What would change my mind: a second writer of a per-agent Scheduled Task appearing
anywhere, or `create.setAccount` growing a win32 branch (see below).

## Known residuals, stated rather than buried

- **The cache is never pruned.** Bounded by the number of distinct agents asked about
  in one process lifetime, which is bounded by the roster. A sweep was considered and
  rejected as code and a test seam in exchange for a non-problem at this scale.
- **`create.setAccount` has no win32 branch.** On Windows an account switch never
  rewrites the Scheduled Task. Pre-existing, out of scope, not carded here. It is also
  part of why the cached path cannot go stale today, which is an uncomfortable thing
  to depend on: whoever fixes that gap must add a `forgetConfigDir` call alongside
  whatever ends up rewriting the task.

## Why this card exists at all

It exists because of my own #2615, where I accepted the per-row cost as "microseconds".
That was measured on darwin's plist read and was true there. An accepted-cost note is
scoped to the platform it was measured on, and nothing carries that scope forward when
somebody later widens the call underneath it.
